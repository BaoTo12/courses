## Narrative Bridge: Engineering the Single-Table Repository

In [Lecture 04.02](./04.02-api-card-dynamodb-client-enhanced-client.md), we studied the exact SDK contracts for `DynamoDbClient`, `QueryRequest`, and conditional expressions. Now, we will implement the production Java 21 persistence layer for **CloudOrder**:

1. **`OrderEntity` (Single-Table Domain Model)**: Maps composite hash and range keys (`PK = CUST#<customerId>`, `SK = ORDER#<orderId>`) alongside overloaded secondary indexes (`GSI1PK = STATUS#<status>`, `GSI1SK = DATE#<createdAt>`).
2. **`OrderRepository` (Data Access Object)**:
   * `putOrder`: Writes domain entities to DynamoDB with TTL expiration.
   * `getOrder`: Performs strongly consistent reads using composite primary keys.
   * `updateOrderStatusWithOptimisticLock`: Atomic status update with `#version = :expectedVersion` preventing concurrent lost updates.
   * `queryOrdersByCustomer`: Efficient hash-range query using `begins_with(SK, "ORDER#")`.
   * `queryOrdersByStatus`: Cross-customer global index query on `GSI1`.
3. **`OrderStreamProcessor` (CDC Stream Consumer)**: Lambda handler reacting to real-time table modifications (`NEW_AND_OLD_IMAGES`).

### Critical Mechanical Implementation Details:
* **Reserved Keyword Aliasing**: DynamoDB reserves words like `status`, `year`, `name`, `date`. Passing `status = :status` triggers `ValidationException`. The repository maps `#status: "status"` via `expressionAttributeNames` to ensure clean parsing.
* **Optimistic Locking Expression**: `conditionExpression("attribute_exists(PK) AND #version = :expectedVersion")` guarantees that if another process updated the item between our read and write, the write aborts with `ConditionalCheckFailedException`, protecting customer payment state from overwrites.
