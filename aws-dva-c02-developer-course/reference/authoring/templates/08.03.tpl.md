## Narrative Bridge: Engineering Observability Telemetry

In [Lecture 08.02](./08.02-api-card-xray-sdk-emf-specification.md), we studied the exact specification for AWS X-Ray subsegments and CloudWatch Embedded Metric Format (EMF). Now, we build the production observability layer for **CloudOrder**:

1. **`EmfMetricsEmitter` (Embedded Metric Format Service)**:
   * Generates structured JSON log records with the `_aws` directive.
   * Keeps low-cardinality aggregation dimensions (`Service`, `Environment`, `PaymentMethod`) inside the `Dimensions` array to avoid metric explosion charges ($0.30 per custom metric).
   * Keeps high-cardinality fields (`OrderId`, `CustomerId`, `IP`) at the root JSON level, making them fully searchable in CloudWatch Logs Insights without creating individual metrics.
2. **`XRayTracingService` (Distributed Trace Propagation)**:
   * Parses incoming `X-Amzn-Trace-Id` headers.
   * Measures execution duration and records indexed **Annotations** (queriable in X-Ray search) and non-indexed **Metadata** (detailed forensic payloads).
3. **`CloudWatchLogsInsightsHelper` (Percentile & Latency Analytics)**:
   * Provides battle-tested query strings for calculating P50, P90, P95, and P99 latency, isolating Lambda cold starts (`@initDuration`), and auditing EMF logs.

### Critical Mechanical Implementation Details:
* **The High-Cardinality Trap**: In CloudWatch, every unique combination of dimension key-value pairs creates a new custom metric ($0.30/metric/month). If you include `OrderId` as a dimension for 1,000,000 orders, your monthly AWS bill will skyrocket by **$300,000**!
* **The EMF Solution**: By placing `OrderId` at the top level of the JSON payload but **excluding it from the `Dimensions` array**, CloudWatch creates zero custom metrics for the ID, while CloudWatch Logs Insights can still search, filter, and aggregate by `OrderId` in milliseconds!
