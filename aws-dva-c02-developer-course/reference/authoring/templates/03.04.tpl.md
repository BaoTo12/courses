## Narrative Bridge: Assembling the Distributed Saga

In [Lecture 03.03](./03.03-build-saga-tasks-compensating-handlers.md), we built and verified the individual Java 21 Lambda functions: `ReserveInventoryFunction`, `ProcessPaymentFunction`, and `CancelInventoryCompensateFunction`.

In a distributed microservice architecture, these functions should not invoke each other directly. Direct Lambda-to-Lambda invocation introduces tight temporal coupling, brittle error handling, and silent transaction abandonment if a container crashes midway.

Instead, we declare an **AWS Step Functions State Machine** in our SAM template. Step Functions maintains persistent state across hours or days, visualizes each execution in real time, executes automatic retries with exponential backoff, and guarantees that if payment declines, the compensating transaction runs without exception.

## Deep-Dive Architectural Breakdown

### 1. The 5 JSONPath Processing Levers
Every Step Functions state processes data through five sequential JSONPath stages:

```text
Raw State Input ──>[ InputPath ]──>[ Parameters ]──>[ Task Execution ]
                                                              │
Next State Input <──[ OutputPath ]<──[ ResultPath ]<──[ ResultSelector ]
```

1. **`InputPath`**: Filters the raw state JSON before feeding it to the task. Defaults to `$` (passes full input).
2. **`Parameters`**: Constructs a custom JSON payload sent to the Lambda handler:
   ```json
   "Parameters": {
     "FunctionName": "arn:aws:lambda:...:function:ReserveInventoryFunction",
     "Payload.$": "$"
   }
   ```
   The `.$` suffix signals to Step Functions that the value is a JSONPath expression rather than a literal string.
3. **`ResultSelector`**: Filters the raw response returned by the task (e.g. Lambda metadata wrapper containing `Payload`, `ExecutedVersion`, `StatusCode`):
   ```json
   "ResultSelector": {
     "reservationId.$": "$.Payload.reservationId",
     "status.$": "$.Payload.status"
   }
   ```
4. **`ResultPath`**: **The Most Critical Field on the DVA-C02 Exam**. Determines where the task output is placed in the overall state JSON.
   * If you set `"ResultPath": "$.inventoryResult"`, the output is inserted into the `inventoryResult` key while preserving `orderId`, `customerId`, and `amount`.
   * ⚠️ **Exam Trap**: If you set `"ResultPath": "$"`, the task output completely overwrites the root state, obliterating all original order data!
5. **`OutputPath`**: Filters the combined state before handing it off to the next state.

### 2. The Exponential Backoff Retry Pattern
```yaml
Retry:
  - ErrorEquals:
      - Lambda.ServiceException
      - Lambda.AWSLambdaException
      - States.TaskFailed
    IntervalSeconds: 2
    MaxAttempts: 2
    BackoffRate: 2.0
```

* **`IntervalSeconds: 2`**: Waits 2 seconds before the first retry attempt.
* **`BackoffRate: 2.0`**: Multiplies the wait time by 2 on each subsequent retry ($2\text{s} \to 4\text{s}$).
* **`MaxAttempts: 2`**: Retries at most twice before declaring task failure.

---

### 3. Catch Blocks & Automated Compensating Rollbacks
```yaml
Catch:
  - ErrorEquals:
      - PaymentDeclinedException
      - States.ALL
    ResultPath: "$.error"
    Next: CompensateInventory
```

* **Targeted Error Catching**: When `ProcessPaymentFunction` throws `PaymentDeclinedException`, Step Functions catches it immediately (bypassing retries, because credit card declines should never be retried automatically).
* **Safe Error Storage**: `"ResultPath": "$.error"` appends the error details (stack trace, error message) under `$.error` without destroying the order state.
* **Compensating Route**: The execution transitions to `CompensateInventory`, which calls `CancelInventoryCompensateFunction` to release the warehouse stock!
