### Question 1: Resilient Lambda Batch Failure Handling

A developer is configuring an AWS Lambda function to consume batches of up to 10 messages from an Amazon SQS standard queue. Currently, if any single message in a batch fails to process, the Lambda function throws an uncaught exception, which causes the entire batch of 10 messages to return to the queue and be reprocessed. This behavior results in successful messages being duplicated downstream.

Which set of actions must the developer take to ensure that ONLY the failed messages are retried while successful messages are permanently acknowledged and removed? (Select TWO)

- [ ] **A.** Change the SQS queue type from a Standard queue to a FIFO queue.
- [ ] **B.** Update the Lambda function's SQS EventSourceMapping to include `FunctionResponseTypes: [ "ReportBatchItemFailures" ]`.
- [ ] **C.** Modify the Lambda function to return an `SQSBatchResponse` object containing a list of `BatchItemFailure` objects populated with each failed message's `ReceiptHandle`.
- [ ] **D.** Modify the Lambda function to return an `SQSBatchResponse` object containing a list of `BatchItemFailure` objects populated with each failed message's `MessageId`.
- [ ] **E.** Call `sqsClient.deleteMessage()` manually inside the Java Lambda code for every failed message before throwing an exception.

<details>
<summary>Click to view Answer & Detailed Explanation</summary>

**Correct Answers: B and D**

**Mechanical Sympathy Breakdown:**
* **B is correct**: The Lambda Event Source Mapping must explicitly declare `FunctionResponseTypes: [ ReportBatchItemFailures ]`. Without this property on the event mapping, Lambda ignores the return value and treats any successful invocation exit as acknowledging the entire batch.
* **D is correct**: In the `SQSBatchResponse`, each `BatchItemFailure` must reference the SQS `MessageId` (via `.withItemIdentifier(message.getMessageId())`).
* **C is incorrect**: A common exam trap! Populating `itemIdentifier` with the `ReceiptHandle` will fail to match the record, causing the runtime to treat all messages as successful and delete the failing message.
* **A is incorrect**: FIFO queues do not change the partial batch failure contract; unhandled exceptions in FIFO still cause batch retries.
* **E is incorrect**: Deleting a failed message from SQS deletes it forever, preventing retry or dead-letter queue routing.

</details>

### Question 2: SNS Fan-Out to SQS Delivery Failure

An application publishes order notification events to an Amazon SNS topic. The developer creates a new Amazon SQS queue named `OrderAuditQueue` and subscribes it to the SNS topic using the AWS Management Console / CloudFormation.

When testing, the publisher receives an HTTP 200 response and a valid `MessageId` from `sns:Publish`. However, the messages never appear in `OrderAuditQueue`, and CloudWatch metric `NumberOfMessagesSent` on the SQS queue remains at zero.

What is the root cause of this failure?

- [ ] **A.** The SNS subscription has not confirmed the subscription handshake via email.
- [ ] **B.** The IAM execution role of the publishing service is missing `sqs:SendMessage` permissions.
- [ ] **C.** The SQS queue does not have an `AWS::SQS::QueuePolicy` resource policy granting the `sns.amazonaws.com` service principal permission to execute `sqs:SendMessage`.
- [ ] **D.** The SQS queue visibility timeout is configured lower than the SNS retry backoff duration.

<details>
<summary>Click to view Answer & Detailed Explanation</summary>

**Correct Answer: C**

**Mechanical Sympathy Breakdown:**
* **C is correct**: Amazon SQS queues are private by default. When an SNS topic attempts to push messages to an SQS queue, it does so as the AWS service principal `sns.amazonaws.com`. SQS rejects the delivery unless an explicit **SQS Queue Policy** grants `sns.amazonaws.com` permission to call `sqs:SendMessage` on that queue ARN, restricted by an `aws:SourceArn` condition matching the SNS topic.
* **A is incorrect**: SQS subscriptions to SNS topics within the same AWS account are confirmed automatically; no manual subscription confirmation handshake is required.
* **B is incorrect**: The publisher only publishes to SNS; it never interacts with SQS directly and therefore needs no SQS permissions.
* **D is incorrect**: Visibility timeout has zero effect on whether incoming messages can be delivered to the queue.

</details>

### Question 3: Diagnosing Duplicate Lambda Invocations

A high-volume financial billing Lambda function processes messages from an Amazon SQS queue. The Lambda function has its timeout set to **30 seconds**. The queue has its `VisibilityTimeout` set to **20 seconds**. 

During peak trading hours, downstream payment services experience latency, causing several Lambda invocations to take 25 seconds to complete. CloudWatch metrics reveal that multiple customers are being charged twice for the same transaction.

What change should the developer make to eliminate this duplicate processing?

- [ ] **A.** Decrease the Lambda function memory from 1769 MB to 512 MB to reduce CPU scheduling thrashing.
- [ ] **B.** Increase the SQS queue `VisibilityTimeout` to at least 180 seconds.
- [ ] **C.** Increase the Lambda function timeout from 30 seconds to 120 seconds.
- [ ] **D.** Configure `ReceiveMessageWaitTimeSeconds` to 0 to enable short polling.

<details>
<summary>Click to view Answer & Detailed Explanation</summary>

**Correct Answer: B**

**Mechanical Sympathy Breakdown:**
* **B is correct**: The AWS Lambda SQS Event Source Mapping invariant dictates that `VisibilityTimeout >= 6 * Function Timeout`. With a 30s function timeout, visibility timeout must be $\ge 180$ seconds. When $V = 20\text{s}$ and an execution takes 25s, the message's visibility expires at second 20 while Worker 1 is still running. SQS re-leases the message to Worker 2, causing duplicate execution.
* **A is incorrect**: Reducing memory decreases CPU and makes the function run even slower.
* **C is incorrect**: Increasing Lambda timeout without adjusting queue visibility timeout makes the race condition worse ($120\text{s} \gg 20\text{s}$).
* **D is incorrect**: Short polling does not change visibility timeout and increases billable empty requests.

</details>

### Question 4: SNS Filter Policy Syntax & Offloading Compute

A developer wants to route orders from an SNS topic to two different SQS queues:
1. `HighValueQueue`: Should receive only orders where the attribute `amount` is greater than or equal to $1000.
2. `StandardQueue`: Should receive all other orders.

Which SNS Subscription Filter Policy should be applied to the `HighValueQueue` subscription?

- [ ] **A.** `{"amount": [">= 1000"]}`
- [ ] **B.** `{"amount": [{"numeric": [">=", 1000]}]}`
- [ ] **C.** `{"amount": {"$gte": 1000}}`
- [ ] **D.** `{"amount": [{"type": "Number", "value": "1000", "operator": "gte"}]}`

<details>
<summary>Click to view Answer & Detailed Explanation</summary>

**Correct Answer: B**

**Mechanical Sympathy Breakdown:**
* **B is correct**: Amazon SNS numeric filter policies require the explicit `"numeric"` operator keyword enclosing an array with the operator string (`">="`, `">"`, `"<="`, `"<"`, `"="`) and the numeric value: `{"amount": [{"numeric": [">=", 1000]}]}`.
* **A, C, and D are incorrect**: These are invalid SNS filter syntax patterns that will fail CloudFormation/API validation.

</details>

### Question 5: Optimizing SQS FIFO Throughput Bottlenecks

A developer migrates an order queue to an Amazon SQS FIFO queue (`Orders.fifo`) to guarantee sequential processing. However, during high-volume testing, the maximum throughput of the queue plateaus at approximately 300 messages per second, even though multiple Lambda workers are available.

The publisher currently sets:
* `MessageDeduplicationId`: Hash of the order body
* `MessageGroupId`: `"ORDER_PROCESSING_GROUP"` (static constant string)

What must the developer do to scale processing throughput while maintaining order per individual customer?

- [ ] **A.** Change `MessageDeduplicationId` to a random UUID for every message.
- [ ] **B.** Set `MessageGroupId` to the individual `customerId` and enable High-Throughput FIFO on the queue (`DeduplicationScope: messageGroup`, `FifoThroughputLimit: perMessageGroupId`).
- [ ] **C.** Increase the Lambda function's `BatchSize` from 10 to 10,000.
- [ ] **D.** Set `ContentBasedDeduplication` to false.

<details>
<summary>Click to view Answer & Detailed Explanation</summary>

**Correct Answer: B**

**Mechanical Sympathy Breakdown:**
* **B is correct**: In SQS FIFO, all messages with the same `MessageGroupId` are strictly ordered and processed by a single consumer thread at a time. Using a static group ID creates a global single-threaded bottleneck. By setting `MessageGroupId = customerId`, SQS maintains strict FIFO ordering per customer, while allowing distinct customers to be processed concurrently across worker fleets. Enabling High-Throughput FIFO scales throughput up to 70,000 msgs/sec.
* **A is incorrect**: Changing deduplication ID does not affect consumer concurrency.
* **C is incorrect**: SQS maximum batch size is 10 messages (or 10,000 for standard queues with custom pollers, but Lambda SQS ESM maximum batch size is 10 for FIFO).
* **D is incorrect**: Content-based deduplication only computes hashes; it does not change concurrency.

</details>
