## Narrative Bridge: The Ghost in the Queue

In [Lecture 02.06](./02.06-live-verification-cloudwatch-sqs.md), we established CloudWatch telemetry to observe queue lag and DLQ routing. But distributed queues introduce subtle timing bugs that unit tests cannot catch.

At 09:15 AM on a Monday, the CloudOrder support desk receives an urgent escalation:  
**Customer VIP-88 was charged twice for a single order (`ORD-DUP-777`)!**

You are called in to investigate. The Java codebase has no intentional duplicate billing logic, yet CloudWatch logs reveal two distinct Lambda execution environments running the exact same order within seconds of each other.

Let's debug this root cause step by step.

## 2. Inspecting the Infrastructure Configuration

Why did SQS deliver the message to a second worker while Worker 1 was still executing?

Check the CloudFormation resource definition in `template.yaml`:

```yaml
# ❌ THE BUGGY INFRASTRUCTURE CONFIGURATION:
BillingQueue:
  Type: AWS::SQS::Queue
  Properties:
    QueueName: CloudOrderBillingQueue
    VisibilityTimeout: 10 # ⚠️ DANGEROUSLY LOW!
    ReceiveMessageWaitTimeSeconds: 20

BillingProcessorFunction:
  Type: AWS::Serverless::Function
  Properties:
    Handler: com.cloudarchitect.dvac02.consumer.BillingQueueProcessor::handleRequest
    Timeout: 30 # Function allowed to run up to 30 seconds
```

---

## 3. The Root Cause: Visibility Timeout Inversion

Here is the exact physical timeline of the race condition:

```text
Time    Worker 1 (Lambda Execution 1)       SQS Visibility Timer (10s)         Worker 2 (Lambda Execution 2)
────────────────────────────────────────────────────────────────────────────────────────────────────────────
00.0s   Receives message msg-777            Timer starts (Expires at 10.0s)    Idle
00.1s   Calls payment API (Takes 13.7s)     Message is INVISIBLE               Idle
10.0s   Still waiting for payment API...    TIMER EXPIRES!                     Idle
                                            Message becomes VISIBLE again!
10.2s   Still waiting for payment API...    Message leased to Worker 2 ──────> Receives message msg-777!
13.7s   Payment API finishes: SUCCESS!                                         Calls payment API...
13.8s   Attempts to acknowledge message                                        Still running...
24.0s   Done (Charged card #1)                                                 Payment API finishes: SUCCESS!
                                                                               Done (Charged card #2 - DUPLICATE!)
```

Because `VisibilityTimeout (10s) < Lambda Execution Duration (13.7s)`, SQS assumed Worker 1 had crashed or died, and legitimately re-leased the message to Worker 2.

---

## 4. The Two-Pronged Production Fix

### Fix 1: Enforce the $V \ge 6 \times L$ SQS Formula
In `template.yaml`, calculate the minimum safe visibility timeout based on your function timeout:
$$\text{VisibilityTimeout} = 6 \times 30\text{s} = 180\text{s}$$

```yaml
# ✅ FIXED INFRASTRUCTURE:
BillingQueue:
  Type: AWS::SQS::Queue
  Properties:
    QueueName: CloudOrderBillingQueue
    VisibilityTimeout: 180 # 6x the 30s Lambda timeout
    ReceiveMessageWaitTimeSeconds: 20
```

Now, even if a payment gateway call takes 29 seconds, the message will remain invisible for a full 180 seconds, completely eliminating this race condition.

### Fix 2: Application-Level Idempotency (Defense in Depth)
In distributed systems, SQS guarantees **at-least-once delivery**, which means network blips can occasionally cause duplicates even with proper visibility timeouts.

To guarantee that an order is never billed twice, the consumer must track processed order IDs:
* Before charging the customer, attempt a conditional write to DynamoDB:
  ```java
  // Idempotency token check
  PutItemRequest putItem = PutItemRequest.builder()
      .tableName("ProcessedOrders")
      .item(Map.of("orderId", AttributeValue.builder().s(orderId).build()))
      .conditionExpression("attribute_not_exists(orderId)")
      .build();
  ```
* If the write fails with `ConditionalCheckFailedException`, log a warning and skip payment execution!

---

## Key DVA-C02 Exam Takeaways

1. **The Invariant**: Always ensure `SQS VisibilityTimeout >= 6 * Lambda Timeout`.
2. **Symptom Recognition**: If exam questions describe messages being re-processed while the original worker is still active, the root cause is **Visibility Timeout being shorter than function execution time**.
3. **At-Least-Once Delivery**: SQS does not guarantee exactly-once delivery in Standard queues. Consumer code must always be **idempotent**.
