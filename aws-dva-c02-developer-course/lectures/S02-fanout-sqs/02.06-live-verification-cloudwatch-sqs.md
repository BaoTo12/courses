## Narrative Bridge: Moving from CLI Testing to Enterprise Observability

In [Lecture 02.05](./02.05-your-turn-cli-fanout-dlq.md), we tested message delivery and poisoned payload routing using CLI calls like `aws sqs get-queue-attributes`. But in high-throughput production systems processing thousands of orders per minute, engineers do not poll the CLI manually.

You need automated CloudWatch alarms that trigger when:
1. Messages are backing up faster than Lambda workers can process them (backlog lag).
2. A single message lands in the Dead Letter Queue (DLQ alert).
3. The queue experiences consumer starvation.

In this lecture, we examine the telemetry and CloudWatch metrics that govern production SQS queues.

---

## 1. High-Yield CloudWatch SQS Metrics

Amazon SQS publishes metrics to the `AWS/SQS` CloudWatch namespace every 5 minutes automatically, or every 1 minute if detailed monitoring is active.

| Metric Name | Unit | What It Measures Mechanically | Operational Significance |
|---|:---:|---|---|
| `ApproximateNumberOfMessagesVisible` | Count | Messages residing in the queue ready to be leased by consumers. | Backlog size. If this grows continuously, consumers are failing or under-provisioned. |
| `ApproximateNumberOfMessagesNotVisible` | Count | Messages currently leased out to consumers (in-flight within their `VisibilityTimeout`). | Active workload. Reflects current concurrency in flight. |
| `ApproximateAgeOfOldestMessage` | Seconds | The time the oldest visible message has been sitting in the queue without being processed. | **The Primary SLA Metric**. Use this rather than message count to drive Auto-Scaling! |
| `NumberOfMessagesSent` | Count | Total messages enqueued (via `SendMessage` or SNS fan-out). | Ingress throughput. |
| `NumberOfMessagesReceived` | Count | Total messages delivered to consumers via `ReceiveMessage`. | Poller activity. |
| `NumberOfMessagesDeleted` | Count | Total messages successfully processed and deleted. | Egress throughput. $\text{Sent} \approx \text{Deleted}$ indicates a healthy queue. |

```text
               ┌────────────────────────────────────────────────────────┐
               │                  Queue Message States                  │
               ├────────────────────────────┬───────────────────────────┤
  Incoming ──> │ Visible (Available)        │ In-Flight (Invisible)     │ ──> Worker Success ──> Deleted
               │ [ApproximateNumberOf-      │ [ApproximateNumberOf-     │
               │  MessagesVisible]          │  MessagesNotVisible]      │ ──> Timeout/Failure ──> Visible again
               └────────────────────────────┴───────────────────────────┘
```

## 2. Why `ApproximateAgeOfOldestMessage` Beats Message Count for Scaling

A common architecture flaw on DVA-C02 is scaling consumers based strictly on `ApproximateNumberOfMessagesVisible`.

### The Problem:
* Suppose you receive 1,000 tiny messages that take 10ms each to process (10 seconds total work). A scale-out alarm on `ApproximateNumberOfMessagesVisible > 500` will spin up excess compute unnecessarily.
* Now suppose you receive 10 large messages that take 60 seconds each to process. `ApproximateNumberOfMessagesVisible` is only 10, so no alarm fires. But those messages sit in the queue for 10 minutes, violating client SLAs!

### The Solution:
Always scale worker pools or evaluate pipeline health using **`ApproximateAgeOfOldestMessage`**:
* If `ApproximateAgeOfOldestMessage > 120` seconds, orders are sitting unprocessed for more than 2 minutes $\to$ Trigger scale-out!

## 3. Engineering Dead Letter Queue Alarms

In a resilient architecture, zero messages should ever enter the Dead Letter Queue under normal operating conditions. If a message lands in `CloudOrderBillingDLQ`, it means a customer's order failed payment processing 3 times and is now stranded.

### CloudFormation Alarm Definition:
```yaml
BillingDLQAlarm:
  Type: AWS::CloudWatch::Alarm
  Properties:
    AlarmName: CloudOrder-BillingDLQ-MessagesDetected
    AlarmDescription: "Triggers when poison pill messages are quarantined to the Billing DLQ"
    Namespace: AWS/SQS
    MetricName: ApproximateNumberOfMessagesVisible
    Dimensions:
      - Name: QueueName
        Value: !GetAtt BillingDLQ.QueueName
    Statistic: Maximum
    Period: 60 # Check every 60 seconds
    EvaluationPeriods: 1
    Threshold: 0
    ComparisonOperator: GreaterThanThreshold
    TreatMissingData: notBreaching
```

* **`Threshold: 0` & `ComparisonOperator: GreaterThanThreshold`**: Triggers whenever at least 1 message enters the DLQ.
* **`TreatMissingData: notBreaching`**: SQS does not emit metrics when the queue is completely empty. Setting `notBreaching` prevents the alarm from flapping into `INSUFFICIENT_DATA`.

## 4. Querying Lambda Partial Batch Failures via CloudWatch Logs Insights

When using `ReportBatchItemFailures`, how do you find which orders failed inside batches?

Open the CloudWatch Logs Insights console, select `/aws/lambda/BillingProcessorFunction`, and run this query:

```sql
fields @timestamp, @message
| filter @message like /\[SQS-LAMBDA\]/
| parse @message "Total failed items reported: *" as failureCount
| filter failureCount > 0
| sort @timestamp desc
| limit 25
```

### Sample Output:
```text
@timestamp               | @message
2026-09-27T08:35:10.103Z | [SQS-LAMBDA] Batch processing complete. Total failed items reported: 1
2026-09-27T08:35:10.852Z | [SQS-LAMBDA] Batch processing complete. Total failed items reported: 1
2026-09-27T08:35:11.602Z | [SQS-LAMBDA] Batch processing complete. Total failed items reported: 1
```

To pinpoint the exact order IDs that triggered exceptions:
```sql
fields @timestamp, @message
| filter @message like /Failed to process message ID/
| parse @message "Failed to process message ID *: *" as messageId, errorReason
| display @timestamp, messageId, errorReason
| sort @timestamp desc
```
