## Narrative Bridge: Proving Fan-Out and DLQ Redrive in the Terminal

In [Lecture 02.04](./02.04-provisioning-sns-sqs-sam-template.md), we studied the declarative SAM template containing our SNS topic, SQS queues, filter policies, DLQ redrive configurations, and Lambda batch mappings.

Now it's time for you to take the wheel. In this hands-on exercise, you will:
1. Build and deploy the serverless stack to your AWS environment.
2. Publish events via the `aws sns publish` CLI with message attributes to verify that SNS filter policies deliver standard orders only to `BillingQueue`, while high-priority orders fan out to both `BillingQueue` and `PriorityQueue`.
3. Inject a poisoned payload and observe SQS redrive mechanics move the poisoned message to `BillingDLQ` after exactly 3 retries (`maxReceiveCount: 3`).

## Exercise 1: Build & Deploy the Fan-Out Stack

From your terminal, navigate to the Module 02 reference directory:

```bash
cd reference/cloudorder/backend/module-02-fanout-queues
mvn clean package -DskipTests
sam build
sam deploy --guided
```

When prompted by the SAM CLI:
* **Stack Name**: `cloudorder-module-02`
* **AWS Region**: `us-east-1` (or your preferred region)
* **Confirm changes before deploy**: `N`
* **Allow SAM CLI IAM role creation**: `Y`

Once deployed, note the outputs:
* `OrderEventsTopicArn`
* `BillingQueueUrl`
* `PriorityQueueUrl`
* `BillingDLQUrl`

## Exercise 2: Test SNS Attribute-Based Fan-Out

### Test Case A: Standard Priority Order
Publish a standard priority order using the AWS CLI:

```bash
aws sns publish \
  --topic-arn "<OrderEventsTopicArn>" \
  --message '{"orderId":"ORD-STD-001","customerId":"cust-1@example.com","amount":35.50,"items":["BOOK-01"]}' \
  --message-attributes '{
    "priority": {"DataType": "String", "StringValue": "STANDARD"},
    "eventType": {"DataType": "String", "StringValue": "ORDER_CREATED"}
  }'
```

**Verification Check**:
1. Inspect the message counts on both queues:
   ```bash
   aws sqs get-queue-attributes \
     --queue-url "<BillingQueueUrl>" \
     --attribute-names ApproximateNumberOfMessages
   
   aws sqs get-queue-attributes \
     --queue-url "<PriorityQueueUrl>" \
     --attribute-names ApproximateNumberOfMessages
   ```
2. **Expected Behavior**: `PriorityQueue` receives **0 messages** because its subscription requires `priority: ["HIGH"]`.

### Test Case B: High Priority Order
Publish a high-priority order:

```bash
aws sns publish \
  --topic-arn "<OrderEventsTopicArn>" \
  --message '{"orderId":"ORD-HIGH-999","customerId":"vip@example.com","amount":1299.00,"items":["LAPTOP-PRO"]}' \
  --message-attributes '{
    "priority": {"DataType": "String", "StringValue": "HIGH"},
    "eventType": {"DataType": "String", "StringValue": "ORDER_CREATED"}
  }'
```

**Verification Check**:
* Check `PriorityQueue`. A message should immediately appear!

## Exercise 3: Simulating a Poison Pill & DLQ Redrive

Now let's test our system's fault-tolerance. Send a poisoned payload directly to `BillingQueue` simulating a corrupted message that cannot be parsed by Jackson:

```bash
aws sqs send-message \
  --queue-url "<BillingQueueUrl>" \
  --message-body '{"orderId":"POISON-PILL","malformedJson":::'
```

### Observe Lambda Logs in Real Time:
Stream CloudWatch logs for the `BillingProcessorFunction`:

```bash
sam logs -n BillingProcessorFunction --stack-name cloudorder-module-02 --tail
```

**What to Observe**:
1. **First Execution**: The Lambda function receives the batch, fails on the poison pill, logs an error, and returns the message ID in `batchItemFailures`.
2. **Retries**: SQS resets the visibility timeout to 0. The poller retries the message. You will observe 3 failed executions in the logs.
3. **Quarantine to DLQ**: After the 3rd failure (`ApproximateReceiveCount = 3`), SQS transfers the message to `BillingDLQ`.

### Verify the DLQ:
Query `BillingDLQ` to confirm the poisoned message was isolated:

```bash
aws sqs receive-message \
  --queue-url "<BillingDLQUrl>" \
  --attribute-names All
```

You should see your malformed payload safely trapped in the dead letter queue without taking down the production processing pipeline!
