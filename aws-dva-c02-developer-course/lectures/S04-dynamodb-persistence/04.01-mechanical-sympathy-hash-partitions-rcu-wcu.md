## Narrative Bridge: Breaking the Relational Paradigm

In [Section 03](../S03-step-functions/README.md), we built a stateful checkout saga to coordinate order validation and payment settlement.

When developers coming from relational databases (PostgreSQL, MySQL) design storage for e-commerce, their first instinct is normalization:
* Create a `customers` table.
* Create an `orders` table with a foreign key `customer_id`.
* Create an `order_items` table with foreign key `order_id`.

To view an order, the application executes multi-table SQL joins (`SELECT * FROM orders JOIN order_items ... JOIN customers ...`).

At 100 requests per second, SQL joins work fine. At **50,000 requests per second**, multi-table joins collapse. Relational database engines must read indices from disk, lock rows, join memory structures, and saturate CPU cores.

Amazon DynamoDB is designed for **predictable single-digit millisecond latency at any scale**, whether you store 10 megabytes or 100 terabytes. To achieve this, DynamoDB abandons joins completely and enforces **Physical Partitioning** and **Single-Table Design**.

---

## 1. Physical Storage Architecture & The Partition Engine

Under the hood, DynamoDB stores data on a fleet of SSD-backed storage servers divided into physical **Partitions**:

```text
                  Incoming Write: PK = "CUST#101", SK = "ORDER#5001"
                                           │
                                           ▼
                                ┌─────────────────────┐
                                │ Internal MD5 Hasher │
                                └──────────┬──────────┘
                                           │
                        ┌──────────────────┴──────────────────┐
                        ▼                                     ▼
             ┌─────────────────────┐               ┌─────────────────────┐
             │     Partition 1     │               │     Partition 2     │
             │   (Hash: 0000-7FFF) │               │   (Hash: 8000-FFFF) │
             ├─────────────────────┤               ├─────────────────────┤
             │ PK: CUST#101        │               │ PK: CUST#804        │
             │  ├── SK: METADATA   │               │  └── SK: ORDER#991  │
             │  ├── SK: ORDER#5001 │               └─────────────────────┘
             │  └── SK: ORDER#5002 │
             └─────────────────────┘
```

### The Hard Physical Invariants of a DynamoDB Partition:
A single DynamoDB physical partition has strict physical hardware boundaries:
* **Maximum Storage Capacity**: **10 GB** of data.
* **Maximum Write Throughput**: **1,000 Write Capacity Units (WCU)** per second.
* **Maximum Read Throughput**: **3,000 Read Capacity Units (RCU)** per second.

When a table exceeds 10 GB of data, or when total provisioned throughput exceeds 1,000 WCU or 3,000 RCU, DynamoDB **splits the partition in two**.

### The Hot Partition Bottleneck:
If you provision 10,000 WCUs across a table that has grown to 10 physical partitions, DynamoDB allocates:
$$\frac{10,000\text{ WCU}}{10\text{ partitions}} = 1,000\text{ WCU per partition}$$
If your application uses a low-cardinality partition key (e.g. `PK = "ACTIVE_ORDERS"` or `PK = countryCode`), 95% of traffic hits a **single partition**. That partition caps out at **1,000 WCUs**, triggering `ProvisionedThroughputExceededException` even though 9,000 WCUs of table capacity sit idle!

> [!IMPORTANT]
> **Partition Key Rule**: Always use a high-cardinality attribute for the Partition Key (`customerId`, `orderId`, `deviceUuid`) to evenly distribute reads and writes across physical storage nodes.

## 2. Capacity Unit Mathematics (The DVA-C02 Exam Invariants)

On the DVA-C02 exam, you will be given data sizes and access patterns and asked to calculate the exact provisioned capacity units required.

### Write Capacity Units (WCU)
* **Base Unit**: **1 KB** per write.
* **Standard Write Formula**:
  $$\text{WCU per write} = \lceil \text{Item Size in KB} \rceil$$
* **Transactional Write Formula (`TransactWriteItems`)**:
  $$\text{WCU per transactional write} = 2 \times \lceil \text{Item Size in KB} \rceil$$

#### WCU Calculation Example:
You write 100 items per second. Each item is **2.3 KB** in size.
1. Round 2.3 KB up to the next 1 KB increment $\to$ **3 KB**.
2. Standard writes: $3\text{ KB} \times 1\text{ WCU} \times 100\text{ writes/sec} = \mathbf{300\text{ WCU}}$.
3. If performed as transactions (`TransactWriteItems`): $3 \times 2 \times 100 = \mathbf{600\text{ WCU}}$.

---

### Read Capacity Units (RCU)
* **Base Unit**: **4 KB** per read.
* **Strongly Consistent Read**: Guarantees the latest write.
  $$\text{RCU per read} = \lceil \frac{\text{Item Size in KB}}{4\text{ KB}} \rceil \times 1$$
* **Eventually Consistent Read** (Default): Reads from any replica node; saves 50% cost!
  $$\text{RCU per read} = \lceil \frac{\text{Item Size in KB}}{4\text{ KB}} \rceil \times 0.5$$
* **Transactional Read (`TransactGetItems`)**:
  $$\text{RCU per transactional read} = \lceil \frac{\text{Item Size in KB}}{4\text{ KB}} \rceil \times 2$$

#### RCU Calculation Example:
You read 200 items per second. Each item is **6.5 KB** in size.
1. Divide by 4 KB and round up: $\lceil \frac{6.5}{4} \rceil = \lceil 1.625 \rceil = \mathbf{2\text{ read blocks (8 KB)}}$.
2. **Strongly Consistent**: $2\text{ blocks} \times 1\text{ RCU} \times 200\text{ reads/sec} = \mathbf{400\text{ RCU}}$.
3. **Eventually Consistent**: $2\text{ blocks} \times 0.5\text{ RCU} \times 200\text{ reads/sec} = \mathbf{200\text{ RCU}}$.
4. **Transactional**: $2\text{ blocks} \times 2\text{ RCU} \times 200\text{ reads/sec} = \mathbf{800\text{ RCU}}$.

## 3. The Single-Table Design Philosophy

Instead of normalizing data into separate tables, **Single-Table Design** pre-joins related entities by storing them under the same Partition Key with structured Sort Keys.

### CloudOrder Single-Table Layout:
| `PK` (Hash Key) | `SK` (Range Key) | `GSI1PK` | `GSI1SK` | Entity Type | Data Attributes |
|---|---|---|---|:---:|---|
| `CUST#101` | `METADATA` | `TIER#GOLD` | `DATE#2026-01-01` | Customer | `name`, `email`, `tier` |
| `CUST#101` | `ORDER#5001` | `STATUS#PENDING` | `DATE#2026-09-27` | Order | `amount: 149.99`, `version: 1` |
| `CUST#101` | `ORDER#5002` | `STATUS#COMPLETED` | `DATE#2026-09-26` | Order | `amount: 45.00`, `version: 3` |
| `CUST#101` | `ORDER#5001#ITEM#A` | - | - | OrderItem | `qty: 2`, `price: 49.99` |

### Why Single-Table Beats Relational at Scale:
1. **Zero SQL Joins**: To fetch Customer 101, their profile, and all their orders in one network call:
   ```java
   KeyConditionExpression: "PK = :pk AND begins_with(SK, :skPrefix)"
   // :pk = "CUST#101", :skPrefix = "ORDER#"
   ```
   DynamoDB reads contiguous SSD sectors on a single partition and returns the customer and all order rows in **less than 4 milliseconds**!
2. **Atomic Batch Transactions**: All records for a customer share the same partition, making multi-item transactions lightning fast with zero distributed cross-node coordination.

## 4. Hard Constraints: The 400 KB Item Limit

Every DynamoDB item has a hard maximum size limit of **400 KB** (including all attribute names, values, and binary blobs).

> [!WARNING]
> Never store large binary payloads (PDF invoices, product images, raw video frames) inside DynamoDB items.  
> **The Production Architecture Pattern**: Store binary assets in Amazon S3, and store only the resulting `s3Key` string inside the DynamoDB item! (We build this in Section 05).
