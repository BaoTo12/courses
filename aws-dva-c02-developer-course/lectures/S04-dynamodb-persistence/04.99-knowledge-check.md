### Question 1: Exact RCU & WCU Capacity Calculations

An enterprise banking application writes **80 items per second** to an Amazon DynamoDB table. Each item is **3.2 KB** in size. The application also executes **150 eventually consistent reads per second**, where each read item is **7.5 KB** in size.

What is the minimum provisioned capacity (WCU and RCU) required to support this workload without throttling?

- [ ] **A.** 240 WCU and 150 RCU
- [ ] **B.** 320 WCU and 150 RCU
- [ ] **C.** 320 WCU and 300 RCU
- [ ] **D.** 80 WCU and 75 RCU

<details>
<summary>Click to view Answer & Detailed Explanation</summary>

**Correct Answer: B**

**Mechanical Sympathy Breakdown:**
* **Write Capacity Units (WCU)**:
  * Base block: 1 KB.
  * Item size: 3.2 KB $\to$ round up to nearest 1 KB = **4 KB**.
  * Each write requires 4 WCUs.
  * Rate: 80 writes/sec.
  * Total WCUs = $80 \times 4 = \mathbf{320\text{ WCU}}$.
* **Read Capacity Units (RCU)**:
  * Base block: 4 KB.
  * Item size: 7.5 KB $\to$ round up to nearest 4 KB = **8 KB (2 blocks of 4 KB)**.
  * Eventually consistent reads cost **0.5 RCU per 4 KB block**.
  * Each read requires: $2\text{ blocks} \times 0.5 = \mathbf{1.0\text{ RCU per read}}$.
  * Rate: 150 reads/sec.
  * Total RCUs = $150 \times 1.0 = \mathbf{150\text{ RCU}}$.
* **Result**: **320 WCU and 150 RCU**.

</details>

### Question 2: Resolving Base Table Write Throttling

A developer maintains an orders table named `OrdersTable` with provisioned capacity set to **2,000 WCU** and **2,000 RCU**. A Global Secondary Index named `CustomerStatusIndex` is attached with provisioned capacity set to **50 WCU**.

During peak traffic, CloudWatch metrics show that the base table is writing at only **400 writes/sec** (well below the 2,000 WCU provisioned limit). However, clients are receiving numerous `ProvisionedThroughputExceededException` errors when executing `putItem` operations against the base table.

What is the root cause and the required resolution?

- [ ] **A.** The partition key on the base table has skewed distribution; enable DynamoDB Accelerator (DAX) to resolve write throttling.
- [ ] **B.** The Global Secondary Index `CustomerStatusIndex` is experiencing write throttling, which is synchronously throttling writes to the base table. Increase the provisioned write capacity on the GSI.
- [ ] **C.** The client is calling `putItem` without setting `ConsistentRead: false`.
- [ ] **D.** The items written exceed 400 KB in size; compress the items before writing.

<details>
<summary>Click to view Answer & Detailed Explanation</summary>

**Correct Answer: B**

**Mechanical Sympathy Breakdown:**
* **B is correct**: In Amazon DynamoDB, when an item written to a base table also updates an item projected into a Global Secondary Index, the write consumes capacity from **both** the base table and the GSI. If the GSI runs out of write capacity (50 WCU), DynamoDB **throttles writes to the base table**, even if the base table has 1,600 unused WCUs! To fix this, GSI write capacity must be scaled up to match or exceed the base table write rate.
* **A is incorrect**: DAX is a read cache; it does not increase write capacity or prevent write throttling.
* **C is incorrect**: `ConsistentRead` is a parameter for read operations (`GetItem`/`Query`), not `PutItem`.
* **D is incorrect**: Exceeding 400 KB throws `ValidationException: Item size has exceeded the acceptable limit`, not `ProvisionedThroughputExceededException`.

</details>

### Question 3: Preventing Lost Updates with Optimistic Locking

Two microservices concurrently read and update the same order status in Amazon DynamoDB. Microservice A reads version 3 of order `ORD-101`. Microservice B reads version 3 of order `ORD-101` one millisecond later. Microservice A successfully updates the order status to `PROCESSING` and increments version to 4. 

Microservice B now attempts to update the status to `CANCELLED`.

Which update expression and condition expression should the developer use to ensure that Microservice B's update is safely rejected rather than overwriting Microservice A's changes?

- [ ] **A.** UpdateExpression: `SET status = :s, version = version + 1`, ConditionExpression: `attribute_exists(orderId)`
- [ ] **B.** UpdateExpression: `SET #s = :s, #v = :newV`, ConditionExpression: `attribute_exists(PK) AND #v = :expectedV`
- [ ] **C.** UpdateExpression: `SET #s = :s`, ConditionExpression: `status = :oldStatus`
- [ ] **D.** Call `dynamoDbClient.transactGetItems()` before every write.

<details>
<summary>Click to view Answer & Detailed Explanation</summary>

**Correct Answer: B**

**Mechanical Sympathy Breakdown:**
* **B is correct**: The classic optimistic locking pattern uses a version counter attribute (`version`). The `ConditionExpression` asserts that the item's current version in the database matches the version read by the client: `#v = :expectedV` (where `:expectedV` is 3). Because Microservice A already incremented `#v` to 4, Microservice B's condition evaluates to false, immediately throwing `ConditionalCheckFailedException` and protecting the state. Attribute names are aliased (`#s`, `#v`) to avoid reserved keyword collisions.
* **A is incorrect**: `attribute_exists(orderId)` only checks that the item exists, allowing Microservice B to overwrite version 4.
* **C is incorrect**: Checking status alone does not prevent race conditions if multiple updates transition between matching statuses.
* **D is incorrect**: `TransactGetItems` is read-only and does not lock the item for subsequent writes.

</details>

### Question 4: Shard Stalling in DynamoDB Streams

An AWS Lambda function is configured to process change data records from a DynamoDB Stream with `BatchSize: 100`. During a schema migration, an item with an unexpected field format is written to the table. When the Lambda function attempts to parse the batch containing this item, an unhandled `JsonParseException` is thrown.

The developer notices that stream processing has completely halted, and the `IteratorAge` metric in CloudWatch is steadily increasing toward 24 hours.

Which EventSourceMapping configuration change will automatically resolve this blockage without manual intervention?

- [ ] **A.** Set `StartingPosition: LATEST` on the EventSourceMapping.
- [ ] **B.** Set `BisectBatchOnFunctionError: true` and configure an `OnFailure` destination to a Dead Letter Queue (DLQ).
- [ ] **C.** Increase the Lambda function memory from 512 MB to 1,769 MB.
- [ ] **D.** Enable DynamoDB Accelerator (DAX) on the stream reader.

<details>
<summary>Click to view Answer & Detailed Explanation</summary>

**Correct Answer: B**

**Mechanical Sympathy Breakdown:**
* **B is correct**: In DynamoDB Streams, records within a shard are strictly ordered. If a batch fails, Lambda retries the same batch by default until the stream data expires (24 hours), blocking all subsequent records in that shard. By enabling `BisectBatchOnFunctionError: true`, Lambda automatically splits the failing batch in half upon failure and retries each half separately. It recursively isolates the single poisoned record, sends it to the `OnFailure` destination (DLQ), and allows the remaining 99 healthy records to continue processing without stalling the shard!
* **A is incorrect**: Changing `StartingPosition` to `LATEST` only applies to newly created EventSourceMappings, not active running streams.
* **C is incorrect**: Memory changes do not resolve JSON parsing exceptions.
* **D is incorrect**: DAX caches DynamoDB table reads, not stream shards.

</details>

### Question 5: Resolving Reserved Keyword Syntax Errors

A developer is writing a DynamoDB `Query` operation to retrieve items from `CloudOrderTable`:

```java
QueryRequest request = QueryRequest.builder()
    .tableName("CloudOrderTable")
    .keyConditionExpression("PK = :pk")
    .filterExpression("year >= :y AND status = :s")
    .expressionAttributeValues(Map.of(
        ":pk", AttributeValue.fromS("CUST#101"),
        ":y", AttributeValue.fromN("2026"),
        ":s", AttributeValue.fromS("CONFIRMED")
    ))
    .build();
```

When executing this query, DynamoDB returns:
`ValidationException: Invalid FilterExpression: Syntax error; token : "year", near type: RESERVED_KEYWORD`

What change must the developer make to execute this query successfully?

- [ ] **A.** Enclose `year` and `status` in single quotes: `'year' >= :y AND 'status' = :s`.
- [ ] **B.** Use `ExpressionAttributeNames` to alias `#yr: "year"` and `#st: "status"`, and update the expression to `#yr >= :y AND #st = :s`.
- [ ] **C.** Convert the `Query` operation to a `Scan` operation.
- [ ] **D.** Rename the table attributes in DynamoDB to uppercase `YEAR` and `STATUS`.

<details>
<summary>Click to view Answer & Detailed Explanation</summary>

**Correct Answer: B**

**Mechanical Sympathy Breakdown:**
* **B is correct**: Both `year` and `status` are official DynamoDB reserved keywords. To use them in `FilterExpression`, `KeyConditionExpression`, or `UpdateExpression`, you must map them to placeholders in `ExpressionAttributeNames` (e.g. `"#yr": "year"`, `"#st": "status"`).
* **A is incorrect**: DynamoDB does not support quote-escaping for identifiers; it will trigger another syntax error.
* **C is incorrect**: `Scan` uses the exact same expression parser and will fail with the identical `ValidationException`.
* **D is incorrect**: DynamoDB attribute names are case-sensitive, but the reserved keyword list is case-insensitive.

</details>
