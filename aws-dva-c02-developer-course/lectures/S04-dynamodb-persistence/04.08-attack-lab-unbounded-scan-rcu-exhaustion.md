## Narrative Bridge: The Single API Call that Can Kill a Table

In [Lecture 04.07](./04.07-debug-reserved-keyword-collision-and-hot-partition.md), we diagnosed syntax and partition skew bugs. Now, we enter the attack lab to analyze how a seemingly innocent API operation—`Scan`—can be weaponized to cause a complete platform outage.

In relational databases, developers are accustomed to running `SELECT * FROM orders WHERE status = 'PENDING'` without an index. The query might take 2 seconds, but the database survives.

In Amazon DynamoDB, executing an unbounded `Scan` against a large production table causes **instant capacity depletion, massive throttling cascades, and thousand-dollar bill shocks**.

Let's analyze the mechanics of a Scan DoS and compare it to an efficient single-table `Query`.

---

## 1. The Anatomy of a Table Scan

A `Scan` operation reads **every single item in the entire table**, across all SSD partitions, from beginning to end.

```text
Table: 10 GB of data (10,485,760 KB)
Scan Operation:
Partition 1 (Read 1.25 GB) ──> Evaluated ──> Filter applied
Partition 2 (Read 1.25 GB) ──> Evaluated ──> Filter applied
...
Partition 8 (Read 1.25 GB) ──> Evaluated ──> Filter applied
Total Data Read from SSD: 10 GB!
```

### The Capacity Destruction Math:
Suppose your table holds 10 GB of order records and you have provisioned **500 RCU**:
1. 10 GB = 10,485,760 KB.
2. Read Capacity Units are metered in 4 KB blocks:
   $$\text{Total RCUs Consumed by ONE Scan} = \frac{10,485,760\text{ KB}}{4\text{ KB}} \times 0.5\text{ (eventual)} = \mathbf{1,310,720\text{ RCUs}}$$
3. If your table has 500 RCUs provisioned:
   $$\text{Throttling Window} = \frac{1,310,720\text{ RCUs}}{500\text{ RCU/sec}} = 2,621\text{ seconds} \approx \mathbf{43.6\text{ minutes!}}$$

A **single HTTP request** triggering a table scan consumes enough read capacity to **throttle the entire production table for 43 minutes**. Every paying customer attempting to view their order or check out receives `ProvisionedThroughputExceededException`!

## 2. Scan vs. Query: The Benchmark Comparison

| Dimension | `dynamoDbClient.scan()` | `dynamoDbClient.query()` |
|---|---|---|
| **Access Pattern** | Reads all physical partitions. | Reads **only the target partition key**. |
| **Data Evaluated** | Scans 100% of items in table. | Scans **only matching sort key items**. |
| **RCU Consumption** | Proportional to **table size** (unbounded growth!). | Proportional to **matching records returned** ($O(1)$). |
| **Latency** | Multiple seconds to minutes. | **3 to 8 milliseconds**. |
| **Production Suitability** | **Anti-pattern**. Strictly prohibited in customer-facing APIs. | **Standard Practice**. The foundational access method of DynamoDB. |

## 3. The FilterExpression Trap (Why Filters Don't Save You!)

A common developer mistake on DVA-C02 is believing that adding a `FilterExpression` to a `Scan` reduces RCU cost:

```java
// ❌ FALSE SENSE OF SECURITY:
ScanRequest request = ScanRequest.builder()
    .tableName("CloudOrderTable")
    .filterExpression("#s = :status") // Still reads 100% of the table!
    .expressionAttributeNames(Map.of("#s", "status"))
    .expressionAttributeValues(Map.of(":status", AttributeValue.fromS("PENDING")))
    .build();
```

### Why This Fails:
* DynamoDB reads the **entire 10 GB** from disk into memory first (charging you the full 1,310,720 RCUs).
* Then, it discards items that don't match `status = "PENDING"`.
* Finally, it returns the remaining 5 items to you.
* **Result**: You got 5 items, but you were billed for 10 GB of reads!

## 4. The Production Defenses

### Defense 1: Enforce Global Secondary Indexes for Ad-Hoc Access
Instead of scanning for `status = "PENDING"`, use our `GSI1` index:
```java
// ✅ EFFICIENT GSI QUERY:
QueryRequest request = QueryRequest.builder()
    .tableName("CloudOrderTable")
    .indexName("GSI1")
    .keyConditionExpression("GSI1PK = :status")
    .expressionAttributeValues(Map.of(":status", AttributeValue.fromS("STATUS#PENDING")))
    .build();
```
* **Data Read**: Only the 5 matching items.
* **RCUs Consumed**: **2.5 RCU** (instead of 1,310,720 RCU!).
* **Latency**: 4ms.

### Defense 2: Rate-Limited Parallel Scans for Offline Batch Jobs
If an offline batch job genuinely requires scanning the full dataset (e.g. nightly analytical dump):
1. **Never run scans against the production operational table**: Stream updates via DynamoDB Streams to Amazon S3 (Data Lake) or Amazon OpenSearch Service.
2. Use **Parallel Scan** with `Segment` and `TotalSegments` to distribute load across worker threads:
   ```java
   ScanRequest segmentScan = ScanRequest.builder()
       .tableName("CloudOrderTable")
       .segment(0)
       .totalSegments(4) // 4 concurrent worker threads
       .limit(100)       // Enforce page limits
       .build();
   ```
