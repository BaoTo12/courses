## Narrative Bridge: Two Classical DynamoDB Production Bugs

In [Lecture 04.06](./04.06-live-verification-cloudwatch-rcu-wcu-throttling.md), we analyzed capacity monitoring and GSI throttling risks.

Now, we enter the debug lab to confront two bugs that strike nearly every cloud developer:
1. **The Reserved Keyword Syntax Crash**: A query crashes immediately before touching data because an attribute name conflicts with DynamoDB's internal SQL-like grammar.
2. **The Hot Partition Throttling Mystery**: A table provisioned with 10,000 WCUs begins throwing `ProvisionedThroughputExceededException` when traffic is barely at 1,100 writes/sec!

Let's debug both defects.

---

## 1. Defect 1: The Reserved Keyword Crash

A developer writes an update expression to mark an order as shipped:

```java
// ❌ THE DEFECTIVE UPDATE REQUEST:
UpdateItemRequest request = UpdateItemRequest.builder()
    .tableName("CloudOrderTable")
    .key(key)
    .updateExpression("SET status = :s") // ⚠️ 'status' is a reserved keyword!
    .expressionAttributeValues(Map.of(":s", AttributeValue.fromS("SHIPPED")))
    .build();

dynamoDbClient.updateItem(request);
```

### The Error:
```text
software.amazon.awssdk.services.dynamodb.model.ValidationException: 
Invalid UpdateExpression: Syntax error; token : "status", near type: RESERVED_KEYWORD
```

### Root Cause:
DynamoDB maintains a list of several hundred **reserved words** that cannot be used as naked identifiers in expressions (including `status`, `year`, `name`, `date`, `percent`, `value`, `connection`). When the query parser encounters `SET status`, it assumes `status` is a grammar keyword and throws a syntax validation failure.

### The Fix: Expression Attribute Names
You must alias reserved attribute names with an expression placeholder beginning with `#`:

```java
// ✅ THE FIXED UPDATE REQUEST:
UpdateItemRequest request = UpdateItemRequest.builder()
    .tableName("CloudOrderTable")
    .key(key)
    .updateExpression("SET #orderStatus = :s") // Alias used here
    .expressionAttributeNames(Map.of(
        "#orderStatus", "status" // Map alias to the physical attribute name
    ))
    .expressionAttributeValues(Map.of(
        ":s", AttributeValue.fromS("SHIPPED")
    ))
    .build();

dynamoDbClient.updateItem(request);
```

## 2. Defect 2: The Hot Partition Throttling Mystery

### The Scenario:
* Table Capacity: Provisioned at **10,000 WCU**.
* Table Size: 80 GB of historical order data (spread across **8 physical partitions**).
* Peak Ingress Traffic: **1,200 writes per second**.
* Symptom: Application logs are inundated with:
  ```text
  software.amazon.awssdk.services.dynamodb.model.ProvisionedThroughputExceededException: 
  The level of configured provisioned throughput for the table was exceeded.
  ```

Why is DynamoDB throttling at 1,200 writes/sec when the table is provisioned for 10,000 writes/sec?

---

### The Root Cause: Partition Key Skew
Inspect the partition key design used by the ingest team:
```text
Item 1: PK = "2026-09-27", SK = "ORD-001"
Item 2: PK = "2026-09-27", SK = "ORD-002"
Item 3: PK = "2026-09-27", SK = "ORD-003"
```
The developer chose the **current date** as the Partition Key so they could easily query today's orders!

### The Physical Partition Math:
1. The table has 8 partitions. Total capacity is divided evenly:
   $$\text{Capacity per partition} = \frac{10,000\text{ WCU}}{8\text{ partitions}} = 1,250\text{ WCU}$$
2. Every order created today has `PK = "2026-09-27"`.
3. The internal MD5 hash of `"2026-09-27"` maps to **Partition 3**.
4. 100% of all 1,200 writes hit **Partition 3 alone**!
5. As traffic climbs slightly above 1,250 writes/sec, Partition 3 exceeds its physical quota and begins dropping requests, while Partitions 1, 2, 4, 5, 6, 7, and 8 sit completely idle!

```text
Partition 1 (Idle):   0 / 1,250 WCU
Partition 2 (Idle):   0 / 1,250 WCU
Partition 3 (HOT!):   1,250 / 1,250 WCU ──> ⚠️ THROTTLING EXCEEDED!
Partition 4 (Idle):   0 / 1,250 WCU
...
Partition 8 (Idle):   0 / 1,250 WCU
```

---

### The Production Fixes

#### Fix Strategy 1: High-Cardinality Partition Keys (Standard Single-Table)
Set `PK = "CUST#" + customerId` or `PK = "ORDER#" + orderId`.  
Because each customer ID produces a distinct MD5 hash, writes are distributed uniformly across all 8 SSD partitions.

#### Fix Strategy 2: Partition Sharding / Salting (For Heavy Aggregations)
If business logic strictly requires partitioning by date, append a random salt or shard suffix from a fixed range (e.g. 1 to 10):
```java
int shardId = ThreadLocalRandom.current().nextInt(1, 10);
String pk = "DATE#" + todayIsoString + "#SHARD#" + shardId;
```
Now writes are scattered evenly across 10 partitions. To query the day's orders, the application issues 10 parallel `Query` requests across each shard key and merges the results in memory.
