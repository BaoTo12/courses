In this lecture, we explore DynamoDB telemetry in CloudWatch and learn how to extract wire-level capacity consumption directly in our application logs.

## 1. Inspecting Live Capacity Consumption with `ReturnConsumedCapacity`

By default, DynamoDB API calls do not return consumed capacity in responses. To monitor costs in your application code or during performance benchmarking, pass `ReturnConsumedCapacity`:

```java
GetItemRequest request = GetItemRequest.builder()
    .tableName("CloudOrderTable")
    .key(key)
    .consistentRead(true)
    .returnConsumedCapacity(ReturnConsumedCapacity.TOTAL) // ⚡ Requests capacity metadata
    .build();

GetItemResponse response = dynamoDbClient.getItem(request);

ConsumedCapacity capacity = response.consumedCapacity();
System.out.println("Consumed RCUs: " + capacity.capacityUnits());
```

### CLI Verification:
```bash
aws dynamodb get-item \
  --table-name CloudOrderTable \
  --key '{"PK": {"S": "CUST#cust-101"}, "SK": {"S": "ORDER#ord-5001"}}' \
  --consistent-read \
  --return-consumed-capacity TOTAL
```

Output:
```json
{
    "Item": { ... },
    "ConsumedCapacity": {
        "TableName": "CloudOrderTable",
        "CapacityUnits": 1.0
    }
}
```
*Result*: Exactly **1.0 RCU** consumed for an item under 4 KB with strongly consistent read.

## 2. High-Yield CloudWatch DynamoDB Metrics

DynamoDB emits operational telemetry to the `AWS/DynamoDB` CloudWatch namespace:

| Metric Name | Dimension | Operational Meaning |
|---|---|---|
| `ConsumedReadCapacityUnits` | TableName | Total RCUs consumed across the table. |
| `ConsumedWriteCapacityUnits` | TableName | Total WCUs consumed across the table. |
| `ReadThrottleEvents` | TableName | Number of read requests rejected due to RCU exhaustion (`ProvisionedThroughputExceededException`). |
| `WriteThrottleEvents` | TableName | Number of write requests rejected due to WCU exhaustion. |
| `UserErrors` | TableName | HTTP 400 errors (e.g. `ConditionalCheckFailedException`, `ValidationException`). |
| `SystemErrors` | TableName | Internal 500 errors on DynamoDB SSD storage fleet. |

## 3. The Fatal GSI Write Throttling Trap (Crucial DVA-C02 Exam Trap!)

Consider this common exam scenario:
* Your base table `CloudOrderTable` is provisioned with **1,000 WCU**.
* Your Global Secondary Index `GSI1` is provisioned with **10 WCU**.
* You write an item to `CloudOrderTable` that contains `GSI1PK` and `GSI1SK`.

### What happens?
When an item is written to the base table, DynamoDB synchronously propagates the update to all GSIs that project that item.  
If `GSI1` runs out of write capacity, **DynamoDB throttles and rejects the write to the BASE TABLE!**

> [!CAUTION]
> **The GSI Bottleneck Invariant**:
> **A throttled GSI throttles writes to the entire base table!**  
> If an exam question describes write throttles on a base table while `ConsumedWriteCapacityUnits` on the base table is well below provisioned capacity, the root cause is **insufficient write capacity on a Global Secondary Index**. Always provision GSIs with write capacity equal to or greater than the base table!

## 4. Query vs. Scan Efficiency Metric: `Count` vs. `ScannedCount`

When querying DynamoDB, CloudWatch metrics and API responses report two counts:
* **`ScannedCount`**: The number of items DynamoDB evaluated from physical storage.
* **`Count`**: The number of items returned to the client after `KeyConditionExpression` and `FilterExpression` were evaluated.

$$\text{Query Efficiency Ratio} = \frac{\text{Count}}{\text{ScannedCount}}$$

* In a healthy single-table query: $\text{Count} = \text{ScannedCount}$ (Efficiency = 1.0).
* In an inefficient query with a heavy `FilterExpression`: $\text{ScannedCount} = 10,000$, $\text{Count} = 2$ (Efficiency = 0.0002).  
  **You were billed 2,500 RCUs to retrieve 2 items!**
