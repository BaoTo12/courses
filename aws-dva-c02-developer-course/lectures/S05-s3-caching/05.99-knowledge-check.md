## Question 1: Presigned URL Validity with Temporary IAM Credentials

A developer creates a serverless document delivery microservice using AWS Lambda. The Lambda function uses the AWS SDK for Java v2 to generate an Amazon S3 presigned URL for invoice downloads. The developer configures the presigned URL signature duration as follows:

```java
GetObjectPresignRequest presignRequest = GetObjectPresignRequest.builder()
        .signatureDuration(Duration.ofDays(5))
        .getObjectRequest(getObjectRequest)
        .build();
```

The Lambda function executes successfully and returns the presigned URL. However, when end users attempt to download the invoice 3 hours later, they receive an HTTP 403 Forbidden error with the error code `ExpiredToken`.

What is the root cause of this failure?

- [ ] A) The maximum allowed expiration time for any S3 presigned URL in AWS is 2 hours.
- [ ] B) S3 bucket versioning is disabled, which automatically restricts presigned URL lifetimes to 60 minutes.
- [ ] C) The Lambda function uses an IAM execution role with temporary STS credentials; presigned URLs cannot outlive the credentials used to sign them.
- [ ] D) The S3 bucket policy lacks the `s3:GetObjectVersion` permission required for multi-day presigned URLs.

<details>
<summary><b>View Answer & Explanation</b></summary>

**Correct Answer:** **C**

**Explanation:**
When an S3 presigned URL is created using temporary security credentials (such as an AWS Lambda IAM execution role, Amazon EC2 instance profile, or AWS STS `AssumeRole` token), the URL is mathematically valid **only until the temporary credentials expire**. AWS Lambda execution role credentials typically have a lifespan of 1 hour to a few hours. Even though the developer specified `Duration.ofDays(5)`, once the STS session token (`X-Amz-Security-Token`) expires, Amazon S3 rejects the request with `ExpiredToken`.

* **Option A is incorrect**: The theoretical maximum duration for an S3 presigned URL created with permanent IAM user credentials is **7 days (604,800 seconds)**.
* **Option B is incorrect**: S3 versioning has zero effect on presigned URL expiration limits.
* **Option D is incorrect**: Bucket policies grant or deny actions; they do not dictate presigned URL expiration windows.
</details>

## Question 2: Diagnosing Redis Performance Degradation in CloudWatch

An e-commerce application uses Amazon ElastiCache for Redis on a `cache.m6g.xlarge` instance (4 vCPUs) as a Cache-Aside layer. During a flash sale, API response times jump from 5 ms to 2,500 ms. 

A developer reviews the Amazon CloudWatch dashboard:
* `CPUUtilization` metric reads **26%**.
* `NetworkBytesIn` and `NetworkBytesOut` are well below instance thresholds.
* `CurrConnections` is stable.

The developer suspects the Redis cache is saturated. Which metric should the developer inspect to confirm Redis engine saturation, and why?

- [ ] A) `FreeableMemory`, because 26% CPU utilization proves the cache is out of RAM.
- [ ] B) `EngineCPUUtilization`, because Redis processes commands on a single thread and can be 100% saturated while host-level `CPUUtilization` shows ~25% on a 4-core instance.
- [ ] C) `DatabaseMemoryUsagePercentage`, because ElastiCache automatically scales CPU when memory exceeds 80%.
- [ ] D) `SwapUsage`, because Redis offloads keys to disk swap space when CPU exceeds 25%.

<details>
<summary><b>View Answer & Explanation</b></summary>

**Correct Answer:** **B**

**Explanation:**
Redis is fundamentally **single-threaded** for command execution. On a multi-core instance (like `cache.m6g.xlarge` with 4 vCPUs), one vCPU executing the Redis event loop at 100% capacity will report an aggregate host `CPUUtilization` of only $100\% / 4 = 25\%$. The `EngineCPUUtilization` metric measures the specific utilization of the core running the Redis engine. If `EngineCPUUtilization` is near 100%, the Redis event loop is blocking and unable to process incoming requests, directly explaining the latency spike.

* **Option A is incorrect**: Host-level CPU of 25% does not correlate with RAM exhaustion.
* **Option C is incorrect**: ElastiCache does not automatically scale CPU based on memory usage without custom autoscaling policies.
* **Option D is incorrect**: SwapUsage occurs when memory is exceeded, not at 25% CPU.
</details>

## Question 3: Mitigating the Cache Stampede (Thundering Herd)

A high-traffic web application caches product inventory details in ElastiCache Redis using the Cache-Aside pattern. All product keys are written with a hardcoded TTL of exactly 15 minutes (`SETEX product:{id} 900 json`).

During peak traffic, when a popular product key expires, hundreds of concurrent application threads experience a cache miss simultaneously. They all query DynamoDB at the same instant, triggering `ProvisionedThroughputExceededException` errors.

Which combination of actions will MOST effectively resolve this issue? (Select TWO)

- [ ] A) Switch the database from DynamoDB to Amazon S3 to handle higher concurrent read bursts.
- [ ] B) Implement distributed mutex locking using Redis `SET key token NX EX seconds` so only one thread queries the database on a cache miss while others wait.
- [ ] C) Add random jitter to the TTL (e.g., $900\text{s} + \text{random}(0, 120)\text{s}$) to desynchronize key expiration times.
- [ ] D) Remove the TTL entirely and rely exclusively on ElastiCache `allkeys-random` eviction.
- [ ] E) Enable DynamoDB Global Tables to automatically duplicate throughput across regions.

<details>
<summary><b>View Answer & Explanation</b></summary>

**Correct Answers:** **B and C**

**Explanation:**
The problem described is a classic **Cache Stampede (Thundering Herd)**.
* **B (Distributed Mutex Locking)**: Using Redis `SET key token NX EX` ensures that when a cache miss occurs, only the first thread acquires the lock to query the underlying database and re-populate the cache. Subsequent threads fail to acquire the lock and wait or return fallback data, shielding DynamoDB from a flood of identical queries.
* **C (TTL Jitter)**: Adding randomized jitter ($900\text{s} + \text{random}$) prevents thousands of keys written in the same burst from expiring simultaneously, smoothing out database load.

* **Option A is incorrect**: S3 is an object store, not a low-latency relational or document database.
* **Option D is incorrect**: Removing TTLs leads to unbounded memory growth, and `allkeys-random` randomly purges active hot keys.
* **Option E is incorrect**: DynamoDB Global Tables replicates data across AWS regions for disaster recovery and multi-region active-active access; it does not solve single-region cache stampedes.
</details>

## Question 4: S3 Event Notification Object Key Parsing in AWS Lambda

An AWS Lambda function is configured to process `s3:ObjectCreated:*` events. When an order invoice is uploaded as `invoices/2026/09/invoice customer#101.pdf`, the Lambda function attempts to download the object:

```java
String key = record.getS3().getObject().getKey();
s3Client.getObject(GetObjectRequest.builder().bucket(bucket).key(key).build());
```

The Lambda function throws `NoSuchKeyException: The specified key does not exist` (HTTP 404).

What must the developer do to fix this issue?

- [ ] A) Replace `s3Client.getObject()` with `s3Client.selectObjectContent()`.
- [ ] B) Enable S3 Transfer Acceleration on the bucket.
- [ ] C) URL-decode the object key from the event payload before passing it to `s3Client.getObject()`.
- [ ] D) Configure an S3 Lifecycle rule to convert spaces to underscores.

<details>
<summary><b>View Answer & Explanation</b></summary>

**Correct Answer:** **C**

**Explanation:**
Amazon S3 URL-encodes object keys in S3 Event Notification JSON payloads. In the event JSON, spaces are converted to `+` or `%20`, and characters like `#` are percent-encoded (`%23`). Therefore, `invoices/2026/09/invoice customer#101.pdf` arrives in the event payload as `invoices/2026/09/invoice+customer%23101.pdf`. Passing the raw encoded string to `s3Client.getObject()` fails because S3 treats the literal percent signs and plus characters as the target key name. The key must be URL-decoded: `URLDecoder.decode(key.replace("+", "%20"), StandardCharsets.UTF_8)`.

* **Option A is incorrect**: S3 Select filters object data with SQL expressions; it does not resolve key name encoding.
* **Option B is incorrect**: Transfer Acceleration accelerates cross-border uploads via CloudFront Edge; it has no impact on event notifications.
* **Option D is incorrect**: S3 Lifecycle rules manage storage class transitions and object expirations, not key renames.
</details>

## Question 5: Securing S3 Origins with CloudFront and SSE-KMS

A company hosts sensitive customer receipts in an Amazon S3 bucket. Security compliance mandates that:
1. All objects must be encrypted at rest using **SSE-KMS** with an AWS Key Management Service (AWS KMS) Customer Managed Key (CMK).
2. Users must only access receipts through an Amazon CloudFront distribution; direct access to the S3 bucket must be blocked.
3. The CloudFront distribution must be able to retrieve the KMS-encrypted objects from S3.

Which origin security solution should the developer implement?

- [ ] A) Configure an Origin Access Identity (OAI) and grant the OAI read permissions on the S3 bucket policy and KMS key.
- [ ] B) Configure an Origin Access Control (OAC), update the S3 bucket policy with condition `AWS:SourceArn` referencing the distribution ARN, and grant the CloudFront service principal (`cloudfront.amazonaws.com`) permission to use the KMS key (`kms:Decrypt`).
- [ ] C) Place the S3 bucket behind an Application Load Balancer and enable AWS WAF token authentication.
- [ ] D) Use S3 Presigned Cookies signed with the KMS CMK private key.

<details>
<summary><b>View Answer & Explanation</b></summary>

**Correct Answer:** **B**

**Explanation:**
**Origin Access Control (OAC)** is AWS's modern mechanism for securing S3 origins behind CloudFront. Crucially, **legacy Origin Access Identity (OAI) does NOT support SSE-KMS**. To serve SSE-KMS encrypted objects through CloudFront, you **must** use OAC. The S3 bucket policy restricts access to the CloudFront distribution via `AWS:SourceArn`, and the KMS Key Policy grants `kms:Decrypt` and `kms:GenerateDataKey` to `cloudfront.amazonaws.com` with the same `AWS:SourceArn` condition.

* **Option A is incorrect**: Legacy OAI does not support KMS encryption.
* **Option C is incorrect**: S3 buckets cannot be placed directly behind an Application Load Balancer as a target group.
* **Option D is incorrect**: CloudFront Signed Cookies use RSA key pairs uploaded to CloudFront Key Groups, not KMS CMK keys.
</details>

## Section 05 Mastery Summary

| Focus Area | Core Takeaway |
|---|---|
| **S3 Presigned URLs** | Pure client-side SigV4 calculation; temporary credentials cap URL expiration to STS token lifespan. |
| **ElastiCache Redis** | Single-threaded engine loop; monitor `EngineCPUUtilization` and mitigate Cache Stampedes with distributed locks and TTL jitter. |
| **S3 Event Notifications** | Always URL-decode object keys in Lambda handlers before interacting with the S3 API. |
| **CloudFront Origins** | Use **Origin Access Control (OAC)** instead of legacy OAI when S3 buckets are encrypted with **SSE-KMS**. |
