## Narrative Bridge: Testing the Edge Boundaries

In [Lecture 01.07](./01.07-debug-malformed-proxy-response.md), we ensured our Lambda function always returns a compliant response.

Now, we test our system defensively against malicious or aberrant client traffic. Our `/orders/{proxy+}` route accepts arbitrary POST requests. What happens if a malicious client or broken script sends a massive 12 MB payload to this endpoint? Will API Gateway forward it? Will our Java 21 Lambda function attempt to deserialize it and crash with an `OutOfMemoryError`?

Let's test this directly against our live stack.

---

## 1. The Vulnerable "Feature"

In an unconstrained greedy ingestion endpoint, the handler attempts to parse the incoming request body using Jackson without verifying content length boundaries:

```java
public APIGatewayProxyResponseEvent handleRequest(APIGatewayProxyRequestEvent input, Context context) {
    // Blindly attempts to parse arbitrary length payloads
    OrderRequest req = OBJECT_MAPPER.readValue(input.getBody(), OrderRequest.class);
    ...
}
```

---

## 2. The Exploit

An attacker sends a multi-megabyte malformed or deeply nested payload to the greedy ingestion route:

```bash
# Generate a 12MB payload
python -c "print('{\"notes\":\"' + 'A'*12000000 + '\"}')" > large_payload.json

# Submit to API Gateway
curl -i -X POST "<OrderApiEndpoint>" \
  -H "Content-Type: application/json" \
  --data-binary @large_payload.json
```

### Observed Output:
```http
HTTP/1.1 413 Request Entity Too Large
Content-Length: 41

{"message": "Request entity too large"}
```

---

## 3. Why It Works & API Gateway Limits

* **The 10 MB Hard Ceiling**: Amazon API Gateway enforces a non-negotiable payload limit of **10 MB** (`10,485,760 bytes`) for both request and response payloads. Any payload exceeding 10 MB is terminated at the edge before invoking Lambda with `413 Request Entity Too Large`.
* **The Heap Exhaustion Threat**: If the payload is 8 MB (under the 10 MB limit), and Lambda is configured with 128 MB or 256 MB RAM, reading and serializing the string with Jackson can exceed the Java JVM maximum heap space (`-Xmx`), triggering `java.lang.OutOfMemoryError` and crashing the microVM.

---

## 4. 🛡 Defense & Mitigation

1. **Allocate Sufficient RAM**: Configure memory $\ge 1,769$ MB in `template.yaml` to ensure ample heap space for Jackson AST nodes.
2. **Defensive Payload Slicing**: Check payload string length before invoking Jackson deserializers:

```java
if (body.length() > 500_000) { // Reject orders exceeding 500 KB
    return buildErrorResponse(413, "PayloadTooLarge", "Order payload exceeds maximum permitted 500 KB limit");
}
```
3. **Large Payload Architecture (Foreshadowing)**: For payloads exceeding 10 MB (e.g. bulk batch orders or invoices), clients must never send raw data through API Gateway. Instead, the API returns an **S3 Presigned URL**, and the client uploads directly to Amazon S3 (which we will build in [Module 4](../S04-dynamodb-s3/)).
