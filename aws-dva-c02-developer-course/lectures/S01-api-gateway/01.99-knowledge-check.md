**1. (Concept: Memory & Compute Physics)**
A developer deploys a CPU-intensive image processing Lambda function written in Java 21 with memory configured to 512 MB. The function takes 4.2 seconds to process each image. If the developer increases the configured memory to 1,769 MB, what will be the effect on compute power and execution duration?

<details><summary>Answer</summary>

**Answer**: The function will be allocated exactly 1 full vCPU thread (up from ~0.29 vCPU), and execution duration will drop significantly (typically by 60–75%).

**Reasoning**: AWS Lambda allocates compute power linearly proportional to memory. 1,769 MB is the exact threshold for 1 full vCPU. Below this threshold, the JVM runs on fractional vCPU shares, throttling JIT compilation and parallel operations.
*(Reference: [Lecture 01.01](./01.01-mechanical-sympathy-api-gateway-lambda.md))*
</details>

**2. (Debugging: The 29-Second Limit)**
An application invokes an API Gateway REST API endpoint which triggers a Java Lambda function that runs a complex calculation. The client consistently receives an `HTTP 504 Gateway Timeout` error after exactly 29 seconds. When reviewing CloudWatch Logs for the Lambda function, the developer observes:
`REPORT Duration: 34120 ms Billed Duration: 34121 ms`
How should the developer resolve this issue?

<details><summary>Answer</summary>

**Answer**: Decouple the architecture asynchronously. Have API Gateway trigger a Lambda function that immediately pushes the order request to an **Amazon SQS queue** or invokes an **asynchronous AWS Step Functions workflow**, returning `HTTP 202 Accepted` to the client immediately.

**Reasoning**: Amazon API Gateway REST and HTTP APIs have an unconfigurable, non-negotiable maximum backend integration timeout of **29 seconds** (29,000 ms). If the backend processing takes 34 seconds, API Gateway terminates the client connection with HTTP 504 at 29s.
*(Reference: [Lecture 01.01](./01.01-mechanical-sympathy-api-gateway-lambda.md) & [Lecture 01.02](./01.02-api-card-requesthandler.md))*
</details>

**3. (Code Reading: Proxy Contract Failure)**
A developer creates an API Gateway endpoint using Lambda Proxy Integration (`AWS_PROXY`). The Java handler executes successfully with no thrown exceptions, returning an instance of `CustomOrderDTO`. The client receives an `HTTP 502 Bad Gateway` error. What is the root cause?

<details><summary>Answer</summary>

**Answer**: In Lambda Proxy Integration, API Gateway requires the response payload to be formatted as an `APIGatewayProxyResponseEvent` containing the top-level keys `statusCode`, `headers`, and `body`.

**Reasoning**: Returning a raw POJO or unformatted String violates the proxy response contract. API Gateway cannot parse the required `statusCode` and terminates the request with HTTP 502 ("Malformed Lambda proxy response").
*(Reference: [Lecture 01.02](./01.02-api-card-requesthandler.md) & [Lecture 01.07](./01.07-debug-malformed-proxy-response.md))*
</details>

**4. (Design: Traffic Shifting & Aliases)**
A company wants to deploy a new version of their Order Ingestion Lambda function. They require 10% of production traffic to be routed to the new version initially, and after 5 minutes of healthy operation without CloudWatch alarms, all traffic should shift to the new version. Which combination of AWS services and configurations achieves this?

<details><summary>Answer</summary>

**Answer**: Use **AWS SAM** with `AutoPublishAlias: live` and set `DeploymentPreference: { Type: Canary10Percent5Minutes }`. This automatically configures **AWS CodeDeploy** to perform canary traffic shifting across published Lambda versions.

**Reasoning**: AWS CodeDeploy natively supports Lambda traffic shifting preferences like `Canary10Percent5Minutes` and `Linear10PercentEvery1Minute`, tracking CloudWatch alarms to execute automatic rollbacks if error rates rise.
*(Reference: [Lecture 01.09](./01.09-extended-lambda-versioning-aliases.md))*
</details>

**5. (Implementation: CORS Resolution)**
A Single-Page Application (SPA) hosted on `https://shop.cloudorder.com` makes an `HTTP POST` request with a custom header `X-Order-Priority` to an API Gateway REST API. The browser blocks the request with a CORS error before sending the POST request. What two configurations are required in API Gateway to fix this?

<details><summary>Answer</summary>

**Answer**:
1. Configure a mock `OPTIONS` method integration on the API resource returning `200 OK` with header `Access-Control-Allow-Headers: Content-Type,Authorization,X-Order-Priority` and `Access-Control-Allow-Origin: https://shop.cloudorder.com` (or `*`).
2. Ensure the Lambda function's `APIGatewayProxyResponseEvent` also includes `Access-Control-Allow-Origin` in its response headers map.

**Reasoning**: The browser initiates a CORS pre-flight `OPTIONS` request whenever custom headers (`X-Order-Priority`) or non-simple methods are used. If API Gateway does not answer the pre-flight `OPTIONS` call with the allowed custom headers, the browser aborts the request.
*(Reference: [Lecture 01.03](./01.03-build-order-api-handler.md) & [Lecture 01.04](./01.04-provisioning-sam-template.md))*
</details>

### The Looming Architectural Bottleneck
Take a close look at what we've built:
When a client sends an `HTTP POST /orders/electronics`, our API Gateway calls our Java Lambda function synchronously. 
* *What happens if processing an order requires reserving inventory, charging credit cards, sending SMS notifications, and generating invoice PDFs?*
* *What happens if 50,000 customers order simultaneously on Black Friday? Our synchronous Lambda functions will exhaust our downstream database connections and exceed API Gateway's 29-second ceiling!*

To solve this, we must **decouple synchronous ingestion from asynchronous processing**.
