## Narrative Bridge: Progressive Traffic Shifting

In [Lecture 01.08](./01.08-attack-lab-unbounded-payload-oom.md), we hardened our application against external abuse.

Now, imagine we have written version 2 of our `OrderApiHandler`. If we simply deploy v2 over v1 all at once, an unforeseen production bug will immediately affect 100% of customers.

To prevent this, AWS provides **Lambda Versioning** and **Aliases** with **Weighted Canary Traffic Routing**.

---

```yaml
Resources:
  OrderApiFunctionAliasLive:
    Type: AWS::Lambda::Alias
    Properties:
      FunctionName: !Ref OrderApiFunction
      FunctionVersion: "2"
      Name: live
      RoutingConfig:
        AdditionalVersionWeights:
          - FunctionVersion: "1"
            FunctionWeight: 0.10 # 10% traffic to version 1, 90% to version 2
```

- **Versions are Immutable**: Once published (`AWS::Lambda::Version`), the code and configuration for that version cannot be modified.
- **Aliases are Mutable Pointers**: An alias (e.g. `live` or `prod`) points to a specific numerical version ARN, shielding API Gateway from code updates.
- **Weighted Routing (Canary)**: The `RoutingConfig` property allows splitting incoming invocations probabilistically between two published versions (e.g. 90% to v2, 10% to v1).
- **SAM Automation**: In AWS SAM, adding `AutoPublishAlias: live` and `DeploymentPreference: { Type: Canary10Percent5Minutes }` automatically generates the CloudFormation version and routes traffic via AWS CodeDeploy (which we will build into a full CI/CD pipeline in [Module 6](../S06-cicd/)).
