## The Story Begins: Ingress for CloudOrder

Every distributed enterprise platform begins with an ingress boundary. For our **CloudOrder** application, this boundary must receive orders from web browsers, mobile clients, and third-party partner systems, parse high-velocity HTTP payloads, validate routing parameters, and pass the data into our compute tier without managing physical servers.

In AWS serverless architecture, this ingress is formed by **Amazon API Gateway** feeding into **AWS Lambda**. But before writing a single line of Java or YAML, you must understand the physical compute and networking boundaries of these two services. If you treat Lambda like a standard always-on Spring Boot or Tomcat container, you will be blindsided by cold starts, connection churn, and integration timeouts.

## 1. The Compute & Ingestion Layer Mechanics

```text
 Client (Browser / Mobile / cURL)
        │
        │ HTTPS POST /orders/electronics?region=us-east-1
        ▼
┌──────────────────────────────── Amazon API Gateway (REST API) ────────────────────────────────┐

│  • Ingestion Payload: Serialized into APIGatewayProxyRequestEvent JSON                        │

└───────────────────────────────────────────────┬───────────────────────────────────────────────┘
                                                │ Synchronous Invoke
                                                ▼
┌────────────────────────────────────────── AWS Lambda ─────────────────────────────────────────┐
│  [MicroVM Cold Start Phase]                                                                   │
│  1. MicroVM Allocation (Firecracker jail on EC2 bare-metal host)                              │
│  2. Runtime Initialization (JVM bootstrapping, classloading, JIT c1/c2 baseline)             │
│  3. Static Initialization (Static variables, singletons, Jackson ObjectMapper, SDK clients)  │

│  [Warm Execution Phase]                                                                       │
│  4. handleRequest(APIGatewayProxyRequestEvent, Context)                                       │
```

## 2. API Gateway: REST vs. HTTP vs. WebSocket APIs

When architecting the entry point for CloudOrder, choosing the right API Gateway flavor is critical for cost, latency, and capabilities:

| Dimension | REST APIs (v1) | HTTP APIs (v2) | WebSocket APIs |
|---|---|---|---|
| **Architecture** | Feature-rich, enterprise proxy | Lightweight, low-latency proxy | Full-duplex persistent TCP connections |
| **Payload Version** | 1.0 format (`APIGatewayProxyRequestEvent`) | 2.0 format (`APIGatewayV2HTTPEvent`) | Frame-based JSON payloads |
| **Integration Types** | Proxy (`AWS_PROXY`), Non-Proxy (VTL), Mock, AWS Services | Proxy (`AWS_PROXY`) only | WebSocket frame routing |
| **Hard Timeout** | **29 seconds** (cannot be increased) | **30 seconds** | **10 minutes** per idle connection |
| **Caching & WAF** | Native API Gateway caching & AWS WAF support | AWS WAF supported; no native stage cache | AWS WAF supported |
| **Usage Plans & Keys** | Full support (API keys, quotas, rate/burst) | Not supported | Not supported |
| **Latency & Cost** | Baseline latency (~15–30ms); $3.50/M requests | ~60% lower latency; $1.00/M requests | Pay per million messages + connection minutes |

> **Architectural Decision for CloudOrder**: We choose **REST APIs** for Section 1 because enterprise order ingestion requires Usage Plans, API Keys, request throttling, and custom Lambda Authorizers (which we will build in [Module 5](../S05-security/)).

## 3. Lambda Execution Environment Lifecycle & Memory-to-vCPU Physics

### The Three Execution Phases
1. **Init Phase**:
   - Spawns the Linux microVM using AWS Firecracker.
   - Bootstraps the Java 21 managed runtime.
   - Runs static initializers and class verification (this is where we will instantiate our singleton `ObjectMapper` in [Lecture 01.03](./01.03-build-order-api-handler.md)).
2. **Invoke Phase**:
   - Calls the `handleRequest` method.
3. **Shutdown Phase**:
   - Triggered if no invocations arrive during the idle window (~5 to 15 minutes). Environment variables and runtime processes are destroyed.

### The 1,769 MB vCPU Allocation Rule
AWS Lambda allocates CPU power strictly proportional to memory:
$$\text{Allocated vCPUs} = \frac{\text{Configured Memory (MB)}}{1769}$$

* At **512 MB**, Lambda provides ~0.29 vCPU. Java classloading and JIT compilation take 1.8–2.5 seconds.
* At **1,769 MB**, Lambda provides exactly **1 full dedicated vCPU thread**.
* At **3,008 MB**, Lambda provides **2 full vCPU threads**, allowing multi-threaded garbage collection and parallel JIT compilation, cutting cold-start duration down to ~400ms.

## 4. Lambda SnapStart with CRaC (Coordinated Restore at Checkpoint)

For Java runtimes, AWS Lambda SnapStart takes an initialized microVM snapshot at deployment time:
1. Lambda compiles code and runs all static initializers during `sam deploy`.
2. Firecracker checkpoints the entire memory page cache to an encrypted cache tier.
3. On customer invocation, Lambda restores the cached snapshot in **sub-200ms**.

> [!WARNING]
> **Ephemeral Uniqueness Warning (CRaC)**:
> If your application initializes unique state (e.g. `UUID.randomUUID()`, random seeds, unique network credentials) inside static initializers, SnapStart will clone that identical state across thousands of microVMs! You must use CRaC resource hooks (`Resource.afterRestore()`) to regenerate unique identifiers after snapshot restoration.

## 5. The Hard 29-Second Ceiling (DVA-C02 Exam Trap)

Amazon API Gateway enforces an absolute, non-negotiable **29-second maximum integration timeout**. 

* If your Java Lambda function takes **29.1 seconds** to complete, API Gateway severs the HTTP connection and returns `504 Gateway Timeout` to the client.
* The Lambda function does *not* stop—it continues executing until its own configured timeout (e.g. 30 seconds), wasting billed execution time while the customer receives an error!
* *Foreshadowing*: In [Section 02](../S02-fanout-sqs/), we will solve this exact limitation by decoupling long-running order processing from synchronous HTTP ingestion using **Amazon SNS and Amazon SQS**.
