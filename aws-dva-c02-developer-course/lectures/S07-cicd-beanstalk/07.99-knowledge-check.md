## Question 1: Selecting the Zero-Downtime Beanstalk Policy with Zero Capacity Degradation

A developer is managing a production web application deployed on AWS Elastic Beanstalk. The application experiences steady traffic 24/7 and cannot tolerate any reduction in fleet capacity during deployments. The management team requires that all application updates occur with zero downtime and that existing instances remain completely untouched until the new version is verified and healthy.

Which Elastic Beanstalk deployment policy should the developer select?

- [ ] A) All at Once
- [ ] B) Rolling
- [ ] C) Immutable
- [ ] D) In-Place Overwrite

<details>
<summary><b>View Answer & Explanation</b></summary>

**Correct Answer:** **C**

**Explanation:**
The **Immutable** deployment policy is the most robust zero-downtime strategy in Elastic Beanstalk:
1. It launches a completely separate, temporary Auto Scaling Group (ASG) containing an identical number of instances.
2. It deploys the new application version to the new ASG and runs health checks.
3. If health checks pass, traffic is transitioned to the new instances, and the old ASG is terminated.
4. Throughout the entire process, 100% of fleet capacity is maintained, and existing instances are never modified until verification succeeds.
5. If deployment fails, the new ASG is terminated immediately, preserving the original environment with zero customer impact.

* **Option A is incorrect**: All at Once takes down all instances simultaneously, causing complete application downtime.
* **Option B is incorrect**: Rolling updates instances in batches, which reduces available fleet capacity during the update (e.g. 50% capacity available while a batch updates).
* **Option D is incorrect**: In-Place Overwrite is not a valid Elastic Beanstalk deployment policy name.
</details>

## Question 2: Resolving CodeDeploy Lifecycle Hook Hanging Timeouts

A developer configures an automated canary deployment for an AWS Lambda function using AWS CodeDeploy. In `appspec.yaml`, the developer registers a `BeforeAllowTraffic` hook pointing to a validation Lambda function:

```yaml
version: 0.0
Resources:
  - TargetFunction:
      Type: AWS::Lambda::Function
      Properties:
        Name: OrderService
        Alias: live
        CurrentVersion: "1"
        TargetVersion: "2"
Hooks:
  - BeforeAllowTraffic: ValidateCanaryHook
```

The `ValidateCanaryHook` Lambda function executes successfully in 2 seconds and returns the string `"SUCCEEDED"`. However, the CodeDeploy console reports that the deployment hangs in `InProgress` for 60 minutes before failing with `The lifecycle event hook execution timed out after 3600 seconds`.

What must the developer do to fix this issue?

- [ ] A) Increase the Lambda function memory size from 128 MB to 1024 MB.
- [ ] B) Update the Lambda function to make an AWS SDK call to `CodeDeployClient.putLifecycleEventHookExecutionStatus()` passing the `DeploymentId`, `LifecycleEventHookExecutionId`, and status `SUCCEEDED`.
- [ ] C) Change the hook name in `appspec.yaml` from `BeforeAllowTraffic` to `PreTrafficCheck`.
- [ ] D) Enable AWS X-Ray active tracing on the hook function.

<details>
<summary><b>View Answer & Explanation</b></summary>

**Correct Answer:** **B**

**Explanation:**
AWS CodeDeploy **does not read the return value or stdout of hook Lambda functions**. CodeDeploy strictly pauses the deployment pipeline until it receives an API call:
`CodeDeployClient.putLifecycleEventHookExecutionStatus(...)`
specifying the `deploymentId`, `lifecycleEventHookExecutionId`, and status (`SUCCEEDED` or `FAILED`). If the Lambda function finishes execution without making this API call, CodeDeploy waits for the maximum hook execution timeout (default: 60 minutes / 3600 seconds) before failing the deployment and initiating a rollback.
</details>

## Question 3: Running Single-Instance Database Migrations in Elastic Beanstalk

A company deploys a multi-instance Java application on AWS Elastic Beanstalk. The application connects to an Amazon Aurora PostgreSQL database. With each application update, database schema migrations must be executed. If multiple EC2 instances attempt to run schema migrations simultaneously during deployment, database deadlocks and migration table corruptions occur.

How should the developer configure Elastic Beanstalk to run database migrations safely on exactly one instance?

- [ ] A) Place a script in `.ebextensions/` under the `commands` section with `leader_only: true`.
- [ ] B) Place a script in `.ebextensions/` under the `container_commands` section with `leader_only: true`.
- [ ] C) Use a Cron job on each EC2 instance that queries Aurora before running migrations.
- [ ] D) Add a pre-build command in `buildspec.yml` to execute migrations directly from CodeBuild.

<details>
<summary><b>View Answer & Explanation</b></summary>

**Correct Answer:** **B**

**Explanation:**
In Elastic Beanstalk `.ebextensions` configuration files:
* **`container_commands`** runs after the application bundle has been extracted on the instance, right before the application server starts.
* Specifying **`leader_only: true`** ensures that Elastic Beanstalk designates exactly **one instance** in the Auto Scaling Group as the leader to execute the command. All other instances skip the command.
* **`commands` (Option A) is incorrect**: The `commands` section executes before the application source is extracted and **does NOT support `leader_only`**; it runs on every instance in the fleet.
</details>

## Question 4: Optimizing AWS CodeBuild Compilation Performance

A developer maintains a continuous integration pipeline using AWS CodeBuild for a large Java 21 multi-module application. The team notices that every build takes over 8 minutes to complete, and inspecting the build logs reveals that Maven repeatedly downloads the same external dependencies from Maven Central on every execution.

Which combination of actions will reduce build duration MOST effectively? (Select TWO)

- [ ] A) Add a `cache` block to `buildspec.yml` specifying the path `'/root/.m2/**/*'`.
- [ ] B) Configure the CodeBuild project to use a `LOCAL` cache with `LOCAL_CUSTOM_CACHE` mode or an Amazon S3 cache bucket.
- [ ] C) Move the `mvn compile` command from the `build` phase to the `post_build` phase.
- [ ] D) Switch the CodeBuild compute environment to Windows Server with .NET Core.
- [ ] E) Delete `pom.xml` and manage JAR files as binary blobs in Git.

<details>
<summary><b>View Answer & Explanation</b></summary>

**Correct Answers:** **A and B**

**Explanation:**
AWS CodeBuild runs inside ephemeral Docker containers that are destroyed after each build.
1. Adding `cache.paths: ['/root/.m2/**/*']` in `buildspec.yml` tells CodeBuild which directory to preserve between builds.
2. In the CodeBuild project settings (CloudFormation or Console), you must enable caching by setting `Type: LOCAL` (with `LOCAL_CUSTOM_CACHE`) or `Type: S3`. On subsequent builds, CodeBuild mounts or unzips the cached dependencies, bypassing public internet downloads and dropping build times from minutes to seconds.
</details>

## Question 5: Progressive Canary Traffic Shifting for AWS Lambda

A developer is configuring continuous deployment for an AWS Lambda microservice using AWS CodeDeploy. The requirements state that:
1. 10% of production traffic must be routed to the newly deployed Lambda version immediately.
2. Traffic must remain split for exactly 5 minutes while synthetic health checks and CloudWatch alarms monitor application performance.
3. If no alarms trigger, 100% of traffic must be routed to the new version.

Which CodeDeploy deployment configuration should the developer specify?

- [ ] A) `CodeDeployDefault.LambdaLinear10PercentEvery1Minute`
- [ ] B) `CodeDeployDefault.LambdaCanary10Percent5Minutes`
- [ ] C) `CodeDeployDefault.LambdaCanary10Percent15Minutes`
- [ ] D) `CodeDeployDefault.LambdaAllAtOnce`

<details>
<summary><b>View Answer & Explanation</b></summary>

**Correct Answer:** **B**

**Explanation:**
AWS CodeDeploy provides pre-configured deployment configurations for Lambda:
* **`LambdaCanary10Percent5Minutes`**: Routes 10% of traffic to the new version in the first increment, pauses for **5 minutes** for monitoring, and then routes the remaining 90% in the second increment.
* **Option A is incorrect**: `LambdaLinear10PercentEvery1Minute` routes an additional 10% every minute for 10 minutes.
* **Option C is incorrect**: `LambdaCanary10Percent15Minutes` waits 15 minutes, which exceeds the 5-minute requirement.
* **Option D is incorrect**: `LambdaAllAtOnce` shifts 100% immediately with zero canary evaluation.
</details>

## Section 07 Mastery Summary

| Focus Area | Core Takeaway |
|---|---|
| **Beanstalk Policies** | **Immutable** provides zero downtime, preserves 100% fleet capacity, and offers the cleanest rollback by isolating updates in a temporary ASG. |
| **CodeDeploy Hooks** | Lambda hooks must explicitly invoke `putLifecycleEventHookExecutionStatus` via the AWS SDK, or CodeDeploy will hang for 60 minutes. |
| **`.ebextensions`** | Use `container_commands` with `leader_only: true` for database schema migrations. |
| **CodeBuild Caching** | Cache `/root/.m2/**/*` with `LOCAL_CUSTOM_CACHE` to avoid downloading Maven dependencies repeatedly. |
| **Lambda Canaries** | `Canary10Percent5Minutes` shifts 10% of traffic, evaluates for 5 minutes, and shifts the remaining 90% if alarms remain clear. |
