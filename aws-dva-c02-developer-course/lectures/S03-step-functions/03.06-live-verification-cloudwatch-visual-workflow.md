## Narrative Bridge: Gaining Operational Clarity

In [Lecture 03.05](./03.05-your-turn-cli-executions-compensating-rollback.md), we triggered executions from the CLI and inspected JSON payloads. But when hundreds of orders are executing simultaneously, distributed systems engineers need visual clarity.

One of AWS Step Functions' greatest advantages over pure event choreography is **deterministic, visual observability**. Every execution maintains a complete, audited graph showing the exact second each task began, how many times it retried, and the full state payload entering and exiting every step.

Let's verify our state machine visually and explore its CloudWatch telemetry.

---

## 1. Navigating the Visual Workflow Graph in the AWS Console

Open the AWS Management Console, navigate to **Step Functions** $\to$ **State machines** $\to$ **CloudOrderCheckoutSaga**.

```text
               ┌──────────────────────┐
               │   ReserveInventory   │ ── [Green: Succeeded]
               └──────────┬───────────┘
                          │
                          ▼
               ┌──────────────────────┐
               │    ProcessPayment    │ ── [Red: Failed (PaymentDeclinedException)]
               └──────────┬───────────┘
                          │ (Catch Transition)
                          ▼
               ┌──────────────────────┐
               │ CompensateInventory  │ ── [Green: Compensating Succeeded]
               └──────────┬───────────┘
                          │
                          ▼
               ┌──────────────────────┐
               │ OrderRolledBackState │ ── [Red Terminal: Halted]
               └──────────────────────┘
```

### Visual State Colors:
* 🟢 **Green**: State succeeded.
* 🔴 **Red**: State failed or unhandled exception.
* 🟡 **Yellow**: State currently running.
* ⚪ **Grey / White**: State was not reached in this branch.

Clicking any state node displays three inspector tabs:
1. **Input**: The exact JSON payload fed into this step after `InputPath` and `Parameters` transformations.
2. **Output**: The JSON payload exiting this step after `ResultSelector`, `ResultPath`, and `OutputPath` transformations.
3. **Task Details**: Resource ARN, duration, retry attempts, and raw error messages.

## 2. Enabling CloudWatch Logging for State Machines

Standard Workflows provide 90-day console execution history by default, but production compliance and alarming require shipping state transition events to **Amazon CloudWatch Logs**.

In SAM / CloudFormation:

```yaml
OrderCheckoutStateMachine:
  Type: AWS::Serverless::StateMachine
  Properties:
    Logging:
      Level: ALL
      IncludeExecutionData: true # Logs full state JSON input/output
      Destinations:
        - CloudWatchLogsLogGroup:
            LogGroupArn: !GetAtt StateMachineLogGroup.Arn
```

> [!NOTE]
> `IncludeExecutionData: true` logs the entire state payload for each transition. If your workflow processes sensitive personal data (PII) or credit card numbers, set `IncludeExecutionData: false` or mask fields to comply with PCI-DSS and GDPR.

## 3. High-Yield CloudWatch Step Functions Metrics

Step Functions publishes metrics to the `AWS/States` namespace:

| Metric Name | Unit | What It Measures | Alarming Best Practice |
|---|:---:|---|---|
| `ExecutionsFailed` | Count | Executions ending in `FAILED` or unhandled error. | Alarm if `> 0` over 5 minutes (indicates failed orders or broken sagas). |
| `ExecutionsSucceeded` | Count | Executions reaching terminal `SUCCEED`. | Monitor for throughput volume. |
| `ExecutionsTimedOut` | Count | Executions exceeding `TimeoutSeconds`. | High-priority alert! Tasks are hanging or polling forever. |
| `ExecutionTime` | Milliseconds | End-to-end duration of the entire workflow. | Scale workers if P99 latency spikes. |
| `ExecutionThrottled` | Count | Invocations rejected due to `startExecution` rate limits. | Indicates you exceeded the 2,000 starts/sec Standard Workflow limit! |

## 4. Querying Execution Errors with CloudWatch Logs Insights

To extract all failed checkout attempts across the fleet:

```sql
fields @timestamp, execution_arn, details.error, details.cause
| filter event_type = "ExecutionFailed"
| sort @timestamp desc
| limit 20
```

To pinpoint slow tasks inside your state machine:
```sql
fields @timestamp, state_name, task_duration = @duration
| filter event_type = "TaskStateExited"
| stats avg(task_duration), p90(task_duration), p99(task_duration) by state_name
```
