## Narrative Bridge: The Anatomy of a Vanished State

In [Lecture 03.06](./03.06-live-verification-cloudwatch-visual-workflow.md), we explored how Step Functions tracks state transitions across execution graphs.

Now, we enter the debug lab to tackle one of the most frequent and baffling production bugs in Step Functions:  
**The State Context Obliteration Bug.**

A junior developer on your team adds an order validation task at the start of the checkout workflow. The validation task runs green, but every single execution immediately crashes on the next step with `NullPointerException`. All order metadata (`orderId`, `customerId`, `amount`, `items`) completely disappears from the workflow!

Let's diagnose and fix this defect.

---

## 1. The Symptom: Downstream Task Crashes

When launching an execution, the workflow halts at `ReserveInventory`:

```text
Execution Status: FAILED
Error: States.TaskFailed
Cause: {"errorMessage": "Cannot reserve inventory: order contains no items", "errorType": "com.cloudarchitect.dvac02.workflow.exception.InventoryUnavailableException"}
```

You inspect the order payload submitted to `startExecution`:
```json
{
  "orderId": "ORD-DEBUG-999",
  "customerId": "charlie@example.com",
  "amount": 250.00,
  "items": ["MECHANICAL-KEYBOARD", "MOUSEPAD"]
}
```
The input clearly had `items: ["MECHANICAL-KEYBOARD", "MOUSEPAD"]`. Why is `ReserveInventory` claiming the order has no items?

---

## 2. Inspecting the Step Transitions in the Console

Open the Step Functions visual inspector for the failed execution and compare the **Input** and **Output** tabs for the new validation step:

### Step 1: Input to `ValidateOrderDetails`
```json
{
  "orderId": "ORD-DEBUG-999",
  "customerId": "charlie@example.com",
  "amount": 250.00,
  "items": ["MECHANICAL-KEYBOARD", "MOUSEPAD"]
}
```

### Step 2: Output from `ValidateOrderDetails`
```json
{
  "isValid": true,
  "validationTimestamp": "2026-09-27T08:41:00Z"
}
```

**Where did `orderId`, `customerId`, and `items` go?!**  
The validation result did not *merge* into the state; it **completely wiped out** the state!

---

## 3. The Root Cause: Misuse of `"ResultPath": "$"`

Inspect the ASL definition in `template.yaml`:

```yaml
# ❌ THE DEFECTIVE ASL DEFINITION:
ValidateOrderDetails:
  Type: Task
  Resource: arn:aws:states:::lambda:invoke
  Parameters:
    FunctionName: !GetAtt ValidateOrderFunction.Arn
    Payload.$: "$"
  ResultPath: "$" # ⚠️ CATASTROPHIC ROOT OVERWRITE!
  Next: ReserveInventory
```

### The Mechanical Breakdown:
In Amazon States Language, `ResultPath` specifies the JSONPath node where the task's return value will be stored:
* `$` refers to the **root of the JSON document**.
* By specifying `"ResultPath": "$"`, you instruct the Step Functions engine:  
  *"Take whatever this Lambda function returns, and replace the ENTIRE state document with it."*
* Since the validator Lambda function only returned `{ "isValid": true }`, the entire original order payload was discarded.
* When `ReserveInventory` executed next, `$.items` was `null`, immediately triggering `InventoryUnavailableException`!

---

## 4. The Two Correct Solutions

Depending on whether you need the task's output downstream, AWS ASL provides two distinct patterns:

### Solution A: Non-Destructive Node Merging (When output IS needed)
Change `ResultPath` to attach the output to a specific sub-key:

```yaml
# ✅ SOLUTION A: Merge output under $.validationResult
ValidateOrderDetails:
  Type: Task
  Resource: arn:aws:states:::lambda:invoke
  Parameters:
    FunctionName: !GetAtt ValidateOrderFunction.Arn
    Payload.$: "$"
  ResultPath: "$.validationResult" # Preserves root keys!
  Next: ReserveInventory
```

**Resulting State Exiting Step**:
```json
{
  "orderId": "ORD-DEBUG-999",
  "customerId": "charlie@example.com",
  "amount": 250.00,
  "items": ["MECHANICAL-KEYBOARD", "MOUSEPAD"],
  "validationResult": {
    "isValid": true,
    "validationTimestamp": "2026-09-27T08:41:00Z"
  }
}
```
All original order properties remain intact, and `validationResult` is safely appended!

---

### Solution B: Discarding Task Output with `"ResultPath": null` (When output is NOT needed)
What if your Lambda function merely executes a validation check or writes an audit log, and its output is completely irrelevant to downstream tasks?

```yaml
# ✅ SOLUTION B: Completely discard task output and pass original input unchanged
ValidateOrderDetails:
  Type: Task
  Resource: arn:aws:states:::lambda:invoke
  Parameters:
    FunctionName: !GetAtt ValidateOrderFunction.Arn
    Payload.$: "$"
  ResultPath: null # ⚡ Discards Lambda output; passes original state forward!
  Next: ReserveInventory
```

> [!IMPORTANT]
> **DVA-C02 Exam Gold**:
> Setting `"ResultPath": null` tells Step Functions: *"Execute the task, but discard the task result and pass the original input unmodified to the next state."*  
> If an exam question asks how to execute an auditing or validation Lambda task without altering the state JSON, the answer is always **`"ResultPath": null`**.

---

## Summary of `ResultPath` Behaviors

| `ResultPath` Value | Behavior | Common Use Case |
|---|---|---|
| `"$.fieldName"` | Appends task output under `fieldName`; preserves all existing state fields. | **Default Best Practice** for stateful multi-step pipelines. |
| `null` | Discards task output completely; passes original input through to next step. | Fire-and-forget logging, notifications, validation tasks. |
| `"$"` | **Overwrites the entire state document** with task output. | Transforming final state before exit (or a catastrophic bug if done midway!). |
| *(Omitted)* | Defaults to `"$"`. | Avoid relying on default; always declare `ResultPath` explicitly! |
