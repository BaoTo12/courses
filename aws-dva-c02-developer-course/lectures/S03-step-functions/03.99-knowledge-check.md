### Question 1: Workflow Engine Selection Under Extreme Load

An e-commerce mobile application handles flash sale order validation. The system receives up to **15,000 requests per second** during promotional peaks. Each order workflow consists of 4 fast task states that run in under 400 milliseconds total. The engineering team has a strict cost ceiling and requires that clients receive synchronous HTTP responses with the final confirmation payload.

Which architecture should the developer select?

- [ ] **A.** Deploy an AWS Step Functions Standard Workflow and invoke it via `sfnClient.startExecution()`.
- [ ] **B.** Deploy an AWS Step Functions Standard Workflow and invoke it via `sfnClient.startSyncExecution()`.
- [ ] **C.** Deploy an AWS Step Functions Express Workflow, configure an Amazon API Gateway REST API with a direct service integration calling `states:StartSyncExecution`, and return the output directly.
- [ ] **D.** Deploy AWS Step Functions Standard Workflows using a `Parallel` state and poll `describeExecution()` every 50ms using a client loop.

<details>
<summary>Click to view Answer & Detailed Explanation</summary>

**Correct Answer: C**

**Mechanical Sympathy Breakdown:**
* **C is correct**:
  1. Standard Workflows have a quota limit of 2,000 execution starts/sec; they will throttle heavily at 15,000 req/sec. Express Workflows support 100,000+ starts/sec.
  2. Standard Workflows bill at $0.025 per 1,000 state transitions ($1,500/minute at 15,000 RPS!), whereas Express Workflows bill by execution duration and memory ($1/M requests).
  3. Only Express Workflows support synchronous execution (`StartSyncExecution`).
  4. Integrating directly with API Gateway eliminates intermediate Lambda compute and cold starts.
* **A is incorrect**: `startExecution` is asynchronous and cannot return the final output in the synchronous HTTP response.
* **B is incorrect**: Standard Workflows do not support `startSyncExecution`.
* **D is incorrect**: Polling loops in client code introduce massive latency, waste compute, and do not resolve the 2,000 starts/sec Standard quota.

</details>

### Question 2: Preserving Input State in ASL Tasks

A developer is configuring a Step Functions state machine. A task named `AuditOrder` invokes an AWS Lambda function that writes audit metadata to an external monitoring system. The `AuditOrder` Lambda function returns a status object: `{"auditLogged": true}`. 

The subsequent state, `ProcessShipment`, requires the original input state containing `orderId`, `customerId`, and `shippingAddress`.

How should the developer configure the `AuditOrder` task in Amazon States Language (ASL) so that the audit Lambda is executed, but the original input state passes completely unmodified to `ProcessShipment`?

- [ ] **A.** Set `"ResultPath": "$"` on the `AuditOrder` task.
- [ ] **B.** Set `"ResultPath": null` on the `AuditOrder` task.
- [ ] **C.** Set `"OutputPath": "$"` on the `AuditOrder` task.
- [ ] **D.** Omit the `ResultPath` parameter completely from the `AuditOrder` task definition.

<details>
<summary>Click to view Answer & Detailed Explanation</summary>

**Correct Answer: B**

**Mechanical Sympathy Breakdown:**
* **B is correct**: In ASL, setting `"ResultPath": null` instructs the Step Functions engine to execute the task, discard the task output completely, and pass the original input state forward to the next state without alteration.
* **A is incorrect**: `"ResultPath": "$"` overwrites the entire state with the task output (`{"auditLogged": true}`), destroying `orderId` and `shippingAddress`.
* **C is incorrect**: `OutputPath` only filters the output *after* `ResultPath` has already merged or overwritten the state.
* **D is incorrect**: If omitted, `ResultPath` defaults to `"$"`, which causes the overwrite bug.

</details>

### Question 3: Resolving Standard Workflow Event History Limits

A daily batch financial settlement state machine runs as a Step Functions Standard Workflow. The state machine contains a loop that checks the status of 40,000 individual merchant ledger items sequentially. After running for 3 hours, the execution abruptly fails with the following CloudWatch error:

```text
ExecutionHistoryExceeded: The execution history of the state machine has reached the maximum size of 25,000 events.
```

What architectural modification should the developer make to allow the state machine to process all 40,000 items reliably?

- [ ] **A.** Submit a service quota increase request to AWS Support to increase the execution history limit to 100,000 events.
- [ ] **B.** Increase the `TimeoutSeconds` of the state machine from 3 hours to 24 hours.
- [ ] **C.** Refactor the processing loop to use a `Map` state configured with **Distributed Map mode**, or launch child state machine executions using `arn:aws:states:::states:startExecution.sync:2`.
- [ ] **D.** Change the Lambda function memory from 512 MB to 1,769 MB to speed up processing.

<details>
<summary>Click to view Answer & Detailed Explanation</summary>

**Correct Answer: C**

**Mechanical Sympathy Breakdown:**
* **C is correct**: The 25,000 event history limit in Standard Workflows is a **hard service limit that cannot be increased** by AWS Support. To process large iterative batches without exceeding the limit:
  1. Use **Distributed Map mode**: Runs iterations as separate child workflow executions, each with its own independent 25,000 event history buffer.
  2. Use **Nested State Machines**: A parent state machine starts child executions to isolate event logs.
* **A is incorrect**: The 25,000 event limit is a hard physical limit; quota increases are not available.
* **B is incorrect**: Execution history limit is based on event count, not duration.
* **D is incorrect**: Memory changes do not affect state transition event counts.

</details>

### Question 4: ASL Retry Configuration with Exponential Backoff

A developer wants to configure an ASL `Task` state that calls an external payment gateway Lambda function. Due to occasional downstream network timeouts, the task should retry only when encountering `Lambda.ServiceException` or `PaymentTimeoutException`. 

The retry strategy must wait **3 seconds** before the first retry, increase the delay by a factor of **2** on each subsequent retry, and attempt a maximum of **3 retries**.

Which ASL `Retry` configuration correctly implements this policy?

- [ ] **A.**
  ```json
  "Retry": [
    {
      "ErrorEquals": [ "Lambda.ServiceException", "PaymentTimeoutException" ],
      "IntervalSeconds": 3,
      "MaxAttempts": 3,
      "BackoffRate": 2.0
    }
  ]
  ```
- [ ] **B.**
  ```json
  "Retry": [
    {
      "ErrorEquals": [ "States.ALL" ],
      "DelaySeconds": 3,
      "MaxRetries": 3,
      "Multiplier": 2.0
    }
  ]
  ```
- [ ] **C.**
  ```json
  "Retry": [
    {
      "ErrorEquals": [ "Lambda.ServiceException", "PaymentTimeoutException" ],
      "IntervalSeconds": 2,
      "MaxAttempts": 3,
      "BackoffRate": 3.0
    }
  ]
  ```
- [ ] **D.**
  ```json
  "Retry": [
    {
      "Errors": [ "PaymentTimeoutException" ],
      "IntervalSeconds": 3,
      "Attempts": 3,
      "Backoff": 2.0
    }
  ]
  ```

<details>
<summary>Click to view Answer & Detailed Explanation</summary>

**Correct Answer: A**

**Mechanical Sympathy Breakdown:**
* **A is correct**: The official ASL specification uses:
  * `ErrorEquals`: Array of error names or custom exception class names.
  * `IntervalSeconds`: Initial delay before the first retry (3 seconds).
  * `MaxAttempts`: Maximum number of retry attempts (3).
  * `BackoffRate`: Exponential multiplier (2.0: wait times will be 3s, 6s, 12s).
* **B, C, and D are incorrect**: Contain invalid ASL field names (`DelaySeconds`, `MaxRetries`, `Multiplier`, `Backoff`) or incorrect parameter values.

</details>

### Question 5: Diagnosing Missing Compensating Rollbacks

A developer deploys a Saga state machine containing two tasks: `ReserveSeat` and `ChargeCreditCard`. If `ChargeCreditCard` fails, the state machine should transition to `CancelSeatReservation`.

During production testing, when `ChargeCreditCard` throws `CreditCardDeclinedException`, the state machine immediately terminates with status `FAILED` and `CancelSeatReservation` is never invoked.

Reviewing the ASL definition:
```json
"ChargeCreditCard": {
  "Type": "Task",
  "Resource": "arn:aws:states:::lambda:invoke",
  "Parameters": { "FunctionName": "...", "Payload.$": "$" },
  "Catch": [
    {
      "ErrorEquals": [ "InsufficentFundsException" ],
      "Next": "CancelSeatReservation"
    }
  ],
  "Next": "OrderCompleted"
}
```

What is the root cause of this failure?

- [ ] **A.** The `Catch` block is missing `"ResultPath"`, causing the task to fail immediately.
- [ ] **B.** The `ErrorEquals` array only catches `InsufficentFundsException`, which does not match `CreditCardDeclinedException`. Because no other catch handler or `States.ALL` wildcard was defined, the unhandled error defaulted to immediate execution failure.
- [ ] **C.** Compensating rollbacks in Step Functions require a `Choice` state; `Catch` cannot route to tasks directly.
- [ ] **D.** The Lambda function timeout was reached, which cannot be caught by ASL `Catch` blocks.

<details>
<summary>Click to view Answer & Detailed Explanation</summary>

**Correct Answer: B**

**Mechanical Sympathy Breakdown:**
* **B is correct**: In ASL, `Catch` blocks evaluate `ErrorEquals` sequentially. If an error does not match any specified error name, Step Functions fails the execution immediately. Because `CreditCardDeclinedException` was not listed in `ErrorEquals` and no fallback `States.ALL` rule was present, the error went unhandled. Adding `States.ALL` or `CreditCardDeclinedException` to `ErrorEquals` resolves the issue.
* **A is incorrect**: Omitting `ResultPath` in a `Catch` block defaults to `"$"` (capturing the error payload), but does not prevent the catch transition from executing.
* **C is incorrect**: `Catch` blocks can transition directly to any valid ASL state.
* **D is incorrect**: Lambda timeouts can be caught using `States.Timeout` or `States.ALL`.

</details>
