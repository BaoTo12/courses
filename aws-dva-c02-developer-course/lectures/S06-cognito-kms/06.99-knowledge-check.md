## Question 1: Resolving Unexpected 403 Forbidden After Successful Authorizer Call

A developer deploys a REST API on Amazon API Gateway protected by a Lambda Custom Token Authorizer. A frontend application sends an HTTP `GET /orders/101` request with a Bearer token. The authorizer executes, verifies the token, and returns the following IAM policy:

```json
{
  "principalId": "user-456",
  "policyDocument": {
    "Version": "2012-10-17",
    "Statement": [{
      "Action": "execute-api:Invoke",
      "Effect": "Allow",
      "Resource": "arn:aws:execute-api:us-east-1:123456789012:api-123/prod/GET/orders/101"
    }]
  }
}
```

The `GET` request succeeds with HTTP 200 OK. Immediately following this, the client issues a `POST /orders` request using the identical Bearer token. The request fails with HTTP 403 Forbidden, and CloudWatch logs show the authorizer Lambda function was not invoked for the `POST` request.

What is the root cause of this failure, and how should the developer resolve it?

- [ ] A) The authorizer Lambda function threw an unhandled exception on the POST request; the developer must increase Lambda timeout.
- [ ] B) API Gateway cached the initial policy for 300 seconds keyed by the token; because the cached policy explicitly allowed only `GET/orders/101`, the `POST` request was denied. The authorizer should wildcard the method and path (`*/*`) in the Resource ARN.
- [ ] C) API Gateway does not support caching policies across different HTTP methods; the developer must disable CORS.
- [ ] D) The client must obtain a new Cognito ID token before making a POST request.

<details>
<summary><b>View Answer & Explanation</b></summary>

**Correct Answer:** **B**

**Explanation:**
API Gateway caches authorizer output policies by default for **300 seconds** (5 minutes), using the authorization token as the cache key. In this scenario:
1. When the client called `GET /orders/101`, the authorizer generated a statement whose `Resource` ARN was restricted strictly to `.../GET/orders/101`.
2. API Gateway saved `{ Token -> Allow .../GET/orders/101 }` into its authorizer cache.
3. When the same client called `POST /orders` within the 5-minute window with the same token, API Gateway retrieved the cached policy. Because the cached policy only permitted `GET/orders/101`, API Gateway denied the `POST` call without executing the Lambda authorizer.
4. **Resolution**: The authorizer must return a policy that wildcards the HTTP method and resource path (e.g., `arn:aws:execute-api:us-east-1:123456789012:api-123/prod/*/*`) so that the cached policy permits other endpoints.
</details>

## Question 2: Encrypting Large Customer Documents in AWS KMS

A developer is building a document archiving service that stores 5 MB customer PDF contracts in Amazon S3. Security compliance mandates that all documents must be encrypted client-side using AWS KMS before being transmitted to S3.

The developer writes code that reads the 5 MB PDF into a byte array and calls `kmsClient.encrypt()` passing the byte array in the `Plaintext` parameter. The operation fails with `ValidationException`.

What is the reason for this failure, and what is the AWS-recommended architecture?

- [ ] A) The KMS Key Policy is missing `kms:EncryptLargePayload`; the developer must update the key policy.
- [ ] B) AWS KMS `Encrypt` has a hard payload limit of 4 KB; the developer should use the **Envelope Encryption** pattern by calling `GenerateDataKey` to obtain a data key, encrypting the 5 MB document locally with AES-256-GCM, and storing the encrypted data key alongside the ciphertext.
- [ ] C) Client-side encryption is unsupported with AWS KMS; the developer must use S3 Server-Side Encryption (SSE-S3) instead.
- [ ] D) The developer must compress the PDF using GZIP to bring it under the 1 MB KMS limit.

<details>
<summary><b>View Answer & Explanation</b></summary>

**Correct Answer:** **B**

**Explanation:**
The AWS KMS `Encrypt` API has a hard physical ceiling of **4,096 bytes (4 KB)**. It cannot directly encrypt payloads larger than 4 KB. To encrypt larger payloads (such as a 5 MB PDF), AWS prescribes **Envelope Encryption**:
1. Call `kmsClient.generateDataKey()` to obtain a 256-bit AES Data Encryption Key (DEK). KMS returns a plaintext DEK and a ciphertext DEK.
2. Encrypt the 5 MB document locally using the plaintext DEK via an authenticated symmetric cipher like AES-GCM.
3. Wipe the plaintext DEK from memory.
4. Upload the encrypted document and the encrypted DEK to S3.
</details>

## Question 3: Choosing the Correct Cognito Service for Direct S3 Access

A mobile photo-sharing application allows users to register using email and password or social identity providers (Google and Apple). Once authenticated, mobile clients need to upload photos directly to a private Amazon S3 bucket using temporary, scoped AWS IAM credentials without routing upload traffic through an application backend.

Which AWS architecture meets these requirements?

- [ ] A) Use Amazon Cognito User Pools for user registration and authentication, and federate the User Pool with an Amazon Cognito Identity Pool to vend temporary AWS STS credentials for S3 uploads.
- [ ] B) Use Amazon Cognito User Pools only, and configure the S3 bucket policy to trust Cognito Access Tokens directly.
- [ ] C) Use Amazon Cognito Identity Pools only, and store passwords in an Amazon DynamoDB table.
- [ ] D) Generate long-term IAM User Access Keys for each registered user and store them in the mobile device's keychain.

<details>
<summary><b>View Answer & Explanation</b></summary>

**Correct Answer:** **A**

**Explanation:**
This is the quintessential DVA-C02 Cognito architecture:
* **Cognito User Pools** handles user authentication, profile directories, social federation (Google/Apple), and password lifecycles, issuing JWT tokens.
* **Cognito Identity Pools (Federated Identities)** takes the JWT issued by the User Pool and exchanges it via AWS STS (`AssumeRoleWithWebIdentity`) for temporary AWS IAM credentials (Access Key, Secret Key, Session Token).
* The client then uses these IAM credentials with the AWS SDK to perform `s3Client.putObject()` directly against the S3 bucket according to the IAM role's permissions.
</details>

## Question 4: Secrets Manager Rotation Failure Safeguards

An application relies on an AWS Secrets Manager secret containing database credentials. Automated rotation is configured using a custom AWS Lambda rotation function executing the 4-step rotation process (`createSecret`, `setSecret`, `testSecret`, `finishSecret`).

During a scheduled rotation, the database network experiences a transient partition during the **`testSecret`** step, causing the test connection to time out.

What happens to the secret versions in AWS Secrets Manager as a result of this failure?

- [ ] A) Secrets Manager deletes the secret entirely, triggering an immediate application outage.
- [ ] B) The secret is marked `AWSCORRUPTED` and rejects all subsequent reads until administratively unlocked.
- [ ] C) The `AWSCURRENT` staging label remains on the previous working secret version; the new unverified secret remains labeled `AWSPENDING`, ensuring live application traffic is not disrupted.
- [ ] D) Secrets Manager automatically promotes the unverified secret to `AWSCURRENT` and attempts to repair the database.

<details>
<summary><b>View Answer & Explanation</b></summary>

**Correct Answer:** **C**

**Explanation:**
The 4-step rotation lifecycle is specifically designed for high availability and zero downtime:
* `createSecret` creates the new secret labeled `AWSPENDING`.
* `setSecret` updates the password on the target database.
* `testSecret` verifies that the `AWSPENDING` credential can actually log in.
If `testSecret` fails, the rotation Lambda exits with an error and **does not execute `finishSecret`**. Because `finishSecret` was never reached, the **`AWSCURRENT` label remains attached to the existing valid secret version**. Existing application instances continuing to read `AWSCURRENT` suffer zero downtime.
</details>

## Question 5: KMS Key Policy vs. IAM Policy Evaluation

A developer creates a Customer Managed Key (CMK) in AWS KMS to encrypt database backups. The developer attaches an IAM policy to an administrative IAM user:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "kms:*",
    "Resource": "*"
  }]
}
```

The KMS Key Policy on the CMK contains only the following statement:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AllowAppRoleOnly",
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::123456789012:role/AppRole" },
    "Action": "kms:Decrypt",
    "Resource": "*"
  }]
}
```

When the administrative IAM user attempts to call `kms:DescribeKey` or `kms:PutKeyPolicy` on this CMK, the request fails with `AccessDeniedException`.

Why is the administrative IAM user denied access?

- [ ] A) The IAM policy uses `"Resource": "*"` which is forbidden for KMS actions.
- [ ] B) In AWS KMS, Key Policies are the primary authorization document; because the Key Policy does not contain a statement delegating access to the AWS root account (`arn:aws:iam::123456789012:root`) and does not mention the IAM user, IAM policies have no effect.
- [ ] C) Administrative users can only access KMS via the AWS Management Console, not via the CLI.
- [ ] D) The developer must enable AWS KMS VPC Endpoints before administrative policies apply.

<details>
<summary><b>View Answer & Explanation</b></summary>

**Correct Answer:** **B**

**Explanation:**
In AWS KMS, **Key Policies are mandatory and primary**. Unlike other services where an IAM policy is sufficient, KMS requires the Key Policy to explicitly permit the action OR to delegate permission control to IAM by allowing the account root principal:
```json
{
  "Sid": "EnableIamUserPermissions",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::123456789012:root" },
  "Action": "kms:*",
  "Resource": "*"
}
```
If this root delegation statement is omitted and the IAM user is not explicitly named in the Key Policy, the Key Policy alone governs access. Since only `AppRole` was granted `kms:Decrypt`, all other users (even administrators with `kms:*` IAM policies) are denied.
</details>

## Section 06 Mastery Summary

| Focus Area | Core Takeaway |
|---|---|
| **Cognito Tokens** | ID Token (`token_use: id`) is for UI/client; Access Token (`token_use: access`) is for API Gateway and microservice authorization. |
| **Authorizer Caching** | API Gateway caches policies for 300s by token; always wildcard methods (`*/*`) to avoid cross-endpoint 403 collisions. |
| **KMS Limits & DEKs** | KMS `Encrypt` is capped at 4 KB; use `GenerateDataKey` Envelope Encryption for arbitrary payload sizes. |
| **Heap Hygiene** | Wiping `byte[]` arrays with `Arrays.fill()` prevents cryptographic key leakage in JVM heap dumps. |
| **Secrets Manager** | Automated rotation's 4-step design guarantees `AWSCURRENT` is never swapped until `testSecret` succeeds. |
