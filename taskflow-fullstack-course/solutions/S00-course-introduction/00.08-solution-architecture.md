**How the two clients get their HTML:** TaskFlow Admin receives **finished HTML** from the server for every navigation. A Servlet loads data, forwards to a JSP, and the JSP (running in Tomcat) writes HTML text into the response. TaskFlow Web receives a small HTML shell and a JavaScript bundle **once**; after that it receives **JSON**, and React builds the HTML (DOM) **inside the browser**. Both call the same filters, services and database; only the last step differs.

**Cookies:**

| Cookie | Set by | Readable by JS? | Sent by |
|---|---|---|---|
| `JSESSIONID` | Tomcat (server) at session creation, changed at login | **No** (HttpOnly) | Browser, automatically, to the Tomcat origin |
| `XSRF-TOKEN` | Server (`/api/auth/csrf`) | **Yes** (by design; js-cookie reads it) | Browser as a cookie **and** JS copies it into a header |
| `lang` | React (i18next detector / js-cookie) **or** JSP language switcher | Yes | Browser, automatically; read by `LocaleFilter` on the server |
| `theme` | React (js-cookie) or JSP switcher | Yes | Browser, automatically |

## 2. Reference `docs/security/threat-notes.md`

```markdown
# TaskFlow Threat Notes (v0, S00)

## Assets
- Users' tasks and comments (confidentiality + integrity)
- User credentials (password hashes) and active sessions
- Admin capabilities (user management, audit log)
- The audit log itself (must be tamper-resistant)
- Availability of login and task APIs

## Entry points
- URL paths and query parameters (both clients)
- HTML form fields, including hidden fields (Admin Portal)
- JSON request bodies (API)
- HTTP headers (Origin, Referer, User-Agent, X-XSRF-TOKEN…)
- Cookies (JSESSIONID, XSRF-TOKEN, lang, theme). All user-editable.
- Stored data written by other users (comments, task titles) that is later rendered

## Trust boundaries
- Browser ⇄ Tomcat: every HTTP request. Everything in the browser, including our own
  React app and its Redux state, is untrusted.
- Tomcat ⇄ MySQL: trusted, but only via our DAOs with a least-privilege DB user.
- Other websites the user visits ⇄ our origin: they can make the browser send requests
  to us (with cookies), but must not be able to read responses.

## Top 5 things that could go wrong
| # | What could go wrong | Asset | Entry point | First defence idea |
|---|---|---|---|---|
| 1 | Change ?id= to see/edit another user's task | Tasks | URL/JSON id | Ownership check on the server |
| 2 | A comment containing <script> runs in admins' browsers | Sessions/admin | Stored comments | Encode output (JSTL c:out, React text) |
| 3 | Search box text changes the SQL query | All data | Query param | Prepared statements |
| 4 | Another site submits "delete task" using my cookies | Tasks | Cross-site request | CSRF token, SameSite |
| 5 | Password guessing on /login | Accounts | Login form/API | Throttling, generic errors |
```

## 3. Line-by-line reasoning

### Why the boundary sits at the edge of Tomcat, not the edge of "our code"

The most common mistake is drawing the React app inside the trusted zone because "we wrote it". What matters isn't who *wrote* the code but who *controls the machine it runs on*. The user controls their browser: they can edit the JS, change Redux state in DevTools, or ignore the UI entirely and use curl. That's why arrow labels include "DevTools / curl / Postman" going directly into Tomcat: **the server can't tell** whether a request came from our React app or from a hand-crafted script.

### Why MySQL is only reachable from Tomcat

The browser never talks SQL. If a diagram shows the browser connected to the database, it would imply the database accepts connections from the internet, a severe misconfiguration. Only the DAO layer talks to MySQL, using a DB user with minimal permissions (S28, S36).

### Why no Java object crosses to the browser

Only HTTP text crosses the boundary. A `List<Task>` becomes HTML text (JSP) or JSON text (API) **before** it leaves Tomcat. If your diagram labelled an arrow "Task objects → browser", relabel it "HTML" or "JSON".

### Why the build-time box is separate

Sass, TypeScript and Maven run on developer machines or CI, before deployment. Separating them reinforces the "where and when" model: SCSS variables and TS types don't exist at runtime.

### Why data from the database appears as an entry point

Stored XSS works because data *written by an attacker earlier* comes back out of *your own* database and gets rendered into *another user's* page. "It came from our DB, so it's trusted" is exactly the wrong assumption. Treat stored user content as untrusted at the moment you **output** it.

## 4. Common wrong answers and why they fail

| Wrong answer | Why it fails |
|---|---|
| "The React app validates input, so the server doesn't need to." | The user can bypass the React app entirely. Server-side validation is mandatory (S11, S37). |
| "HttpOnly cookies are safe from everything." | HttpOnly stops **JavaScript reading** the cookie. It doesn't stop the browser **sending** it, which is why CSRF protection is still needed. |
| "CORS protects our API from attackers." | CORS controls whether *other websites' JavaScript* can *read* responses in a browser. curl ignores CORS completely (S47). |
| "Admin pages are safe because the link is hidden." | Hidden links are UX. `/admin/*` must be protected by an authorisation filter (S42). |
