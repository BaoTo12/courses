## A. `isOverdue`

```ts
/** A task is overdue if it has a due date before `today` and is not DONE. */
export function isOverdue(task: Task, today: IsoDate): boolean {
  return task.status !== 'DONE' && task.dueDate !== null && task.dueDate < today;
}
```

(Import `IsoDate` from `./domain` alongside the other types.)

- **Narrowing through `&&`**: after `task.dueDate !== null &&`, TypeScript knows the right-hand side sees a `string`, so `<` compares two strings. Without that check: `'task.dueDate' is possibly 'null'`.
- **String comparison of ISO dates** is correct because `YYYY-MM-DD` sorts lexicographically in date order. It would break with `DD/MM/YYYY`, one more reason APIs use ISO 8601.
- **`today` as a parameter** keeps the function **pure**: same input → same output. With `new Date()` inside, the test would pass today and fail next month. The caller (a component or selector) provides "today", which is also how you'll make overdue logic testable in Redux selectors (S21).
- **Time zones:** "today" should be computed in the **user's** time zone (e.g. `new Date().toLocaleDateString('en-CA')` gives `YYYY-MM-DD` in local time). `toISOString().slice(0, 10)` uses **UTC**, which gives the wrong day for Vietnamese users (UTC+7) **before 07:00 local time**: at 05:00 on 1 October in Hanoi it's still 30 September in UTC, so a task due "today" would look like it's due tomorrow. (Verified: `new Date('2026-10-01T05:00:00+07:00').toISOString().slice(0, 10)` → `'2026-09-30'`.) That's a classic bug, and a good reason to keep date logic in one tested helper.

## B. `countByPriority`

```ts
export function countByPriority(tasks: readonly Task[]): Record<Priority, number> {
  const counts: Record<Priority, number> = { LOW: 0, MEDIUM: 0, HIGH: 0 };
  for (const task of tasks) {
    counts[task.priority] += 1;
  }
  return counts;
}
```

Tests:

```ts
describe('countByPriority (05.11)', () => {
  it('always returns all three keys', () => {
    expect(countByPriority([])).toEqual({ LOW: 0, MEDIUM: 0, HIGH: 0 });
  });
  it('counts per priority', () => {
    expect(countByPriority(makeTasks())).toEqual({ LOW: 1, MEDIUM: 1, HIGH: 1 });
  });
});
```

The `Record<Priority, number>` annotation on `counts` does real work: if a new priority `'CRITICAL'` is added to the union, this literal fails to compile (`Property 'CRITICAL' is missing`). The type system points you to the code that must change.

## C. `loadTasks` (`src/api.ts`)

```ts
import type { Task } from './domain';

/**
 * Load tasks from a JSON document shaped like { "tasks": [ ... ] }.
 * The response body is untrusted: it is treated as `unknown` and checked before use.
 */
export async function loadTasks(url: string): Promise<Task[]> {
  const response = await fetch(url);
  if (!response.ok) {
    throw new Error(`Failed to load tasks: HTTP ${response.status}`);
  }

  const data: unknown = await response.json();

  if (typeof data === 'object' && data !== null && 'tasks' in data && Array.isArray(data.tasks)) {
    // ⚠️ Remaining gap: Array.isArray narrows to any[], so each ELEMENT is still unchecked.
    // We trust that every element is a Task. Per-item validation arrives with type guards (06.08).
    return data.tasks;
  }

  throw new Error('Invalid response: expected { tasks: [...] }');
}
```

Tests (`src/api.test.ts`), stubbing the global `fetch`:

```ts
import { afterEach, describe, expect, it, vi } from 'vitest';
import { loadTasks } from './api';

const respondWith = (body: unknown, status = 200) =>
  vi.stubGlobal('fetch', async () => new Response(JSON.stringify(body), { status }));

afterEach(() => {
  vi.unstubAllGlobals();
});

describe('loadTasks', () => {
  it('returns the tasks array', async () => {
    respondWith({ tasks: [{ id: 1, title: 'A' }] });
    await expect(loadTasks('/db.json')).resolves.toHaveLength(1);
  });

  it('throws with the HTTP status on non-2xx', async () => {
    respondWith({ error: 'nope' }, 503);
    await expect(loadTasks('/db.json')).rejects.toThrow('HTTP 503');
  });

  it('throws on an unexpected shape', async () => {
    respondWith({ error: 'Unauthorized' });
    await expect(loadTasks('/db.json')).rejects.toThrow('Invalid response');
  });

  it('throws when tasks is not an array', async () => {
    respondWith({ tasks: 'oops' });
    await expect(loadTasks('/db.json')).rejects.toThrow('Invalid response');
  });
});
```

### Reasoning

- **`const data: unknown = await response.json()`**: `response.json()` is typed `Promise<any>` in the DOM library. Annotating the variable as `unknown` immediately **downgrades** the `any` to something safe; from here on the compiler forces checks.
- **The narrowing chain**: `typeof … 'object'` → `!== null` → `'tasks' in data` → `Array.isArray(data.tasks)`. Each step is a runtime check that TS tracks (05.07).
- **The honest gap**: `Array.isArray` narrows to `any[]`. Verified with the compiler: assigning `data.tasks` to a `number` reports `Type 'any[]' is not assignable to type 'number'`. So returning it as `Task[]` compiles *without* checking the elements. The comment makes the gap visible to reviewers. In 06.08 you'll write `isTask(value): value is Task` and use `data.tasks.every(isTask)`.
- **Test 3 is the realistic one**: an expired session typically returns `{ "error": "Unauthorized" }`. With `as Task[]`, that object would flow into the app and crash on `.map`. With the checks, you get a clear error at the boundary.
- **`vi.stubGlobal` + `unstubAllGlobals`**: replace `fetch` for one test and restore it afterwards so tests don't leak into each other.

## Common wrong approaches

| Attempt | Problem |
|---|---|
| `return (await response.json()) as Task[];` | Forbidden by the task, and it's the 05.13 bug: no check at all. |
| `const data = await response.json(); return data.tasks;` | `data` is `any`, so this compiles and checks nothing. |
| Checking `response.status === 200` only | `201`/`204` are also success; use `response.ok` (200–299). |
| `catch (e) { return []; }` around everything | Hides real failures (network down looks like "no tasks"). Let errors surface; the UI decides how to show them. |
| `isOverdue` using `new Date()` inside | Impure, time-dependent tests, and time-zone surprises. |
