## A. `groupBy`

```ts
/** Group by the value of a property. Keys only exist for values that occur. (06.12) */
export function groupBy<T, K extends keyof T>(
  items: readonly T[],
  key: K,
): Map<T[K], T[]> {
  const groups = new Map<T[K], T[]>();
  for (const item of items) {
    const groupKey = item[key];
    const group = groups.get(groupKey);
    if (group) {
      group.push(item);
    } else {
      groups.set(groupKey, [item]);
    }
  }
  return groups;
}
```

### Why `Map` and not `Record`

- **Key types:** `Record<K, V>` needs `K extends string | number | symbol`. The compiler confirms: `Record<null, string>` → `Type 'null' does not satisfy the constraint 'string | number | symbol'.` `Task['categoryId']` is `number | null`, so a `Record` can't even be declared for it.
- **Runtime keys:** object keys are strings at runtime (`groups[1]` is stored as `'1'`), and `null` would become `'null'`. A `Map` keeps the **real values** (`1`, `null`) as keys.
- **Order:** `Map` iterates in insertion order, so "first seen" order comes for free.

`groupByStatus` (04.14) returned a `Record<TaskStatus, Task[]>` with **all** keys pre-filled. That's a different contract (fixed columns). Generic `groupBy` only knows the values that occur, so a `Map` fits.

### How the types flow

```ts
groupBy(tasks, 'categoryId');
// T = Task (from tasks), K = 'categoryId' (from the literal) → Map<number | null, Task[]>
groupBy(tasks, 'categoryId').get(null);   // Task[] | undefined ✅
groupBy(tasks, 'nope');
// error TS2345: Argument of type '"nope"' is not assignable to parameter of type 'keyof Task'.
```

`get` returns `T[] | undefined` because the key might not exist. The same honesty as `noUncheckedIndexedAccess`.

## B. Labels (`src/labels.ts`)

```ts
import type { Priority, TaskStatus } from './domain';
import { assertNever } from './guards';

/** Exhaustive switch: adding a status to TASK_STATUSES breaks the build here. (06.12) */
export function statusLabel(status: TaskStatus): string {
  switch (status) {
    case 'TODO':
      return 'To do';
    case 'IN_PROGRESS':
      return 'In progress';
    case 'DONE':
      return 'Done';
    default:
      return assertNever(status);
  }
}

/** Alternative: a Record lookup table. Also exhaustive (missing key = compile error). */
export const PRIORITY_COLOR: Record<Priority, string> = {
  LOW: '#14b8a6',
  MEDIUM: '#f59e0b',
  HIGH: '#ef4444',
};

export function priorityColor(priority: Priority): string {
  return PRIORITY_COLOR[priority];
}
```

**Switch vs `Record`:** both are exhaustive. A `Record` is shorter for pure value lookups; a `switch` is better when branches do different *work*. (In S25 these labels move to i18next translation files, and the exhaustiveness check moves to typed translation keys.)

## C. What happens when `'BLOCKED'` is added

Actual compiler output from the reference project:

```text
src/labels.ts(14,26): error TS2345: Argument of type '"BLOCKED"' is not assignable to parameter of type 'never'.
src/task-utils.ts(61,9): error TS2741: Property 'BLOCKED' is missing in type '{ TODO: never[]; IN_PROGRESS: never[]; DONE: never[]; }' but required in type 'Record<"BLOCKED" | "DONE" | "IN_PROGRESS" | "TODO", Task[]>'.
```

Reading them:
1. **`labels.ts`**: the `switch` doesn't handle `'BLOCKED'`, so `status` in `default` is `'BLOCKED'`, not `never`. You need a label.
2. **`task-utils.ts`**: `groupByStatus` pre-fills a `Record<TaskStatus, Task[]>`, and the literal lacks a `BLOCKED` array. The board needs a fourth column.

And what **didn't** error is just as instructive:
- `isTaskStatus` now accepts `'BLOCKED'` automatically, because it reads the `TASK_STATUSES` **array**. That's "values first, types derived" (06.05) paying off.
- The **SCSS** status map (03.07) knows nothing about TypeScript. `'blocked'` needs colours there too, and no compiler will tell you. Cross-language consistency needs conventions, a checklist, or code generation (S48 discusses generating TS types from Java).

## Common wrong approaches

| Attempt | Problem |
|---|---|
| `function groupBy<T>(items: T[], key: string)` | `item[key]` fails to compile (can't index `T` with `string`), and `'nope'` would be accepted. |
| `Record<string, T[]>` with `String(item[key])` | Compiles, but `null` becomes `'null'`, `1` becomes `'1'`; you lose the key type. |
| `default: return 'Unknown';` in `statusLabel` | Silences exhaustiveness: a new status compiles and shows "Unknown" in the UI. |
| `default: return status as never;` | Also silences the check. `assertNever(status)` fails to compile precisely when you need it to. |
