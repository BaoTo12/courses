## 1. Reference solution

First, two new tokens in `_variables.scss` (add near the colour palette; `@use 'sass:color';` is already at the top from 02.08):

```scss
$color-surface-muted: #f1f5f9;                             // slate 100: disabled backgrounds
$focus-ring-width: 3px;
$color-focus-ring: color.change($color-primary, $alpha: 0.25);
$color-focus-ring-danger: color.change($color-danger, $alpha: 0.25);
```

`styles/components/_form.scss`:

```scss
@use '../abstracts/variables' as *;

.form {
  display: flex;
  flex-direction: column;
  gap: $space-4;
  max-width: 560px;

  &__actions {
    display: flex;
    gap: $space-2;
    margin-top: $space-2;

    // .btn + .btn already adds margin-left; cancel it inside a flex row using gap
    .btn + .btn {
      margin-left: 0;
    }
  }
}

.form-field {
  display: flex;
  flex-direction: column;
  gap: $space-1;

  &__label {
    font-size: $font-size-sm;
    font-weight: $font-weight-medium;
    color: $color-text;
  }

  &__input {
    width: 100%;
    padding: $space-2 $space-3;
    font-size: $font-size-sm;
    line-height: 1.5;
    color: $color-text;
    background: $color-surface;
    border: 1px solid $color-border;
    border-radius: $radius-md;
    transition: border-color 150ms ease, box-shadow 150ms ease;

    &::placeholder {
      color: $color-text-muted;
    }

    // :focus (not :focus-visible) on text inputs: browsers show :focus-visible for
    // inputs even after a mouse click anyway, because the user is about to type.
    // Using :focus keeps behaviour identical and explicit.
    &:focus {
      outline: none;                 // replaced by the ring below (never remove without replacing)
      border-color: $color-primary;
      box-shadow: 0 0 0 $focus-ring-width $color-focus-ring;
    }

    &:disabled {
      background: $color-surface-muted;
      cursor: not-allowed;
    }

    // Invalid by attribute alone (JSP/React may set only aria-invalid)
    &[aria-invalid='true'] {
      border-color: $color-danger;

      &:focus {
        box-shadow: 0 0 0 $focus-ring-width $color-focus-ring-danger;
      }
    }
  }

  // Textarea: vertical resize only
  // @at-root is required: an interpolated #{&} is NOT treated as a parent reference,
  // so without it Sass would output `.form-field textarea.form-field__input`.
  @at-root textarea#{&}__input {
    resize: vertical;
    min-height: 5rem;
  }

  &__help {
    font-size: 0.75rem;
    color: $color-text-muted;
  }

  &__error {
    font-size: 0.75rem;
    font-weight: $font-weight-medium;
    color: $color-danger;
  }

  // Invalid via the wrapper modifier
  &--error &__input {
    border-color: $color-danger;

    &:focus {
      box-shadow: 0 0 0 $focus-ring-width $color-focus-ring-danger;
    }
  }
}
```

Load it in `main.scss` after the other components:

```scss
@use 'components/form';
```

## 2. Compiled selectors (and their specificity)

| SCSS | Compiled selector | Specificity |
|---|---|---|
| `&__input` | `.form-field__input` | (0,1,0) |
| `&:focus` | `.form-field__input:focus` | (0,2,0) |
| `&[aria-invalid='true']` | `.form-field__input[aria-invalid='true']` | (0,2,0) |
| its `&:focus` | `.form-field__input[aria-invalid='true']:focus` | (0,3,0) |
| `@at-root textarea#{&}__input` | `textarea.form-field__input` | (0,1,1) |
| `&--error &__input` | `.form-field--error .form-field__input` | (0,2,0) |
| its `&:focus` | `.form-field--error .form-field__input:focus` | (0,3,0) |

All within the (0,3,0) budget.

## 3. Reasoning behind the key decisions

### Why `&--error &__input` works

Inside `.form-field { … }`, **both** `&`s are replaced by `.form-field`. So `&--error &__input` becomes `.form-field--error .form-field__input`: "an input element of a field that has the error modifier". Using `&` twice keeps the block name in one place; rename the block and everything follows.

### Why the error-focus rule comes after the normal focus rule

`.form-field--error .form-field__input:focus` (0,3,0) beats `.form-field__input:focus` (0,2,0) on specificity anyway, so order doesn't matter here. But for the `aria-invalid` version, both the invalid border (0,2,0) and the normal focus border (0,2,0) have **equal** specificity. Then **source order** decides. Because `&:focus` is written **before** `&[aria-invalid='true']`, the invalid border colour wins even while focused, which is what we want. Swap them and a focused invalid field turns blue. It's a subtle cascade detail worth knowing.

### Why `@at-root textarea#{&}__input` needs interpolation *and* `@at-root`

Writing `textarea&__input` is a Sass error: `&` may only appear at the **start** of a compound selector. Interpolating `#{&}` inserts the parent selector as **plain text** instead. But there's a catch: because it's just text, Sass doesn't know you referenced the parent, so it applies the normal nesting rule and **prepends the parent again**, giving `.form-field textarea.form-field__input`. `@at-root` tells Sass "emit this selector at the root, without prepending the parent", producing the intended `textarea.form-field__input`.

This `#{&}` + `@at-root` combination is a well-known Sass idiom, and a well-known trap when you forget the `@at-root`. An alternative that's simpler and equally fine is a modifier class in the HTML (`.form-field__input--textarea`), but we weren't allowed to change the HTML.

### `:focus` vs `:focus-visible` for text inputs

For buttons, `:focus-visible` hides the ring after a mouse click. For **text inputs**, browsers treat focus as "visible" even after clicking, because a caret appears and the user will type. So `:focus` and `:focus-visible` behave the same for inputs. Either is acceptable; the important part is **never** removing the outline without a replacement.

### Why also style `[aria-invalid='true']`

Later, JSP (S37) and React (S11) will mark invalid fields. `aria-invalid` is what **screen readers** use to announce "invalid". If the visual state is tied to the same attribute, you can't forget one of them: the accessibility attribute *is* the style hook.

## 4. Common wrong approaches

| Approach | Problem |
|---|---|
| `.form .form-field .form-field__input:focus { … }` | Specificity (0,4,0) for no reason; breaks the budget; couples the style to `.form` being a parent. |
| `outline: none;` with no replacement | Keyboard users can't see where focus is. An accessibility failure. |
| `input, select, textarea { … }` (element selectors, globally) | Styles *every* control in the app, including third-party widgets; hard to override. Scoped classes are safer. |
| Colour-only error indication | Colour-blind users may not notice. Our solution also shows **text** (`.form-field__error`). |
| Hard-coded `#dc2626` in `_form.scss` | Bypasses tokens; the next theme change misses it. |
