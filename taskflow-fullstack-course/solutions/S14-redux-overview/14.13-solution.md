## Part A: where each piece of data lives

| # | Data | Home | Why |
|---|---|---|---|
| 1 | Tasks from the API | **Redux** (`tasks`), later the **RTK Query** cache (S22) | Read by the list, board, details, dashboard and badge; changed by many events. |
| 2 | Loading/error status of the list | **Redux**, next to the tasks | It describes the same data; components render loading/error states from it. |
| 3 | Categories | **Redux** (`categories`) | Shared (sidebar, form select, badges), rarely changes, loaded once. |
| 4 | Status filter | **URL** (`?status=`) | Shareable, survives reload and Back (S12). Copying it into Redux would create two sources of truth. |
| 5 | Search text while typing | **URL** (`?q=`, with `replace`) + debounce in the component | Same as 4. The debounced copy is local derived state (`useDebounce`). |
| 6 | Logged-in user | **Redux** (`auth`) | Needed everywhere (header, guards, "can edit"), changed by login/logout/session expiry events. |
| 7 | Theme | **Context** (keep S10's) | Small, rarely changes, and styled-components' `ThemeProvider` already consumes it. Moving it gains nothing. |
| 8 | Toasts | **Redux** (`ui.toasts`) | Raised from anywhere, including non-React code (thunks in S18, the 401 interceptor in S24). A context can't be reached from outside React; the store can. |
| 9 | Form values while typing | **Local** (`TaskForm`) | The Style Guide's rule: only the submitted result becomes global (14.03 §4). |
| 10 | Delete dialog open | **Local** | Only one component cares. |
| 11 | Bulk selection | **Redux** (`ui.selectedTaskIds`) | Several components need it: checkboxes on cards, a "3 selected" toolbar, the bulk action. **Ids only**, in an array. |
| 12 | Open-task count | **Nowhere**: a **selector** | Derived from `tasks`. Storing it would let it disagree with the list. |
| 13 | Id on `/tasks/5` | **URL** (route param) | The URL *is* the identity of the page. |
| 14 | UI language | **i18next** (S25), mirrored in `auth.user.locale` for the server | i18next owns the current language and its own change events; S25 explains the integration. |

The most common mistakes: putting 4, 5 and 12 in Redux ("because Redux is global"), and putting 9 in Redux ("because the form submits to Redux").

## Part B: the state tree

```ts
import type { Category, SortDirection, SortKey, Task, User } from '../domain/types';

/** The lifecycle of one request (RequestState from 06.07, flattened for normalised slices). */
type LoadStatus = 'idle' | 'loading' | 'succeeded' | 'failed';

/** Normalised collection: ordered ids + a lookup table (S19; RTK's EntityState in S21). */
interface Normalised<T> {
  ids: number[];
  entities: Record<number, T>;
}

interface TasksState extends Normalised<Task> {
  status: LoadStatus;
  error: string | null;
}

interface CategoriesState extends Normalised<Category> {
  status: LoadStatus;
}

interface AuthState {
  user: User | null;
  /** 'unknown' until GET /api/auth/me answers (S24): don't redirect to login before we know. */
  status: 'unknown' | 'authenticated' | 'anonymous';
}

interface Toast {
  id: number; // same Toast shape as the S10 ToastProvider
  tone: 'success' | 'error' | 'info';
  message: string;
}

interface UiState {
  toasts: Toast[];
  /** Bulk selection: ids only, never copies of tasks. An array (serialisable), not a Set. */
  selectedTaskIds: number[];
}

/** Remembered user preferences that are NOT part of the URL (the URL owns status/q/view: S12). */
interface ListPrefsState {
  sort: { key: SortKey; direction: SortDirection };
  pageSize: 10 | 20 | 50;
}

export interface RootState {
  tasks: TasksState;
  categories: CategoriesState;
  auth: AuthState;
  ui: UiState;
  listPrefs: ListPrefsState;
}
```

### Design decisions

- **Normalised collections** (`ids` + `entities`). "Show task 17" is `entities[17]`, and "update task 17" replaces one entry: no scanning, no mapping over 500 tasks. `ids` keeps the server's order. You'll write the normalisation by hand in S19, then let `createEntityAdapter` generate it in S21. (In S15 you'll start with a plain array, to learn the basic update patterns first.)
- **`status` + `error` per collection**, not one global "loading" flag: the categories can be loaded while the tasks fail.
- **`auth.status` has three values.** With only `user: User | null`, the app can't tell "not logged in" from "we haven't asked the server yet", and would redirect to `/login` during the first split second of every page load (S24).
- **`selectedTaskIds` is an array of ids.** Copies of tasks would go stale when a task changes; a `Set` isn't serialisable (DevTools, 14.11).
- **`listPrefs` instead of a `filters` slice.** The official Fundamentals tutorial keeps its todo filters in Redux, because that app has no router. TaskFlow already made the URL the source of truth for `status`/`q`/`view` in S12, and we keep it. Only preferences that should **not** be in shareable URLs (your preferred sort and page size) go to Redux. The curriculum's S15 exercise is adjusted accordingly: you'll write a `listPrefsReducer` (plus reducers for the `ui` slice). The patterns you practise are identical.
- **Theme stays in context**, and **no `api` key yet**: RTK Query adds its own cache slice in S22.

What's deliberately **absent**: counts, filtered lists, "all done?" (selectors); form drafts; the current route; `Date` objects (dates stay ISO strings, as they come from the API).

## Part C: 12 actions

| # | Type | Payload | Dispatched when… | Handled by |
|---|---|---|---|---|
| 1 | `tasks/fetchStarted` | — | The list request starts | tasks |
| 2 | `tasks/fetchSucceeded` | `Task[]` | The list arrives | tasks |
| 3 | `tasks/fetchFailed` | `string` (message) | The list request fails | tasks |
| 4 | `tasks/taskAdded` | `Task` (from the server, with its id) | The POST returned 201 | tasks |
| 5 | `tasks/taskUpdated` | `Task` | A PUT/PATCH returned the saved task | tasks |
| 6 | `tasks/taskDeleted` | `taskId: number` | The DELETE returned 204 | tasks, **ui** (drop it from `selectedTaskIds`) |
| 7 | `tasks/completedCleared` | `taskIds: number[]` | The server deleted all completed tasks | tasks, ui |
| 8 | `categories/fetchSucceeded` | `Category[]` | Categories arrive | categories |
| 9 | `auth/loggedIn` | `User` | Login succeeded | auth |
| 10 | `auth/loggedOut` | — | Logout succeeded, or the session expired (401) | **auth, tasks, categories, ui**: everything user-specific resets |
| 11 | `ui/toastShown` / `ui/toastDismissed` | `Toast` / `id` | Something worth telling the user happened / the toast expired or was closed | ui |
| 12 | `listPrefs/sortChanged` | `{ key, direction }` | The user picked another sort order | listPrefs |

### Why events, not setters

Compare `tasks/taskDeleted` with a setter-style `ui/selectedTaskIdsSet`:
- The event says **what happened**, once. Every slice that cares reacts to it (#6 is handled by `tasks` **and** `ui`). The component doesn't need to know which slices exist.
- With setters, the component deleting a task must also remember to dispatch "remove it from the selection", "update the count"… Each new feature adds another dispatch to every call site, and one forgotten dispatch leaves the state inconsistent.
- The DevTools log of events reads like a story: *fetchSucceeded, taskUpdated, loggedOut*. A log of setters reads like assembly: *tasksSet, selectionSet, flagSet*.

#10 is the classic "many slices, one action" (15.10): logging out must clear bob's tasks before alice logs in on the same browser. Missing that is a real data-exposure bug (S24 includes it in the security review).

### About timestamps and ids

None of these payloads is generated inside a reducer. Ids come from the server (#4). Toast ids and timestamps are created where the action is **created** (an action creator or a thunk), never in the reducer (15.04: reducers must be deterministic).
