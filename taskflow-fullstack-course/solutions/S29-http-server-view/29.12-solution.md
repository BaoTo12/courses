# Solution 29.12 · Five Annotated HTTP Exchanges

> Exercise: [`lectures/S29-http-server-view/29.11-your-turn-capture-exchanges.md`](../../lectures/S29-http-server-view/29.11-your-turn-capture-exchanges.md)
> Exchange 2 below is a real capture from the course's mock API. The Tomcat ones show the shape you'll get; dates, lengths and ETags differ on your machine.

---

## 1. Page load (Tomcat, a static file)

```text
> GET /taskflow/ HTTP/1.1           curl: method, path = context "/taskflow" + "/", HTTP/1.1
> Host: localhost:8080              curl (from the URL); Tomcat picks the <Host> from it
> User-Agent: curl/8.18.0           curl
> Accept: */*                       curl: "anything"
< HTTP/1.1 200                      Tomcat 9 sends no reason phrase ("OK") by default
< Accept-Ranges: bytes              DefaultServlet: static files support range requests
< ETag: W/"812-…"                   DefaultServlet: a version tag for caching (If-None-Match → 304)
< Last-Modified: …                  the file's timestamp
< Content-Type: text/html           from conf/web.xml's MIME mapping for .html
< Content-Length: 812               the file's size
< Date: …                           Tomcat
```

The **welcome file** mechanism served `index.html` for `/taskflow/` (28.04). No charset, because a static file's bytes are sent as-is. The page declares `<meta charset="utf-8">` itself.

## 2. Form POST (mock API)

```text
> POST /api/tasks HTTP/1.1
> Content-Type: application/x-www-form-urlencoded     curl -d: form encoding by default
> Content-Length: 30                                   title=Hello+world&priority=HIGH (spaces → +)
< HTTP/1.1 415 Unsupported Media Type                  our server.mjs: JSON bodies only
< X-Powered-By: Express                                Express (a header worth removing in production: it reveals the stack)
< Content-Type: application/json; charset=utf-8        the error body (02-project-spec §5)
```

"415" tells the client to change the **representation**, not the content: send `application/json`.

## 3. Redirect (Tomcat adds the trailing slash)

```text
> GET /taskflow HTTP/1.1
< HTTP/1.1 302
< Location: /taskflow/             Tomcat: a context root without "/" is redirected, so relative URLs resolve correctly
```

curl shows it and stops. `curl -L` would follow. A browser follows it automatically, and relative links like `static/css/app.css` (28.10 §5) then resolve under `/taskflow/`.

## 4. 404 for `WEB-INF`

```text
> GET /taskflow/WEB-INF/web.xml HTTP/1.1
< HTTP/1.1 404
< Content-Type: text/html;charset=utf-8     Tomcat's default error page (S43 replaces it)
```

The file exists, and the container refuses by specification (28.04 §3). A 404, not a 403, doesn't even confirm it's there.

## 5. JSON call from TaskFlow Web (logged in, secure mock)

```text
GET /api/tasks?sort=dueDate,asc&page=0&size=20 HTTP/1.1     Axios: params serialised from pageQuery (23.07)
Accept: application/json                                    our Axios instance's default header (13.03)
Cookie: JSESSIONID=…; XSRF-TOKEN=…; tf_lang=vi; …           the BROWSER: every matching cookie (24.01)
X-Request-Id: 3f0c…                                         our request interceptor (13.08)
(no X-XSRF-TOKEN)                                           a GET is safe: the CSRF interceptor skips it (24.11)
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Cache-Control: no-cache
```

A PATCH from the same page would also carry `X-XSRF-TOKEN` (the same value as the cookie) and `Content-Type: application/json`.

## Answers to the recurring questions

- **Client vs you:** `Host`, `User-Agent`, `Accept-Encoding` and `Cookie` come from the program (curl or the browser). `Accept`, `X-Request-Id` and `X-XSRF-TOKEN` come from **your** code.
- **Charset:** present on dynamic responses that set it (Express JSON, Tomcat's error pages). Static HTML relies on `<meta charset>`. Our JSPs will set it explicitly (S32).
