# Solution 26.13 · The Security Audit: Three Planted Issues

> Exercise: [`lectures/S26-frontend-security/26.12-your-turn-security-audit.md`](../../lectures/S26-frontend-security/26.12-your-turn-security-audit.md)
> The fixed patterns are the ones in the reference project, verified by `src/security/security.test.tsx`.

---

## Change 1: credentials in the console, and a production switch anyone can flip

**Checklist items broken:** "Logs … are development-only", "No secrets in … logs" (26.09).

**The attack:**
- `config.data` on `POST /auth/login` is `{ username, password }`, so the password is printed in plain text. It ends up in screenshots attached to bug reports, and in screen recordings.
- `config.headers` contains `X-XSRF-TOKEN`.
- `?debug` works **in production**. An attacker who has XSS (or someone at the shared computer) can turn on verbose logging, and support staff may ask users to "add ?debug and send us the console".

**Fix:** development only, and never bodies or headers. The existing timing log already does this:

```ts
function logTiming(method, url, outcome, metadata) {
  if (!import.meta.env.DEV || metadata === undefined) return;          // dev builds only: no runtime switch
  console.debug(`[api] ${method?.toUpperCase()} ${url} → ${outcome} in ${ms} ms`); // method, URL, status: no payloads
}
```

If production diagnostics are needed, send **scrubbed** events to a server you control, never to the console.

## Change 2: DOM-based / reflected XSS through the URL

**Checklist items broken:** "User content is rendered as text", "The only `dangerouslySetInnerHTML` is `SanitizedHtml`" (26.02, 26.04, 26.07).

**The attack:** `q` comes from `?q=` in the URL (12.03). A link such as

```text
http://localhost:5173/tasks?q=%3Cimg%20src%3Dx%20onerror%3Dalert(document.cookie)%3E
```

runs script for **anyone who clicks it** while logged in: in a chat, an email, or a task comment. The URL itself is the payload.

**Fix:** React elements instead of an HTML string. `<mark>` is still there:

```tsx
{visibleCount === 0 && q && (
  <p>
    No tasks match <mark>{q}</mark>.
  </p>
)}
```

(With i18n, use `<Trans i18nKey="noMatch" values={{ q }} components={{ mark: <mark /> }} />`, 25.03 §5.)

## Change 3: `javascript:` through `window.open`

**Checklist items broken:** "`window.open` and `location.*` never receive unvalidated URLs" (26.05, 26.06).

**The attack:** a task description containing `[docs](javascript:alert(document.cookie))`. The link in the description is harmless (`SafeLink` renders it as text). But the **button** passes the raw URL to `window.open`, which React never sees. Clicking "Open link" runs the script. With a shared task, or as an admin viewing a user's task (26.03 §3), it's an attack on someone else.

**Fix:** the same policy as `SafeLink`, and no opener:

```tsx
const firstLink = parseLinks(task.description).find((s) => s.kind === 'link');
const href = firstLink?.kind === 'link' ? safeHref(firstLink.url) : undefined;
…
{href && (
  <Button size="sm" onClick={() => window.open(href, '_blank', 'noopener,noreferrer')}>Open link</Button>
)}
```

The button isn't rendered at all for unsafe URLs. Simpler still, make it a `<SafeLink>`.

## A test for fix 3

```ts
it('the popup button only exists for safe URLs', () => {
  const unsafe = parseLinks('[docs](javascript:alert(1))')[0];
  expect(unsafe?.kind === 'link' ? safeHref(unsafe.url, 'http://localhost') : 'n/a').toBeUndefined();
});
```
