# Lecture 10.04 · One Source of Truth for Tokens: CSS Variables vs TypeScript Values

> **Section:** S10 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes

---

## 1. The design question

TaskFlow has **three consumers** of the same design tokens:

```text
             ┌──▶ SCSS components (React + JSP)       compile time
tokens ──────┼──▶ styled-components (React only)       runtime (JS)
             └──▶ JSP portal (HTML + compiled CSS)      server-rendered HTML, no React
```

Where should the token **values** live so that all three stay in sync?

## 2. Option A: SCSS owns the values; the TS theme holds `var()` references

```ts
export const theme = {
  colors: {
    primary: 'var(--color-primary)',
    surface: 'var(--color-surface)',
    priority: { LOW: 'var(--color-priority-low)', … },
  },
};
```

- SCSS (03.13) already emits `--color-*` custom properties for light, dark and "system", with **pure CSS**.
- The styled-components theme is just a **typed map of names → `var()` references**.
- Switching themes changes `data-theme` on `<html>`; **the browser** recomputes every `var()`. The theme object **never changes**, so there are no styled-component re-renders and no new classes.

Verified in TaskFlow's reference app: switching light → dark → system left a priority segment's class name identical (`sc-hKwBjT jANiXY`) and the styled stylesheet at 17 rules, while computed colours followed the theme.

## 3. Option B: TypeScript owns the values; SCSS reads them

Tokens in a TS/JSON file; a build step generates SCSS variables or CSS custom properties from it (tools like Style Dictionary do this). The theme object holds real values.

## 4. Trade-offs

| | Option A: SCSS values + `var()` refs | Option B: TS values (+ generated CSS) |
|---|---|---|
| Single source | ✅ SCSS maps | ✅ TS/JSON tokens |
| JSP portal can use tokens | ✅ natively | ✅ via generated CSS |
| Theme switch cost | Browser recomputes vars; **no React re-render** | Swapping objects re-renders styled components (unless the values are also var()s) |
| JS needs a *real* colour value (canvas chart, colour maths) | Read at runtime: `getComputedStyle(document.documentElement).getPropertyValue('--color-primary')` | Directly available |
| Tooling | None extra | A token build step |
| Typed in TS | ✅ (names) | ✅ (names + values) |

**TaskFlow chooses Option A.** The design system is SCSS-first because the JSP portal needs it, and Option A adds zero tooling. Option B is common in larger organisations with many platforms (web, iOS, Android) sharing tokens.

## 5. Values that can't be CSS variables

Media queries can't use `var()` (02.04). Breakpoints stay **literal values** in both SCSS (`$breakpoints`) and the TS theme (`theme.breakpoints`), which is a small, documented duplication.

## 6. Summary

- Three consumers need the same tokens; values should live in one place.
- Option A (TaskFlow): SCSS owns values → CSS custom properties; the TS theme maps names to `var()` references. No re-render on theme switch.
- Option B: TS owns values and generates CSS; better for multi-platform design systems.
- Breakpoints remain literal in both (media-query limitation).
