## 1. The pieces

```text
            ┌─────────────── i18next instance ───────────────┐
 plugins ──►│ .use(Backend)   where resources come from       │
            │ .use(Detector)  which language to use            │
            │ .use(initReactI18next)  React bindings           │
            │                                                   │
            │ resources: { en: { common: {…}, tasks: {…} },    │
            │              vi: { common: {…}, tasks: {…} } }   │
            │ language: 'vi'   fallbackLng: 'en'               │
            └───────────────────────────────────────────────────┘
 t('tasks:details.edit')  → "Sửa"
     └ns─┘ └──key path──┘
```

| Concept | Meaning | TaskFlow |
|---|---|---|
| **instance** | holds the config, the language and the loaded resources | one app instance (`src/i18n/i18n.ts`); tests create their own |
| **resources** | `language → namespace → nested keys → strings` | `public/locales/{en,vi}/{common,tasks,dashboard}.json` |
| **namespace** | one JSON file; the unit of loading | `common` (always), `tasks`, `dashboard` (on demand) |
| **key** | a dot path inside a namespace | `details.deleteConfirm` |
| **fallbackLng** | used when a key is missing in the current language | `'en'` |
| **plugins** | `.use(x)` before `.init()` | HTTP backend, language detector, react-i18next |

## 2. Key lookup, step by step

`t('details.edit')` in namespace `tasks`, language `vi`:

1. `vi/tasks.json` → `details.edit` found → "Sửa".
2. If it's missing: `en/tasks.json` (the fallback).
3. If that's missing too: the `defaultValue` option, if given.
4. Otherwise: the **key itself**, `details.edit`. That's visible, and it's how you spot missing translations.

## 📇 API card: `i18next.init(options)` (the options TaskFlow uses)

| Option | Type | Default | Meaning |
|---|---|---|---|
| `resources` | object | — | inline translations (tests). Otherwise a backend loads them. |
| `lng` | string | detected | force a language; overrides the detector. Leave it unset with a detector. |
| `fallbackLng` | `string \| string[] \| object` | `'dev'` | where missing keys come from |
| `supportedLngs` | `string[]` | `false` (any) | the allow-list of languages (25.06) |
| `nonExplicitSupportedLngs` | boolean | `false` | accept `vi-VN` when `vi` is supported |
| `load` | `'all' \| 'currentOnly' \| 'languageOnly'` | `'all'` | which codes to load for `vi-VN`: both, `vi-VN` only, or `vi` only |
| `ns` | `string \| string[]` | `'translation'` | namespaces to load at init |
| `defaultNS` | string | `'translation'` | the namespace for keys without `ns:` |
| `interpolation.escapeValue` | boolean | `true` | HTML-escape interpolated values (25.08) |
| `detection` | object | — | the detector's options (25.04) |
| `backend` | object | — | the backend's options (`loadPath`, 25.11) |

**Returns** a Promise that resolves with `t` when the initial resources are loaded.

**Other instance members:** `t(key, options)`, `changeLanguage(lng)`, `language` (the raw value, e.g. `vi-VN`), `resolvedLanguage` (the supported one in use, `vi`), `loadNamespaces(ns)`, `on('languageChanged', cb)`, `createInstance()`, `exists(key)`.

**When to use i18next:** any app with more than one language, or one that will likely get a second.

**When not to:** a single-language internal tool. `Intl` alone covers dates and numbers.

**Common mistakes:**
- Calling `t` at **module level**, before init (e.g. in a constant). It returns keys. Translate at render time.
- Setting `lng` *and* using a detector. `lng` wins, and the detector is ignored.
- Reading `i18n.language` to choose a UI option. It may be `vi-VN`. Use `resolvedLanguage`.
