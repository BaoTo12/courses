# Lecture 00.03 · The Web in One Picture: Where Does Each Piece of Code Run?

> **Section:** S00 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> **Project feature:** none. You'll do a 5-minute experiment in your browser.

---

## 1. Why this lecture matters

Web development spreads one application across several machines and several moments in time. The most common source of confusion, for juniors and seniors alike, is losing track of **which machine** is executing **which code** at **which moment**.

This lecture gives you a single picture you'll reuse for the rest of the course.

---

## 2. The actors

```text
 ┌────────────────────┐        HTTP request         ┌─────────────────────┐        SQL        ┌──────────┐
 │      BROWSER       │ ──────────────────────────▶ │       SERVER        │ ────────────────▶ │ DATABASE │
 │ (user's computer)  │ ◀────────────────────────── │  (Tomcat on a JVM)  │ ◀──────────────── │ (MySQL)  │
 └────────────────────┘        HTTP response        └─────────────────────┘      result rows  └──────────┘
   HTML parser                                          Servlets, filters                        tables
   CSS engine                                           JSP (as servlets)                        indexes
   JavaScript engine                                    EL, JSTL
   cookie storage                                       services, DAOs
```

Three separate programs, usually on separate machines:

1. **The browser** (Chrome, Edge…) on the user's computer. It can do four big things: send HTTP requests, parse HTML into a DOM, apply CSS, and execute JavaScript. It also stores cookies and decides when to send them.
2. **The server**: for us, **Tomcat** running on a Java Virtual Machine. It listens for HTTP requests, runs your Java code, and sends back HTTP responses.
3. **The database**: MySQL. Only the server talks to it. **The browser never talks to the database directly.**

And there's a fourth "place" that isn't a running system at all:

4. **Build time on the developer's machine.** Compilers and bundlers (Sass, TypeScript, Vite, Maven, and Tomcat's JSP translator) transform your source code into what actually runs. Their output is what gets shipped; the source is not.

---

## 3. The only thing that crosses the wire: text (bytes)

Between the browser and the server there is **only HTTP**. HTTP messages are (essentially) text:

```http
GET /taskflow/tasks HTTP/1.1
Host: localhost:8080
Cookie: JSESSIONID=8F2C1A...; lang=vi
Accept: text/html
```

```http
HTTP/1.1 200 OK
Content-Type: text/html;charset=UTF-8
Set-Cookie: ...

<!DOCTYPE html>
<html>…<td>Write report</td>…</html>
```

That's it. No Java objects, no JSP, no Servlet, no `Task` class, no Redux store travels over the network. **Only bytes**: headers and a body. The body might be HTML, CSS, JavaScript, JSON or an image, but it's always just data.

> 🧠 **Mental model:** the network is a slot in a wall. The server can only push *text* through it. The browser can only push *text* back. Everything else stays on its own side of the wall.

This one fact explains a lot:
- A Java object can't be "sent to" JavaScript. It has to be turned into text (HTML or JSON) first, and that conversion happens **on the server**.
- A JavaScript variable can't be "read by" the Servlet. It has to be sent as text (a form field, query parameter, header or JSON body) in a **new** request.

## 4. Timeline of a server-rendered page (JSP)

Let's follow what happens when an admin opens the task list in TaskFlow Admin.

```text
Time ─────────────────────────────────────────────────────────────────────────────────▶

BROWSER   [1 user clicks link] [2 sends GET /tasks]                     [8 receives HTML]
                                                                         [9 parses HTML → DOM]
                                                                         [10 downloads CSS/JS]
                                                                         [11 renders pixels]
                                                                         [12 runs JS, if any]
                                   │                                         ▲
                                   ▼                                         │
SERVER                   [3 Tomcat parses request] [4 filters run]           │
                         [5 TaskListServlet runs → asks service/DAO]         │
                         [6 forward → list.jsp runs: EL + JSTL → HTML text]  │
                         [7 response bytes sent] ─────────────────────────────┘
                                   │         ▲
                                   ▼         │
DATABASE                     [SELECT … FROM tasks]
```

Key facts to lock in:

- Steps 3–7 happen **on the server**, **before** the browser has anything to show.
- The JSP (step 6) **executes on the server**. By the time the browser receives the page, the JSP has *finished* running. The browser never sees JSP syntax, EL or JSTL tags, only their *output*.
- JavaScript on that page (step 12) runs **after** everything on the server has finished. It can't "call back into" the JSP. If it needs more data, it must send a **new** HTTP request.

## 5. Timeline of the React app (SPA)

Now the same data in TaskFlow Web.

```text
BROWSER  [1 open URL] [2 GET /]              [4 gets small index.html]
                                              [5 downloads JS bundle]
                                              [6 JS runs: React renders "Loading…"]
                                              [7 Axios: GET /api/tasks]           [10 receives JSON]
                                                                                  [11 Redux store updated]
                                                                                  [12 React re-renders list]
                              │                             │                          ▲
                              ▼                             ▼                          │
SERVER             [3 returns static index.html]   [8 API Servlet → service → DAO]     │
                                                   [9 writes JSON] ────────────────────┘
```

Key facts:

- The first response (`index.html`) is nearly **empty**: a `<div id="root"></div>` and a `<script>` tag.
- The HTML you eventually see is created **in the browser**, by React, from JSON data.
- Navigating inside the app (e.g. to task details) usually **doesn't request a new page** at all. React swaps components and maybe fetches more JSON.

## 6. Build time: code that never runs in production

Some of your code is transformed before it ever reaches a server or browser:

| You write | Transformed by | Into | When |
|---|---|---|---|
| `*.scss` | Sass compiler | `*.css` | Build time (your machine or CI) |
| `*.ts`, `*.tsx` | TypeScript/Vite (esbuild) | `*.js` | Build time |
| JSX `<TaskCard/>` | Vite/esbuild | `jsx(TaskCard, …)` calls | Build time |
| `*.java` | `javac` via Maven | `*.class` bytecode | Build time |
| `*.jsp` | Tomcat's **Jasper** | `*_jsp.java` → `*_jsp.class` | **First request** (or at deploy with precompilation) |

That last row is special: JSP is translated **on the server**, at runtime, the first time the page is requested. It's still a "compile" step, just a lazy one. You'll read the generated Java code in Lecture 33.03.

Consequences you'll meet repeatedly:
- **SCSS variables** don't exist in the browser. You can't change them from JavaScript (Lecture 02.04).
- **TypeScript types** don't exist at runtime. A JSON response typed as `Task` can still contain anything (Lecture 05.13).
- **JSP tags** don't exist in the browser. "View Source" shows only HTML (Lecture 32.08).

## 7. 🛠 Experiment (5 minutes)

Do this now in Chrome or Edge. It builds the habit that matters most.

1. Open any server-rendered site (e.g. a Wikipedia article).
2. Press **Ctrl+U** (View Source). This is the **exact text the server sent**.
3. Press **F12** → **Elements** tab. This is the **current DOM**, which JavaScript may have changed since.
4. Open **Network** tab, refresh, click the first request (the document):
   - Look at **Headers** → request line, status, `Content-Type`.
   - Look at **Response** → the raw HTML.
5. Now open a single-page app (e.g. a web email client, or any React site) and repeat step 2. Notice how *little* HTML is in View Source compared with what you see on screen.

Write down in one sentence the difference between **View Source** and the **Elements** panel. We'll use this distinction many times, especially in S32 and S49.

## 8. Common mistakes this picture prevents

| Mistake | Why it's wrong |
|---|---|
| "My JSP will update when the user clicks." | The JSP ran once on the server. Clicks are handled by browser JavaScript, or by sending a new request. |
| "I'll pass the Java `user` object to JavaScript." | Only text crosses the wire. The server must write it as JSON/HTML text, and then it's a copy, not the object. |
| "JavaScript can read the session." | The session lives in server memory. The browser only has a cookie with an ID, often not even readable by JS (HttpOnly). |
| "The React app talks to MySQL." | Never. It talks HTTP to the server; only the server talks SQL. |
| "Hiding the button protects the action." | Hiding happens in the browser, which the user controls. Protection must happen on the server. |

---

## 9. Summary

- Three running systems: **browser**, **server (Tomcat)**, **database**. Plus **build time**.
- Only **HTTP text** crosses between browser and server. No objects, no code sharing.
- **JSP executes on the server, before** the browser receives anything; the browser gets only HTML.
- **React executes in the browser, after** the JS bundle arrives; it fetches JSON and builds the DOM.
- SCSS, TypeScript and JSX are **build-time** languages; JSP is translated lazily by Tomcat.

## 10. Check yourself

1. A JSP contains `<script>let count = ${tasks.size()};</script>`. The user adds a task using a JavaScript button that calls the API. Does `count` change? Why?
2. Can the browser run an SQL query against MySQL in TaskFlow? What would it have to do instead?
3. Where does the SCSS `$primary` variable exist at the moment the user clicks a button?
4. What's the difference between View Source and the Elements panel?

<details>
<summary>Answers</summary>

1. **No.** `${tasks.size()}` was evaluated **on the server** when the page was generated; the browser received something like `let count = 7;`, which is now just a JavaScript literal. The JavaScript would have to update `count` itself (or reload the page / fetch fresh data).
2. **No.** It must send an HTTP request to the server (e.g. `GET /api/tasks`); a Servlet calls the service/DAO, which runs the SQL and returns the result as JSON or HTML.
3. **Nowhere.** It existed only at build time. The browser has only the compiled CSS values (or CSS custom properties, if you emitted them).
4. **View Source** = the original bytes the server sent. **Elements** = the live DOM right now, including anything JavaScript created or changed.

</details>
