# Lecture 00.06 · Security Mindset: Assets, Entry Points, Trust Boundaries

> **Section:** S00 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes

## 1. Why security starts in lecture 6, not lecture 500

Security bolted on at the end rarely works. The vulnerabilities in this course (XSS, SQL injection, CSRF, IDOR…) aren't exotic hacker tricks. They're what happens when a normal developer writes normal code **without asking one question**:

> **"What if the person sending this request is not who I think, or not doing what I expect?"**

This lecture gives you a lightweight way of thinking that you'll apply in every part of the course. It isn't a formal threat-modelling framework; it's the mid-level habit that prevents most real-world bugs.

---

## 2. Three words: assets, entry points, trust boundaries

### Assets: what's worth protecting?

In TaskFlow:

| Asset | Why it matters |
|---|---|
| Users' tasks and comments | Private data; might contain confidential work information |
| User accounts (passwords, sessions) | Taking over an account gives access to everything that user can do |
| Admin capabilities | Managing users, viewing audit logs: the highest privilege |
| Integrity of data | Nobody should silently change or delete others' tasks |
| Availability | Login brute force or heavy queries shouldn't take the app down |
| The audit log | If attackers can erase it, you can't investigate |

### Entry points: where can input get in?

Everything an attacker can send you:

- **URLs**: path, query parameters (`?id=5&status=DONE`)
- **Form fields**, including hidden fields
- **JSON request bodies**
- **HTTP headers**: `User-Agent`, `Referer`, `Origin`, custom headers
- **Cookies**, including ones you set yourself (the user can edit them)
- **Uploaded files** (if any)
- **Data from the database that another user originally wrote** (comments!), which is how stored XSS works

### Trust boundaries: where does "trusted" become "untrusted"?

A **trust boundary** is a line where data moves from something you don't control to something you do.

```text
   UNTRUSTED                          │  TRUSTED (you control it)
                                      │
   User's browser                     │  Tomcat + your Java code
   ├─ React app (JS, Redux state)     │  ├─ filters
   ├─ cookies, localStorage           │  ├─ servlets, services, DAOs
   ├─ DevTools, curl, Postman         │  └─ MySQL (through your DAOs only)
   └─ other websites the user visits  │
                                      │
                         ═════ THE BOUNDARY: every HTTP request ═════
```

The critical point: **your own React app is on the untrusted side.** You wrote it, but it runs on the user's machine. The user can open DevTools, modify the JavaScript, edit Redux state, change cookies, or skip the app entirely and send requests with curl.

> 🧠 **Mental model: "The client is not yours."**
> Anything that runs in the browser (JavaScript, hidden fields, disabled buttons, form validation, Redux state, JS-readable cookies) can be read and changed by the user. Security decisions must happen on the server.

## 3. Four questions for every feature

Whenever you build a feature in this course, ask:

1. **Who can call this?** (Anyone? Logged-in users? Only admins? Only the owner?)
2. **What input does it accept, and what if the input is hostile?** (Too long, wrong type, contains `<script>`, contains `' OR 1=1 --`, references someone else's ID.)
3. **Where does output go, and is it encoded for that place?** (HTML body, HTML attribute, JavaScript, URL, SQL.)
4. **What if the request comes from another website** that the logged-in user happens to visit? (CSRF, CORS.)

These four questions catch most vulnerabilities before they're written.

## 4. A preview of the attacks you'll perform (on your own app)

Here's a quick tour. You'll do each one hands-on later.

| Attack | One-line explanation | The question it violates | Lab |
|---|---|---|---|
| **XSS** | Attacker-supplied text is placed into a page as HTML/JS, so the browser runs the attacker's script as if it were yours | Q3: output not encoded | S26, S30, S34, S35 |
| **SQL injection** | Input is glued into an SQL string and changes the query's meaning | Q2: input treated as code | S36 |
| **CSRF** | Another site makes the user's browser send a state-changing request with the user's cookies | Q4: cross-site request | S37, S47 |
| **IDOR** | Changing `id=5` to `id=6` gives access to someone else's data | Q1: no ownership check | S42 |
| **Session fixation** | The attacker makes the victim log in with a session ID the attacker already knows | Q1: identity binding | S41 |
| **Open redirect** | `?returnUrl=https://evil…` bounces users to a phishing site through your trusted domain | Q2: unvalidated input | S24, S41 |
| **Mass assignment** | Sending `"role":"ADMIN"` in a JSON body sets a field that shouldn't be settable | Q2: unexpected input | S37, S46 |
| **Info leakage** | Stack traces reveal versions, SQL and file paths | Q3: output to an attacker | S43 |
| **CORS misconfiguration** | Any website can read your API responses with the user's cookies | Q4 | S47 |

## 5. Two principles you'll see everywhere

### Validate input, encode output

These are two **different** defences for two different problems:

- **Input validation** (at the boundary): reject what doesn't make sense. The title is required and ≤ 200 chars; `status` must be one of three values; `id` must be a number.
- **Output encoding** (at the point of use): make data safe *for the specific place* it's being written. HTML-encode for HTML, attribute-encode for attributes, use parameters for SQL, URL-encode for URLs.

Validation alone can't prevent XSS. `O'Brien <3 cats` is a perfectly valid title that contains `'` and `<`. Encoding at output time is what makes it harmless.

### Defence in depth

Don't rely on one layer. For example, to stop user A deleting user B's task:

1. The UI doesn't show a delete button on B's tasks (UX, **not** security).
2. The authentication filter ensures A is logged in.
3. The CSRF filter ensures the request came from TaskFlow, not another site.
4. **The service layer checks that A owns the task** ← the real authority.
5. The DB user has only the permissions the app needs.

If one layer has a bug, another still stands.

---

## 6. What "middle level" means for you

At middle level, you're expected to:
- recognise these vulnerability classes in code reviews,
- write code that avoids them by default (prepared statements, encoded output, CSRF tokens, ownership checks),
- configure the common protections (cookie flags, security headers, CORS),
- explain the reasoning to a teammate.

You're **not** expected to design authentication protocols, do cryptography, or run professional penetration tests. Those are specialist skills (see [03-security-scope.md](../../03-security-scope.md)).

## 8. Summary

- **Assets** (what to protect), **entry points** (where input enters), **trust boundaries** (where untrusted becomes trusted).
- **Every HTTP request crosses the trust boundary.** Your own React app is on the untrusted side.
- Four questions per feature: *who can call it · hostile input · output encoding · cross-site requests*.
- **Validate input, encode output**: two different jobs.
- **Defence in depth**: UI hints + filters + service checks + DB permissions.

## 9. Check yourself

1. Why is the React app you wrote considered "untrusted"?
2. A task title is validated to be ≤ 200 characters. Is it now safe to print into HTML without encoding? Why?
3. Which layer is the real authority for "only the owner may delete a task"?
4. List four entry points in TaskFlow besides form fields.

<details>
<summary>Answers</summary>

1. It runs in the user's browser, which the user fully controls: they can modify the code and state, or bypass it entirely with curl.
2. **No.** A 200-character title can still contain `<script>` or `"` characters. Length validation doesn't make the text safe for HTML; output encoding does.
3. The **server's service layer** (an ownership check in `TaskService`). UI hiding and filters help, but only the service knows who owns the task.
4. Any four of: URL path, query parameters, JSON bodies, headers, cookies, uploaded files, data previously stored by other users (e.g. comments).
