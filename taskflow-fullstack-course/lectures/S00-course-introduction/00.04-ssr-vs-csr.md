# Lecture 00.04 · Server-Side Rendering vs Client-Side Rendering

> **Section:** S00 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> **Project feature:** none. You'll understand *why* TaskFlow has two rendering models.

---

## 1. What "rendering" means here

In web development, **rendering** usually means *turning data into HTML* (or into DOM nodes). The data is something like a list of `Task` objects. The HTML is something like `<li class="task">Write report</li>`.

The key question is **who does that turning, and where**:

- **Server-side rendering (SSR):** the **server** turns data into HTML and sends finished HTML to the browser. JSP is SSR.
- **Client-side rendering (CSR):** the server sends **data** (JSON), and **JavaScript in the browser** turns it into DOM. A classic React SPA is CSR.

---

## 2. Side by side: the same task list

### SSR (TaskFlow Admin, JSP)

```text
Browser ── GET /tasks ─────────────────────────▶ Tomcat
                                                  TaskListServlet: tasks = service.findAll()
                                                  request.setAttribute("tasks", tasks)
                                                  forward → list.jsp
                                                  <c:forEach items="${tasks}"> … </c:forEach>
Browser ◀── 200 text/html  <ul><li>Write report</li><li>Fix login bug</li></ul> ──
Browser: parse + paint. Done.
```

What the browser receives:

```html
<ul class="task-list">
  <li class="task task--high">Write report</li>
  <li class="task task--medium">Fix login bug</li>
</ul>
```

### CSR (TaskFlow Web, React)

```text
Browser ── GET / ──────────────────────────────▶ static server
Browser ◀── index.html:  <div id="root"></div><script src="/assets/app.js"></script>
Browser ── GET /assets/app.js ─────────────────▶
Browser ◀── (JavaScript bundle)
Browser: runs React → renders "Loading…"
Browser ── GET /api/tasks ─────────────────────▶ Tomcat → API Servlet
Browser ◀── 200 application/json  [{"id":1,"title":"Write report",...}, ...]
Browser: Redux store updated → React renders <ul><li>…</li></ul> into the DOM
```

What the browser receives from the API:

```json
[
  { "id": 1, "title": "Write report", "priority": "HIGH" },
  { "id": 2, "title": "Fix login bug", "priority": "MEDIUM" }
]
```

The final pixels can look identical. The *path* is completely different.

## 3. The nine questions, applied

### 1–2. What problem does each solve, and why does it exist?

- **SSR** is the original model of the web: documents generated by the server. It exists because browsers were originally just document viewers, and it's still the simplest way to show data on a page.
- **CSR** exists because some apps need **rich interactivity**: drag-and-drop boards, instant filtering, optimistic updates, no full-page reloads. Doing that by reloading server pages for every interaction feels slow and clumsy.

### 3–4. How does each work, and what happens internally?

- **SSR:** each navigation = a full HTTP request/response cycle. The server keeps the templates and the logic; the browser holds almost no application state (maybe a cookie). Internally, Tomcat runs a Servlet, forwards to a JSP (which is itself a compiled Servlet), and writes HTML into the response stream.
- **CSR:** the browser downloads an *application*. Application state lives in **browser memory** (React state, Redux store). The server becomes a **data API**. Internally, React keeps a virtual tree, compares it with the previous one (reconciliation), and updates the real DOM.

### 5. How do they interact?

In TaskFlow they share the **same backend services**. SSR Servlets and API Servlets both call `TaskService`. They share the **same session cookie**, so both are authenticated by the same login. In S49 they even share a **page**: a JSP renders the frame and a React "island" renders a board inside it.

### 6. Alternatives and hybrids

This isn't a strict either/or. Modern options include:
- **SSR frameworks for React** (Next.js, Remix/React Router framework mode): render React on the server for the first load, then "hydrate" in the browser.
- **Islands architecture:** mostly server HTML with small interactive JavaScript islands (what you'll build in S49).
- **Progressive enhancement:** server HTML that works without JavaScript, enhanced when JavaScript is available.
- **Server-driven partial updates** (e.g. htmx-style): the server returns HTML fragments instead of JSON.

We won't use these frameworks, but understanding SSR and CSR deeply makes all of them easy to learn later. They're combinations of the same two ideas.

### 7. Trade-offs

| Aspect | SSR (JSP) | CSR (React SPA) |
|---|---|---|
| First meaningful paint | Fast: HTML arrives ready | Slower: download JS, run it, fetch data, render |
| Interactions after load | Each navigation = full round trip + page reload | Instant local updates; only data goes over the wire |
| Where state lives | Server (request/session) | Browser memory (+ server for persistence) |
| Complexity | Lower; one place for logic | Higher; client state, caching, API design, build tooling |
| SEO / no-JS | Works naturally | Needs extra work (SSR/prerendering) |
| Server load | Renders HTML on every request | Serves JSON; rendering cost moves to users' devices |
| Security surface | Output encoding in templates; CSRF on forms | XSS in the SPA, API authorisation, CSRF on API, CORS, token/cookie handling |
| Team skills | Java-centric | Needs strong JS/TS + API skills |

### 8. When to use SSR (JSP)

- Admin/back-office pages, CRUD-heavy screens, content pages.
- Teams with strong server-side skills and simple interaction needs.
- Pages where first-load speed and simplicity matter more than rich interaction.

### 9. When to avoid it

- Highly interactive UIs (boards, editors, dashboards that update live).
- When the same data must also serve mobile apps (you'd need an API anyway).

And the reverse for CSR: great for rich interactivity; overkill for a simple form-and-table admin page.

## 4. The security angle (preview)

Both models have their own classic vulnerabilities, and TaskFlow will show you both:

- **SSR:** the template writes user data into HTML. If it doesn't **encode** it, you get **XSS** (S32, S34, S35). Forms submitted with cookies need **CSRF** protection (S37).
- **CSR:** React escapes text by default, but `dangerouslySetInnerHTML` and `javascript:` URLs reintroduce XSS (S26). The API must enforce authorisation on every endpoint (S46), and cross-origin calls bring **CORS** and cookie questions (S47).

In both models, one rule holds: **the server is the security boundary**. Rendering location changes *how* you protect data, not *where* the final authority lives.

---

## 5. Common confusions

> ⚠️ **"JSP is old, so it's slower."** Not necessarily. For a first page load, SSR is often *faster* because the browser gets ready-to-paint HTML. SPAs win on *subsequent* interactions.

> ⚠️ **"React apps don't need a server."** They still need an API server for data, and something to serve the static files.

> ⚠️ **"Using React means no HTML from the server."** React SSR frameworks exist, and even our SPA gets a small `index.html` from a server.

---

## 6. Summary

- **SSR:** the server turns data into HTML; the browser displays it. JSP is SSR.
- **CSR:** the server sends JSON; browser JavaScript builds the DOM. React SPA is CSR.
- SSR: simpler, fast first load, full-page navigations. CSR: richer interactions, more complexity.
- Hybrids (SSR frameworks, islands) combine the two ideas; TaskFlow builds a simple island in S49.
- The **server is always the security boundary**.

1. In which model does the browser receive `<li>Write report</li>` directly from the server?
2. Where does "the current filter" live in a CSR app vs an SSR app?
3. Give one reason a company might keep a JSP admin portal instead of rewriting it in React.
4. True or false: using React removes the need for CSRF protection.

<details>
<summary>Answers</summary>

1. **SSR** (JSP). In CSR the server sends JSON and React creates the `<li>` in the browser.
2. **CSR:** in browser memory (component state, Redux, or the URL). **SSR:** in the request (query parameters like `?status=DONE`) and sometimes the session; each new page request carries it again.
3. Any of: it works and rewriting is costly/risky; admin pages don't need rich interactivity; the team's strength is Java; incremental migration is safer.
4. **False.** If the API authenticates with cookies, a malicious site can make the browser send those cookies. CSRF protection is still needed (S24, S47).
