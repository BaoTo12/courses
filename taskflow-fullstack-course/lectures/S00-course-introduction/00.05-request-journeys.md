## 2. Journey A: the server-rendered page (TaskFlow Admin)

Scenario: an admin clicks **Tasks** in the navigation bar.

```text
                    Browser
                       │  ① HTTP GET /taskflow/tasks?status=TODO
                       │     Cookie: JSESSIONID=…; lang=vi
                       ↓
               ② Tomcat Connector  (parses the HTTP text into Java objects)
                       │
                       ↓
               ③ Filter chain
                  Encoding → Logging → SecurityHeaders → Locale → Authentication → CSRF → Authorization
                       │
                       ↓
               ④ TaskListServlet.doGet(request, response)
                       │
             ┌─────────┴───────────┐
             ↓                     ↓
   ⑤ taskService.search(…)    ⑤' response.sendRedirect(…)   (e.g. not logged in → /login)
             │                     → a NEW request starts at ①
             ↓
   ⑥ DAO → SQL → MySQL → List<Task>
             │
             ↓
   ⑦ request.setAttribute("tasks", tasks)
             │
             ↓
   ⑧ request.getRequestDispatcher("/WEB-INF/views/tasks/list.jsp").forward(request, response)
             │
             ↓
   ⑨ list_jsp (a servlet generated from list.jsp)
        EL     ${tasks}, ${task.title}, ${sessionScope.user.displayName}
        JSTL   <c:forEach>, <c:if>, <c:out>, <fmt:message>
             │
             ↓
   ⑩ HTML text written into the response
             │
             ↓
               Back out through the filters (they can add headers or log the status)
                       │
                       ↓
   ⑪ Browser receives HTML → parses → requests CSS/JS → paints
```

## 3. Journey B: the single-page app (TaskFlow Web)

Scenario: a user clicks the checkbox to mark a task **done**.

```text
  ① onClick handler in <TaskCard>
          │
          ↓
  ② dispatch( updateTask({ id: 5, status: 'DONE' }) )        ← RTK Query mutation (or a thunk)
          │
          ↓
  ③ Redux middleware chain
       (listener middleware, RTK Query middleware, logger…)
       optimistic update: cache patched immediately → UI shows "done" at once
          │
          ↓
  ④ axiosBaseQuery → Axios instance
          │
          ↓
  ⑤ Axios request interceptors
       reads XSRF-TOKEN cookie with js-cookie → adds header X-XSRF-TOKEN
       adds request ID
          │
          ↓
  ⑥ Browser sends HTTP PATCH /api/tasks/5
       browser automatically attaches Cookie: JSESSIONID=… (HttpOnly: JS can't see it)
          │
          ↓
  ⑦ Tomcat → filters (CORS, logging, CSRF double-submit check, authentication)
          │
          ↓
  ⑧ TaskApiServlet → taskService.updateForUser(…)  (ownership check: IDOR protection)
          │
          ↓
  ⑨ DAO → MySQL → JSON response {"id":5,"status":"DONE",…}
          │
          ↓
  ⑩ Axios response interceptors (normalise errors; 401 → session expired)
          │
          ↓
  ⑪ RTK Query updates the cache (or rolls back the optimistic patch on error)
          │
          ↓
  ⑫ Memoised selectors (reselect) recompute only if their inputs changed
          │
          ↓
  ⑬ useSelector sees a new reference → React re-renders only affected components
          │
          ↓
  ⑭ React commits DOM changes → browser paints
```

## 4. What the two journeys have in common

Look at the middle of both diagrams: **Tomcat → filters → Servlet → service → DAO → MySQL**. It's the same backend. The differences are at the edges:

| | Journey A (JSP) | Journey B (SPA) |
|---|---|---|
| Who starts the request | The browser, because of a link/form | JavaScript (Axios), because of a click handler |
| What the server returns | Full HTML page | JSON data |
| Who produces the final HTML | JSP on the server | React in the browser |
| How CSRF is prevented | Hidden form token (synchroniser) | Cookie → header (double-submit) |
| How "not logged in" is handled | Redirect to `/login` | JSON 401 → frontend navigates to login |
| What happens after | Browser replaces the whole page | React updates only what changed |

## 5. What "understanding" will look like

Here's a sample of the questions you'll be able to answer by the end:

- Where does `user` in `${user.name}` come from? Which scopes are searched, and in what order?
- When was the JSP executed? Did the browser execute any JSP? What did Tomcat do with `list.jsp` on the first request?
- What happens at ⑤' if the Servlet redirects instead of forwarding? Do the request attributes survive?
- Why is JSTL preferable to a scriptlet at ⑨?
- At ⑤ in Journey B, why can js-cookie read `XSRF-TOKEN` but not `JSESSIONID`?
- At ⑬, why would `useSelector(s => s.tasks.filter(…))` re-render on every action, and how does `createSelector` fix it?
- At ⑦, what exactly does CORS protect, and what doesn't it protect?

If any of those sound intimidating, good. They're the destination.

---

## 6. Summary

- **Journey A (JSP):** browser → Tomcat → filters → Servlet → service/DAO → request attributes → forward → JSP (EL + JSTL) → HTML → browser.
- **Journey B (SPA):** click → dispatch → middleware/RTK Query → Axios + interceptors (js-cookie for CSRF) → browser adds session cookie → Tomcat → filters → API Servlet → service/DAO → JSON → cache → selectors → re-render.
- The **backend middle is shared**; the edges differ.
- Every numbered arrow has a lecture. Use this page as your map.

## 7. Check yourself

1. In Journey A, which step turns Java objects into HTML text?
2. In Journey B, who attaches the `JSESSIONID` cookie to the request: Axios, js-cookie, or the browser?
3. At ⑤' (redirect), how many HTTP requests does the browser make in total to see the final page?
4. Which arrow in Journey B protects against a user editing someone else's task?

<details>
<summary>Answers</summary>

1. Step ⑨: the JSP (compiled into a servlet) evaluates EL and JSTL and writes HTML into the response (⑩).
2. **The browser.** It automatically attaches cookies that match the request's domain/path (given the right `withCredentials`/same-origin conditions). js-cookie can't even read an HttpOnly cookie.
3. **Two:** the original request, which gets a 302 + `Location`, and a new request to the redirect target.
4. ⑧: the **service-layer ownership check** (`updateForUser`). Filters (⑦) check "are you logged in?"; only the service knows "is this *your* task?".

</details>
