# Lecture 06.05 · `keyof`, `typeof`, Indexed Access Types, and `as const`

> **Section:** S06 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes

---

## 1. Types from types: `keyof` and indexed access

```ts
type TaskKey = keyof Task;              // 'id' | 'title' | 'description' | 'status' | …
type StatusType = Task['status'];       // TaskStatus
type DueType = Task['dueDate'];         // string | null
type TitleOrDue = Task['title' | 'dueDate'];   // string | null
```

- `keyof T` = the union of property names.
- `T[K]` = the type of property `K` (**indexed access type**). Same bracket syntax as runtime property access, but on types.

```ts
type Status = Task['status'];
const st: Status = 'NOPE';
//    ~~ error TS2322: Type '"NOPE"' is not assignable to type '"DONE" | "IN_PROGRESS" | "TODO"'.
```

## 2. `typeof` in a type position: types from values

JavaScript's `typeof x` (a runtime operator) returns a string like `'object'`. TypeScript reuses the keyword **in type positions** to mean "the type of this value":

```ts
const defaultFilter = { status: undefined, q: '' };
type FilterShape = typeof defaultFilter;          // { status: undefined; q: string }

function makeStore() { return { getState: () => ({ tasks: [] as Task[] }) }; }
type Store = ReturnType<typeof makeStore>;        // the store's type, derived from the code
```

This is how Redux types are derived from the implementation (`typeof store.dispatch`, 06.03).

## 3. `as const`: freeze literal types

Without `as const`, TypeScript widens (05.04):

```ts
const statuses = ['TODO', 'IN_PROGRESS', 'DONE'];            // string[]
const statuses2 = ['TODO', 'IN_PROGRESS', 'DONE'] as const;  // readonly ['TODO', 'IN_PROGRESS', 'DONE']
```

`as const` means: **the narrowest possible type**. Literals stay literal, arrays become readonly tuples, object properties become readonly.

```ts
const conf = { page: 0, size: 20 } as const;
conf.page = 1;
//   ~~~~ error TS2540: Cannot assign to 'page' because it is a read-only property.
```

## 4. The pattern: values first, types derived

```ts
export const TASK_STATUSES = ['TODO', 'IN_PROGRESS', 'DONE'] as const;
export type TaskStatus = (typeof TASK_STATUSES)[number];
//                        ^^^^^^^^^^^^^^^^^^^^  the tuple type
//                                              [number] = "the type of any element" → the union
```

Reading `(typeof TASK_STATUSES)[number]` step by step:
1. `typeof TASK_STATUSES` → `readonly ['TODO', 'IN_PROGRESS', 'DONE']`
2. `[number]` → indexed access with **any number index** → the union of element types → `'TODO' | 'IN_PROGRESS' | 'DONE'`

Why it's better than a separately declared union:

| Need | How the pattern delivers |
|---|---|
| Type-check values | `TaskStatus` union |
| Render a dropdown of all statuses | `TASK_STATUSES.map(…)` at **runtime** |
| Validate untrusted input | `TASK_STATUSES.includes(x)` (06.08) |
| Add a new status | Edit **one** array; the type follows |

It's the TypeScript answer to "I want enum-like iteration without `enum`" (05.06).

### Same for objects

```ts
export const STATUS_LABEL = {
  TODO: 'To do',
  IN_PROGRESS: 'In progress',
  DONE: 'Done',
} as const satisfies Record<TaskStatus, string>;
```

`satisfies` (TS 4.9+) **checks** the value against a type (all statuses present, all strings) **without widening** it. You keep the literal types *and* get the completeness check. Compare:

| | `const x: Record<TaskStatus, string> = …` | `const x = … satisfies Record<TaskStatus, string>` |
|---|---|---|
| Checks completeness | ✅ | ✅ |
| Type of `x.TODO` | `string` | `'To do'` (with `as const`) |

## 5. Summary

- `keyof T` → property-name union; `T[K]` → property type.
- `typeof value` in a type → the value's type (derive types from code).
- `as const` → narrowest literal/readonly types.
- **Values first, types derived**: `const ARR = [...] as const; type U = (typeof ARR)[number]`.
- `satisfies` checks without widening.
