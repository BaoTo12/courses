# Lecture 06.09 · `unknown` at the Boundaries: `catch (e)`, JSON Parsing, Axios Errors

> **Section:** S06 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes

---

## 1. Trust boundaries in code

Remember 00.06: trust boundaries are where data you don't control enters. In frontend TypeScript, the boundaries are:

| Boundary | What you get | Correct type |
|---|---|---|
| `await response.json()` / Axios `response.data` without a generic | Parsed JSON | `unknown` → validate |
| `JSON.parse(text)` | Anything | `unknown` → validate |
| `localStorage.getItem(k)`, cookies (js-cookie), URL params | `string \| null` | Parse → validate |
| `catch (e)` | **Anything** that was thrown | `unknown` → narrow |
| `window.postMessage`, third-party scripts | Anything | `unknown` → validate |

Inside the boundary, once validated, you work with precise types. Validate **once, at the edge**, not everywhere.

## 2. `catch (e)` is `unknown` (and why)

```ts
try {
  JSON.parse('not json');
} catch (e) {
  console.log(e.message);
  //          ~ error TS18046: 'e' is of type 'unknown'.
}
```

Under `strict` (`useUnknownInCatchVariables`), the caught value is `unknown`, because **JavaScript can throw anything**:

```js
throw new Error('x');                 // an Error
throw 'just a string';                // a string
throw { status: 401, message: '…' };  // an object (some libraries throw plain objects)
throw undefined;                      // even this
```

Handle it with narrowing or the `toErrorMessage` helper from 06.08:

```ts
try {
  await saveTask(task);
} catch (e) {
  showToast(toErrorMessage(e));   // works for Error, string, ApiError, anything
}
```

## 3. Axios errors (preview of S13)

Axios rejects with an `AxiosError`, which has `response?.data` (the server's body, e.g. our `ApiError`), `response?.status`, `code` (e.g. `'ECONNABORTED'` for timeouts), and `message`. It provides a type guard:

```ts
import axios from 'axios';

try {
  await api.patch(`/tasks/${id}`, body);
} catch (e) {
  if (axios.isAxiosError<ApiError>(e)) {
    const serverMessage = e.response?.data.message;   // typed via the generic, but only an ASSUMPTION
    const status = e.response?.status;                 // undefined for network errors / timeouts
  }
}
```

⚠️ `isAxiosError<ApiError>(e)` narrows `e` to an Axios error, but the `<ApiError>` generic is **a promise, not a check** of the body shape. A proxy might return HTML. In S13 you'll write an interceptor that normalises every failure into a validated `ApiError` using `isApiError`, so components never deal with raw errors.

## 4. Summary

- At every trust boundary, start from `unknown` and validate or narrow.
- `catch (e)` is `unknown` because anything can be thrown; use a helper like `toErrorMessage`.
- Library generics like `axios.isAxiosError<ApiError>` narrow the error object but don't validate the body.
