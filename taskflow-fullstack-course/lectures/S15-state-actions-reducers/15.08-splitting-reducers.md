# Lecture 15.08 · Splitting Reducers: Slice Reducers, Each Owning One Key

> **Section:** S15 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> 🔗 Official companion reading: Fundamentals Part 3 ("Splitting Reducers", "Combining Reducers")

---

## 1. One reducer for everything doesn't scale

The store takes **one** reducer: the **root reducer**. You could write it as one giant `switch`:

```ts
function rootReducer(state = initialRootState, action: AppAction): RootState {
  switch (action.type) {
    case 'tasks/taskAdded':
      return { ...state, tasks: { ...state.tasks, items: [...state.tasks.items, action.payload] } };
    case 'listPrefs/sortChanged':
      return { ...state, listPrefs: { ...state.listPrefs, sort: action.payload } };
    // … 30 more cases, each copying the root AND its slice
  }
}
```

Every case repeats `{ ...state, x: { ...state.x, … } }`, and the file grows with every feature.

## 2. The solution: delegate each key to its own reducer

```ts
function rootReducer(state: RootState | undefined, action: AppAction): RootState {
  return {
    tasks: tasksReducer(state?.tasks, action),
    listPrefs: listPrefsReducer(state?.listPrefs, action),
    ui: uiReducer(state?.ui, action),
  };
}
```

- Each **slice reducer** knows only its own part of the state (`state.tasks`), and returns only its own part.
- **Every** slice reducer receives **every** action (hence `default: return state`, 15.07).
- The root reducer just assembles the results.
- Each slice reducer's default parameter provides its initial state, so the root's initial state is assembled automatically.

This is the Redux pattern called **reducer composition**. It's how a large app's state is split across dozens of feature files.

## 3. One problem left

The hand-written root above **always returns a new root object**, even when no slice changed (for an unknown action, every slice returns its same state, but `{ tasks, listPrefs, ui }` is a fresh object). Subscribers comparing the root reference would think something changed after every action. Redux's `combineReducers` fixes that, and you'll write it yourself in 15.09.

## 4. Summary

- The store has one root reducer; split it into slice reducers, one per top-level key.
- Each slice reducer sees every action but only its own state.
- The combination step should keep the same root object when nothing changed.
