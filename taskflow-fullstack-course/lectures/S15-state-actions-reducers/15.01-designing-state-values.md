# Lecture 15.01 · Designing State Values: Minimal, Not Derived, Serialisable

> **Section:** S15 · R2: State, Actions and Reducers
> **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> 🔗 Official companion reading: Redux **Fundamentals, Part 3** ("State, Actions, and Reducers": designing the state values)

---

## 1. Start from the UI and the data, not from the code

The official tutorial designs state before writing a single reducer. Ask two questions:
1. **What does the UI need to show?** Task list, loading spinner, error message, toasts, selection checkboxes, the sort order.
2. **What changes, and why?** The server sends tasks; the user completes one; a toast expires; the user logs out.

From those, list the **values** the app must remember. That's the state.

## 2. Rule 1: keep the minimal state

> Store the **smallest** set of values from which everything else can be computed.

| Value | Store it? | Why |
|---|---|---|
| The tasks | ✅ | Can't be computed from anything else |
| Number of open tasks | ❌ | `tasks.filter((t) => t.status !== 'DONE').length` |
| The filtered list | ❌ | Tasks + filters (URL) → computed by a selector (S21) |
| "All tasks done?" | ❌ | `tasks.every((t) => t.status === 'DONE')` |
| Loading status | ✅ | Can't be computed; it describes a request in progress |
| The selected task ids | ✅ | User input nobody else knows |
| "Is any task selected?" | ❌ | `selectedTaskIds.length > 0` |

Storing derived values creates **two sources of truth**. Every reducer that changes the tasks would also have to update the count, and the day one of them forgets, the badge says "3 open" while the list shows 4. It's the Redux version of 08.05 ("you might not need an effect"): compute during render (here: in selectors) instead of syncing copies.

## 3. Rule 2: serialisable only

Everything in state must survive `JSON.stringify` → `JSON.parse` unchanged:

| ✅ Allowed | ❌ Not allowed | Instead |
|---|---|---|
| strings, numbers, booleans, `null` | `undefined` as a meaningful value | `null` |
| arrays, plain objects | `Map`, `Set` | objects/records, arrays of ids |
| ISO date strings (`'2026-10-03'`) | `Date` objects | `toISOString()` when creating the action |
| | class instances, Promises, functions, DOM nodes, `AbortController` | keep them in components, middleware or thunks |

Why it matters: the DevTools record and replay state (14.11), state can be persisted (to `localStorage`, for example) or sent to the server for a bug report, and equality checks stay simple. RTK adds a dev-time check that **warns** about non-serialisable values (S20).

The 14.13 solution verified that TaskFlow's design passes: a sample `RootState` value came back from `JSON.parse(JSON.stringify(…))` identical.

## 4. Rule 3: describe the data, not the components

Don't design state as "what `TaskList` needs" and "what `Header` needs". Components change constantly; the **data** of the domain (tasks, categories, the user) changes rarely. Design around the data, and let each component **select** what it needs (15.02).

## 5. TaskFlow's S15 state values

```text
tasks      { items: Task[], status: 'idle'|'loading'|'succeeded'|'failed', error: string | null }
listPrefs  { sort: { key, direction }, pageSize }
ui         { toasts: Toast[], selectedTaskIds: number[] }
```

(`auth` joins in S24. `tasks.items` becomes normalised in S19.)

## 6. Summary

- Minimal: store only what can't be computed. Derived data goes in selectors.
- Serialisable: JSON-safe values only; dates as strings; ids instead of objects; arrays instead of Sets.
- Organise around domain data, not around components.
