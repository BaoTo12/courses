# Lecture 15.03 · Designing Actions: Events, Not Setters

> **Section:** S15 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> 🔗 Official companion reading: Fundamentals Part 3 ("Designing Actions"); Style Guide: "Model Actions as Events, Not Setters", "Write Meaningful Action Names", "Use the domain/eventName Convention"

---

## 1. List the events first

Before writing types, list **what can happen** in TaskFlow, in plain language:

- The task list started loading / arrived / failed to load.
- A task was created, updated or deleted (the server confirmed it).
- The server marked all tasks done. The server deleted the completed tasks.
- The user changed the sort order or page size.
- A toast was shown / dismissed. A task was selected or unselected; the selection was cleared.
- The user logged out.

Each line becomes one action type.

## 2. Naming: `domain/eventName`, past tense

```text
tasks/fetchStarted      tasks/taskAdded        listPrefs/sortChanged     ui/toastShown
tasks/fetchSucceeded    tasks/taskUpdated      listPrefs/pageSizeChanged ui/taskSelectionToggled
tasks/fetchFailed       tasks/taskDeleted      auth/loggedOut            ui/selectionCleared
```

- **`domain/`** prefix: groups actions in the DevTools and avoids collisions (two features can both have a `…/cleared`).
- **Past tense**: an action reports something that **happened**. Reducers decide what it means.
- Old codebases use `SCREAMING_CASE` constants (`ADD_TODO`, `SET_FILTER`). They work the same way; the convention changed.

## 3. Events vs setters

Setter style:

```ts
dispatch({ type: 'tasks/setItems', payload: items.filter((t) => t.id !== id) });
dispatch({ type: 'ui/setSelectedTaskIds', payload: selected.filter((x) => x !== id) });
```

Event style:

```ts
dispatch(taskDeleted(id));
```

| | Setters | Events |
|---|---|---|
| Where the logic lives | In the **component**, which computes the new values | In the **reducers**, which decide what the event means |
| One user action → | Several dispatches, easy to forget one | One dispatch; every interested slice reacts (15.10) |
| DevTools log | "setItems, setSelectedTaskIds…" (what, but not why) | "taskDeleted" (why) |
| Adding a feature that reacts to deletion | Edit every place that deletes | Add a `case` in the new feature's reducer |

With events, reducers hold the logic, and the logic can be **tested** without any UI (15.11).

## 4. The payload: what happened, not the result

- `taskDeleted(5)`: the id. Not "the list without task 5".
- `taskUpdated(task)`: the task **as returned by the server** (13.13). The reducer doesn't recompute it.
- `allCompleted({ updatedAt })`: the event's data, **including values a reducer isn't allowed to generate**. A reducer can't call `Date.now()` (15.04), so the time is decided when the action is created.
- Keep payloads **small and serialisable** (15.01): ids and plain data, not DOM events (`dispatch({ type: 'x', payload: event })` puts a huge non-serialisable object in the log).

## 5. Action creators

Each action type gets a creator function in the slice file:

```ts
export const taskDeleted = (id: number) => ({ type: 'tasks/taskDeleted', payload: id });
```

Callers never type action objects by hand. That prevents typos in `type` strings, and it gives one place to put payload preparation (generating an id or a timestamp). 15.07 adds precise types.

## 6. Summary

- List events in plain language, then name them `domain/eventName` in the past tense.
- Events, not setters: one dispatch per real-world event, with the logic in reducers.
- Payloads carry what happened (ids, server data, timestamps), serialisable and small.
