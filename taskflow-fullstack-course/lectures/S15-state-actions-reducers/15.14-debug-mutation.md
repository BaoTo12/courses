# Lecture 15.14 · 🐞 Debug: "The State Didn't Change in DevTools"

> **Section:** S15 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~25 minutes
> Reproduced with redux 5.0.1 in Node: a real store, a history of states recorded by a subscriber, and the selector a component would use.

---

## Symptom

A teammate "simplifies" the update case:

```js
case 'tasks/taskUpdated': {
  const task = state.items.find((t) => t.id === action.payload.id);
  Object.assign(task, action.payload);
  return { ...state }; // "new object, so it's immutable"
}
```

Reports:
- "In the Redux DevTools, the `tasks/taskUpdated` action shows **no diff**. And when I jump back to before the update, the task **still shows the new title**."
- (From S17 on) "The task card doesn't re-render after saving; it updates only when something else re-renders it."

Verified with a subscriber recording every state, and `selectFirst = (s) => s.items[0]`:

```json
{ "rootChanged": true, "itemsArraySame": true, "selectedItemSame": true,
  "previousStateTitle": "New title", "diffWouldShow": "no difference" }
```

## Investigation checklist

1. Which objects are **new** after the dispatch, and which are the **same references** as before?
2. The history's **previous** state says `'New title'`. How can a past state change?
3. A component selects `state.items[0]`. What does a `===` comparison tell it? (14.06, 14.09 step ⑥)
4. How would a frozen-input test (15.11) have reported this?

## Explanation

- `{ ...state }` creates a new **root** object. But `items` is the same array, and the task inside it is the **same object**, which was **modified in place**.
- The "previous state" in the history (and in the DevTools) **is that same task object**, so the past changed too. The diff compares old and new: both now say `'New title'`, so there's no difference.
- A selector returning `state.items[0]` returns the same reference before and after. `useSelector` (S17) compares with `===`, sees no change, and doesn't re-render. The card shows stale data until something else re-renders it.
- With `deepFreeze` in the test, `Object.assign(task, …)` throws *"Cannot assign to read only property 'title' of object '#<Object>'"*. The bug would never have reached the app.

The same bug hides in the knowledge-check classic:

```js
return { ...state, items: state.items.sort(bySortKey) }; // sort() mutates the OLD array, then returns it
```

On frozen state: *"Cannot assign to read only property '0' of object '[object Array]'"* (verified in 15.11). Fix: `state.items.toSorted(bySortKey)`, or better, don't store sorted copies at all: sort in a selector (S21).

## Fix

Copy along the path (15.05):

```ts
case 'tasks/taskUpdated':
  return {
    ...state,
    items: state.items.map((task) => (task.id === action.payload.id ? action.payload : task)),
  };
```

## Lessons

- "I returned a new object" isn't enough: **every object on the path** to the change must be new, and nothing in the old state may be modified.
- When DevTools show "no diff" or time travel shows the future, suspect mutation first.
- Freeze reducer inputs in tests. It turns silent corruption into an immediate, precise error.
- RTK (S20) makes this class of bug nearly impossible: Immer for writes, and a dev-mode check that throws on mutations outside reducers.
