# Lecture 15.04 · Reducer Rules: Only State + Action; No Mutation, No Async, No Side Effects, No Randomness

> **Section:** S15 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> 🔗 Official companion reading: Fundamentals Part 3 ("Rules of Reducers"); Style Guide: "Reducers Must Not Have Side Effects", "Do Not Mutate State"

---

## 1. The rules

A reducer must:

1. **Compute the new state only from its arguments**, `state` and `action`.
2. **Not modify** the existing `state` (or the action). Make copies (14.06).
3. **Not do anything asynchronous** and **not cause side effects**: no API calls, no timers, no `localStorage`, no logging you depend on, no `dispatch`.
4. **Not use non-deterministic values**: no `Date.now()`, `new Date()`, `Math.random()`, `crypto.randomUUID()`, or reading anything outside its arguments (module variables, `window`, the URL).

Each rule protects a property you rely on:

| Rule broken | What breaks |
|---|---|
| 1. Reads outside data (`window.location`, a module-level variable) | Same actions no longer give the same state; replay and tests lie |
| 2. Mutation | Change detection, DevTools history, memoised selectors (14.06) |
| 3. Side effects | Replay repeats them (time travel would call your API again); tests need mocks; order of effects becomes unpredictable |
| 4. `Date.now()` / `Math.random()` | Replay produces different values; tests can't assert exact state; two tabs replaying the same log disagree |

## 2. Where the "impure" parts go instead

| You need… | Put it in… | TaskFlow example |
|---|---|---|
| A timestamp | The **action creator** (or the thunk) | `allCompleted(updatedAt = new Date().toISOString())` |
| A generated id | The action creator, or better the **server** | Toast ids: `toastShown()` increments a counter; task ids come from the API |
| An API call | A **thunk** or middleware (S18) | `fetchTasks()` dispatches `fetchStarted` → `fetchSucceeded`/`fetchFailed` |
| A timer | A thunk or a component effect | "Dismiss the toast after 4 s" dispatches `toastDismissed` later |
| Reading other slices | The **thunk** (`getState()`), or pass it in the payload | "Complete all visible tasks" computes the ids, then dispatches |

The reducer receives finished facts and computes state. Everything messy happens before the dispatch.

## 3. Redux enforces some of this (verified in 14.10)

| You do in a reducer | Redux says (development build) |
|---|---|
| `store.dispatch(…)` | *Reducers may not dispatch actions.* |
| `store.getState()` | *You may not call store.getState() while the reducer is executing. The reducer has already received the state as an argument…* |

Mutation, `Date.now()` and API calls are **not** detected by Redux core. Your tests (15.11) and RTK's dev checks (S20) are the safety net.

## 4. "No side effects" includes subtle ones

- `console.log` in a reducer is harmless for debugging, but don't build behaviour on it.
- `array.sort()` **is** a side effect: it mutates the array it's called on, even inside a spread expression (15.14).
- Throwing for invalid input is allowed but rarely useful: validate in the UI/thunk before dispatching.
- Returning `undefined` is forbidden: `combineReducers` throws (15.15). Return `null` for "no value".

## 5. Summary

- Reducers: `(state, action) → newState`, deterministic, no mutation, no side effects.
- Time, randomness, ids, API calls and timers live in action creators, thunks or components.
- Redux catches dispatch/getState inside reducers; tests and RTK catch the rest.
