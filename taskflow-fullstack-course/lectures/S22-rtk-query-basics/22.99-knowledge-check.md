# Lecture 22.99 · ✅ Knowledge Check: RTK Query Basics

> **Section:** S22 · **Type:** ✅ Knowledge Check · **Track:** ★ Core · **Time:** ~25 minutes
> Answer first, then open the explanation.

---

**1.** Which of these is *server* state in TaskFlow? (a) the sort order, (b) the comments of task 5, (c) the quick-find text, (d) the theme.

<details><summary>Answer</summary>

**(b).** A page refresh reloads it from the server, and someone else can change it. The others belong to this browser tab (22.01).
</details>

**2.** Two components mount `useGetTasksQuery({ size: 100 })` and `useGetTasksQuery({ size: 100 })` at the same time, and a third mounts `useGetTasksQuery({ size: 5 })`. How many requests, and how many cache entries?

<details><summary>Answer</summary>

**Two requests, two entries**: `getTasks({"size":100})` (2 subscribers, deduped) and `getTasks({"size":5})`. The key is the endpoint plus the serialized arg (22.02).
</details>

**3.** Your base query does `throw new Error('Network down')` on failure. What goes wrong?

<details><summary>Answer</summary>

A base query must **return** `{ error }`. A throw is treated as an unexpected crash: RTK logs it, and the hook's `error` is a generic `SerializedError`. Your `ApiErrorPayload` shape, `fieldErrors` included, is lost. Also, an `Error` instance isn't serialisable state (22.03).
</details>

**4.** After a toggle, the list refetches. What are the **hook's** `isLoading` and `isFetching` during that refetch? What does `apiSlice.endpoints.getTasks.select(LIST_QUERY)(state).isLoading` say?

<details><summary>Answer</summary>

Hook: `isLoading: false`, `isFetching: true`. The cache entry: `isLoading: true`, because it's `status === 'pending'`. Hence 22.14's blinking spinner (22.05 §2).
</details>

**5.** The user opens task 5, goes back to the list after 10 s, and returns to task 5 after another 30 s. How many `GET /tasks/5`? And if they return after 90 s instead?

<details><summary>Answer</summary>

After 30 s: **one** request in total. The entry was unsubscribed but kept for `keepUnusedDataFor` (60 s), so it's served from the cache. After 90 s: **two**. The entry was removed at 60 s, so it's fetched again (22.06).
</details>

**6.** `try { await deleteTask(id) } catch { showError() }`. The server answers 403. What does the user see?

<details><summary>Answer</summary>

**No error.** Without `.unwrap()`, the trigger's promise resolves to `{ error }` and never throws (22.07).
</details>

**7.** Fill the table: does the mutation refetch the entry?

| Entry provides | Mutation invalidates | Refetch? |
|---|---|---|
| `['Task']` | `['Task']` | ? |
| `[{ type: 'Task', id: 5 }]` | `['Task']` | ? |
| `['Task']` | `[{ type: 'Task', id: 5 }]` | ? |
| `[{ type: 'Task', id: 5 }]` | `[{ type: 'Task', id: 6 }]` | ? |

<details><summary>Answer</summary>

Yes, yes, **no**, no. A bare invalidation hits all tags of the type; an id invalidation hits only the same id (22.08 §3).
</details>

**8.** A new endpoint, `getStats: build.query<Stats, void>({ query: () => '/stats', providesTags: ['Task'] })`, feeds the dashboard's numbers. Does it stay correct after a toggle, an add, a delete and "clear completed"? Why? And what's the cost?

<details><summary>Answer</summary>

**Correct:** every TaskFlow task mutation invalidates the bare `'Task'`, and a bare invalidation hits every `'Task'` provider, `getStats` included. **Cost:** every task write also refetches the stats, if the dashboard is mounted. If it isn't, the entry is just removed (22.06). That's acceptable here. With precise id tags (S23), `getStats` would need its own tag, such as `{ type: 'Task', id: 'STATS' }` or a `'Stats'` type, and the mutations would have to invalidate it explicitly.
</details>

**9.** Why does "Clear completed" use one `queryFn` mutation instead of calling `deleteTask` in a loop?

<details><summary>Answer</summary>

Each `deleteTask` would invalidate `'Task'` → N list refetches, and N toasts. One `queryFn` endpoint sends the N DELETEs through the same base query, reports partial success as data, and invalidates **once** (22.07 §4).
</details>

**10.** After `deleteTask(5)` succeeds on the details page, the Network tab shows `GET /api/tasks/5 → 404`. Why, and why doesn't the user see "Not found"?

<details><summary>Answer</summary>

`getTask(5)` provides the bare `'Task'` and is still subscribed (the page is still mounted while navigation is pending). So the invalidation refetches it, and it's gone. The page returns `null` when `deletion.isSuccess`, so the 404 is never rendered. S23 avoids the request itself (22.09 §4).
</details>

**11.** Why must logout dispatch `apiSlice.util.resetApiState()`?

<details><summary>Answer</summary>

The cache isn't one of your slices, so it doesn't reset on `loggedOut`. Without the reset, the next user on the same tab sees the previous user's cached tasks until a refetch (22.09 §5; S23 goes deeper).
</details>

**12.** Name one situation where you'd still write a `createAsyncThunk` or a listener instead of an endpoint.

<details><summary>Answer</summary>

Any of these: a multi-step workflow with progress state, a write that must read the current state first (the toggle thunk wraps an endpoint), a reaction to actions (toasts, analytics), or throw-away results you don't want cached (quick find). See 22.10.
</details>
