## 1. Queries read, mutations write

| | Query | Mutation |
|---|---|---|
| Runs | automatically, when subscribed | only when **you call the trigger** |
| Cached? | yes, per argument | no; the last result is kept **per hook instance** |
| Deduped? | yes | no: two calls = two requests |
| Hook | `const result = useXQuery(arg)` | `const [trigger, result] = useXMutation()` |
| Staleness | provides tags | **invalidates** tags (22.08) |

## 2. TaskFlow's mutations

✍️ Add to `endpoints` in `src/features/api/apiSlice.ts` (after the queries):

```ts
    // ── Mutations: write, then invalidate what they made stale ───────────────
    addTask: build.mutation<Task, CreateTaskRequest>({
      query: (request) => ({ url: '/tasks', method: 'POST', data: request, validate: isTask }),
      invalidatesTags: ['Task'],
    }),
    updateTask: build.mutation<Task, { id: number; request: CreateTaskRequest }>({
      query: ({ id, request }) => ({ url: `/tasks/${id}`, method: 'PUT', data: request, validate: isTask }),
      invalidatesTags: ['Task'],
    }),
    patchTask: build.mutation<Task, { id: number; changes: UpdateTaskRequest }>({
      query: ({ id, changes }) => ({ url: `/tasks/${id}`, method: 'PATCH', data: changes, validate: isTask }),
      invalidatesTags: ['Task'],
    }),
    deleteTask: build.mutation<void, number>({
      query: (id) => ({ url: `/tasks/${id}`, method: 'DELETE' }),
      transformResponse: () => undefined, // 204 No Content: Axios gives '' as data
      invalidatesTags: ['Task'],
    }),
```

(Add `CreateTaskRequest` and `UpdateTaskRequest` to the `api-types` import, and export the four new hooks.)

- The arg is **one value**. When a request needs two things (an id and a body), pass an object: `{ id, request }`.
- `transformResponse` reshapes the response before it's stored or returned. Here it turns Axios's empty-string body into a clean `undefined`, which matches `void`.
- Every mutation invalidates `'Task'`, so after any write every subscribed task query refetches. That's crude but correct. S23 makes it precise with ids and optimistic updates.

## 3. Using a mutation in a component

```tsx
const [addTask, { isLoading: isSaving }] = useAddTaskMutation();

async function handleSubmit(values: TaskFormValues) {
  try {
    const saved = await addTask(toCreateRequest(values)).unwrap(); // Task, or it throws the error payload
    navigate(`/tasks/${saved.id}`, { replace: true });
  } catch (err) {
    setFieldErrors(fieldErrorsOf(err) ?? {});                      // 400 → field messages (13.09 / 20.09)
  }
}
```

- `addTask(arg)` returns a promise-like object. **Without** `.unwrap()` it resolves to `{ data } | { error }` and **never throws**, so `try/catch` would catch nothing. That's the #1 mutation bug.
- `.unwrap()` resolves to the data, or **throws the base query's error**: our `ApiErrorPayload`, so `fieldErrorsOf(err)` works unchanged.
- `isLoading` on a mutation means "this hook's last call is in flight". Use it to disable the Save button.

## 4. `queryFn`: when an endpoint isn't one request

"Clear completed" deletes N tasks. The server has no bulk-delete endpoint. With N calls to `deleteTask`, **each** would invalidate `'Task'` and trigger N list refetches. What we want is N DELETEs and **one** invalidation:

```ts
export interface ClearCompletedResult {
  deleted: number[];
  failed: number[];
}
// … inside endpoints:
    /**
     * Several DELETEs, ONE invalidation (22.07): a `queryFn` instead of `query` when an endpoint
     * isn't a single request. It receives the base query to make each request.
     */
    clearCompleted: build.mutation<ClearCompletedResult, number[]>({
      async queryFn(ids, _api, _extraOptions, baseQuery) {
        const results = await Promise.all(ids.map((id) => baseQuery({ url: `/tasks/${id}`, method: 'DELETE' })));
        const deleted = ids.filter((_id, index) => !results[index]?.error);
        const failed = ids.filter((_id, index) => results[index]?.error);
        return { data: { deleted, failed } };
      },
      invalidatesTags: ['Task'],
    }),
```

- `queryFn(arg, api, extraOptions, baseQuery)` replaces `query`. It must follow the base-query contract: **return** `{ data }` or `{ error }`, and never throw.
- The fourth parameter **is our `axiosBaseQuery`**, so each DELETE still goes through the interceptors and error normalisation.
- It returns **partial success** as data (`{ deleted, failed }`): "3 of 4 deleted" is a result, not an error. The UI toasts both counts (22.09).
- The verification test counts **one** `GET /tasks` after the DELETEs.

Two components that each call `useDeleteTaskMutation()` get **separate** `isLoading`/`data`. If a header spinner must reflect a delete started in a list row, share the result:

## 📇 API card: `build.mutation(definition)` and `useXxxMutation(options?)`

### Endpoint definition

| Field | Type | Meaning |
|---|---|---|
| `query(arg)` | `(arg) => BaseQueryArgs` | Builds the request. (Or `queryFn`, not both.) |
| `queryFn(arg, api, extraOptions, baseQuery)` | `=> MaybePromise<{ data } \| { error }>` | Custom logic; may call `baseQuery` several times. |
| `transformResponse(response, meta, arg)` | `=> Result` | Reshape success data. |
| `transformErrorResponse(error, meta, arg)` | `=> Error` | Reshape the error. |
| `invalidatesTags` | `tags \| (result, error, arg) => tags` | What becomes stale (22.08). |
| `onQueryStarted(arg, { dispatch, getState, queryFulfilled, … })` | `async` | Side effects around the request: optimistic updates (S23). |
| `extraOptions` | any | Passed to the base query as its third argument. |

### Hook

```ts
const [trigger, result] = useUpdateTaskMutation({ fixedCacheKey?, selectFromResult? })
const promise = trigger(arg)   // .unwrap(), .abort(), .reset(), .requestId, .arg
```

| Result field | Meaning |
|---|---|
| `data`, `error` | of the **last** call from this hook instance |
| `isUninitialized`, `isLoading`, `isSuccess`, `isError` | its status (mutations have **no** `isFetching`) |
| `originalArgs` | the arg of the last call |
| `reset()` | back to uninitialized (hide "Saved ✓" after a while) |

**Outside React:** `await dispatch(apiSlice.endpoints.patchTask.initiate({ id, changes })).unwrap()`. That's what TaskFlow's `toggleTask` thunk does (22.09).

**Minimal example (outside TaskFlow):**

```tsx
const [likePost, { isLoading }] = useLikePostMutation();
<button disabled={isLoading} onClick={() => likePost(post.id).unwrap().catch(showError)}>♥ {post.likes}</button>
```

**When to use:** any server write whose result or side effects affect cached queries.

**When not to:**
- A request that reads data on demand ("search as you type", "preview") → a lazy **query**. Mutations aren't cached or deduped.
- A write that has nothing to do with the cache and needs heavy orchestration (a multi-step upload with progress) → a thunk that may *end* with `invalidateTags` (22.10).

**Common mistakes:**
- `try { await trigger(arg) } catch` without `.unwrap()`. It never throws.
- Calling a mutation in a loop and invalidating N times. Use one `queryFn` endpoint (or a bulk API).
- Expecting two `useXMutation()` calls to share `isLoading`. Use `fixedCacheKey`.
- Throwing inside `queryFn`. Return `{ error }` instead.
