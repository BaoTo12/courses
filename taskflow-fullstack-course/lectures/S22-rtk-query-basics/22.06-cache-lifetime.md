## 1. The timeline

```text
t=0     A mounts   useGetTaskQuery(5) ── subscribe(A) ── entry missing  → GET /tasks/5      status: pending
t=0     B mounts   useGetTaskQuery(5) ── subscribe(B) ── already pending → no request (dedupe)
t=0.1s  response                                                      → status: fulfilled, data
t=10s   A, B unmount                    ── 0 subscribers → start the keepUnusedDataFor timer (60 s)
t=30s   C mounts   useGetTaskQuery(5) ── subscribe(C) ── timer cancelled; data served instantly, NO request
t=40s   C unmounts                      ── timer restarts: 60 s from now
t=100s  timer fires                     → entry removed (api/queries/removeQueryResult)
```

- **Dedupe** is per cache key: one request, however many subscribers.
- A new subscriber to an entry that is **fulfilled** gets the cached data and sends **no request**, even if the data is old. You can ask for fresher data with `refetchOnMountOrArgChange` (22.05).
- Removal happens only at **0 subscribers + timer**. Navigating away and back within 60 s is instant.

## 2. Tuning the lifetime

```ts
createApi({ keepUnusedDataFor: 60, … })            // global default, seconds
build.query({ keepUnusedDataFor: 5, … })             // e.g. a heavy report: free memory quickly
build.query({ keepUnusedDataFor: Infinity, … })       // reference data that never changes (countries)
```

TaskFlow keeps the default. `getTasks(LIST_QUERY)` is subscribed by `AppLayout` for the whole logged-in session (22.09), so it's never collected anyway.

## 3. Refetching

| Trigger | What happens |
|---|---|
| `refetch()` from the hook, or `promise.refetch()` | a new request for that entry, `isFetching` true, old `data` kept |
| a mutation **invalidates** a tag the entry provides (22.08) | refetch if subscribed; otherwise the entry is **removed** |
| `refetchOnMountOrArgChange`, `pollingInterval`, `refetchOnFocus` | see 22.05 |
| `dispatch(apiSlice.util.invalidateTags(['Task']))` | invalidation without a mutation, e.g. after a WebSocket message |

## 4. Cancellation

- `const p = dispatch(endpoint.initiate(arg)); p.abort();` aborts the request. Because `axiosBaseQuery` passes `signal` to Axios (22.03), the HTTP request is really cancelled. The thunk rejects with an `AbortError` (as any aborted `createAsyncThunk` does, 20.10).
- **Unsubscribing does not abort** (verified). If the user leaves a page before its request finishes, the response still arrives and is cached for the next visit. That's usually what you want.
- **Races are handled for you.** If two requests for the same key overlap (a refetch while one is in flight), only the result of the **latest** request is stored. This is S20's `requestId` check (20.10), done by the library.

## 5. Structural sharing: refetches don't break memoization

After a refetch, RTK Query compares the new response with the cached one **deeply**, and it **reuses** every unchanged object and array (`copyWithStructuralSharing`):

```text
before refetch:  data.items = [t1, t2, t3]
server changes only task 2
after refetch:   data.items = [t1, t2', t3]   ← NEW array; t1 and t3 are the SAME objects as before
nothing changed: data                        ← the SAME object as before: no re-render at all
```

That's why S21's work still pays off: `TaskListItem` is `memo`'d on the task object. After a toggle refetches the whole list, **only the toggled card re-renders**. We measured this in the browser in 22.09.

> 💡 Structural sharing is on by default (`structuralSharing: true` per endpoint). Turn it off only for huge responses where the deep compare costs more than the re-render.

## ✅ Recap

- An entry lives while it has subscribers, plus `keepUnusedDataFor` (60 s).
- Invalidated + subscribed → refetch. Invalidated + unsubscribed → removed.
- `abort()` cancels the HTTP request (thanks to `signal`); unsubscribing doesn't.
- Refetches keep unchanged objects identical, so `memo` and selectors keep working.
