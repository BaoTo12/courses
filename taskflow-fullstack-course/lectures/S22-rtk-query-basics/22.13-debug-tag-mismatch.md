# Lecture 22.13 · 🐞 Debug: "I Saved It, but the List Didn't Update"

> **Section:** S22 · **Type:** 🐞 Debug · **Track:** ＋ Extended · **Time:** ~20 minutes
> Verified by: the matching-rules test in `src/verification/s22-rtk-query.claims.test.ts` (a bare provider is not hit by an id invalidation)

*Extended track: outline. Reproduce it, find it with the DevTools, then fix it.*

---

**The bug.** A teammate made the task tags "more precise", but only on the mutation side:

```ts
getTasks: build.query<Page<Task>, TaskQuery>({ query: …, providesTags: ['Task'] }),        // unchanged
patchTask: build.mutation<Task, { id: number; changes: UpdateTaskRequest }>({
  query: …,
  invalidatesTags: (_r, _e, { id }) => [{ type: 'Task', id }],                              // "precise"
}),
```

**Symptom.** Toggle a task: the PATCH succeeds and the "Completed" toast appears, but the card doesn't move to Done until you reload.

**Find it (5 steps):**

1. Network tab: a `PATCH /api/tasks/3` and **no** `GET /api/tasks?size=100` after it. So it's not a rendering bug: no refetch happened.
2. Redux DevTools → the `api/executeMutation/fulfilled` action. The mutation ran.
3. DevTools → the **RTK Query** tab (or `state.api.provided`). `getTasks({"size":100})` is listed under `Task` **without an id**: it provides the bare tag only.
4. Compare with 22.08 §3. Invalidating `{ type: 'Task', id: 3 }` matches only entries that provide id 3. A bare provider isn't one.
5. Conclusion: provider and invalidator disagree about granularity.

**Fixes, from quick to right:**

- Quick: invalidate the bare tag again, `invalidatesTags: ['Task']`. That's correct, and what S22 ships.
- Right (S23): make the **provider** precise too. `providesTags: (result) => [...(result?.items.map(({ id }) => ({ type: 'Task' as const, id })) ?? []), { type: 'Task', id: 'LIST' }]`. Then a PATCH invalidates `{ type: 'Task', id }`, and a POST or DELETE invalidates `{ type: 'Task', id: 'LIST' }`.

**Takeaway.** When tags don't fire, look at **what the entry provides**, not only at what the mutation invalidates. Always change both sides together, and add a test that counts requests (like `comments.test.ts`).
