## 1. Look at what S20 and S21 built

Open `tasksSlice.ts` and `tasksThunks.ts` as they are at the `s21-end` tag. Count what TaskFlow writes by hand just to **show the tasks the server already has**:

| Concern | Where it lives at `s21-end` |
|---|---|
| The data itself | `tasksSlice` (an entity adapter, 21.13) |
| "Is it loading? Did it fail? With what error?" | `status` + `error` fields, three `addCase`s per thunk |
| "Don't fetch twice at once" | the `condition` option of `fetchTasks` (20.10) |
| "Fetch on first render" | a `useEffect` in `AppLayout` that dispatches `fetchTasks()` |
| "After a save, the list is stale" | reducers that patch the list with the saved task, by hand, per thunk |
| "After logout, forget everything" | a `loggedOut` case in every slice |
| Categories | the **same** again in `categoriesSlice` + `categoriesThunks` |
| Comments (coming in 22.11) | …the same a third time |

None of that code is about *tasks*. It is about **caching data that belongs to someone else**. Every feature that reads from the server repeats it, and every copy can have its own bug.

## 2. Two kinds of state

| | **Client state** | **Server state** |
|---|---|---|
| Owner | the browser tab | the server (MySQL behind the servlets, S28+) |
| Examples in TaskFlow | sort order, page size, theme, the quick-find text, open dialogs, toasts | tasks, categories, comments, the current user's profile |
| Can it be out of date? | No: the app *is* the source of truth | **Yes, always**: another tab, another user or the admin portal can change it |
| Needs | a place to live, reducers | fetching, caching, de-duplication, loading/error flags, **re-fetching when stale**, forgetting when unused |
| Right tool | a slice (`createSlice`) | a **data-fetching cache** (RTK Query) |

The copy of the tasks in your Redux store is not "the tasks". It is **a snapshot of the server at some moment**, a cache. Treating it like client state is why S20 needed hand-written patches after every save.

> 💡 Rule of thumb: **if a refresh of the page would load it from the server, it's server state.** If a refresh would lose it or read it from a cookie/localStorage, it's client state.

## 3. What a cache must do

Whatever library you use (RTK Query, TanStack Query, SWR, Apollo), a server-state cache answers the same questions:

1. **Keying.** `GET /tasks?size=100` and `GET /tasks/5` are different data. Each argument gets its own **cache entry**.
2. **De-duplication.** Ten components ask for the same entry at once → **one** request.
3. **Status per entry.** loading / fetching / success / error, without hand-written reducers.
4. **Lifetime.** Keep an entry while someone uses it; drop it some time after the last user leaves.
5. **Staleness.** After a mutation, know **which** entries are now wrong and refetch them.
6. **Cancellation and races.** An old response must never overwrite a newer one.

S20's hand-written thunks did (2), half of (3) and (5), and none of (4). RTK Query does all six, **declaratively**: you describe endpoints; it writes the slice, the thunks, the reducers and the hooks.

## 4. What stays in slices after S22

RTK Query does **not** replace Redux. After this section, TaskFlow's store looks like this:

```text
state
├── api          ← RTK Query's cache: tasks, categories, comments (server state)
├── listPrefs    ← sort + page size (client state, a slice)
├── ui           ← toasts, selection (client state, a slice)
└── quickFind    ← the search box (client state + a listener, 21.15)
```

Your S21 skills stay: memoized selectors now read **from the cache** (22.09), listeners react to **endpoint matchers** (22.09), and `listPrefs`/`ui` are ordinary slices.

## 5. When a slice is still the right answer for server data

- The data is **written by the client** and only later saved (a draft, a multi-step wizard). Until it is saved, it's client state.
- You need **offline-first** behaviour with a local queue of edits: a cache that refetches is the wrong model. You need a sync engine.
- Real-time streams (a chat log over WebSocket) can still live in RTK Query (`onCacheEntryAdded`, S23), but sometimes a slice fed by a listener is simpler.

## ✅ Recap

- Server state is a **cache of someone else's data**: it can always be stale.
- The six cache jobs (keying, dedupe, status, lifetime, staleness, races) are the same for every feature, so they belong in a library, not in each slice.
- RTK Query lives **inside** your Redux store as one more slice (`state.api`); client state stays in your own slices.
