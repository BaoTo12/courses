# Lecture 22.08 · Tags: `providesTags`, `invalidatesTags`, and the Matching Rules

> **Section:** S22 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~45 minutes

## 1. The idea

Every cache entry **declares what it contains** (`providesTags`). Every mutation **declares what it changed** (`invalidatesTags`). When a mutation succeeds, the middleware finds every entry whose tags match and:

- refetches it if it has subscribers;
- removes it if it doesn't. It would be stale on the next visit anyway.

You never write "after saving a task, refetch the list and the details page and the dashboard". You write "this list contains Tasks" and "this save changed Tasks".

## 2. Two shapes of tag

```ts
'Task'                     // a bare tag: "tasks in general"
{ type: 'Task', id: 5 }    // an id tag: "task 5"
{ type: 'Task', id: 'LIST' } // a convention (S23): "the list of tasks", i.e. its membership
```

The `type` must be listed in `tagTypes`. The `id` is any string or number.

## 3. The matching rules (verified)

| Entry provides ↓ / mutation invalidates → | `'Task'` | `{ type: 'Task', id: 5 }` |
|---|---|---|
| `'Task'` | ✅ refetched | ❌ **not** refetched |
| `{ type: 'Task', id: 5 }` | ✅ refetched | ✅ refetched |
| `{ type: 'Task', id: 6 }` | ✅ refetched | ❌ |

Read it as:

- **Invalidating a bare tag hits everything of that type**, with or without ids.
- **Invalidating an id tag hits only entries that provide that same id.** An entry that provides only the bare `'Task'` is *not* hit. That's the row people get wrong (22.13).

## 4. Static tags vs tag functions

TaskFlow's task endpoints use **static** tags: every task query provides `'Task'`, and every mutation invalidates `'Task'`. That's simple and always correct. It's also wasteful: saving task 5 refetches every task query, including `getTask(7)` if it's mounted.

**Tag functions** compute tags from the data or the arg:

```ts
getComments: build.query<Comment[], number>({
  query: (taskId) => `/tasks/${taskId}/comments`,
  providesTags: (_result, _error, taskId) => [{ type: 'Comment', id: taskId }],
}),
addComment: build.mutation<Comment, { taskId: number; body: string }>({
  query: ({ taskId, body }) => ({ url: `/tasks/${taskId}/comments`, method: 'POST', data: { body } }),
  invalidatesTags: (_result, _error, { taskId }) => [{ type: 'Comment', id: taskId }],
}),
```

This is what you build in 22.11. Posting a comment on task 5 refetches **only** `getComments(5)`. The test proves that `getComments(6)` isn't touched.

The signature is `(result, error, arg) => tags`:

- `result` is `undefined` when the request failed. Guard it (`result ? … : []`) if you build tags from the data.
- `arg` is the endpoint's argument, and it is always available. For "which entity did this mutation touch", the arg is often all you need.

## 5. Timing: when does the refetch happen?

- Tags are invalidated when the mutation's result action is dispatched. Then the refetches start.
- With the default `invalidationBehavior: 'delayed'`, if other queries or mutations are still running, the refetch waits until they settle. That avoids refetching data that another in-flight mutation is about to change again. `'immediately'` refetches right away.
- A **failed** mutation invalidates too: RTK runs `invalidatesTags` for the fulfilled **and** the rejected-with-an-error cases, and passes `error`. If a failed write can't have changed anything, return `[]` when `error` is set.
- `dispatch(apiSlice.util.invalidateTags(['Task']))` does the same without a mutation. Use it for "the server told us something changed" (S47).

## 6. What "invalidate" does NOT do

- It doesn't update data locally. The new data comes from the **refetch**. For instant UI, you patch the cache yourself (`updateQueryData`, optimistic updates, S23).
- It doesn't cross API slices. Tags are per `createApi`, which is one more reason for **one** API slice.
- It doesn't prevent the wasted request you'll see in 22.09: after deleting task 5, `getTask(5)` (the details page you're on) provides `'Task'`, gets invalidated, and refetches. The result is a `404`. S23 fixes it with id tags and by removing the entry.

## 📇 API card: `providesTags` / `invalidatesTags` / `util.invalidateTags`

| | On | Type | Called with |
|---|---|---|---|
| `providesTags` | queries | `TagDescription[] \| (result, error, arg, meta) => TagDescription[]` | every time the entry's data (or error) is stored |
| `invalidatesTags` | mutations | same shape | when the mutation settles |
| `apiSlice.util.invalidateTags(tags)` | an action creator | `TagDescription[]` | dispatch it anywhere |

`TagDescription` = `TagType | { type: TagType; id?: string | number }`.

**Minimal example (outside TaskFlow):** a shop's cart:

```ts
getCart: build.query<Cart, void>({ query: () => '/cart', providesTags: ['Cart'] }),
getProduct: build.query<Product, string>({ query: (sku) => `/products/${sku}`, providesTags: (_r, _e, sku) => [{ type: 'Product', id: sku }] }),
addToCart: build.mutation<Cart, { sku: string; qty: number }>({
  query: (body) => ({ url: '/cart/items', method: 'POST', body }),
  // the cart changed, and so did that product's stock:
  invalidatesTags: (_r, _e, { sku }) => ['Cart', { type: 'Product', id: sku }],
}),
```

**When to use:** always, for every query and every mutation that changes what some query shows.

**When not to:** data that never changes (a list of countries). Give it no tags and a long `keepUnusedDataFor`.

**Common mistakes:**
- Providing only `'Task'` and invalidating `{ type: 'Task', id }`. Nothing refetches (22.13).
- A type missing from `tagTypes`. It's a type error; don't "fix" it with a cast.
- `providesTags: (result) => result.items.map(…)` without handling `result === undefined` (an error). It crashes.
- Expecting invalidation to refetch an unmounted page. Unsubscribed entries are removed, and they refetch on the next visit.

## ✅ Recap

- **Provide** what you contain, **invalidate** what you changed.
- A bare invalidation hits every tag of that type. An id invalidation hits only the same id.
- Tag functions `(result, error, arg)` make it precise. Static tags make it simple.
