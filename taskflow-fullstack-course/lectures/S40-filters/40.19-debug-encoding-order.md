# Lecture 40.19 · 🐞 Debug: POST Data Is Still Garbled (a Parameter Was Read Before the Encoding Filter Ran)

> **Section:** S40 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~15 minutes

---

## 1. Symptom

A new filter was added **before** `encoding` in `web.xml`:

```xml
<filter-mapping><filter-name>csrf</filter-name><url-pattern>/*</url-pattern></filter-mapping>       <!-- moved up -->
<filter-mapping><filter-name>encoding</filter-name><url-pattern>/*</url-pattern></filter-mapping>
```

## 2. Cause

`CsrfFilter` calls `request.getParameter("_csrf")`. The **first** call to any parameter method makes the container parse the whole body, with the encoding **at that moment**: none was set, so ISO-8859-1. From then on, `setCharacterEncoding` has **no effect**: the spec says it must be called before reading parameters or the body, and later calls are ignored.

## 3. Find it

- Log `request.getCharacterEncoding()` in the servlet: it says `UTF-8`, which is misleading. The body was parsed earlier.
- Look for **anything** that reads parameters before the encoding filter: another filter, a valve, a listener, a logging filter that logs parameters.

## 4. Fix

The encoding filter goes **first** (40.14), and no filter reads parameters before it. TaskFlow's `web.xml` comment says so, for the next person who reorders the filters.

## ✅ Takeaway

The request encoding is fixed the moment the first parameter is read. "Set encoding" must happen before any code, in any filter, touches a parameter.
