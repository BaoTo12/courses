# Lecture 40.08 · Dispatcher Types: `REQUEST`, `FORWARD`, `INCLUDE`, `ERROR`, `ASYNC`

> **Section:** S40 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes

---

## 1. Filters run per **dispatch**, not per request

A single browser request can pass through the container's dispatcher several times:

```text
GET /tasks                     REQUEST   → filters mapped for REQUEST → TaskListServlet
  forward to list.jsp          FORWARD   → filters mapped for FORWARD (none in TaskFlow) → list.jsp
    <jsp:include flash.jsp>    INCLUDE   → filters mapped for INCLUDE → flash.jsp
sendError(404) with an <error-page> (S43)
                               ERROR     → filters mapped for ERROR → the error page
```

| Dispatcher type | When |
|---|---|
| `REQUEST` (the default) | a request arriving from the client |
| `FORWARD` | `RequestDispatcher.forward` |
| `INCLUDE` | `RequestDispatcher.include`, `<jsp:include>` |
| `ERROR` | the container rendering an `<error-page>` (S43) |
| `ASYNC` | an async request resumed with `AsyncContext.dispatch()` (S45) |

## 2. Choosing

| Filter | Dispatchers | Why |
|---|---|---|
| encoding, logging, maintenance, CSRF | `REQUEST` | once per client request; logging on FORWARD would log each request twice |
| security headers | `REQUEST` + `ERROR` | an error page is a new response body that needs the headers (S43) |
| authentication (S41) | `REQUEST` | forwards and includes are internal: the check already happened |

**"Why didn't my filter run on the JSP?"** Because the JSP is reached by a **forward**, and the filter is mapped for `REQUEST` only. That's usually correct: guard the entry point, not the internal steps. If a JSP must be protected, keep it under `WEB-INF` (32.08), where no request can reach it directly.

## ✅ Recap

A filter mapping lists the dispatcher types it applies to; by default only `REQUEST`. Add `ERROR` for anything error pages need; rarely `FORWARD`/`INCLUDE`.
