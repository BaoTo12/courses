# Lecture 46.10 · 🔓 Mass Assignment in a JSON API (Conceptual)

> **Section:** S46 · **Type:** 🔓 Attack Lab (conceptual) · **Track:** ★ Core · **Time:** ~15 minutes
> Verified (after the defence): `S46JsonApiTest.clientsCannotSetServerControlledFields`

---

## 1. The flaw

JSON makes mass assignment (37.11, 42.08) even easier to write:

```java
Task task = Json.read(request, Task.class);   // ❌ bind the body into the ENTITY
service.update(task);
```

Every property of `Task` becomes settable by the client, not just the six the form shows:

| Extra field in the body | Effect |
|---|---|
| `"ownerId": 2` | the task moves to another user (or is taken from them) |
| `"id": 5` on a POST | overwrites someone's existing task instead of creating one |
| `"createdAt": "2000-01-01T00:00:00Z"` | forged history |
| `"role": "ADMIN"` on a profile endpoint binding into `User` | privilege escalation |
| `"enabled": true` | a disabled account re-enables itself |

Nothing in the UI sends these fields, which is why nobody notices: an attacker edits the request in DevTools or sends it with curl.

## 2. What made it possible

Binding **into an object that has more fields than the client may set**, combined with a mapper that fills every field it recognises.

## Lesson

The shape of what a client may send must be written down separately from the shape of what is stored. 46.11 does that.
