# Lecture 46.01 · Same Service Layer, Different View: HTML vs JSON

> **Section:** S46 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes

---

Part 3 starts where Part 2's architecture pays off. The **service** layer doesn't know how its results are shown.

```text
                       ┌─ TaskListServlet ─ TaskFilter from ?status=&q= ─┐
Browser (Admin Portal) ┤                                                 ├─► TaskService.page(…, caller) ─► TaskDao ─► MySQL
                       │   forward → list.jsp → HTML                     │         ▲
React (TaskFlow Web) ──┴─ TaskApiServlet ─ TaskFilter from ?status=&q= ──┘         │ the SAME ownership rules (42.05, 42.09)
                           Json.write → PageDto<TaskDto> → JSON
```

## What changes, what stays

| Concern | JSP controller | API servlet |
|---|---|---|
| input | form parameters → `TaskForm` | JSON body → `TaskInput`; query parameters |
| validation errors | 400 + the form again, messages next to fields | 400 + `{"fieldErrors": {…}}` |
| success after a write | 303 redirect (PRG) + flash | 201 + `Location` + the resource; 204 for delete |
| output | request attributes → JSP → HTML (escaped by the view) | DTO records → Jackson → JSON (escaped by React when rendered) |
| errors | error pages (S43) | the standard error JSON (46.08) |
| not logged in | 303 to `/login` | 401 JSON (S47) |
| CSRF | a hidden `_csrf` field | JSON-only bodies (46.07), then a double-submit header (S47) |
| **business rules, ownership, queries** | `TaskService` | **the same `TaskService`** |

## Why this matters

A rule fixed in the service is fixed for both clients. A rule implemented in a controller (or worse, a view) has to be implemented twice, and one copy will drift. S42 put ownership in the service **for exactly this moment**: the API gets IDOR protection without a line of new authorisation code (46.12).

## ✅ Recap

Two controllers, two formats, one service. Everything below the controller is shared.
