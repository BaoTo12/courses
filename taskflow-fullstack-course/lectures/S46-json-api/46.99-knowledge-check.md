# Lecture 46.99 · ✅ Knowledge Check: A REST API with Servlets

> **Section:** S46 · **Type:** ✅ Knowledge Check · **Track:** ★ Core · **Time:** ~15 minutes

**1. (Concept)** What changes between rendering the task list as JSP and as JSON, and what stays identical?

<details><summary>Answer</summary>

**Changes:** the input parsing (form/query parameters → `TaskFilter` in both, but the API validates strictly and returns 400; the HTML list falls back to defaults), the numbering (1-based clamped vs 0-based), the output (request attributes + JSP vs DTOs + Jackson), error handling (pages vs error JSON), success conventions (PRG vs 201/204), and later authentication responses (redirect vs 401).

**Identical:** `TaskService.page/pageAt`, the owner scope, `TaskFilter`/`TaskSort`, the DAO queries, the database. Everything below the controller (46.01).
</details>

**2. (Code reading)** Given `pathInfo` values `null`, `/`, `/5`, `/5/comments`, `/abc`, what does `TaskApiServlet` do (for GET)?

<details><summary>Answer</summary>

| `pathInfo` | segments | GET → |
|---|---|---|
| `null` | `[]` | the list |
| `/` | `[]` | the list |
| `/5` | `["5"]` | task 5 (404 if missing or not yours) |
| `/5/comments` | `["5", "comments"]` | task 5's comments |
| `/abc` | `["abc"]` | 404 `Task not found` (not a valid id) |

And `/5/x` → 404 `No endpoint GET /api/tasks/5/x`.
</details>

**3. (Design)** 400 vs 422 vs 409: choose for "title blank", "category in use", "malformed JSON".

<details><summary>Answer</summary>

- **Malformed JSON → 400**: the request can't even be parsed.
- **Title blank → 400 or 422**: the JSON is fine, a field breaks a rule. 422 ("unprocessable entity") states that precisely; many APIs (and TaskFlow's contract, fixed in Part 1) use 400 with `fieldErrors`. Pick one and use it consistently.
- **Category in use (deleting a category that tasks reference) → 409 Conflict**: the request is valid, but conflicts with the **current state** of the resource; it may succeed later (after the tasks move). TaskFlow's HTML equivalent is `CategoryService.DeleteResult.IN_USE` (37.15).
</details>

**4. (Implementation)** `GET /api/stats` with counts by status and priority for the current user.

<details><summary>Answer</summary>

`StatsApiServlet`: `service.countByStatus(user)` and `service.countByPriority(user)` (both use `ownerScope`), `total` = the sum, written as `StatsDto(total, byStatus, byPriority)`:

```text
{"total":22,"byStatus":{"TODO":10,"IN_PROGRESS":6,"DONE":6},"byPriority":{"LOW":5,"MEDIUM":9,"HIGH":8}}
```

(Numbers for illustration.) Every key present, zeros included, so the client never has to handle a missing key.
</details>

**5. (Security)** Why does TaskFlow's API ignore `"ownerId": 2` in a PATCH instead of rejecting it?

<details><summary>Answer</summary>

`FAIL_ON_UNKNOWN_PROPERTIES` is off, and `TaskInput` never reads `ownerId`: the field has no effect, so ignoring it is safe, and clients that send whole objects back (React sends the task it received) keep working. What matters is that nothing binds it (46.11). Rejecting unknown fields would also be safe, just stricter for clients.
</details>
