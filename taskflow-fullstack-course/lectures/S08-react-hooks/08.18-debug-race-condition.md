# Lecture 08.18 · 🐞 Debug: Search Shows Results for an Older Query (a Race Condition)

> **Section:** S08 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~20 minutes

---

## Setup (📦 provided): a fake search API with realistic, uneven latency

`src/data/fake-search.ts`:

```ts
import type { Task } from '../domain/types';
import { SAMPLE_TASKS } from './sample-tasks';

/** Simulates a server search. Short queries are SLOWER (more rows to scan, say). */
export function fakeSearch(q: string, signal?: AbortSignal): Promise<Task[]> {
  const delay = Math.max(100, 900 - q.length * 250);
  return new Promise((resolve, reject) => {
    const timer = setTimeout(() => {
      resolve(SAMPLE_TASKS.filter((t) => t.title.toLowerCase().includes(q.toLowerCase())));
    }, delay);
    signal?.addEventListener('abort', () => {
      clearTimeout(timer);
      reject(new DOMException('Aborted', 'AbortError'));
    });
  });
}
```

## Symptom

```tsx
function ServerSearch() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState<Task[]>([]);

  useEffect(() => {
    fakeSearch(query).then(setResults);
  }, [query]);

  return (
    <>
      <SearchBox value={query} onChange={setQuery} />
      <TaskList tasks={results} onToggle={() => {}} onEditTitle={() => {}} />
    </>
  );
}
```

Type "rep" quickly. The input says **"rep"**, but the list shows the results for **"r"** (all tasks containing "r"). It happens only sometimes, and only when typing fast. Classic.

## Investigation checklist

1. How many requests are in flight after typing three letters quickly?
2. In what order do the responses **arrive**? (Look at the delays.)
3. Which response calls `setResults` **last**?
4. What does the effect's cleanup do right now?

## Explanation

```text
t=0ms    query "r"   → request A (900-250 = 650 ms)
t=50ms   query "re"  → request B (400 ms)      → arrives t=450
t=100ms  query "rep" → request C (150 ms)      → arrives t=250
                                               …A arrives t=650 → setResults(results for "r")  ← LAST WINS
```

Responses arrive **out of order**. Without cleanup, every response calls `setResults`, and the **slowest**, the oldest query's, overwrites the newest. A Node simulation of this exact timing (same delay formula, a short list of titles, keystrokes 50 ms apart) produced:

```text
buggy: {"q":"r","r":["Write quarterly report","Fix login redirect bug","Prepare sprint demo","Review onboarding doc"]}
fixed: {"q":"rep","r":["Write quarterly report","Prepare sprint demo"]}
```

This is a **race condition**: the result depends on timing you don't control. Real networks behave exactly like this (caches, server load, different query costs).

## Fix: make each effect run responsible for its own request

```tsx
useEffect(() => {
  const controller = new AbortController();
  fakeSearch(query, controller.signal)
    .then(setResults)
    .catch((error: unknown) => {
      if (controller.signal.aborted) return;
      console.error(error);
    });
  return () => controller.abort();   // a newer query cancels the older request
}, [query]);
```

When `query` changes, React runs the **cleanup** of the previous effect first, aborting its request, so its result can never arrive. Only the latest query's response can call `setResults`.

If an API can't be aborted, use an **ignore flag** instead:

```tsx
useEffect(() => {
  let ignore = false;
  fakeSearch(query).then((r) => { if (!ignore) setResults(r); });
  return () => { ignore = true; };
}, [query]);
```

Combine with `useDebounce` (08.12) to send fewer requests in the first place: debounce **reduces** requests, and cleanup **guarantees** correct ordering. You want both.

## Where this comes back

- **S18:** the same race with Redux thunks (a slow `fetchTasks` overwriting a newer one) and the request-ID fix.
- **S22:** RTK Query handles this for you: results are cached per argument, so an old query's response lands in the cache entry for *that* query and can't overwrite the newer one.
