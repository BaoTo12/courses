# Lecture 08.01 · What a Hook Really Is, and Why the Rules of Hooks Exist

> **Section:** S08 · React Hooks in Depth
> **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> 🔗 Official reading: react.dev → Reference → "Rules of Hooks"

---

## 1. The puzzle

A component is a plain function that React calls on every render (07.04). Local variables start fresh each time. Yet this works:

```tsx
function TaskCard({ task }: TaskCardProps) {
  const [isEditing, setIsEditing] = useState(false);
  const [draft, setDraft] = useState(task.title);
  // …
}
```

How does `useState(false)` "remember" it was set to `true` last time? `useState` has no key or name. It's called with the same arguments every render.

## 2. The answer: hooks are identified by call order

React stores hook data **on the component instance** (the Fiber node for this position in the tree, 07.04) as an ordered list:

```text
TaskCard instance (task id 3)
  hook[0]: state  → isEditing = true
  hook[1]: state  → draft = "Plan offsite"
  hook[2]: ref    → inputRef
  hook[3]: effect → deps [true]
```

During each render, React walks this list **in order**:
- 1st hook call in the function → `hook[0]`
- 2nd hook call → `hook[1]`
- …

So `useState(false)` doesn't need a name: **being the first hook call** is its identity. The initial value is only used on the very first render, when the slot is created.

> 🧠 **Mental model:** each component instance has a small array of "memory cells". Hooks are how your function reads and writes cells, matched purely by **position**.

## 3. The Rules of Hooks follow directly

**Rule 1: only call hooks at the top level.** Not inside conditions, loops or nested functions.

```tsx
function TaskCard({ task }: TaskCardProps) {
  if (task.status === 'DONE') {
    const [x, setX] = useState(0);   // ❌ called only sometimes
  }
  const [isEditing, setIsEditing] = useState(false);
}
```

On a render where the condition is false, `isEditing`'s call becomes the **1st** hook, but last time it was the **2nd**. React hands it the wrong cell. Data gets scrambled, or React throws `Rendered fewer hooks than expected`. The same applies to loops (a different count each render) and early returns placed **before** a hook call.

**Rule 2: only call hooks from React functions**, meaning components or other custom hooks (names starting with `use`). A normal utility function isn't called during a render, so there's no instance to attach the memory to.

The linter enforces both. The Vite template's `.oxlintrc.json` has `"react/rules-of-hooks": "error"`.

### Correct patterns for conditional behaviour

```tsx
const [isEditing, setIsEditing] = useState(false);   // always called
if (task.status === 'DONE') { … }                     // condition AFTER hooks, using their values

useEffect(() => {
  if (!isEditing) return;                            // condition INSIDE the hook
  inputRef.current?.select();
}, [isEditing]);
```

## 4. The hooks you'll use in this course

| Hook | Purpose | Lecture |
|---|---|---|
| `useState` | Local state | 07.08, 08.02 |
| `useEffect` | Synchronise with external systems (fetch, timers, DOM, subscriptions) | 08.03 |
| `useRef` | Mutable box that doesn't trigger renders; DOM references | 08.06 |
| `useReducer` | State + update logic as `(state, action) → state` | 08.07 |
| `useContext` | Read a value provided higher in the tree | 08.09 |
| `useMemo` / `useCallback` | Cache values / functions between renders | 08.13, S21 |
| `useId` | Stable unique IDs for accessibility attributes | 08.14 |
| `useTransition` / `useDeferredValue` | Mark updates as non-urgent | 08.14 |
| `useLayoutEffect` | Effects that must run before paint | 08.14 |
| React-Redux: `useSelector`, `useDispatch` | Read from and dispatch to a Redux store | S17 |

## 5. Summary

- Hooks store data on the component **instance**, matched by **call order**.
- Therefore: call hooks unconditionally, at the top level, from components or custom hooks.
- Put conditions **inside** hooks or **after** them, never around them.

## 6. Check yourself

1. Why does `useState(task.title)` not reset the draft when `task.title` changes later?
2. What goes wrong if a hook is called after an early `return` that only happens sometimes?

<details>
<summary>Answers</summary>

1. The initial value is used **only when the slot is created** (first render). Afterwards, React returns the stored value. (To reset on a new task, change the component's `key` (07.11), or update the draft explicitly.)
2. On renders that return early, fewer hooks are called than on other renders, so the call order changes and React either mismatches cells or throws "Rendered fewer hooks than expected".

</details>
