# Lecture 08.02 · `useState` in Depth: Batching, Functional Updates, Lazy Initial State, Stale Closures

> **Section:** S08 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes

---

## 1. Batching: many updates, one render

```tsx
function handleReset() {
  setStatusFilter(null);
  setQuery('');
  setView('list');
}
```

Three setters, but React renders **once**. Since React 18, updates are **automatically batched** everywhere: event handlers, promises, timeouts. React queues the updates, finishes running your handler, then processes the queue and renders.

Why batch? Performance (one render instead of three), and **consistency**: you never render an intermediate state where the filter is reset but the query isn't.

## 2. Functional updates (recap from 07.08, now with the queue model)

```tsx
setCount(count + 1);
setCount(count + 1);
setCount(count + 1);
// queue: [set to 1, set to 1, set to 1] → result 1 (if count was 0)

setCount((c) => c + 1);
setCount((c) => c + 1);
setCount((c) => c + 1);
// queue: [c→c+1, c→c+1, c→c+1] → processed in order → 3
```

React processes the queue in order during the next render: a plain value **replaces**, a function **receives the result so far**. Rule: **if the next state depends on the previous state, use the function form.** It's also required for correctness in closures that outlive a render (timers, subscriptions; see §4).

## 3. Lazy initial state

```tsx
const [value, setValue] = useState(() => readFromLocalStorage(key));   // function: called ONCE
const [value2, setValue2] = useState(readFromLocalStorage(key));       // called EVERY render (result ignored after the first)
```

Passing a **function** tells React "call this only when creating the state". Use it when computing the initial value is expensive or has side effects (reading `localStorage`, parsing JSON). Our `useLocalStorage` hook (08.12) uses it.

## 4. Stale closures: the bug behind many "React is weird" moments

Every render creates **new** handler functions that close over **that render's** state (04.08). If a function created during an old render runs later, it sees **old** state.

```tsx
function Stopwatch() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setSeconds(seconds + 1);      // ❌ `seconds` is from the FIRST render: always 0
    }, 1000);
    return () => clearInterval(id);
  }, []);                           // effect runs once → interval callback never updated

  return <p>{seconds}</p>;         // shows 1, then stays at 1 forever
}
```

The interval callback was created in the first render, where `seconds` is `0`. Every tick sets `0 + 1`.

Fixes:
- **Functional update** (best here): `setSeconds((s) => s + 1)`. No need to read `seconds` at all.
- Or include `seconds` in the effect's dependencies (the effect re-subscribes each second, which is wasteful here).
- Or keep the latest value in a ref (08.06) for callbacks that must read fresh values without re-subscribing.

## 5. Setting the same value bails out

```tsx
setStatusFilter('DONE');   // already 'DONE' → Object.is equal → React skips re-rendering children
```

(React may still call the component function once to confirm, but won't re-render children or commit.) That's the flip side of 07.17's bug: same reference = "nothing changed".

## 6. State with objects: replace, don't merge

Unlike old class components' `this.setState`, the `useState` setter **replaces** the value:

```tsx
const [form, setForm] = useState({ title: '', priority: 'MEDIUM' as Priority });
setForm({ title: 'X' });                               // ❌ priority is gone (and a TS error)
setForm((f) => ({ ...f, title: 'X' }));                // ✅ spread to keep the other fields
```

## 7. Summary

- Updates are batched → one render, consistent state.
- Use `setX(prev => next)` when next depends on prev; the queue is processed in order.
- Lazy init `useState(() => expensive())` runs once.
- Stale closures: callbacks from old renders see old state; functional updates or refs fix it.
- Same value → bail out; object state is replaced, not merged.

## 8. Check yourself

1. `setCount(count + 1); setCount(c => c + 1);` with `count = 0`. Result?
2. Why does the stopwatch above stop at 1?

<details>
<summary>Answers</summary>

1. **2**: the first sets 1, the second receives 1 and returns 2.
2. The interval callback closed over `seconds = 0` from the first render and the effect never re-runs, so it keeps setting `0 + 1`.
