# Lecture 08.09 · `useContext`: Context as Dependency Injection, and Its Re-render Cost

> **Section:** S08 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> 🔗 Official reading: react.dev → Learn → "Passing Data Deeply with Context"

---

## 1. The problem

The theme preference is needed by a toggle in the **header**, and potentially by charts on the dashboard, a modal, a date picker… Passing `theme` and `setTheme` through every component is prop drilling (07.14).

## 2. Context in three steps

```tsx
// 1. Create it (with a default used when there's NO provider above)
const ThemeContext = createContext<ThemeContextValue | null>(null);

// 2. Provide a value somewhere up the tree
<ThemeContext.Provider value={{ preference, setPreference, cycle }}>
  <App />
</ThemeContext.Provider>

// 3. Read it anywhere below, without props
const theme = useContext(ThemeContext);
```

`useContext` finds the **nearest** provider above the calling component and returns its `value`. Any component in the subtree can read it, however deep.

> 🧠 **Mental model: dependency injection.** Like Spring injecting a bean into any class that asks for it, a provider "registers" a value for a subtree, and components "request" it by context. It's a Java concept you already know, in React form. (Spring comes back in the backend part of the course.)

## 3. The `null` default + a custom hook pattern

```ts
export const ThemeContext = createContext<ThemeContextValue | null>(null);

export function useTheme(): ThemeContextValue {
  const context = useContext(ThemeContext);
  if (context === null) {
    throw new Error('useTheme must be used inside <ThemeProvider>');
  }
  return context;
}
```

- A `null` default means "no provider", which is almost always a bug (forgot to wrap the app).
- The custom hook converts that into a **clear error** and narrows the type to `ThemeContextValue`, so components never deal with `null`.
- Components import `useTheme`, not the context object. That's a clean API.

## 4. The re-render cost

When a provider's `value` changes (by `Object.is`), **every component that reads that context re-renders**, even if it only uses a part of the value that didn't change, and even if memoised with `React.memo`.

Two practical consequences:

1. **Memoise the provided object.** `value={{ preference, setPreference }}` creates a **new object every render** of the provider → all consumers re-render every time the provider's parent re-renders. Wrap it in `useMemo` (08.10 does).
2. **Don't put fast-changing, widely-used data in one big context.** A context holding "all tasks + filters + UI state" re-renders every consumer on every change. That's one reason **Redux** exists: `useSelector` lets each component subscribe to **only the slice it uses** and re-render only when **that** changes (S17). Context is great for low-frequency values (theme, locale, current user); Redux (or similar) is better for large, frequently updated app state.

(Fun fact: React-Redux's `<Provider>` uses context to pass the **store object**, which never changes, so context itself causes no re-renders. The subscriptions happen through `useSelector`. More in S17.)

## 5. Summary

- `createContext` → `<Provider value>` → `useContext` anywhere below: dependency injection for components.
- `null` default + a `useX()` hook that throws gives clear errors and non-null types.
- Changing a context value re-renders **all** its consumers: memoise the value; keep contexts small and low-frequency.
- Redux's selective subscriptions address context's re-render cost for big app state.
