# Lecture 08.17 · 🐞 Debug: the Infinite Fetch Loop (an Object in the Dependency Array)

> **Section:** S08 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~15 minutes

---

## Symptom

A teammate wants the hook to reload when the filter changes, and writes:

```tsx
function useFilteredTasks(status: TaskStatus | null) {
  const [tasks, setTasks] = useState<Task[]>([]);
  const options = { status };                          // "group the params nicely"

  useEffect(() => {
    const controller = new AbortController();
    fetchTasks(controller.signal).then((all) =>
      setTasks(filterTasks(all, { status: options.status ?? undefined })),
    );
    return () => controller.abort();
  }, [options]);

  return tasks;
}
```

The Network panel fills with **hundreds** of `db.json` requests (most cancelled), the fan spins, and the list flickers.

## Investigation checklist

1. When does the effect re-run? What does React compare? (08.03)
2. Is `options` the same object on the next render?
3. What happens after `setTasks(...)`?
4. Why doesn't the loop stop even though the data is identical each time?

## Explanation

```text
render 1: options = {…}#1 → effect runs → fetch → setTasks(new array)
render 2: options = {…}#2  (NEW object, Object.is(#1, #2) === false) → cleanup (abort) + effect again → fetch → setTasks(new array)
render 3: options = {…}#3 → …forever
```

- `options` is created **in the render body**, so it's a new object every render (08.13).
- Dependencies are compared with `Object.is`: a new object always counts as "changed".
- The effect sets state with a **new array** (`filterTasks` returns one), which causes another render, which creates another `options`… an infinite loop.
- The cleanup aborts each previous request, which is why most are cancelled. That's the only thing keeping it from being even worse.

## Fixes (best first)

1. **Depend on the primitive**, not a wrapper object:
   ```tsx
   useEffect(() => { … filterTasks(all, { status: status ?? undefined }) … }, [status]);
   ```
2. If you really need an object, **create it inside the effect** (it's then not a dependency).
3. If an object must come from outside, **memoise** it: `const options = useMemo(() => ({ status }), [status]);`
4. And reconsider the design: filtering is **derived data**. Fetch once, filter during render (08.05). The effect should synchronise with the *server query*, not with client-side filtering.

## How to spot it quickly

- Network panel: the same request repeating endlessly.
- React DevTools → Profiler: a component rendering continuously.
- The lint rule for effect dependencies is right to list `options`; the bug is **creating** `options` in render, not listing it.
