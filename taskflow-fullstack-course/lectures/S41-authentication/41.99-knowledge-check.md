# Lecture 41.99 · ✅ Knowledge Check: Cookies, Sessions and Authentication

> **Section:** S41 · **Type:** ✅ Knowledge Check · **Track:** ★ Core · **Time:** ~20 minutes

---

**1. (Concept)** Where is session data stored: in the browser or on the server? What does the browser hold?

<details><summary>Answer</summary>

On the server, in Tomcat's memory (`StandardManager`), and on disk at a clean shutdown (41.04). The browser holds only the **id** in the `JSESSIONID` cookie. Whoever presents that id is treated as that session, so the id is the thing to protect: `HttpOnly`, `Secure`, `SameSite`, never in URLs, and changed at login (41.02).
</details>

**2. (Concept)** Why change the session id at login?

<details><summary>Answer</summary>

A session exists before login (TaskFlow's login page stores a CSRF token in it), and its id may be known to someone else: an attacker who planted it in the victim's browser (session fixation, 41.10). Keeping the id across login would hand them the authenticated session. `request.changeSessionId()` keeps the data but kills the old id (41.11). The CSRF token is reset for the same reason.
</details>

**3. (Code reading)** A filter mapped to `/*` calls `request.getSession()` for every request, including static resources. What's the cost?

<details><summary>Answer</summary>

Every anonymous request, whether it's a visitor, a bot, a health check or a CSS file loaded before the cookie exists, **creates** a session: memory on the server, a `Set-Cookie` in the response, a `sessionCreated` event, persistence to disk at shutdown, and a 15-minute timeout before it's freed. A crawler can create thousands. Use `getSession(false)` to read, and create sessions only when you store something (41.02).
</details>

**4. (Debugging)** In production behind HTTPS, users are logged out on every request. What do you check?

<details><summary>Answer</summary>

Follow the cookie (41.21):
- **`Secure` over HTTP.** TLS ends at the proxy, and the proxy talks HTTP to Tomcat. If the app sets `Secure` based on a request it believes is HTTP, or the site is actually served over plain HTTP somewhere (a redirect chain, a health-check host), the browser never sends the cookie back. Configure `RemoteIpValve` so Tomcat knows the original scheme.
- **Path mismatch.** The proxy maps `/` to Tomcat's `/taskflow`, but the cookie says `Path=/taskflow`, so the browser never sends it for `/`. Rewrite the cookie path at the proxy (`ProxyPassReverseCookiePath`) or deploy as the root context.
- **Host mismatch.** `www.` vs the bare domain, or a `Domain` attribute that doesn't match.
- **Several Tomcats without sticky sessions.** Each request lands on a server that doesn't know the session (41.04).
</details>

**5. (Design)** What should, and shouldn't, be stored in the session for an authenticated user?

<details><summary>Answer</summary>

**Should:** a small, serialisable identity: id, username, display name, role (`AuthUser`, 41.07). Also the CSRF token, flash messages, and small per-user UI state (recently viewed, 38.10).

**Shouldn't:**
- the password or its hash;
- personal data that isn't needed on every request;
- whole entities or lists, which go stale and use memory per user;
- anything that must be up to date across users, such as permissions that an admin can revoke. The session copy doesn't change when the database does: S42 re-checks `enabled` on each request.
- non-serialisable objects (DAOs, connections, `EntityManager`s).
</details>

**6. (Code reading)** Why does logout use POST, and why `invalidate()` rather than `removeAttribute("currentUser")`?

<details><summary>Answer</summary>

POST: a GET logout can be triggered by any page (`<img src=".../logout">`), a cross-site nuisance, and prefetchers may follow links. POST + CSRF token makes it deliberate (41.08). `invalidate()`: everything tied to the login (the CSRF token, recently viewed, flash) goes with it; with `removeAttribute`, a later user of the same browser would inherit it, and the old session id would stay valid.
</details>

**7. (Implementation)** Add an admin-only "Unlock bob" action to the throttle. What must it check?

<details><summary>Answer</summary>

```java
public void unlock(String username) { byAccount.remove(key(username)); }
```

behind `POST /admin/users/unlock` (S42): an admin role check on the server, the CSRF token (the filter does it), an audit event `ACCOUNT_UNLOCK` with the admin's username, then a PRG redirect. The IP counters stay: they protect against spraying from one address.
</details>
