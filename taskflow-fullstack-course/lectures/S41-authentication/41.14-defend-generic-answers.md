# Lecture 41.14 · 🛡 Defend: Generic Messages, Consistent Timing

> **Section:** S41 · **Type:** 🛡 Defend · **Track:** ★ Core · **Time:** ~15 minutes
> Verified: `S41AuthenticationTest.unknownUserAndWrongPasswordGetTheSameAnswer` (same status, same message, password never echoed)

---

| Channel | TaskFlow |
|---|---|
| message | one constant: `"Invalid username or password."` for unknown users, wrong passwords **and** disabled accounts |
| status | the same (200 + the form) for all three |
| timing | an unknown username still costs one BCrypt check: `hasher.burnTime(password)` against a dummy hash of the same cost |
| echo | the username comes back (the user typed it); the password never does |
| audit | the details (which case it was) go to the **audit log**, for administrators, never to the response |

```java
if (credentials.isEmpty()) {
  hasher.burnTime(pass);                                        // same cost as a real check (41.14)
  valid = false;
} else {
  valid = hasher.matches(pass, credentials.get().passwordHash()) && credentials.get().enabled();
}
```

**Not perfect:** a database lookup that finds a row can still take slightly longer than one that doesn't, and the throttle (41.15) behaves per account. The goal is to remove the **large, easy** signals. Measuring timing differences of a few milliseconds over the internet takes many requests, and the throttle limits those.

**The same rule elsewhere:** "If an account exists for this email, we've sent a reset link." A sign-up form necessarily reveals taken usernames, so throttle it and require a CAPTCHA there instead.

## ✅ Recap

One message, one status, similar timing, and the details only in the audit log.
