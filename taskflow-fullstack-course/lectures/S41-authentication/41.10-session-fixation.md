# Lecture 41.10 · 🔓 Session Fixation (Conceptual)

> **Section:** S41 · **Type:** 🔓 Attack Lab (conceptual) · **Track:** ★ Core · **Time:** ~15 minutes
> Verified: `S41AuthenticationTest.aSuccessfulLoginChangesTheSessionIdAndGoesBack` (the `JSESSIONID` before and after login differ)

---

## 1. The flaw

If the session id **stays the same** across login, then whoever knew the id **before** login knows it **after**. And a session id can be known in advance:
- the attacker obtains a valid (anonymous) session id for themselves: just visiting the login page creates one;
- if they can make the victim's browser **use** that id (via a sibling subdomain setting a cookie for the parent domain, a URL-rewriting app that accepts `;jsessionid=` in links, or physical access to a shared computer), the victim logs in **into the attacker's session**;
- the attacker, still holding that id, is now logged in as the victim.

## 2. Why TaskFlow was exposed without a fix

The login page creates a session (it holds the CSRF token), and a plain "store the user in the current session" keeps that same id after the password check.

## 3. What limits the entry points

- `<tracking-mode>COOKIE</tracking-mode>`: no `;jsessionid=` in URLs is accepted (41.02).
- `HttpOnly` stops scripts from **reading** the cookie, but not every way of **setting** one.

The real fix doesn't depend on closing every way in: 41.11.

## Lesson

An authentication boundary must also be an **identity** boundary for the session: the id that existed before the proof must not be the id after it.
