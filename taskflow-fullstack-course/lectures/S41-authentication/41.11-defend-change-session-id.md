# Lecture 41.11 · 🛡 Defend: `request.changeSessionId()` at Login; `invalidate()` at Logout

> **Section:** S41 · **Type:** 🛡 Defend · **Track:** ★ Core · **Time:** ~15 minutes
> Verified: `S41AuthenticationTest.aSuccessfulLoginChangesTheSessionIdAndGoesBack`, `.logoutDestroysTheSessionAndPrivatePagesAreNotCached`

## 📇 API card: changing the session id

| Call | Effect | Since |
|---|---|---|
| `request.changeSessionId()` | same `HttpSession` object and attributes, **new id**; returns the new id; `Set-Cookie` with it | Servlet 3.1 |
| `session.invalidate()` + `request.getSession()` | the old way: a brand-new, empty session (copy what you need first) | always |
| `HttpSessionIdListener.sessionIdChanged(event, oldId)` | notified of changes (e.g. to update a "sessions by id" map) | Servlet 3.1 |

## TaskFlow

```java
case SUCCESS -> {
  request.changeSessionId();                                  // 🛡 session fixation (41.11): same data, new id
  HttpSession session = request.getSession();
  session.setAttribute(CurrentUser.SESSION_KEY, result.user());
  Csrf.reset(request);                                        // a new token for the logged-in session
  …
```

- `changeSessionId()` keeps the attributes, so a flash or a pre-login preference survives, but the **id** anyone might have known is dead.
- The CSRF token is reset too: a token that existed before login shouldn't authorise actions after it.
- **Logout** → `invalidate()` (41.08): the id and everything in it are gone.
- **Privilege changes** (a user becomes admin, or re-authenticates for a sensitive action) → change the id again.

Tomcat can also do it automatically for container-managed login (`changeSessionIdOnAuthentication` on its authenticator valve). With hand-written login, it's your line to write.

## ✅ Recap

New id at login, destroyed session at logout. One line each, and session fixation is gone.
