# Lecture 41.21 · 🐞 Debug: After Login, the User Is Immediately Sent Back to the Login Page

> **Section:** S41 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~15 minutes

---

## 1. Symptom

The password is right, the audit log says `LOGIN_OK`, and yet the browser ends up on `/login` again. Sometimes it loops: DevTools shows `303 → /login → 303 → /login…`, and the browser gives up with "too many redirects".

## 2. Checklist

| # | Cause | How to see it |
|---|---|---|
| 1 | the filter **protects `/login` itself**: the login page redirects to the login page | `/login` missing from the public paths; the loop starts at the very first GET |
| 2 | the login stored the user in a session the next request doesn't find: `request.getSession(false)` returned `null` in the login servlet and the code silently skipped storing | log the session id in the POST and the next GET |
| 3 | the user is stored under one attribute name and read under another (`"user"` vs `"currentUser"`) | one constant (`CurrentUser.SESSION_KEY`) for both |
| 4 | `invalidate()` **after** storing the user ("clean start"), or `changeSessionId()` in the wrong order with a copy | read the login code in order |
| 5 | the cookie isn't sent back: `Secure` on plain HTTP, a `Path` that doesn't cover the app, or a different host name (`localhost` vs `127.0.0.1`) | DevTools → the 303's `Set-Cookie`, then the next request's `Cookie` header |
| 6 | the static CSS is protected (40.18): the page works, but the **CSS request** is redirected | the loop is in the CSS request, not the page |

## 3. TaskFlow's guards

`/login` is in `PUBLIC_PATHS`; one constant for the session key; `getSession()` (creating) at login, `getSession(false)` everywhere else; the `S41AuthenticationTest` login tests go from the login POST to a protected page with the same client.

## ✅ Takeaway

Follow the session id: in the login response's `Set-Cookie`, in the next request's `Cookie`, and in the attribute name the filter reads.
