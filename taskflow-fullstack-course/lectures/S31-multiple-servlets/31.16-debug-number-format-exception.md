# Lecture 31.16 · 🐞 Debug: `NumberFormatException` Crashes the Page on `?id=abc`

> **Section:** S31 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~15 minutes
> Verified (the fix): `S31TaskServletsTest.viewValidatesTheId` (`?id=abc` → 400, not 500)

---

## 1. The code and the symptom

```java
long id = Long.parseLong(request.getParameter("id"));   // 💥 for "abc", "", null ("Cannot parse null string")
```

`/tasks/view?id=abc` → **HTTP 500**, and Tomcat's default error page shows `java.lang.NumberFormatException: For input string: "abc"` **with a stack trace**: class names, line numbers, the Tomcat version.

## 2. Two problems, not one

1. **The wrong status.** It's the **client's** malformed input → **400**. A 500 says "our bug", and monitoring treats it as an outage. Scanners hitting `?id=abc` would fill your error dashboards.
2. **Information disclosure.** Stack traces tell attackers your frameworks, versions and code structure. S43 installs custom error pages that never show them, and Tomcat's `ErrorReportValve` can hide the version and trace too.

## 3. Fix: parse without throwing, decide the status yourself

```java
Long id = Params.positiveId(request.getParameter("id"));    // null for null/""/"abc"/"-1"/overflow
if (id == null) {
  response.sendError(HttpServletResponse.SC_BAD_REQUEST, "Parameter 'id' must be a positive number");
  return;
}
```

`Params.positiveId` catches `NumberFormatException` in **one** place and returns `null`. Every servlet then states the rule in one line.

## 4. Look for the family

The same crash appears with `Integer.parseInt`, `LocalDate.parse` (`DateTimeParseException`), `Enum.valueOf` (`IllegalArgumentException`), and `UUID.fromString`. Every conversion of a parameter needs a non-throwing path (31.02).

## ✅ Takeaway

Bad input → 400 by design, never an uncaught exception → 500. And don't show stack traces to users (S43).
