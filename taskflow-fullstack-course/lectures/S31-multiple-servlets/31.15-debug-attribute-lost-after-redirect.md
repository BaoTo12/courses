# Lecture 31.15 · 🐞 Debug: An Attribute Set Before `sendRedirect` Is `null` on the Next Page

> **Section:** S31 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~15 minutes

---

## 1. The code

```java
// TaskDeleteServlet.doPost
store.delete(id);
request.setAttribute("message", "Task deleted");                 // ①
response.sendRedirect(request.getContextPath() + "/tasks");
```

```java
// TaskListServlet.doGet
String message = (String) request.getAttribute("message");         // ② always null
if (message != null) out.println("<p class=\"text-success\">" + Html.escape(message) + "</p>");
```

## 2. Why: two requests

```text
Request #1  POST /taskflow/tasks/delete   ← request object A: setAttribute("message") on A
            ◄ 302 Location: /taskflow/tasks
            (request A is finished and discarded)
Request #2  GET /taskflow/tasks            ← a NEW request object B: B has no "message"
```

Attributes live in **one request object** (31.09). A redirect ends that request, and the browser starts another (31.06). The attribute was never lost: it stayed in a request that no longer exists.

(With a **forward**, it would work, but then Reload would re-POST the delete. Wrong trade.)

## 3. Fixes

| Option | How | Trade-off |
|---|---|---|
| a query parameter | `sendRedirect(ctx + "/tasks?deleted=1")`, and the list shows a **fixed** message for `deleted=1` | simple; the message sticks in the URL (a reload shows it again). Never put raw message **text** in the URL (it's editable → phishing text) |
| a **flash** attribute in the session | set `session.setAttribute("flash", …)` before the redirect; the next page reads it **and removes it** | the standard answer; S38 builds it |

## ✅ Takeaway

A redirect = two requests. Request attributes don't cross it. Use the URL (fixed codes) or a session flash.
