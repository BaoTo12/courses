# Lecture 31.99 · ✅ Knowledge Check: Multiple Servlets

> **Section:** S31 · **Type:** ✅ Knowledge Check · **Track:** ★ Core · **Time:** ~15 minutes

---

**1.** After a forward, what does the browser's URL bar show? After a redirect?

<details><summary>Answer</summary>

Forward: the **original** URL (the browser made one request and never learned about the target). Redirect: the **new** URL from `Location` (the browser made a second request) (31.08).
</details>

**2.** `request.setAttribute("msg", "Saved"); response.sendRedirect("tasks");`: will `/tasks` see `msg`?

<details><summary>Answer</summary>

**No.** The redirect makes the browser send a new request with a new request object, and attributes belonged to the old one. Use a fixed query parameter or a session flash (31.15).
</details>

**3.** The list page shows a stale "Task saved" message after a refresh, and the browser asks to resend a form. Was forward or redirect used after the save?

<details><summary>Answer</summary>

**Forward**, or a page rendered directly by the POST handler. The URL is still the POST's, so Reload re-sends the POST: the message reappears, and worse, the task may be saved again. Use a redirect after a successful POST (PRG) (31.04, 31.08).
</details>

**4.** Parameter or attribute: the task id from the URL, a list the servlet loaded, an error message the servlet computed?

<details><summary>Answer</summary>

The id is a **parameter** (the client sent it). The list and the error message are **attributes** (server-computed objects for the view) (31.09).
</details>

**5.** Implement a `/tasks?status=DONE` filter using parameters only.

<details><summary>Answer</summary>

```java
TaskStatus filter = TaskStatus.parse(request.getParameter("status"));   // null if missing or unknown
List<Task> tasks = filter == null ? store.findAll() : store.findByStatus(filter);
```

Links: `ctx + "/tasks?status=" + status.name()`. An unknown value shows everything, a deliberate choice for a filter (31.01).
</details>

**6.** Why must a servlet `return` immediately after `sendRedirect` or `sendError`?

<details><summary>Answer</summary>

Both commit the response. Code after them still runs: writing more output throws or is ignored, and worse, it may perform actions that the early exit was meant to prevent (30.18, 31.03).
</details>

**7.** `sendRedirect("/tasks")` from an app deployed at `/taskflow` lands on a 404. Why, and the fix?

<details><summary>Answer</summary>

A browser URL starting with `/` is relative to the **server** root, so it goes to `http://host/tasks`, outside the app. Use `request.getContextPath() + "/tasks"`. (Dispatcher paths are the opposite: relative to the app, without the context, 31.11.)
</details>
