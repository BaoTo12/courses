## 1. Why no React?

React-Redux hides how the store and the UI talk to each other. Here you'll wire them by hand: a reducer, a store, a `render()` function and `store.subscribe(render)`. S17 then shows what React-Redux does on top of the same three store methods.

### A 2026 detail: there is no `<script src="redux.js">` any more

Older tutorials load Redux with a classic `<script>` tag that defines a global `Redux` (a "UMD" build). **Redux 5 no longer ships one.** Verified: `node_modules/redux/dist/` contains only ES module and CommonJS files:

| File | What it is |
|---|---|
| `redux.mjs` | ES module, **development** build: full error messages and extra checks |
| `redux.browser.mjs` | ES module, **production** build for browsers: minified, errors reduced to codes |
| `redux.legacy-esm.js`, `cjs/` | For older bundlers and Node's `require` |

So the page uses `<script type="module">` and `import`. Two consequences:

1. **Modules don't load from `file://`.** Double-clicking `index.html` fails (browsers block module imports from local files). Serve the folder over HTTP:

   ```bash
   npx http-server -c-1
   ```

   and open the URL it prints (`-c-1` disables caching, 12.12).

2. **Development vs production build.** First I imported `redux.browser.mjs`. Every mistake then produced a coded message, for example *"Minified Redux error #9; visit https://redux.js.org/Errors?code=9 for the full message…"*. The development build (`redux.mjs`) gives the full message instead. But it reads `process.env.NODE_ENV`, which exists in Node, and which **bundlers replace** at build time (Vite does it for you in the React app). Without a bundler, the page defines it with a tiny classic `<script>` before the module. That's a just-in-time lesson in what bundlers do: libraries ship dev and prod code paths, and the build picks one.

## 3. ✍️ `index.html` (complete)

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <title>Redux counter (no React, no build)</title>
    <style>
      body { font-family: system-ui, sans-serif; margin: 2rem; }
      output { display: inline-block; min-width: 3ch; font-size: 2rem; font-weight: 700; }
      button { font-size: 1rem; margin: 0.25rem; }
      #log { font-family: ui-monospace, monospace; font-size: 0.85rem; white-space: pre; }
    </style>
  </head>
  <body>
    <h1>Redux counter</h1>
    <p>Clicked: <output id="value">0</output> times</p>
    <p>
      <button id="increment">+</button>
      <button id="decrement">−</button>
      <button id="incrementIfOdd">Increment if odd</button>
      <button id="incrementAsync">Increment async</button>
      <button id="incrementBy5">+5</button>
    </p>
    <h2>Action log</h2>
    <div id="log"></div>

    <script>
      // Redux's DEVELOPMENT build reads process.env.NODE_ENV, a Node-ism that bundlers (Vite) replace at
      // build time. Without a bundler, we define it ourselves. 'development' = readable errors + extra checks.
      window.process = { env: { NODE_ENV: 'development' } };
    </script>
    <script type="module">
      // Redux 5 ships ES modules only (no UMD `<script>` build any more).
      // redux.mjs = development build. redux.browser.mjs = minified production build (coded error messages).
      import { createStore } from './node_modules/redux/dist/redux.mjs';

      // ── 1. The initial state ────────────────────────────────────────────────
      const initialState = { value: 0 };

      // ── 2. The reducer: (state, action) → new state. Pure: no mutation, no side effects. ─
      function counterReducer(state = initialState, action) {
        switch (action.type) {
          case 'counter/incremented':
            return { ...state, value: state.value + 1 };
          case 'counter/decremented':
            return { ...state, value: state.value - 1 };
          case 'counter/incrementedBy':
            return { ...state, value: state.value + action.payload };
          default:
            return state; // unknown action (including Redux's own init action): state unchanged
        }
      }

      // ── 3. The store. The 2nd argument hooks up the Redux DevTools extension if it's installed. ─
      const store = createStore(counterReducer, window.__REDUX_DEVTOOLS_EXTENSION__?.());

      // ── 4. The UI: a render function that reads the CURRENT state ─────────────
      const valueEl = document.getElementById('value');
      function render() {
        valueEl.textContent = String(store.getState().value);
      }
      render(); // show the initial state
      store.subscribe(render); // …and re-render after every dispatch

      // A second, independent subscriber: an action log (subscribers don't know about each other).
      const logEl = document.getElementById('log');
      let lastAction = null;
      store.subscribe(() => {
        logEl.textContent += `${JSON.stringify(lastAction)} → ${JSON.stringify(store.getState())}\n`;
      });

      // ── 5. Dispatching actions in response to user input ─────────────────────
      function dispatch(action) {
        lastAction = action;
        store.dispatch(action);
      }
      // Action creators: functions that build action objects (no magic).
      const incremented = () => ({ type: 'counter/incremented' });
      const decremented = () => ({ type: 'counter/decremented' });
      const incrementedBy = (amount) => ({ type: 'counter/incrementedBy', payload: amount });

      document.getElementById('increment').addEventListener('click', () => dispatch(incremented()));
      document.getElementById('decrement').addEventListener('click', () => dispatch(decremented()));
      document.getElementById('incrementBy5').addEventListener('click', () => dispatch(incrementedBy(5)));
      document.getElementById('incrementIfOdd').addEventListener('click', () => {
        // Reading state to DECIDE whether to dispatch is fine (the decision lives outside the reducer).
        if (store.getState().value % 2 !== 0) dispatch(incremented());
      });
      document.getElementById('incrementAsync').addEventListener('click', () => {
        // Async work happens OUTSIDE the reducer; when it's done, we dispatch a plain action.
        setTimeout(() => dispatch(incremented()), 1000);
      });

      // For experimenting in the console (a learning aid, not app code). Use dispatch(…) there
      // (not store.dispatch) so the action log knows which action ran.
      window.store = store;
      window.dispatch = dispatch;
      window.actions = { incremented, decremented, incrementedBy };
    </script>
  </body>
</html>
```

## 4. Walkthrough

### ① The initial state and ② the reducer

The reducer handles three action types and returns `state` for everything else. The `default` branch matters: the store sends its own **init action** first. Verified: a reducer that records what it receives saw one action of type `@@redux/INITp.y.f.h.p.m` (a random suffix, so no app reducer can accidentally handle it). With `state = undefined`, the default parameter produces `{ value: 0 }`.

Every case returns a **new** object (`{ ...state, value: … }`), never `state.value++` (14.06).

### ③ The store

`createStore(reducer, enhancer?)`. The optional second argument here is the DevTools **enhancer** (14.11, and in depth in 16.05). If the extension isn't installed, `window.__REDUX_DEVTOOLS_EXTENSION__?.()` is `undefined`, and `createStore` works without it. VS Code shows ~~`createStore`~~ struck through: that's the deprecation nudge from 14.04, not an error.

### ④ The UI: render + subscribe

```js
render();                 // initial paint
store.subscribe(render);  // after every dispatch
```

This is the whole "UI binding": read state, draw, repeat on change. `render()` doesn't receive the state or the action. It asks the store with `getState()`. Subscribers are **not told which action happened** (the log subscriber needs a workaround: the `dispatch` wrapper records `lastAction`). That limitation is exactly why **middleware** exists (S16): middleware sees every action.

`subscribe` returns an **unsubscribe** function. Verified: a listener registered, called once by a dispatch, then unsubscribed, was not called by the next dispatch.

### ⑤ Dispatching

Buttons dispatch **actions made by action creators**. Two handlers show where "logic" belongs:
- **Increment if odd** reads `getState()` to decide **whether** to dispatch. The decision is outside the reducer. The reducer stays a pure "how state changes".
- **Increment async** waits 1 s, **then** dispatches a plain action. The reducer never sees a timer. In S18, thunks give this pattern a standard home.

## 5. Try it

1. Click the buttons: the number and the log update. Verified sequence: `+`, `+`, `−`, "if odd" (1 is odd → 2), "if odd" (2 is even → no action), `+5`, then async after 1 s → **1, 2, 1, 2, 7, 8**. Notice the second "if odd" produced **no log line**: no action, no reducer call, no notification.
2. In the console:
   ```js
   dispatch(actions.incrementedBy(10));
   store.getState();
   ```
3. Break the rules and read the development build's messages (all verified):

   | You type | Redux says |
   |---|---|
   | `store.dispatch('counter/incremented')` | *Actions must be plain objects. Instead, the actual type was: 'string'. You may need to add middleware…* |
   | `store.dispatch({})` | *Actions may not have an undefined "type" property. You may have misspelled an action type string constant.* |
   | `store.dispatch(() => {})` | *Actions must be plain objects. Instead, the actual type was: 'function'…* (a preview of thunks, S18) |
   | a reducer that calls `store.dispatch` | *Reducers may not dispatch actions.* |
   | a reducer that calls `store.getState()` | *You may not call store.getState() while the reducer is executing. The reducer has already received the state as an argument…* |

   One mistake is **not** caught: a reducer without an initial state (`(state, action) => state`) makes `getState()` return `undefined`, silently. `createStore` doesn't check it (`combineReducers` does: 15.15).
