# Lecture 14.02 · Why Use Redux: Predictable Updates, One Place to Look, Tooling

> **Section:** S14 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> 🔗 Official companion reading: Essentials Part 1 ("Why Should I Use Redux?")

---

## 1. The problem Redux addresses

As an app grows, **shared state** gets harder to reason about. Consider TaskFlow at the end of Part 1:
- the list, the board, the details page, the dashboard and a header badge all show tasks;
- a toggle, an edit, a delete, a filter change and a login can each change what they show;
- some changes come from the server (a fetch finishing), some from the user, some from timers (a toast expiring).

Without structure, the questions "**what** changed this value, **when**, and **why**?" become hard to answer. Changes happen in many components, in many callbacks, in many orders.

## 2. What Redux gives you

### Predictability

State changes **only** by dispatching an action, and **only** reducers compute the new state. Reducers are pure: same state + same action = same result, every time. So any state can be explained as `initialState` + a list of actions. Nothing else could have changed it.

### One place to look

The state lives in one store, and the update logic lives in the reducers. When a value is wrong, you don't search every component for a `setX` call: you look at the actions that were dispatched, and at the reducer that handled them.

### Tooling that follows from the design

Because every change is a plain, serialisable object passing through one point, tools can **record** them. The Redux DevTools (14.11) show:
- every action, in order, with its payload;
- the state after each action, and a **diff**;
- **time travel**: jump back to any earlier state and replay forward;
- the stack trace of where each action was dispatched.

That's hard to get from scattered `useState` calls.

### Separation of concerns

Components describe **what happened** (`dispatch(taskCompleted(5))`); reducers decide **how state changes**; middleware handles **side effects** (API calls, logging). Each layer is smaller, and reducers are the easiest code in the app to unit-test (S15).

### Well-known patterns

Redux has been around since 2015. Its conventions (the Style Guide, `createSlice`, RTK Query) are shared across companies, so a new team member recognises the structure immediately.

## 3. What it costs

Nothing is free:
- **Indirection:** a click goes through an action creator, `dispatch`, middleware and a reducer before the UI updates. More files, more concepts to learn.
- **Boilerplate**, historically. Hand-written Redux (S15–S19) has a lot of it. Redux Toolkit (S20) removes most of it, which is why RTK is the official recommendation today.
- **Rules to respect:** no mutation, serialisable state and actions, no side effects in reducers. Breaking them causes subtle bugs, which you'll debug in S15 and S16.

14.03 turns these trade-offs into a decision guide.

## 4. Summary

- Redux makes state changes **predictable** (only actions, only pure reducers) and **traceable** (one store, one action log).
- DevTools and time travel are consequences of that design.
- The price is indirection and learning curve. RTK reduces the boilerplate.
