# Lecture 14.08 · The Three Principles

> **Section:** S14 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes
> 🔗 Official companion reading: Fundamentals Part 2 ("Redux Concepts and Data Flow"): the principles

---

## 1. Single source of truth

> The **global** state of the app lives in **one object tree**, in **one store**.

- Debugging and inspection get simpler: the whole app's shared state is one object you can log, snapshot, serialise or send in a bug report.
- Features like "save and restore the session state", or rendering on the server with the state sent to the client, become straightforward.
- It doesn't mean *all* state goes in Redux (14.03): local UI state still lives in components. It means the **shared** state has one home, not several stores that must be kept in sync.

## 2. State is read-only

> The only way to change the state is to **dispatch an action**, an object describing what happened.

- Components can't write `store.getState().value = 5` (well, they *can* in JavaScript, and it's a bug: 14.06).
- Every change is **centralised** and happens in a **strict order**, one action at a time. No race between two components writing the same field.
- Actions are plain objects, so they can be logged, serialised, stored and **replayed**. That's what the DevTools do.

## 3. Changes are made with pure reducer functions

> Reducers take the previous state and an action, and return the **next** state. They're **pure**.

- Pure = the output depends only on the inputs, and there are no side effects. Same state + same action → same next state, always.
- Consequences: reducers are trivial to **unit-test** (S15), **replay** is exact (time travel), and you can split one big reducer into smaller ones that each own a part of the state (15.08) and **compose** them.

## 2 + 3 in one picture

```text
state₀ ──reduce(a₁)──► state₁ ──reduce(a₂)──► state₂ ──reduce(a₃)──► state₃
```

Given `state₀` and the list `[a₁, a₂, a₃]`, `state₃` is fully determined. That's the Redux "promise", and every rule you'll learn exists to keep it true.

## 4. Summary

1. One store, one state tree for shared state.
2. Change only by dispatching actions.
3. Pure reducers compute the next state.
