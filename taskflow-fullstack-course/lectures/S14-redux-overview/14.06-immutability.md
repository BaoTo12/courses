# Lecture 14.06 · Immutability Revisited: Why Redux Needs New References

> **Section:** S14 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> 🔗 Official companion reading: Essentials Part 1 ("Immutability"); the Redux FAQ, "Immutable Data"
> Builds on: 04.03 (values vs references), 04.05 (immutable update patterns), 07.17 (the mutation bug in React)

---

## 1. The one-line reason

Redux, React-Redux and the DevTools decide **"did this state change?"** with **reference equality**: `prevState === nextState`, and the same check for each nested slice. That comparison takes nanoseconds, however big the state is. It only works if **every change produces a new object**, and **unchanged parts keep their old references**.

## 2. What goes wrong with mutation (verified)

A reducer that mutates and returns the same object:

```js
const store = createStore((state = { n: 0 }, action) => {
  if (action.type === 'inc') {
    state.n++;        // ❌ mutation
    return state;     // ❌ same reference
  }
  return state;
});
let fired = 0;
store.subscribe(() => fired++);
const before = store.getState();
store.dispatch({ type: 'inc' });
```

Result in the reference run: `fired === 1`, `store.getState().n === 1`, and **`before === store.getState()` is `true`**.

- The plain store **did** notify subscribers: `createStore` notifies on every dispatch without comparing.
- But anything that compares references concludes **"nothing changed"**. That includes React-Redux's `useSelector` (S17: the component won't re-render), memoised selectors (S21: stale cached results), and the DevTools (the "previous" state was modified in place, so the history is corrupted and time travel shows the wrong values).

In S15 (15.14) you'll debug exactly this: "the state didn't change in DevTools".

## 3. The patterns (a refresher from 04.05)

```js
// update a field
{ ...state, value: state.value + 1 }

// add to an array
{ ...state, items: [...state.items, newItem] }

// update one item by id: a new array, a new object for that item, the SAME objects for the rest
{ ...state, items: state.items.map((t) => (t.id === id ? { ...t, done: true } : t)) }

// remove
{ ...state, items: state.items.filter((t) => t.id !== id) }

// nested: copy every level on the path to the change
{ ...state, filters: { ...state.filters, status: 'DONE' } }
```

Watch out for methods that **mutate** in place: `push`, `pop`, `splice`, `sort`, `reverse`, `fill`, and assignment to `obj.x` or `arr[i]`. Their non-mutating equivalents are spread, `concat`, `slice`, `filter`, `map`, and ES2023's `toSorted`, `toReversed`, `toSpliced`, `with`.

## 4. "Copying everything must be slow"

Spread copies are **shallow**. `{ ...state, value: 1 }` copies the top-level property references; a 1,000-task array in `state.items` is not copied, only its reference is. The update-by-id pattern creates one new array (of references) and one new task object. That's cheap, and it's exactly what lets unchanged tasks keep their identity, so React can skip re-rendering their cards (S21 builds on this).

## 5. Where immutability is enforced

- **Hand-written Redux** (S15–S19): only by discipline and code review. You'll write reducer tests that check that the input state isn't modified (with `Object.freeze` or a deep-equal snapshot).
- **Redux Toolkit** (S20): `createSlice` uses **Immer**, so you can write `state.value++` inside a slice reducer. Immer records the "mutations" on a draft and produces a new immutable state. RTK also adds a dev-only check that **throws** if you mutate state outside a reducer.

## 6. Summary

- Redux detects change by reference: new object = changed, same reference = unchanged.
- Mutating and returning the same object makes changes invisible to React-Redux, selectors and DevTools (verified: same reference after a "change").
- Copy along the path to the change; share everything else. Shallow copies are cheap.
- RTK's Immer lets you write mutating syntax safely. Understand the manual way first.
