# Lecture 13.06 · Interceptors Internals: the Request and Response Chains

> **Section:** S13 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~35 minutes
> Every ordering claim below was verified in the reference app with Axios 1.20.

---

## 1. What an interceptor is

A function Axios runs on **every** request before it's sent, or on every response before your code receives it:

```ts
api.interceptors.request.use(onRequest, onRequestError);
api.interceptors.response.use(onFulfilled, onRejected);
```

It's the same idea as a **servlet filter** (S40), just on the client: code that wraps every call without each call knowing about it. Also like Redux **middleware** (S16), which you'll write by hand soon.

## 2. The chain is a promise chain

Conceptually, Axios builds this chain for each request:

```text
promise = Promise.resolve(config)
  .then(requestInterceptorB)      ← request interceptors: LAST registered runs FIRST
  .then(requestInterceptorA)
  .then(dispatchRequest)          ← the actual HTTP call (XHR)
  .then(responseC, responseCError) ← response interceptors: FIRST registered runs FIRST
  .then(responseD, responseDError)
  → your await / .then / .catch
```

### 🔬 Verified order

Two request interceptors (A added first, B second) and two response interceptors (C first, D second), then a successful call and a 404:

```text
request B (added 2nd)
request A (added 1st)
response C (added 1st)
response D (added 2nd)
--- then a 404:
request B (added 2nd)
request A (added 1st)
response C error
response D error
caller catch
```

Remember it as an **onion**: request interceptors are **prepended** (the last one added is the outermost on the way in), response interceptors are **appended** (the first one added sees the response first). If interceptor A adds a header that B depends on, **register B first**… or better, avoid order dependencies.

## 3. Returning and rejecting: the rules

Because it's a promise chain, the **return value** decides what happens next:

| In a… | You… | Effect |
|---|---|---|
| request interceptor | `return config` | Continue with this (possibly modified) config. **Forgetting `return`** passes `undefined` onward. Verified: the call failed with `TypeError: Cannot read properties of undefined (reading 'cancelToken')` (a confusing message pointing inside Axios), and nothing was sent. |
| request interceptor | `throw` / `return Promise.reject(err)` | The request is **never sent**. Verified: a request interceptor that throws produced `"blocked in interceptor"` in the caller's `catch`, and the mock's log showed **no** request. |
| response `onFulfilled` | `return response` | The caller receives it. |
| response `onFulfilled` | `throw` | Turns a 2xx into a failure (e.g. "200 but the body says error"). |
| response `onRejected` | `return Promise.reject(err)` | The failure continues to the caller. ✅ Normal. |
| response `onRejected` | **`return something`** | ⚠️ **Recovers**: the caller's `await` **resolves** with that value, as if the request had succeeded. Useful for retries (`return api(config)`), a bug otherwise (13.14). |

That last row is the most dangerous line in any Axios codebase. Verified in 13.14: an interceptor that logged the error and `return error` made a failed `POST` (400) **resolve**. The page then showed "Created: undefined" and navigated to `/tasks/undefined`.

## 4. Async interceptors

Interceptors may be `async` (return a promise). Axios waits for it. A request interceptor can, for example, `await` fetching a fresh CSRF token before the request goes out (S24).

Side effect worth knowing: by default, request interceptors run **asynchronously**, so the XHR isn't sent in the same tick as your call. Verified consequence in TaskFlow: in StrictMode, the effect's first request (whose controller is aborted immediately by the simulated unmount, 08.03) was cancelled **before being sent**. The mock's log shows **one** `GET /api/tasks?size=100`, not two. (The `fetch` version from S08 showed the first request as "(canceled)" in the Network tab.) Axios also offers `{ synchronous: true }` when registering a request interceptor, which you'll rarely need.

## 5. Ejecting

`use()` returns an id; `api.interceptors.request.eject(id)` removes it. Useful in tests, or for a temporary interceptor. In app code, interceptors are registered once, at module load, in `client.ts`.

## 6. What belongs in an interceptor

✅ Cross-cutting and identical for every call: correlation ids, timing/logging, auth or CSRF headers (S24), error **normalisation** (13.07), a global reaction to 401 (S24).

❌ Business logic ("if it's a task, also refresh the dashboard"), UI (showing a toast from the interceptor makes it impossible for a caller to handle an error quietly), or anything that only some calls need (pass it per call in the config instead).

## 7. Summary

- Interceptors form a promise chain around the HTTP call. Request interceptors run last-registered-first; response interceptors run first-registered-first.
- `return config` / `return response` to continue; reject to fail. **Returning from `onRejected` recovers**, which is correct for retries and a silent bug otherwise.
- A throwing request interceptor stops the request from being sent.
