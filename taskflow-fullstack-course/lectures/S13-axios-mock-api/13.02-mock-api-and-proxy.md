# Lecture 13.02 · 🛠 Running the Mock API, and the Vite Dev Proxy `/api → :3001`

> **Section:** S13 · **Type:** 🛠 Build · **Track:** ★ Core · **Time:** ~40 minutes
> **Project feature:** `mock-api/` running on port 3001; the React dev server forwards `/api/*` to it
> 📦 Provided: [`provided/mock-api/`](../../provided/mock-api/) (server, seed data, README)

---

## 1. Why a mock API

The real backend arrives in Part 3. Until then we need something that:
- speaks the **same contract** (URLs, JSON shapes, status codes, error body) as the future servlets;
- **persists** changes (create a task, reload, it's still there);
- can **fail on demand**, so you can build loading and error states.

That's the mock. When Part 3 arrives, you switch the proxy target from the mock to Tomcat (48.02), and nothing else changes.

Keep it running in its own terminal. Then, in another terminal, try it:

```bash
curl "http://localhost:3001/api/tasks?size=2&sort=dueDate,asc"
```

Verified output shape (the reference run):

```json
{ "items": [ { "id": 12, "title": "Order team T-shirts", "dueDate": "2026-09-15", … }, { "id": 21, … } ],
  "page": 0, "size": 2, "totalItems": 22, "totalPages": 11 }
```

Why 22, when the seed has 25 tasks? Because the mock's default user is **alice**, and tasks 23–25 belong to **bob**. The API only returns the caller's own tasks. That's authorization on the server (12.07), already at work.

### json-server, and why we don't use its automatic routes

json-server's famous feature is: point it at a JSON file and it creates REST routes for every top-level key: `GET /tasks`, `POST /tasks`, `GET /users`… **We deliberately don't mount those routes.** Our `db.json` contains `users` with passwords. An automatic `GET /users` would publish them, and `PATCH /tasks/5 {"ownerId": 2}` would let anyone give tasks to other users. Its responses also don't match our contract (no page envelope, no error body).

So `server.mjs` uses json-server for three things only: an **Express** server, the **lowdb** file database (`router.db`), and the request **logger**. The contract's endpoints are written by hand, in the same order your servlet **filters** and servlets will handle them in Part 2:

```text
request → [latency + failure simulation] → [who is calling? session cookie] → [JSON-only + CSRF check]
        → auth endpoints | [must be logged in] → tasks / comments / categories / stats → 404 fallback
```

The lesson generalises: **auto-generated CRUD over your database is an access-control hole** unless every field and every row is checked. OWASP calls the field part *mass assignment* (you'll defend against it in S46).

### Learning helpers

- `?_mockDelay=3000` makes one request slow (the default latency is 300 ms, so loading states are visible).
- `?_mockStatus=503` makes one request fail with that status and a proper error body.
- `npm run reset` restores the seed data.
- `npm run start:secure` (from S24) requires login and the CSRF header.

## 4. The problem: two origins

The React dev server runs on `http://localhost:5173`, the mock on `http://localhost:3001`. Different **ports** = different **origins**. A page on `:5173` calling `http://localhost:3001/api/tasks` is a **cross-origin** request, and the browser's **same-origin policy** won't let the page read the response unless the server opts in with CORS headers (13.10, 13.15). The mock doesn't opt in, on purpose (`noCors: true`), because production TaskFlow won't be cross-origin either.

## 5. The solution: the Vite dev proxy

Make the browser talk to **one** origin. The dev server forwards API calls:

```text
Browser ──GET http://localhost:5173/api/tasks──▶ Vite (5173) ──GET http://localhost:3001/api/tasks──▶ mock (3001)
        ◀──────────── 200 JSON ─────────────────        ◀──────────────── 200 JSON ─────────────────
```

The browser only sees `localhost:5173`: same origin, no CORS, and cookies set by the API belong to `localhost:5173`. The proxy is server-to-server, where the same-origin policy doesn't exist.

✍️ `frontend/vite.config.ts`:

```ts
import { fileURLToPath, URL } from 'node:url';
import react from '@vitejs/plugin-react';
import { defineConfig } from 'vite';

// https://vite.dev/config/
export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: {
      // The shared design system lives outside the frontend folder (taskflow/styles).
      '@styles': fileURLToPath(new URL('../styles', import.meta.url)),
    },
  },
  server: {
    proxy: {
      // The browser calls /api/… on the Vite origin (same origin: no CORS, cookies just work).
      // Vite forwards the request to the mock API (13.02). In Part 3: the Tomcat backend (48.02).
      '/api': 'http://localhost:3001',
    },
  },
  preview: {
    proxy: {
      '/api': 'http://localhost:3001',
    },
  },
});
```

Restart `npm run dev` (config changes need a restart), then open `http://localhost:5173/api/tasks?size=1` in the browser: JSON from the mock, served by Vite.

- The path is forwarded **unchanged** (`/api/tasks` → `http://localhost:3001/api/tasks`), because the mock already serves under `/api`. (Vite's object form, `{ target, rewrite }`, can change the path when a backend doesn't match. You'll need that in 48.02, where Tomcat serves under `/taskflow/api`.)
- `preview.proxy` does the same for `npm run preview` (the production build, 12.08).

### Production has the same shape

In production there's no Vite server. The same "one origin" idea is achieved by deploying the React build **inside** the backend's origin (S49: the WAR serves both `/app/*` and `/api/*`), or by a reverse proxy such as Nginx in front of both.

## 6. What happens when the mock is down

Stop the mock and reload the app. Verified: the request doesn't fail with a network error. **Vite's proxy answers** with `502 Bad Gateway` and an empty body, and its terminal prints `http proxy error: /api/tasks … ECONNREFUSED`. Keep that in mind for 13.08: behind a proxy, "server down" looks like a 5xx.
