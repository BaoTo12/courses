# Lecture 13.11 · 🛡 Environment Variables in Vite: `import.meta.env.VITE_*` Is Public

> **Section:** S13 · **Type:** 🛡 Defence · **Track:** ★ Core · **Time:** ~25 minutes
> **Security scope:** sensitive data exposure / secrets management (see `03-security-scope.md`)

---

## 1. How Vite env vars work

Vite reads `.env` files from the project root (`frontend/`):

| File | Loaded | Commit it? |
|---|---|---|
| `.env` | always | ✅ only non-sensitive defaults |
| `.env.local` | always, overrides `.env` | ❌ (Vite's template git-ignores `*.local`) |
| `.env.development` / `.env.production` | by mode (`dev` / `build`) | ✅ non-sensitive |
| `.env.production.local` | by mode, local override | ❌ |

Only variables prefixed **`VITE_`** are exposed to your code, as `import.meta.env.VITE_…`. Vite also provides `import.meta.env.MODE`, `DEV`, `PROD` and `BASE_URL` (12.12).

## 2. "Exposed" means "pasted into the bundle"

There is no server at runtime to ask for the value. At **build time**, Vite **replaces** every `import.meta.env.VITE_X` with the literal string. The result ships to every user's browser.

### 🔬 Experiment (verified)

`.env.local`:

```ini
VITE_ANALYTICS_KEY=pk_demo_12345
DB_PASSWORD=super-secret-db-pass
```

and one temporary line in `main.tsx`:

```ts
console.log('env probe', import.meta.env.VITE_ANALYTICS_KEY, import.meta.env.DB_PASSWORD);
```

After `npm run build`, the minified bundle contained:

```js
console.log(`env probe`,`pk_demo_12345`,void 0)
```

- The `VITE_` value is **in the file**, readable by anyone who opens DevTools → Sources, or runs `curl` on the JS.
- `DB_PASSWORD` became `void 0` (`undefined`): **not** exposed, thanks to the prefix rule. That's the safety net: a variable without the prefix can't leak by accident.

(Remove the probe line and `.env.local` after trying this.)

## 3. The rule

> **Anything the browser needs is public. Secrets never go into a frontend build**, whatever the variable is called, however the bundle is minified or obfuscated.

| ✅ OK as `VITE_*` | ❌ Never in the frontend |
|---|---|
| API base URL (`VITE_API_BASE_URL`) | Database passwords, JDBC URLs with credentials |
| Public keys meant for browsers (a Maps key restricted to your domain, a publishable payment key) | Private/secret API keys (payment *secret* keys, cloud credentials) |
| Feature flags that aren't sensitive | Signing keys, JWT secrets, encryption keys |
| App version, build time | "Admin passwords" for a hidden page |

If the browser needs to call a service that requires a secret, the **backend** holds the secret and calls the service on the user's behalf (a proxy endpoint). The user gets the result, never the key.

## 4. Related leaks to know

- **Source maps** (`build.sourcemap: true`) publish your original source code, including comments. Fine for open-source; decide deliberately for company code. Vite's default is `false` for builds.
- **Committed `.env` files**: once a secret is pushed to git, rotating it is the only fix. Deleting the file doesn't remove it from history.
- **Hard-coded URLs to internal systems** ("staging-db.internal:5432") tell attackers what to look for.
- **Comments** are stripped by minification, but strings aren't.

## 5. TaskFlow

The only variable is `VITE_API_BASE_URL` (optional, default `'/api'`). It's declared in `src/vite-env.d.ts` (13.04), with a comment reminding readers it's public.

The Java backend (Part 2) gets its secrets, such as the password of the least-privilege MySQL user created in 28.07, from **server-side** configuration (environment variables or Tomcat's configuration files, 28.03) that never reaches the browser.

## 6. Summary

- `VITE_*` variables are string-replaced into the bundle at build time. They're **public**.
- Non-prefixed variables aren't exposed: the prefix is a safety net, not a vault.
- Secrets live on the server, which calls third parties on the user's behalf.
