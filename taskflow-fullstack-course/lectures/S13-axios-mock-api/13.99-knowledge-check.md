## E. Implementation

17. Write a **retry-once** response interceptor for TaskFlow's `api`:
    - retry only **idempotent** methods (GET, HEAD, PUT, DELETE), only on **transient** failures (no response, or 502/503/504), never cancelled requests, at most once, after 300 ms;
    - it must see the **raw** `AxiosError` (think about registration order with the normalising interceptor);
    - explain why POST is excluded.

    Test it with `?_mockStatus=503`, `?_mockDelay=` plus a short timeout, a 404, and a POST.

<details>
<summary><b>Answers</b></summary>

1. **Safe:** GET, HEAD (and OPTIONS). **Idempotent:** those plus PUT and DELETE (and PATCH when it sets values). (a) A GET must never change data. Links, prefetchers and `<img src>` on other sites trigger GETs, so a GET delete link can be triggered by anyone (TaskFlow Admin deletes via POST, S37). (b) Only idempotent requests can be retried blindly. A retried POST may create a duplicate, because the first attempt may have succeeded with only the response lost.

2. Missing CSRF header → **403** `CSRF_TOKEN_INVALID` (verified in secure mode; the check runs before authentication, even for login). Anonymous `GET /api/tasks` → **401** `UNAUTHENTICATED`. 401 = "who are you?", 403 = "not allowed".

3. (a) **Same origin**: no CORS, no preflights, and cookies (the session in S24) just work. (b) **It matches production**, where the app and API share an origin (S49). Also: the API URL lives in one place (the proxy target), which is what 48.02 changes.

4. Request: **last registered runs first** (B, then A). Response: **first registered runs first** (C, then D). Verified with a success and a 404 (13.06 §2).

5. `VITE_*` values are **string-replaced into the JavaScript** at build time (verified: `pk_demo_12345` appeared literally in the bundle). Minification doesn't hide strings. Anyone can read it in DevTools or with curl, and a secret key would let them act as your company. The key must be rotated, and secrets must live on the server.

6. `fetch` **resolves** with `response.ok === false` and `status 404`. Axios **rejects** with `AxiosError` (`ERR_BAD_REQUEST`, `response.status 404`).

7. `data` is `[]`. The rejection handler **returned a value**, which recovers the chain: the 404 became a "success". The caller can't tell anything went wrong.

8. (a) No preflight: a simple GET (it's sent; the response is just hidden from the script). (b) **Preflight**: our instance adds `X-Request-Id`, a custom header. (c) **Preflight**: `Content-Type: application/json` isn't a "simple" content type. (d) **Preflight**: DELETE isn't a simple method.

9. **No.** `get<Task>` is an assertion, with no runtime check (use `unknown` + `isTask`). `isAxiosError<ApiError>` checks only that `e` is an AxiosError, not the body. `e.response!` crashes on network errors and timeouts, and `data.message` is `undefined` for a proxy's empty 502. Use `toApiRequestError` (it validates with `isApiError`).

10. Timeout (`code: 'ECONNABORTED'`), cancellation (`CanceledError`, `ERR_CANCELED`), connection refused / DNS / offline (`ERR_NETWORK`), CORS block (`ERR_NETWORK`, identical to the script). Tell them apart with `error.code` for the first two, and the **DevTools console + Network tab** for the rest (the browser hides the reason from scripts on purpose).

11. The browser reached the **Vite proxy**, which couldn't reach the mock (`ECONNREFUSED` in the Vite terminal) and answered **502** itself, with an empty body. Behind any proxy or load balancer, "backend down" looks like a 5xx.

12. The interceptor **doesn't `return config`**. `undefined` is passed to Axios's dispatch step, which crashes reading `config.cancelToken` before sending anything (verified).

13. `remove()` dispatches `taskRemoved` (an **urgent** update), and `navigate()` is wrapped in `startTransition` by React Router 8 (a **low-priority** update). React renders the urgent one first: still on `/tasks/26`, but the task is gone, so the page renders the 404. Then the navigation commits. Fix: render nothing while `isDeleting` (13.13 §5).

14. It isolates the transport: typed functions with validated results, one normalised error type, and interceptors in one place. In Part 3 only the base URL/proxy changes. RTK Query (S22) can replace the internals without touching components. It's also easy to fake in tests.

15. The hook can't know the right UX (a toast, an inline form error, a silent retry, or nothing for a cancelled request). Swallowing there would make callers believe the save succeeded (13.14). The page, which knows the context, decides.

16. **Pessimistic**: the UI changes only after the server accepts. During the 300 ms, the old state stays (verified: the button still said "Mark done" 100 ms after the click). **Optimistic** would update immediately, then roll back and notify on failure. It needs a snapshot of the previous state, conflict handling, and care with concurrent edits (RTK Query's `onQueryStarted` + `patchResult.undo()`, 23.04).

17. Register it **before** the normalising interceptor (response interceptors run first-registered-first, so it sees the raw `AxiosError`). In `client.ts`, put it right after `axios.create(…)`:

    ```ts
    declare module 'axios' {
      interface InternalAxiosRequestConfig {
        metadata?: { startedAt: number };
        /** Set by the retry interceptor: at most one retry per request. */
        retried?: boolean;
      }
    }

    const IDEMPOTENT = ['get', 'head', 'put', 'delete'];

    api.interceptors.response.use(undefined, async (error: unknown) => {
      if (!axios.isAxiosError(error) || !error.config || axios.isCancel(error)) return Promise.reject(error);
      const config = error.config;
      const transient = error.response === undefined || [502, 503, 504].includes(error.response.status);
      if (transient && IDEMPOTENT.includes(config.method ?? 'get') && !config.retried) {
        config.retried = true;
        await new Promise((resolve) => setTimeout(resolve, 300));
        return api(config); // recover: the caller receives the second attempt's result
      }
      return Promise.reject(error);
    });

    // …then the existing timing/normalising interceptor.
    ```

    Verified with a throwaway instance built the same way (attempts counted by a request interceptor):

    | Request | Attempts | Final error |
    |---|---|---|
    | `GET ?_mockStatus=503` | 2 | `http 503` |
    | `GET ?_mockDelay=800`, timeout 200 ms | 2 | `timeout` |
    | `GET /tasks/999` | 1 | `http 404` (4xx isn't retried) |
    | `POST ?_mockStatus=503` | 1 | `http 503` (POST isn't retried) |

    The retry passes through the **request** interceptors again, so it gets a new `X-Request-Id` and start time. That's arguably correct: it's a new HTTP request. Some teams keep the id and add an attempt counter instead. **POST is excluded** because the first attempt may have been processed by the server even though the response was lost (a timeout or a 502 from a proxy after the backend committed). Retrying would create a duplicate task. Making POSTs retryable needs an **idempotency key** the server deduplicates on.
