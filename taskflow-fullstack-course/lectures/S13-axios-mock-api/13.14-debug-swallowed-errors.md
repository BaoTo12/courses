# Lecture 13.14 · 🐞 Debug: the Interceptor Swallows Errors, and the Page Thinks the Save Succeeded

> **Section:** S13 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~25 minutes
> Reproduced in the reference app with a throwaway Axios instance.

---

## Symptom

A teammate adds "better error logging" to the client:

```ts
api.interceptors.response.use(
  (response) => response,
  (error) => {
    console.warn('[api] request failed', error.message);
    return error; // "we've handled it"
  },
);
```

and simplifies an endpoint function:

```ts
export async function createTask(request: CreateTaskRequest): Promise<Task> {
  const { data } = await api.post<Task>('/tasks', request);
  return data;
}
```

QA reports: *"Creating a task with an empty title shows a green toast **'Created: undefined'** and opens a page at **`/tasks/undefined`**, which says 'Page not found'. Nothing was saved."*

Verified with a throwaway instance posting `{ title: '' }` to the mock:

```js
{ resolved: true, resIsAxiosError: true, createdIsUndefined: true,
  toastWouldSay: 'Created: undefined', navigateTo: '/tasks/undefined' }
```

## Investigation checklist

1. The server answered `400`. Where did the failure go? Look at what the response error handler **returns**. (13.06 §3)
2. What does `await api.post(…)` resolve with in that case?
3. `api.post<Task>` promised `data: Task`. Why didn't TypeScript complain? (13.05 §2)
4. Why did the page show a success toast and navigate?

## Explanation

1. **Returning from `onRejected` recovers the promise chain.** A value returned from a rejection handler becomes the **fulfilment** value of the next step. So `await api.post(…)` **resolved**, with the `AxiosError` object itself as the "response".
2. `const { data } = <an AxiosError>` → `data` is `undefined` (errors have `response.data`, not `data`).
3. `api.post<Task>` is an **assertion**. TypeScript trusted it; nothing checked at runtime. `createTask` returned `undefined` typed as `Task`.
4. `NewTaskPage` did exactly what it should do with a successful `Task`: toast `created.title`, navigate to `created.id`.

Two defects combined:
- the interceptor **converted a failure into a success**;
- the endpoint **didn't validate** the response, so the bad value travelled into the UI.

## Fix

1. The interceptor must **reject**:
   ```ts
   (error: unknown) => {
     console.warn('[api] request failed', error);
     return Promise.reject(toApiRequestError(error)); // or: throw toApiRequestError(error);
   }
   ```
2. Endpoints request `unknown` and **validate** (13.05):
   ```ts
   const { data } = await api.post<unknown>('/tasks', request);
   return expectTask(data); // throws ApiRequestError('unexpected') for anything that isn't a Task
   ```

With TaskFlow's real code, **either fix alone** would have prevented the green toast: the reject makes the page's `catch` run; the validation throws on `undefined`. That's defence in depth applied to your own code.

## When is "return a value from `onRejected`" correct?

When you truly recover, and the value is **what the caller asked for**:

```ts
async (error) => {
  const config = error.config;
  if (isTransient(error) && config && !config._retried && isIdempotent(config.method)) {
    config._retried = true;
    return api(config); // retry: the caller receives the real response of the second attempt
  }
  return Promise.reject(toApiRequestError(error));
}
```

(That's the knowledge-check implementation exercise.)

## Lessons

- In a promise chain, **`return` = success, `throw`/reject = failure**, in handlers too.
- "Handling" an error means deciding what the **user** sees. A logging layer must pass the failure on.
- A type argument on `get<T>`/`post<T>` is a promise you make to the compiler, not a check.

## Related traps

- `async` functions that `catch` and `console.error` without re-throwing: same bug, one layer up (13.13 §7).
- `.catch(() => {})` "to silence an unhandled rejection warning": the warning was right.
- `try { await save(); } finally { toast('Saved!'); }`: `finally` runs on failure too.
