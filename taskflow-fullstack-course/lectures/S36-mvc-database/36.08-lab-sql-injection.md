# Lecture 36.08 · 🔓 SQL Injection: Why Concatenated SQL Is Broken

> **Section:** S36 · **Type:** 🔓 Attack Lab (conceptual) · **Track:** ★ Core · **Time:** ~20 minutes
> Verified: `S36SqlInjectionLabTest` pins the behaviour described here against the real schema, and shows the parameterised version rejecting it.
> The fix is 36.09. This lecture explains the flaw. It isn't an exploitation walkthrough.

---

## 1. The vulnerable pattern

```java
String sql = "SELECT … FROM tasks WHERE title LIKE '%" + q + "%' ORDER BY id";   // ❌ input becomes part of the SQL text
statement.executeQuery(sql);
```

The database receives **one string** and parses it. It can't tell which characters the developer wrote and which came from the user. If the input contains SQL syntax (a quote, a keyword, a comment marker), that syntax is parsed as part of the query.

## 2. What that allows, in general

`S36SqlInjectionLabTest` confirms each of these against TaskFlow's real database:

| Consequence | Why it's possible |
|---|---|
| **The filter is bypassed:** every row is returned | the input closes the string literal and adds a condition that is always true |
| **Other tables are read**, including `users.password_hash` | the input appends a second `SELECT` whose rows are merged into the result |
| **Error messages help the attacker** | a malformed query returns a database error that reveals structure (column counts, names) |
| Some damage is **limited by the environment** | Connector/J rejects several statements in one call by default (`allowMultiQueries=false`), and the DB user's grants limit writes (36.10) |

The last row isn't a defence you can rely on: reading data (the second row) needs neither.

## 3. Where it hides in real code

- search boxes and filters (`LIKE '%…%'`);
- `ORDER BY` built from a "sort" parameter: it can't be a `?` parameter, so developers concatenate it (36.09 §3);
- `IN (…)` lists built by joining ids;
- "internal" values (cookies, headers, hidden fields): anything from the request is user input;
- stored data reused in a later query (second-order injection).

## 4. Recognising it in review

Any SQL string built with `+`, `String.format`, `StringBuilder.append` or a template **from a variable** is a finding, unless the variable comes from a constant in your own code (like TaskFlow's `TaskSort` allow-list). `Statement.executeQuery(sql)` with a non-constant `sql` is the smell to grep for.

## Lesson

The flaw isn't a missing filter for "bad characters": it's that **data and code travel in the same string**. The fix separates them (36.09).
