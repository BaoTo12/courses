# Lecture 36.02 · Layers: Controller → Service → DAO → Database; Why the Servlet Never Touches the Database

> **Section:** S36 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes

---

## 1. The call chain for "toggle task 7"

```text
POST /taskflow/tasks/toggle  id=7
  TaskToggleServlet.doPost          Params.positiveId("7") → 7; 400 if invalid
    TaskService.toggle(7)           rule: DONE ↔ TODO; false if no such task
      TaskDao.findById(7)           SELECT … FROM tasks WHERE id = ?
      TaskDao.updateStatus(7, DONE) UPDATE tasks SET status = ? WHERE id = ?
        (provided data layer)       borrows a pooled database connection
          MySQL
  ← 302 Location: /taskflow/tasks   (or 404 if toggle returned false)
```

## 2. Each layer's single job

| Layer | Knows | Doesn't know | Changes when… |
|---|---|---|---|
| Controller | HTTP: parameters, status codes, attributes, views | SQL, the rules | URLs, forms, pages change |
| Service | the use cases and rules | HTTP, SQL | the business changes |
| DAO | queries, tables | HTTP, the rules | the schema or database changes |
| Database | storage, constraints, transactions | everything above | — |

A layer calls only the one **below** it. The dependency arrows point down, never up: a DAO never imports `javax.servlet`.

## 3. Why the servlet never touches the database

| If the servlet ran SQL… | Consequence |
|---|---|
| the JSON API (S46) needs the same query | copy-paste → two versions drift apart |
| you want to test "toggle" | you need a running Tomcat **and** a database |
| a column is renamed | you search every servlet |
| a developer builds SQL from `request.getParameter` | SQL injection is one keystroke away (36.08) |

With DAOs, all queries are in a handful of classes, reviewed together, each following the same rule: parameters only (36.09).

## 4. What about "Repository"?

A DAO (Data Access Object) is organised around **tables** and SQL operations (`TaskDao.updateStatus`). A Repository (Domain-Driven Design, Spring Data) is organised around **domain collections** ("all overdue tasks of user X"). In small apps they're the same class with a different name. TaskFlow uses "DAO" because that's what you'll see in most servlet codebases.

## 5. Is a service layer always needed?

For a pure "read a row, show it" page, the service is a pass-through (`TaskService.find` just calls `tasks.find`). Keep it anyway when:
- there are rules (toggle, comments need a task, S37's validation, S42's ownership checks);
- several DAOs must be combined (`details()`);
- transactions will span several statements (S45).

Consistency matters too: controllers **always** talk to services, so nobody wonders where the rule is.

## ✅ Recap

Controller → Service → DAO → database, each knowing only its own concern. SQL lives only in DAOs, which makes it reviewable, reusable and injection-safe.
