# Lecture 36.07 · Front Controller vs a Servlet per Use Case; How Spring MVC Grew from This

> **Section:** S36 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes

---

## 1. What TaskFlow does: one servlet per use case

```text
/tasks          → TaskListServlet
/tasks/view     → TaskViewServlet
/tasks/new      → TaskCreateServlet
/tasks/toggle   → TaskToggleServlet
/tasks/delete   → TaskDeleteServlet
/tasks/comment  → TaskCommentServlet
```

Simple, explicit, and the container does the routing (30.11). The cost grows with the app: every servlet repeats "fetch the service in `init()`, parse the id, 400/404, forward to `/WEB-INF/views/…`".

## 2. The Front Controller pattern

**One** servlet receives everything and dispatches to small handler objects:

```java
@WebServlet("/app/*")
public class FrontController extends HttpServlet {
  private final Map<String, Action> actions = Map.of(
      "GET /tasks", new ListTasksAction(),
      "GET /tasks/view", new ViewTaskAction(),
      "POST /tasks/toggle", new ToggleTaskAction());

  @Override
  protected void service(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
    Action action = actions.get(req.getMethod() + " " + req.getPathInfo());
    if (action == null) { resp.sendError(404); return; }
    String view = action.execute(req, resp);                 // returns "tasks/list" or "redirect:/tasks"
    if (view.startsWith("redirect:")) resp.sendRedirect(req.getContextPath() + view.substring(9));
    else req.getRequestDispatcher("/WEB-INF/views/" + view + ".jsp").forward(req, resp);
  }
}
```

Now the repeated parts (error handling, view resolution, redirects, later CSRF checks, S42) are written **once**.

## 3. That's how frameworks started

| Era | Framework | The front controller |
|---|---|---|
| 2000 | Apache Struts 1 | `ActionServlet` + `Action` classes + `struts-config.xml` |
| 2003+ | **Spring MVC** | `DispatcherServlet` + `@Controller` methods |
| today | Spring Boot | the same `DispatcherServlet`, auto-configured |

A Spring MVC controller is our pattern with the plumbing generated from annotations:

```java
@Controller
public class TaskController {
  private final TaskService service;                            // injected (our listener's job)
  @GetMapping("/tasks/view")
  public String view(@RequestParam long id, Model model) {      // parsing + 400 done by Spring
    model.addAttribute("details", service.details(id).orElseThrow(NotFoundException::new));  // request attributes
    return "tasks/view";                                        // → /WEB-INF/views/tasks/view.jsp
  }
}
```

Everything you've learned (request attributes, forward vs redirect, views under `WEB-INF`, a service layer) is what `DispatcherServlet` does underneath. When a Spring app misbehaves, this is the level you debug at.

## 4. Which to use

| Situation | Choice |
|---|---|
| learning, small apps, TaskFlow | a servlet per use case: nothing hidden |
| a growing app without a framework | a front controller once the repetition hurts |
| a real product | a framework (Spring MVC), and knowing what it does for you |

## ✅ Recap

A front controller centralises routing and cross-cutting steps. Spring MVC's `DispatcherServlet` is exactly that, with annotations instead of a map.
