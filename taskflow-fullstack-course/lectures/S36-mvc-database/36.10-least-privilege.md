# Lecture 36.10 · 🛡 Defence in Depth: the Least-Privilege Database User

> **Section:** S36 · **Type:** 🛡 Defend · **Track:** ★ Core · **Time:** ~20 minutes
> Verified: `S36LeastPrivilegeTest` (as `taskflow_app` on the real MySQL: schema changes and audit edits are denied with error 1142; `mysql.user` is out of reach; the app's own tables, password hashes included, are readable)

---

## 1. What TaskFlow's app user may do (`db/04-grants.sql`, 28.07)

| Table | Rights |
|---|---|
| `users`, `categories`, `tasks`, `comments` | `SELECT, INSERT, UPDATE, DELETE` |
| `audit_events` | `SELECT, INSERT` only (append-only) |
| schema (`CREATE`, `DROP`, `ALTER`), other databases, `GRANT` | none |

The application **connects as this user**, never as `root`. Schema changes are run by a separate migration user (or an admin) at deploy time.

## 2. What it limits, as tested

| If an attacker (or a bug) runs… | Result |
|---|---|
| `DROP TABLE comments`, `CREATE TABLE …`, `ALTER TABLE …` | ❌ error **1142**: "command denied to user 'taskflow_app'" |
| `UPDATE audit_events …` / `DELETE FROM audit_events` | ❌ 1142: the log of what happened can't be rewritten |
| `SELECT … FROM mysql.user` | ❌ 1142: other databases are invisible |
| `SELECT password_hash FROM users` | ✅ **allowed**: the app needs `users` for login |

## 3. What it doesn't limit

The last row is the lesson. Least privilege limits **the blast radius**. It doesn't make an injection harmless: the app legitimately reads and writes its own data, so anything injected can too. That's why:

- **36.09 is the defence.** Least privilege is the second layer.
- Passwords are stored as **bcrypt** hashes (28.07): a leaked hash still has to be cracked, slowly.
- Further hardening, if you need it: column-level grants (`GRANT SELECT (id, username, display_name, role) ON users …` for a reporting user), separate users per component (the JSON API vs the admin portal), and views instead of tables.

## 4. Why "defence in depth"

Every control fails sometimes: a developer concatenates one query, a library has a bug. Layers mean one failure isn't a catastrophe:

```text
input validation (shape)  →  parameterised SQL  →  least-privilege DB user  →  hashed secrets  →  audit log (append-only)
```

## ✅ Recap

Run the app as a user that can only do what the app needs. It turns "drop the database" into "denied", but not "read the data": parameterised queries remain the real defence.
