# Lecture 36.14 · 🐞 Debug: A Test Passes Alone and Fails in the Suite (a Real One from This Course)

> **Section:** S36 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~15 minutes
> This happened while building S36: `S36MvcDatabaseTest` failed on the first full run.

---

## 1. Symptom

One test sent several "hostile" searches and expected `No tasks.` for each of them, including a search for `%`. On the full `mvn package`, it failed on `%`: the page listed a task.

## 2. Investigate

- The failing input was `%`, and the page showed "Coverage at 100% …".
- That title isn't in the seed. It was created by **another test in the same class**, `likeWildcardsInTheSearchAreLiteral`, which JUnit happened to run first.
- So the search was **correct**: `%` is escaped (36.09 §2), and it found the one title that really contains a `%`.

## 3. Cause

All test classes share one MySQL (`TestDatabase`, 36.03), and JUnit doesn't guarantee test order. A test that asserts "no rows match X" depends on **no other test** ever creating a matching row.

## 4. Fix, and the rules for shared-database tests

The `%` case was removed from the "no results" list: the literal-`%` test already covers it, positively.

| Rule | Why |
|---|---|
| tests that **change** data create their **own** rows (unique titles: `System.nanoTime()`) | no test depends on another's leftovers (S31 already did this) |
| assert on rows **you** created, or on seed rows nobody changes | stable whatever the order |
| avoid "the whole table has exactly N rows" / "nothing matches" unless the input can't match anything created | other tests add rows |
| alternatives: a fresh schema per test class, transactions rolled back after each test, or `@TestMethodOrder` | isolation has costs (speed, complexity): choose deliberately |

## ✅ Takeaway

A test that passes alone and fails in the suite depends on shared state. Find what else wrote to it. Here the code was right, and the test's assumption was wrong.
