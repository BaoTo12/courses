# Lecture 36.06 · The View-Model Question: Entities or View DTOs in the JSP?

> **Section:** S36 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes

---

## 1. Two options

| | Pass entities (`Task`) | Pass view models (`TaskDetails`, `CommentDetails`) |
|---|---|---|
| What | the domain object as loaded | an object shaped for **one page** |
| TaskFlow | the list: `List<Task>` | the details page: task + category + owner + comments |
| + | no extra classes | exactly what the page needs; nested data ready (`${details.owner.displayName}`); nothing more |
| − | the view may need data the entity doesn't carry (the owner's **name**, not `ownerId`) → lookups in the view (impossible now) or in the controller (clutter) | one more class per complex page |

## 2. The danger of passing too much

An entity passed to a view carries **every** field, including ones the page must never show. If `User` carried `passwordHash`, a careless `<c:out value="${user}"/>` or a debug page (34.16) could print it, and in S46's JSON API, Jackson serialises every getter unless told otherwise. TaskFlow's `User` has **no** hash field, and `UserDao` never selects the column: what isn't loaded can't leak.

## 3. TaskFlow's rule

- Simple lists of one kind of thing → entities (`List<Task>`, `List<Category>`).
- Pages combining several things, or needing derived values → a view model assembled by the **service** (`TaskDetails`).
- Never an object holding secrets, whatever its purpose.

## 4. Where view models are built

In the **service** (as `TaskService.details` does) when the combination is a use case ("show a task with its context"), which the JSON API will reuse. In the controller when it's purely presentational (the `pageTitle`).

## ✅ Recap

Entities for simple pages; view models when a page needs a combined or derived shape. Either way, never hand a view an object with data it must not show.
