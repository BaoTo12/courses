# Lecture 32.02 · Architecture Before/After: the Servlet Prepares, the JSP Renders

```text
BEFORE (S31)                                   AFTER (S32 →)
┌───────────────────────────────┐              ┌──────────────────────────┐        ┌──────────────────────────┐
│ TaskListServlet               │              │ TaskListServlet          │        │ /WEB-INF/views/tasks/    │
│  - read & validate parameters │              │  (CONTROLLER)            │forward │        list.jsp          │
│  - load tasks                 │     ──►      │  - read & validate params│───────►│  (VIEW)                  │

```

| Responsibility | Controller (servlet) | View (JSP) |
|---|---|---|
| HTTP: method, parameters, status codes, redirects | ✅ | ❌ |
| Validation, loading, authorisation | ✅ | ❌ |
| Deciding **which** page, or a redirect or an error | ✅ | ❌ |
| HTML, CSS classes, text | ❌ | ✅ |
| Escaping output | ❌ | ✅ (S35: automatic with `<c:out>`) |

The rule from now on: **a servlet never writes HTML again**, and **a JSP never decides anything important** (no database calls, no redirects, no permission checks). The knowledge check asks why. Short answer: when HTML is in two places, nobody knows where to change it. When logic is in the view, it isn't tested, and it runs **after** the response may be committed (30.18).

This is **MVC** (Model–View–Controller) in its classic servlet form ("Model 2"). S36 completes it with a service and DAO layer behind the controller. Spring MVC's `@Controller` + a template engine is the same idea, generalised.
