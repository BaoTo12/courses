# Lecture 32.10 · 🛠 Link the Shared CSS; Static Resources and the `default` Servlet

> **Section:** S32 · **Type:** 🛠 Build · **Track:** ★ Core · **Time:** ~20 minutes
> Verified: `S30ServletsTest.webInfIsNeverServed` (`/taskflow/static/css/app.css` → 200), `S32JspTest` (the JSP links `/taskflow/static/css/app.css`)

## 1. Who serves `app.css`?

```text
GET /taskflow/static/css/app.css
  → Context /taskflow → mapping: no servlet matches /static/css/app.css exactly or by prefix
  → the DEFAULT servlet ("/", from conf/web.xml) → reads webapp/static/css/app.css → 200 text/css
```

Tomcat's `DefaultServlet` serves every file in the WAR's public root (28.04), with `Content-Type` from the extension, `ETag`/`Last-Modified` for caching, and range requests. Nothing to configure.

## 2. Linking it from a JSP, correctly

```jsp
<link rel="stylesheet" href="<%= request.getContextPath() %>/static/css/app.css">
```

- **Absolute with the context path**: it works from `/taskflow/tasks` and from `/taskflow/tasks/view` (32.15), and under any context path (28.10).
- In S34 the same line becomes `href="${pageContext.request.contextPath}/static/css/app.css"`, and in S35, `<c:url value="/static/css/app.css"/>`.

## 3. The shared design system on the admin portal

The JSP uses the same classes as TaskFlow Web: `page`, `page__header`, `page__nav-link`, `btn btn--sm btn--secondary`, `badge`, `form-field`. The admin portal looks like the same product for free, because `npm run styles:jsp` compiles the same SCSS (28.08).

## 4. Don't route static files through servlets

- A servlet mapped to `/*` or `/` would **swallow** these requests (30.11), and the CSS stops loading.
- Filters mapped to `/*` (S39) **do** see static requests: authentication filters must let `/static/**` through, or the login page is unstyled.
