# Lecture 32.07 · Why JSPs Live in `WEB-INF/views`

> **Section:** S32 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes
> Verified: `S32JspTest.jspsUnderWebInfCannotBeRequestedDirectly` (`GET /taskflow/WEB-INF/views/tasks/list.jsp` → 404)

---

## If the JSP were at the web root

`src/main/webapp/tasks/list.jsp` could be requested **directly**: `GET /taskflow/tasks/list.jsp`. What happens then?

1. **No controller ran.** `request.getAttribute("tasks")` is `null`, so `tasks.isEmpty()` → `NullPointerException` → a 500 with a stack trace (information disclosure, 31.16).
2. **The controller's checks are skipped.** From S41, the controller verifies the login and the permissions. A direct request to the view bypasses that. With a JSP that loads its own data (the anti-pattern of S33), that's a real data leak.
3. The view's URLs become part of the public API, and users bookmark `list.jsp`.

## Under `WEB-INF`

- The container **refuses** direct requests to `/WEB-INF/**` with 404 (28.04). The test confirms it for our JSP.
- A **forward** is server-internal, so it can reach them: `getRequestDispatcher("/WEB-INF/views/tasks/list.jsp")`.
- So **the only way to a view is through its controller**. Every page request passes the controller's validation and (from S41) the security checks.

## Convention

```text
WEB-INF/views/
├── tasks/   list.jsp  view.jsp  form.jsp (S37)
├── admin/   users.jsp (S42)  audit.jsp (S45)
├── auth/    login.jsp (S41)
└── error/   404.jsp  500.jsp (S43)
```

One folder per feature, the same names as the controllers' URLs. A JSP at the web root is a mistake from now on.
