# Lecture 32.16 · 🐞 Debug: `ClassNotFoundException: com.sun.el.ExpressionFactoryImpl` (a Real One from This Course)

> **Section:** S32 · **Type:** 🐞 Debug · **Track:** ＋ Extended · **Time:** ~15 minutes
> This happened while building S32's reference project; the fix is in the pom.

*Extended track: outline.*

---

**Symptom.** The moment the tests started rendering JSPs (embedded Tomcat + Jasper), every page answered **500**:

```text
SEVERE: Servlet.service() for servlet [com.taskflow.web.tasks.TaskListServlet] … threw exception
  [org.apache.jasper.JasperException: Unable to compile class for JSP] with root cause
java.lang.ClassNotFoundException: com.sun.el.ExpressionFactoryImpl
```

**Investigation.**
- `com.sun.el…` is **GlassFish's** EL implementation. Tomcat's is `org.apache.el.ExpressionFactoryImpl`. Why would anything ask for GlassFish's?
- `javax.el.ExpressionFactory.newInstance()` finds an implementation through `META-INF/services`, and **falls back to a hard-coded default**. In the `javax.el:javax.el-api:3.0.0` **API jar**, that default is `com.sun.el.ExpressionFactoryImpl`.
- The S28 pom declared `javax.el-api` as `provided`. `provided` jars are on the **test** classpath, and it came **before** Tomcat's own EL jar, so its `ExpressionFactory` class won, with the wrong default.

**Fix.** Remove `javax.el-api` from the pom. Our code never imports `javax.el`, and Tomcat (the real one, and the embedded one in tests) ships the API **and** the implementation together. All 20 tests went green.

**Lessons.**
1. Declare only APIs you **compile against**. "Provided, just in case" jars still land on the test classpath.
2. When one class loader has two copies of an API, the **first on the classpath** wins. `mvn dependency:tree` (28.05) and the classpath order explain most `ClassNotFoundException`s of "impossible" classes.
3. `com.sun.*` or `org.glassfish.*` in a Tomcat stack trace means an API jar from another container crept in.
