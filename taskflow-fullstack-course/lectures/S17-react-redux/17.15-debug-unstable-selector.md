# Lecture 17.15 · 🐞 Debug: `useSelector(state => state.tasks.filter(…))` Re-Renders on *Every* Action

> **Section:** S17 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~20 minutes
> Reproduced in the reference app (numbers and warning text from 17.14's measurements).

---

## Symptom

A teammate writes a "due soon" sidebar:

```tsx
function DueSoonSidebar() {
  const dueSoon = useAppSelector((state) =>
    state.tasks.items.filter((t) => t.dueDate !== null && t.dueDate <= '2026-10-05' && t.status !== 'DONE'),
  );
  return <ul>{dueSoon.map((t) => <li key={t.id}>{t.title}</li>)}</ul>;
}
```

It works, but the Profiler shows the sidebar re-rendering when a **toast** appears, when the **sort preference** changes: on every action in the app. And the console shows (React-Redux 9, development):

```text
Selector unknown returned a different result when called with the same parameters. This can lead to unnecessary rerenders.
Selectors that return a new reference (such as an object or an array) should be memoized: https://redux.js.org/usage/deriving-data-selectors#optimizing-selectors-with-memoization
```

## Investigation checklist

1. When does `useSelector` re-run the selector? (17.04)
2. How does it decide whether to re-render?
3. What does `Array.prototype.filter` return when **nothing** matches differently?
4. What did React-Redux's "stability check" do to produce that warning?

## Explanation

- After every dispatch, `useSelector` re-runs the selector and compares the result with the previous one using `===`.
- `filter` **always** returns a **new array**, even when its contents are identical. So `newResult === previousResult` is always `false`, and the component re-renders after every action. Measured with the badge in 17.14: 2 renders (StrictMode) for each unrelated action, versus 0 with a number-returning selector.
- In development, React-Redux calls a selector **twice** with the same state the first time it runs. If the two results aren't `===`, the result is "unstable", and it logs the warning. The selector is anonymous, hence "Selector unknown".
- Note the difference from 17.02: raw `useSyncExternalStore` with the same selector **crashes** (infinite loop). React-Redux survives it, but the cost is a re-render after every action. With many such components, that's a slow app.

## Fixes, from simplest to most general

1. **Return a primitive** if that's all the component needs (a count, a boolean).
2. **Select the stable input, derive in the component**:
   ```tsx
   const items = useAppSelector(selectTasks);          // same array until the tasks change
   const dueSoon = items.filter(isDueSoon);           // recomputed only when this component renders
   ```
   Now the component re-renders only when **tasks** change. For a small list, that's the pragmatic fix.
3. **Memoise the selector** with `createSelector` (S21): it recomputes only when `state.tasks.items` changes, and otherwise returns the **same** array reference. That's the proper fix for derived arrays used in many places.
4. `useAppSelector(selector, shallowEqual)` compares arrays element by element. It helps when the elements themselves are stable, but it's O(n) on every action. Prefer 2 or 3.

(Also note the hard-coded date: "today" belongs in a parameter or a selector argument, not in a literal: 05.12.)

## Lessons

- `filter`, `map`, `slice`, spread and object literals in a selector = a new reference = a re-render after every action.
- Read React-Redux's development warnings: they point at exactly this.
- Derived data: select stable inputs and derive, or memoise (S21).
