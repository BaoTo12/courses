# Lecture 17.01 · Integrating Redux with Any UI: Subscribe → Read State → Re-Render

> **Section:** S17 · R4: UI and React
> **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes
> 🔗 Official companion reading: Redux **Fundamentals, Part 5** ("UI and React": integrating Redux with a UI)

---

## 1. The same three steps for every UI

You already did this in 14.10, with plain DOM code:

```js
render();                  // 1. read state and draw the initial UI
store.subscribe(render);   // 2. after every dispatch…
                           // 3. …read state again and update the UI
```

Every UI binding for Redux (React, Angular, Vue, a terminal app) follows the same cycle:

1. **Create** the store.
2. **Subscribe** to updates.
3. In the subscription callback: **read** the current state, **extract** the data this piece of UI needs, and **update** the UI **if that data changed**.
4. **Render** the initial UI.
5. **Dispatch** actions in response to user input.

## 2. What's missing from the hand-written version

The 14.10 counter re-rendered **everything** after **every** action. For a real app, a binding must also:
- let each component subscribe to **only its own data**, and skip re-rendering when that data didn't change (14.09, step ⑥);
- make the store available everywhere without passing it through props;
- avoid "tearing": in concurrent React, all components rendered in one pass must see the **same** store state;
- clean up subscriptions when components unmount.

That's what **React-Redux** does. The next lecture builds a minimal version with React's own primitive, so you can see where each of these comes from.

## 3. Summary

- Subscribe → read → compare → update: the same cycle for every UI library.
- A good binding adds per-component subscriptions, change detection, store access through context, and consistency under concurrent rendering.
