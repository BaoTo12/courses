# Lecture 17.10 · Passing IDs to Child Components vs Whole Objects: Re-Render Implications

> **Section:** S17 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> 🔗 Official companion reading: Fundamentals Part 5 ("Passing IDs to Components"); Essentials Part 6 (performance)

---

## 1. Two ways to render a list

**A. The parent selects the list and passes objects** (TaskFlow today):

```tsx
function TasksPage() {
  const items = useAppSelector(selectTasks);
  return <TaskList tasks={items} … />;   // TaskList renders <TaskCard task={task} /> for each
}
```

**B. The parent selects ids; each item selects its own object:**

```tsx
function TaskIdList() {
  const ids = useAppSelector(selectTaskIds);          // number[]
  return ids.map((id) => <TaskCardById key={id} id={id} />);
}

function TaskCardById({ id }: { id: number }) {
  const task = useAppSelector((state) => selectTaskById(state, id));
  // …render the card
}
```

## 2. What happens when ONE task changes

| | A: objects | B: ids |
|---|---|---|
| The `items` array | new (the reducer mapped over it) | — |
| Parent re-renders? | ✅ yes | ❌ no, **if** the ids array is unchanged |
| Every card re-renders? | ✅ yes, because the parent re-rendered (unless `React.memo`) | ❌ only the changed card: its selector returns a new object; the others return the same object as before |

With `React.memo(TaskCard)`, pattern A also skips unchanged cards: the reducer kept unchanged tasks as the **same objects** (15.05's "reuse everything else"), so memo's shallow prop comparison sees identical `task` props. Either way, **immutability with preserved identity** is what makes the optimisation possible.

## 3. The catch with pattern B

`selectTaskIds` must return the **same array** when only a task's content changed. With TaskFlow's current state (an `items` array), `state.tasks.items.map((t) => t.id)` creates a new array every time: 17.04's problem, and a re-render of the parent after every action.

Normalised state (S19) stores `ids` directly in the state (`{ ids: number[], entities: Record<number, Task> }`), and a task update leaves `ids` untouched. That's why the official tutorial introduces ids together with normalisation. TaskFlow will switch to pattern B in S19–S21, when it has the state shape to support it.

## 4. Should you optimise now?

Not yet. 22 tasks re-render in well under a frame. Measure first (React DevTools Profiler, S21) when the list is long or the cards are expensive. The point of this lecture is the **mental model**: in Redux + React, re-renders are decided by **what each component selects** and **whether references were preserved**.

## 5. Summary

- Objects down: simple; one change re-renders the list (unless memoised).
- Ids down, each item selects itself: one change re-renders one item, but needs a stable ids array (normalised state).
- Both rely on reducers keeping unchanged objects identical.
