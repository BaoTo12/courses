# Lecture 17.04 · `useSelector` in Depth: Runs After Every Dispatch, Compares with `===`, Re-Renders Only on a Change

> **Section:** S17 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~35 minutes
> 🔗 Official companion reading: Fundamentals Part 5 ("Reading State from the Store with useSelector"); Essentials Part 4; the React-Redux API page for `useSelector`
> Measured in the reference app with a temporary `console.count` in a component (numbers below).

---

## 1. What `useSelector` does

```tsx
const openCount = useAppSelector(selectOpenTaskCount); // (state) => number
```

1. On render: calls the selector with the current state and returns the result.
2. Subscribes to the store.
3. **After every dispatch**, anywhere in the app: calls the selector **again** with the new state.
4. Compares the new result with the previous one using **`===`** (reference equality).
5. Re-renders the component **only if** they differ.

Two consequences shape everything else in this section:
- **Selectors run a lot**: every mounted `useSelector`, after every action. Keep them cheap. Heavy derived data needs memoisation (`createSelector`, S21).
- **What you return decides when you re-render.** Return exactly what the component needs, and make sure an unchanged value is `===` to the previous one.

## 2. 🔬 Measured: the header badge

`OpenTasksBadge` selects a **number**, `selectOpenTaskCount`. The table shows re-renders per dispatch, in development with StrictMode (which double-renders on purpose):

| Dispatched | Open count | Badge re-renders |
|---|---|---|
| `listPrefs/sortChanged` | unchanged | **0** |
| `ui/toastShown` | unchanged | **0** |
| `tasks/taskUpdated` (title edited) | unchanged | **0**: the tasks slice changed, but the **number** didn't |

The selector ran after every one of those dispatches; the component rendered only when its data changed. Primitive results (numbers, strings, booleans) compare by value, so they're the easiest case.

## 3. Returning objects and arrays

| Selector | Same reference when nothing relevant changed? | Re-renders on unrelated actions? |
|---|---|---|
| `(s) => s.tasks` | ✅ yes: reducers keep the slice object when they don't handle an action (15.12) | No |
| `(s) => s.tasks.items` | ✅ yes | No |
| `(s) => s.tasks.items.find((t) => t.id === id)` | ✅ yes: returns an existing object | No |
| `(s) => s.tasks.items.filter(…)` | ❌ **no**: `filter` always creates a new array | **Yes, after every action** (17.15) |
| `(s) => ({ tasks: s.tasks, prefs: s.listPrefs })` | ❌ **no**: a new object every time | **Yes** |

Measured with the `filter` version in the badge: **2 re-renders for each unrelated action** (sort change, toast), and React-Redux logged (development only):

```text
Selector unknown returned a different result when called with the same parameters. This can lead to unnecessary rerenders.
Selectors that return a new reference (such as an object or an array) should be memoized: https://redux.js.org/usage/deriving-data-selectors#optimizing-selectors-with-memoization
```

That's React-Redux's **stability check**: in development, the first time a `useSelector` runs, it calls the selector **twice** with the same state and warns if the results aren't `===`. A sibling check warns if a selector returns the **entire** root state (*"…returned the root state when called. This can lead to unnecessary rerenders…"*). Both run once per `useSelector` call by default.

### Three fixes for "I need an array or object"

1. **Select less**: return primitives or existing references, and derive in the component (cheap derivations are fine during render).
2. **Several `useSelector` calls** instead of one returning an object:
   ```tsx
   const items = useAppSelector(selectTasks);
   const status = useAppSelector(selectTasksStatus);
   ```
3. **Memoised selectors** (`createSelector`, S21) that return the **same** array when their inputs didn't change. Or, for small objects, `useSelector(selector, shallowEqual)`: the second argument replaces `===` with a key-by-key comparison.

## 4. `useSelector` and re-renders from other causes

`useSelector` only decides whether the **store** causes a re-render. A component still re-renders when its parent does, or when its own state or context changes. React-Redux doesn't prevent those. `React.memo` (08.13) and passing ids (17.10) do.

## 5. Summary

- `useSelector` runs its selector after every dispatch and re-renders only when the result changes by `===`.
- Primitives and existing references are safe; `filter`/`map`/object literals are new every time.
- React-Redux's development checks warn about unstable selectors and whole-state selectors.
- Fixes: select less, split into several selectors, memoise (S21), or pass `shallowEqual`.
