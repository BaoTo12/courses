# ✅ S17 Knowledge Check: UI and React (React-Redux)

## A. Concept

1. An unrelated `ui/toastShown` action is dispatched. Which `useSelector` calls **run**? Which components **re-render**? [17.04]
2. React-Redux puts the store in a context. Why doesn't that re-render every component on every change, unlike TaskFlow's old `TasksProvider`? [17.03]
3. What does `useSyncExternalStore` need, and what happens if `getSnapshot` returns a new array on every call? [17.02]
4. Why do form drafts stay in local state in a Redux app? [17.08]

## B. Code reading

5. What's wrong with this, and how would you fix it? [17.04, 17.15]
   ```tsx
   const { tasks, listPrefs } = useAppSelector((state) => ({ tasks: state.tasks, listPrefs: state.listPrefs }));
   ```
6. How many times does this component re-render after `dispatch(sortChanged('title', 'desc'))`, in production? [17.04]
   ```tsx
   const count = useAppSelector((state) => state.tasks.items.length);
   ```
7. In a `connect`ed component, `mapStateToProps` returns `{ openCount, selectedCount }`, a new object every time. Does it re-render after every action? Why is the answer different from question 5? [17.12]

## C. Debugging

8. The console shows *"Selector unknown returned a different result when called with the same parameters."* What does it mean, and how do you find which selector? [17.15]
9. *"could not find react-redux context value; please ensure the component is wrapped in a <Provider>"* appears only in a widget rendered with its own `createRoot`. Fix? [17.16]
10. The details page shows **stale** data after you navigate back from editing. How do you tell, with the Redux DevTools, whether the reducer or the selector is wrong? [17.07, 14.11]

## D. Design

11. Where should "is the delete-confirmation dialog open" live? And "the ids of tasks checked for a bulk action"? [17.08]
12. Pattern A (parent passes task objects) vs pattern B (parent passes ids; each card selects its task): when does B pay off, and what does it require from the state shape? [17.10]

## E. Implementation

13. A category sidebar needs, for each category, the number of tasks in it. Write the selector(s) and the component, making sure an unrelated action doesn't re-render the sidebar.

---

<details>
<summary><b>Answers</b></summary>

1. **Every** mounted `useSelector` runs its selector (after every dispatch, 17.04). Only components whose selector result changed (`!==`) re-render. For a toast: the toast list (S20), and nothing that selects tasks or preferences. Measured: the open-tasks badge re-rendered 0 times.

2. The context value is the **store object**, which never changes, so the context never triggers re-renders. State updates reach components through store **subscriptions**: each `useSelector` compares its own result and re-renders only its own component. `TasksProvider`'s context value **was** the state, so every change re-rendered every consumer.

3. `subscribe(callback)` (returning an unsubscribe) and `getSnapshot()`. React re-renders when the snapshot changes by `Object.is`. A new array on every call looks like a change on every check: verified, React warns *"The result of getSnapshot should be cached to avoid an infinite loop"* and throws *"Maximum update depth exceeded"*.

4. Nobody else needs a half-typed value. Keystrokes in Redux would run every reducer and every selector app-wide per key press; cancel becomes extra work. Only the **submitted** result becomes an event (`tasks/taskAdded` with the server's task).

5. The selector returns a **new object** every time, so the component re-renders after **every** action (and React-Redux warns about an unstable selector). Fix: two calls, `useAppSelector(selectTasksState)` and `useAppSelector((s) => s.listPrefs)`, both returning stable references; or pass `shallowEqual` as the second argument.

6. **Zero.** `sortChanged` doesn't touch `tasks`, so `items.length` is the same number, `===` holds, and there's no re-render. (In development with StrictMode, still zero, since there's nothing to render.)

7. **No.** `connect` compares the `mapStateToProps` result **shallowly** (key by key): `openCount` and `selectedCount` are unchanged numbers, so there's no re-render. `useSelector` compares the whole result with `===`, and a new object literal is never `===` the previous one.

8. In development, React-Redux ran a selector twice with the **same** state and got two different references (arrays or objects created inside the selector), so the component will re-render after every action. The warning's payload includes a `stack`: expand it in the console to find the component, then look for `filter`/`map`/object literals in its `useSelector` calls.

9. Each `createRoot` is a separate React tree with no provider above the widget. Wrap the widget's root in `<Provider store={store}>` with the **same** store object, so both trees share state.

10. Select the edit action in the DevTools (`tasks/taskUpdated`) and check the **State** or **Diff** tab. If the state **after** the action contains the new values, the reducer is right, and the problem is in the component: a selector returning something else, or a component not subscribed (reading from a stale prop or a local copy). If the state is **old** or the diff is empty, the reducer is wrong (or mutated: 15.14).

11. The dialog flag: **local state** (one component). The checked ids: **Redux `ui.selectedTaskIds`** (several components: the checkboxes, a "3 selected" toolbar, the bulk action, plus reactions to deletions, 15.10).

12. Pattern B pays off with **long lists or expensive items**, when single items change often: only the changed item re-renders. It requires a **stable ids array**: the ids must be stored in state (normalised `ids` + `entities`, S19) or memoised, so that editing a task doesn't create a new ids array. Measure before optimising.

13. Keep each selector result stable or primitive:
    ```ts
    /** A number per category: primitives compare by value (17.04). */
    export const selectTaskCountForCategory = (state: RootState, categoryId: number): number =>
      state.tasks.items.filter((task) => task.categoryId === categoryId).length;
    ```
    ```tsx
    function CategoryCount({ categoryId }: { categoryId: number }) {
      const count = useAppSelector((state) => selectTaskCountForCategory(state, categoryId));
      return <span className="text-muted">{count}</span>;
    }
    ```
    Each sidebar row renders `<CategoryCount categoryId={c.id} />`. An unrelated action leaves every count unchanged, so nothing re-renders. The `filter` runs inside the selector, but its **result** is a number. (Returning `filter(…)` itself would re-render on every action, 17.15. `createSelector` in S21 makes "tasks by category" arrays stable too.)

</details>
