# Lecture 43.99 · ✅ Knowledge Check: Error Handling

> **Section:** S43 · **Type:** ✅ Knowledge Check · **Track:** ★ Core · **Time:** ~15 minutes

---

**1. (Concept)** Trace a `NullPointerException` in a servlet to the rendered 500 page: every component involved.

<details><summary>Answer</summary>

1. `TaskViewServlet.doGet` throws the NPE; it propagates up through `HttpServlet.service` and back out of `chain.doFilter` in each filter, through csrf, authorization, authentication, maintenance and headers. None of them catch it.
2. `ErrorHandlingFilter` catches it. It's not a known exception, so it logs the stack trace with the request id (MDC) and calls `response.resetBuffer()` + `sendError(500)`.
3. `RequestLoggingFilter` logs `GET … 500 Nms` and clears the MDC; the chain returns to Tomcat.
4. `StandardHostValve` sees the error status, finds `<error-page><error-code>500` → `/WEB-INF/views/errors/500.jsp`, sets the `javax.servlet.error.*` attributes, and performs an **ERROR dispatch** of the same request.
5. `SecurityHeadersFilter` (mapped for ERROR) runs; the others don't.
6. Jasper runs `500.jsp`: header include, `${requestId}` from the request attribute, footer. The response goes out with status 500.

Without `ErrorHandlingFilter`, step 2 is skipped: `StandardWrapperValve` logs the exception, and the `Throwable` `<error-page>` is chosen.
</details>

**2. (Code reading)** `sendError(404)` vs `setStatus(404)`: what does the user see in each case?

<details><summary>Answer</summary>

`sendError(404)`: the buffer is cleared, and after the request returns, the container shows the 404 error page (TaskFlow's `404.jsp`). `setStatus(404)`: nothing else happens. The user sees whatever the code writes next (a view it forwards to), or an **empty** body with status 404 if it writes nothing. Error pages are only triggered by `sendError` and by uncaught exceptions.
</details>

**3. (Design)** What information should a user see on a 500 page? What should the log contain?

<details><summary>Answer</summary>

**User:** that something went wrong on **our** side, that it's been recorded, what to do next (try again, go back), and a **reference** (the request id). The normal layout, so they can continue. No exception type or message, no stack trace, no SQL, no server version (43.09).

**Log:** at ERROR level, with the same request id: the method and URI, the user (if any), the full exception with its cause chain. No passwords, tokens or session ids (43.11). The access log line has the status and duration.
</details>

**4. (Debugging)** A controller calls `sendError(404)` but the user sees a 500 and the log has `IllegalStateException: Cannot forward after response has been committed`. Why?

<details><summary>Answer</summary>

A missing `return` after `sendError`: the method continued and called `forward(...)` to the normal view on a response that `sendError` had already marked as an error (committed). TaskFlow's controllers now `throw new NotFoundException()`, which can't "continue" by accident (43.08).
</details>

**5. (Concept)** Why is the request id passed to the 500 page as a request attribute rather than read from the MDC?

<details><summary>Answer</summary>

The error page renders during the ERROR dispatch, **after** the filter chain (including `RequestLoggingFilter`) has returned, and that filter clears the MDC in its `finally`. The request object is the same one throughout (43.03), so a request attribute survives until the error page runs.
</details>
