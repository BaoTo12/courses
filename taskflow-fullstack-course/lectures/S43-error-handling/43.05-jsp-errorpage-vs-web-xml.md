# Lecture 43.05 · JSP `errorPage` / `isErrorPage` vs `web.xml`; Why `web.xml` Wins in MVC

> **Section:** S43 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes

---

## 📇 API card: JSP-level error handling

| Piece | Effect |
|---|---|
| `<%@ page errorPage="/WEB-INF/views/errors/500.jsp" %>` | an exception **in this JSP** forwards to that page |
| `<%@ page isErrorPage="true" %>` | the page gets the `exception` implicit object (`${pageContext.exception}`) |
| `${pageContext.errorData}` | works in any error page (43.04) |

## Why TaskFlow doesn't use `errorPage`

| | `errorPage` in each JSP | `<error-page>` in `web.xml` |
|---|---|---|
| covers | exceptions in **that JSP** | everything: servlets, filters, JSPs, `sendError`, static 404s |
| in MVC | the controller runs first: its exceptions never reach the JSP | the controller's exceptions included |
| status | Jasper's forward sets 500; easy to end up with 200 in custom setups | the status of the error |
| per page | must be repeated (or put in a `jsp-property-group`) | once |

In an MVC application almost all errors happen in the controller or the service, **before** the view is chosen. A JSP-level setting would miss them. `web.xml` is the one place that sees all of them.

## `isErrorPage` and `exception`

`isErrorPage="true"` exists so a page can print `exception.getMessage()`. That's precisely what an error page shouldn't do (43.09). TaskFlow's error pages don't declare it, which means `${pageContext.exception}` is simply unavailable to them, and a future edit can't "just print the message".

## ✅ Recap

JSP-level error pages are a legacy of JSP-only applications. In MVC, map errors in `web.xml`.
