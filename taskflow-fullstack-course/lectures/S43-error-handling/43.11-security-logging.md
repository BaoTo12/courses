# Lecture 43.11 · 🛡 Security Logging: What to Log, What Never to Log

> **Section:** S43 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes

---

## 1. Two logs, two purposes

| | Application log (logback) | Audit log (`audit_events`) |
|---|---|---|
| for | developers, operations | security, administrators, investigations |
| contains | requests, errors, stack traces | who did what security-relevant thing, when, from where |
| format | text lines with the request id | rows: `type`, `username`, `ip`, `at`, `details` |
| mutable? | files rotate and expire | **append-only** for the app (36.10: only INSERT and SELECT granted) |

## 2. What TaskFlow records

| Event | Where | Since |
|---|---|---|
| every request: method, URI, status, duration, request id | app log | 40.06 |
| unhandled exceptions with stack traces | app log | 43.08 |
| `LOGIN_OK`, `LOGIN_FAIL`, `LOGIN_THROTTLED`, `LOGOUT` | audit | 41.07 |
| `ACCESS_DENIED` (URL or data) | audit | 42.03, 42.05 |
| `USER_ENABLED`, `USER_DISABLED`, `ROLE_CHANGED`, `SESSION_REVOKED` | audit | 42.07 |
| validation anomalies worth a signal (e.g. a CSRF token mismatch) | app log (warning) | a good extension of 40.13 |

## 3. Never

| Never log | Because |
|---|---|
| passwords (even wrong ones: they're often a real password with a typo) | anyone with log access gets credentials |
| session ids, CSRF tokens, reset tokens, API keys | log access becomes account access |
| full request bodies or all parameters "for debugging" | they contain the above |
| personal data beyond what's needed | privacy law; logs are copied widely |
| raw user input without neutralising line breaks | **log injection**: a username containing a newline can forge a fake log line |

TaskFlow's request line logs the URI and query string, and TaskFlow keeps secrets out of URLs (the session id: `COOKIE` tracking, 41.02; forms: POST). The audit `details` are fixed texts plus ids ("task 23", "user 2 → ADMIN").

## 4. Making logs useful

- A **request id** on every line (MDC), shown to users on errors (43.10).
- **UTC** timestamps, synchronised clocks.
- Levels that mean something: `ERROR` = someone should look; `WARN` = unusual but handled; `INFO` = the request line.
- Alerts on patterns: many `LOGIN_FAIL`s for one account, `ACCESS_DENIED` bursts from one user.

## ✅ Recap

Log who did what, when, from where, especially failures and denials. Never log secrets. Keep the audit trail append-only.
