# Lecture 43.09 · 🔓 Information Leakage through Error Pages (Conceptual)

> **Section:** S43 · **Type:** 🔓 Attack Lab (conceptual) · **Track:** ★ Core · **Time:** ~15 minutes
> Verified: `S43ErrorHandlingTest.anUnhandledExceptionShowsOnlyTheRequestId`, `.tomcatsOwnErrorPagesShowNoVersionOrReport` (after the fix)

---

## 1. What an unconfigured Tomcat shows

Without `<error-page>` entries and with the default `ErrorReportValve`, an uncaught exception produces a page titled "HTTP Status 500 – Internal Server Error" containing:
- the **exception type and message**, e.g. TaskFlow's `/debug/fail`: `Simulated failure in SELECT password_hash FROM users WHERE id = 3 (taskflow_app@mysql:3306)`;
- the full **stack trace**, with package and class names, and the root cause;
- a footer with the exact **server version** (`Apache Tomcat/9.0.x`).

## 2. What each piece tells someone probing the site

| Leak | Tells them |
|---|---|
| SQL fragments, table and column names | the schema; which inputs reach which queries (a map for injection attempts) |
| database user and host | internal network names, account names |
| stack traces | frameworks and libraries in use (and their versions, from class names), code structure |
| the server version | which published vulnerabilities to look up |
| different errors for different inputs | a way to test hypotheses one request at a time |

None of this is an attack by itself; it makes every other attack cheaper.

## 3. Other places details leak

- `sendError(500, e.getMessage())`: the message goes into `javax.servlet.error.message` and onto a page that prints it;
- JSON APIs returning `{"error": e.toString()}` (S46 avoids this);
- debug endpoints left enabled (TaskFlow's `/debug/*` answer only loopback requests);
- verbose headers (`X-Powered-By`, `Server`).

## Lesson

An error page is output to an untrusted client. It gets a status, a fixed message and a reference number. The details go to the log.
