# Lecture 43.03 · The Error Dispatch Flow

> **Section:** S43 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> Verified: `S43ErrorHandlingTest.anUnknownPageGetsTheCustom404` (the error page still sees the request's `currentUser`), `.anUnhandledExceptionShowsOnlyTheRequestId` (the ERROR dispatch gets the security headers)

---

## 1. Step by step: `GET /taskflow/tasks/view?id=999999`

```text
Tomcat (StandardHostValve)
 └─ REQUEST dispatch: the filter chain
     encoding → logging → errors → headers → maintenance → authentication → authorization → csrf
       └─ TaskViewServlet: service.details(…) is empty → throw new NotFoundException()
     errors (ErrorHandlingFilter) catches it → response.sendError(404)        ← marks the response; renders nothing yet
     logging logs "GET /taskflow/tasks/view?id=999999 404 12ms"
 ◄─ the chain returns
 └─ StandardHostValve sees "error 404", finds <error-page> 404 → /WEB-INF/views/errors/404.jsp
     sets the javax.servlet.error.* request attributes (43.04)
     ERROR dispatch (a forward of the SAME request object) to 404.jsp
       only filters mapped with <dispatcher>ERROR</dispatcher> run: securityHeaders
       404.jsp renders with the layout; currentUser is still a request attribute
```

For an exception that nothing catches, the start is different: the exception leaves the chain, `StandardWrapperValve` logs it ("Servlet.service() … threw exception") and records it as `javax.servlet.error.exception` with status 500. The rest is the same.

## 2. Consequences

| Fact | Consequence |
|---|---|
| it's the **same request** | attributes set before the error (the user, the request id, the CSRF token) are visible to the error page |
| it's a new **dispatch** of type ERROR | REQUEST-only filters don't run again: the error page must not **depend** on them (43.14) |
| the dispatch happens **after** the chain returned | the logging filter's line is already written; the MDC is cleared (hence the request id as a request attribute, 43.12) |
| `request.getServletPath()` during the error dispatch | the error page's path; the original URI is in `javax.servlet.error.request_uri` |
| the status stays | the page is served with 404/500, not 200: crawlers and scripts see the real outcome |

## 3. Dispatcher types, completed

`REQUEST` (from the client) · `FORWARD` (`RequestDispatcher.forward`) · `INCLUDE` (`include`, `<jsp:include>`) · **`ERROR`** (this) · `ASYNC` (45.13). `request.getDispatcherType()` says which one is running.

## ✅ Recap

An error doesn't render where it happens: it's recorded, the chain unwinds, and the container forwards the same request to the error page, running only ERROR-mapped filters.
