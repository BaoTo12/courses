# Lecture 04.02 · `let`, `const`, Block Scope, and Why `const` Does Not Mean Immutable

> **Section:** S04 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes

---

## 1. Three ways to declare a variable

| | `var` (legacy) | `let` | `const` |
|---|---|---|---|
| Scope | **Function** | **Block** `{ … }` | **Block** |
| Reassignable | ✅ | ✅ | ❌ |
| Usable before declaration | Yes, as `undefined` (hoisting) | ❌ ReferenceError (temporal dead zone) | ❌ ReferenceError |
| Use it? | No | When you must reassign | **Default choice** |

```js
if (true) {
  var a = 1;
  let b = 2;
}
console.log(a); // 1: var leaks out of the block
console.log(b); // ReferenceError: b is not defined
```

The classic `var` bug, which closures (04.08) make visible:

```js
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i));   // 3 3 3
for (let j = 0; j < 3; j++) setTimeout(() => console.log(j));   // 0 1 2
```

With `let`, each loop iteration gets a **new binding** `j`, so each callback captures its own value. With `var` there's one `i` for the whole function, and by the time the callbacks run it's `3`.

**TaskFlow rule:** `const` by default, `let` when you genuinely reassign, never `var`.

## 2. `const` does not mean immutable

This is the most important sentence of the lecture:

> **`const` means the *variable* can't be reassigned. It says nothing about whether the *value* can change.**

```js
const tasks = [];
tasks.push({ id: 1 });      // ✅ allowed: we changed the array, not the variable
tasks = [];                 // ❌ TypeError: Assignment to constant variable.

const task = { title: 'A' };
task.title = 'B';           // ✅ allowed: object mutated
```

`const` protects the **binding** (the arrow from the name to the box). The box's contents are still mutable.

```text
const tasks ──────▶ [ {id:1} ]      ← contents can change (push, splice, assignment…)
      ✗ can't point the arrow elsewhere
```

## 3. Why this matters for React and Redux

React and Redux detect changes by checking whether a value is a **different reference** (04.03). This code looks harmless:

```js
const tasks = state.tasks;
tasks.push(newTask);        // mutates the SAME array
setTasks(tasks);            // React: "same reference as before → nothing changed" → no re-render
```

`const` didn't stop it; it can't. What stops it is **discipline** (immutable update patterns, 04.05), **tooling** (Redux Toolkit's immutability check middleware, S20), or **freezing** (`Object.freeze`, which is shallow).

### `Object.freeze`: runtime immutability (shallow)

```js
'use strict';
const task = Object.freeze({ title: 'A', tags: ['x'] });
task.title = 'B';     // ❌ TypeError in strict mode (silently ignored in sloppy mode)
task.tags.push('y');  // ✅ works! freeze is SHALLOW; the inner array isn't frozen
```

The S04 test file uses a recursive `deepFreeze` helper so any accidental mutation in your functions **throws**. You'll see it in 04.06.

## 4. Summary

- Use `const` by default, `let` when reassigning, never `var`.
- Block scope + per-iteration `let` bindings fix the classic loop/closure bug.
- **`const` ≠ immutable.** It prevents reassignment, not mutation.
- React/Redux need *new references* for changes; immutability is a discipline, backed by tools.
