# Lecture 04.12 · The Event Loop: Call Stack, Task Queue, Microtasks

> **Section:** S04 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes

---

## 1. Why you need this

You'll meet questions like:
- "Why does `console.log(state)` right after `setState` show the **old** value?" (S08)
- "Why did my loading spinner never appear?"
- "Why does this log in a surprising order?"

All are answered by the **event loop**, the mechanism that decides *when* each piece of JavaScript runs.

## 2. The pieces

```text
┌──────────────────────┐    ┌───────────────────────────────┐
│      CALL STACK      │    │  Web APIs / Node APIs         │
│ (what runs NOW,      │    │  timers, network, DOM events  │
│  one frame at a time)│    │  (run OUTSIDE JavaScript)     │
└──────────┬───────────┘    └──────────────┬────────────────┘
           │                               │ when done, queue a callback
           │                ┌──────────────┴─────────────────┐
           │                │ MICROTASK QUEUE                │ ← promise callbacks (.then, await continuations),
           │                │                                │   queueMicrotask
           │                ├────────────────────────────────┤
           │                │ TASK QUEUE (macrotasks)        │ ← setTimeout, setInterval, I/O, UI events
           │                └────────────────────────────────┘
           ▼
   EVENT LOOP: when the call stack is EMPTY:
     1. run ALL microtasks (including ones queued by microtasks)
     2. (browser) maybe render: style, layout, paint
     3. take ONE task from the task queue, run it
     4. repeat
```

Key facts:
1. **JavaScript runs one thing at a time**, to completion. A function is never interrupted halfway by another JavaScript callback.
2. Async APIs (timers, `fetch`) do their waiting **outside** the JS thread, then **queue a callback**.
3. **Microtasks (promises) run before the next task (timers)**, and all of them run before the browser gets a chance to render.

## 3. The classic ordering puzzle

```js
console.log('1 sync');

setTimeout(() => console.log('2 timeout'), 0);

Promise.resolve().then(() => console.log('3 microtask'));

(async () => {
  console.log('4 async start (sync part)');
  await null;
  console.log('5 after await (microtask)');
})();

console.log('6 sync end');
```

Output:

```text
1 sync
4 async start (sync part)
6 sync end
3 microtask
5 after await (microtask)
2 timeout
```

Why:
- All **synchronous** code runs first: 1, then the async function runs **synchronously up to its first `await`** (4), then 6.
- The stack is empty → run **all microtasks**: the `.then` (3), then the code after `await` (5).
- Then the **task** queue: the timeout (2), even though its delay was `0`.

`setTimeout(fn, 0)` means "queue a task as soon as possible", which is always **after** the current code **and** all pending microtasks.

## 4. Rendering and long tasks

The browser can only repaint **between tasks** (when the stack is empty and microtasks are drained).

```js
button.onclick = () => {
  spinner.style.display = 'block';   // DOM changed…
  heavySynchronousWork();            // …but 2 seconds of blocking JS: no paint happens!
  spinner.style.display = 'none';
};
```

The user never sees the spinner: by the time the browser gets to paint, it's already hidden again. And the page is frozen for 2 seconds. Lessons:
- Never do long synchronous work on the main thread (chunk it, or use a Web Worker).
- Real async work (`await fetch(…)`) *does* let the browser paint in between, which is why loading states work with real network requests.

An infinite loop of microtasks (a promise callback that always queues another) also blocks rendering forever, because microtasks are drained completely before painting.

## 5. How this explains React's "async" `setState` (preview of S08)

```js
function handleClick() {
  setCount(count + 1);
  console.log(count);   // still the OLD value
}
```

`setCount` doesn't change the `count` variable. It **schedules a re-render**. The `count` in this function is a constant captured by this render's closure (04.08). React batches updates from the same event and re-renders afterwards, and the *next* render gets a new `count`. It isn't really "async" in the promise sense; it's "applied in the next render". But the event-loop model helps you reason about *when* the new render happens.

## 6. Summary

- One call stack; JavaScript runs to completion; async waiting happens outside JS.
- Callbacks are queued: **microtasks** (promises, `await` continuations) and **tasks** (timers, events, I/O).
- When the stack empties: all microtasks → (render) → one task → repeat.
- `setTimeout(fn, 0)` runs after all microtasks. Long synchronous work blocks rendering.

## 7. Check yourself

Predict the output:

```js
setTimeout(() => console.log('A'), 0);
Promise.resolve().then(() => {
  console.log('B');
  setTimeout(() => console.log('C'), 0);
  Promise.resolve().then(() => console.log('D'));
});
console.log('E');
```

<details>
<summary>Answer</summary>

`E B D A C`

E (sync) → microtasks: B, which queues timeout C and microtask D → D runs (microtasks drain completely) → tasks in order: A (queued first), then C.

</details>
