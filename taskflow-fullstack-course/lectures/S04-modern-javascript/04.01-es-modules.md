# Lecture 04.01 · ES Modules: `import` / `export`, Named vs Default, and Why Bundlers Exist

> **Section:** S04 · Modern JavaScript for React and Redux
> **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes

---

## 1. The problem modules solve

Early JavaScript had no module system. Every `<script>` shared **one global scope**:

```html
<script src="utils.js"></script>   <!-- defines function format() -->
<script src="chart.js"></script>   <!-- ALSO defines format() → silently overwrites the first -->
<script src="app.js"></script>     <!-- which format() do I get? depends on script order -->
```

Sound familiar? It's the same problem as Sass's `@import` (02.07): global names, invisible dependencies, order-dependent behaviour. **ES modules** (ESM), standardised in 2015, fixed it the same way `@use` did.

## 2. The rules of ES modules

1. **Each file is a module with its own scope.** Top-level variables are *not* global.
2. **You export what others may use.** Everything else is private to the file.
3. **You import what you need.** Dependencies are explicit at the top of the file.
4. **A module is evaluated once**, however many files import it; importers share the same instance.
5. **Modules run in strict mode** automatically (e.g. assigning to a frozen object throws instead of failing silently, which the S04 tests rely on).

## 3. Named exports

```js
// task-utils.js
export function addTask(tasks, task) { return [...tasks, task]; }
export const PRIORITIES = ['LOW', 'MEDIUM', 'HIGH'];
```

```js
// app.js
import { addTask, PRIORITIES } from './task-utils.js';
import { addTask as appendTask } from './task-utils.js';   // rename on import
import * as taskUtils from './task-utils.js';               // namespace object: taskUtils.addTask
```

## 4. Default exports

```js
// TaskCard.jsx
export default function TaskCard(props) { … }
```

```js
import TaskCard from './TaskCard.jsx';       // importer picks ANY name
import Card from './TaskCard.jsx';           // same thing, different local name
```

### Named or default? Team conventions

| | Named | Default |
|---|---|---|
| Name enforced | ✅ Same name everywhere (easier to search/refactor) | ❌ Each importer can pick a different name |
| Multiple per file | ✅ | Only one |
| Used by | Utilities, hooks, Redux slices' action creators and selectors | React components (commonly), config files, lazy-loaded route components |

Many teams (and TaskFlow) prefer **named exports** everywhere except where a tool requires a default (e.g. `React.lazy`, some config files). Consistency beats either choice.

## 5. Live bindings (a subtle internal detail)

Imports are **live, read-only views** of the exporting module's variables, not copies:

```js
// counter.js
export let count = 0;
export function increment() { count++; }

// app.js
import { count, increment } from './counter.js';
console.log(count);   // 0
increment();
console.log(count);   // 1: the binding is live
count = 5;            // ❌ TypeError: Assignment to constant variable (imports are read-only)
```

You'll rarely depend on this, but it explains why a module is "shared state" for all importers. That's why a Redux store created in `store.js` is the same object everywhere it's imported (S16).

## 6. Where do modules run?

| Environment | How ESM works there |
|---|---|
| **Browser** | `<script type="module" src="app.js">`. The browser fetches each imported file (many HTTP requests). |
| **Node** | `.mjs` files, or `.js` with `"type": "module"` in `package.json` (our playground). |
| **Vite (dev)** | Serves your modules to the browser as native ESM, transforming TS/JSX on the fly. Very fast startup. |
| **Vite (build)** | **Bundles** hundreds of modules into a few optimised files. |

### Why bundlers still exist

Native ESM in browsers works, but shipping 800 small files means 800 requests, no dead-code elimination, and no TS/JSX support. A **bundler** (Vite uses Rollup/Rolldown internally for production builds) resolves the whole import graph at build time and outputs a few optimised, minified chunks. The concept is the same as Sass compiling many partials into one CSS file.

**Tree shaking:** because ESM imports/exports are **static** (analysable without running code), bundlers can drop exports nobody imports. That's one more reason to prefer named imports like `import { debounce } from 'lodash-es'` over importing an entire library object.

## 7. CommonJS: the other module system you'll see

Older Node code uses **CommonJS**:

```js
const fs = require('fs');
module.exports = { addTask };
```

`require` is a function call evaluated at runtime (not static), synchronous, and can't be tree-shaken as well. You'll see it in older Node tools and configs. New frontend code uses ESM.

## 8. Summary

- ES modules: per-file scope, explicit `export`/`import`, evaluated once, strict mode.
- Named exports keep names consistent; default exports let importers rename. TaskFlow prefers named.
- Imports are live read-only bindings; a module is a shared singleton for all importers.
- Browsers support ESM natively; bundlers (Vite) combine and optimise modules for production.
- CommonJS (`require`) is the older Node system.

## 9. Check yourself

1. Two modules both import `store.js`. Do they get the same store object or two copies?
2. Why can a bundler remove an unused **named** export but not always an unused property of a default-exported object?
3. What's wrong with `import { default } from './TaskCard.jsx'`?

<details>
<summary>Answers</summary>

1. **The same object.** A module is evaluated once, and all importers share its exports.
2. Named ESM exports are statically analysable: the bundler knows exactly which names are imported. Properties of an object are runtime values; the bundler can't always prove a property is unused.
3. `default` is a reserved word; you can't bind it as a local name. Use `import TaskCard from …` (or `import { default as TaskCard } from …`).

</details>
