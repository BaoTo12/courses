# Lecture 04.16 · 🐞 Debug: "I Updated the Task, but the Old List Changed Too"

> **Section:** S04 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~15 minutes

---

## Symptom

A teammate implements **undo** for the task board. They keep a history of previous task lists:

```js
const history = [];

function renameTask(tasks, id, newTitle) {
  history.push(tasks);                         // save the previous state for undo
  const next = [...tasks];                     // "copy the array so we don't mutate"
  const task = next.find((t) => t.id === id);
  task.title = newTitle;
  return next;
}

let tasks = [{ id: 1, title: 'Draft' }];
tasks = renameTask(tasks, 1, 'Final');
console.log(history[0][0].title);   // expected 'Draft' … but prints 'Final'!
```

"Undo" restores a list that already contains the new title. They insist: "I copied the array with spread!"

## Investigation checklist

1. Draw the arrows (04.03): after `const next = [...tasks]`, what do `next[0]` and `tasks[0]` point to?
2. Which line actually changes data? What does it change: the array, or an object inside it?
3. Is `history[0]` the same array as `tasks` was?
4. How would the S04 test suite's `deepFreeze` have revealed this immediately?

## Explanation

```text
tasks (old) ──▶ [ ●─────────┐ ]
                            ├──▶ { id: 1, title: 'Draft' → 'Final' }
next ────────▶ [ ●─────────┘ ]
history[0] ───▶ (same array as tasks)
```

- `[...tasks]` creates a **new array** holding the **same object references** (a shallow copy, 04.04).
- `task.title = newTitle` mutates **that shared object**, so the "old" list sees the change too.
- The array copy protected nothing, because the change wasn't in the array.

**Fix:** create a new object for the changed task, and don't mutate:

```js
function renameTask(tasks, id, newTitle) {
  history.push(tasks);
  return tasks.map((t) => (t.id === id ? { ...t, title: newTitle } : t));
}
```

Now `history[0][0]` still points to the original, unchanged `{ id: 1, title: 'Draft' }`.

**Why this matters beyond undo:** time-travel debugging in Redux DevTools (S16), React's comparison of previous and next props, and memoised selectors all rely on **old state objects staying unchanged**. A single in-place mutation corrupts all of them. In development, Redux Toolkit's immutability middleware detects exactly this and throws (S20).

**How `deepFreeze` would catch it:** freezing the tasks makes `task.title = newTitle` throw `Cannot assign to read only property 'title'`, pointing at the exact line.
