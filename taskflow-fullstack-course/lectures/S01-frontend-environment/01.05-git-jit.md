# Lecture 01.05 · 🧩 Just-in-time Git: Branches for Labs, Tags for Checkpoints

> **Section:** S01 · **Type:** 🧩 Just-in-time · **Track:** ★ Core · **Time:** ~25 minutes
> Only the Git you need for this course: not a full Git course.

---

## 1. The three things you'll do with Git

1. **Commit** your progress lecture by lecture.
2. **Tag** the end of each section (`s07-end`), then **compare** your code with earlier states.
3. **Branch** for attack labs (`lab/sqli`), so vulnerable code never reaches `main`.

---

## 2. Mental model: commits, branches, tags

```text
            s01-end          s02-end
               │                │
  A ─── B ─── C ─── D ─── E ─── F        ← main (branch = a movable pointer)
                     \
                      X ─── Y            ← lab/xss-stored (experiment, never merged)
```

- A **commit** is a snapshot of the whole project, plus a pointer to its parent.
- A **branch** is a *movable* name pointing at a commit; it moves forward when you commit on it.
- A **tag** is a *fixed* name pointing at a commit; it doesn't move. Perfect for checkpoints.

---

## 3. Daily workflow

```bash
git status                              # what changed?
git add -p                              # stage changes piece by piece (review as you go)
git commit -m "feat(styles): button component"
git log --oneline --decorate --graph    # history with tags and branches
```

`git add -p` is worth the habit: it shows each change and asks whether to include it, so you review your own diff before committing, exactly as a reviewer would.

---

## 4. Checkpoints (tags)

At the end of each section:

```bash
git tag s02-end
```

Compare your current code with a checkpoint:

```bash
git diff s02-end                            # everything changed since the end of S02
git diff s19-end s20-end -- frontend/src    # classic Redux vs Redux Toolkit
git diff s02-end --stat                     # just the list of files
```

Look at a file as it was at a checkpoint:

```bash
git show s02-end:styles/components/_button.scss
```

If you need to move a tag (you added more work to the section):

```bash
git tag -f s01-end
```

(Only do this for your local, personal tags. Moving tags that others have fetched causes confusion.)

## 5. Lab branches

Before a 🔓 attack lab:

```bash
git switch -c lab/sqli          # create and switch to a new branch
# … write the deliberately vulnerable code, run the attack, take notes …
git commit -am "lab: vulnerable search (DO NOT MERGE)"
git switch main                 # back to safe code
```

Then implement the 🛡 fix on `main`. The lab branch stays as a record of what the vulnerability looked like. You can diff it against the fix:

```bash
git diff lab/sqli main -- backend/src/main/java/com/taskflow/dao
```

## 6. Recovering when things go wrong

| Situation | Command |
|---|---|
| Undo uncommitted changes to one file | `git restore path/to/file` |
| Undo **all** uncommitted changes (careful: they're gone) | `git restore .` |
| Unstage a file (keep changes) | `git restore --staged path/to/file` |
| Try the checkpoint's version without losing your work | `git stash` → `git switch -c try-checkpoint s12-end` → … → `git switch main` → `git stash pop` |
| Undo the last commit but keep its changes | `git reset --soft HEAD~1` |

> ⚠️ `git reset --hard` and `git restore .` **discard** work permanently. Prefer `git stash` when in doubt.

---

## 7. Summary

- **Commit** often, with meaningful messages; review with `git add -p`.
- **Tags** = fixed checkpoints (`sNN-end`); `git diff <tag>` shows what you changed since.
- **Lab branches** keep vulnerable code off `main`.
- Recover with `restore`, `stash`, and `switch -c` to a tag.
