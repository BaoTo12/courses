# Lecture 23.99 · ✅ Knowledge Check: RTK Query Advanced Patterns

> **Section:** S23 · **Type:** ✅ Knowledge Check · **Track:** ★ Core · **Time:** ~25 minutes
> Answer first, then open the explanation.

---

**1. Concept.** Optimistic vs pessimistic updates: what does each do, what does the user experience on failure, and when is each appropriate?

<details><summary>Answer</summary>

**Optimistic:** patch the cache before the answer, and undo on failure. It feels instant, but the failure shows up *after* the fact (a jump back plus a toast). Use it for small, likely-to-succeed, reversible actions: toggles, priority, renames. **Pessimistic:** wait, then write the server's answer. There's a spinner or disabled button meanwhile, the UI is never wrong, and the failure shows where the user is (form errors). Use it for validated forms, payments, anything whose result you can't predict (23.04, 23.06).
</details>

**2. Code reading.** The cache holds `getTasks({"size":100})`, `getTasks({"page":0,"size":20})` and `getTasks({"page":1,"size":20})`. Which entries does `updateQueryData('getTasks', { page: 0 }, …)` touch?

<details><summary>Answer</summary>

**None.** `{ page: 0 }` serializes to `getTasks({"page":0})`, which isn't cached, and `updateQueryData` never creates entries. It touches exactly one entry, the one whose serialized arg is identical, so a partial arg matches nothing (23.04, 23.15).
</details>

**3. Debugging.** After a failed PATCH, the UI shows the optimistic state forever. What's missing?

<details><summary>Answer</summary>

The rollback: `onQueryStarted` doesn't `try/catch` `await queryFulfilled` and call `patch.undo()`, or it undoes only one of several patches. (Also check that `invalidatesTags` returns `[]` on error, which is fine, but then **nothing** refetches, so the undo is the only way back.)
</details>

**4. Design (security).** What must happen to client caches on logout, and why isn't it enough on its own?

<details><summary>Answer</summary>

Every slice resets (`loggedOut`), and the RTK Query cache is emptied (`resetApiState()`), including results still in flight. One thunk does both on every logout path (23.11). That's not enough, because the client is under the user's control. The server must end the session, send `Cache-Control: no-store`, and authorise every request (23.10 §4).
</details>

**5.** A list provides only item-id tags, **without** `{ Task, 'LIST' }`. What breaks?

<details><summary>Answer</summary>

**Creating** a task doesn't refresh the lists. `addTask` changes membership, not any existing id, so no id tag matches. (Deleting still works, since the deleted id is in the list.) (23.01)
</details>

**6.** Why does `updateTask` invalidate only `TASK_LIST`, and not `{ Task, id }`?

<details><summary>Answer</summary>

It already wrote the server's answer into `getTask(id)` with `upsertQueryData`. Invalidating the id would refetch the entry we just wrote. The lists still refetch, because an edit may change their order or membership (23.06).
</details>

**7.** Why did S22 send `GET /tasks/5 → 404` after a delete, and why doesn't S23?

<details><summary>Answer</summary>

S22: the details page was still mounted, so still **subscribed** to `getTask(5)`, when the invalidation hit, and a subscribed entry is refetched. S23 navigates away first (the optimistic delete), so the entry has no subscriber and is **removed** instead (23.05).
</details>

**8.** What does `upsertQueryEntries` do that `updateQueryData` can't? Why does TaskFlow use it in `getTasks`?

<details><summary>Answer</summary>

It **creates** entries (many at once, one action, no requests). TaskFlow seeds `getTask(id)` for every task a list returns, so opening a task from the list needs no request (23.06).
</details>

**9.** You call `commentsApi.usePrefetch('getComments')` on hover. Hovering card 7 three times within a minute sends how many requests? And a hover two minutes later?

<details><summary>Answer</summary>

**One**, because without options `prefetch` only fetches when there's no entry. Two minutes later, the unsubscribed entry was removed after `keepUnusedDataFor` (60 s), so a new hover fetches again (23.08).
</details>

**10. Implementation.** Sketch an infinite-scroll version of the list that **merges** pages into one cache entry.

<details><summary>Answer</summary>

```ts
getTaskFeed: build.query<Page<Task>, { page: number; size: number }>({
  query: (arg) => ({ url: '/tasks', params: arg, validate: (d) => isPageOf(d, isTask) }),
  serializeQueryArgs: ({ endpointName }) => endpointName,          // ONE entry for all pages
  merge: (cached, incoming) => { cached.items.push(...incoming.items); cached.page = incoming.page; },
  forceRefetch: ({ currentArg, previousArg }) => currentArg?.page !== previousArg?.page,
}),
// component: const [page, setPage] = useState(0); useGetTaskFeedQuery({ page, size: 20 }); "Load more" → setPage(p => p + 1)
```

Caveats: invalidation refetches only the **last** arg, so reset the feed on writes, or use RTK 2's `build.infiniteQuery`, which manages pages and refetches all of them.
</details>
