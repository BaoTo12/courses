# Lecture 23.15 · 🐞 Debug: The Optimistic Update Patches the Wrong Cache Entry

> **Section:** S23 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~25 minutes
> Verified by: `src/features/api/taskCache.test.ts` ("23.04 optimistic patch" asserts that **both** cached lists change; with the buggy version below, the second assertion fails)

---

## 1. The bug report

> "Ticking a task on the Tasks page does nothing for a second, then it jumps. But the header counter ('3 open') updates instantly. I thought we had optimistic updates?"

## 2. The code

A teammate wrote the optimistic patch from the docs' example:

```ts
async onQueryStarted({ id, changes }, { dispatch, queryFulfilled }) {
  const patch = dispatch(
    apiSlice.util.updateQueryData('getTasks', LIST_QUERY, (page) => {
      const task = page.items.find((item) => item.id === id);
      if (task) Object.assign(task, changes);
    }),
  );
  try { await queryFulfilled; } catch { patch.undo(); }
},
```

## 3. Investigate

1. **DevTools → Log.** After `executeMutation/pending`, there's **one** `queryResultPatched`. Open it: the patched `queryCacheKey` is `getTasks({"size":100})`.
2. **DevTools → State → `api.queries`.** The list on screen is `getTasks({"page":0,"size":20,"sort":"dueDate,asc"})` (23.07). It was **not** patched.
3. Why the counter was instant: `OpenTasksBadge` reads the app-wide list, `getTasks(LIST_QUERY)`. That's the one entry that was patched.
4. Conclusion: `updateQueryData` patches **exactly one entry, the one for that arg**. The page's entry has a different arg, so it waited for the refetch.

## 4. Fix

Patch every cached argument of the endpoint:

```ts
const patches = apiSlice.util.selectCachedArgsForQuery(getState(), 'getTasks').map((query) =>
  dispatch(apiSlice.util.updateQueryData('getTasks', query, (page) => { … })),
);
// and the detail entry:
patches.push(dispatch(apiSlice.util.updateQueryData('getTask', id, (task) => void Object.assign(task, changes))));
try { await queryFulfilled; } catch { for (const patch of patches) patch.undo(); }
```

Alternatives, and when they fit:

- **Only the entry on screen:** pass the page's arg in the mutation's argument (`{ id, changes, listArgs }`). It's precise, but every caller must know it.
- **Normalised cache:** one entities collection plus id lists (23.02). One patch updates every view, but it's a bigger redesign.

## 5. Prevent it

- A test that patches with **two** cached lists with different args, and asserts both. TaskFlow's "23.04 optimistic patch" test does exactly this with `{ size: 100 }` and `{ status: 'TODO', size: 100 }`.
- Rule of thumb: **any time the same item can be in several entries, patch by `selectCachedArgsForQuery`, not by a constant arg.**
