# Lecture 23.03 · `selectFromResult`: Read Part of a Cache Entry, Re-render Less

> **Section:** S23 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes
> 🔗 Official companion reading: Redux Essentials **Part 8** ("Selecting values from results"); RTK Query docs, "Queries → Selecting data from a query result"
> In TaskFlow: `DashboardPage` (since 22.09): `useGetTasksQuery(LIST_QUERY, { selectFromResult: ({ isLoading }) => ({ isLoading }) })`

---

## 1. The problem

`useGetTasksQuery(LIST_QUERY)` in a component means: "re-render me whenever **anything** in this result changes". That includes `isFetching` flipping on and off at every refetch, and new `data` after every toggle. A component that needs only one task, or only a count, pays for all of it.

## 2. The option

```ts
const { task } = useGetTasksQuery(LIST_QUERY, {
  selectFromResult: ({ data }) => ({ task: data?.items.find((t) => t.id === taskId) }),
});
```

- Your function receives the **whole hook result** (`data`, `isLoading`, `isFetching`, `error`…) and returns **an object**.
- The hook compares that object with the previous one **shallowly**, field by field with `===`. If every field is identical, the component doesn't re-render.
- The subscription is unchanged: the entry is still fetched and kept alive. You only filter what triggers **your** re-renders.

`find` returns the task **object** from the cache. Structural sharing (22.06) keeps it identical when a refetch didn't change it, so the card above re-renders only when *its* task changed.

## 3. The trap: new arrays and objects

```ts
// ❌ filter() returns a NEW array on every call → the shallow compare always fails → no benefit at all
selectFromResult: ({ data }) => ({ open: data?.items.filter((t) => t.status !== 'DONE') ?? [] }),
```

Fix it with a memoized selector, created **per component** because it caches the last input (21.07):

```ts
const selectOpen = useMemo(
  () => createSelector([(res: { data?: Page<Task> }) => res.data], (data) => data?.items.filter((t) => t.status !== 'DONE') ?? NO_TASKS),
  [],
);
const { open } = useGetTasksQuery(LIST_QUERY, { selectFromResult: (result) => ({ open: selectOpen(result) }) });
```

Or ask whether you need an array at all. A **count** is a number, which compares by value:

```ts
selectFromResult: ({ data }) => ({ openCount: data?.items.filter((t) => t.status !== 'DONE').length ?? 0 }),
```

## 4. `selectFromResult` or a Redux selector?

| | `selectFromResult` | `useAppSelector(selectX)` over `endpoint.select(arg)` |
|---|---|---|
| Subscribes / fetches | ✅ yes (it's the query hook) | ❌ no: someone else must subscribe |
| Reusable across components | per hook call | ✅ yes: one memoized selector, many components |
| Combines with other slices (sort prefs, UI) | awkward | ✅ natural (`createSelector` inputs) |
| TaskFlow uses it for | the dashboard's loading flag | stats, sorted list, board columns, counts (22.09) |

TaskFlow subscribes once in `AppLayout` and reads everywhere through selectors. `selectFromResult` fits a component that **owns** its subscription and needs a slice of it.

## 📇 API card: `selectFromResult`

```ts
useXQuery(arg, { selectFromResult: (result: UseQueryStateDefaultResult) => Record<string, unknown> })
useXQueryState(arg, { selectFromResult })   // same, without subscribing
useXMutation({ selectFromResult })           // also available on mutations
```

**Returns:** exactly your object. Other fields (`refetch` aside) are **not** included unless you return them.

**When to use:** a component that needs a small, stable piece of a big entry, or only a flag.

**When not to:** the derivation combines other state, or several components need it → a memoized selector.

**Common mistakes:**
- Returning new arrays or objects (§3).
- Forgetting to return `isLoading`/`error` and then wondering why the component can't show them.
- Defining an inline `createSelector` **inside** the render without `useMemo`. It's a new selector every render, so it has no cache.
