# Lecture 23.10 · 🛡 Cache and Identity: User B Must Never See User A's Tasks

> **Section:** S23 · **Type:** 📖 Theory (🛡 Security) · **Track:** ★ Core · **Time:** ~35 minutes
> Verified: `src/features/api/taskCache.test.ts` ("23.11 clearUserData": slices reset, the cache is emptied, and a response still in flight is dropped)

---

## 1. The scenario

A shared computer at an office or a library:

1. **A** logs in and opens their tasks. The cache holds `getTasks(…)`, `getTask(…)` × 20 and `getComments(7)`.
2. **A** clicks "Log out". The UI goes back to the login page.
3. **B** logs in on the same tab. `AppLayout` subscribes to `getTasks(LIST_QUERY)`, and the entry **already exists**: RTK Query serves A's cached list at once, with no request (22.06). B sees A's tasks until something refetches.
4. Worse: B opens `/tasks/7`, which is seeded (23.06), and reads A's task and A's comments. The server never got a chance to say 403.

This is an **information disclosure** bug (OWASP A01, broken access control, on the client side). Nothing is wrong on the server. The client **cached across an identity change**.

## 2. The rule

> Any cache keyed by *what* was requested, but not by *who* requested it, must be **emptied when "who" changes**.

That covers Redux slices (`loggedOut`, 20.11), the RTK Query cache (`resetApiState()`), and anything in `localStorage`/`sessionStorage` with user data. It doesn't include cookies with preferences like the theme.

## 3. What `resetApiState()` does

- It removes **every** query and mutation entry, and all subscription bookkeeping.
- A request **still in flight** when you reset is dropped when its response arrives. There's no entry left to fill. The test starts user A's `getTasks`, logs out before it answers, and checks that `state.api.queries` stays `{}`.
- It doesn't abort requests, so the response still travels. It just never reaches the state.
- Streaming entries (23.09) are removed, so their `cacheEntryRemoved` resolves and the connections close.

## 4. Why it isn't enough on its own

The client reset is **hygiene**, not access control:

| Threat | Client reset helps? | Real defence |
|---|---|---|
| B sees A's cached data in the same tab | ✅ yes | + the server session ends on logout (S38) |
| B presses Back and the browser shows a cached **HTTP** response | ❌ no (that's the browser's HTTP cache, not Redux) | `Cache-Control: no-store` on API responses (S41) |
| B calls the API with A's still-valid session cookie | ❌ no | server-side logout invalidates the session (S38), plus a short session lifetime |
| A's data in the JS heap until reload | partly | on sensitive apps, **reload** the page after logout (`window.location.assign('/login')`) |
| B edits A's task by id | ❌ irrelevant | authorisation checks on every request, **server-side** (S41: the IDOR lab) |

The design answer to "why isn't the client reset enough?": the client is under the user's control, so **only the server enforces who may see what**. The client reset only stops *accidental* disclosure between people sharing a browser.

## 5. Other identity changes

- **Session expiry**: a 401 from any request should run the same clean-up (S24 adds it to the Axios interceptor).
- **Switching accounts or tenants** without logging out: the same reset. Or include the tenant in every query arg, so the cache keys differ.
- **Impersonation** in the admin portal (S45): a full reload is simplest.

## ✅ Recap

- Cache entries are keyed by *request*, not by *user*. **Empty them when the user changes.**
- `resetApiState()` drops in-flight results too, but it doesn't abort them.
- The client reset prevents accidental disclosure. Real protection is server-side sessions, `no-store`, and authorisation.
