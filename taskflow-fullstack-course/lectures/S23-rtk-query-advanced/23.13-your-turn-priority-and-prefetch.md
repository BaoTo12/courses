## Part A: change the priority from the details page

1. On `TaskDetailsPage`, next to the badges, show a **Priority** `<select>` (`LOW`, `MEDIUM`, `HIGH`), for logged-in users only.
2. Changing it sends `PATCH /tasks/:id` with `{ priority }`.
3. It must be **optimistic**: the badge and the priority bar change at once. If the server refuses, they return to the old value, and an error toast appears.
4. Selecting the value that's already set sends nothing.
5. Validate the `<select>` value with a type guard. No `as Priority`.

> 🤔 Before you write any cache code: re-read `patchTask` in `apiSlice.ts` (23.05). What does it already do for *any* `changes` object?

**Test it:** add a case to `src/features/api/taskCache.test.ts`: subscribe to `getTask(1)`, make writes fail, patch `{ priority: 'HIGH' }`, then assert the entry says `HIGH` before the answer and `MEDIUM` after the rejection.

## Part B: open a task without waiting for its comments

When the mouse enters a card in the list view, **prefetch that task's comments**, so the details page shows them with no "Loading comments…".

- Use the generated `usePrefetch`.
- Don't prefetch the task itself. Why would that be useless here? (Hint: 23.06.)
- `TaskList` must stay presentational: it gets an optional callback prop, and the **page** decides what hovering does.

**Check it:** Network tab. Hover a card, and `GET /api/tasks/:id/comments` fires. Click it, and no second comments request is sent.
