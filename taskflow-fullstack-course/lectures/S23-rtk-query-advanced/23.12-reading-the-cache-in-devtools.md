# Lecture 23.12 · Reading RTK Query's Cache in the Redux DevTools

> **Section:** S23 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> 🔗 Official companion reading: RTK Query docs, "Usage → Debugging" (the RTK Query monitor in the Redux DevTools)

---

## 1. Two views of the same data

The Redux DevTools extension has an **RTK Query** tab, next to Log, Chart and State. It reads `state.api` and presents it per entry. Use it to answer "what's cached, and why". Use the **State** tab to see the raw shape.

## 2. `state.api`, field by field

| Key | Contains | Ask it |
|---|---|---|
| `queries` | one object per cache entry, keyed `endpoint(args)`: `status`, `data`, `error`, `originalArgs`, `requestId`, `startedTimeStamp`, `fulfilledTimeStamp` | Is it cached? Since when? With what arg exactly? |
| `mutations` | per mutation **request** (or `fixedCacheKey`), while a hook/component keeps it | Did the save run? What did it return or throw? |
| `provided` | tag → the cache keys that provide it | Which entries will `{ Task, 5 }` hit? (22.13, 23.15) |
| `subscriptions` | cache key → subscriber ids: a **lagging mirror** of the middleware's counts (22.02) | Is anything keeping this entry alive? |
| `config` | `reducerPath`, `keepUnusedDataFor`, `refetchOnFocus`…, `online`, `focused`, `middlewareRegistered` | Is the middleware installed? Are the focus listeners set up? |

## 3. Debugging recipes

| Symptom | Look at | Typical cause |
|---|---|---|
| Nothing loads, entries stay `pending` | `config.middlewareRegistered` | middleware not added (22.04) |
| A save doesn't refresh a list | the **Log** tab: the `executeMutation/fulfilled` action; then `provided` | tag mismatch (22.13) |
| Two requests for "the same" data | `queries` keys | args differ: `{ size: 100 }` vs `{ page: 0, size: 100 }` |
| An optimistic change doesn't show | `queries[key]` of the entry on screen vs the one you patched | wrong arg in `updateQueryData` (23.15) |
| Data from the previous user | `queries` after logout | no `resetApiState()` (23.10) |
| An entry never goes away | `subscriptions` | a component still subscribed (a hidden tab, a layout) |

## 4. The action log, read once end to end

Tick a task with the DevTools open:

```text
api/executeMutation/pending        meta.arg: { endpointName: 'patchTask', originalArgs: { id: 3, changes: { status: 'DONE' } } }
api/queries/queryResultPatched     ← the optimistic patch, once per cached getTasks entry + getTask(3) (23.05)
api/executeMutation/fulfilled      ← the listener's "Completed: …" toast follows
ui/toastShown
api/executeQuery/pending           ← the refetches of the entries that provide { Task, 3 } (23.01)
api/executeQuery/fulfilled
```

Each step is a place to set a breakpoint: `diff` shows exactly what the patch or the refetch changed.

## ✅ Recap

- `queries` = what's cached; `provided` = what a tag will hit; `subscriptions` = who keeps it alive; `mutations` = what the writes did.
- Most "RTK Query doesn't refresh" bugs are an **arg** or **tag** mismatch that `queries` and `provided` show directly.
