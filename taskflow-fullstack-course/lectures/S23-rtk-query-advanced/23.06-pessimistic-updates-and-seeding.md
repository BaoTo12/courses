## 1. Pessimistic = wait, then write the answer

The edit form (`EditTaskPage`) sends a whole task with PUT. The server validates it (400 with field errors), and it may change what we sent (trimmed title, a new `updatedAt`). We **can't** guess the result, so we **wait** for it:

```ts
updateTask: build.mutation<Task, { id: number; request: CreateTaskRequest }>({
  query: …,
  async onQueryStarted({ id }, { dispatch, queryFulfilled }) {
    try {
      const { data: saved } = await queryFulfilled;
      dispatch(apiSlice.util.upsertQueryData('getTask', id, saved));
    } catch {
      // The form shows the error (unwrap in EditTaskPage): the cache was never touched.
    }
  },
  invalidatesTags: (_result, error) => (error ? [] : [TASK_LIST]),
}),
```

- After the save, `EditTaskPage` navigates to `/tasks/:id`. `getTask(id)` **already holds the server's answer**: instant, no request.
- It invalidates only `TASK_LIST`, not `{ Task, id }`. Invalidating the id would refetch the `getTask(id)` we just wrote. The lists still refetch, because an edit can change their order or membership (a new due date, a new status on a filtered page).
- The test pins the sequence: `PUT /tasks/1`, `GET /tasks`, and **no** `GET /tasks/1`.

**Optimistic vs pessimistic**, in one line: optimistic *predicts* the answer and may be wrong, while pessimistic *waits* for the answer and is always right. Choose by how predictable and how likely the success is (23.04 §5).

## 2. Seeding: one request fills many entries

The list already has every task's full data. Opening `/tasks/7` from the list used to send `GET /tasks/7` anyway, because `getTask(7)` is its own cache entry (22.09). Seed those entries when the list arrives:

```ts
getTasks: build.query<Page<Task>, TaskQuery>({
  …,
  async onQueryStarted(_query, { dispatch, queryFulfilled }) {
    try {
      const { data } = await queryFulfilled;
      dispatch(
        apiSlice.util.upsertQueryEntries(data.items.map((task) => ({ endpointName: 'getTask', arg: task.id, value: task }))),
      );
    } catch {
      // The list's own entry holds the error: nothing to seed.
    }
  },
}),
```

- **`upsertQueryEntries`** writes many entries in **one** action. No requests are sent, and the entries are `fulfilled` at once.
- They have no subscribers. When a details page subscribes, the data is there, so there's no request. The test checks `server.requests` is just `['GET /tasks']`.
- Seeded data is as fresh as the list. A task edited elsewhere a minute ago is stale in both, and tags or refetches handle it the same way.

## 3. `upsertQueryData` vs `upsertQueryEntries` vs `updateQueryData`

| | Creates a missing entry? | Requests? | Actions | Use for |
|---|---|---|---|---|
| `updateQueryData(ep, arg, recipe)` | ❌ no-op | none | 1 (patch) | optimistic patches of what's shown (23.04) |
| `upsertQueryData(ep, arg, value)` | ✅ | none (it runs like a request that resolves at once: `pending` → `fulfilled`) | 2 | one entry: the pessimistic write above, test setup (`task-cache.ts`) |
| `upsertQueryEntries([{ endpointName, arg, value }])` | ✅ | none | 1 | many entries at once: seeding |

## 📇 API card: `upsertQueryData` · `upsertQueryEntries`

```ts
await dispatch(api.util.upsertQueryData('getTask', 7, task));          // returns a promise, like a query
dispatch(api.util.upsertQueryEntries([{ endpointName: 'getTask', arg: 7, value: task }, …]));
```

| Param | Meaning |
|---|---|
| `endpointName` | a **query** endpoint's name (type-checked) |
| `arg` | the exact argument, which determines the cache key |
| `value` | the full result type (not a partial) |

**Minimal example (outside TaskFlow):** after `createOrder` succeeds, put the returned order into `getOrder(order.id)` so the confirmation page opens instantly.

**When to use:** you **have** the server's data from another response.

**When not to:** you're guessing. That's an optimistic patch (23.04), which must be undoable. Or you only have part of the data: `value` must be complete, so use `updateQueryData` on an existing entry instead.

**Common mistakes:**
- Seeding with list items that are **summaries** (fewer fields than the details endpoint). The details page then shows missing fields. TaskFlow's list returns full tasks, so it's safe.
- Upserting and then invalidating the same entry in the same mutation. That's a wasted refetch (§1).
