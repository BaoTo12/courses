# Lecture 23.04 · Optimistic Updates: `onQueryStarted`, `updateQueryData`, `undo()`

> **Section:** S23 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~45 minutes
> 🔗 Official companion reading: Redux Essentials **Part 8** ("Implementing optimistic updates"); RTK Query docs, "Manual Cache Updates → Optimistic Updates"
> Verified: `src/features/api/taskCache.test.ts` ("23.04 optimistic patch": both cached lists and the detail change before the answer; all three roll back on a 500; the error toast appears)

---

## 1. Why

With S22, ticking a task shows nothing for a moment. The PATCH goes out, the answer comes back, the list refetches, and only then does the card move. On a slow network that takes seconds. The user clicks again, and now it toggles twice.

An **optimistic update** changes the cache **before** the server answers, assuming success, and **rolls back** if the server says no.

```text
click ─► patch the cache (instant UI) ─► PATCH /tasks/1 ─┬─ 200 ─► keep it (optionally refetch to confirm)
                                                          └─ 4xx/5xx ─► undo the patch + tell the user
```

## 2. The three pieces

```ts
likePost: build.mutation<Post, number>({
  query: (id) => ({ url: `/posts/${id}/like`, method: 'POST' }),
  async onQueryStarted(id, { dispatch, queryFulfilled }) {
    // ① patch a cache entry NOW; keep the "patch result" to undo it
    const patch = dispatch(
      api.util.updateQueryData('getPost', id, (draft) => {
        draft.likes += 1;           // an Immer draft: mutate freely (20.05)
      }),
    );
    try {
      await queryFulfilled;          // ② wait for the server
    } catch {
      patch.undo();                  // ③ failed → restore exactly what was there
    }
  },
}),
```

- **`onQueryStarted(arg, api)`** runs when the request **starts**, which is where you patch. It isn't a React effect: it runs in the middleware, whoever triggered the mutation (a hook, a thunk, a test).
- **`updateQueryData(endpointName, arg, recipe)`** is a thunk. It patches **one existing cache entry**, the one for exactly that `arg`. If the entry doesn't exist, it does nothing.
- **`dispatch(...)` returns a `PatchCollection`** with `patches`, `inversePatches` and `undo()`. `undo()` applies the inverse patches: it restores the fields you changed, **not** a whole snapshot. Other changes made in the meantime survive.
- **`queryFulfilled`** is a promise that resolves to `{ data, meta }` or **rejects** with `{ error, isUnhandledError }`. Always `try/catch` it, or you get an unhandled rejection.

## 3. The question you must answer: *which* entries?

A task appears in **several** cache entries:

- `getTasks({"size":100})`, the app-wide list;
- `getTasks({"page":0,"size":20,"sort":"dueDate,asc"})`, the page on screen (23.07);
- `getTasks({"status":"TODO",…})`, a filtered page visited earlier;
- `getTask(1)`, the details entry.

Patch only one of them and the others show the old state. That's 23.15's bug. RTK Query can list the cached arguments of an endpoint:

```ts
for (const query of api.util.selectCachedArgsForQuery(getState(), 'getTasks')) {
  dispatch(api.util.updateQueryData('getTasks', query, (page) => { … }));
}
```

## 4. After success: trust, or confirm?

| Strategy | On success | Pros / cons |
|---|---|---|
| **Optimistic + invalidate** (TaskFlow's `patchTask`) | the id tag refetches the entries that contain the task | the server's version wins (server-computed `updatedAt`, re-sorting); costs one refetch |
| **Optimistic only** | nothing | no extra request; the cache may drift from the server (other fields the server changed) |
| **Optimistic + write the response** | `updateQueryData` again with `data` | exact, no refetch; more code |

## 5. Optimistic or not?

| Use optimistic for | Don't, for |
|---|---|
| toggles, likes, reorders, renames: small, frequent, **very likely to succeed** | payments, sign-ups, anything with **server-side validation that often fails** |
| actions that are easy to reverse visually | actions whose failure the user must not miss (use a pessimistic update + a spinner, 23.06) |

## 📇 API card: `onQueryStarted` · `updateQueryData` · `PatchCollection`

| API | Signature | Notes |
|---|---|---|
| `onQueryStarted` | `async (arg, { dispatch, getState, extra, requestId, queryFulfilled, getCacheEntry, updateCachedData? }) => void` | on queries **and** mutations. `updateCachedData` exists on queries only (it patches *this* entry). |
| `api.util.updateQueryData` | `(endpointName, arg, (draft) => void \| newValue, updateProvided = false) => ThunkAction<PatchCollection>` | patches an **existing** entry; a no-op if it's missing. `updateProvided: true` recomputes its tags. |
| `PatchCollection` | `{ patches, inversePatches, undo() }` | `undo()` reverses only these patches |
| `api.util.patchQueryData` | `(endpointName, arg, patches)` | re-applies patches (e.g. redo) |
| `api.util.selectCachedArgsForQuery` | `(state, endpointName) => Arg[]` | every argument currently cached for that endpoint |

**Minimal example (outside TaskFlow):** the `likePost` in §2.

**When to use:** high-confidence, reversible writes where waiting feels slow.

**When not to:** likely-to-fail writes, or writes whose result you can't predict locally (a server-computed price). Use a pessimistic update instead (23.06).

**Common mistakes:**
- Patching one cache entry when the item is in several (23.15).
- Not catching `queryFulfilled`: the undo never runs, and the UI shows the optimistic state forever.
- Calling `updateQueryData` with an arg that's "equal but not the same": `{ size: 100 }` vs `{ size: 100, page: 0 }` are **different** entries.
- Expecting `updateQueryData` to **create** an entry. Use `upsertQueryData` for that (23.06).
