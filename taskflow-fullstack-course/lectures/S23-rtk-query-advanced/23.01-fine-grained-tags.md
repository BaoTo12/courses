## 1. What S22's bare tags cost

In S22, every task query provides `'Task'` and every task mutation invalidates `'Task'`. That is correct, but it's a sledgehammer:

| You do | S22 refetches |
|---|---|
| rename task 1 | the list, `getTask(1)`, **and** `getTask(2)`, and every other open task |
| delete task 5 on its page | the list, **and** `getTask(5)` itself, which answers `404` |

The fix is to describe the cache more precisely. Answer two questions for every entry: **which tasks does it contain**, and **does it depend on which tasks exist?**

## 2. The pattern: one tag per item, plus a `LIST` tag

```ts
const TASK_LIST = { type: 'Task', id: 'LIST' } as const;

getTasks: build.query<Page<Task>, TaskQuery>({
  query: …,
  providesTags: (result) => [...(result?.items.map(({ id }) => ({ type: 'Task' as const, id })) ?? []), TASK_LIST],
}),
getTask: build.query<Task, number>({
  query: …,
  providesTags: (_result, _error, id) => [{ type: 'Task', id }],
}),
```

- A list provides `{ Task, 1 }`, `{ Task, 2 }`, … (**its items**), plus `{ Task, 'LIST' }` (**its membership**).
- A details entry provides just its id.
- `'LIST'` is not special to RTK Query. It is only an id nobody else uses. The docs use the same convention.
- `as const` keeps `'Task'` a literal type. Without it, TypeScript widens the value to `string`, and the tag type is rejected.
- When the query fails, `result` is `undefined`. The list still provides `TASK_LIST`, so a later create refetches it.

## 3. Mutations say exactly what they changed

| Mutation | Changes | Invalidates |
|---|---|---|
| `addTask` | which tasks exist | `TASK_LIST` |
| `patchTask` | task *id*'s fields | `{ Task, id }` → the lists containing it and its `getTask(id)` |
| `updateTask` | the same, but it writes the answer itself (23.06) | `TASK_LIST` |
| `deleteTask` | membership **and** task *id* | `{ Task, id }` + `TASK_LIST` |
| `clearCompleted` | membership + each deleted id | the deleted ids + `TASK_LIST` |

In `apiSlice.ts`, every function form looks like this:

```ts
invalidatesTags: (_result, error, { id }) => (error ? [] : [{ type: 'Task', id }]),
```

`error ? [] : …`: a failed write changed nothing on the server, so it invalidates nothing (22.08 §5).

## 4. Check the table from 22.08 again

With these tags:

- Patch task 1. The list provides `{Task,1}`, so it refetches. `getTask(1)` refetches. `getTask(2)` does **not**. The test counts `GET /tasks`, `GET /tasks/1` and `PATCH /tasks/1`, and nothing else.
- Create a task. Only `TASK_LIST` providers refetch: the lists. The open details pages are untouched.
- Delete task 5. The lists refetch. `getTask(5)` is invalidated too. If the details page is still mounted, it would refetch and get a 404. 23.05 makes sure it isn't mounted by then.

## 5. When is it worth it?

- **Always worth it:** the `LIST` split. Creates are frequent, and they shouldn't refetch detail views.
- **Worth it when details pages or several lists are open at once:** per-id tags.
- **Not worth it:** tiny apps with one list and no detail cache. Bare tags are simpler and just as correct.

## ✅ Recap

- Lists provide **item ids + `LIST`**. Details provide their **id**.
- Field changes invalidate the **id**. Creates and deletes invalidate **`LIST`** (a delete also invalidates the id).
- Tag functions receive `(result, error, arg)`. Use the **arg** for mutations, and return `[]` on error.
