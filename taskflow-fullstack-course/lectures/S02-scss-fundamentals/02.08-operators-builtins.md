# Lecture 02.08 · Operators and Built-in Modules: `sass:math`, `sass:color`, Units

> **Section:** S02 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes

---

## 1. Why computation in stylesheets?

Design systems are full of *relationships*: "the hover colour is the primary colour, 10% darker", "small padding is half the normal padding", "line height is font size × 1.5". Expressing relationships instead of hard-coding results means one change propagates correctly.

---

## 2. Arithmetic operators and units

```scss
$space-4: 16px;

.a { padding: $space-4 * 0.5; }        // 8px
.b { margin: $space-4 + 4px; }         // 20px
.c { width: 100% - 20%; }              // 80%
.d { top: -$space-4; }                 // -16px
```

Sass **tracks units** and refuses nonsense:

```scss
.x { width: 10px + 2em; }   // ✗ Error: incompatible units px and em
.y { width: 10px * 2px; }   // ✗ Error at output: 20px*px isn't a valid CSS value
.z { width: 10px + 2; }     // 12px (unitless numbers adopt the other unit)
```

Mixing units that can only be resolved **in the browser** (like `%` and `px`, or `rem` and `px`) needs CSS's runtime `calc()`:

```scss
.sidebar { width: calc(100% - #{$space-8}); }   // browser computes it at layout time
```

Here's the compile-time/runtime split again: Sass computes what it can know at build time; `calc()` defers to the browser what depends on the layout.

### Division: use `math.div`

The `/` character is ambiguous in CSS (`font: 16px/1.5`, `grid-area: 1 / 2`), so **`/` as division is deprecated** in Sass:

```scss
@use 'sass:math';

.half { width: math.div(100%, 2); }       // 50%
.ratio { padding-top: math.div(9, 16) * 100%; }  // 56.25%
```

### Comparison and equality

`==`, `!=`, `<`, `>`, `<=`, `>=` return booleans for use in `@if` (S03). `and`, `or`, `not` combine them.

### Strings

```scss
$prefix: 'tf';
.#{$prefix}-hidden { display: none; }   // .tf-hidden (interpolation in a selector)
```

`#{…}` (**interpolation**) inserts a value into selectors, property names, custom property values, media queries and strings.

## 3. Built-in modules

Sass's built-in functions live in modules you load with `@use`:

| Module | Useful functions |
|---|---|
| `sass:math` | `math.div`, `math.round`, `math.ceil`, `math.floor`, `math.min`, `math.max`, `math.abs`, `math.percentage`, `math.$pi` |
| `sass:color` | `color.adjust`, `color.scale`, `color.mix`, `color.change`, `color.channel` |
| `sass:string` | `string.index`, `string.slice`, `string.unquote`, `string.to-upper-case` |
| `sass:list` | `list.nth`, `list.length`, `list.append`, `list.join` |
| `sass:map` | `map.get`, `map.merge`, `map.has-key`, `map.keys`, `map.values` (S03) |
| `sass:meta` | `meta.type-of`, `meta.inspect` (debugging) |

### Colour functions

```scss
@use 'sass:color';

$primary: #4f46e5;

.a { background: color.adjust($primary, $lightness: -8%); }   // absolute: 8 points darker
.b { background: color.scale($primary, $lightness: -15%); }   // relative: 15% of the way to black
.c { background: color.mix($primary, #fff, 20%); }             // 20% primary, 80% white (a tint)
.d { background: color.change($primary, $alpha: 0.2); }        // same colour, 20% opacity
```

- **`adjust`** changes a channel by a fixed amount. Can overshoot on very light/dark colours.
- **`scale`** changes it *proportionally* toward the extreme, which usually gives more predictable results for hover states. Prefer it.
- The old global functions `darken()`, `lighten()`, `transparentize()` are **deprecated**. You'll see them in older code; they map to `color.adjust`.

> 🧠 These run at **compile time**. For runtime theming you'll emit the *results* as custom properties (S03), or use CSS's own `color-mix()` in the browser (03.17).

### Debugging values

```scss
@use 'sass:meta';
@debug meta.inspect($primary);       // prints to the terminal during compilation
@debug math.div(9, 16);              // 0.5625
```

`@debug`, `@warn` and `@error` print during compilation. You'll use `@error` in S03 to reject invalid mixin arguments.

## 4. Applying it to TaskFlow

Let's make the dark hover colours **derived** instead of hard-coded. In `_variables.scss`:

```scss
@use 'sass:color';

$color-primary: #4f46e5;
$color-primary-dark: color.scale($color-primary, $lightness: -15%);

$color-danger: #dc2626;
$color-danger-dark: color.scale($color-danger, $lightness: -15%);
```

Now a rebrand is a one-line change: set `$color-primary` and the hover follows.

> 🔎 **Don't be surprised by the output format.** Recent Dart Sass versions (with CSS Color 4 support) may emit derived colours as something like `rgb(16.53%, 12.28%, 87.39%)` instead of a hex code. It's valid CSS and renders the same colour. Only the notation differs.

(Designers sometimes want exact hand-picked hover colours. Derivation is a choice, not a law. Both are valid, and the variable names hide the decision from components.)

---

## 5. Summary

- Arithmetic works with **unit checking**; incompatible units → compile error; runtime-only math → `calc()`.
- Use **`math.div`**, not `/`, for division.
- **Interpolation `#{}`** inserts values into selectors, properties, custom properties and media queries.
- Built-in modules: `sass:math`, `sass:color` (`scale` > `adjust`; `darken()` is deprecated), `sass:map`, `sass:string`, `sass:list`, `sass:meta`.
- `@debug` prints values while compiling.

## 6. Check yourself

1. What does `math.div(24px, 16px)` return? What about `math.div(24px, 16)`?
2. Why is `width: 100% - 32px;` an error in Sass while `calc(100% - 32px)` is fine?
3. Replace `darken($color-primary, 10%)` with the modern API.

<details>
<summary>Answers</summary>

1. `1.5` (units cancel, giving a unitless ratio) and `1.5px`.
2. `%` depends on the parent's width, which is only known at **layout time in the browser**; Sass can't compute it. `calc()` is evaluated by the browser.
3. `color.adjust($color-primary, $lightness: -10%)` (with `@use 'sass:color';`). Consider `color.scale(…)` for proportional darkening.
