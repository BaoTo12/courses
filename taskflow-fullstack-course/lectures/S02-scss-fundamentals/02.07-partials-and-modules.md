# Lecture 02.07 · Partials and Modules: `@use` vs the Deprecated `@import`

> **Section:** S02 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes

---

## 1. The problem: one giant stylesheet

A real design system has dozens of components. One file is unmanageable; many files need a way to **share** variables and mixins, and to **combine** into one CSS output. That's what Sass's module system does.

---

## 2. Partials

A **partial** is an SCSS file whose name starts with `_`:

```text
styles/components/_button.scss
```

The underscore tells Sass: "don't compile this file on its own; it's meant to be loaded by another file". When loading, you omit both the underscore and the extension:

```scss
@use 'components/button';     // finds components/_button.scss
```

---

## 3. `@use`: the modern module system

### What `@use` does

```scss
// _variables.scss
$color-primary: #4f46e5;
$-internal-ratio: 1.25;          // leading - or _ = PRIVATE to this module

// _button.scss
@use '../abstracts/variables';

.btn { background: variables.$color-primary; }
```

When Sass sees `@use 'x'`, it:

1. **Loads the module once** per compilation, however many files `@use` it. Its CSS output (if any) is included once.
2. **Exposes its members** (variables, mixins, functions) under a **namespace**, by default the last part of the path (`variables`).
3. Makes them available **only in the file that wrote the `@use`**. Not globally.

### Namespaces

```scss
@use '../abstracts/variables';            // variables.$color-primary
@use '../abstracts/variables' as v;       // v.$color-primary
@use '../abstracts/variables' as *;       // $color-primary (no namespace)
```

- Namespaces tell you **where a name comes from** and prevent collisions (two modules can both have `$size`).
- `as *` is convenient for a **design-token module** you use everywhere. Avoid it for many modules at once (collisions, unclear origins).

In TaskFlow we'll use `as *` for tokens and mixins (from S03, via one `abstracts` index), and namespaces for built-in modules (`math.div`, `color.adjust`).

### Private members

Names starting with `-` or `_` (e.g. `$-internal-ratio`) **can't be used outside** their module. That gives a library a public API and hidden internals.

### Configuration with `with`

```scss
// _variables.scss
$radius-md: 6px !default;

// main.scss
@use 'abstracts/variables' with ($radius-md: 4px);
```

Only `!default` variables can be configured, and only on the **first** `@use` of that module.

### Rules

- `@use` must come **before** any other rules in the file (except `@forward` and variable declarations used for configuration).
- **Members are not global.** If `_button.scss` needs `$color-primary`, `_button.scss` must `@use` the variables module itself, even if `main.scss` already did. This is the #1 surprise when moving from `@import` (Lecture 02.12).

---

## 4. `@import`: the old way, and why it's deprecated

```scss
// OLD
@import 'variables';
@import 'button';
```

`@import` (Sass's version, not CSS's) literally **pasted** the file in, and everything became **global**:

| Problem with `@import` | Consequence |
|---|---|
| Everything global | Any file could use any variable, so dependencies were invisible; name collisions overwrote silently. |
| Loaded every time it's imported | Import a file 3 times → its CSS is output 3 times (bloat, duplicates). |
| Order-dependent | A partial worked only if something imported variables *before* it. Reorder imports and everything breaks. |
| No privacy | Libraries couldn't hide internals. |

Dart Sass has **deprecated `@import`** (since 1.80, with removal planned for Dart Sass 3.0), along with global built-in functions like `darken()` (use `sass:color` instead, Lecture 02.08). You'll still see `@import` in older codebases, including at work, so you need to *read* it. New code uses `@use`.

> 🔎 **How to tell:** if an old codebase has one `_variables.scss` and nothing ever imports it except `main.scss`, it relies on `@import` making everything global. Migrating means adding `@use` to each partial that needs it. (There's an official migrator: `npx sass-migrator module --migrate-deps main.scss`.)

---

## 5. `@use` vs CSS's `@import url(...)`

Don't confuse them:
- **Sass `@use` / `@import 'file'`** → resolved **at compile time**; output is one CSS file.
- **CSS `@import url('file.css')`** → resolved **by the browser at runtime**; extra HTTP request.

Sass leaves plain CSS imports (with `url()`, `.css` extension or media queries) untouched in the output.

---

## 6. Where TaskFlow is heading

In S02, `main.scss` `@use`s each partial directly, and each partial `@use`s `abstracts/variables`. In S03 you'll add `abstracts/_index.scss` that **`@forward`s** variables, mixins and functions, so every partial writes a single line:

```scss
@use '../abstracts' as *;
```

---

## 7. Summary

- Partials start with `_`; load them without `_` or extension.
- `@use` loads a module **once**, exposes members under a **namespace**, and **only in that file**.
- `as *` removes the namespace (good for a token module); `-private` members stay hidden; `with (...)` configures `!default` variables.
- `@import` is **deprecated**: global, duplicate output, order-dependent. Read it; don't write it.

---

## 8. Check yourself

1. `main.scss` has `@use 'abstracts/variables' as *;` then `@use 'components/button';`. `_button.scss` uses `$color-primary` without its own `@use`. What happens?
2. Three components `@use` `_variables.scss`, which contains a `:root { … }` rule. How many times does that rule appear in the CSS?
3. Why can't `_button.scss` read `$-internal-ratio` from `_variables.scss`?

<details>
<summary>Answers</summary>

1. **Compile error: "Undefined variable."** `@use` makes members available only in the file that wrote it; `main.scss`'s `@use` doesn't leak into `_button.scss`.
2. **Once.** A module is evaluated and output once per compilation, regardless of how many files `@use` it. (With `@import` it would appear three times.)
3. Names starting with `-` or `_` are **private** to their module.

</details>
