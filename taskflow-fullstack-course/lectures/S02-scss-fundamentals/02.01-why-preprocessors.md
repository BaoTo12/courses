## 1. The problem: plain CSS at scale

Here's a realistic excerpt of plain CSS after a few months of a project like TaskFlow:

```css
.btn-primary { background: #4f46e5; border-radius: 6px; padding: 8px 16px; }
.btn-primary:hover { background: #4338ca; }
.link { color: #4f46e5; }
.badge-in-progress { background: #fef3c7; color: #92400e; border-radius: 6px; padding: 2px 8px; }
.card { border-radius: 8px; padding: 16px; box-shadow: 0 1px 3px rgba(0,0,0,.1); }
.card .card-title { font-size: 18px; }
.card .card-title a { color: #4f46e5; }
.card .card-title a:hover { color: #4338ca; }
@media (min-width: 768px) { .task-grid { grid-template-columns: repeat(2, 1fr); } }
@media (min-width: 768px) { .sidebar { display: block; } }
```

What's wrong?

| Problem | Where you see it |
|---|---|
| **Repetition / magic numbers** | `#4f46e5` appears four times. Change the brand colour and you'll miss one. `6px` vs `8px` radius: intentional or accident? |
| **No relationships** | `#4338ca` is "primary, a bit darker", but nothing in the code says so. |
| **Repeated selectors** | `.card .card-title …` is typed again and again. |
| **Repeated media queries** | `min-width: 768px` is a magic breakpoint copied everywhere. |
| **No modules** | One giant file, or many files glued by `@import url()` (which makes extra HTTP requests in plain CSS). |
| **No logic** | You can't generate `.badge--todo`, `.badge--done`… from a list. You write each by hand. |

None of this is a disaster in a 200-line stylesheet. In a 20,000-line stylesheet maintained by a team, it's a constant source of inconsistency and bugs.

## 2. What a preprocessor does

A **CSS preprocessor** is a language that *compiles to CSS*. You write in a richer language with variables, nesting, modules, functions and loops; a compiler turns it into plain CSS that browsers understand.

```text
  styles/*.scss  ──(Sass compiler, on YOUR machine, at build time)──▶  main.css  ──▶ browser
```

The browser never knows Sass existed. That's the central idea of this section, and it comes back in almost every section:

> 🧠 **Compile time vs runtime.** Sass features exist only while compiling. Anything that must change *while the page is running* (like a user switching to dark mode) needs a runtime mechanism: CSS custom properties, classes toggled by JavaScript, or styled-components.

---

## 3. The main preprocessors, and why Sass

| Tool | Status |
|---|---|
| **Sass (SCSS syntax)** | The industry standard; actively developed (Dart Sass). What most companies use, including many teams that also use styled-components. |
| Less | Still around in older projects (e.g. older Bootstrap), much less active |
| Stylus | Rare today |
| PostCSS | Not a language but a *plugin pipeline* for CSS (autoprefixer, future syntax). Often used *alongside* Sass (Vite uses it automatically for prefixes). |

## 4. Doesn't modern CSS make Sass unnecessary?

Modern CSS has caught up a lot: **custom properties** (`--color-primary`), native **nesting**, `color-mix()`, `@layer`, container queries. We'll use custom properties heavily (S03).

But Sass still adds real value:
- **Modules** (`@use`/`@forward`) with namespaces and private members, compiled into *one* CSS file.
- **Maps, loops and functions**: generate variants from data (`@each $status in $statuses`).
- **Mixins**: reusable blocks with parameters (`@include respond-to(md)`).
- **Compile-time errors**: `@error "Unknown breakpoint: #{$name}"` fails the build instead of silently shipping broken CSS.

Lecture 03.17 revisits this in more depth once you know what both offer.

## 5. SCSS vs Sass syntax

Sass has two syntaxes:

```scss
// SCSS (.scss): a superset of CSS. Every valid CSS file is valid SCSS.
.btn {
  color: $primary;
  &:hover { color: $primary-dark; }
}
```

```sass
// Indented syntax (.sass): no braces or semicolons, indentation-based
.btn
  color: $primary
  &:hover
    color: $primary-dark
```

We use **SCSS**. It's what almost every team uses, and you can paste any CSS into it.

---

## 7. Summary

- Plain CSS at scale suffers from repetition, magic numbers, no modules and no logic.
- A preprocessor compiles a richer language into CSS **at build time**. Browsers only see CSS.
- Sass/SCSS is the standard; SCSS syntax is a superset of CSS.
- Sass adds modules, maps, loops, mixins, functions and compile-time errors on top of modern CSS.
