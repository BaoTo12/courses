# Lecture 02.04 · Variables: Sass Variables vs CSS Custom Properties

> **Section:** S02 · **Type:** 📖 Theory + small build · **Track:** ★ Core · **Time:** ~25 minutes
> **Project feature:** `styles/abstracts/_variables.scss`: TaskFlow's first design tokens

---

## 1. The problem

`#4f46e5` appears in 20 places. The designer changes the brand colour. You search-and-replace and miss the one written as `#4F46E5`, and another written as `rgb(79, 70, 229)`. Now the UI is subtly inconsistent.

Variables give each design decision **one name** and **one place**.

---

## 2. Sass variables

```scss
$color-primary: #4f46e5;
$radius-md: 6px;
$space-4: 16px;

.btn {
  background: $color-primary;
  border-radius: $radius-md;
  padding: $space-4 * 0.5 $space-4;   // 8px 16px
}
```

Compiled:

```css
.btn {
  background: #4f46e5;
  border-radius: 6px;
  padding: 8px 16px;
}
```

### What happens internally

At compile time Sass keeps a table of variable names → values. When it evaluates `$color-primary`, it **substitutes the value**. After compilation, there is no variable anymore; the literal `#4f46e5` is written into every place it was used.

### Scope

```scss
$gap: 8px;             // module-level (visible in this file, and to files that @use it)

.card {
  $gap: 16px;          // LOCAL to this block. Shadows the outer $gap here only.
  padding: $gap;       // 16px
}

.list {
  gap: $gap;           // 8px: the outer one is unchanged
}
```

Local variables inside blocks don't leak. (There's a `!global` flag to assign a module-level variable from inside a block; you'll almost never need it, and it's usually a smell.)

### `!default`: configurable defaults

```scss
// in a library partial
$radius-md: 6px !default;   // "use 6px unless someone configured another value"
```

`!default` only assigns if the variable is not already defined. It's how libraries let you configure them with `@use 'lib' with ($radius-md: 4px)` (Lecture 02.07).

## 3. CSS custom properties (a.k.a. CSS variables)

```css
:root {
  --color-primary: #4f46e5;
}
.btn {
  background: var(--color-primary);
}
```

These look similar but are a **completely different thing**:

| | Sass variable `$x` | CSS custom property `--x` |
|---|---|---|
| Exists when? | **Compile time only** | **Runtime**, in the browser |
| In compiled CSS? | No (replaced by its value) | **Yes**, kept as-is |
| Can JavaScript read/change it? | No | **Yes**: `element.style.setProperty('--x', …)` |
| Cascades / inherits through the DOM? | No | **Yes**: can differ per element subtree (e.g. `[data-theme=dark]`) |
| Can be used in Sass math/functions at compile time? | Yes | No (the value isn't known yet) |
| Media query conditions? | Yes (`@media (min-width: $bp-md)`) | **No** (`var()` doesn't work in media query conditions) |

> 🧠 **Mental model:** a Sass variable is a **find-and-replace done by the compiler**. A custom property is a **live value the browser looks up** every time it computes styles.

---

## 4. Which one when? (The nine-question summary)

- **Use Sass variables** for values fixed at build time: breakpoints, the spacing scale, values used in Sass calculations, anything used in media queries.
- **Use custom properties** for values that must change **at runtime**: themes (light/dark), user preferences, values that differ per component subtree, values JavaScript or styled-components should read.
- **The professional pattern (S03):** define the design tokens once in Sass (maps), then **emit** them as custom properties:

```scss
$color-primary: #4f46e5;

:root {
  --color-primary: #{$color-primary};   // interpolation #{} writes the Sass value into CSS
}
```

You get compile-time structure *and* runtime flexibility. That's the bridge that lets React/styled-components and the JSP portal share one theme (S10, S32).

## 5. 🛠 Build: TaskFlow's first tokens

Create `styles/abstracts/_variables.scss`:

```scss
// ─── Colour palette ───────────────────────────────────────────
$color-primary: #4f46e5;       // indigo 600
$color-primary-dark: #4338ca;  // indigo 700
$color-danger: #dc2626;        // red 600
$color-danger-dark: #b91c1c;

$color-text: #0f172a;          // slate 900
$color-text-muted: #64748b;    // slate 500
$color-border: #e2e8f0;        // slate 200
$color-surface: #ffffff;
$color-background: #f8fafc;    // slate 50

// Status (TaskStatus)
$color-status-todo-bg: #e0e7ff;
$color-status-todo-fg: #3730a3;
$color-status-in-progress-bg: #fef3c7;
$color-status-in-progress-fg: #92400e;
$color-status-done-bg: #dcfce7;
$color-status-done-fg: #166534;

// Priority
$color-priority-low: #14b8a6;
$color-priority-medium: #f59e0b;
$color-priority-high: #ef4444;

// ─── Spacing scale (4px base) ─────────────────────────────────
$space-1: 4px;
$space-2: 8px;
$space-3: 12px;
$space-4: 16px;
$space-6: 24px;
$space-8: 32px;

// ─── Radius, shadow, typography ───────────────────────────────
$radius-sm: 4px;
$radius-md: 6px;
$radius-lg: 8px;
$radius-full: 999px;

$shadow-sm: 0 1px 2px rgba(15, 23, 42, 0.06);
$shadow-md: 0 1px 3px rgba(15, 23, 42, 0.1), 0 1px 2px rgba(15, 23, 42, 0.06);

$font-family-base: system-ui, -apple-system, 'Segoe UI', Roboto, sans-serif;
$font-size-sm: 0.875rem;
$font-size-base: 1rem;
$font-size-lg: 1.125rem;
$font-size-xl: 1.5rem;
$font-weight-medium: 500;
$font-weight-semibold: 600;

// ─── Breakpoints ──────────────────────────────────────────────
$bp-md: 768px;
$bp-lg: 1024px;
```

(Yes, the status colours are separate variables for now. That's tedious, and deliberately so: in S03 you'll turn them into a **map** and generate the badge classes with a loop. Feeling the pain first makes the solution meaningful.)

Use them in `main.scss`:

```scss
@use 'base/reset';
@use 'abstracts/variables' as *;

body {
  font-family: $font-family-base;
  background: $color-background;
  color: $color-text;
}
```

`as *` means "bring the variables in without a namespace", so you can write `$color-text` instead of `variables.$color-text`. Lecture 02.07 explains namespaces and when `as *` is appropriate.

Save → compile → refresh. The page should look the same as before, but now it's driven by tokens.

## 6. Common mistakes

> ⚠️ **Trying to change a Sass variable at runtime.** `document.documentElement.style.setProperty('$color-primary', 'red')` does nothing. There's no such property in the CSS.

> ⚠️ **Forgetting interpolation when emitting custom properties.** `--color-primary: $color-primary;` compiles to exactly that text (Sass treats custom property values as mostly literal). Use `#{$color-primary}`.

> ⚠️ **Naming by value instead of purpose.** `$indigo` tells you what it is, not what it's for. `$color-primary` survives a rebrand.

---

## 7. Summary

- Sass variables = **compile-time** find-and-replace; scoped; `!default` for configurable defaults.
- CSS custom properties = **runtime** values that cascade and can be changed by JS.
- Build-time constants (breakpoints, scales) → Sass. Runtime-switchable values (themes) → custom properties, usually **emitted from Sass tokens**.
- TaskFlow now has `abstracts/_variables.scss`.

## 8. Check yourself

1. Can JavaScript change `$color-primary` after the page loads? What would you use instead?
2. What does `--brand: #{$color-primary};` compile to if `$color-primary: #4f46e5`?
3. Why can't you write `@media (min-width: var(--bp-md))`?

<details>
<summary>Answers</summary>

1. No. It doesn't exist at runtime. Use a CSS custom property (`--color-primary`) and change it via a class/attribute (`[data-theme=dark]`) or `style.setProperty`.
2. `--brand: #4f46e5;`
3. Media query conditions are evaluated outside the element cascade; `var()` isn't allowed there. Use a Sass variable for breakpoints.
