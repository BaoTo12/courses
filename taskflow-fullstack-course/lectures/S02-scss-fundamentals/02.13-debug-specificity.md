# Lecture 02.13 · 🐞 Debug: "My Hover Style Doesn't Apply": Specificity After Nesting

> **Section:** S02 · **Type:** 🐞 Debug · **Track:** ＋ Extended · **Time:** ~15 minutes

---

## Symptom

A developer wants task-title links in cards to turn **red** when the task is overdue. They add a utility class:

```scss
// styles/utilities/_text.scss
.text-danger {
  color: $color-danger;
}
```

and in the HTML:

```html
<h3 class="card__title"><a href="#" class="text-danger">Fix login redirect bug</a></h3>
```

The link stays the **default text colour**, not red. They try hovering: it turns primary blue, never red.

Meanwhile, somewhere in the card styles, an earlier developer wrote:

```scss
.page {
  .page__main {
    .card {
      .card__title {
        a {
          color: inherit;
          &:hover { color: $color-primary; }
        }
      }
    }
  }
}
```

---

## Investigation checklist

1. In DevTools → Elements, select the link. In **Styles**, is `.text-danger` listed? Is its `color` **crossed out**?
2. Which rule wins, and what's its full selector?
3. Compute the specificity of both selectors.
4. Can you fix it **without** `!important` and without making `.text-danger` longer?

---

## Explanation

**Cause.** The nested SCSS compiles to:

```css
.page .page__main .card .card__title a { color: inherit; }            /* (0,4,1) */
.page .page__main .card .card__title a:hover { color: #4f46e5; }      /* (0,5,1) */
```

versus:

```css
.text-danger { color: #dc2626; }                                      /* (0,1,0) */
```

(0,4,1) beats (0,1,0), regardless of source order. DevTools shows `.text-danger`'s `color` **crossed out**, which is the visual signature of a specificity loss.

**The tempting wrong fixes:**
- `color: $color-danger !important;` → works today, starts an arms race (the next override needs `!important` too, and then only a *more specific* `!important` can win).
- `.page .page__main .card .card__title a.text-danger` → matches the specificity, couples a utility to one HTML structure, and makes the problem worse.

**The right fix:** remove the unnecessary nesting at the source. Nothing about link colour depends on being inside `.page__main`:

```scss
.card {
  &__title a {
    color: inherit;
    &:hover { color: $color-primary; }
  }
}
```

compiles to `.card__title a` (0,1,1) and `.card__title a:hover` (0,2,1).

Now `.text-danger` (0,1,0)… **still loses** to (0,1,1), because an element selector adds (0,0,1). Two clean options:

1. **Style the link through a class** instead of the `a` element: `&__title-link` → `.card__title-link` (0,1,0). Then `.text-danger` wins if it comes **later in the output**, so put utilities last in `main.scss` (a common convention: utilities are the final layer).
2. **Use a modifier** instead of a utility: `.card__title--overdue a { color: $color-danger; }`. Modifiers belong to the component and are designed to override its defaults.

Option 2 is usually the better design: "overdue" is a *state of the card*, not a random colour. Utilities are best for layout helpers and genuinely generic tweaks.

---

## Takeaways

- A crossed-out declaration in DevTools = it lost the cascade. Hover the selector to see its specificity (Chrome shows it in a tooltip).
- Deep nesting silently inflates specificity. Keep selectors to one or two classes.
- Put utilities last, and prefer component modifiers for component states.
- `!important` in component code is a sign that the specificity design has failed. Fix the design instead.
