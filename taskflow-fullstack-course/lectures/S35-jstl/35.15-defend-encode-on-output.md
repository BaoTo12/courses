# Lecture 35.15 · 🛡 Defend: Encode at Render Time; Why "Sanitise on Input" Alone Fails

> **Section:** S35 · **Type:** 🛡 Defend · **Track:** ★ Core · **Time:** ~25 minutes
> Verified: `S35JstlTest.storedXssInACommentIsRenderedAsText` (`<img src=x onerror=alert('stored')>` is stored as typed and rendered as `&lt;img src=x onerror=alert(&#039;stored&#039;)&gt;`)

---

## 1. The fix

```jsp
<td class="comment__body"><c:out value="${item.comment.body}"/></td>
```

The payload is saved unchanged, and every render turns it into text:

```html
<td class="comment__body">&lt;img src=x onerror=alert(&#039;stored&#039;)&gt;</td>
```

The comment shows exactly what the attacker typed, and nothing runs.

## 2. "Why not just strip `<script>` when saving?"

It's the first idea everyone has. Here's why it isn't enough on its own:

| Problem | Example |
|---|---|
| **The output context isn't known when saving** | the same comment goes into HTML (escape `<`), an attribute (escape `"`), a JSON API (escape `"` and `\`, S46), a CSV export (`=cmd…` formula injection), an email subject. No single input filter is right for all of them |
| **Blacklists are always incomplete** | strip `<script>` → `<img onerror>`, `<svg onload>`, `<scr<script>ipt>`, `javascript:` URLs, encoded variants… |
| **Other entry points** | the JSON API (S46), bulk imports, a DB migration, an older version of the app: data that never went through *this* filter |
| **It damages legitimate data** | "Use a < b when sorting" loses text; "O'Brien" gets mangled |
| **Mistakes are permanent** | a filter bug stores bad data forever. An output-encoding bug is fixed by redeploying |
| **Double encoding** | encode on input **and** on output → `&amp;lt;` shows on screen, and someone "fixes" it with `escapeXml="false"`… |

## 3. The rule

```text
INPUT:   validate SHAPE (type, length, allowed values) → store data RAW
OUTPUT:  encode for the CONTEXT, every time, at the last moment (<c:out>, fn:escapeXml, <c:url>/<c:param>)
```

TaskFlow's `TaskCommentServlet` validates length and blankness, and nothing else. The views encode.

## 4. When sanitising *is* right

When users are **supposed** to write HTML (rich-text comments), you can't escape it: you must allow some tags. Then use an **allow-list sanitiser** on output (or on input *and* output):
- in the browser: DOMPurify (26.04);
- in Java: the OWASP Java HTML Sanitizer, with a policy such as `Sanitizers.FORMATTING.and(Sanitizers.LINKS)`.

Even then, it's an allow-list of what's safe, never a block-list of what's dangerous.

## 5. Defence in depth (later sections)

- **Content-Security-Policy** without `'unsafe-inline'` (S42): even an injected `onerror` wouldn't run. It's the second lock, not the first.
- `HttpOnly` session cookie (28.04): limits what a script can steal.

## ✅ Takeaways

- Store what users typed. Encode it where it's printed, for that context.
- Input validation is about shape and business rules, not about HTML.
- Allow-list sanitising only when HTML is a feature.
