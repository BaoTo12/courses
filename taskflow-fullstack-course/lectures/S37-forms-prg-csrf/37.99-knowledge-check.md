# Lecture 37.99 · ✅ Knowledge Check: Forms, PRG and CSRF

> **Section:** S37 · **Type:** ✅ Knowledge Check · **Track:** ★ Core · **Time:** ~20 minutes

---

**1. (Concept)** On validation failure, forward or redirect? On success? Why the difference?

<details><summary>Answer</summary>

Failure → **forward** with 400: the errors and the typed values are request attributes, which only live in this request, and nothing was saved, so Reload is harmless. Success → **redirect** (303): the next page comes from a GET, so Reload/Back don't repeat the POST (37.05, 37.08).
</details>

**2. (Code reading)** Trace every request (method, URL, status): open the form → submit it invalid → fix it → submit valid → Reload.

<details><summary>Answer</summary>

1. `GET /taskflow/tasks/new` → 200 (form; a session and token are created).
2. `POST /taskflow/tasks/new` → 400 (the same form, with errors and the typed values).
3. `POST /taskflow/tasks/new` → 303, `Location: /taskflow/tasks/view?id=N`.
4. `GET /taskflow/tasks/view?id=N` → 200, "Task created." (flash consumed).
5. Reload → `GET /taskflow/tasks/view?id=N` → 200, no flash, no second task.
</details>

**3. (Debugging)** A hidden `ownerId` field in the form lets users create tasks for others. Where's the flaw?

<details><summary>Answer</summary>

The server **trusts** a value from the request for a security-relevant field: mass assignment (37.11). Hidden fields are as editable as any other. The owner must come from the server's state (the session's user, S41). The form object shouldn't even read `ownerId`.
</details>

**4. (Design)** Why must delete never be a GET link, even with a confirm dialog?

<details><summary>Answer</summary>

GET must be safe (29.03): links are prefetched, crawled, logged, shared, and triggered by `<img>` tags on any site, and none of these goes through your confirm dialog. The dialog is UX, not protection. Deletion must be a POST (with a CSRF token) (37.02, 37.12).
</details>

**5. (Concept)** Why does a CSRF token stop the attack when the session cookie doesn't?

<details><summary>Answer</summary>

The browser attaches cookies to every request to TaskFlow, whichever site triggered it: the cookie proves the browser, not the page. The token is only found **inside** TaskFlow's pages, and other sites can't read those (same-origin policy), so a forged request can't include it (37.13).
</details>

**6. (Implementation)** An "Undo delete" link in the flash after deleting a task. What state is needed?

<details><summary>Answer</summary>

Options: a **soft delete** (a `deleted_at` column; the flash offers a POST form "Undo" → clear `deleted_at`; a job purges old rows later), or a snapshot of the deleted task (and its comments) kept server-side with a one-time id in the session, re-inserted on undo. Either way, the undo is a **POST with a CSRF token**, not a GET link. The flash then holds structured data (message + undo id), not just text. Soft delete is simpler and also survives multiple tabs.
</details>
