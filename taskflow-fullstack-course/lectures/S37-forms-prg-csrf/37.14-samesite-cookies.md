# Lecture 37.14 · SameSite Cookies: a Second Layer, Not the Only One

> **Section:** S37 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes

---

## 1. What `SameSite` does (24.02)

| Value | The cookie is sent on… | CSRF effect |
|---|---|---|
| `Strict` | same-site requests only, not even when following a link from elsewhere | blocks cross-site POSTs **and** GETs; users arriving from an email link look logged out |
| `Lax` (browsers' default when unset) | same-site requests + top-level **GET** navigations from other sites | blocks cross-site POST forms, `fetch`, images… |
| `None; Secure` | everything | none |

With `Lax`, the forged POST of 37.12 arrives **without** the session cookie → TaskFlow sees an anonymous request.

## 2. Setting it on Tomcat 9

Tomcat doesn't add `SameSite` to `JSESSIONID` by default. It's configured on the cookie processor, in `META-INF/context.xml` (S41, 41.12):

```xml
<Context>
  <CookieProcessor sameSiteCookies="lax"/>
</Context>
```

## 3. Why the token stays

| Limit of SameSite | Example |
|---|---|
| "site" ≠ "origin" | `evil.example.com` and `taskflow.example.com` are the **same site**: a compromised or user-content subdomain is inside the wall |
| `Lax` still sends cookies on top-level GETs | any state change reachable by GET is still exposed (another reason for 37.02) |
| older browsers and embedded webviews | may ignore it |
| the default can differ | browsers applied `Lax` by default at different times; don't rely on defaults for security |

The token protects regardless of any of these. `SameSite` makes a missed token check much less dangerous. That's defence in depth, like 36.10.

## ✅ Recap

`SameSite=Lax` stops browsers sending the session cookie on cross-site POSTs: an excellent second layer. The synchroniser token remains the defence you control.
