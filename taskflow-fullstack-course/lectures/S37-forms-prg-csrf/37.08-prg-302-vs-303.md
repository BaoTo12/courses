# Lecture 37.08 · PRG (Post/Redirect/Get): Why Redirect After Success; 302 vs 303

> **Section:** S37 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> Verified: `S37FormsTest` (create, edit, delete → `303` + `Location`), and S31/S33/S35's tests, updated from `302` to `303`

---

## 1. The pattern

```text
① POST /taskflow/tasks/new  title=…        → 303 See Other   Location: /taskflow/tasks/view?id=31
② GET  /taskflow/tasks/view?id=31          → 200  the task, "Task created."
   URL bar: /tasks/view?id=31 · Reload repeats ② (a GET): harmless · Back skips over the POST
```

## 📇 API card: `Http.seeOther` (TaskFlow) vs `sendRedirect`

✍️ `src/main/java/com/taskflow/web/Http.java`

```java
package com.taskflow.web;

import javax.servlet.http.HttpServletResponse;

/** S37 (37.08): small HTTP helpers for controllers. */
public final class Http {

  private Http() {}

  /**
   * 303 See Other: "done; now GET the result over there". The status made for Post/Redirect/Get: unlike 302,
   * its meaning is unambiguous, so the next request is always a GET, whatever the first method was.
   */
  public static void seeOther(HttpServletResponse response, String location) {
    response.setStatus(HttpServletResponse.SC_SEE_OTHER);
    response.setHeader("Location", location);
  }
}
```

| | `response.sendRedirect(url)` | `Http.seeOther(response, url)` |
|---|---|---|
| status | **302 Found** | **303 See Other** |
| relative URLs | resolved by Tomcat | must be absolute or root-relative (TaskFlow always passes `ctx + "/…"`) |
| commits the response | yes | not until the response is written (nothing more is written, so the effect is the same) |

## 2. 302 vs 303 vs 307

| Status | After a POST, the browser's next request is… | Meaning |
|---|---|---|
| **302 Found** | a GET in practice (every browser), but the spec historically said "the same method" | "temporarily elsewhere": ambiguous |
| **303 See Other** | always a **GET** | "done; see the result over there": exactly PRG |
| 307 Temporary Redirect | the **same** method and body (POST again) | "repeat this request there": never for PRG |

Browsers treat 302 like 303 after a form POST, so S31's 302 worked. 303 **says** what we mean, and HTTP clients other than browsers (scripts, the JSON API's consumers) follow it correctly. That's why the tests assert 303 now.

## 3. When NOT to redirect

- **Validation failed** → forward with 400 (37.05): the errors and the typed values live in the request.
- **A pure read** (GET) → just render.

## ✅ Recap

Successful POST → 303 → GET the result. The page the user sees comes from a GET, so Reload, Back and bookmarks behave.
