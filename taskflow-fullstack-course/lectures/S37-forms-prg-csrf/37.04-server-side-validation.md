# Lecture 37.04 · Server-Side Validation: Never Trust the Client

> **Section:** S37 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> Verified: `S37FormsTest.invalidInputComesBackWithErrorsAndTheUsersValues`, `.aDuplicateTitleIsAFormErrorNotA500`

---

## 1. The browser's checks are UX

`required`, `maxlength="120"`, `type="date"`, a `<select>` with three options: the browser enforces them for **honest** users. Anyone can bypass them with DevTools, `curl`, or a script. The test sends `priority=URGENT`, `dueDate=2026-02-30` and `categoryId=999`, none of which the form's controls could produce.

## 2. What to check, in what order

| Check | TaskFlow field | Rule |
|---|---|---|
| **presence** | title | not blank after trimming |
| **length** | title ≤ 120, description ≤ 2000 | = the column sizes (28.07): a longer value would fail in the database instead |
| **type/format** | dueDate | `LocalDate.parse` → `2026-02-30` is **not** a date |
| **allow-list** | priority | one of the enum's values (`Priority.parse`) |
| **reference** | categoryId | a positive number **and** an existing category |
| **business rule** | title unique per owner | enforced by the database's `UNIQUE` → `DuplicateKeyException` → a form error |

Collect **all** errors, not just the first: the user fixes everything in one go.

## 3. Where each kind of check lives

| Kind | Layer | Why |
|---|---|---|
| shape (present, length, parseable, allowed values) | the form object (`TaskForm.validate`) | it's about **this** form's input |
| rules about the data (unique title, "category in use", 37.15) | service / database | every entry point must obey them: the JSON API (S46) too |
| authorisation ("may this user edit this task?") | service + filter (S42) | never a form's job |

**Why the database's `UNIQUE` and not a "does it exist?" query first?** Two requests at the same moment could both see "no" and both insert. The constraint is the only check that can't race. The app translates its failure into a friendly message.

## 4. Error messages

Say what's expected ("must be a date (YYYY-MM-DD)"), not what went wrong internally ("DateTimeParseException"). Never echo SQL errors or stack traces to users (S43).

## ✅ Recap

Validate everything on the server: presence, length, format, allow-lists, references, then business rules. The browser's checks only make honest users' lives easier.
