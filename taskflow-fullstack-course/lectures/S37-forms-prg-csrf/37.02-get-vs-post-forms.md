# Lecture 37.02 · GET vs POST Forms: Search vs Create/Update/Delete

> **Section:** S37 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes

---

## 1. The rule

| Form | Method | Why |
|---|---|---|
| search, filters, sort (the list's form, 36.12) | **GET** | it **reads**; the result is shareable, bookmarkable, reloadable (`/tasks?q=report&sort=due`) |
| create, edit, delete, toggle, comment | **POST** | it **changes** data (29.03: GET must be *safe*) |

## 2. What goes wrong with a GET that changes data

| GET `/tasks/delete?id=7` is… | Consequence |
|---|---|
| prefetched by the browser or a link-preview bot | the task is deleted without anyone clicking |
| in history, logs, the `Referer` header | the "action" leaks and can be replayed |
| an `<img src="…/tasks/delete?id=7">` on any web page | deleted by every visitor's browser (the CSRF problem in its simplest form, 37.12) |

TaskFlow's delete, toggle and comment servlets implement **only** `doPost`: a GET gets `405 Method Not Allowed` (30.07), and `S37FormsTest` checks it.

## 3. And a POST that only reads?

It breaks Back/Reload ("Confirm form resubmission"), can't be bookmarked, and hides the search from the URL. Use GET for reads, even long filter forms.

## ✅ Recap

GET for forms that read (the URL is the result's address), POST for forms that change something. A confirm dialog doesn't make a GET delete safe: the request can be made without the dialog.
