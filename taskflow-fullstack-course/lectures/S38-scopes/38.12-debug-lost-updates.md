# Lecture 38.12 · 🐞 Debug: the Application-Scope Counter Is Wrong Under Load (Non-Atomic `++`)

> **Section:** S38 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~20 minutes

---

## 1. The code

A first version of the request counter:

```java
public class AppStats {
  private long requests;                       // ❌ a plain field in an application-scoped object
  public void requestStarted() { requests++; }
  public long getRequests() { return requests; }
}
```

## 2. Symptom

Fire 1 000 requests with 50 in parallel (a load tool, or 30.06's `curl` loop with `-P 50`). `/debug/stats` says **987**, a different number each time, always too low. With one request at a time it's always exact.

## 3. Why

`requests++` is three steps: **read** the value, **add** 1, **write** it back. Two threads interleave:

```text
thread A: read 41
thread B: read 41
thread A: write 42
thread B: write 42        ← one increment lost
```

On top of that, without `volatile` or synchronisation, another thread may not even **see** the latest value (the Java memory model allows caching in registers and CPU caches).

## 4. Fixes

| Fix | Notes |
|---|---|
| `LongAdder.increment()` / `sum()` | TaskFlow's choice for a hot counter: little contention |
| `AtomicLong.incrementAndGet()` | fine for moderate traffic; a compare-and-swap loop |
| `synchronized` methods | correct, but every request waits for the lock |
| `volatile long` + `++` | ❌ still broken: `volatile` fixes **visibility**, not the read-modify-write race |

The same applies to maps: `map.put(id, map.get(id) + 1)` on a `HashMap` loses updates **and** can corrupt the map; use `ConcurrentHashMap.computeIfAbsent(…).increment()` or `merge(id, 1L, Long::sum)`.

## ✅ Takeaway

Anything in application scope (and any servlet field, 30.05) is shared by all request threads. Use the atomic and concurrent types. A test with one request at a time will never show the bug.
