# Lecture 38.09 · 🛡 Sensitive Data and Scope

> **Section:** S38 · **Type:** 🛡 Defend · **Track:** ★ Core · **Time:** ~15 minutes

---

## 1. Rules

| Rule | Why |
|---|---|
| **Nothing user-specific in application scope** | every request of every user can read it (38.08, bug 1) |
| **Minimise the session** | sessions are serialised to disk at shutdown (`SESSIONS.ser`), copied between cluster nodes, and live for 30 min after the user leaves. Everything there can end up in files, other servers, and heap dumps |
| store **ids and display data**, not secrets | S41's session user: id, username, display name, role, and never the password or its hash |
| no credentials, tokens for other systems, or full documents in the session | if one is needed, keep it server-side, encrypted at rest, with a short lifetime |
| **debug pages** that show scopes are loopback-only | `/debug/el`, `/debug/stats`, `/debug/request-info` return 404 to other machines |
| `invalidate()` at logout, `changeSessionId()` at login | S41: no data survives a logout; a pre-login session id can't be reused |

## 2. Why "the hash is fine to keep" is wrong

A password hash is exactly what an attacker needs for an offline cracking attempt. A heap dump taken for a memory bug, a session file on a shared disk, or a debug page left on in production turns it into a leak. The user object in the session never needs it: the check happens once, at login, against the database.

## 3. What TaskFlow keeps in the session (`docs/scopes.md`)

The CSRF token, a flash message until shown, ≤ 5 recently viewed ids, and, from S41, the logged-in user's non-secret fields. That's all.

## ✅ Recap

Application scope is public to all users. The session is private but not secret: it's persisted and copied. Keep both minimal, and keep secrets out of both.
