<summary><b>Answers</b></summary>

1. On a link click: **nothing** for the navigation itself. React Router calls `history.pushState`, and React renders the new route (verified: 0 new navigation entries). Only data or lazy chunks may be requested. On **F5**: a full `GET /tasks/5` for the document. The server must answer with `index.html` (SPA fallback); otherwise 404.

2. (a) Path param, `/tasks/:id`: it **identifies** the resource. (b) and (c) Search params, `?sort=due&page=3`: they describe **how to view** the list. They're optional and combinable.

3. The guard runs in the user's browser, which the user controls. They can edit the auth state with React DevTools or a breakpoint, read the protected page's code from the bundle, or skip the UI and call the API with curl. Real protection: the **server** authenticates every request (a filter returning 401, S41) and authorizes every object access (ownership check, 403, S44).

4. An attacker crafts a link to the **real** site whose post-login redirect goes to **their** site (`?returnTo=https://taskf1ow.example`), borrowing the real domain's trust for phishing. We validate anyway because (a) `navigate()` throws instead of falling back, which leaves the user stuck with an error; (b) it doesn't protect `location.href`, `<a href>` or a server-side `sendRedirect`; (c) library behaviour can change. Defence in depth: validate with an allowlist where the value is used.

5. `navigate()` is called **during render**, which is a side effect in a pure function (07.04). React Router warns in development: *"You should call navigate() in a React.useEffect(), not when your component is first rendered."* It can run twice in StrictMode, and the page continues rendering with no user. Fix: `if (!user) return <Navigate to="/login" replace />;` (or wrap the route in `RequireAuth`).

6. Without `replace`: **6** new entries ("r", "re", … "report"), and Back steps through them letter by letter. With `replace`: **0** new entries. The current entry is updated each time.

7. `'/tasks?q=a'` → `'/tasks?q=a'`; `'//evil.example'` → `'/tasks'`; `'https://evil.example'` → `'/tasks'`; `/\evil.example` → `'/tasks'`; `null` → `'/tasks'`.

8. `lazy(…)` is called on **every render** of `App`, which creates a **new component type** each time. React sees a different type at the same position, unmounts the old subtree and mounts a new one (losing its state), and the new lazy component suspends again. Call `lazy` once at module top level.

9. A router hook or component (`<Routes>`) rendered with no `<BrowserRouter>` above it. TypeScript checks types, not the **runtime component tree**: whether a provider is an ancestor is only known when rendering. Fix: wrap the tree in `<BrowserRouter>` (in `main.tsx`).

10. Vite built with the default `base: '/'`, so the HTML references `/assets/…` from the site root, but the files are under `/app/assets/…`. Fix: build with `base: '/app/'`, and derive the router `basename` and data URLs from `import.meta.env.BASE_URL`.

11. In `EditTaskPage`'s save handler: `navigate(\`/tasks/${id}\`, { replace: true })` **without** `state: location.state`. The new history entry has no state, so `backToListHref` falls back to `/tasks`. (Also check that the details page's Edit link passes `state={location.state}`.)

12. The `Cache-Control` header on `index.html`. If it's cached (e.g. `max-age=3600`), browsers keep loading the old HTML, which names the old hashed assets. Serve `index.html` with `no-cache` and hashed assets with a long `immutable` cache.

13. **The URL.** It's shareable, it survives reload and Back/Forward, and it's a single source of truth: the component derives the filters from it. `useState` is lost on navigation and reload; a context is global for a per-view concern; `localStorage` is shared across tabs.

14. No. That makes task URLs non-canonical and leaks the list's filters into shared links. Alternative: **history state** (`<Link state={{ listSearch }}>`). Trade-off: it belongs to one history entry, so a new tab or a pasted link has no state (fall back to `/tasks`). And it must be validated, because it's `unknown` and survives reloads.

15. Lazy-load pages with heavy dependencies (charts, rich-text editors, date libraries) or that most users rarely open (admin, settings, reports). Don't split the main landing page or tiny pages. The extra request costs more than it saves. Measure the chunk sizes (`npm run build`) before and after.

16. Example:
    ```ts
    export function neighbours(tasks: readonly Task[], id: number): { prev: number | null; next: number | null } {
      const index = tasks.findIndex((t) => t.id === id);
      if (index === -1) return { prev: null, next: null };
      // noUncheckedIndexedAccess (on in our tsconfig): tasks[i] is Task | undefined, out of range → null
      return {
        prev: tasks[index - 1]?.id ?? null,
        next: tasks[index + 1]?.id ?? null,
      };
    }
    ```
    In the page: parse the remembered search (`new URLSearchParams(listSearch)`), validate `status` with `isTaskStatus`, compute `filterTasks(state.data, { status, q })`, then `neighbours(visible, task.id)`. Render `<Link to={\`/tasks/${prev}\`} state={location.state}>` so the state keeps travelling. Tests: middle item → both; first → `prev: null`; last → `next: null`; single → both null; unknown id → both null. (`tasks[-1]` is `undefined` in JavaScript, not the last element, so the first item correctly gets `prev: null`.)
