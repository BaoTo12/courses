# Lecture 12.12 · 🐞 Debug: Refreshing `/tasks/5` on a Static Server Gives 404

> **Section:** S12 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~30 minutes
> Every symptom below was reproduced with the reference app's production build and `http-server`.

---

## Symptom

A teammate deploys TaskFlow Web to a test server. They copy `dist/` into the server's `app/` folder, so the app lives at `http://test-server/app/`. They report three bugs:

1. "Opening `http://test-server/app/` shows a **blank page**."
2. After they "fixed" (1), "the list says **Failed to load tasks: HTTP 404**."
3. After they "fixed" (2), "clicking around works, but **refreshing** any page (e.g. `/app/tasks/5`) gives the server's **404** page."

And a fourth one, from a user: "4. After your fix I still see the old version."

Reproduce it yourself:

```bash
npm run build
```

```bash
mkdir -p ../site/app && cp -r dist/* ../site/app/
```

```bash
npx http-server ../site -p 5195
```

## Investigation checklist

1. For the blank page: open DevTools → **Network**. Which requests fail, and what URLs do they use?
2. Open `dist/index.html`. What do the `<script src>` and `<link href>` look like?
3. For "Failed to load tasks": which URL does `fetch-tasks.ts` request?
4. For the refresh 404: which **file** does the static server look for? (12.08)
5. For "still the old version": look at the `Cache-Control` response header of `index.html`.

## Explanation

### Bug 1: absolute asset URLs (Vite's `base`)

Verified: `dist/index.html` contained

```html
<script type="module" crossorigin src="/assets/index-gNEwgURu.js"></script>
```

`/assets/…` is relative to the **site root**, so the browser requested `http://localhost:5195/assets/index-….js` → **404**. The file is at `/app/assets/…` (which returned 200). No JavaScript loaded, so the page stayed blank.

**Fix:** tell Vite where the app will live, with the `base` option (in `vite.config.ts`, or on the command line):

```bash
npx vite build --base /app/
```

The generated URLs become `/app/assets/…`. `base` is also exposed to your code as `import.meta.env.BASE_URL` (`'/'` in dev, `'/app/'` here).

> 🪟 **Windows Git Bash trap (observed):** in Git Bash, `--base /app/` was silently rewritten to `C:/Program Files/Git/app/`, and the HTML referenced `src="/Program Files/Git/app/assets/…"`. Git Bash (MSYS) converts arguments that look like Unix paths. Run the command from PowerShell, or prefix it: `MSYS_NO_PATHCONV=1 npx vite build --base /app/`. Setting `base` in `vite.config.ts` avoids the problem entirely.

### Bug 2: an absolute `fetch` URL, and the router's `basename`

With `base` fixed, the app loaded but showed *"Failed to load tasks: HTTP 404"*. `fetch-tasks.ts` requested `'/db.json'`, a root-relative URL again. And even with the data fixed, the router would be wrong: without a basename, React Router sees the path `/app/tasks` and matches **no** route except `*`.

**Fix:** derive both from `BASE_URL`.

`src/data/fetch-tasks.ts`:

```ts
// BASE_URL ends with '/': '/db.json' in dev, '/app/db.json' under a sub-path (12.12)
const response = await fetch(`${import.meta.env.BASE_URL}db.json`, { signal });
```

`src/main.tsx`:

```tsx
{/* BASE_URL comes from Vite's `base` option: '/' in dev, '/<context>/app/' when deployed in S49 (12.12) */}
<BrowserRouter basename={import.meta.env.BASE_URL}>
```

Verified after rebuilding with `--base /app/`:
- `/app/` redirected to `/app/tasks`, and the 8 tasks loaded;
- the first card's link rendered as `href="/app/tasks/1"`: `<Link to="/tasks/1">` gets the basename **automatically**, so no component changed;
- the breadcrumb linked to `/app/tasks`.

In dev (`base` = `'/'`), everything behaves exactly as before. (From S13, API calls go through Axios with `baseURL: '/api'`. The API isn't part of the SPA's `base`; it's a separate path on the server.)

### Bug 3: no SPA fallback

`/app/tasks/5` isn't a file, so the static server returns 404 on a refresh or a pasted link (verified: 404). This is 12.08's lesson. Clicking works because client-side navigation never asks the server.

**Fix:** configure SPA fallback on the server (see 12.08 §3 for what "correct" means). On Tomcat, that's the `SpaFallbackFilter` in S49. For a quick local test, `vite preview --base /app/` does it for you (verified: `/app/tasks/5` → 200 `text/html`, `/app/db.json` → 200 `application/json`).

### Bug 4: `index.html` was cached for an hour

Verified: `http-server` sends `Cache-Control: max-age=3600` by default, for every file. After a new deploy, the browser kept using its cached `index.html`, which pointed at the **old** script (`index-BrB5nKLt.js`) for up to an hour, although the server already had a new one (`index-D7vPppnc.js`).

**Fix: the standard SPA caching rule.**

| File | Header | Why |
|---|---|---|
| `index.html` | `Cache-Control: no-cache` (always revalidate) | It's the entry point that names the current asset files. |
| `assets/*-<hash>.js/css` | `Cache-Control: public, max-age=31536000, immutable` | The hash changes whenever the content changes, so a file with a given name never changes. |

(`http-server -c-1` disables caching completely, which is fine for local testing. In S49 you'll set these headers in the Tomcat filter.)

## Lessons

- **"Works in dev, broken in prod" deployment bugs are usually about paths**: `base`, `basename`, absolute URLs in code, and the fallback.
- **Use one source of truth for the base path** (`import.meta.env.BASE_URL`) instead of hard-coding `/app` in several places.
- **Caching:** never cache `index.html` for long; cache hashed assets forever.
- **Read the Network tab first.** Every bug here was visible as one failing request.

## Related traps

- **Relative paths** such as `fetch('db.json')` seem to fix bug 2, but they're resolved against the **current URL**: on `/app/tasks/5` they request `/app/tasks/db.json`. Use `BASE_URL`, not relative paths.
- **`<a href="/tasks">`** (instead of `<Link>`) ignores the basename. That's one more reason to use `Link` (12.02 §6).
- **Setting `base: './'`** makes the asset URLs relative, which works for some static hosts but breaks on deep links (the same problem as the relative `fetch`). With client-side routing, prefer an absolute `base`.
