# Lecture 12.03 · Params (`useParams`) and Search Params (`useSearchParams`): the URL as State

> **Section:** S12 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes

---

## 1. Two places for data in a URL

```text
/tasks/5?status=DONE&q=report&view=board
       ↑  └────────── search params (query string) ──────────┘
   path param (:id)
```

| | Path params | Search params |
|---|---|---|
| Identify | **Which resource** (task 5) | **How to view** it (filters, sort, page, view mode) |
| Read with | `useParams()` | `useSearchParams()` |
| Required? | Part of the route pattern | Optional, any number |

## 2. `useParams`: strings (or undefined), always

```tsx
const { id: rawId } = useParams();   // string | undefined
```

Params are **strings** taken from the URL, which the **user controls** (they can type `/tasks/abc` or `/tasks/-1`). Parse and validate, as with form values (11.03) and request parameters on the server (S31):

```ts
/** Route params are strings (or undefined). A task id must be a positive integer. */
export function parseTaskId(raw: string | undefined): number | null {
  if (raw === undefined || !/^\d+$/.test(raw)) return null;
  const id = Number(raw);
  return Number.isSafeInteger(id) && id > 0 ? id : null;
}
```

`Number('abc')` is `NaN`, `Number('')` is `0`, and `Number('1e3')` is `1000`. The regex check first avoids all of those surprises.

## 3. `useSearchParams`: a `URLSearchParams` you can update

```tsx
const [searchParams, setSearchParams] = useSearchParams();
const rawStatus = searchParams.get('status');          // string | null
```

`setSearchParams` accepts a new `URLSearchParams` (or an updater function receiving the current one), plus navigate options:

```tsx
setSearchParams(
  (current) => {
    const next = new URLSearchParams(current);
    next.set('status', 'DONE');
    return next;
  },
  { replace: true },
);
```

Copying `current` keeps the **other** params (`q`, `view`) intact.

## 4. The URL as state: why put filters in the URL?

Before S12, the filter lived in `useState`. Moving it to the URL means:
- **Shareable**: a colleague opens exactly your filtered view.
- **Survives reload and Back/Forward.**
- **One source of truth**: the component *derives* the filter from the URL on every render; there's no `useState` to keep in sync.

It's the same principle as derived data (08.05): don't copy the URL into state; read it.

### `replace` vs `push`

Every `setSearchParams` call creates a history entry by default. Typing "report" letter by letter would add 6 entries, and Back would step through them one letter at a time. For **filter tweaks** use `{ replace: true }`, which updates the current entry. For **real navigations** (opening a task), push a new entry.

## 5. Validate search params like any input

```tsx
const rawStatus = searchParams.get('status');
const statusFilter: TaskStatus | null = isTaskStatus(rawStatus) ? rawStatus : null;
```

`/tasks?status=HACKED` just falls back to "All". The 06.08 type guard does the work again. (And never put a raw URL param into `dangerouslySetInnerHTML`, CSS or a redirect: S26, 10.10, 12.07.)

## 6. Summary

- Path params identify resources; search params describe views.
- Both are **strings from the user**: parse and validate.
- Filters in the URL are shareable and reload-safe, and the component derives them rather than storing them.
- Use `replace` for filter changes, push for navigations.
