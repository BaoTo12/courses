# Lecture 03.04 · 🛠 Build: `to-rem()` and `space($n)`

> **Section:** S03 · **Type:** 🛠 Build · **Track:** ★ Core · **Time:** ~20 minutes
> **Project feature:** `styles/abstracts/_functions.scss`

---

## 1. Why these two functions

**`to-rem()`.** Designers hand you pixel values (`18px` title). But `rem` units respect the user's browser font-size setting, which is an accessibility requirement: users with low vision increase the default font size, and `px`-based text ignores that. `to-rem(18px)` lets you think in pixels and ship accessible `rem`s.

**`space($n)`.** A **spacing scale** based on a 4px unit: `space(1)` = 4px, `space(4)` = 16px, `space(6)` = 24px. Instead of remembering `$space-1 … $space-8` variables (and inventing `$space-5` when you need it), you get a consistent scale from one rule.

---

## 2. ✍️ Update `_variables.scss`

Add configurable defaults (near the top of `styles/abstracts/_variables.scss`):

```scss
$base-font-size: 16px !default;
$space-unit: 4px !default;
```

`!default` makes them configurable via `@use … with (…)` (02.07), e.g. a denser admin theme could use `$space-unit: 3px`.

---

## 3. ✍️ Create `styles/abstracts/_functions.scss`

```scss
@use 'sass:math';
@use 'variables' as *;

/// Convert a px value to rem, relative to $base-font-size.
/// to-rem(18px) → 1.125rem
@function to-rem($px, $base: $base-font-size) {
  @if math.unit($px) != 'px' {
    @error 'to-rem() expects a px value, got #{$px}.';
  }
  @return math.div($px, $base) * 1rem;
}

/// Spacing scale: multiples of $space-unit.
/// space(4) → 16px, space(0.5) → 2px
@function space($n) {
  @return $n * $space-unit;
}
```

### Why each line

- **`math.unit($px) != 'px'`**: `to-rem(1.5rem)` or `to-rem(18)` are mistakes; fail loudly.
- **`math.div($px, $base) * 1rem`**: `18px / 16px` = `1.125` (unitless, since px cancels), times `1rem` = `1.125rem`.
- **`space($n)`** returns **px**. Why not rem? Spacing in px is a common, defensible choice (spacing often shouldn't scale with text size), but some teams use rem everywhere. It's a design decision; the function hides it, so switching later is a one-line change.

---

## 4. Use them

In a component, for example `_card.scss`:

```scss
@use '../abstracts/variables' as *;
@use '../abstracts/mixins' as *;
@use '../abstracts/functions' as *;

.card {
  gap: space(2);
  padding: space(4);
  padding-left: space(5);

  &__title {
    font-size: to-rem(18px);
    @include truncate(2);
  }
}
```

Compiled:

```css
.card { gap: 8px; padding: 16px; padding-left: 20px; }
.card__title { font-size: 1.125rem; /* + truncate declarations */ }
```

Three `@use` lines per component is now clearly too many. That's fixed in 03.10–03.11 with `@forward`.

### Try the guard rails

```scss
.x { font-size: to-rem(1.2rem); }
```

```text
Error: "to-rem() expects a px value, got 1.2rem."
  ╷
1 │ .x { font-size: to-rem(1.2rem); }
  │                 ^^^^^^^^^^^^^^
```

---

## 5. Migrating from `$space-N` variables

You don't need to rewrite everything at once. During 03.11's refactor, replace `$space-4` → `space(4)` as you touch each file. Keep the old variables until the last usage is gone, then delete them. That's how real design-system migrations are done: incrementally, with both APIs working for a while.

---

## 6. Summary

- `to-rem(px)` converts designer pixels into accessible `rem`s, with an `@error` guard.
- `space(n)` implements a 4px spacing scale from one configurable unit.
- `!default` on `$base-font-size` / `$space-unit` makes them configurable.
