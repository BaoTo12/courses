# Lecture 30.06 · 🛠 Build: Log Every Lifecycle Method; Observe with Several Tabs; `loadOnStartup`

> **Section:** S30 · **Type:** 🛠 Build · **Track:** ★ Core · **Time:** ~30 minutes

---

## 1. The logging already in `HelloServlet`

```java
@WebServlet(urlPatterns = "/hello", loadOnStartup = 1)
public class HelloServlet extends HttpServlet {
  private final AtomicLong requestCount = new AtomicLong();

  @Override public void init() throws ServletException { log("init(): HelloServlet created once, at deployment"); }
  … doGet prints "Request #N handled by <thread name>" …
  @Override public void destroy() { log("destroy(): the application is stopping; " + requestCount.get() + " requests served"); }
}
```

`log(…)` (from `GenericServlet`) writes to the **container's** log, with the servlet's name. In Tomcat that's `localhost.<date>.log` (the IDE and Docker consoles show it too).

## 2. Experiment

1. **Deploy** and watch the log: `HelloServlet: init(): HelloServlet created once, at deployment` appears **during deployment**, before any request, because of `loadOnStartup = 1`.
2. **Remove `loadOnStartup`**, redeploy: no `init` line. Request `/hello`, and now it appears, just before the first response.
3. **Open three tabs** and reload each a few times: the counter keeps rising **across tabs** (one shared object), and the thread names vary (`http-nio-8080-exec-3`, `…-exec-5`).
4. **Load test it** a little, to see concurrency:

   ```bash
   for i in $(seq 1 50); do curl -s http://localhost:8080/taskflow/hello > /dev/null & done; wait
   curl -s http://localhost:8080/taskflow/hello | grep Request      # Request #52 (or so): no lost updates, thanks to AtomicLong
   ```

   Replace `AtomicLong` with a `long` and `count++`, run it a few times, and you'll sometimes see fewer than 51: lost updates.
5. **Stop or undeploy** the app: `destroy(): … N requests served` appears.

## 3. What to take away

| Observation | Explains |
|---|---|
| one `init` line, however many requests | one instance (30.05) |
| many thread names | the connector's pool (30.03) |
| the counter shared across tabs and users | fields are **application-wide** state, not per-user |
| `destroy` at undeploy | where to release resources (S36: closing the connection pool) |

## ✅ Checkpoint

You can predict, before looking at the log, when `init` and `destroy` will run in each experiment.
