# Lecture 18.04 · The Real `redux-thunk` Source; `withExtraArgument` (Injecting the API Client)

> **Section:** S18 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> 🔗 Reference: `node_modules/redux-thunk/dist/redux-thunk.mjs` (read it: it's the whole library)

---

## 1. The whole library

Open `node_modules/redux-thunk/dist/redux-thunk.mjs` (version **3.1.0**). The runtime code is a single factory, `createThunkMiddleware(extraArgument)`, whose middleware does exactly what yours does (18.03):
- if the action is a function, call it with `(dispatch, getState, extraArgument)` and return the result;
- otherwise, `return next(action)`.

The package exports two things built from that factory:
- **`thunk`**: the middleware with no extra argument (`createThunkMiddleware()`);
- **`withExtraArgument`**: the factory itself, so you can pass an extra argument.

The rest of the package is TypeScript types: `ThunkAction`, `ThunkDispatch` and `ThunkMiddleware` (18.08 uses the first two). Redux's own `Dispatch` type is **not** changed, so TaskFlow types its dispatch explicitly as `AppDispatch`.

### v2 → v3 differences you'll meet in older code

| redux-thunk 2 | redux-thunk 3 |
|---|---|
| `import thunk from 'redux-thunk'` (default export) | `import { thunk } from 'redux-thunk'` (named export) |
| `thunk.withExtraArgument(api)` | `withExtraArgument(api)` (separate named export) |

Verified while writing 18.03's test: with v3, `thunk.withExtraArgument` doesn't exist, and TypeScript says *"Property 'withExtraArgument' does not exist on type 'ThunkMiddleware<any, AnyAction, undefined>'"*.

## 2. Why inject dependencies with `extra`?

A thunk could just `import { getTasks } from '../../api/tasks'`. Injecting it instead:

```ts
export const fetchTasks = (query = DEFAULT_QUERY): AppThunk<Promise<void>> =>
  async (dispatch, _getState, { api, nextRequestId, listRequest }) => {
    // …uses api.getTasks(…), never imports it
  };
```

- **Tests pass a fake API.** 18.13's tests create a store with `makeStore(state, { api: fakeApi() })`, and every thunk uses the fake: no network, no mocking of module imports, and each test chooses exactly what the "server" returns, including errors and **out-of-order responses** (18.11).
- **Per-store services.** Each store gets its own `extra`. TaskFlow's `extra` also holds a request-id generator and the in-flight list request (18.11), so tests with separate stores can't interfere with each other.
- **Swapping implementations.** Part 3 could inject a different API client (the real backend) without touching any thunk.

It's **dependency injection**, the same idea as Spring's constructor injection, which you may know from Java. You'll use the plain-servlet version of it in Part 2, where a `ServletContextListener` creates the services at startup and the servlets receive them (S45).

## 3. ✍️ TaskFlow's `extra`: `src/app/thunk-types.ts`

```ts
export interface ThunkExtra {
  api: typeof tasksApi;
  /** Ids for requests (18.11): generated OUTSIDE reducers, which must stay deterministic (15.04). */
  nextRequestId: () => string;
  /** The list request in flight, so a newer one can abort it (18.11). One holder PER STORE. */
  listRequest: { controller: AbortController | null };
}
```

`typeof tasksApi`, with `import type * as tasksApi from '../api/tasks'`, is the type of the **whole module object**: `{ getTasks, getTask, createTask, updateTask, patchTask, deleteTask }`. A fake must implement the same functions, so the compiler keeps fakes honest.

And in `store.ts`, a fresh `extra` per store:

```ts
function buildExtra(overrides: Partial<ThunkExtra> = {}): ThunkExtra {
  let requestCounter = 0;
  return {
    api: tasksApi,
    nextRequestId: () => `req-${++requestCounter}`,
    listRequest: { controller: null },
    ...overrides,
  };
}
```

## 4. Summary

- `redux-thunk` is one tiny factory: `thunk` = no extra; `withExtraArgument(x)` = with one.
- v3 uses named exports; `thunk.withExtraArgument` is gone.
- Inject the API (and other services) through `extra`: testable, per-store, swappable thunks.
