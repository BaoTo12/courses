# Lecture 18.05 · Thunk Functions vs Thunk Action Creators; `(dispatch, getState, extra)`

> **Section:** S18 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> 🔗 Official companion reading: Fundamentals Part 6 ("Writing Thunks"); the Redux docs page "Writing Logic with Thunks"

---

## 1. Two layers

```ts
// a THUNK FUNCTION: what the middleware calls
const loadEverything = async (dispatch, getState, extra) => { … };
dispatch(loadEverything);

// a THUNK ACTION CREATOR: a function that RETURNS a thunk function (so you can pass arguments)
const saveTaskChanges = (id: number, changes: UpdateTaskRequest): AppThunk<Promise<Task>> =>
  async (dispatch, _getState, { api }) => {
    const saved = await api.patchTask(id, changes);
    dispatch(taskUpdated(saved));
    return saved;
  };
dispatch(saveTaskChanges(5, { title: 'New title' }));
```

The pattern mirrors plain actions: `taskUpdated(task)` is an action **creator** returning an action **object**; `saveTaskChanges(id, changes)` is a thunk action **creator** returning a thunk **function**. TaskFlow always writes creators, even without arguments (`fetchTasks()`), so every call site looks the same: `dispatch(something(…))`.

## 2. The three arguments

| Argument | What it is | Use it to… |
|---|---|---|
| `dispatch` | The store's full-chain dispatch (18.03) | Dispatch plain actions (results), or other thunks (compose flows) |
| `getState` | The store's `getState` | Read **current** state: decide whether to do something (18.09), find data needed for the request |
| `extra` | Whatever was given to `withExtraArgument` | Reach services: the API, id generators (18.04) |

`getState()` returns the state **at the moment you call it**. After an `await`, call it **again** if you need fresh data. A variable captured before the `await` may be stale by then.

```ts
async (dispatch, getState, { api }) => {
  const before = getState().tasks.items.length;
  await api.createTask(request);
  const after = getState().tasks.items.length; // other actions may have run while we waited
};
```

## 3. What a thunk may return

Anything. The value comes back from `dispatch`:

| Return | Caller writes | TaskFlow example |
|---|---|---|
| Nothing | `dispatch(thunk())` | — |
| `Promise<void>` | `await dispatch(fetchTasks())` | Wait for loading to finish (tests, "fetch then navigate") |
| `Promise<Task>` | `const created = await dispatch(saveNewTask(req))` | Navigate to the new task's page (18.07) |
| `Promise<boolean>` | `if (await dispatch(deleteTask(id))) navigate(…)` | The thunk handles errors itself (18.12) |

Two error-handling styles, both used in TaskFlow:
- **Reject** (`saveNewTask`, `saveTask`, `saveTaskChanges`): the **caller** knows best how to show the error (a form keeps its values and shows the message).
- **Resolve with a status and report via toasts** (`toggleTaskOnServer`, `deleteTask`, `clearCompleted`): the feedback is always the same toast, so the thunk does it once for every caller.

Pick one per thunk and document it in its comment. Mixing them in one thunk (toast **and** reject) makes callers show the error twice.

## 4. Summary

- A thunk action creator returns a thunk function; always dispatch `creator(args)`.
- `(dispatch, getState, extra)`: dispatch results, read fresh state, reach injected services.
- `dispatch(thunk)` returns the thunk's value; choose "reject" or "resolve + toast" per thunk.
