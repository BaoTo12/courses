# Lecture 18.08 · TS: `ThunkAction`, `AppThunk<ReturnType>`, `ThunkDispatch`, Typing `extra`

> **Section:** S18 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes
> 🔗 Official companion reading: the Redux docs page "Usage with TypeScript" ("Type Checking Redux Thunks")
> Every error message below was produced by `tsc` in the reference app.

---

## 1. `ThunkAction<R, S, E, A>`

From `redux-thunk`, the type of a thunk function:

```ts
type ThunkAction<ReturnType, State, ExtraThunkArg, BasicAction extends Action> =
  (dispatch: ThunkDispatch<State, ExtraThunkArg, BasicAction>, getState: () => State, extraArgument: ExtraThunkArg) => ReturnType;
```

Four type parameters: what the thunk returns, the state type (for `getState`), the extra argument type, and the plain actions `dispatch` accepts.

## 2. `AppThunk<R>`: fix three of them once

```ts
export type AppThunk<R = void> = ThunkAction<R, RootState, ThunkExtra, AppAction>;
```

Now every thunk action creator declares only its **return type**:

```ts
export const fetchTasks = (query = DEFAULT_QUERY): AppThunk<Promise<void>> =>
  async (dispatch, getState, { api }) => { … };   // all three parameters inferred
```

- `getState()` returns `RootState`; `getState().tasks.items` autocompletes.
- `{ api }` is destructured from `ThunkExtra`; `api.getTasks` is the real function's type (`typeof tasksApi`).
- `dispatch` accepts `AppAction`s **and** `AppThunk`s.
- Returning the wrong thing is caught: a thunk declared `AppThunk<Promise<Task>>` that returns nothing fails to compile.

## 3. `AppDispatch = ThunkDispatch<RootState, ThunkExtra, AppAction>`

`ThunkDispatch` is an overloaded function type:
- given a thunk returning `R`, it returns `R` (so `await dispatch(saveNewTask(r))` is a `Task`);
- given a plain action, it returns that action.

`useAppDispatch = useDispatch.withTypes<AppDispatch>()` (17.06) is what gives components these types.

## 4. Why `store.ts` declares `AppStore` by hand

Redux's `applyMiddleware` types **do** know about thunks, when they can see the middleware. Verified: `createStore(rootReducer, applyMiddleware(withExtraArgument(extra)))` produces a store whose `dispatch` accepts thunks.

But TaskFlow builds its chain as an array, `Middleware[]` (conditional logger, 16.11), and spreads it: `applyMiddleware(...buildMiddleware(extra))`. The element type `Middleware` has no idea which middleware adds what, so the inferred `dispatch` is plain again. Dispatching a thunk then fails (verified):

```text
error TS2345: Argument of type 'AppThunk<Promise<void>>' is not assignable to parameter of type 'AppAction'.
```

So `store.ts` states the truth once:

```ts
export type AppStore = Store<RootState, AppAction> & { dispatch: AppDispatch };
// …
return createStore(rootReducer, preloadedState, composeEnhancers(applyMiddleware(...buildMiddleware(extra)))) as AppStore;
```

It's the third library-typing boundary in the Redux track (16.03's preloaded state, 16.05's `compose`, and this one). Each is one documented assertion at the edge, and the rest of the app stays fully typed. RTK's `configureStore` (S20) infers all three correctly, which is one concrete reason the Redux team recommends it.

## 5. Typing `extra`

```ts
export interface ThunkExtra {
  api: typeof tasksApi;           // import type * as tasksApi from '../api/tasks'
  nextRequestId: () => string;
  listRequest: { controller: AbortController | null };
}
```

- `typeof tasksApi` (a namespace import's type) keeps the fake API honest: a fake missing `patchTask`, or with a wrong signature, fails to compile.
- `Partial<ThunkExtra>` for `makeStore`'s overrides: tests replace only what they need.

## 6. Summary

- `AppThunk<R> = ThunkAction<R, RootState, ThunkExtra, AppAction>`: thunks declare only what they return.
- `AppDispatch = ThunkDispatch<…>`: `dispatch(thunk)` returns the thunk's type.
- A spread `Middleware[]` loses the thunk typing: declare `AppStore` once (RTK infers it).
