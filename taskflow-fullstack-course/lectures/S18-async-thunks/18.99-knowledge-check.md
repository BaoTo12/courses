<summary><b>Answers</b></summary>

1. It's a plain function `(dispatch, getState, extra) => …`. Nothing about it is special. The **thunk middleware** makes it run: when a dispatched value is a function, the middleware calls it with those arguments instead of passing it to the reducers, and returns its result (18.03).

2. (a) Reducers must return the new state **synchronously**, and a response arrives later. (b) Reducers may not dispatch, so they couldn't report the result (*"Reducers may not dispatch actions."*). (c) Reducers must be pure and deterministic: replaying actions (DevTools, tests) would repeat the network calls and could produce different states.

3. **Request ids** (checked in the reducer) guarantee **correctness**: a stale response can never replace newer data, even if it arrives last. **Abort** saves network and client work, but it can't guarantee anything on its own: a response may arrive just before the abort, and the server may still process the request. Use ids for correctness, abort for efficiency.

4. Tests pass a fake API with `makeStore(state, { api })`: no network, no module mocking, and full control over results, errors and **response order**. Each store gets its own services (TaskFlow's per-store `listRequest` holder). And the implementation can be swapped (Part 3's backend) without touching thunks.

5. Whatever the thunk returns, so its promise resolves with the thunk's result. `fetchTasks()` resolves to `undefined` (`Promise<void>`: it never rejects; errors become `fetchFailed`). `saveNewTask(r)` resolves with the created `Task` (or rejects with an `ApiRequestError`).

6. Several problems:
   - The loop is **sequential** (one request after another). It's fine for a few tasks, slow for many. Consider `Promise.allSettled` (17.13).
   - There's **no error handling**: the first failed PATCH rejects the whole thunk, leaving some tasks renamed and some not, and the caller gets a rejection with no information about which succeeded.
   - `tasks` was captured **before** the awaits. It's a snapshot, and other actions may have changed the store meanwhile (fine here, but be aware: 18.05 §2).
   - `console.log` of counts proves nothing: renaming doesn't change the number of items.

   A "rename" event is also a candidate for a bulk server endpoint.

7. Logged, in order: `tasks/taskUpdated`, then `ui/toastShown` (if the task became DONE). **Not logged:** the thunk itself: the thunk middleware (second in the chain) calls functions and never passes them on, so the logger (third) only sees plain actions. (The API timing line `[api] PATCH /tasks/1 → 200` comes from the Axios interceptor, not the logger.)

8. The path: Axios rejects → the response interceptor rejects with an `ApiRequestError` (13.07) → `api.createTask` rejects → the `saveNewTask` thunk has no `try`, so its promise rejects → `await dispatch(saveNewTask(…))` in the page throws → the page's `catch` shows the toast. It gets lost wherever someone **catches without re-throwing or reporting**: an interceptor that returns instead of rejecting (13.14); a thunk with `catch (e) { console.error(e) }`; a page calling `dispatch(saveNewTask(…))` **without** `await` (the rejection becomes an unhandled promise rejection, and the form never learns it failed). The form stuck in "Saving…" is the clue that nobody handled the rejection.

9. The dispatched function reached a store without thunk middleware: a store created without `applyMiddleware(thunk…)`, the wrong store, or `import thunk from 'redux-thunk'` with v3 (no default export). Fix: create every store with `makeStore()`, and import `{ thunk }` / `withExtraArgument`.

10. (a) An **unconditional refetch** on every mount (an effect in the page). (b) A reducer that **resets `items`** on `fetchStarted`. Fix: keep items while loading, and load "if needed" (18.09).

11. **Thunk** when the feedback is always the same wherever it's triggered (toggle, delete, clear completed): written once, and tested by asserting `store.getState().ui.toasts` after dispatching, with no React needed. **Component** when the feedback depends on the screen: a form keeps its values and shows the error near the fields or in a toast, so the thunk rejects and the page decides. Either way, not both for the same thunk (double toasts).

12. Alternatives: the server's cache headers or an `ETag`/`Last-Modified` check (a conditional GET that costs little when nothing changed); events that make data stale (after a mutation elsewhere, or when the window regains focus: RTK Query's `refetchOnFocus`, S23); real-time updates (WebSocket) that make polling unnecessary. The value is a **product** decision: how stale may this data be before users are misled? Engineering implements it.

13. Verified with the fake API (both paths pass):
    ```ts
    /** Re-reads one task from the server. 404 → someone else deleted it: remove it locally too. */
    export const refreshTask =
      (id: number): AppThunk<Promise<void>> =>
      async (dispatch, _getState, { api }) => {
        try {
          dispatch(taskUpdated(await api.getTask(id)));
        } catch (error) {
          if (error instanceof ApiRequestError && error.status === 404) {
            dispatch(taskDeleted(id));
            dispatch(toastShown({ tone: 'info', message: 'This task was deleted elsewhere.' }));
            return;
          }
          dispatch(toastShown({ tone: 'error', message: toErrorMessage(error) }));
        }
      };
    ```
    ```ts
    it('updates from the server, and removes on 404', async () => {
      const ok = makeStore(preloaded, { api: { ...realApi, getTask: vi.fn(async (id: number) => t(id, 'Fresh')) } });
      await ok.dispatch(refreshTask(1));
      expect(ok.getState().tasks.items[0]?.title).toBe('Fresh');

      const gone = makeStore(preloaded, {
        api: { ...realApi, getTask: vi.fn(async () => { throw new ApiRequestError({ kind: 'http', status: 404, message: 'Task not found' }); }) },
      });
      await gone.dispatch(refreshTask(1));
      expect(gone.getState().tasks.items.map((x) => x.id)).toEqual([2]);
      expect(gone.getState().ui.toasts.at(-1)?.message).toBe('This task was deleted elsewhere.');
    });
    ```
    (`taskDeleted` also clears the id from the selection: 15.10. Remember that the mock returns 404, not 403, for other users' tasks, 13.02, so this path also covers "you lost access".)
