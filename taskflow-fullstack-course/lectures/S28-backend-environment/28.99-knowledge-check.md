# Lecture 28.99 · ✅ Knowledge Check: Backend Environment

> **Section:** S28 · **Type:** ✅ Knowledge Check · **Track:** ★ Core · **Time:** ~15 minutes

---

**1.** Why is `servlet-api` marked `provided`? What breaks if you bundle it?

<details><summary>Answer</summary>

Tomcat already supplies `javax.servlet.*` in its `lib/`. `provided` = "compile against it, don't put it in `WEB-INF/lib`". A bundled copy is ignored by a spec-compliant container, which always loads these classes from its own copy. If it's a different version, or the container loads it anyway, two copies of `Servlet` from two class loaders give `ClassCastException` / `NoSuchMethodError` (28.05 §3).
</details>

**2.** Why can the browser request `/taskflow/static/css/app.css`, but never `/taskflow/WEB-INF/web.xml`?

<details><summary>Answer</summary>

The container serves files from the WAR's root, but the Servlet specification forbids serving anything under `WEB-INF/` (and `META-INF/`), so the answer is 404. The application itself can still use those files (forward to JSPs, class loading). That's why JSPs and configuration go under `WEB-INF` (28.04).
</details>

**3.** The app deploys as `/backend-1.0-SNAPSHOT`. Where does the context path come from, and how do you change it?

<details><summary>Answer</summary>

From the WAR's **file name** (`backend-1.0-SNAPSHOT.war`), which Maven builds from `artifactId-version` when there's no `<finalName>`. Set `<finalName>taskflow</finalName>` → `/taskflow`, or name the file `ROOT.war` → `/`, or set the IDE's *Application context*. Delete the old WAR and its unpacked folder (28.10).
</details>

**4.** Why must JSTL be bundled in the WAR for Tomcat 9, and which JSTL?

<details><summary>Answer</summary>

Tomcat implements Servlet, JSP and EL, not JSTL. Without the jar, tag libraries can't be resolved. It must be the **`javax`** JSTL 1.2 (`javax.servlet:jstl:1.2`), not Jakarta JSTL 2/3 (28.05, 28.02).
</details>

**5.** `mvn dependency:tree` shows `slf4j-api:1.7.36` next to `logback-classic:1.5.6`. What's the problem, and the fix?

<details><summary>Answer</summary>

Maven kept one version by "nearest, then first declared", and chose HikariCP's old 1.7.36. SLF4J 1.7 can't bind to Logback 1.5, so logging silently disappears. Declare `slf4j-api` 2.0.x directly: a depth-1 dependency is nearest (28.05 §4).
</details>

**6.** Name three things the `taskflow_app` MySQL user can't do, and why that matters.

<details><summary>Answer</summary>

It can't create, drop or alter tables, grant privileges, touch other databases, or update or delete audit events. A SQL injection or a stolen app password is then limited to the app's own rows, and it can't erase the audit trail (28.07 §5).
</details>
