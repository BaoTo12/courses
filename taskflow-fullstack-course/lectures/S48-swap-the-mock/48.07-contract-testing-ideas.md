# Lecture 48.07 · Contract Testing Ideas

> **Section:** S48 · **Type:** 📖 Theory · **Track:** ＋ Extended · **Time:** ~10 minutes

*Extended track: outline.*

---

- **The problem:** the React app's types (`src/domain/types.ts`) and the Java DTOs (`web/api/dto/Dtos.java`) describe the same JSON twice. Nothing checks they agree; 48.05's lab shows what drifts.
- **Shared examples:** keep canonical JSON files (`contract/task.json`, `contract/error-400.json`). The Java tests assert that responses match them (field names and types); the TypeScript tests parse them with the app's guards (`isApiError`, `isPageOf`). Cheap, and catches renames.
- **Schema first:** write the contract as **OpenAPI** (`openapi.yaml`); generate TypeScript types (`openapi-typescript`) and validate server responses against it in tests. The schema becomes the single source.
- **Code first:** generate the schema or TypeScript types **from** the Java DTOs (`springdoc`, `typescript-generator`), and fail the build when the generated file changes unexpectedly.
- **Consumer-driven contracts (Pact):** the React app's tests record the interactions they expect; the backend's build replays them against the real API. Good when teams deploy independently.
- **What each catches** (48.05's six): renamed fields (3), changed types (6), changed error shape (4) and status codes (5) with any of the above; formats inside strings (1) only with a pattern in the schema; enum casing (2) with an `enum` in the schema.
- **What TypeScript alone catches:** nothing at runtime. Types describe what you **expect**; a server that sends something else passes straight through `axios` into the store. Runtime guards (TaskFlow's `guards.ts`) or schema validation at the boundary close the gap.
