# Lecture 26.99 · ✅ Knowledge Check: Frontend Security

> **Section:** S26 · **Type:** ✅ Knowledge Check · **Track:** ★ Core · **Time:** ~20 minutes

---

**1.** If XSS happens, why is an HttpOnly session cookie still valuable, but not a complete defence?

<details><summary>Answer</summary>

**Valuable:** the script can't *read* `JSESSIONID`, so it can't take the session away and keep using it after the tab closes. The attack is limited to the time the page is open. **Not complete:** while the page is open, the script can call the API as the user. The browser attaches the cookie, the script reads the CSRF token, and it can exfiltrate data or change it (26.01 §3, the 26.03 lab).
</details>

**2.** Which of these are vulnerable, with `x` user-controlled?

```tsx
a) <p>{x}</p>
b) <a href={x}>link</a>
c) <div dangerouslySetInnerHTML={{ __html: x }} />
d) <div style={{ backgroundImage: `url(${x})` }} />
e) <img src={x} />
```

<details><summary>Answer</summary>

- **a)** Safe: escaped text.
- **b)** `javascript:` is blocked by React 19, but `data:` and phishing URLs pass, so use `SafeLink`.
- **c)** Vulnerable: raw HTML.
- **d)** Risky: CSS `url()` requests a URL of the attacker's choice (tracking, CSS injection with a crafted value such as `x) ; …`). Validate or don't allow it.
- **e)** No script execution from `src` in modern browsers, but it makes a request to an attacker-chosen host (tracking, internal URLs), so allow-list it.

(26.02, and the "what React 19 does" tests.)
</details>

**3.** Where must "only the owner can delete a task" live? Where can it *also* live, and why?

<details><summary>Answer</summary>

**Must:** on the server, on every DELETE (the mock's `findAccessibleTask`; the servlet's service layer in S41). **Also:** in the client, to hide or disable the Delete button for UX. The user can bypass the client with DevTools or curl (26.08), so it never counts as protection.
</details>

**4.** Implement `SafeLink`.

<details><summary>Answer</summary>

```tsx
const ALLOWED = new Set(['http:', 'https:', 'mailto:']);
export function SafeLink({ href, children }: { href: string; children: ReactNode }) {
  let url: URL | undefined;
  try { url = new URL(href.trim(), window.location.origin); } catch { url = undefined; }
  if (!url || !ALLOWED.has(url.protocol)) return <span className="text-muted">{children}</span>;
  const external = url.origin !== window.location.origin;
  return <a href={url.href} title={url.href} {...(external ? { target: '_blank', rel: 'noopener noreferrer' } : {})}>{children}</a>;
}
```

An allow-list on the **parsed** protocol, the normalised URL is used, and external links get no opener (26.06).
</details>

**5.** Why does blocking `<script>` tags not stop XSS?

<details><summary>Answer</summary>

Script also runs from event-handler attributes (`<img onerror>`, `<svg onload>`), `javascript:` URLs, `<iframe srcdoc>`, and more. The list of vectors is open-ended, so only an **allow-list** (DOMPurify's `ALLOWED_TAGS`/`ALLOWED_ATTR`), or not rendering HTML at all, works (26.03, 26.04).
</details>

**6.** A CSP of `script-src 'self'; connect-src 'self'` is in place. Which parts of 26.03's attack still work?

<details><summary>Answer</summary>

The inline `onerror` doesn't run, and exfiltration to another origin is blocked. If an attacker *did* get script running (e.g. through an allowed script with a gadget), same-origin API calls would still work. CSP is a second wall, not a replacement for sanitising (26.11).
</details>
