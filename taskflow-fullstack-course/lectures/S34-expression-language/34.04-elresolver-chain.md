## 1. What `${…}` becomes in the generated servlet

In S33 you read the generated `list_jsp.java` (33.03). Here is what Jasper wrote for S34's `view.jsp`:

```java
public final class view_jsp extends org.apache.jasper.runtime.HttpJspBase
    implements org.apache.jasper.runtime.JspSourceDependent,
               org.apache.jasper.runtime.JspSourceImports {
  …
  static {
    _jspx_imports_packages = new java.util.LinkedHashSet<>(4);
    _jspx_imports_packages.add("javax.servlet");
    _jspx_imports_packages.add("javax.servlet.http");
    _jspx_imports_packages.add("javax.servlet.jsp");
    _jspx_imports_classes = new java.util.LinkedHashSet<>(2);
    _jspx_imports_classes.add("com.taskflow.web.Html");     // the page imports, handed to EL too
  }
  …
      out.write((java.lang.String) org.apache.jasper.runtime.PageContextImpl.proprietaryEvaluate(
          "${Html.escape(pageTitle)}", java.lang.String.class, (javax.servlet.jsp.PageContext)_jspx_page_context, null));
```

Three things to notice:

1. The expression stays a **string**: `"${Html.escape(pageTitle)}"`. It's parsed (and cached) by the EL engine at runtime, not compiled to Java. That's why a typo in a property name is never a compile error.
2. The result is coerced to **`String`** for template text: `null` → `""` (34.03).
3. `header.jspf` and `view.jsp` both import `Html`, but it's in the set once. The page's imports are also given to EL, which is how `${Html.escape(…)}` finds the class (34.17).

## 2. The resolver chain

The EL engine doesn't know about scopes, maps or beans. It asks a chain of **ELResolvers**, one after the other, until one says "resolved". For a JSP, the chain is (JSP 2.3 spec):

```text
 1. ImplicitObjectELResolver    pageContext, param, header, cookie, requestScope, …     (base == null)
 2. resolvers added by the application or libraries (JspApplicationContext.addELResolver)
 3. StreamELResolver            .stream() on collections                          (EL 3.0)
 4. StaticFieldELResolver       Html.escape(…), Integer.MAX_VALUE                  (EL 3.0)
 5. MapELResolver               base is a Map        → map.get(key)
 6. ResourceBundleELResolver    base is a ResourceBundle
 7. ListELResolver              base is a List       → list.get(index)
 8. ArrayELResolver             base is an array     → array[index]
 9. BeanELResolver              any other object     → the getter (34.07)
10. ScopedAttributeELResolver   findAttribute(name)                                (base == null)
```

## 3. Walk through `${details.category.name}`

Each step is a call `getValue(context, base, property)` down the chain:

| Step | `base` | `property` | Who answers | Result |
|---|---|---|---|---|
| 1 | `null` | `"details"` | not an implicit object… **ScopedAttribute** | the `TaskDetails` from request scope |
| 2 | `TaskDetails` | `"category"` | not a Map/List/array… **Bean** → `getCategory()` | a `Category`, or `null` |
| 3 | `Category` | `"name"` | **Bean** → `getName()` | `"Work"` |
| 3′ | `null` (no category) | `"name"` | nobody: EL stops | `null` → prints nothing (34.08) |

The resolvers for `base == null` (1 and 10) handle **names**. The ones in the middle handle **properties of a value**. Map before Bean is why `${stats.TODO}` reads a map key, not a `getTODO()` method.

## 4. Why it's designed as a chain

- **Extensible:** Spring adds a resolver so `${someBean}` finds Spring beans. JSF adds its own. You could add one (rare).
- **Uniform:** one syntax, `a.b` / `a[b]`, for maps, lists, arrays and beans.
- **Cost:** it's reflection plus a few `instanceof` checks per step. It's fast enough for pages. Tomcat caches parsed expressions and bean property lookups.

## ✅ Recap

`${…}` becomes `proprietaryEvaluate("${…}", String.class, pageContext, null)`. At runtime a chain of resolvers handles each step: names by implicit objects or scoped attributes, values by Map, List, array or Bean.
