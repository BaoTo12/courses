## 1. TaskFlow's fix (for now)

```jsp
<input type="search" name="q" value="${Html.escape(param.q)}">
```

`Html.escape` (30.14) turns `& < > " '` into entities. The attack from 34.18 now arrives as text:

```html
<input type="search" name="q" value="&quot;&gt;&lt;script&gt;alert(document.domain)&lt;/script&gt;">
```

The browser decodes the entities **inside the attribute value**. The box shows the text the attacker typed, and nothing executes. All of TaskFlow's S34 views do the same for titles, descriptions, names, and anything from `param`, `header` or `cookie`.

## 2. But "escape" depends on *where* the text lands

The browser parses a page with different parsers in different places. Each **context** has its own dangerous characters:

| Context | Example | Dangerous | Correct encoding | In JSP |
|---|---|---|---|---|
| HTML body | `<p>${x}</p>` | `<` `&` | HTML entity-encode | `Html.escape` now; `<c:out>` / `fn:escapeXml` (S35) |
| quoted HTML attribute | `value="${x}"` | `"` (or `'`), `&` | HTML entity-encode; **always quote** the attribute | same |
| unquoted attribute | `value=${x}` | a space, `>` | don't: always quote | — |
| URL parameter | `href="/tasks?q=${x}"` | `&` `#` `=` space | **URL-encode** the value, then HTML-encode the URL | `<c:url>` + `<c:param>` (S35) |
| URL as a whole | `href="${x}"` | `javascript:` | an **allow-list** of schemes (26.07); encoding alone doesn't help | validate in Java |
| JavaScript string | `<script>var q = '${x}';</script>` | `'` `\` `</script>` newline | JS string escaping (`'`, `<`) | avoid: put data in a `data-` attribute or JSON (S49) |
| CSS | `style="color:${x}"` | everything | don't put untrusted data here | — |

## 3. Why HTML escaping isn't enough in JavaScript

```jsp
<script>const search = { q: '${Html.escape(param.q)}', tag: '${Html.escape(param.tag)}' };</script>
```

Inside `<script>`, entities are **not** decoded: `'` arrives in JavaScript as the six characters `&#39;` (wrong data, but harmless). `Html.escape` doesn't touch the **backslash**, though. Send `?q=\&tag=,x:alert(1)//`:

```js
const search = { q: '\', tag: ',x:alert(1)//' };
//                   └── \' is an escaped quote: the string q continues…
//                       …until the quote before ",x:" → then x:alert(1) is CODE
```

The backslash swallows the closing quote, so the second value is outside any string: it runs. The rule: **never** put untrusted text inside `<script>`. Use:

```jsp
<div id="search" data-query="${Html.escape(param.q)}"></div>
<script>const q = document.getElementById('search').dataset.query;</script>
```

The attribute is an HTML context, so HTML escaping is exactly right there.

## 4. The checklist for every `${…}` that prints

1. Can anyone other than a developer influence this value (request, database, another user)? → **escape it**.
2. Which context? → pick the encoding from the table.
3. Attributes → quoted, always.
4. URLs → URL-encode the parts, and validate the scheme of whole URLs.
5. `<script>` → no untrusted data inside. Use `data-` attributes.

Numbers, enums and dates from your own model (`${task.id}`, `${task.status}`, `${task.dueDate}`) can't contain markup, so TaskFlow prints them directly.

## ✅ Takeaways

- Escaping isn't one function: HTML body and quoted attributes need entity encoding, URLs need URL encoding, `<script>` needs "don't".
- `Html.escape` in EL is S34's bridge. S35 replaces it with `<c:out>` and `fn:escapeXml`, which are the standard way.
