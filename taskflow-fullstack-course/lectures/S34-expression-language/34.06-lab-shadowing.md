# Lecture 34.06 · 🔓 Lab: Shadowing: a Request Attribute `user` Hides the Logged-in User

> **Section:** S34 · **Type:** 🔓 Attack Lab / 🐞 Debug · **Track:** ★ Core · **Time:** ~20 minutes
> ⚠️ Local only, in a lab branch. Uses a stand-in for the S38 login.

---

## 1. The setup

Pretend the login already exists (S38): a filter puts the logged-in user in the session.

```java
// lab only: in any servlet's doGet, before forwarding
request.getSession().setAttribute("user", directory.findUser(1).orElseThrow());   // alice, logged in
```

The shared header greets and decides what to show:

```jsp
<span>Signed in as ${user.displayName}</span>
<a href="…/admin" ${user.admin ? '' : 'hidden'}>Admin</a>
```

(The page must be `session="true"` for this lab.)

## 2. The "feature" that breaks it

An admin page to **edit another user** sets the edited user as a request attribute:

```java
request.setAttribute("user", directory.findUser(3).orElseThrow());   // editing "admin"
request.getRequestDispatcher("/WEB-INF/views/users/edit.jsp").forward(request, response);
```

## 3. What happens

Open the edit page as alice:

- The header says **"Signed in as Admin"**.
- The **Admin** link appears, for a user who isn't one.

`${user}` searches request **before** session (34.03). The header is now reading the edited user, not the logged-in one.

## 4. Why it's a security bug, not just a display bug

The link is only the visible part. The same pattern in a check:

```jsp
${user.admin ? '<button>Delete everything</button>' : ''}
```

…or in a tag that decides access (`<c:if test="${user.admin}">`, S35) grants UI power based on **whichever `user` is nearest**. Any page that puts a user-shaped object named `user` in the request, even a profile page showing someone else's details, turns the header into a lie.

(The **server** must still check permissions in the controller; S42's authorization filter does. But a view that shows admin controls to non-admins invites exactly the requests you then have to refuse.)

## 5. Fixes

| Fix | Why |
|---|---|
| the header reads `${sessionScope.currentUser}` | explicit scope + a name nothing else uses (34.05) |
| model attributes get specific names: `editedUser`, `owner`, `author` | no accidental overlap |
| authorization decisions are made in Java (filter/controller), views only display | a view can't grant anything |

## Lesson

The automatic scope search is convenient, and it lets any narrower scope **override** a wider one. For values that identify the user, override is a vulnerability. Name them uniquely and read them from one explicit scope.
