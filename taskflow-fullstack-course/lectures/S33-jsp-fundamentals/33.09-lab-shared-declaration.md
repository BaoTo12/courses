# Lecture 33.09 · 🔓 Lab: A `<%! %>` Declaration Shared Across Users and Threads

> **Section:** S33 · **Type:** 🔓 Attack Lab · **Track:** ★ Core · **Time:** ~25 minutes
> ⚠️ Local only, in a lab branch.

---

## 1. The "feature"

A developer wants "the last search" on the list page, and writes:

```jsp
<%! String lastSearch; %>                                              <%-- a FIELD of list_jsp (33.07) --%>
<%
  String q = request.getParameter("q");
  if (q != null) lastSearch = q;
%>
<p>Your last search: <%= Html.escape(lastSearch) %></p>
```

## 2. The data leak

1. Browser A (alice): `/taskflow/tasks?q=salary review for bob`.
2. Browser B (bob), a different computer: `/taskflow/tasks` → **"Your last search: salary review for bob"**.

There's one `list_jsp` instance for the whole application (30.05). Its fields are **everyone's**. "Your" last search is really "anybody's".

## 3. The race condition

```jsp
<%! int views = 0; %>
<% views++; %>           <%-- read-modify-write, not atomic --%>
```

Hit it with 200 concurrent requests (30.06's `curl` loop): the final count is often **below** 200. Two threads read the same value and both write +1: lost updates.

## 4. Fixes

| Need | Correct place |
|---|---|
| per-user state ("my last search") | the **session** (S38): `session.setAttribute("lastSearch", q)`, set by the **controller** |
| per-request values | local variables / request attributes |
| a genuinely global counter | an `AtomicLong` in application scope, updated by a controller or filter |
| anything in a JSP | nothing: views don't keep state |

## Lesson

A declaration looks like "a variable of the page". It's actually a **field of a singleton** accessed by many threads, and the page's visitors share it. It's the servlet-field bug (30.05) in disguise, and one more reason for "no Java in views".
