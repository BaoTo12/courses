# Lecture 33.04 · When Translation Happens; Jasper's Development Mode; Precompilation

> **Section:** S33 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> Observed while building this section: after a `web.xml` change, Jasper kept using the old translation until the work folder was cleaned.

---

## 1. Jasper's rule

On each request for a JSP (in **development** mode), Jasper compares the timestamps of:
- the `.jsp` file;
- every **static include** it recorded (`_jspx_dependants` in the generated class, 33.03);
- (and tag files and TLDs it depends on).

If any is newer than the generated class, it re-translates and recompiles. Otherwise, it reuses the class.

## 2. What it does NOT notice

| You changed | Re-translated? | Fix |
|---|---|---|
| the `.jsp` | ✅ | — |
| a `<%@ include %>` fragment (`.jspf`) | ✅ (it's a dependant) | — |
| a `<jsp:include>` target | n/a (included at **runtime**, compiled separately) | — |
| **`web.xml`'s `<jsp-config>`** (encoding, trimming) | ❌ | redeploy **and** clear `work/` |
| a Java class the JSP uses | the JSP isn't re-translated; the new class is used after a **redeploy** | redeploy |

The course's test harness deletes its work folder before each test class for exactly this reason. It was added when a `jsp-config` change seemed to have "no effect" (33.19).

**"My JSP change doesn't appear"**, the checklist: exploded vs WAR deployment (28.06)? The right file (under `src/main/webapp` or the IDE's output)? A cached page in the browser (hard reload)? A stale `work/` folder (stop, delete `work/Catalina/localhost/taskflow`, start)? Development mode off (§3)?

## 3. Development vs production mode

`JspServlet` init parameters in `conf/web.xml`:

| Parameter | Default | Production |
|---|---|---|
| `development` | `true` (check timestamps on every request) | `false` |
| `checkInterval` | `0` | e.g. `300` seconds between background checks (with `development=false`) |
| `modificationTestInterval` | `4` s | — |
| `trimSpaces` | `false` | `true` (smaller HTML) |

## 4. Precompilation

For production, compile all JSPs **at build time** (the `jspc` Maven plugin), or warm them at startup. Benefits: no first-request delay, and syntax or compile errors fail the **build**, not a user's request. TaskFlow's tests do something similar for free: every JSP a test renders is translated and compiled by the embedded Jasper.
