# Lecture 07.01 · Why React Exists: from Vanilla DOM Pain to `UI = f(state)`

> **Section:** S07 · React Fundamentals

## 1. Remember the pain list (04.13)

When you built the task board with vanilla DOM APIs, you wrote down what hurt:

1. **Verbose DOM building**: `createElement`, `className`, `textContent`, `append`… 30 lines per card.
2. **Re-render everything by hand**: `replaceChildren` destroyed and rebuilt every card on every click.
3. **State and DOM out of sync**: forget one `render()` call and the screen lies.
4. **Event plumbing**: delegation, `dataset`, string ↔ number conversions.
5. **No reusable components**.

Every one of these gets worse as an app grows. React exists to solve exactly these problems.

## 2. The core idea: UI is a function of state

> 🧠 **`UI = f(state)`**. You describe **what** the UI should look like for a given state. React figures out **how** to update the real DOM to match.

```tsx
function TaskCard({ task }: { task: Task }) {
  return (
    <article className="card">
      <h3 className="card__title">{task.title}</h3>
      <StatusBadge status={task.status} />
    </article>
  );
}
```

That's the entire "render" for a card. Compare it with `createCard` from 04.13. There's no `createElement`, and no "remember to update the badge when status changes". When `task.status` changes, React calls `TaskCard` again with the new `task`, compares the new description with the old one, and changes **only the badge's text and class** in the real DOM.

### Declarative vs imperative

| Imperative (vanilla, 04.13) | Declarative (React) |
|---|---|
| "Create an `h3`, set its class, set its text, append it…" | "A card contains a title and a badge." |
| You manage every DOM change | React computes DOM changes from state changes |
| Easy to forget an update → UI lies | UI is always recomputed from state → consistent |

## 3. How React solves each pain point

| Pain (04.13) | React's answer |
|---|---|
| Verbose DOM building | **JSX**: HTML-like syntax compiled to function calls (07.03) |
| Rebuild everything | **Reconciliation**: diff the new description against the previous one and apply minimal DOM changes (07.04) |
| State/DOM sync | **State** (`useState`): change state → React re-renders automatically (07.08) |
| Event plumbing | Handlers attached directly in JSX: `onClick={() => onToggle(task.id)}` (07.09) |
| No reuse | **Components**: functions that return UI, composed like building blocks (07.05, 07.13) |

## 4. What React is not

- **Not a framework for everything.** React renders UI. Routing (React Router, S12), data fetching (Axios S13, RTK Query S22), global state (Redux, S14+), styling (SCSS, styled-components) and forms come from other libraries or your own code. That's why this course teaches them all.
- **Not server-side by default.** A Vite React app is **client-side rendered** (00.04): the browser downloads JS, then React builds the DOM. (React *can* render on the server with frameworks like Next.js; not in this course.)
- **Not magic performance.** React avoids unnecessary *DOM* work, but it still calls your component functions. Knowing *when* it re-renders (S08, S21) is part of the job.

## 5. Where React runs in TaskFlow

Back to the course's central question: **where does this code run?** React runs **in the browser**, after `main.tsx` is downloaded and executed. It never sees the JSP portal, and the Java backend never sees React. They meet only through HTTP (JSON), and in S49, inside one page.

## 6. Summary

- React = declarative UI: describe the UI for the current state; React updates the DOM.
- It addresses the vanilla pain points with JSX, reconciliation, state, event props and components.
- React is only the view layer; routing, data, global state and styling are separate concerns.
- A Vite React app renders in the browser.
