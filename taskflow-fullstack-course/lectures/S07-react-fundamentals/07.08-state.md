# Lecture 07.08 · State with `useState`: What Triggers a Re-render, and Why You Must Not Mutate

> **Section:** S07 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes
> 🔗 Official reading: react.dev → Learn → "State: A Component's Memory", "Updating Arrays in State"

---

## 1. Why a normal variable doesn't work

```tsx
function Counter() {
  let count = 0;
  return <button onClick={() => { count++; }}>{count}</button>;
}
```

Clicking does nothing visible, for two reasons:
1. Changing a local variable **doesn't tell React** to re-render.
2. Even if it re-rendered, `let count = 0` runs again, because **every render is a fresh function call**, so locals start over.

A component needs **memory that survives renders** and **a way to request a re-render**. That's state.

## 2. `useState`

```tsx
import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

- `useState(0)` returns a tuple (05.03): the **current value** and a **setter**.
- React stores the value **outside your function**, in the component's instance in the tree (07.04), and hands it back on every render.
- Calling `setCount(next)` stores the new value and **schedules a re-render**. On that render, `useState` returns `next`.

With TypeScript, the type is inferred from the initial value. Give it explicitly when the initial value doesn't show the full type:

```tsx
const [tasks, setTasks] = useState<Task[]>(SAMPLE_TASKS);
const [statusFilter, setStatusFilter] = useState<TaskStatus | null>(null);   // null alone would infer `null`
```

(Remember 05.04: `useState([])` infers `never[]`.)

## 3. Each render has its own state (a snapshot)

```tsx
function handleClick() {
  setCount(count + 1);
  console.log(count);   // still the OLD value
}
```

`count` is a `const` in **this render's** closure (04.08). `setCount` doesn't change it. It asks React for a **new render** in which `count` will be the new value. Think of each render as a **snapshot** with its own props, state and event handlers.

## 4. Functional updates: when the next state depends on the previous

```tsx
setCount(count + 1);
setCount(count + 1);   // both read the same snapshot → +1 total, not +2

setCount((c) => c + 1);
setCount((c) => c + 1);   // each receives the latest queued value → +2
```

React **batches** updates within the same event and processes them in order. A function updater receives the **pending** value, so it's correct even when several updates queue up. Use it whenever the next state is computed from the previous one:

```tsx
function handleToggle(id: number) {
  setTasks((current) => toggleTask(current, id));
}
```

(`toggleTask` is your pure function from S04. React state updates and pure functions are made for each other.)

## 5. Never mutate state: React compares references

When you call `setTasks(next)`, React checks `Object.is(next, previous)`. If it's the **same reference**, React **bails out**: no re-render (04.03).

```tsx
// ❌ same array, mutated in place
const t = tasks.find((x) => x.id === id)!;
t.status = 'DONE';
setTasks(tasks);          // Object.is(tasks, tasks) → true → nothing happens

// ✅ new array, new object for the changed task
setTasks((current) => current.map((x) => (x.id === id ? { ...x, status: 'DONE' } : x)));
```

The mutated version is also dangerous beyond "no update": the old snapshot now contains changed data, so any later render or memoised component sees corrupted history. That's 07.17's debug lecture.

## 6. State is local, isolated and private

Two `<Counter />`s each have their own `count`: state belongs to the **instance at a position in the tree** (07.04). If the same component appears in the same position across renders, it keeps its state. If it's removed, its state is gone.

## 7. What should be state? (a preview of "Thinking in React")

Ask of each piece of data:
- Does it **change over time** because of user action or data loading? → maybe state.
- Can it be **computed** from other state or props? → **not** state. Compute it during render.

```tsx
const [tasks, setTasks] = useState<Task[]>(SAMPLE_TASKS);
const [statusFilter, setStatusFilter] = useState<TaskStatus | null>(null);

// derived, NOT state:
const visibleTasks = filterTasks(tasks, { status: statusFilter ?? undefined });
```

Storing `visibleTasks` in state too would create two sources of truth that can disagree. Derived data is computed; S21 shows how to memoise it when it's expensive.

## 8. Summary

- State = memory that survives renders + a setter that schedules a re-render.
- Each render sees a **snapshot**; the setter doesn't change the current variable.
- Use **functional updates** when the next value depends on the previous one.
- React compares with `Object.is`: **never mutate**, always pass new objects/arrays.
- Don't store what you can derive.
