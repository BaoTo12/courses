# Lecture 07.14 · One-Way Data Flow and Prop Drilling: the Problem Redux Will Solve

> **Section:** S07 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes

---

## 1. One-way data flow

In React, data flows **down** (parent → child via props) and **events flow up** (child → parent via callbacks). A child never reaches up and changes its parent's data directly.

```text
   state (App)
     │ props ↓           ↑ callbacks
   children ... grandchildren
```

Benefits: you can always answer "where does this value come from?" by walking **up** the tree, and "who can change it?" is always the component that owns the state. Debugging is predictable.

## 2. The cost: prop drilling

As TaskFlow grows, imagine these needs:

- The **header** shows "3 open tasks" and the user's name.
- The **dashboard** (another page) shows stats about the same tasks.
- A **task detail** page edits a task, and the list must reflect the change.
- A **toast** area anywhere shows "Saved!" after any change.

With `useState` in `App`, every piece of shared data and every callback must be passed **through every intermediate component**, even those that don't use it:

```text
App (tasks, setTasks, user, toasts, addToast, filter, setFilter …)
 └─ Layout (tasks, user, toasts…)             ← doesn't use tasks, just passes them on
     └─ Main (tasks, onToggle, addToast…)      ← doesn't use most of these either
         └─ Dashboard (tasks)
         └─ TaskPage
             └─ TaskList (tasks, onToggle, addToast)
                 └─ TaskCard (task, onToggle, addToast)
```

This is **prop drilling**:
- Intermediate components get cluttered with props they only forward.
- Renaming or adding a piece of shared state touches many files.
- Moving a component means re-threading its props.
- Every state change in `App` re-renders the whole tree below it (07.04).

## 3. The solutions you'll learn, in order

| Tool | What it solves | Section |
|---|---|---|
| **Composition** (pass components as `children`) | Removes some drilling by building the subtree where the data lives | 07.13 |
| **`useReducer`** | Centralises complex update logic, with actions describing events | S08 |
| **Context** | Delivers a value to any descendant without drilling | S08 |
| **Redux** | A global store with actions, reducers, middleware, DevTools, and selective subscriptions (components re-render only when *their* data changes) | S14–S23 |
| **RTK Query** | Server data caching, so you don't manually store fetched data at all | S22–S23 |

The official Redux tutorials start from exactly this point: state that many components in different parts of the app need to share and update. You've now felt the problem, so the solution will make sense.

## 4. Summary

- One-way data flow: data down, events up. It's predictable and debuggable.
- Prop drilling: shared state threaded through components that don't need it.
- Composition, `useReducer`, Context, Redux and RTK Query each address parts of the problem.
