# Lecture 07.04 · Elements, Components, Instances; the Virtual DOM; Render vs Commit

> **Section:** S07 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes
> 🔗 Official reading: react.dev → Learn → "Render and Commit", "Keeping Components Pure"

---

## 1. Three words people mix up

| Term | What it is | Example |
|---|---|---|
| **Component** | A **function** that returns elements | `function TaskCard({ task }) { … }` |
| **Element** | A **plain object** describing what to show (07.03) | `{ type: TaskCard, props: { task } }` |
| **Instance** (in the tree) | React's internal record of a component **at a position** in the tree, holding its **state** and hooks | "the TaskCard at position 2 in the list" |

When you write `<TaskCard task={t} />` three times, you have **one** component, **three** elements, and **three** instances in React's tree, each with its own state.

## 2. The two phases: render and commit

When state changes, React does **two separate things**:

```text
          ┌──────────────── RENDER PHASE ────────────────┐   ┌──── COMMIT PHASE ────┐
setState → │ call component functions → new element tree   │ → │ apply minimal changes │ → browser
          │ compare with previous tree ("reconciliation")  │   │ to the real DOM       │   paints
          └────────────────────────────────────────────────┘   └──────────────────────┘
          pure computation, no DOM changes                     DOM mutations, then effects (S08)
```

1. **Render phase:** React calls your component functions to get the new element tree. It compares ("diffs") it against the tree from last time. **No DOM is touched.** Your function must be **pure** here: same props/state → same output, no side effects.
2. **Commit phase:** React applies only the **differences** to the real DOM (change a text node, add a class, insert one card). Then it runs effects (S08).

> ⚠️ **"Re-render" ≠ "DOM update".** A component can re-render (its function runs again) and produce exactly the same output, so the commit changes **nothing** in the DOM. Re-renders cost JS time; DOM updates cost more. S21 is about avoiding unnecessary re-renders where it matters.

## 3. The "virtual DOM"

"Virtual DOM" is the popular name for the element tree: a lightweight JS representation of the UI that React can compute and compare cheaply, instead of reading and writing the (slow) real DOM. React's internal structure is called the **Fiber tree**: one node per component instance, holding its hooks/state and links to parent, child and sibling.

## 4. What triggers a render

1. **Initial render**: `createRoot(...).render(<App />)`.
2. **State update** in a component (`setTasks(...)`) → that component **and its descendants** re-render.
3. **Context change** (S08) → components reading that context re-render.
4. **Parent re-render** → children re-render by default, even if their props didn't change (unless memoised with `React.memo`, S21).

Props changing doesn't cause a render on its own. The *parent re-rendering* is what passes new props.

## 5. Reconciliation: how React matches old and new trees

React compares trees **by position and type**:
- Same **type** at the same position (e.g. still an `<article>`, still a `TaskCard`) → **update** the existing DOM node/instance, keeping its state.
- Different **type** → **destroy** the old subtree (losing state) and **create** a new one.
- In lists, **`key`** tells React which item is which across renders (07.11).

This explains a famous bug: defining a component **inside** another component's body gives it a **new function identity** on every render → "different type" → React destroys and recreates it every time (losing focus and state). You'll debug the styled-components version in 09.15.

## 6. Why components must be pure (and what StrictMode does about it)

Because React may call your component functions **more than once**, at times it chooses, and may throw away a result, the render phase must have **no side effects**:

```tsx
// ❌ impure: mutates outside data during render
let renderCount = 0;
function Counter() {
  renderCount++;
  return <p>{renderCount}</p>;
}
```

In development, **`StrictMode` renders components twice** to make impurity visible (the count jumps by 2). That's a feature: code that breaks under double rendering has a real bug that would appear in rarer situations in production.

Side effects (fetching data, subscriptions, timers, DOM measurements) belong in **event handlers** or **effects** (S08), not in the render body.

## 7. Summary

- Component = function; element = description object; instance = a position in React's tree with state.
- **Render** (compute + diff, pure) vs **commit** (apply minimal DOM changes, then effects).
- Re-render ≠ DOM update.
- Renders are triggered by state updates, context changes and parent re-renders.
- Reconciliation matches by position, type and key; a changed type destroys state.
- Keep render pure; StrictMode double-renders in development to expose impurity.

## 8. Check yourself

1. When a parent re-renders, do its children re-render? Does the DOM change?
2. Why must you never define a component inside another component's body?
3. Is it OK to `fetch()` inside a component body?

<details>
<summary>Answers</summary>

1. Children **re-render** by default (their functions run). The DOM changes **only** where their output differs.
2. Each render creates a new function → a new component **type** → React unmounts and remounts it, losing state and focus, and doing extra work.
3. **No.** That's a side effect during render (and it would run on every render, twice in StrictMode). Use an effect (S08) or a data layer (RTK Query, S22).

</details>
