# Lecture 07.13 · Composition, Lifting State Up, and "Thinking in React"

> **Section:** S07 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> 🔗 Official reading: react.dev → Learn → "Thinking in React", "Sharing State Between Components"

---

## 1. Composition over inheritance

React components don't extend each other. You build bigger components by **putting components inside components**:

- **Specialisation by props:** `Button` with `variant="danger"` instead of a `DangerButton` subclass.
- **Containment with `children`:** `PageLayout` renders whatever you put inside it (07.05).
- **Slots with named props:** `<PageLayout title="Tasks" subtitle={<Counter/>}>`, where any prop can hold elements.

This is why a Java developer's reflex (base class + subclasses) doesn't apply to React UI. You'll almost never write `class X extends Y` in React.

## 2. Lifting state up

**Problem:** two sibling components need the same changing data. `FilterBar` sets the filter; `TaskList` needs the filtered tasks; the title shows the count.

**Rule:** put the state in the **closest common parent**, then pass it **down** as props and pass **callbacks** down so children can request changes.

```text
                 App  ← owns tasks + statusFilter
         ┌────────┼─────────────┐
   PageLayout  FilterBar      TaskList
   (count)    value/onChange  tasks/onToggle
                                  │
                               TaskCard (onToggle)
```

That's exactly what you built in 07.12. Neither `FilterBar` nor `TaskList` knows the other exists. They communicate **through** `App`.

### Controlled vs uncontrolled components

- **Controlled:** the parent owns the value (`value` + `onChange` props). `FilterBar` is controlled. Easy to coordinate and reset.
- **Uncontrolled:** the component keeps its own internal state. Simpler, but the parent can't read or set it.

You'll meet the same distinction with form inputs in S11.

## 3. "Thinking in React": the five steps (applied to TaskFlow)

1. **Break the UI into a component hierarchy.** `App > PageLayout > (FilterBar, TaskList > TaskCard > (StatusBadge, PriorityBadge, Button))`.
2. **Build a static version** with props only (07.06).
3. **Find the minimal state:** `tasks` and `statusFilter`. Not `visibleTasks` (derived), not the count (derived).
4. **Decide where each piece of state lives:** the closest common parent of everything that uses it → `App`.
5. **Add inverse data flow:** callbacks (`onToggle`, `onChange`) from children to the state owner.

These steps are also the basis for deciding what goes into **Redux** later (S14–S15): global state is state whose "closest common parent" is effectively the whole app.

## 4. Summary

- Compose components with props, `children` and slot props; no inheritance.
- Shared changing data → lift state to the closest common parent; pass values down and callbacks down.
- Controlled components receive `value` + `onChange`.
- Thinking in React: hierarchy → static → minimal state → where it lives → inverse data flow.
