# Lecture 21.16 · Listeners vs Thunks vs Custom Middleware: Choosing the Right Tool

> **Section:** S21 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes

---

## 1. Three tools that can all "do something async with the store"

| | Thunk (`createAsyncThunk`) | Listener | Custom middleware |
|---|---|---|---|
| **Starts when** | code **dispatches it** (usually a component) | a matching **action** or **state change** happens | **every** action passes through it |
| **Caller gets a result** | yes: a promise of the final action, `.unwrap()` | no: `dispatch` returns immediately | whatever the middleware returns |
| **Sees the action before the reducers** | — | no (runs after) | yes (can modify, delay, **block** it) |
| **Built-in async helpers** | lifecycle actions, `signal`, `condition` | `delay`, `take`, `condition`, `fork`, `cancelActiveListeners`, `signal` | none: you write it |
| **Typical use** | "load / save **this**, and tell me how it went" | "**whenever** X happens, do Y" | cross-cutting concerns on **all** actions: logging, crash reporting, analytics |
| **TaskFlow examples** | `fetchTasks`, `saveTask`, `deleteTask` | save toasts, quick find | logger, crash reporter, analytics (S16) |

## 2. Decision questions

1. **Does the caller need the result** (navigate after save, show field errors)? → **thunk**.
2. **Is it a reaction** to something that happened, independent of who caused it? → **listener**.
3. Does it need **"latest wins"** cancellation or a multi-step workflow (wait for A, then B, with a timeout)? → **listener**.
4. Does it apply to **every** action, or must it change or stop actions **before** the reducers? → **middleware**.
5. Is it **fetching and caching server data** that several components read? → none of these: **RTK Query** (S22).

## 3. Combining them is normal

The save flow in TaskFlow uses all three:

```text
TaskForm submit
  → dispatch(saveTask(...)).unwrap()        THUNK: does the PUT, the page awaits it
      → 'tasks/save/pending' / 'fulfilled'   through every MIDDLEWARE (logger, crash reporter, analytics)
      → reducers upsert the task
      → LISTENER sees 'tasks/save/fulfilled' → dispatches toastShown("Saved: …")
  → the page navigates to the details
```

Each tool does the part it's best at.

## 4. Anti-patterns

- A thunk that exists only to be dispatched **after another action** (`useEffect` watching state, then dispatching): that's a listener, without the component in the middle.
- A listener whose effect only computes something from state and stores it: that's a **selector**.
- A custom middleware re-implementing debouncing or cancellation: that's a listener.
- A listener that a component waits for (polling state until the effect is done): the component wanted a thunk.

## 5. Summary

- Thunks: started by callers, return results.
- Listeners: reactions to actions or state changes, with cancellation and workflow helpers.
- Middleware: every action, before the reducers.
- Server cache: RTK Query.
