# Lecture 21.02 · Why Selectors Need Memoization: New References Mean Re-Renders

> **Section:** S21 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> Verified: the recomputation counts in §3 come from `src/verification/s21-selectors-and-listeners.claims.test.ts`.

---

## 1. How `useSelector` decides to re-render (recap of 17.04)

After every dispatch, React-Redux runs each mounted component's selector and compares the result with the previous one using **`===`** (reference equality, by default). Different → re-render; same → nothing.

So what a selector **returns** decides how often its component renders:

| Selector returns | After an unrelated action (a toast) |
|---|---|
| a primitive (`state.tasks.status`, a count) | the same value → `===` → no re-render |
| an existing object from the state (`state.tasks.entities`) | the same reference (Immer kept it, 20.05) → no re-render |
| a **new** array or object (`tasks.filter(…)`, `{ total, done }`) | a new reference every time → **re-render**, even if the content is equal |

## 2. The bug in one line

```ts
const selectDoneTasks = (state: RootState) => selectTasks(state).filter((t) => t.status === 'DONE');
```

Every call creates a new array. React-Redux notices it too: in development, `useSelector` warns *"Selector unknown returned a different result when called with the same parameters. This can lead to unnecessary rerenders."* (17.15). And every toast, every keystroke in the quick find, every sort change re-renders this component and all of its children.

## 3. Memoized: new reference only when the input changed

```ts
const selectDoneTasks = createSelector([selectTasks], (tasks) => tasks.filter((t) => t.status === 'DONE'));
```

Verified (claims test, *"unrelated changes return the cached result"*): with the same `tasks` array in two different root states, the selector returned the **same** array, and the filter ran **once**.

That's the whole point: `createSelector` turns "same inputs" into "same output reference", and "same output reference" into "no re-render".

## 4. It's not about speed (usually)

Filtering 22 tasks takes microseconds. Memoizing it saves almost no **computation**. What it saves is the **re-render** of everything below the component that selected the new array. That's why the rule is about **returned references**, not about expensive code:

- A selector that returns a **new object or array** must be memoized (or return primitives instead).
- A selector that returns a **primitive** or an **existing reference** doesn't need `createSelector` (21.09 §2).

## 5. Where TaskFlow stood at the end of S20

- `selectTasks` and the category selectors were memoized (19.02).
- But `TasksPage` filtered the list **in render** (`filterTasks(items, …)`), and passed **new** `task` objects and **new** callbacks to cards that weren't memoized. Every render of the page re-rendered all 22 cards (measured in 21.03).

The next lecture measures that before changing anything.

## 6. Summary

- `useSelector` re-renders on a **new reference**.
- `filter`, `map`, `{…}` in a selector = a new reference on every call = a re-render on every action.
- `createSelector` returns the cached reference while its inputs are unchanged.
