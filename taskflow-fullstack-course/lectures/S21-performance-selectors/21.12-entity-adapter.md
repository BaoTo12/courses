## 1. You already wrote an entity adapter

In S19 you normalised tasks by hand: `{ ids: number[], entities: Record<number, Task> }`, plus `normalize`, an `upsert` helper, `removeMany`, and memoized selectors to get an ordered array back. That pattern is so common that RTK generates it:

| You wrote (S19–S20) | The adapter provides |
|---|---|
| the `{ ids, entities }` shape | `adapter.getInitialState(extra?)` |
| `upsert(state, task)`, `removeMany(state, ids)`, `normalize(tasks)` | `setOne`, `upsertOne`, `removeMany`, `setAll`, … (12 methods) |
| `selectTasks` (denormalize, memoized), `selectTaskById` | `getSelectors()` → `selectAll`, `selectById`, `selectIds`, `selectEntities`, `selectTotal` |

The **shape doesn't change**, which is why TaskFlow's migration (21.13) passed all tests without edits.

## 2. 📇 API card: `createEntityAdapter`

```ts
const adapter = createEntityAdapter<T>(options?)
```

| Option | Default | Meaning |
|---|---|---|
| `selectId` | `(entity) => entity.id` | how to get an entity's id; **required** by the types when `T` has no `id` field (verified with an `isbn` key) |
| `sortComparer` | `false` (unsorted: `ids` keep insertion / `setAll` order) | `(a, b) => number`; when given, `ids` are kept sorted after **every** insert and update (verified) |

**State**

```ts
adapter.getInitialState()                           // { ids: [], entities: {} }
adapter.getInitialState({ status: 'idle' })         // + your extra fields
adapter.getInitialState({ status: 'idle' }, items)  // + initial entities (verified)
```

**CRUD methods.** Each has two forms: `(state, argument)`, or `(state, action)` using `action.payload`. So a method can be a **case reducer directly** (`reducers: { bookAdded: adapter.addOne }`, verified). Inside a slice they mutate the draft; called standalone they return a **new** state (verified).

| Method | Argument | Behaviour (verified where marked ✓) |
|---|---|---|
| `addOne` / `addMany` | entity / entities | add; an **existing id is ignored**, not replaced ✓ |
| `setOne` / `setMany` | entity / entities | add or **replace entirely** ✓ |
| `setAll` | entities | replace **everything**; `ids` in the given order ✓ |
| `upsertOne` / `upsertMany` | entity / entities | add, or **shallow-merge** into the existing one ✓ |
| `updateOne` / `updateMany` | `{ id, changes }` / array of them | merge `changes` into an existing entity; unknown ids are ignored ✓ |
| `removeOne` / `removeMany` | id / ids | remove ✓ |
| `removeAll` | — | empty `ids` and `entities`, keep your extra fields ✓ |

**Selectors**

```ts
const { selectAll, selectById, selectIds, selectEntities, selectTotal } =
  adapter.getSelectors((state: RootState) => state.books);   // bound to the root state
adapter.getSelectors();                                       // unbound: take the entity state itself
```

`selectAll` is memoized (same array until `ids` or `entities` change, verified). `getSelectors` also accepts `{ createSelector }` as a second argument to use your own `createSelector`.

**Minimal example (outside TaskFlow)**

```ts
const booksAdapter = createEntityAdapter<Book>({ sortComparer: (a, b) => a.title.localeCompare(b.title) });

const booksSlice = createSlice({
  name: 'books',
  initialState: booksAdapter.getInitialState({ status: 'idle' as 'idle' | 'loading' }),
  reducers: {
    bookAdded: booksAdapter.addOne,
    bookUpdated: booksAdapter.updateOne,
  },
  extraReducers: (builder) => {
    builder.addCase(fetchBooks.fulfilled, (state, action) => {
      booksAdapter.setAll(state, action.payload);
      state.status = 'idle';
    });
  },
});

export const { selectAll: selectAllBooks, selectById: selectBookById } =
  booksAdapter.getSelectors((state: RootState) => state.books);
```

## 3. Which "write" method? A decision table

| The data you have | Use |
|---|---|
| a full list from the server, replacing what you had | `setAll` |
| one **complete** entity from the server (after POST/PUT/PATCH) | `setOne` (TaskFlow: the server returns the whole task) |
| a **partial** entity that may or may not exist yet | `upsertOne` |
| a change to an entity you know exists | `updateOne({ id, changes })` |
| a new entity that must **not** overwrite an existing one | `addOne` |

The classic bug: `upsertOne` with an entity whose field was **removed** on the server (`dueDate` omitted instead of `null`): the shallow merge keeps the old value. With complete server objects, `setOne` is the safe choice.

## 4. `sortComparer`: sorted ids, or a sorting selector?

- **`sortComparer`**: `ids` are always sorted by **one** fixed order; every insert and update re-sorts. Good for a canonical order (messages by date).
- **A sorting selector** (TaskFlow's `selectSortedTasks`, 21.05): the order depends on a **user preference** that changes at runtime. `ids` keep the server's order, the selector sorts.

TaskFlow uses no `sortComparer`, because the order is a preference.

## 5. When to use it, when not

**Use it when** a slice holds a **collection of records with ids** that you look up by id and update one at a time.

**Don't use it when** the collection is tiny and never looked up by id (TaskFlow's toasts), or when the data is **server cache** managed by RTK Query (S22). RTK Query keeps its own cache; you'd only use an adapter inside `transformResponse` for normalised lookups (S23).

## 6. Common mistakes

- `addOne` to "update" (it silently ignores existing ids).
- `upsertOne` with partial server data that omits cleared fields.
- Calling `adapter.getSelectors()` **inside a component**: it creates new memoized selectors on every render. Create them once at module level.
- Mutating `state.entities[id]` and forgetting `ids` when adding: use the adapter methods, which keep both in sync.

## 7. Summary

- `createEntityAdapter` = the S19 normalised shape + 12 CRUD methods + 5 selectors.
- Methods work standalone, on drafts, or directly as case reducers.
- Choose `setAll` / `setOne` / `upsertOne` / `updateOne` / `addOne` by what data you have.
- `sortComparer` for a fixed order; a selector for a user-chosen order.
