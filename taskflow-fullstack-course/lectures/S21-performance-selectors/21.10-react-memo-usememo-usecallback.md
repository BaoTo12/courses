# Lecture 21.10 · `React.memo`, `useMemo`, `useCallback` in Depth: When They Help, When They're Noise

> **Section:** S21 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~40 minutes
> Verified (React 19.2, development build, 22 tasks): the three experiments in §4 were measured on TaskFlow's list with a temporary render counter (21.03 §3), removing one piece at a time.

---

## 1. Why a component re-renders

A function component renders again when:

1. its **own state** changes (`useState`, `useReducer`);
2. a **context** it reads changes;
3. an **external store** it subscribes to gives a new value (`useSelector`, which uses `useSyncExternalStore`);
4. its **parent** re-renders. By default, React re-renders **all children** of a component that rendered, whether their props changed or not.

Reason 4 is the one these three tools are about. Rendering is usually cheap; it becomes a problem for **many** children (a list of cards) or **expensive** ones (charts, big tables).

## 2. 📇 API cards

### `memo`

```ts
const MemoComponent = memo(Component, arePropsEqual?)
```

| Parameter | Meaning |
|---|---|
| `Component` | the component to memoize |
| `arePropsEqual(prevProps, nextProps)` | optional; return `true` to **skip** the render. Default: every prop compared with `Object.is` (a shallow comparison) |

**Returns** a component that, when its parent re-renders, **skips** rendering if its props are equal. It still re-renders for reasons 1–3 (its own state, context, store subscriptions).

- **Use it when** a component renders often with the **same props** and rendering it isn't trivial, typically **list items** and heavy widgets.
- **Don't use it when** the props change on almost every render anyway (the comparison is wasted), or for cheap leaf components rendered once.
- **Common mistakes:** passing a new object, array or function as a prop on every render (`style={{…}}`, `items={list.filter(…)}`, `onClick={() => …}`): the shallow comparison fails every time and `memo` does nothing (§4, experiment B). Writing a custom `arePropsEqual` that ignores a function prop can leave the component calling a **stale** callback.

### `useMemo`

```ts
const value = useMemo(calculateValue, dependencies)
```

| Parameter | Meaning |
|---|---|
| `calculateValue` | a pure function with no arguments, returning the value to cache |
| `dependencies` | every reactive value `calculateValue` uses; compared with `Object.is` to the previous render's |

**Returns** the cached value while the dependencies are unchanged; recalculates otherwise. In development with StrictMode, React calls `calculateValue` **twice** (to reveal impurity). React may also throw the cache away (the docs allow it), so use it for **performance**, never for correctness.

- **Use it when** (a) a calculation is measurably expensive, (b) the value is passed to a **memoized** child or used in another hook's dependencies and must keep its identity, or (c) you create something that must be created **once** per component instance (TaskFlow's per-column selector: `useMemo(() => makeSelectTaskIdsByStatus(), [])`, 21.07).
- **Don't use it when** the calculation is cheap and nobody compares the result's identity. And not for **Redux-derived data**: that belongs in a memoized **selector**, which also works outside components and is testable.
- **Common mistakes:** missing dependencies (a stale value; the lint rule `react-hooks/exhaustive-deps` catches this in ESLint setups); an object literal in the dependency array (never equal, recalculates every render).

### `useCallback`

```ts
const cachedFn = useCallback(fn, dependencies)   // ≈ useMemo(() => fn, dependencies)
```

**Returns** the **same function object** while the dependencies are unchanged. It doesn't make the function faster; it keeps its **identity** stable.

- **Use it when** the function is a prop of a **memoized** child (TaskFlow's `handleToggle` and `handleEditTitle` → every `TaskListItem`), or a dependency of another hook (`useEffect`, `useMemo`).
- **Don't use it when** the function goes to a non-memoized element (`<button onClick>`): the identity doesn't matter there.
- **Common mistakes:** a dependency that changes every render (then it's a new function every time anyway); reading state inside the callback without listing it (a stale closure). In TaskFlow, moving the "is the title different?" check into `TaskCard` (21.05) removed the callback's dependency on the task list, which is what made it stable.

## 3. How they fit together on the list

```text
TasksPage re-renders (a task changed)
  └─ TaskList (new ids array? only if the visible ids changed: resultEqualityCheck, 21.08)
       └─ TaskListItem ×22   memo: props { taskId, onToggle, onEditTitle } all the same → SKIP
            └─ except the toggled one: its useSelector(selectTaskById) returned a NEW task → renders
```

Each piece is necessary:

- `memo` → items can skip when the parent renders.
- `useCallback` → the function props really are the same.
- Selecting by **id** inside the item → only the item whose task changed gets new data.

## 4. The experiments (measured)

Toggling one task, then changing the sort, on the list of 22 cards (development: each real render counts twice because of StrictMode, 21.03):

| Version | Toggle one task | Change the sort |
|---|---|---|
| A. `memo` + `useCallback` (TaskFlow) | **1** card (2 renders) | **0** cards |
| B. `memo`, but `handleToggle` without `useCallback` | **22** cards (44 renders) | — |
| C. `useCallback`, but `TaskListItem` without `memo` | **22** cards (44 renders) | **22** cards (44 renders) |

Removing **either** piece brings back the S20 behaviour. That's the lesson: these tools work as a **set**, and one missing piece silently cancels the rest. Only a measurement shows it.

## 5. The React Compiler (know it exists)

React 19 has an optional build-time **React Compiler** (a Babel plugin) that inserts this memoization automatically. TaskFlow doesn't use it: you need to understand manual memoization to read existing code and to debug the compiler's output. If a project enables it, most hand-written `useMemo`/`useCallback` become unnecessary.

## 6. Summary

- `memo` skips re-renders caused by the parent when props are shallow-equal.
- `useCallback`/`useMemo` keep identities stable (and cache expensive values).
- They only help **together**, and only where measured.
- Derived Redux data goes in selectors, not in `useMemo`.
