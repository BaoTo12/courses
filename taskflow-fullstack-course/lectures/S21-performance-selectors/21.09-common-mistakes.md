# Lecture 21.09 · Common Selector Mistakes, and Memoizing Things That Don't Need It

> **Section:** S21 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> Verified: every "recomputes" / "same result" statement is a test in `src/verification/s21-selectors-and-listeners.claims.test.ts`.

---

## 1. Mistakes that make memoization fail

| # | Mistake | What happens (verified) | Fix |
|---|---|---|---|
| 1 | An input selector builds a value: `(s) => ({ tasks: s.tasks })`, `(s) => s.tasks.map(t => t.id)` | recomputes on **every new state** (every action); dev warning *"An input selector returned a different result…"* | input selectors only **extract**; move `map`/`{…}` into the result function |
| 2 | The result function returns its input: `createSelector([selectTasks], (tasks) => tasks)` | nothing gained; dev warning *"The result function returned its own inputs…"* | use `selectTasks` directly |
| 3 | An input selector returns an **object argument** itself: `(_s, filter) => filter` | a new `{ … }` per render → recomputes on every call (2 calls → 2 recomputations) | extract primitives: `(_s, f) => f.status` (4 calls → 1 recomputation) |
| 4 | A selector created **in the component body**: `const sel = createSelector(…)` | a new selector with an empty cache on every render | module level, or `useMemo(() => makeSelector(), [])` |
| 5 | One parameterised selector shared by many instances **with `lruMemoize` size 1** | thrashing: 4 alternating calls → 4 recomputations | a factory per instance, or the default memoizer (21.07) |
| 6 | `useSelector((s) => selectTasks(s).filter(…))` in a component | the memoized selector is followed by an **unmemoized** `filter`: a new array per call | put the `filter` in a memoized selector |

## 2. Memoizing things that don't need it

`createSelector` has a cost: two caches, the dev checks, memory for results. It's pure overhead for:

| Selector | Why no memoization |
|---|---|
| `(state) => state.tasks.status` | a primitive: `===` works already |
| `(state) => state.listPrefs.sort` | an existing reference |
| `(state, id) => state.tasks.entities[id]` | an existing reference (O(1) lookup) |
| `(state) => state.tasks.ids.length` | a primitive |
| a value used once in an event handler | nobody compares it: compute it where it's needed |

The rule from 21.02: memoize when you **create** new objects or arrays that components select.

### Memoizing `selectTaskById`?

Tempting, pointless: `state.tasks.entities[id]` already returns the **same** object until that task changes (Immer keeps unchanged entities, 20.05). A `createSelector` around it would add a cache lookup to get the same reference. (This is a 21.99 question.)

## 3. Returning primitives instead

Sometimes the best fix is to select **less**:

```ts
// re-renders whenever the tasks array changes
const doneCount = useAppSelector((s) => selectTasks(s).filter((t) => t.status === 'DONE')).length;
// re-renders only when the COUNT changes
const doneCount = useAppSelector((s) => selectTasks(s).filter((t) => t.status === 'DONE').length);
```

The second selector does the same work but returns a number, so `===` stops re-renders when an unrelated task field changes. TaskFlow's `OpenTasksBadge` (17.13) and the dashboard's completion rate (21.17) use this.

## 4. Summary

- Input selectors extract, result functions compute; no new objects in inputs.
- Create selectors once (module level or `useMemo`).
- Don't memoize reads and primitives.
- Selecting a primitive is often the simplest optimisation.
