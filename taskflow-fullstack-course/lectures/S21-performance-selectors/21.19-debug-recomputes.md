# Lecture 21.19 · 🐞 Debug: a `createSelector` That Recomputes on Every Action

> **Section:** S21 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~20 minutes
> Reproduced with reselect 5.3 (via RTK 2.12): the counts and the warning are pinned by `src/verification/s21-selectors-and-listeners.claims.test.ts` (*"an input selector that builds a new object"*).

---

## Symptom

A teammate adds a header widget, "Open: 16 · Sorted by: due date", with one selector "to keep things together":

```ts
export const selectHeaderInfo = createSelector(
  [(state: RootState) => ({ tasks: selectTasks(state), sort: state.listPrefs.sort })],
  ({ tasks, sort }) => ({ open: tasks.filter((t) => t.status !== 'DONE').length, sortKey: sort.key }),
);
```

The Profiler shows the widget re-rendering on **every** action: toasts, quick-find keystrokes, everything. In development the console also shows, once:

> An input selector returned a different result when passed same arguments. This means your output selector will likely run more frequently than intended. Avoid returning a new reference inside your input selector, e.g. `createSelector([state => state.todos.map(todo => todo.id)], todoIds => todoIds.length)`

A unit test that calls the selector **twice with the same state** passes ("same result"), which confuses everyone.

## Investigation checklist

1. What does the input selector return? Is it the same reference on two calls? (21.04 §2)
2. Why does calling it twice with the **same** state object return the cached result anyway? (the two caches)
3. What changes about `state` after a toast is dispatched?
4. How many `recomputations()` after dispatching three unrelated actions?

## Explanation

- The input selector builds `{ tasks, sort }`: a **new object** on every call.
- Called twice with the **same** `state` object, the **arguments cache** (`argsMemoize`) answers the second call before the input selector even runs. That's why the naive test passes (verified: `a === b`).
- But every dispatch creates a **new root state** (the `ui` slice changed, so the root object is new). New argument → the input selector runs → a new object → the result function runs → a **new** result object → `useSelector` sees a change → re-render. Verified: with a second root state (unrelated change), the selector recomputed and returned a different object.

So the bug appears in the app (a new state after every action) and hides in a test that reuses one state.

## Fix

Input selectors **extract**; the result function **combines**:

```ts
export const selectHeaderInfo = createSelector(
  [selectTasks, (state: RootState) => state.listPrefs.sort.key],
  (tasks, sortKey) => ({ open: tasks.filter((t) => t.status !== 'DONE').length, sortKey }),
);
```

Or, simpler, two selectors returning primitives: `selectOpenTaskCount` (already exists) and `(state) => state.listPrefs.sort.key`. No object, nothing to memoize.

### A test that would have caught it

```ts
const before = selectHeaderInfo(store.getState());
store.dispatch(toastShown({ tone: 'info', message: 'unrelated' })); // a NEW root state
expect(selectHeaderInfo(store.getState())).toBe(before);
expect(selectHeaderInfo.recomputations()).toBe(1);
```

Always test memoization **across an unrelated dispatch**, not by calling twice with the same state.

## Lessons

- Never build objects or arrays in input selectors; the dev warning points at exactly this.
- The arguments cache hides the bug in tests that reuse a state object.
- Selecting primitives is often the simplest fix.
