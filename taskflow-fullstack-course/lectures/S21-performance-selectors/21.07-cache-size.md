# Lecture 21.07 · Cache Size Pitfalls: One Selector, Many Components, Different Arguments

> **Section:** S21 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> Verified: recomputation counts from `src/verification/s21-selectors-and-listeners.claims.test.ts` and `taskListSelectors.test.ts`.

---

## 1. The classic problem

The board has three columns. Each needs "the ids of the tasks with **my** status". One shared, parameterised selector:

```ts
const selectTaskIdsByStatus = createSelector(
  [selectSortedTasks, (_state: RootState, status: TaskStatus) => status],
  (tasks, status) => tasks.filter((t) => t.status === status).map((t) => t.id),
);
```

Three components call it in turn with `'TODO'`, `'IN_PROGRESS'`, `'DONE'`, after every dispatch.

- With a cache of **size 1** (reselect 4's default, or `lruMemoize` today), each call **evicts** the previous column's result. Every call recomputes and returns a **new** array; every column re-renders after every action. Verified: 4 alternating calls → **4** recomputations. This is called **cache thrashing**.
- With reselect 5's default **`weakMapMemoize`**, results are cached **per argument set**. Verified: the same 4 calls → **2** recomputations; each column keeps getting its own cached array.

So in reselect 5, the shared selector is fine **for primitive arguments**. The problem hasn't disappeared, though:

- codebases still configure `lruMemoize` (to bound memory), and reselect 4 is still found in RTK 1.x apps;
- an **object** argument created per render defeats any cache unless the input selectors extract primitives (21.09);
- a per-argument cache keeps an entry for **every** distinct **primitive** argument until `clearCache()` (objects are released by garbage collection), unless you bound it with `maxSize` (21.08).

## 2. The robust pattern: a selector **factory**

Give each component instance its **own** selector:

```ts
export const makeSelectTaskIdsByStatus = () =>
  createSelector(
    [selectSortedTasks, (_state: RootState, status: TaskStatus) => status],
    (tasks, status) => tasks.filter((task) => task.status === status).map((task) => task.id),
    keepSameIds,
  );
```

```tsx
const BoardColumn = memo(function BoardColumn({ status, … }: BoardColumnProps) {
  // One selector INSTANCE per column (21.07): created once per mounted column, never shared.
  const selectTaskIdsByStatus = useMemo(() => makeSelectTaskIdsByStatus(), []);
  const taskIds = useAppSelector((state) => selectTaskIdsByStatus(state, status));
  …
});
```

- `useMemo(() => make…(), [])` creates the selector **once** per mounted column. Without `useMemo`, a new selector (with an empty cache) would be created on every render, which is worse than no memoization.
- Each instance only ever sees one status, so even a size-1 cache always hits.
- Verified (*"one instance per column, no thrashing"*): two instances, called after an unrelated action, returned their cached arrays; **2** recomputations in total.

TaskFlow's oxlint rule `react/use-memo` requires the inline arrow: `useMemo(makeSelect…, [])` is reported (*"Expected the first argument to be an inline function expression"*).

## 3. When to use which

| Situation | Choice |
|---|---|
| Argument is a primitive, few distinct values, reselect 5 defaults | a shared selector is fine |
| Many instances with different arguments (a column, a row), or `lruMemoize` in the project | a **factory** + `useMemo` per instance |
| Argument is a lookup key (`selectTaskById(state, id)`) and the result is an existing reference | no memoization at all |

## 4. Summary

- A size-1 cache thrashes when components alternate arguments; reselect 5's default caches per argument.
- A factory gives each component its own cache and works with any memoizer.
- Create the instance once: `useMemo(() => makeSelector(), [])`.
