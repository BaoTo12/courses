# Lecture 21.03 · 🛠 Measure First: the React Profiler, "Highlight Updates", and Render Counts

> **Section:** S21 · **Type:** 🛠 Build (measurement) · **Track:** ★ Core · **Time:** ~40 minutes
> Verified: the render counts in §4 were measured in the browser on the S20 code and on the S21 code, with the temporary counter shown in §3 (22 seed tasks, development build).

---

## 1. Rule: no optimisation without a measurement

"This is probably slow" is how codebases fill up with `useMemo` that does nothing. Measure, change one thing, measure again. Three tools, from the most visual to the most precise.

## 2. React DevTools (browser extension)

Install **React Developer Tools** for Chrome or Firefox. It adds two tabs to the browser's DevTools: *Components* and *Profiler*.

**Highlight updates.** In *Components* → ⚙ settings → *General* → **"Highlight updates when components render."** Every component that renders flashes with a coloured border. Toggle a task on TaskFlow's list: with the S20 code, **every card** flashes.

**The Profiler.**

1. Open the *Profiler* tab. In its ⚙ settings, enable **"Record why each component rendered while profiling."**
2. Click **Record** (the blue circle), do **one** interaction (toggle one task), click **Stop**.
3. The top bar shows one bar per **commit** (each time React applied changes to the DOM). Select a commit.
4. The **flame graph** shows the component tree for that commit. **Grey** components did **not** render; coloured ones did (the colour is the time taken). Hover or select a component to see *"Why did this render?"*: *"Props changed: (task, onToggle)"*, *"Hook 1 changed"*, *"The parent component rendered"*.

What to look for: components that rendered although **their** data didn't change. On the S20 list, a toggle shows **all 22** `TaskCard`s coloured, and the reasons point at the parent (the page re-rendered and passed new callback props), not at the cards' own tasks. (The exact wording of the reasons varies between DevTools versions; the numbers in §4 come from the counter in §3, which doesn't.)

## 3. Counting renders precisely (temporary code)

The DevTools are visual. To get **numbers** you can compare before and after, count renders with a throwaway line, and **delete it afterwards**:

```ts
// TEMPORARY, at the top of the component body (TaskCard in S20, TaskListItem in S21)
((window as any).__renders ??= {})[task.id] = ((window as any).__renders[task.id] ?? 0) + 1;
```

Then in the browser console:

```js
window.__renders = {};                       // reset
// … do ONE interaction …
Object.values(window.__renders).reduce((a, b) => a + b, 0); // total renders
Object.keys(window.__renders).length;                       // how many different cards
```

React also has a built-in **`<Profiler>`** component for this, usable in code and tests:

```tsx
<Profiler id="dashboard" onRender={(id, phase, actualDuration) => console.log(id, phase, actualDuration)}>
  …
</Profiler>
```

`onRender` runs once per **commit** of that subtree, with `phase` = `'mount'` or `'update'`. The 21.17 solution uses it to prove that unrelated actions cause **zero** commits on the dashboard.

### StrictMode doubles the numbers in development

TaskFlow renders inside `<StrictMode>` (main.tsx), which in development calls every component function **twice** per render to reveal impure code. So in development, a counter inside a component counts **2** per real render. Compare numbers taken in the same mode, or divide by two. (The Profiler's commit count isn't doubled.)

## 4. The baseline (S20) and the target (S21)

Measured on the list page with 22 tasks:

| Interaction | S20 code | S21 code (after 21.05 and 21.11) |
|---|---|---|
| Initial load | 44 card renders (22 cards × 2, StrictMode) | 44 (same: every card must render once) |
| Toggle **one** task | **44** renders, all **22** cards | **2** renders, **1** card (the toggled one) |
| Change the sort (S21 only: the sort control arrives in 21.05) | — | **0** card renders: the cards are only re-ordered |
| A toast appears and auto-dismisses | 0 | 0 |

Why S20 re-rendered everything: `TasksPage` re-renders when `selectTasks` returns a new array (a task changed). It then renders `TaskList` with a new filtered array, which renders every `TaskCard`. None of them is memoized, so each re-renders because its parent did. Even with `React.memo`, the page passed **new callbacks** each render (`handleToggle` was a plain function), which would have defeated it (21.10).

The toast row is 0 in both versions for a good reason: `TasksPage` doesn't select anything that a toast changes (the `ui` slice isn't read there), so it doesn't re-render at all.

## 5. What you'll change, and why each piece is needed

1. **Selectors that return stable references**: the visible ids as a memoized array (21.05).
2. **Cards connected by id**: each item selects its own task, so only the changed task's item gets a new value from `useSelector` (21.11).
3. **`React.memo`** on the item, so a parent re-render with the same props skips it (21.10).
4. **Stable callbacks** (`useCallback`), so the props really are the same (21.10).

Remove any one of the four, and the measurement goes back up. That's why you measure after each change.

## 6. Summary

- Measure with the React DevTools (highlight updates, Profiler with "why did this render"), or count with a temporary counter or `<Profiler>`.
- In development, StrictMode renders twice: compare like with like.
- S20: one toggle = 22 cards re-rendered. The goal for S21: 1.
