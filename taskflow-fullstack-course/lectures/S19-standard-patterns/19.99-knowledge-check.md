## A. Concept

1. What problems does normalisation solve? When is it overkill? [19.05]
2. Why is `'idle' | 'loading' | 'succeeded' | 'failed'` better than `isLoading` + `hasError` + `isLoaded`? [19.03]
3. What does `createSelector` compare to decide whether to recompute? What must input selectors never do? [19.02]
4. Where do timestamps and generated ids come from in TaskFlow, and why not from reducers? [19.01]

## B. Code reading

5. Write the reducer case that renames task 5 immutably in normalised state (`{ ids, entities }`). Which references change, and which stay the same? [19.06]
6. Why does this selector cause a re-render after every action, and how do you fix it? [19.02, 17.15]
   ```ts
   const selectDoneTasks = (state: RootState) => selectTasks(state).filter((t) => t.status === 'DONE');
   ```
7. In reselect 5, a selector `selectTasksByCategory(state, categoryId)` is called with 1, then 2, then 1. How many times does the result function run? And in reselect 4? [19.02]

## C. Debugging

8. After renaming a category, three cards show the old name until reload. Diagnose and fix without adding more reducer cases. [19.13]
9. The details page of a task shows "Page not found" for a split second after a direct visit to `/tasks/5`. Which status check is missing? [19.04]

## D. Design

10. Where do you generate ids for optimistically created entities, and for server-created entities? [19.01]
11. A 400 response says `{"fieldErrors": {"title": "…", "ownerId": "…"}}`. Why does `pickFormErrors` drop `ownerId`, and why do server field errors live in form **state** rather than being derived? [19.09]

## E. Implementation

12. Write `selectTasksWithCategory`: a memoised selector returning `{ task, category }[]` view models, with `category` `undefined` for uncategorised tasks. Test that (a) the join is right, (b) an unrelated action returns the same array, (c) renaming a category is reflected.

<details>
<summary><b>Answers</b></summary>

1. **Solves:** O(1) lookups by id; updates that touch one entity (and leave `ids`, the "list", unchanged, so fewer re-renders); **no duplicated data** (each fact stored once, related data referenced by id), so no stale copies. **Overkill:** small collections always rendered whole, never looked up by id, with no relations (TaskFlow's toasts), or server data managed by RTK Query's cache.

2. Four named, mutually exclusive states instead of eight boolean combinations, several of them contradictory. Each event sets one field; components branch on explicit names; "idle" (never requested) is distinguishable from "loading" (don't start another request, 18.09).

3. The **results of its input selectors**, by reference (`===`). If all are the same as last time, it returns the cached result. Input selectors must return existing references (`state.tasks.ids`), never build new arrays or objects (`filter`/`map`), or the cache never hits.

4. In **action creators** (`allCompleted(updatedAt = new Date().toISOString())`, `toastShown` assigning `nextToastId++`), in **thunks** (`extra.nextRequestId()`), or from the **server** (task ids, `updatedAt`). Reducers must be deterministic: replaying the same actions must produce the same state (time travel, tests).

5. ```ts
   case 'tasks/taskRenamed': {
     const { id, title } = action.payload;
     const task = state.entities[id];
     if (!task) return state;
     return { ...state, entities: { ...state.entities, [id]: { ...task, title } } };
   }
   ```
   **New:** the slice object, `entities`, and task 5's object. **Same:** `ids` (the order didn't change) and every other task object. That's why components selecting `ids`, or other tasks, don't re-render.

6. `filter` creates a new array on every call, so `useSelector` sees a change after every action. Fix: `createSelector([selectTasks], (tasks) => tasks.filter((t) => t.status === 'DONE'))`. It recomputes only when `selectTasks` returns a new array, which is itself memoised.

7. **Twice** in reselect 5: its default `weakMapMemoize` caches a result per argument set, so the third call (argument 1 again) hits the cache (verified: 2 recomputations, and the same array returned). In reselect 4 (its `defaultMemoize`, cache size 1; renamed `lruMemoize` in v5), **three** times: each new argument evicted the previous result.

8. The category name was **copied** into tasks (denormalised): the categories slice was updated, the copies weren't. Fix: store only `categoryId` in tasks and join when reading (`selectCategoryById` in a small component, or a memoised view-model selector). One copy of the name, so a rename updates everything (verified: all 5 cards changed).

9. The page decides "not found" before the data has loaded. Check the status first: `if (!task && (status === 'idle' || status === 'loading')) return <Loading/>;`, and only then `if (!task) return <NotFoundPage/>;`.

10. **Server-created:** the server assigns the id, and the client adds the entity only after the response (pessimistic), or replaces a temporary one. **Optimistic:** the client generates a **temporary** id (in the action creator or thunk, never the reducer), shows the entity immediately, and on success replaces the temporary entity with the server's (new id), or removes it on failure (23.04).

11. The server's object is **untrusted input**: `ownerId` isn't a field of this form, and showing or processing unknown keys would be wrong (or, with a hostile server or proxy, dangerous). `pickFormErrors` allowlists the form's fields. Server errors are **state** because they come from an event (a response), not from the current values: they can't be recomputed from `values` the way client validation can, and they must be cleared when the user edits that field.

12. Verified (all three assertions pass):
    ```ts
    export interface TaskWithCategory {
      task: Task;
      category: Category | undefined;
    }

    export const selectTasksWithCategory = createSelector(
      [selectTasks, (state: RootState) => state.categories.entities],
      (tasks, categories): TaskWithCategory[] =>
        tasks.map((task) => ({ task, category: task.categoryId === null ? undefined : categories[task.categoryId] })),
    );
    ```
    ```ts
    it('joins tasks with categories, memoised', () => {
      const store = makeStore({ tasks: { ...normalize([t(1, 1), t(2, null)]), status: 'succeeded', error: null, currentRequestId: null, fetchedAt: 1 } });
      store.dispatch(categoriesFetchSucceeded([{ id: 1, name: 'Work', color: '#2563eb' }]));
      const first = selectTasksWithCategory(store.getState());
      expect(first.map((vm) => `${vm.task.id}:${vm.category?.name ?? '-'}`)).toEqual(['1:Work', '2:-']);
      store.dispatch(toastShown({ tone: 'info', message: 'x' }));
      expect(selectTasksWithCategory(store.getState())).toBe(first);          // (b) same array
      store.dispatch(categoriesFetchSucceeded([{ id: 1, name: 'Office', color: '#2563eb' }]));
      expect(selectTasksWithCategory(store.getState())[0]?.category?.name).toBe('Office'); // (c)
    });
    ```
    The input selectors are `selectTasks` (memoised) and `state.categories.entities` (an existing reference): both stable between unrelated actions.
