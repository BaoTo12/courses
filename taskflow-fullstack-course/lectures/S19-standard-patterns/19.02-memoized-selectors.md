# Lecture 19.02 · Memoised Selectors: the Problem (New Arrays Every Call) and a First `createSelector`

> **Section:** S19 · **Type:** 📖 Theory + 🛠 Build · **Track:** ★ Core · **Time:** ~35 minutes
> 🔗 Official companion reading: Fundamentals Part 7 ("Memoizing Selectors with createSelector"); the Redux docs page "Deriving Data with Selectors"
> Verified by the tests in §4 (reselect **5.3.0**).

---

## 1. The problem, again

17.04 and 17.15 showed it: a selector that builds a new array or object on every call makes `useSelector` re-render its component after **every** action. And with normalised state (19.05), even "the list of tasks" has to be **built** from `ids` and `entities`:

```ts
const selectTasks = (state: RootState) => state.tasks.ids.map((id) => state.tasks.entities[id]); // new array every call
```

We need a selector that returns the **same array** until its inputs change.

## 2. Memoisation

**Memoisation** = cache a function's result, keyed by its inputs. Called again with the same inputs, it returns the cached result (the same reference) without recomputing.

`createSelector` from **reselect** builds memoised selectors:

```ts
import { createSelector } from 'reselect';

export const selectTasks = createSelector(
  [selectTaskIds, (state: RootState) => state.tasks.entities],   // 1. INPUT selectors: cheap, return existing references
  (ids, entities) => denormalize({ ids, entities }),             // 2. RESULT function: runs only when an input changed
);
```

1. On each call, reselect runs the **input selectors**.
2. It compares their results with the previous call's, by reference (`===`).
3. If all are the same, it returns the **cached** result: the same array as last time.
4. Otherwise it runs the result function and caches the new result.

Install it:

```bash
npm install reselect@5
```

(This installs **reselect 5.3.0**. Redux Toolkit re-exports `createSelector` from it, so you'll import it from `@reduxjs/toolkit` from S20.)

## 3. The rules for input selectors

- **Return existing references** (`state.tasks.ids`, `state.tasks.entities`). Never `filter`/`map` in an **input** selector: that would change every time and defeat the cache.
- **Keep them cheap**: they run on every call.
- The **result function** is where the work goes (mapping, filtering, sorting, counting).

## 4. 🔬 Verified: same reference until the data changes

From `tasksSlice.test.ts`:

```ts
it('selectTaskById is a lookup; selectTasks is memoised', () => {
  const store = makeStore({ tasks: loaded(task(1), task(2)) });
  expect(selectTaskById(store.getState(), 2)?.title).toBe('Task 2');

  const first = selectTasks(store.getState());
  expect(first.map((t) => t.id)).toEqual([1, 2]);
  // An unrelated action: the tasks slice is unchanged → the SAME array is returned.
  store.dispatch({ type: 'ui/selectionCleared' });
  expect(selectTasks(store.getState())).toBe(first);
  // A task changes → a new array (with the new task object).
  store.dispatch(taskUpdated(task(2, { title: 'Changed' })));
  const second = selectTasks(store.getState());
  expect(second).not.toBe(first);
  expect(second[1]?.title).toBe('Changed');
});
```

And `selectTaskCountsByCategory` (19.11) returned the **same object** after a `ui/toastShown`: the sidebar using it doesn't re-render for toasts.

## 5. Where memoisation matters, and where it doesn't

- ✅ Selectors that return **new arrays or objects** (lists, joins, groupings) used with `useSelector`.
- ✅ **Expensive** derivations (sorting 1,000 tasks) called often.
- ❌ Selectors that return a **primitive** or an **existing reference** (`selectTasksStatus`, `selectTaskById`): nothing to gain.
- Selectors **with arguments** (`selectTasksByCategory(state, categoryId)`): in reselect **5**, the default memoizer (`weakMapMemoize`) keeps a result **per set of arguments**. Verified: calling with 1, then 2, then 1 recomputed only **twice**, and the third call returned the same array as the first. (Reselect 4, still common in codebases, cached only **one** result, so alternating arguments recomputed every time.) S21 covers the options and their memory trade-offs.

## 6. Summary

- `createSelector([inputs…], result)`: recompute only when an input reference changes; otherwise return the cached (same) result.
- Input selectors return existing references; the work goes in the result function.
- TaskFlow now has `selectTasks`, `selectCategories` and `selectTaskCountsByCategory` memoised. S21 goes deeper.
