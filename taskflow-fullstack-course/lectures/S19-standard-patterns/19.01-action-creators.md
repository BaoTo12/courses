# Lecture 19.01 · Action Creators: Why They Exist, Consistency, and "Prepare" Logic Outside Reducers

> **Section:** S19 · R6: Standard Redux Patterns
> **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> 🔗 Official companion reading: Redux **Fundamentals, Part 7** ("Standard Redux Patterns": action creators)

---

## 1. Recap: what TaskFlow's action creators already do

Since S15, every action is built by a creator in its slice file:

```ts
export const taskDeleted = (id: number): TasksActionOf<'tasks/taskDeleted'> => ({ type: 'tasks/taskDeleted', payload: id });
```

The official tutorial lists three reasons to use them, and you've now met all three:
1. **Consistency.** The `type` string and payload shape are written once. Call sites can't misspell `'tasks/taskDeleted'`, and TypeScript checks the argument.
2. **Encapsulation.** Callers pass domain values (`id`, `task`); the creator decides the action's structure. Changing the payload shape changes one function.
3. **Preparation.** Values that must not be computed in reducers are computed **in the creator**.

## 2. "Prepare" logic: the non-deterministic parts

Reducers must be deterministic (15.04). So anything random, time-based, or generated goes into the creator:

| Value | TaskFlow's creator | Why not in the reducer |
|---|---|---|
| A timestamp | `allCompleted(updatedAt = new Date().toISOString())`, `fetchSucceeded(requestId, tasks, fetchedAt = Date.now())` | Replay would produce different times |
| A generated id | `toastShown(input)` assigns `id: nextToastId++` | Replays would create different ids; two tabs would disagree |
| A request id | `extra.nextRequestId()` in the thunk (18.11) | Same, plus tests need predictable ids |

The default-parameter pattern (`updatedAt = new Date().toISOString()`) gives the best of both: production code calls `allCompleted()`, and tests call `allCompleted('2026-10-01T10:00:00Z')` and get exact, repeatable results (15.11).

RTK's `createSlice` formalises this as a **`prepare` callback** (S20): a function that turns the creator's arguments into `{ payload, meta }` before the action is built. It's the same idea, with a name.

## 3. IDs: who generates them?

- **Server-created entities** (tasks, comments): the **server** assigns the id (the POST returns it: 18.07). The client never invents one.
- **Client-only entities** (toasts): the client generates the id **in the creator**.
- **Optimistic creation** (adding a task to the UI before the server answers, 23.04): the client needs a **temporary** id, created in the creator or thunk, and replaced by the server's id when the response arrives. That's why optimistic updates need extra care.

## 4. Summary

- Action creators give consistency, encapsulation, and a home for "prepare" logic.
- Time, random values and generated ids are computed in creators (or thunks), never in reducers.
- Server entities get server ids; client-only entities get creator-generated ids.
