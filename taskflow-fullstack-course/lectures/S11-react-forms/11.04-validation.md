# Lecture 11.04 · Validation: When to Validate, and How to Model Errors

> **Section:** S11 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes

---

## 1. When to show errors (the UX question)

| Strategy | Feels like | Problem |
|---|---|---|
| **On every keystroke, immediately** | Nagging: "Title is required" before you've typed anything | Hostile |
| **Only on submit** | Clean, but late | You fill 10 fields, then get 5 errors |
| **After the field is left (blur), then live** | Calm, then helpful | ← TaskFlow |
| **After the first submit attempt, then live everywhere** | Clear | ← TaskFlow (combined with blur) |

The rule TaskFlow uses: **show a field's error once it has been "touched" (blurred) or after a submit attempt; from then on, update it live as the user types.**

## 2. Errors are derived, not stored

Given the current values, the errors are fully determined. So compute them **during render** (08.05):

```tsx
const errors = validateTaskForm(values, localToday(), mode === 'create');
```

Don't `useState` the errors and sync them with an effect: that's two sources of truth, and errors would lag one render behind.

What *is* state: which fields were **touched**, and whether a submit was **attempted**, because those record user **history**, not a function of the values.

```tsx
const [touched, setTouched] = useState<Partial<Record<keyof TaskFormValues, boolean>>>({});
const [submitAttempted, setSubmitAttempted] = useState(false);

const visibleError = (field: keyof TaskFormValues) =>
  touched[field] || submitAttempted ? errors[field] : undefined;
```

## 3. Modelling errors with types

```ts
export type TaskFormErrors = Partial<Record<keyof TaskFormValues, string>>;
```

- `Record<keyof TaskFormValues, string>` → one message per field…
- `Partial<…>` → …but only for fields that have an error (06.03).
- `errors.titel` is a compile error; the keys are the form's fields.

This shape deliberately matches the backend's `ApiError.fieldErrors` (06.04): `{ "title": "must not be blank" }`. In S48 server field errors will be merged into the same display.

## 4. Where validation lives

- **The rules**: a pure function in `domain/task-form.ts`, testable and reusable (the edit form uses the same rules).
- **The display policy** (touched/submitted): in the component.
- **The authoritative check**: on the **server** (11.08, S37, S46). Client validation is for the user's convenience.

## 5. Summary

- Show errors after blur or submit attempt, then live.
- Errors are **derived** from values; touched/submitted are **state**.
- `Partial<Record<keyof Values, string>>` types field errors and mirrors the API's `fieldErrors`.
- Rules in pure functions; the server re-validates.
