# Lecture 11.07 · Accessibility Basics for Forms: Labels, `aria-invalid`, `aria-describedby`, Focus

> **Section:** S11 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes

---

## 1. Why it matters (and why it's part of "correct")

Forms are where inaccessible UIs hurt most. A screen-reader user who can't tell which field is invalid **can't complete the task at all**. Many organisations, especially public-sector clients and large enterprises, have **legal accessibility requirements** (e.g. WCAG 2.x conformance). Treat accessibility as correctness, not decoration.

## 2. The checklist TaskFlow's form meets

| Requirement | How |
|---|---|
| Every control has a **programmatic label** | `<label htmlFor={id}>` + `id` from `useId` (08.14) |
| Invalid state is **announced**, not only coloured | `aria-invalid="true"` (also drives the red styling, 02.11) |
| The error text is **associated** with the field | `aria-describedby` → error id (and help id) |
| Errors are **text**, not colour alone | `.form-field__error` paragraph |
| Keyboard works everywhere | Native `input`/`select`/`button`; visible `:focus-visible` rings (02.06) |
| Status messages are announced | "Unsaved changes" with `aria-live="polite"`; toasts with `role="status"` / `role="alert"` (10.13) |
| The form has an accessible name | `aria-label="New task"` (or a visible heading via `aria-labelledby`) |

## 3. Focus management after submit

A good practice on a failed submit: **move focus to the first invalid field**, so keyboard and screen-reader users land where the problem is:

```tsx
const formRef = useRef<HTMLFormElement>(null);
// after a failed validation:
formRef.current?.querySelector<HTMLElement>('[aria-invalid="true"]')?.focus();
```

Because error visibility updates on the **next** render, do this in an effect that runs when `submitAttempted` changes, or after a `requestAnimationFrame`. It's left as a stretch goal in 11.10.

## 4. Test it yourself (5 minutes)

- **Keyboard only**: Tab through the form, submit with Enter, reach Cancel. Can you always see where focus is?
- **Screen reader**: Windows has **Narrator** built in (Ctrl+Win+Enter). Focus the title field after a failed submit and listen: it should say the label, "invalid entry", and the error text.
- **DevTools → Elements → Accessibility pane**: inspect the computed name and description of each control.

## 5. Summary

- Labels via `htmlFor`/`id`; invalid via `aria-invalid`; messages via `aria-describedby`; status via live regions.
- Never rely on colour alone; keep native elements for keyboard support.
- Move focus to the first invalid field after a failed submit.
