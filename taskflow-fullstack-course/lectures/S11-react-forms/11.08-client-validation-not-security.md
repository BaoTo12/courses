# Lecture 11.08 · 🛡 Client-Side Validation Is UX, Not Security: Bypassing It in 30 Seconds

> **Section:** S11 · **Type:** 📖 Theory (🔓 demo) · **Track:** ★ Core · **Time:** ~20 minutes

---

## 1. The claim

> Every rule in `validateTaskForm` can be bypassed by any user, in seconds, without special tools.

That's not a flaw in our code. It's the nature of the client (00.06: **the client is not yours**).

## 2. 🔓 Three bypasses (try them on your local app)

**a) Call the submit logic directly from DevTools.** Sources panel → set a breakpoint on the first line of `handleSubmit` → click **Create task** with an empty title → while paused, the console has access to the function's closure, so type `onSubmit({ ...values, title: '', priority: 'HIGH' })` and press Enter. The validation step never ran. (React DevTools can also edit component state and props directly.)

**b) Change the option values.** Elements panel → edit a `<option value="HIGH">` into `value="URGENT"`, then select it. Our type guard (11.03) refuses it on the client, but only because *we* wrote that guard, and the next bypass skips the UI completely.

**c) Skip the UI entirely.** Once the real API exists (S13/S46), anyone can send:

```bash
curl -X POST http://localhost:8080/taskflow/api/tasks -H "Content-Type: application/json" \
  -d '{"title":"","priority":"URGENT","dueDate":"1999-01-01","ownerId":42}'
```

No React, no form, no validation. Just an HTTP request (00.03). Note the `"ownerId":42`: trying to create a task **for another user** is mass assignment (06.04, S46).

## 3. So why validate on the client at all?

| Client validation | Server validation |
|---|---|
| Fast feedback, no round trip | The **only** enforcement that counts |
| Guides honest users | Protects against dishonest users and bugs in other clients |
| Can be skipped | Can't be skipped (it's on the machine you control) |
| Duplicated rules are fine | Must be complete |

Both, for different reasons. The server returns `400` with `fieldErrors` (06.04's `ApiError`), and the client shows them in the same `FormField` slots (S48).

## 4. Keeping rules in sync

The same rules exist twice: TypeScript (`validateTaskForm`) and Java (S37 Bean Validation-style checks). Options to limit drift:
- Keep client rules a **subset** of server rules (never stricter than the server, or users see errors the server wouldn't give).
- Share constants (`TITLE_MAX = 120`) through documentation, or generate them from the API contract (S48 discusses contract tooling).
- Always handle server `fieldErrors` gracefully: the server is the final word.

## 5. Summary

- Any client-side check can be bypassed: DevTools, modified HTML, or raw HTTP requests.
- Client validation = UX; server validation = security and integrity.
- Show server field errors in the same UI; keep client rules a subset of server rules.
