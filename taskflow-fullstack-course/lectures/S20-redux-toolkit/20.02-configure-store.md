# Lecture 20.02 · `configureStore`: What It Sets Up by Default

> **Section:** S20 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes
> Verified with `@reduxjs/toolkit` 2.12.0 in Node and in TaskFlow's dev build. Every message below was captured, not recalled.

---

## 1. Install

```bash
npm install @reduxjs/toolkit
```

RTK depends on `redux`, `immer`, `reselect` and `redux-thunk`, and re-exports what you need from them (`createSelector`, `isAction`, the `Middleware` type…). In a normal RTK app you import everything from `@reduxjs/toolkit` and list only it (plus `react-redux`) in `package.json`.

After the migration (20.10), nothing in TaskFlow imports `reselect` directly any more, so it's uninstalled (`npm uninstall reselect`; it stays installed as RTK's own dependency). `redux` and `redux-thunk` stay as direct dependencies on purpose: the learning tests compare our hand-written `mini-redux` with the real `createStore` and `redux-thunk` (16.03, 18.03).

## 2. The smallest store

```ts
import { configureStore } from '@reduxjs/toolkit';

export const store = configureStore({
  reducer: {                 // an object → combineReducers is called for you
    tasks: tasksReducer,
    listPrefs: listPrefsReducer,
  },
});
```

Compare with S16's `store.ts`: no `createStore`, no `applyMiddleware`, no `compose`, no `window.__REDUX_DEVTOOLS_EXTENSION_COMPOSE__`. One call.

`reducer` accepts either an object of slice reducers (combined for you) or one root reducer function. TaskFlow passes its `rootReducer` (a function), because `RootState` is derived from it and tests import it (20.03).

## 3. What you get for free

### 3.1 Middleware: `getDefaultMiddleware()`

Measured in development (RTK 2.12): **4 middleware**, in this order (from RTK's source, `buildGetDefaultMiddleware`):

| # | Middleware | What it does | In production? |
|---|---|---|---|
| 1 | action-creator check | warns when you dispatch the **creator** instead of calling it | no |
| 2 | immutability check | throws when state was **mutated** (inside a dispatch, or between two dispatches) | no |
| 3 | thunk | the same `redux-thunk` you used in S18 | **yes** |
| 4 | serializability check | logs an error when a **non-serialisable** value is in an action or in the state | no |

In production only the thunk middleware remains: the checks are expensive (they walk the whole state tree after every action) and exist to catch bugs during development.

The exact messages, so you recognise them:

- Mutating state inside a reducer (thrown):
  > A state mutation was detected inside a dispatch, in the path: items.1. Take a look at the reducer(s) handling the action {"type":"bad"}.
- Mutating state **outside** a reducer, for example in a component, then dispatching anything (thrown on the next dispatch):
  > A state mutation was detected between dispatches, in the path 'items.1'. This may cause incorrect behavior.
- Dispatching an action creator without calling it: `dispatch(selectionCleared)` instead of `dispatch(selectionCleared())` (a `console.warn`):
  > Detected an action creator with type "demo/ping" being dispatched. Make sure you're calling the action creator before dispatching, i.e. `dispatch(ping())` instead of `dispatch(ping)`. This is necessary even if the action has no payload.
- A `Date`, `Map`, class instance or function in an action or the state (a `console.error`, debugged in 20.16):
  > A non-serializable value was detected in the state, in the path: `tasks.fetchedAt`. Value: …

Compare with S15: there, only `deepFreeze` in **tests** caught mutations (15.11). Now the running app catches them too.

### 3.2 Enhancers: DevTools and auto-batching

- **Redux DevTools** are connected automatically (`devTools: true` by default). TaskFlow passes `devTools: import.meta.env.DEV` so production users can't inspect the store (14.11 §5).
- `getDefaultEnhancers()` returned **2** enhancers: the middleware enhancer (`applyMiddleware` with the list above) and RTK's `autoBatchEnhancer`, which lets RTK Query (S22) batch many low-priority notifications into one. You won't configure it in this course.

## 4. Customising middleware without losing the defaults

The `middleware` option is a **callback** that receives `getDefaultMiddleware`. Returning your own array **without** calling it would remove thunk and every check, a common mistake:

```ts
// ❌ replaces the defaults: no thunk, no checks
middleware: () => [logger],

// ✅ keeps the defaults and adds yours
middleware: (getDefaultMiddleware) => getDefaultMiddleware().concat(logger),
```

`getDefaultMiddleware()` returns a `Tuple`, an array subclass with typed `.prepend()` and `.concat()`. Use those (not `[...spread]`), so TypeScript keeps track of what each middleware adds to `dispatch`. That's exactly the S18 problem where a `Middleware[]` spread lost the thunk's dispatch type (18.08).

`getDefaultMiddleware` takes options for each default:

```ts
getDefaultMiddleware({
  thunk: { extraArgument: extra },                        // TaskFlow: the injected API (18.04)
  serializableCheck: { ignoredActions: ['some/action'] }, // escape hatches (20.16)
  immutableCheck: { warnAfter: 64 },                      // warn when a check takes longer than 64 ms
})
```

## 5. TaskFlow's `store.ts` after S20

```ts
export function makeStore(preloadedState?: Partial<RootState>, extraOverrides?: Partial<ThunkExtra>) {
  const extra = buildExtra(extraOverrides);
  const crashReporter = createCrashReporter((crash) => console.error('[crash]', crash.actionType, crash));
  const analytics = createAnalyticsMiddleware((event) => console.info('[analytics]', event));

  return configureStore({
    reducer: rootReducer,
    preloadedState,
    // getDefaultMiddleware() = thunk (with our extra argument) + dev-only immutability & serializability checks
    middleware: (getDefaultMiddleware) => {
      const chain = getDefaultMiddleware({ thunk: { extraArgument: extra } }).prepend(crashReporter); // first: wraps all
      return import.meta.env.DEV ? chain.concat(createLoggerMiddleware(), analytics) : chain.concat(analytics);
    },
    devTools: import.meta.env.DEV,
  });
}

export const store = makeStore();

// Inferred, not declared (compare 18.08): configureStore knows what the middleware add to dispatch.
export type AppStore = ReturnType<typeof makeStore>;
export type AppDispatch = AppStore['dispatch'];
```

Three things carried over from S16–S18, unchanged in meaning:

1. **`makeStore` is a factory**, so every test gets a fresh store with its own preloaded state and fake API (16.14, 18.13).
2. **The crash reporter is first** (`.prepend`): it wraps everything after it, including thunks and the checks, so it sees every exception (16.14).
3. **Your middleware still work**: the logger, redaction and analytics from S16 are ordinary Redux middleware. RTK didn't change the middleware API (16.09).

And one thing is gone: the hand-written `AppStore` type (18.08). `ReturnType<typeof makeStore>` now has a `dispatch` that accepts thunks and returns what they return, **inferred** from the middleware `Tuple`.

## 6. 📇 API card: `configureStore`

```ts
function configureStore(options: ConfigureStoreOptions): EnhancedStore
```

| Option | Type | Required | Default | Meaning |
|---|---|---|---|---|
| `reducer` | a reducer function, or an object of slice reducers | **yes** | — | The root reducer. An object is passed to `combineReducers` for you. |
| `middleware` | `(getDefaultMiddleware) => Tuple<Middleware[]>` | no | `getDefaultMiddleware()` | The middleware chain. Always build it **from** `getDefaultMiddleware()` with `.prepend()` / `.concat()`. |
| `preloadedState` | the state (or part of it) | no | `undefined` | Initial state, e.g. in tests or restored from storage. With a combined reducer, an object with the same keys. |
| `devTools` | `boolean` or DevTools options (`name`, `maxAge`, `actionSanitizer`, `stateSanitizer`, `actionsDenylist`, `trace`, …) | no | `true` | Connect the Redux DevTools extension. Set to `false` (or `import.meta.env.DEV`) in production. |
| `enhancers` | `(getDefaultEnhancers) => Tuple<StoreEnhancer[]>` | no | `getDefaultEnhancers()` | Store enhancers (rare, 16.12). Extend the defaults, don't replace them. |
| `duplicateMiddlewareCheck` | `boolean` | no | `true` | Development check that the same middleware **instance** isn't added twice. |

**`getDefaultMiddleware(options?)`**: each key turns one default on (`true`), off (`false`), or configures it (an object):

| Key | Configuration object (main fields) |
|---|---|
| `thunk` | `{ extraArgument }`: the third argument of every thunk (18.04) |
| `immutableCheck` | `{ ignoredPaths, warnAfter (ms, default 32), isImmutable }` |
| `serializableCheck` | `{ ignoredActions, ignoredActionPaths (default `['meta.arg', 'meta.baseQueryMeta']`), ignoredPaths, ignoreState, ignoreActions, warnAfter (default 32), isSerializable, getEntries }` |
| `actionCreatorCheck` | `{ isActionCreator }` |

(Option names and defaults are copied from RTK 2.12's type definitions.)

**Returns** an `EnhancedStore`: the Redux store you know (`getState`, `dispatch`, `subscribe`, `replaceReducer`, plus an `'@@observable'` interop key, verified), whose `dispatch` type includes what the middleware add (thunks).

**Minimal example (outside TaskFlow)**

```ts
import { configureStore } from '@reduxjs/toolkit';

const store = configureStore({
  reducer: { counter: counterReducer, todos: todosReducer }, // combined for you
});
store.dispatch({ type: 'counter/incremented' });
```

**Use it when** you create any Redux store: it's the standard entry point, and it gives you thunk, DevTools and the development checks with no setup.

**Don't use it when** you're *learning how a store works* (S16's `createStore`), or maintaining legacy code that you aren't migrating yet. There's no production reason to prefer `createStore`.

**Common mistakes**

- `middleware: () => [logger]` (or `[...getDefaultMiddleware(), logger]` with a spread): removes thunk and the checks, or loses the types. Use `getDefaultMiddleware().concat(logger)`.
- Turning `serializableCheck` off globally to silence one warning. Ignore **one** action or path instead (20.16).
- Creating a store per request or per render in app code. One store per app; a `makeStore()` **factory** is for tests (and server rendering).
- Leaving `devTools: true` in production: anyone can read the whole state and replay actions.

## 7. Summary

- `configureStore` = `combineReducers` (for an object) + `createStore` + `applyMiddleware(default middleware)` + DevTools + auto-batching.
- Development adds 3 checks: action-creator misuse (warn), mutation (throw), non-serialisable values (error). Production keeps only thunk.
- Customise with `middleware: (getDefaultMiddleware) => getDefaultMiddleware(options).prepend(…).concat(…)`, never by replacing the defaults.
