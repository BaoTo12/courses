# Lecture 20.11 · `extraReducers` for Cross-Slice Events: Logout Resets Everything

> **Section:** S20 · **Type:** 📖 Theory + 🛠 small build · **Track:** ★ Core · **Time:** ~30 minutes
> **Project feature:** logging out dispatches `auth/loggedOut`; every slice resets; the data is loaded again.
> Verified: `tsc`, lint, **9 test files / 88 tests** (one new test below); in the browser the logger printed the sequence in §4.

---

## 1. `reducers` vs `extraReducers`: who owns the event?

| | `reducers` | `extraReducers` |
|---|---|---|
| Defines a **new** action type? | yes: `name/key`, and generates its creator | no: handles actions **defined elsewhere** |
| Typical content | the slice's own events: `taskSelectionToggled`, `sortChanged` | thunk lifecycles (`fetchTasks.fulfilled`), other features' events (`loggedOut`), matchers |
| Written as | an object of case reducers | a builder callback (20.07) |

The rule behind it is 15.10's: **one event, many reducers**. An event has one owner (the slice or file that creates its action creator) and any number of listeners. `extraReducers` is how a slice listens without owning.

## 2. The event: `auth/loggedOut`

```ts
// src/features/auth/authActions.ts
import { createAction } from '@reduxjs/toolkit';

// The auth slice arrives in S24. Its logout EVENT is needed now: every slice resets on it (15.10, 20.11).
export const loggedOut = createAction('auth/loggedOut');
```

It lives in its own file, not in a slice, because four slices import it and none owns it (S24's auth slice will then import it too, rather than redefining it).

## 3. Every slice resets

```ts
// tasksSlice.ts
.addCase(loggedOut, () => initialTasksState)
// categoriesSlice.ts
.addCase(loggedOut, () => initialCategoriesState)
// listPrefsSlice.ts
builder.addCase(loggedOut, () => initialListPrefsState);
// uiSlice.ts
.addCase(loggedOut, () => initialUiState);
```

Each case **returns** the initial state (20.05 rule 1): replacing the whole slice is simpler and safer than clearing fields one by one, and a field added later is reset automatically.

### Why reset everything?

TaskFlow will be used on shared computers (a meeting room, a colleague's laptop). If Alice logs out and Bob logs in, Bob must not see Alice's tasks, categories or selection even for a moment, and must not get her sort preferences. That's a **security** requirement (information disclosure), not just tidiness. Part 2 enforces it on the server (each request only returns the logged-in user's data); the client must not keep a copy either.

### Alternative: a root reducer that resets

A common pattern is resetting in the root reducer:

```ts
const appReducer = combineReducers({ … });
export const rootReducer: typeof appReducer = (state, action) =>
  appReducer(loggedOut.match(action) ? undefined : state, action); // undefined → every slice's initial state
```

It's shorter, and you can't forget a slice (verified: it type-checks with RTK's `combineReducers`, and a selection disappears on `loggedOut()`). TaskFlow uses per-slice cases instead, because some slices will need to **keep** something in S24 (for example, the theme or language preference that isn't user data), and a per-slice case states that decision explicitly in the slice that owns the data. Both are accepted patterns; pick one per app.

## 4. 🛠 Wire it: dispatch on logout, and load again

The S12 `AuthProvider` managed the fake user in React state only. It sits **inside** the Redux `<Provider>` (see `main.tsx`), so it can dispatch:

```ts
export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const dispatch = useAppDispatch(); // this provider is inside the Redux <Provider> (main.tsx)

  const value = useMemo<AuthContextValue>(
    () => ({
      user,
      login: (username) =>
        setUser({ id: 1, username, displayName: username, role: 'USER', locale: 'en' }),
      logout: () => {
        setUser(null);
        dispatch(loggedOut()); // every slice resets: the next user must not see this user's data (20.11)
      },
    }),
    [user, dispatch],
  );

  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}
```

After the reset, the task list is `idle` and empty. `AppLayout` loaded the data in an effect that ran once, on mount. Add `user` to its dependencies, so a change of user loads the data again:

```ts
// `user` is a dependency: after a logout every slice is reset (20.11), so the data is loaded again.
useEffect(() => {
  void dispatch(fetchTasksIfNeeded());
  void dispatch(fetchCategories()); // its `condition` skips it once loaded; in parallel with the tasks
}, [dispatch, user]);
```

After a **login**, `fetchTasksIfNeeded` skips the request while the data is fresh (18.09); after a **logout** the data is gone, so both requests run.

Captured in the browser's console (the S16 logger), clicking "Log out":

```text
[redux] auth/loggedOut            changed: Array(2)   ← tasks and categories (listPrefs and ui were already initial)
[redux] tasks/fetch/pending
[redux] categories/fetch/pending
[api] GET /tasks → 200
[redux] tasks/fetch/fulfilled
[api] GET /categories → 200
[redux] categories/fetch/fulfilled
```

`changed: Array(2)`: `listPrefs` and `ui` were still their initial objects, and returning the initial state gave the **same** reference, so the logger (which lists the slices that got a new reference, 14.06) reported no change for them.

## 5. The race you must think about: a request in flight at logout

Alice's list is loading; she logs out; **then** her response arrives. Would it write her tasks into the empty store, for Bob to see?

No: `loggedOut` resets `currentRequestId` to `null`, and the `fulfilled` case ignores any response whose `meta.requestId` isn't the current one (18.11). A new test proves it:

```ts
it('a fetch still in flight at logout cannot write the old user’s tasks back (20.11)', () => {
  const inFlight = tasksReducer(loaded(task(1)), fetchTasks.pending('old-user', undefined));
  const afterLogout = deepFreeze(tasksReducer(deepFreeze(inFlight), loggedOut())); // currentRequestId → null
  const late = fetchTasks.fulfilled({ tasks: [task(1), task(2)], fetchedAt: 9000 }, 'old-user', undefined);
  expect(tasksReducer(afterLogout, late)).toBe(afterLogout);
});
```

The request-id pattern you built for "a slow old search can't overwrite a newer one" also protects user data across a logout. (S24 adds aborting all in-flight requests on logout, and S41/S47 make the server reject a request whose session has ended.)

## 6. Summary

- `reducers` = events the slice owns (creators generated); `extraReducers` = events owned elsewhere.
- Shared events live in small files (`authActions.ts`) created with `createAction`.
- On logout, every slice returns its initial state; the data is reloaded for the next user.
- The request-id check makes a late response from before the logout harmless.
