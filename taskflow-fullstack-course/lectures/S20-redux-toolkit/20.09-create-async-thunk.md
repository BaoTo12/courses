# Lecture 20.09 · `createAsyncThunk`: Lifecycle Actions, `rejectWithValue`, `condition`, `unwrap()`

> **Section:** S20 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~60 minutes
> 🔗 Official companion reading: Redux Essentials **Part 5** ("Async Logic and Data Fetching")
> Verified with RTK 2.12 in Vitest: every action shown below was captured from a real dispatch (request ids shortened).

## 1. What you wrote by hand in S18, per async operation

For `fetchTasks` alone:

- three action types and creators: `fetchStarted(requestId)`, `fetchSucceeded(requestId, tasks)`, `fetchFailed(requestId, message)`;
- a request id generator in `extra`, so the reducer could ignore stale responses (18.11);
- a `try / catch` that turned exceptions into a failure action, and an `isCancelled` check;
- three reducer cases.

Every async operation in every app needs the same shape: "started, then succeeded **or** failed", with an id to tell requests apart. `createAsyncThunk` generates all of it.

## 2. The API

```ts
const thunkActionCreator = createAsyncThunk(
  typePrefix,                     // 'tasks/fetch'
  payloadCreator,                 // async (arg, thunkAPI) => payload
  options?,                       // { condition, dispatchConditionRejection, idGenerator, … }
);
```

The smallest example, captured:

```ts
const double = createAsyncThunk('demo/ok', async (n: number) => n * 2);

double.typePrefix     // 'demo/ok'
double.pending.type   // 'demo/ok/pending'
double.fulfilled.type // 'demo/ok/fulfilled'
double.rejected.type  // 'demo/ok/rejected'

await dispatch(double(21))
// { type: 'demo/ok/fulfilled', payload: 42,
//   meta: { arg: 21, requestId: 'TXNn5jQh…', requestStatus: 'fulfilled' } }
```

## 3. The lifecycle, step by step

When you `dispatch(fetchTasks({ q: 'x' }))`:

1. **`condition`** (if given) runs. If it returns `false`, stop: nothing is dispatched (§7).
2. A **request id** is generated (a `nanoid`, 21 characters) and `tasks/fetch/pending` is dispatched **synchronously**, with `meta: { arg, requestId, requestStatus: 'pending' }`. Captured: right after the `dispatch(...)` call returns, `state.tasks.status` is already `'loading'`.
3. The **payload creator** runs: `async (arg, thunkAPI) => …`.
4. If it returns (or its promise resolves) → `tasks/fetch/fulfilled` with `payload` = the returned value.
   If it throws, or returns `rejectWithValue(x)` → `tasks/fetch/rejected`.
5. The promise returned by `dispatch` **resolves with that final action**. It **never rejects**.

The `thunkAPI` object (the second parameter) contains everything a hand-written thunk had, and more:

| Field | Use |
|---|---|
| `dispatch`, `getState`, `extra` | as in S18 (TaskFlow's `extra` = `{ api, listRequest }`) |
| `requestId` | the id also found in every lifecycle action's `meta` |
| `signal` | an `AbortSignal`, aborted by `promise.abort()`: pass it to the HTTP call |
| `rejectWithValue(value)` | reject **with a payload you choose** (§5) |
| `fulfillWithValue(value, meta?)` | fulfil with extra `meta` (rare) |

## 4. Handling the lifecycle in a slice

The thunk's actions belong to no slice, so slices handle them in `extraReducers`:

```ts
extraReducers: (builder) => {
  builder
    .addCase(fetchTasks.pending, (state, action) => {
      state.status = 'loading';
      state.error = null;
      state.currentRequestId = action.meta.requestId; // the NEWEST fetch wins
    })
    .addCase(fetchTasks.fulfilled, (state, action) => {
      if (action.meta.requestId !== state.currentRequestId) return; // stale: ignore
      // … store action.payload.tasks
    })
    .addCase(fetchTasks.rejected, (state, action) => {
      if (action.meta.requestId !== state.currentRequestId) return;
      // …
    });
}
```

That's S18's request id logic (18.11), with `meta.requestId` generated for you. `action.payload` and `action.meta.arg` are fully typed from the payload creator.

## 5. Errors: `action.error` vs `rejectWithValue`

### A thrown error becomes a **serialised** `action.error`

Actions must be plain data, so RTK can't put an `Error` instance in them. It copies `name`, `message`, `stack` and `code` into a plain object (a `SerializedError`). Captured, for `throw new TypeError('boom')`:

```json
{ "type": "demo/plain/rejected",
  "meta": { "requestId": "zQvVpwPp…", "rejectedWithValue": false, "requestStatus": "rejected",
            "aborted": false, "condition": false },
  "error": { "name": "TypeError", "message": "boom", "stack": "…" } }
```

Custom fields are lost. TaskFlow's `ApiRequestError` carries `status`, `kind` and `fieldErrors`, and none of those would survive.

### `rejectWithValue`: you choose the payload

```ts
async (request: CreateTaskRequest, { extra, rejectWithValue }) => {
  try {
    return await extra.api.createTask(request);
  } catch (error) {
    return rejectWithValue(toApiErrorPayload(error)); // a plain, serialisable object
  }
}
```

Captured with `rejectWithValue({ message: 'Server says no' })`:

```json
{ "type": "demo/wv/rejected",
  "payload": { "message": "Server says no" },
  "meta": { "rejectedWithValue": true, "requestStatus": "rejected", "aborted": false, "condition": false, "requestId": "9f5lW9dO…" },
  "error": { "message": "Rejected" } }
```

Note `error.message` is the generic **`"Rejected"`**. The real information is in **`payload`**. A reducer that reads only `action.error.message` shows "Rejected" to the user (debugged in 20.18). TaskFlow reads the payload first:

```ts
state.error = action.payload?.message ?? action.error.message ?? 'Unexpected error';
```

The value passed to `rejectWithValue` goes into an action, so it must be **serialisable**. That's why TaskFlow converts the `ApiRequestError` into an `ApiErrorPayload` (`kind`, `status`, `code`, `message`, `fieldErrors`) with `toApiErrorPayload`. Passing the error instance itself triggers the serializability check (20.16).

## 6. Cancelling: `signal` and `promise.abort()`

The promise returned by `dispatch(fetchTasks())` has extra members (captured: `abort` and `unwrap` are functions; `requestId` is 21 characters; `arg` is `{ q: 'x' }`).

`promise.abort(reason)` aborts `thunkAPI.signal`, and **immediately** dispatches `rejected`. Captured, after `promise.abort('user left')`:

```json
{ "type": "tasks/fetch/rejected",
  "meta": { "arg": { "q": "x" }, "requestId": "f6e_0zfj…", "rejectedWithValue": false,
            "requestStatus": "rejected", "aborted": true, "condition": false },
  "error": { "name": "AbortError", "message": "user left" } }
```

TaskFlow's reducer treats `meta.aborted` as "not an error" and went back to `status: 'idle'` (captured), rather than showing a red error banner for something the user did on purpose.

TaskFlow's `fetchTasks` also aborts the **previous** list request when a new one starts (18.11). It combines both reasons into one signal for Axios:

```ts
AbortSignal.any([signal, controller.signal]) // RTK's abort OR "a newer fetch started"
```

A typical use of `abort()` in a component: `useEffect(() => { const p = dispatch(fetchTasks(q)); return () => p.abort(); }, [q])`. TaskFlow's list page doesn't need it, because a newer fetch already aborts the older one.

## 7. `condition`: don't start at all

```ts
export const fetchCategories = createAppAsyncThunk('categories/fetch', payloadCreator, {
  condition: (_arg, { getState }) => {
    const { status } = getState().categories;
    return status === 'idle' || status === 'failed'; // false → skip
  },
});
```

When `condition` returns `false`:

- the payload creator **doesn't run**, no `pending` is dispatched, and the `rejected` action is **not dispatched** either (verified: the store notified its subscribers only twice, for the first dispatch's `pending` + `fulfilled`);
- the promise still resolves with a rejected action whose `meta.condition` is `true` and whose `error.name` is `'ConditionError'`;
- `unwrap()` on it **throws** that `ConditionError`: don't `unwrap()` a thunk that may legitimately be skipped, or catch it.

`condition` replaces S18's hand-written "if needed" thunks for simple cases. TaskFlow keeps `fetchTasksIfNeeded` as a plain thunk because its rule takes a clock (`now`) for tests; `condition` can't receive extra parameters beyond the thunk's argument.

## 8. `unwrap()`: back to try/catch in components

The promise **always resolves** with an action, so this is a bug:

```ts
const result = await dispatch(deleteTask(id));
if (result) navigate('/tasks'); // ❌ always truthy: a rejected ACTION is still an object
```

Two correct styles:

```ts
// 1. Ask which action it was (a type guard)
const result = await dispatch(deleteTask(id));
if (deleteTask.fulfilled.match(result)) navigate(backHref, { replace: true });

// 2. unwrap(): resolves with the payload, or THROWS
try {
  const created = await dispatch(saveNewTask(request)).unwrap();
  navigate(`/tasks/${created.id}`);
} catch (error) {
  // error = the rejectWithValue payload (an ApiErrorPayload), or a SerializedError
}
```

What `unwrap()` throws, captured:

| The thunk… | `unwrap()` throws |
|---|---|
| returned `rejectWithValue(x)` | `x` itself: `{ message: 'Server says no' }` |
| threw `new TypeError('boom')` | the **SerializedError** `{ name: 'TypeError', message: 'boom', stack }`: a plain object, **not** an `Error` instance (`instanceof Error` → `false`) |
| was skipped by `condition` | a `ConditionError` (serialised the same way) |

So error helpers must accept plain objects with a `message`. TaskFlow's `toErrorMessage` does (19.09), and `fieldErrorsOf` reads `fieldErrors` from either an `ApiRequestError` or its payload.

## 9. An optional argument: `TaskQuery | void`

```ts
export const fetchTasks = createAppAsyncThunk('tasks/fetch', async (query: TaskQuery | void, thunkAPI) => { … });

dispatch(fetchTasks());          // ✅
dispatch(fetchTasks({ q: 'r' })); // ✅
```

Verified with `tsc`:

| Payload creator's first parameter | `dispatch(thunk())` |
|---|---|
| `query: TaskQuery = DEFAULT` (a default value) | ❌ *Expected 1-2 arguments, but got 0.* |
| `query: TaskQuery \| void` | ✅ |
| `query: TaskQuery \| undefined` | ✅ |
| `query?: TaskQuery` | not allowed: a required parameter (`thunkAPI`) can't follow an optional one |

RTK builds the creator's parameter list from the parameter's **type**; a default value doesn't change the type, so the argument stays required. TaskFlow uses `| void` (the form the RTK docs show) and writes `query ?? DEFAULT_QUERY` inside. A thunk with no argument at all declares `_: void`.

## 10. `createAppAsyncThunk`: types declared once

Without help, every thunk would need its `getState` type, `extra` type and reject value spelled out as generics. `withTypes` fixes them once:

```ts
export const createAppAsyncThunk = createAsyncThunk.withTypes<{
  state: RootState;
  dispatch: AppDispatch;
  extra: ThunkExtra;
  rejectValue: ApiErrorPayload;
}>();
```

In every thunk made with it, `getState()` returns `RootState`, `extra.api` is typed, and `rejectWithValue` accepts only an `ApiErrorPayload`. The same idea as the typed hooks (20.08).

## 11. Testing: the creators can build lifecycle actions

For **reducer** tests, you don't need to run the thunk:

```ts
fetchTasks.pending('r1', undefined)                                  // (requestId, arg)
fetchTasks.fulfilled({ tasks: [task(3)], fetchedAt: 5000 }, 'r2', undefined) // (payload, requestId, arg)
fetchTasks.rejected(null, 'r1', undefined, payload)                  // (error, requestId, arg, rejectValue?)
```

For **thunk** tests, dispatch into `makeStore(preloaded, { api: fakeApi })` and assert on the resolved action and the state, as in 18.13.

## 12. 📇 API card: `createAsyncThunk`

```ts
createAsyncThunk<Returned, ThunkArg, ThunkApiConfig>(
  typePrefix: string,
  payloadCreator: (arg: ThunkArg, thunkAPI) => Returned | Promise<Returned> | rejectWithValue(…),
  options?: AsyncThunkOptions,
): AsyncThunk
```

**The payload creator's `thunkAPI`** (from RTK 2.12's `BaseThunkAPI` type):

| Member | Meaning |
|---|---|
| `dispatch`, `getState`, `extra` | as in a hand-written thunk |
| `requestId` | this run's id (also `meta.requestId` of its actions) |
| `signal` | an `AbortSignal`, aborted by `promise.abort()`, by `thunkAPI.abort()`, or by an external signal passed at dispatch |
| `abort(reason?)` | abort this run **from inside** (verified: the result has `meta.aborted: true`) |
| `rejectWithValue(value, meta?)` | return it to reject with `action.payload = value` |
| `fulfillWithValue(value, meta?)` | return it to fulfil with extra `meta` |

**Options:**

| Option | Default | Meaning |
|---|---|---|
| `condition(arg, { getState, extra })` | — | return `false` to skip the run: no `pending`, nothing dispatched (§7). May be async. |
| `dispatchConditionRejection` | `false` | when `true`, a skipped run **does** dispatch its `rejected` action with `meta.condition: true` (verified) |
| `idGenerator(arg)` | `nanoid` | how `requestId` is made (verified with a custom one) |
| `serializeError(error)` | `miniSerializeError` | how a thrown error becomes `action.error` |
| `getPendingMeta({ arg, requestId }, { getState, extra })` | — | extra fields for the `pending` action's `meta` |

**Returns** an async-thunk action creator:

| Member | Meaning |
|---|---|
| `thunk(arg, { signal }?)` | creates the thunk to dispatch; the optional second argument passes an **external** `AbortSignal` (verified: aborting it rejects the run with an `AbortError`) |
| `.pending` / `.fulfilled` / `.rejected` | the three action creators, each with `.type` and `.match()`; usable in tests to build actions (§11) |
| `.settled` | a matcher for "fulfilled **or** rejected" (verified) |
| `.typePrefix` | the string you passed |

`dispatch(thunk(arg))` returns a promise of the final action, with `abort(reason?)`, `requestId`, `arg` and `unwrap()`. For an action you already have, `unwrapResult(action)` does what `unwrap()` does (verified).

**Minimal example**

```ts
export const fetchUser = createAsyncThunk('users/fetch', async (id: number, { signal, rejectWithValue }) => {
  const response = await fetch(`/api/users/${id}`, { signal });
  if (!response.ok) return rejectWithValue({ status: response.status });
  return (await response.json()) as User;
});

// component
const result = await dispatch(fetchUser(5));
if (fetchUser.fulfilled.match(result)) show(result.payload.name);
```

**Use it when** an async operation's progress or result belongs in Redux state (loading flags, the loaded data, errors shown in several places), and you want the lifecycle actions for free.

**Don't use it when**

- the data is **server cache** that several screens read, refetch and invalidate: **RTK Query** (S22) does that with far less code;
- the async logic only answers to **other actions** ("when X happens, do Y"): a **listener** (21.14);
- the result is used only by one component and never stored: call the API in the component (or with RTK Query's lazy hooks).

**Common mistakes**

- Reading `action.error.message` after `rejectWithValue` (it says `"Rejected"`, 20.18).
- Putting a class instance (an `Error`, an `AxiosError`) into `rejectWithValue` (not serialisable, 20.16).
- Treating the dispatch result as a boolean (§8).
- `unwrap()` without `try/catch` (20.99 Q7).
- Declaring an optional argument with a default value instead of `| void` (§9).

## 13. Summary

- `createAsyncThunk(prefix, async (arg, thunkAPI) => payload, { condition })` generates `pending` / `fulfilled` / `rejected` with `meta.requestId` and `meta.arg`.
- `dispatch(thunk())` returns a promise that **always resolves with an action**; use `.match()` or `.unwrap()`.
- Thrown errors are serialised (custom fields lost, message kept); `rejectWithValue(serialisablePayload)` carries what you need; then `error.message` is just `"Rejected"`.
- `promise.abort()` → `signal` aborted + `rejected` with `meta.aborted: true`.
- `condition` returning `false` = nothing dispatched; `unwrap()` throws a `ConditionError`.
- `createAsyncThunk.withTypes<…>()` = `createAppAsyncThunk`.
