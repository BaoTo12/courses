# Lecture 20.13 · Redux Style Guide Essentials: the Rules You'll Be Held To in Code Review

> **Section:** S20 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> 🔗 Official companion reading: the **Redux Style Guide** (redux.js.org/style-guide). 19.10 covered the general rules; this lecture adds what changes with RTK, as a review checklist.

---

## 1. Priority A (Essential), revisited with RTK

| Rule | Before RTK | With RTK |
|---|---|---|
| Do not mutate state | discipline + `deepFreeze` in tests | Immer in slices; **the immutability check throws in development** (20.02). Mutation outside slices is still a bug. |
| Reducers must not have side effects | discipline | unchanged: RTK can't detect a `fetch` or `Date.now()` in a case reducer. Put them in `prepare` or a thunk. |
| No non-serialisable values in state or actions | discipline | **the serializability check logs them** (20.16) |
| Only one store per app | `store.ts` | unchanged (`makeStore` is for tests) |

## 2. Priority B rules that are specific to RTK code

| Rule (paraphrased) | Reviewer's question | TaskFlow |
|---|---|---|
| **Use Redux Toolkit** for Redux logic | "Why is this a hand-written `switch` reducer?" | all slices (the `mini-redux/` folder is learning code, and says so) |
| **Use Immer** for immutable updates | "Why the nested spreads in a slice?" | spreads only where they're clearer, e.g. returning a whole new slice |
| **Model actions as events**, not setters | "`setTasks`? What *happened*?" | `sortChanged`, `taskSelectionToggled`, `loggedOut`, `tasks/fetch/fulfilled` |
| **Let many reducers respond to the same action** | "Why does the delete thunk dispatch three actions?" | `deleteTask.fulfilled` is handled by `tasks` **and** `ui` (20.11) |
| **Avoid dispatching many actions in a row** | "These three dispatches: are they one event?" | one `fulfilled` action per operation; toasts are separate events on purpose |
| **Put as much logic as possible in reducers** | "Could the reducer decide this?" | yes for derived updates (`allCompleted` skips DONE tasks); no where the **server** decides (13.13, 19.10 §3) |
| **Reducers own the state shape** | "Why does the payload decide the state structure?" | `normalize(action.payload.tasks)` in the reducer, not in the thunk |
| **Name state slices after the data**, not the component | "`taskListPage` slice?" | `tasks`, `categories`, `listPrefs`, `ui` |
| **Treat reducers as state machines** | "Can `status` be `loading` with an `error`?" | the status enum; `pending` clears `error` |
| **Use static typing** | "Why is `state` `any` here?" | `.withTypes()` hooks, `createAppAsyncThunk`, lint rule (20.08) |
| **Use plain JavaScript objects for state** | "Is that an Immutable.js `Map`, or a class?" | plain objects and arrays only |
| **Use the Redux DevTools** | "Can you show the action sequence?" | enabled in development (`devTools: import.meta.env.DEV`) |

## 3. RTK-specific review checklist

Paste this into your PR template when a change touches Redux:

- [ ] Case reducers either mutate the draft **or** return a new value, never both; one-line arrow functions don't accidentally return (20.05).
- [ ] No reassignment of `state` (it's a no-op).
- [ ] No `Date`, class instance, `Error`, `Map`/`Set` or function in state or actions. Errors travel as serialisable payloads (`rejectWithValue(toApiErrorPayload(e))`).
- [ ] Timestamps, ids and random values come from `prepare` or a thunk, not from a case reducer.
- [ ] Every `createAsyncThunk` handles `rejected` somewhere, and reads `action.payload` before `action.error.message`.
- [ ] Callers of thunks use `.unwrap()` in a `try/catch`, or `.match()`. Never `if (await dispatch(thunk()))`.
- [ ] `getDefaultMiddleware()` is extended (`.prepend` / `.concat`), never replaced.
- [ ] Selectors that build arrays or objects are memoised (`createSelector`); input selectors return existing references (19.02).
- [ ] Components import `useAppSelector` / `useAppDispatch`, never the plain hooks (enforced by lint).
- [ ] Events that several slices need live in a shared file (`createAction`), not duplicated as strings.

## 4. Priority C (Recommended): conventions

The guide's Priority C rules, all followed by TaskFlow: **write action types as `domain/eventName`**; **use the Flux Standard Action shape** (`type`, `payload`, `meta`, `error`: exactly what RTK generates); **use action creators**; **use RTK Query for data fetching** (S22–S23); **use thunks and listeners for other async logic** (S18, S21); **move complex logic outside components**; **use selector functions to read state**, **named `selectThing`**; **avoid putting form state in Redux** (17.08). They're conventions: follow the team's, and don't spend long review threads on them.

## 5. Summary

- RTK turns two of the four essential rules into runtime checks; the other two (no side effects in reducers, one store) remain yours.
- Most review comments on RTK code are about **events vs setters**, **one event → many reducers**, **serialisable errors**, and **handling the thunk result correctly**.
- Keep the checklist in the PR template.
