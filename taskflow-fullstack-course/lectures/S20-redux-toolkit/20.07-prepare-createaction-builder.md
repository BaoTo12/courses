# Lecture 20.07 · `prepare` Callbacks, `nanoid`, `createAction`, `createReducer` and the Builder

> **Section:** S20 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~35 minutes
> Verified with RTK 2.12: outputs below are captured; the builder-order error was triggered in TaskFlow's tasks slice.

---

## 1. `prepare`: when the payload isn't just "the argument"

A plain case reducer generates a creator that takes **one** argument and uses it as `payload`. Two situations need more:

1. **Several arguments**, to keep an existing signature (`sortChanged(key, direction)`).
2. **Values that must not be computed in a reducer**: ids, timestamps, random numbers (15.04, 19.01).

Write the case as an object with `reducer` and `prepare`:

```ts
allCompleted: {
  reducer(state, action: PayloadAction<{ updatedAt: string }>) {
    // … uses action.payload.updatedAt
  },
  prepare(updatedAt: string = new Date().toISOString()) {
    return { payload: { updatedAt } };
  },
},
```

The generated creator takes `prepare`'s parameters: `allCompleted()` or `allCompleted('2026-09-26T08:00:00Z')` (tests pass a fixed time). `prepare` runs **when the action is created**, before dispatch, so the reducer stays deterministic: replaying the action in the DevTools gives the same state.

`prepare` must return `{ payload }` and may add `meta` and `error`: `{ payload, meta: { source: 'keyboard' }, error: false }`. TypeScript checks that `prepare`'s `payload` matches the reducer's `PayloadAction<…>`.

## 2. `nanoid`: ids generated on the client

RTK re-exports a small `nanoid()`: a random, URL-safe string, **21 characters** (captured: `'ab3fA2dW4lbl7_PNGadvX'`). It's not cryptographically secure; use it for UI ids (toasts, temporary ids for optimistic items, 23.04), never for secrets or tokens.

TaskFlow's toasts used a module-level counter (`nextToastId++`) in S18. With `prepare` and `nanoid`:

```ts
export const toastShown = createAction('ui/toastShown', (input: ToastInput) => ({
  payload: { ...input, id: nanoid() },
}));
```

Captured with a simplified version whose `prepare` takes only a message: `{ type: 'ui/toastShown', payload: { message: 'Saved', id: 'ab3fA2dW4lbl7_PNGadvX' } }`. The id is now a `string`, so the `Toast` type changes from `id: number` to `id: string`; after that edit, `tsc` points you at every place that still assumes a number (the `ToastProvider`, `toastDismissed`'s payload, the ui tests).

Why not keep the counter? A module-level counter is **shared state outside Redux**: two stores in the same test file share it, and ids restart at 1 after a page reload while old toasts might be persisted. `nanoid` has neither problem.

## 3. `createAction`: an action creator without a slice

Some events don't belong to one slice: `auth/loggedOut` is handled by every slice (20.11), and the auth slice itself arrives only in S24. `createAction` makes the creator alone:

```ts
import { createAction } from '@reduxjs/toolkit';

export const loggedOut = createAction('auth/loggedOut');                // no payload: loggedOut()
export const toastDismissed = createAction<string>('ui/toastDismissed'); // payload: string
export const toastShown = createAction('ui/toastShown', prepareFn);      // with prepare
```

Every RTK action creator (from `createAction`, `createSlice` or `createAsyncThunk`) has:

| Member | Captured / meaning |
|---|---|
| `.type` | `'listPrefs/pageSizeChanged'`. Use it wherever a string is needed (TaskFlow's analytics `TRACKED_ACTIONS` set is built from `.type`s, so a renamed action can't silently stop being tracked). |
| `.match(action)` | `true`/`false`, and a **type guard**: inside `if (toastShown.match(action))`, `action.payload` is typed. Useful in middleware (16.10), which receive `unknown` actions. |
| `String(creator)` | `'listPrefs/pageSizeChanged'` (`toString()` returns the type; don't rely on it in new code). |

## 4. `createReducer`: `createSlice` without the creators

`createSlice` uses `createReducer` inside. You use it directly when a reducer handles only actions defined elsewhere:

```ts
const lastSeenReducer = createReducer(initialState, (builder) => {
  builder
    .addCase(loggedOut, () => initialState)
    .addCase(toastShown, (state, action) => {
      state.lastToastId = action.payload.id;
    });
});
```

It gives you Immer (20.05) and the builder, and nothing else. In TaskFlow, every reducer is a slice, so `createReducer` isn't used; recognise it in other codebases.

## 5. The builder callback

`extraReducers` (and `createReducer`) take a **builder callback**. The builder has three methods:

| Method | Handles | Example |
|---|---|---|
| `addCase(creatorOrType, reducer)` | exactly one action type | `.addCase(loggedOut, () => initialTasksState)` |
| `addMatcher(predicate, reducer)` | every action for which the predicate returns true | `.addMatcher(isAnyOf(saveNewTask.fulfilled, saveTask.fulfilled), upsert)` (20.12) |
| `addDefaultCase(reducer)` | every action nothing else handled | rarely needed |

Why a callback instead of an object `{ [type]: reducer }`? **Types.** Passing the creator to `addCase` lets TypeScript infer the action's payload type in the reducer: in `.addCase(deleteTask.fulfilled, (state, action) => …)`, `action.payload` is a `number` without any annotation. (RTK 2 removed the old object notation for exactly this reason.)

### The order rule

All `addCase` calls must come **before** any `addMatcher`, and `addDefaultCase` last. Two safety nets enforce it:

1. **TypeScript**, when the calls are **chained** (TaskFlow's style): the object returned by `.addMatcher(…)` has no `addCase` method, so `builder.addMatcher(…).addCase(…)` doesn't compile (*"Property 'addCase' does not exist on type 'Omit<ActionReducerMapBuilder<…>, "addCase" | …>'"*).
2. **At runtime**, when they're **separate statements** (`builder.addMatcher(…); builder.addCase(…);`), which compile. Even then `createSlice` itself succeeds, because RTK 2 runs the builder callback **lazily**, the first time the reducer is called (or `getInitialState()`). In the app that's when the store is created, so the app fails at startup, and so does every test that creates a store.

Captured runtime message (both facts are pinned by `src/verification/s20-store-and-immer.claims.test.ts` in the reference project):

> `builder.addCase` should only be called before calling `builder.addMatcher`

Why the rule: for one action, RTK runs **the matching case first, then every matching matcher, in order**. Writing them in that order makes the code read the way it runs.

## 6. 📇 API cards

### `createAction`

```ts
createAction<P = void>(type: string): PayloadActionCreator<P>
createAction(type: string, prepare: (...args) => { payload: P; meta?: M; error?: E }): PayloadActionCreator
```

| Parameter | Meaning |
|---|---|
| `type` | the action type string, `domain/eventName` |
| `P` (generic) | the payload type, when there's no `prepare`: `createAction<number>('counter/set')` |
| `prepare` | builds the action from any arguments; may add `meta` and `error` (verified: `{ type, payload, meta, error }`, a Flux Standard Action) |

**Returns** an action creator: call it to get an action; it also has `.type`, `.match(action)` (a type guard) and `toString()`.

**Use it when** an event has no single owning slice (`auth/loggedOut`, toasts dispatched from every feature), or when you need the creator before the slice exists. **Otherwise** define the event in a slice's `reducers`, which creates it for you.

### `createReducer`

```ts
createReducer<S>(initialState: S | (() => S), builderCallback: (builder) => void): Reducer<S> & { getInitialState(): S }
```

**Returns** a reducer with Immer, and `getInitialState()` (verified). **Use it** for a reducer that only reacts to other creators. **Prefer `createSlice`** as soon as the reducer has events of its own.

### The builder (`extraReducers` and `createReducer`)

| Method | Signature | Handles |
|---|---|---|
| `addCase` | `(creatorOrType, caseReducer)` | exactly one action type; `action` typed from the creator |
| `addAsyncThunk` | `(thunk, { pending?, fulfilled?, rejected?, settled? })` | the lifecycle of one `createAsyncThunk`; `settled` runs after **both** `fulfilled` and `rejected` |
| `addMatcher` | `(typeGuard, caseReducer)` | every action the type guard accepts; **all** matching matchers run, in order |
| `addDefaultCase` | `(caseReducer)` | actions nothing else handled |

**Order:** `addCase` → `addAsyncThunk` → `addMatcher` → `addDefaultCase`. Chained, TypeScript enforces it; as separate statements, the first reducer call throws (§5).

`addAsyncThunk` (added in a recent RTK 2.x release; present in 2.12) is a shorter way to write three `addCase`s for one thunk (verified: a successful and a failing run logged `pending, fulfilled, settled, pending, rejected, settled`):

```ts
builder.addAsyncThunk(fetchUser, {
  pending: (state) => { state.status = 'loading'; },
  fulfilled: (state, action) => { state.user = action.payload; },
  rejected: (state, action) => { state.error = action.payload?.message ?? action.error.message ?? null; },
  settled: (state, action) => { state.lastRequestStatus = action.meta.requestStatus; }, // 'fulfilled' | 'rejected'
});
```

TaskFlow keeps three `addCase`s for `fetchTasks` because they read like the S18 code you already know; both forms are equivalent.

### `nanoid`

```ts
nanoid(size?: number): string   // default size 21
```

A random, URL-safe id (verified: 21 characters). **Use it** for client-side ids of UI objects (toasts, temporary ids), called in `prepare` or a thunk. **Never** for secrets, tokens or anything security-related: it isn't a cryptographically secure generator.

## 7. Summary

- `prepare(...args) => ({ payload, meta?, error? })`: custom signatures and non-deterministic values, outside the reducer.
- `nanoid()` for UI ids; not for secrets.
- `createAction(type, prepare?)` for events with no owning slice; every creator has `.type` and `.match()`.
- `createReducer(initial, builder => …)` = Immer + builder, no generated creators.
- Builder: `addCase` (one type, inferred payload) → `addMatcher` → `addDefaultCase`, in that order.
