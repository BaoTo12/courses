# Lecture 20.12 · ＋ Matchers: `isAnyOf`, `isPending`, `isRejected`, and a Global Loading/Error Slice

> **Section:** S20 · **Type:** 📖 Theory · **Track:** ＋ Extended · **Time:** ~25 minutes
> Verified: TaskFlow's `isAnyOf` matcher (in the tasks slice, covered by the write-thunk tests); the `requests` slice below was built and tested in a scratch test (2 tests pass) and is **not** added to TaskFlow, for the reason in §4.

---

## 1. `addMatcher`: one reducer for many action types

`addCase` handles one type. `addMatcher(predicate, reducer)` handles every action for which `predicate(action)` returns `true`. RTK ships predicate builders ("matchers") that are also **type guards**, so `action` is typed inside the reducer.

| Matcher | Matches |
|---|---|
| `isAnyOf(a, b, …)` | any of the given creators / matchers |
| `isAllOf(a, b, …)` | all of them |
| `isPending(thunkA, thunkB)` / `isFulfilled(…)` / `isRejected(…)` | those thunks' lifecycle actions; **with no arguments: any thunk's** |
| `isRejectedWithValue(…)` | rejected actions that carry a `rejectWithValue` payload |
| `isAsyncThunkAction(…)` | any lifecycle action of those thunks (or of any thunk) |

## 2. In TaskFlow: four thunks, one upsert

```ts
.addMatcher(
  isAnyOf(saveNewTask.fulfilled, saveTask.fulfilled, saveTaskChanges.fulfilled, toggleTaskOnServer.fulfilled),
  (state, action) => upsert(state, action.payload), // action.payload: Task (all four return a Task)
);
```

TypeScript computes `action` as the union of the four `fulfilled` action types; their payloads are all `Task`, so `action.payload` is `Task`. If one of them returned something else, `upsert(state, action.payload)` would stop compiling. The matcher is type-checked, not just convenient.

## 3. A global "anything loading?" slice

A classic use: a thin progress bar at the top of the page while **any** request is running, and a place for the last error. Without matchers, every slice would have to report its own loading state. With them:

```ts
interface RequestsState {
  pending: Record<string, string>; // requestId → thunk type prefix
  lastError: string | null;
}

const requestsSlice = createSlice({
  name: 'requests',
  initialState: { pending: {}, lastError: null } as RequestsState,
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addMatcher(isPending, (state, action) => {
        state.pending[action.meta.requestId] = action.type.replace(/\/pending$/, '');
      })
      .addMatcher(isFulfilled, (state, action) => {
        delete state.pending[action.meta.requestId];
      })
      .addMatcher(isRejected, (state, action) => {
        delete state.pending[action.meta.requestId];
        if (action.meta.condition || action.meta.aborted) return; // skipped or cancelled: not an error
        const payload = isRejectedWithValue(action) ? (action.payload as ApiErrorPayload | undefined) : undefined;
        state.lastError = payload?.message ?? action.error.message ?? 'Unexpected error';
      });
  },
});

const selectIsBusy = (state: { requests: RequestsState }) => Object.keys(state.requests.pending).length > 0;
```

What the scratch tests verified:

- After `fetchTasks.pending('a')` and `fetchCategories.pending('b')`: `pending` is `{ a: 'tasks/fetch', b: 'categories/fetch' }` and `selectIsBusy` is `true`.
- After `fetchTasks.fulfilled(…, 'a')`, a `saveNewTask.rejected` with a payload, and `fetchCategories.rejected(new Error('boom'), 'b')`: `selectIsBusy` is `false` and `lastError` is `'boom'` (the last one).
- A rejected action with `rejectWithValue({ message: 'Invalid title', … })` sets `lastError` to `'Invalid title'`, not `"Rejected"` (20.18).

Why keyed by `requestId` and not a counter? A counter works too, but the map also tells you **which** operations are running (handy in the DevTools), and deleting a key that isn't there is harmless, while decrementing a counter twice makes it negative. A thunk skipped by its `condition` doesn't reach this slice at all: neither `pending` nor its `rejected` action is dispatched (20.09 §7).

The `as ApiErrorPayload` cast is needed because generic `isRejected` (no arguments) can't know the payload type of every thunk in the app.

## 4. Why TaskFlow doesn't add it

- TaskFlow's pages already show loading and errors **where they happen** (the list's status, the form's field errors, toasts for background actions). A global bar would duplicate them.
- From S22, **RTK Query** tracks loading and errors per request and per cache entry, which removes most hand-written loading state.

Know the pattern; use it when a design really needs a global indicator.

## 5. Matchers and the builder order

Matchers run **after** the matching `addCase` for the same action, in the order they were added, and **all** matching matchers run (not just the first). Keep that in mind when a matcher and a case touch the same field.

## 6. 📇 API card: the matcher utilities

Every matcher is a function `(action: unknown) => action is SomeAction`: a **type guard**, usable in `builder.addMatcher`, in listeners (21.14), in middleware and in plain `if`s.

| Utility | Called with | Matches |
|---|---|---|
| `isAnyOf(m1, m2, …)` | action creators and/or matchers | any of them |
| `isAllOf(m1, m2, …)` | action creators and/or matchers (type guards) | all of them (verified; a plain boolean function isn't accepted by the types) |
| `isPending(...thunks)` | async thunks, or **nothing** | their `pending` actions; with no arguments, **any** thunk's |
| `isFulfilled(...thunks)` | same | `fulfilled` actions |
| `isRejected(...thunks)` | same | `rejected` actions (thrown, `rejectWithValue`, aborted, condition) |
| `isRejectedWithValue(...thunks)` | same | only rejections that carry a `rejectWithValue` payload |
| `isAsyncThunkAction(...thunks)` | same | any of the three lifecycle actions (verified) |
| `thunk.settled` | — | that thunk's `fulfilled` **or** `rejected` |
| `creator.match` | — | one action creator's actions |
| `isFluxStandardAction(value)` | a value | an object shaped `{ type, payload?, meta?, error? }` |

**Use them when** one reaction applies to a **family** of actions (all saves, all pending requests). **Prefer `addCase`** for one action: it's clearer and the payload type is exact.

**Common mistakes**

- Writing a matcher as a boolean function (`(a) => a.type.endsWith('/pending')`) and then reading `action.meta` in the reducer: without `action is …`, TypeScript knows nothing. Use the utilities, or declare the type guard.
- Passing a matcher **inline** to a listener's `matcher` option (TypeScript loses the action type there, 21.14).
- Expecting only the first matching matcher to run: **all** matching matchers run, after the matching case.

## 7. Summary

- `addMatcher(predicate, reducer)` handles families of actions; RTK's matchers are type guards.
- `isAnyOf(...creators)` for "these specific events"; `isPending()` / `isFulfilled()` / `isRejected()` without arguments for "any thunk".
- A global requests slice is 20 lines with matchers; use it only if the UI needs it.
