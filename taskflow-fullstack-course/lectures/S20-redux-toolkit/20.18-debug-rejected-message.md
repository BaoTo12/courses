# Lecture 20.18 · 🐞 Debug: the `rejected` Case Shows "Rejected" Instead of the Server's Message

> **Section:** S20 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~25 minutes
> Reproduced with RTK 2.12 in Vitest. The actions below are captured.

---

## Symptom (two teammates, two bugs)

**Bug A.** Stop the mock API and open the task list. Instead of *"The server is unavailable (HTTP 502). Try again in a moment."*, the error banner says:

> Rejected

The slice's `rejected` case:

```ts
.addCase(fetchTasks.rejected, (state, action) => {
  state.status = 'failed';
  state.error = action.error.message ?? 'Unexpected error';
})
```

**Bug B.** Another teammate "fixed" the banner by removing `rejectWithValue` from the thunk, letting the error propagate:

```ts
async (request: CreateTaskRequest, { extra }) => extra.api.createTask(request) // throws ApiRequestError
```

Now the banner shows the right text. But creating a task with a duplicate title no longer shows *"A task with this title already exists."* under the Title field: a red toast with the general message appears instead.

## Investigation checklist

1. For a thunk that returns `rejectWithValue(x)`, where does `x` end up in the rejected action? What's in `action.error` then? (20.09 §5)
2. For a thunk that **throws**, what does RTK copy from the error into `action.error`? Which fields of `ApiRequestError` survive?
3. What does `unwrap()` throw in each case? What does `fieldErrorsOf(error)` find?

## Explanation

Captured actions:

```json
// thunk returned rejectWithValue({ message: 'Server says no' })
{ "type": "demo/wv/rejected",
  "payload": { "message": "Server says no" },
  "meta": { "rejectedWithValue": true, … },
  "error": { "message": "Rejected" } }

// thunk threw new TypeError('boom')
{ "type": "demo/plain/rejected",
  "meta": { "rejectedWithValue": false, … },
  "error": { "name": "TypeError", "message": "boom", "stack": "…" } }
```

**Bug A:** with `rejectWithValue`, the information is in **`action.payload`**. `action.error` exists too, but only holds the generic `"Rejected"`. The reducer read the wrong field.

**Bug B:** without `rejectWithValue`, RTK **serialises** the thrown error into `action.error`, keeping only `name`, `message`, `stack` and `code`. The message survives, which is why the banner looked fixed. But `status`, `kind` and **`fieldErrors`** are dropped. `unwrap()` then throws that `SerializedError` (a plain object, 20.09 §8); `fieldErrorsOf` finds no `fieldErrors`, so `NewTaskPage` falls back to a toast.

## Fix

Keep `rejectWithValue` with a serialisable payload in every thunk, and read the **payload first** in reducers:

```ts
// thunk
} catch (error) {
  return rejectWithValue(toApiErrorPayload(error)); // kind, status, code, message, fieldErrors
}

// reducer
.addCase(fetchTasks.rejected, (state, action) => {
  // …
  state.error = action.payload?.message ?? action.error.message ?? 'Unexpected error';
})
```

The `??` chain covers all three origins of a rejected action: `rejectWithValue` (payload), an unexpected throw, e.g. a bug in the payload creator (`error.message`), and nothing usable (the fallback).

Verified in TaskFlow: the thunk test *"turns an API error into a rejected action with the SERVER message"* expects `payload` to match `{ kind: 'http', status: 503, message: 'Server unavailable' }` and the state's `error` to be `'Server unavailable'`; the duplicate-title check in the browser shows the field error under Title, with no toast.

### Make the wrong field hard to read

`createAppAsyncThunk` declares `rejectValue: ApiErrorPayload`, so `action.payload` is typed (`ApiErrorPayload | undefined`) in every `rejected` case. A team rule for review (20.13): *"a rejected case must read `action.payload` first"*.

## Lessons

- `rejectWithValue(x)` → `action.payload = x`, `action.error.message = "Rejected"`.
- A thrown error → `action.error` = `{ name, message, stack, code }`; custom fields are lost.
- Convert domain errors into a serialisable payload with everything the UI needs, and read `payload ?? error`.
