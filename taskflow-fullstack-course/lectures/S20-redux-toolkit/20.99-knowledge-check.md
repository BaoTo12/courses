<details>
<summary><b>Answers</b></summary>

1. `state` is an Immer **draft**, a Proxy around the current state. Writes are recorded on copies; the original is never touched. When the reducer finishes, Immer builds the next state: modified objects are new, untouched subtrees are the same references (structural sharing), and the result is frozen. The reducer effectively returns a new state, exactly like hand-written spreads.

2. Development: the **action-creator check** (warns on `dispatch(creator)` without calling it), the **immutability check** (throws on mutations inside or between dispatches), **thunk**, and the **serializability check** (logs non-serialisable values in actions and state). Production: only **thunk**.

3. Immer compares by **reference**. A new object literal is always a different reference, so it counts as a change, and the reducer returns a new state (verified: `=== s0` is `false`). Assigning identical **primitives** isn't recorded as a change, so nothing is modified and Immer returns the **same** state object (verified: `true`). Same state = no re-render for subscribers.

4. `tasks/fetch/pending` (`meta: { arg, requestId, requestStatus: 'pending' }`), `tasks/fetch/fulfilled` (`payload` = the returned value; `meta: { arg, requestId, requestStatus: 'fulfilled' }`), `tasks/fetch/rejected` (`meta: { arg, requestId, requestStatus: 'rejected', rejectedWithValue, aborted, condition }`, plus `error` and possibly `payload`). The thunk creator also exposes them as `fetchTasks.pending.type` etc., and `fetchTasks.typePrefix` is `'tasks/fetch'`.

5. (a) `payload: { message: 'No' }`, `meta.rejectedWithValue: true`, `error: { message: 'Rejected' }`. (b) no `payload`; `error: { name: 'TypeError', message: 'boom', stack: '…' }` (a serialised copy: custom fields of an error class would be lost). Captured in 20.09.

6. `createSlice` returns normally (RTK 2 runs the builder lazily); the **first reducer call** throws *"`builder.addCase` should only be called before calling `builder.addMatcher`"*. In the app that first call happens when the store is created, so TaskFlow fails at startup, and every test that builds a store fails too. Every `addCase` must come before any `addMatcher` (then `addDefaultCase`), because that's the order in which they run for an action: the matching case first, then all matching matchers. Move the `loggedOut` case above the matcher. **Chained**, it wouldn't even compile: the object returned by `addMatcher` has no `addCase` method, so TypeScript reports *"Property 'addCase' does not exist…"*. Chaining (TaskFlow's style) turns this runtime error into a compile error.

7. The promise returned by `unwrap()` **rejected** and nobody handled it: the call wasn't awaited inside a `try/catch` (for example `void dispatch(saveTask(…)).unwrap()`, or a `.then()` without `.catch()`). The browser logs *"Uncaught (in promise)"* with the payload; React error boundaries don't catch errors from event handlers or promises; **the user sees nothing**: no field errors, no toast, a form that looks stuck. Fix: `try { await dispatch(saveTask(…)).unwrap(); … } catch (error) { show field errors or a toast }`, or use `.match()` on the resolved action.

8. `dispatch(asyncThunk())` resolves with the **final action**, fulfilled or rejected, and an action object is always truthy. The S18 thunk resolved with `true`/`false`; the RTK one doesn't. Fix: `const result = await dispatch(deleteTask(id)); if (deleteTask.fulfilled.match(result)) navigate(back);` (or `unwrap()` in a `try/catch`). Verified in the browser: with the DELETE failing, the page stays and the error toast appears.

9. No. After the bad value enters the state, the **state** message repeats after **every** action and names whichever action just ran. Scroll up to the **first** message, the one about an **action** (*"…in an action, in the path: `payload.fetchedAt`"*, with the dispatched action): it identifies the thunk and the reducer that put the `Date` in. Fix: store epoch ms or an ISO string.

10. `reducers` define the slice's **own** events: each key generates an action type (`name/key`) and a creator. `extraReducers` handle actions **defined elsewhere**: other slices' events, `createAction` events, thunk lifecycles, matchers; they generate nothing. In the tasks slice: `auth/loggedOut` in `extraReducers` (`addCase(loggedOut, () => initialTasksState)`, owned by the auth feature); `ui/toastShown` **nowhere**: the tasks slice has no reason to react to toasts. The tasks **thunks** dispatch them; the ui slice handles them.

11. `uiSlice.ts` imports `deleteTask` and `clearCompleted` from `tasksThunks.ts` (for `extraReducers`), and the thunks dispatch toasts. With `toastShown` in `uiSlice.ts`, the two modules import each other. It works as long as every use is deferred (RTK 2 builds `extraReducers` lazily). But a single top-level use such as `export const TOAST_TYPE = toastShown.type` makes loading fail when `uiSlice` is imported first (verified: *"TypeError: Cannot read properties of undefined (reading 'type')"*). It's an import-order time bomb; a leaf module removes the cycle.

12. **Root reducer:** you can't forget a slice, and a new slice resets automatically. **Per slice:** each slice decides explicitly, in its own file, what a logout means for its data, including keeping non-user preferences (theme, language); the reset is visible where the data is defined and tested with the slice.

13. Verified in TaskFlow's reference project (the test passes):
    ```ts
    const fetchTasksOnce = createAppAsyncThunk(
      'tasks/fetch',
      async (query: TaskQuery | void, { extra, signal, rejectWithValue }) => {
        try {
          const page = await extra.api.getTasks(query ?? { size: 100 }, signal);
          return { tasks: page.items, fetchedAt: Date.now() };
        } catch (error) {
          return rejectWithValue(toApiErrorPayload(error));
        }
      },
      { condition: (_query, { getState }) => getState().tasks.status !== 'loading' },
    );
    ```
    ```ts
    it('a second dispatch while pending does not start a request', async () => {
      const getTasks = vi.fn(async () => ({ items: [], page: 0, size: 100, totalItems: 0, totalPages: 0 }));
      const store = makeStore(undefined, { api: { ...realApi, getTasks } });
      let notifications = 0;
      store.subscribe(() => notifications++);

      const first = store.dispatch(fetchTasksOnce());
      expect(store.getState().tasks.status).toBe('loading'); // pending was dispatched synchronously
      const second = store.dispatch(fetchTasksOnce());
      const [a, b] = await Promise.all([first, second]);

      expect(getTasks).toHaveBeenCalledTimes(1);
      expect([a.type, b.type]).toEqual(['tasks/fetch/fulfilled', 'tasks/fetch/rejected']);
      expect(fetchTasksOnce.rejected.match(b) && b.meta.condition).toBe(true);
      await expect(second.unwrap()).rejects.toMatchObject({ name: 'ConditionError' });
      expect(notifications).toBe(2); // pending + fulfilled: the condition's rejected action is NOT dispatched
    });
    ```
    It works because `pending` is dispatched **synchronously** inside the first `dispatch(...)`, so the second call's `condition` already sees `'loading'`.

    Why TaskFlow's `fetchTasks` doesn't use it: its callers pass **different queries** (search as you type, filters), and the **newest** query must win: a newer fetch aborts the older one and the reducer ignores stale responses (18.11). A "skip while loading" condition would drop the newer query and show results for an old one. The "don't fetch twice" rule belongs to callers that load the **same** data, which is what `fetchTasksIfNeeded` (a plain thunk) does for the layout.
