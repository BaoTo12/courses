# Lecture 20.17 · 🐞 Debug: an Immer Reducer Both Mutates *and* Returns. Why Is It Forbidden?

> **Section:** S20 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~20 minutes
> Reproduced with RTK 2.12 (Immer 11.1.18) in TaskFlow's reference project: the runtime error with Vitest, the compiler errors with `tsc`. All messages are captured.

---

## Symptom

During the `categories` migration (20.14), a teammate wants the `pending` case to also clear an old error, "in one go":

```ts
.addCase(fetchCategories.pending, (state) => {
  state.status = 'loading';
  return { ...state, error: null }; // "reset the error too"
})
```

`tsc` and lint are happy. At runtime, the first time categories load after a failure (or on the first load), the dispatch throws:

```text
Error: [Immer] An immer producer returned a new value *and* modified its draft. Either return a new value *or* modify the draft.
```

The sidebar never leaves its previous state, and TaskFlow's crash-reporting middleware (first in the chain, 16.14) reports the failure with the action type `categories/fetch/pending`.

## Investigation checklist

1. What did the case reducer do to the draft? What did it return?
2. If Immer accepted both, which result should it keep? (20.05 §3, rule 1)
3. Why doesn't TypeScript catch this, when it does catch `(state, action) => state.toasts.push(action.payload)`? (see below)

## Explanation

Immer's contract: a producer either **modifies the draft and returns nothing** (Immer builds the next state from the recorded changes), **or returns a completely new state** (Immer uses it as is, and the draft must be untouched). Here the reducer did both: it assigned `state.status` (a recorded change) **and** returned a new object. Which is "the" next state? The draft says `status: 'loading'` with the old error; the returned object happens to contain both changes, but only because the spread read the draft **after** the assignment. Reorder two lines and they'd differ. Immer refuses to guess and throws.

### What TypeScript catches and what it can't

RTK types a case reducer's return as `void | State | Draft<State>`.

- `return { ...state, error: null }` **is** a valid `State`, so the buggy reducer above compiles. Only Immer, at runtime, knows that the draft was also modified.
- A one-line arrow such as `(state, action) => state.toasts.push(action.payload)` returns a **number** (`push` returns the new length), and `tsc` rejects it. Captured, in `reducers`:

  > Type 'number' is not assignable to type 'void | NoInfer<{ toasts: Toast[]; ids: number[]; }> | WritableNonArrayDraft<NoInfer<…>>'.

  and in a builder `addCase`, the less readable:

  > error TS2769: No overload matches this call.

  followed by the same "Type 'number' is not assignable…" line inside *"Overload 1 of 2"*. When a builder call shows TS2769, read the first overload's message: it's the real reason. In a JavaScript file (no types), the one-liner compiles and throws the same Immer error at runtime.

## Fix

Pick **one** style:

```ts
// mutate (TaskFlow's choice for small changes)
.addCase(fetchCategories.pending, (state) => {
  state.status = 'loading';
  state.error = null;
})

// or return a whole new state, without touching the draft
.addCase(fetchCategories.fulfilled, (_state, action) => {
  return { ...normalize(action.payload), status: 'succeeded', error: null };
})
```

For one-line arrows that mutate, use a block body `{ … }`. (Also accepted by Immer: `void state.toasts.push(x)`, or returning the draft itself; the block body is clearer.)

## Lessons

- In Immer reducers: **mutate the draft, or return a new state**. Never both.
- TypeScript catches a returned non-state value (like `push`'s number), but not a returned state object after a mutation; only the runtime error does.
- On TS2769 "No overload matches this call", read the message under the first overload.
