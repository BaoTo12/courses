## 1. You have written Redux the long way on purpose

In S14–S19 you built every piece of Redux by hand: action type strings, action creators, `switch` reducers with spreads, `combineReducers`, `createStore` + `applyMiddleware` + the DevTools `compose`, thunks with a request id, memoised selectors. That wasn't wasted time. Everything Redux Toolkit (RTK) does is **a generated version of something you have already written**, so nothing in this section is magic.

Here is what the hand-written version cost you, with the lecture where you felt it:

| Pain | Where you met it |
|---|---|
| Every action spelled three times: the type string, the union member, the creator | 15.03, 19.01 |
| Nested spreads in every reducer case; one forgotten spread = a mutation bug | 15.05, 15.11 (`deepFreeze` in tests to catch it) |
| A type-safe `default:` branch needed `AppAction`, a union of **every** slice's actions | 15.07 |
| Redux 5's `combineReducers` inferred `never` for our narrow action unions → one cast | 16.03 §5 |
| `createStore` + `applyMiddleware` + `__REDUX_DEVTOOLS_EXTENSION_COMPOSE__` by hand | 16.11 |
| `Middleware[]` lost the thunk's dispatch type → `AppStore` declared by hand | 18.08 |
| Each async operation = 3 action types + 3 creators + 3 reducer cases + a request id generator | 18.06, 18.11 |
| "Is this value serialisable? Did I mutate?" checked only by discipline and tests | 19.10 |

None of these is hard. Together they are **a lot of places to make a small mistake**, and the mistakes (a mutation, a typo in a type string, a stale response) don't fail loudly.

## 2. What Redux Toolkit is

RTK is the **official** package for writing Redux logic (`@reduxjs/toolkit`, maintained by the Redux team). The Redux docs say it plainly: RTK is the standard way to write Redux today, and the "classic" style you learned is what RTK writes *for* you. The `redux` core is still inside it: `configureStore` calls `createStore`, `createSlice` produces an ordinary reducer function, and the store is the same object with `getState` / `dispatch` / `subscribe`.

| Hand-written (S14–S19) | RTK (S20) | What it generates or adds |
|---|---|---|
| `createStore` + `applyMiddleware` + DevTools compose | `configureStore` | thunk, DevTools, **dev-only checks** for mutation, serialisability and misuse of action creators (20.02) |
| type constants + creators + `switch` reducer | `createSlice` | action creators, action types (`name/reducerName`), the reducer (20.04) |
| spreads | **Immer** (inside `createSlice` / `createReducer`) | immutable updates written as mutations (20.05) |
| `(payload) => ({ type, payload })` | `createAction` | a creator with `.type` and `.match()` (20.07) |
| 3 action types + a request id per operation | `createAsyncThunk` | `pending` / `fulfilled` / `rejected`, `meta.requestId`, abort, `condition`, `unwrap()` (20.09) |
| `reselect` | re-exported `createSelector` | the same library (S21 goes deeper) |
| hand-normalised `{ ids, entities }` | `createEntityAdapter` | CRUD reducers and selectors (S21) |
| thunks + `useEffect` for server data | **RTK Query** | caching, deduplication, invalidation (S22–S23) |

## 3. What stays exactly the same

- One store, state is read-only, changes happen only by dispatching actions, reducers are pure (14.04).
- Actions are **events** named `domain/eventName` (15.03). `createSlice` builds exactly those names.
- Many reducers may respond to the same action (15.10). That's `extraReducers` (20.11).
- Components use `useSelector` / `useDispatch` through typed hooks (17.06).
- Selectors, normalisation, the status enum, "fetch if needed", ignoring stale responses: all your S18–S19 patterns keep working; RTK automates part of them.

## 4. How S20 is organised

1. **The store:** `configureStore` (20.02) and the RTK app structure (20.03).
2. **Slices:** `createSlice` (20.04), Immer (20.05), then you migrate `listPrefs` and `tasks` (20.06), with the helpers `prepare`, `createAction` and the builder (20.07).
3. **Types:** `.withTypes()` hooks (20.08).
4. **Async:** `createAsyncThunk` (20.09), then all S18 thunks are replaced and the hand-written boilerplate deleted, with honest line counts (20.10).
5. **Cross-slice events:** logout resets everything (20.11); matchers (20.12).
6. **Style Guide** rules for RTK code in review (20.13).
7. **Your turn:** `categories` + `ui` (20.14, solution 20.15).
8. **Debugging** the three errors RTK beginners hit first (20.16–20.18).

The rule for the whole section: **behaviour doesn't change**. The 87 tests written for the hand-written store must pass against the RTK store, with only a few expected edits (for example, thunks now resolve with an action instead of throwing, 20.10).

## 5. Summary

- RTK = the official, standard way to write Redux. It generates what you wrote by hand.
- It removes whole classes of mistakes: accidental mutation (Immer + checks), typos in type strings (generated), stale typings (inferred), missing pending/rejected handling (generated lifecycle).
- Understanding classic Redux is what lets you **debug** RTK, which is why you learned it first.
