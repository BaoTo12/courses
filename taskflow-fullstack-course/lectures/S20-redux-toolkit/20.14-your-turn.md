# Lecture 20.14 · 🎯 Your Turn: Migrate `categoriesSlice` and `uiSlice` (Toasts), Including `createAsyncThunk`

> **Section:** S20 · **Type:** 🎯 Your Turn · **Track:** ★ Core · **Time:** ~90 minutes

---

## 1. The task

Two slices are still hand-written: `categories` (with its S19 thunk) and `ui` (toasts and the bulk selection, with the temporary `.match()` block from 20.10 §5). Migrate both to RTK, then delete everything the migration made unnecessary.

## 2. Requirements

### `categories`

1. `fetchCategories` becomes a `createAsyncThunk` built with `createAppAsyncThunk`, type prefix `categories/fetch`.
2. It loads **once per session**: when the categories are loaded or loading, dispatching it again must not send a request, and must not dispatch `pending`. After a **failure**, dispatching it again retries.
3. Failures reject with a serialisable `ApiErrorPayload`; the slice stores the **server's** message.
4. The slice uses `createSlice`, same state shape (`{ ids, entities, status, error }`), and resets on `loggedOut`.
5. The selectors (`selectCategoryById`, `selectCategories`, `selectTaskCountsByCategory`) keep their names, behaviour and memoisation.

### `ui`

6. `createSlice` for the selection events: `taskSelectionToggled(id)` and `selectionCleared()`.
7. `toastShown({ tone, message })` generates the toast id with `nanoid` in a `prepare` callback; the id becomes a `string` everywhere (the `Toast` type, `toastDismissed`, the `ToastProvider`).
8. Thunks from **any** feature can dispatch `toastShown`, and `tasksThunks.ts` must not import `uiSlice.ts` (explain why in a comment).
9. Deleting a task, or clearing completed tasks, removes them from the selection. If none of them was selected, the reducer returns the **same** state object.
10. Everything resets on `loggedOut`.

### Clean-up

11. Delete `app/app-action.ts` and every use of `AppAction`; remove the `as Reducer<…>` cast in `rootReducer.ts`; remove the temporary `.match()` block in `ui`.
12. No test may be deleted. Tests may change only where behaviour changed on purpose (toast ids, renamed events).

## 3. Hints

<details>
<summary>Hint 1: "once per session" without a hand-written "if needed" thunk</summary>

`createAsyncThunk`'s third argument accepts `{ condition: (arg, { getState }) => boolean }`. Returning `false` means: don't run, don't dispatch anything (20.09 §7). Which statuses should allow a request?
</details>

<details>
<summary>Hint 2: where do the toast actions live?</summary>

`uiSlice.ts` will import `deleteTask` and `clearCompleted` from `tasksThunks.ts` (for `extraReducers`). If `tasksThunks.ts` imported `toastShown` from `uiSlice.ts`, the two modules would import each other. Put the toast actions in their own file with `createAction`, and let both import from it.
</details>

<details>
<summary>Hint 3: the fulfilled case of categories</summary>

The whole slice is rebuilt from the response. Returning a new value is simpler than assigning four fields (20.05 rule 1).
</details>

<details>
<summary>Hint 4: "the same state object when nothing changed"</summary>

With Immer, not assigning is enough: check whether any removed id is selected **before** assigning `state.selectedTaskIds = …filter(…)`.
</details>

## 4. Acceptance checklist

- [ ] `npm test`, `npx tsc -b`, `npm run lint` pass; no test deleted.
- [ ] `grep -r AppAction src` finds nothing; `rootReducer.ts` has no cast.
- [ ] A test proves `fetchCategories` calls the API **once** for two dispatches.
- [ ] A test proves a toast id is a string and two toasts get different ids.
- [ ] A test proves deleting an unselected task returns the same `ui` state object, and a store test proves a deleted **selected** task leaves the selection (there's no selection UI yet, so this is checked in tests).
- [ ] Browser: the sidebar shows the four categories with counts; toasts appear and auto-dismiss; `AppLayout` dispatches `fetchCategories()` on every user change, yet the logger shows `categories/fetch/pending` → `categories/fetch/fulfilled` only on the first load and after a logout (which reset the slice), and **nothing** after a login.
- [ ] No serializability warnings in the console.
