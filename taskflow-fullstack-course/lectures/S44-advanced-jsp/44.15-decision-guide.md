# Lecture 44.15 · When These Features Add Unnecessary Complexity: A Decision Guide

> **Section:** S44 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes

---

## Choosing the reuse mechanism

| Need | Use | Not |
|---|---|---|
| the same static markup on every page, no parameters | `<%@ include %>` of a `.jspf` (the header's meta tags) | a tag file (nothing to parameterise) |
| a self-contained widget that could be its own page | `<jsp:include>` (flash messages, 39.03) | a static include that shares every variable |
| a component with parameters and/or a body: layout, badge, pagination, form field | a **tag file** | `<jsp:include>` + string `<jsp:param>`s |
| Java logic producing output: formatting `java.time`, computing labels | a **`SimpleTagSupport`** handler | a tag file with EL gymnastics |
| a value inside an expression | an **EL function** | a tag (can't be used inside `${…}`) |
| data the page needs | the **controller** | any of the above |

## Warning signs

| Sign | Means |
|---|---|
| a tag file with ten attributes | it's a page, not a component |
| nested `<c:choose>` deciding business rules in a tag | the rule belongs in the service |
| a custom tag that queries the database | the view now has hidden I/O (and 43.07's committed-response problem) |
| an EL function per page | one-off helpers: a controller attribute is simpler |
| a TLD for something `fn:` already does | reuse JSTL |

## Where TaskFlow stops

Tag files for the layout, the badge, pagination and sort headers; two small handlers for dates; one function. Everything else stays in controllers, services and plain JSTL.

## ✅ Recap

Pick the lightest mechanism that fits: include → `<jsp:include>` → tag file → tag handler, and never move data access or business rules into the view layer.
