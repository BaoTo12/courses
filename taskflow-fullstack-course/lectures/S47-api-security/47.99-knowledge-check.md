# Lecture 47.99 · ✅ Knowledge Check: API Security for a Single-Page App

> **Section:** S47 · **Type:** ✅ Knowledge Check · **Track:** ★ Core · **Time:** ~15 minutes

---

**1. (Concept)** Does CORS stop curl from calling your API? Then what *does* it protect?

<details><summary>Answer</summary>

No. CORS is enforced by **browsers**; curl, Postman and servers ignore it, and TaskFlow answers them normally (authentication and CSRF still apply). CORS protects **users**: it stops other websites' JavaScript, running in the user's browser with the user's cookies, from **reading** your responses (and, through preflights, from sending non-simple requests). It's a relaxation of the same-origin policy for origins you trust (47.08).
</details>

**2. (Concept)** Why must `XSRF-TOKEN` be JS-readable while `JSESSIONID` must not be?

<details><summary>Answer</summary>

`JSESSIONID` **is** the authentication: if a script (an XSS) could read it, it could be sent elsewhere and used from another machine. It only needs to be **sent** by the browser, never read. `XSRF-TOKEN` proves the request came from a page of our origin: the SPA must **read** it to copy it into the header, which a cross-site page can't do. Stealing it without the session is useless (47.05, 47.07).
</details>

**3. (Debugging)** Login works in Postman, but the browser never stores the session cookie. Causes?

<details><summary>Answer</summary>

- **Cross-origin calls without credentials:** `fetch` without `credentials: 'include'` / Axios without `withCredentials: true` ignores `Set-Cookie` from another origin (and doesn't send cookies).
- **`SameSite=None` without `Secure`:** browsers reject it; over plain HTTP a `Secure` cookie is rejected too (41.99 Q4).
- **A different site:** cross-site cookies blocked by the browser's third-party cookie settings.
- **Path mismatch through a proxy:** `Path=/taskflow` while the page calls `/api` via Vite: the cookie is stored but never sent back (48.02).
- **CORS response without `Access-Control-Allow-Credentials: true`:** the browser discards the response, cookies included.
Postman has none of these rules, which is why it "works there".
</details>

**4. (Design)** Filter order for `/api/*`: CORS, logging, CSRF, auth. Justify.

<details><summary>Answer</summary>

TaskFlow: encoding → **logging** → errors → locale → **cors** → api → headers → maintenance → **apiCsrf** → **authentication** → authorization.
- **logging** first: every request, including rejected ones, gets a request id and a log line.
- **cors** before everything that can refuse: preflights are answered without credentials (47.16), and CORS headers are on every error so the SPA can read it.
- **api** (error JSON) right after, so anything later becomes JSON.
- **apiCsrf** before **authentication**: the login POST is protected as well, and a forged request is refused without even looking up the session.
- **authentication** then **authorization**: who, then what.
</details>

**5. (Security)** An attacker controls `blog.taskflow.example` and can set cookies for `taskflow.example`. What changes, and how do you harden against it?

<details><summary>Answer</summary>

The blog is **same-site** with TaskFlow, so `SameSite=Lax` no longer blocks its requests, and it can **plant** an `XSRF-TOKEN` whose value it knows. Two things still stand in its way: it's a different **origin**, so sending the `X-XSRF-TOKEN` header needs a CORS preflight that TaskFlow refuses; and it can't read TaskFlow's responses. The double submit has become the **only** barrier, though, and any mistake (the blog's origin added to the CORS list, an endpoint that accepts form posts) opens it. Harden with a **signed** token (an HMAC of the session id: a planted value doesn't verify) or the `__Host-` cookie prefix (a cookie with no `Domain`, which subdomains can't set, 41.12). And fix the subdomain.
</details>
