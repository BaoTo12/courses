# Lecture 47.11 · Dev vs Prod Topology: Vite Proxy, Separate Origins, One WAR

> **Section:** S47 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes

---

| Topology | The browser sees | CORS needed? | Cookies |
|---|---|---|---|
| **A. Vite proxy** (S48): the page and `/api` both from `http://localhost:5173`; Vite forwards `/api/*` to `http://localhost:8080/taskflow/api/*` | one origin | ❌ | Tomcat's cookies pass through the proxy; their `Path=/taskflow` must be rewritten to `/` (48.02) |
| **B. separate origins**: the SPA on `https://app.example`, the API on `https://api.example` | two origins | ✅ exact allow-list + credentials | `SameSite=Lax` still works (same **site**: `example`); across **sites** you'd need `SameSite=None; Secure` and lose that defence |
| **C. one WAR** (S49): React's build in the WAR's static files, the API at `/taskflow/api` | one origin | ❌ | nothing to rewrite |

## Which to choose

- **Development:** A. The SPA calls relative URLs (`/api/tasks`), exactly as in production C; no CORS configuration to get wrong; hot reload keeps working.
- **Production:** C (or any setup where a reverse proxy serves both under one origin). Simplest security: no CORS, same-site cookies, one TLS certificate.
- B only when you must (a separately deployed frontend, several frontends): then CORS is required and every item of 47.10 matters.

## Why TaskFlow still has a `CorsFilter`

`http://localhost:5173` calling `http://localhost:8080` **directly** (without the proxy) is topology B in miniature. The allow-list makes that work while developing, and the filter is where a production origin would be listed. With C in production, the list can be empty.

## ✅ Recap

Same origin (a proxy in development, one deployment in production) avoids CORS entirely. Separate origins need an exact allow-list, and cost you `SameSite` if they're separate sites.
