# Lecture 47.15 · 🐞 Debug: Every POST from React Gets 403

> **Section:** S47 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~15 minutes

---

## 1. Symptom

GETs work, login works in curl, but in the browser every POST/PATCH/DELETE (sometimes the login itself) answers `403 {"error":"CSRF_TOKEN_INVALID"}`.

## 2. Checklist: follow the token

| # | Cause | Where to look |
|---|---|---|
| 1 | the SPA never called `GET /api/auth/csrf`, so there's no cookie | DevTools → Application → Cookies: is `XSRF-TOKEN` there? |
| 2 | the cookie's **Path** doesn't cover the page: `Path=/taskflow` while the SPA runs at `/` (js-cookie can't see it) | the cookie's Path column; TaskFlow sets `Path=/` explicitly |
| 3 | the cookie is **HttpOnly** (someone "hardened" it) | the HttpOnly column: then JavaScript can't read it, by definition |
| 4 | the header **name** differs: `X-CSRF-TOKEN` vs `X-XSRF-TOKEN` | Network → the request's headers |
| 5 | the header is sent **stale**: the token rotated at login (a new `Set-Cookie`), the app kept the old value in memory | read the cookie per request (TaskFlow's interceptor does), not once at startup |
| 6 | a different **host**: the page on `127.0.0.1`, the API on `localhost` (different cookie jars) | the address bar vs the request URL |
| 7 | a proxy strips or renames custom headers | compare the browser's request with what Tomcat logs |
| 8 | for cross-origin calls: `withCredentials` off, so the cookie isn't sent | Axios config; the request's Cookie header |

## 3. The fastest check

In the Console on the SPA's page:

```js
document.cookie                        // must contain XSRF-TOKEN=…
```

Then compare its value with the `X-XSRF-TOKEN` header of the failing request in the Network tab. They must be identical.

## ✅ Takeaway

A double-submit 403 means the two copies differ or one is missing. Check the cookie (exists, readable, right path), then the header (right name, current value).
