# Lecture 47.07 · Why the Attacker Can't Read the Cookie to Forge the Header

> **Section:** S47 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes

---

Picture a page on `evil.example` trying `PATCH http://localhost:8080/taskflow/api/tasks/5` with the victim's session.

| Attempt | Blocked by |
|---|---|
| a `<form method="post">` | a form can't send `PATCH`, can't set headers, and can't send `application/json` → 415 (46.07); also no `X-XSRF-TOKEN` → 403 |
| `fetch(url, {method: "PATCH", credentials: "include", headers: {"X-XSRF-TOKEN": "?"}})` | a custom header (and `PATCH`, and JSON) makes it a **non-simple** request: the browser sends a **preflight** `OPTIONS` first; TaskFlow's CORS filter doesn't approve `evil.example` → the real request is never sent (47.08) |
| read `document.cookie` to get `XSRF-TOKEN` | `document.cookie` on `evil.example` shows `evil.example`'s cookies only (the same-origin policy) |
| read the token from a TaskFlow response | reading a cross-origin response requires CORS approval: denied |
| `SameSite=Lax` | on top of all that, the browser doesn't even attach `JSESSIONID` to cross-site subrequests |

## The one precondition

All of this assumes the attacker **can't run script on TaskFlow's own origin**. With XSS, the script is same-origin: it reads the cookie, sets the header, and the double submit passes. CSRF defences protect against *other* sites, never against XSS on your own (S26, S35, 40.12).

## SameSite's role

| | Without CSRF tokens | With them |
|---|---|---|
| `SameSite=Lax` | blocks cross-site POST/PATCH with cookies in modern browsers; not in older ones; not "same-site" attacks from sibling subdomains | defence in depth |
| `SameSite=None` (needed for truly cross-site cookie use) | no protection | the token is the defence |

## ✅ Recap

The attacker can make the browser send your cookie, but can't read it, can't set a custom header cross-origin without your CORS consent, and can't read your responses.
