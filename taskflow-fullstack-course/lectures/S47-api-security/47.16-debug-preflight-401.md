# Lecture 47.16 · 🐞 Debug: The Preflight `OPTIONS` Hits the Auth Filter and Gets 401

> **Section:** S47 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~15 minutes
> Verified: `S47ApiSecurityTest.corsAllowsOnlyTheListedOrigin` (the preflight → 204 without any session)

---

## 1. Symptom

With the SPA on another origin, GETs work but every PATCH/DELETE fails in the Console:

```text
Access to XMLHttpRequest at 'http://localhost:8080/taskflow/api/tasks/5' from origin 'http://localhost:5173'
has been blocked by CORS policy: Response to preflight request doesn't pass access control check:
It does not have HTTP ok status.
```

The Network tab shows `OPTIONS … 401` (or 403, or 302), and the PATCH is never sent.

## 2. Cause

The browser's preflight carries **no cookies** and **no custom headers**, by design. When the CORS handling sits after authentication (or the CSRF filter), the preflight is treated like an anonymous request: 401 (or a CSRF 403, or a redirect to the login page). A preflight must get a 2xx with the `Access-Control-*` headers, or the browser cancels the real request.

## 3. Fix

- Handle CORS **first** among the API filters, and **answer** preflights there without calling the chain (TaskFlow's `CorsFilter`, mapped before `api`, `apiCsrf` and `authentication`).
- Treat `OPTIONS` as a safe method in CSRF checks (TaskFlow's filters do).
- In Spring Security the same bug appears as "CORS works until I add authentication"; the fix is `http.cors()` so its CORS filter runs before the authentication filters.

## ✅ Takeaway

Preflights are anonymous by definition: answer them before any filter that demands a session or a token.
