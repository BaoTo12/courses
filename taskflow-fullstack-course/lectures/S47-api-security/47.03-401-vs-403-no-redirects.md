# Lecture 47.03 · 401 vs 403 for APIs; Never Redirect an API Call to a Login Page

> **Section:** S47 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes
> Verified: `S47ApiSecurityTest.anonymousApiCallsGetJson401NotARedirect`

---

## 1. What went wrong in S46

S46's API sat behind S41's `AuthenticationFilter`, which answers anonymous requests with `303 See Other → /taskflow/login?returnUrl=…`. For an XHR/fetch call:
- the browser **follows** the redirect silently (fetch does, Axios does);
- the SPA receives `200 OK` with the **HTML** of the login page;
- `JSON.parse` fails with "Unexpected token '<'", or worse, the code treats the HTML as data;
- the SPA never learns that the session expired, so it can't show its own login screen.

## 2. The API's answers

| Situation | Status | Body |
|---|---|---|
| no session / expired / account disabled | **401** | `{"error":"UNAUTHENTICATED","message":"Not logged in"}` |
| wrong username or password | **401** | `{"error":"BAD_CREDENTIALS","message":"Invalid username or password"}` |
| logged in, CSRF header missing or wrong | **403** | `{"error":"CSRF_TOKEN_INVALID"}` |
| logged in, another user's task | **404** (42.05) | `{"error":"NOT_FOUND"}` |
| too many login failures | **429** + `Retry-After` | `{"error":"TOO_MANY_REQUESTS"}` |

The React app (S24) already reacts to these: a 401 dispatches `auth/sessionExpired` → the cache is reset → the login page (48.04).

## 3. One filter, two behaviours

The request type decides, not the user agent or an `Accept` header guess:

```java
if (Api.isApiRequest(request)) throw ApiException.unauthenticated();     // /api/* → JSON 401
… Http.seeOther(response, login)                                          // pages → 303 to /login
```

`WWW-Authenticate` is required with 401 by the HTTP specification for HTTP authentication schemes (Basic, Bearer); cookie-session APIs commonly omit it, as TaskFlow's contract does.

## ✅ Recap

Pages redirect; APIs answer. 401 means "authenticate", 403 means "not allowed", always as JSON.
