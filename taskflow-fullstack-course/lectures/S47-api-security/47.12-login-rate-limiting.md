# Lecture 47.12 · 🛠 Build: Rate Limiting `/api/auth/login` (the S41 Throttle), 429 + `Retry-After`

> **Section:** S47 · **Type:** 🛠 Build · **Track:** ★ Core · **Time:** ~15 minutes
> Verified: `S47ApiSecurityTest.apiLoginIsThrottled` (5 failures → the 6th is 429, `Retry-After: 900`)

---

An API login endpoint is **easier** to brute-force than a form: no page to render, JSON in, JSON out, scriptable at thousands of requests per minute. It must share the form login's throttle, or attackers simply switch doors.

TaskFlow's API login calls the **same** `AuthService.login`, so the same `LoginThrottle` counts both (5 failures per account, 20 per IP, 15 minutes: 41.15). The servlet only translates the outcome:

```java
case THROTTLED -> {
  response.setHeader("Retry-After", String.valueOf(auth.throttleSeconds()));   // 900
  throw ApiException.tooManyRequests();                                        // 429 TOO_MANY_REQUESTS
}
default -> throw ApiException.badCredentials();                                // 401, the same for every failure
```

`Retry-After` survives the exception: `ApiExceptionFilter` calls `resetBuffer()`, which clears the body, not the headers.

| Client | Reaction to 429 |
|---|---|
| React (TaskFlow Web) | shows "Too many failed attempts. Please try again later." (the `message`) |
| a well-behaved script | waits `Retry-After` seconds |
| an attacker | loses the time, and the account stays safe even for the right password (41.15) |

**Beyond one server:** the throttle is in memory. With several instances, use a shared store or rate-limit at the reverse proxy (per IP) as an outer layer.
