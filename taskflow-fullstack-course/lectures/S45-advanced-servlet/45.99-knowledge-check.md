# Lecture 45.99 · ✅ Knowledge Check: Advanced Servlet Topics

> **Section:** S45 · **Type:** ✅ Knowledge Check · **Track:** ★ Core · **Time:** ~15 minutes

---

**1. (Concept)** Which of these are thread-safe *by construction*: local variables, servlet fields, request attributes, session attributes, context attributes?

<details><summary>Answer</summary>

| | By construction? |
|---|---|
| local variables | ✅ each thread has its own stack |
| request attributes | ✅ one request is handled by one thread at a time (async hand-offs happen-before by the API) |
| servlet fields | ❌ one instance, all threads |
| session attributes | ❌ the same user's concurrent requests (tabs, parallel AJAX) share them |
| context attributes | ❌ everyone shares them |

"Thread-safe" for the last three requires the **objects** to be immutable or concurrent (45.04).
</details>

**2. (Code reading)** Spot the concurrency bug:

```java
@WebServlet("/report")
public class ReportServlet extends HttpServlet {
  private final SimpleDateFormat format = new SimpleDateFormat("yyyy-MM-dd");
  private int generated;
  protected void doGet(HttpServletRequest req, HttpServletResponse res) throws IOException {
    generated++;
    res.getWriter().write("Report #" + generated + " for " + format.format(new Date()));
  }
}
```

<details><summary>Answer</summary>

Two: `generated++` is a read-modify-write on a shared field (lost updates, duplicate numbers: use an `AtomicInteger` or `LongAdder`), and `SimpleDateFormat` is not thread-safe (concurrent `format` calls corrupt its internal state and print wrong dates: use `DateTimeFormatter`, which is immutable). Also, the counter is per server and lost on restart: if the number matters, it belongs in the database.
</details>

**3. (Design)** Where do you create singletons (services, pools) in a plain Servlet app, and why not in a servlet's `init()`?

<details><summary>Answer</summary>

In a `ServletContextListener.contextInitialized` (45.08): it runs before every filter and servlet, in a defined order, fails the deployment if something is missing, and has `contextDestroyed` to close everything. A servlet's `init()` runs when **that** servlet loads, possibly after filters that already need the services; ownership of shared objects by one servlet is arbitrary; and its `destroy()` isn't the application's end. The objects go into context attributes (TaskFlow's `AppContextListener.taskService(context)` accessors).
</details>

**4. (Implementation)** Show the "currently active sessions" count on the admin dashboard.

<details><summary>Answer</summary>

Two counters exist: `AppStats.getActiveSessions()` (all sessions, from `HttpSessionListener`, 38.07) and `SessionRegistry.loggedInSessions()` / `loggedInUsers()` (logged-in ones, 45.09). In the controller:

```java
request.setAttribute("loggedInUsers", sessions.loggedInUsers());
request.setAttribute("activeSessions", stats.getActiveSessions());
```

and in the view: `Logged in now: <c:forEach …><c:out value="${name}"/></c:forEach> · all sessions: ${activeSessions}`. TaskFlow shows it on `/admin/audit`. Per server only: in a cluster, sessions live on several servers (or in a shared store).
</details>

**5. (Debugging)** `startAsync()` throws `IllegalStateException: A filter or servlet of the current chain does not support asynchronous operations`. Fix?

<details><summary>Answer</summary>

Every filter mapped to the request's path, and the servlet, must declare async support: `<async-supported>true</async-supported>` in each `<filter>` (or `asyncSupported = true` on `@WebFilter`/`@WebServlet`). One non-async filter in the chain is enough to forbid it (45.13).
</details>
