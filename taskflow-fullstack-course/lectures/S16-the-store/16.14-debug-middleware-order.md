# Lecture 16.14 · 🐞 Debug: Middleware Order: the Logger Shows the Action *After* a Transform You Expected Before It

> **Section:** S16 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~20 minutes
> Reproduced in the reference tests (`middleware.test.ts`, "16.14").

---

## Symptom

TaskFlow keeps accepting an old action type from a legacy widget, `LEGACY_SORT`. A `renamer` middleware translates it into `listPrefs/sortChanged`:

```ts
const renamer: Middleware = () => (next) => (action) =>
  next((action as { type: string }).type === 'LEGACY_SORT' ? sortChanged('title', 'desc') : action);
```

Two teammates set up recording middleware (like the logger) differently and get different results for the same `dispatch({ type: 'LEGACY_SORT' })`:

- Teammate A: `applyMiddleware(renamer, recorder)` records **`listPrefs/sortChanged`**.
- Teammate B: `applyMiddleware(recorder, renamer)` records **`LEGACY_SORT`**.

Teammate B's analytics dashboard shows thousands of `LEGACY_SORT` events, and "sort changed" looks unused. The product team almost removes the sort feature.

Verified: `seen` was `['listPrefs/sortChanged', 'LEGACY_SORT']` (A first, B second).

## Investigation checklist

1. In `applyMiddleware(m1, m2)`, which middleware receives the action first? (16.09)
2. What does each middleware see: the action as dispatched, or as passed to `next` by the previous one?
3. Which order is "correct" for a logger? For analytics? For a crash reporter?

## Explanation

The chain is `m1(m2(realDispatch))`. `m1` sees the action **as dispatched**; `m2` sees what `m1` passed to `next`.
- A: `renamer` first → it calls `next(sortChanged(…))` → `recorder` sees the **renamed** action.
- B: `recorder` first → it records `LEGACY_SORT` → then calls `next`, and `renamer` renames it afterwards.

Neither is a bug in Redux. The order **is** the configuration.

## Fix: decide what each middleware should observe

| Middleware | Should see | Position |
|---|---|---|
| Crash reporter | everything, including errors from other middleware | **first** |
| Transformers (renaming, adding `meta`) | the raw action | early |
| Logger / analytics | the action the **reducers** will receive | **after** transformers |
| Thunk (S18) | functions, before anything expects `{ type }` | early (in RTK's defaults, only the development-only immutability check comes before it) |

For TaskFlow: `applyMiddleware(crashReporter, renamer, logger, analytics)`.

The DevTools extension's compose (16.11) adds its enhancer as the **innermost** layer, closest to the real store, so it records what reaches the store after the whole middleware chain. It also shows `listPrefs/sortChanged`. When the logger and the DevTools disagree about an action, compare their positions.

## Lessons

- `applyMiddleware(a, b, c)`: `a` sees the action first, and `c` hands it to the reducers.
- Observers belong after transformers; the crash reporter belongs first.
- Keep transformers rare: code that silently rewrites actions surprises everyone. Prefer fixing the dispatching code (here: update the legacy widget, then delete the renamer).
