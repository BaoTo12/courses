## E. Implementation

14. Write a middleware that **blocks** any action with `meta.requiresAuth === true` when `state.auth.user` is `null`, and dispatches `ui/toastShown` ("Please log in") instead. <details>
<summary><b>Answers</b></summary>

1. ```text
   store.dispatch(action)
   └─ A: before → next(action)
      └─ B: before → next(action)
         └─ C: before → next(action)
            └─ real dispatch: reducers run, state saved, subscribers notified
         ┌─ C: after (state is already updated) → return result
      ┌─ B: after → return result
   ┌─ A: after → return result
   store.dispatch returns A's return value
   ```
   Verified trace: `A before, B before, C before, C after, B after, A after`.

2. **Currying + closures**: the outer levels run once (setup and chain assembly) and capture `storeAPI` and `next`. The inner function runs per action with both already available. Each middleware's `next => …` level maps a dispatch to a wrapped dispatch, so the chain can be built with **composition**: `compose(...chain)(realDispatch)`.

3. **Enhancer** for both. It controls store creation, so it can wrap the reducer before the store sees it and return a store with extra methods (`getDispatchStats`). Middleware only wraps `dispatch`.

4. So that state transitions are strictly ordered and predictable: when `dispatch(x)` returns, the reducers have processed `x` and every subscriber has run. Code that dispatches then calls `getState()` sees the result of its own action. Async work is added **outside** the store (thunks).

5. `f(g(h(x)))`. With no functions, `compose()` returns the identity: `compose()(x) === x`.

6. `before 0` → `listener 1` → `returned { type: 'inc' }` → `after 1`. The listener runs **inside** `dispatch`, before it returns.

7. Since Redux 5, the middleware's `action` parameter is typed `unknown`: with thunk middleware, **functions** also travel through the chain, and a function has no `.type`. `isAction` narrows safely; non-actions are passed on with `next(action)`.

8. `dispatch` notifies listeners **before** assigning the new state (`listeners.forEach(l => l()); state = reducer(state, action);`). Save first, then notify.

9. A middleware that calls `next(action)` without **returning** its result. `dispatch` then returns `undefined`, so `await undefined` resolves immediately and the thunk's promise (and its errors) is lost. Find it by testing `expect(store.dispatch(action)).toBe(action)` with the full chain, then bisecting the middleware list.

10. The module reads `window.__REDUX_DEVTOOLS_EXTENSION_COMPOSE__` at import time, and Vitest runs in Node, where `window` doesn't exist. (`import.meta.env.DEV` is `true` in Vitest, so that check alone doesn't help.) Guard with `typeof window !== 'undefined'`, and create stores through a `makeStore()` factory.

11. **Their order.** The analytics middleware is registered **before** the renamer, so it sees the raw action. The logger is **after** it, so it sees the renamed action. Put observers after transformers (and the crash reporter first).

12. **Yes:** logging, API calls (thunks are middleware), crash reporting, analytics. **No:** validating form input (UI and server), formatting for display (selectors).

13. **Allowlist.** It fails safe: new action types (possibly carrying credentials or personal data) aren't tracked until someone decides they should be. A denylist tracks everything new by default. And send the type only, never payloads.

14. One possible implementation (it type-checks against Redux 5's `Middleware` type):
    ```ts
    import { isAction } from 'redux';
    import type { Middleware } from 'redux';
    import { toastShown } from '../../features/ui/uiSlice';

    interface WithAuth {
      auth: { user: unknown };
    }

    const hasRequiresAuth = (action: unknown): boolean =>
      isAction(action) && (action as { meta?: { requiresAuth?: boolean } }).meta?.requiresAuth === true;

    export const requireAuthMiddleware: Middleware<object, WithAuth> = (storeAPI) => (next) => (action) => {
      if (hasRequiresAuth(action) && storeAPI.getState().auth.user === null) {
        storeAPI.dispatch(toastShown({ tone: 'info', message: 'Please log in to do that.' }));
        return undefined; // blocked: the action never reaches the reducers
      }
      return next(action);
    };
    ```
    When blocking, return `undefined` (or a meaningful value your team agrees on, documented), and **don't** call `next`. The toast is dispatched with `storeAPI.dispatch`, so it goes through the whole chain (logger, analytics). As 12.07 taught: this is UX only, and the API still rejects unauthenticated requests.
