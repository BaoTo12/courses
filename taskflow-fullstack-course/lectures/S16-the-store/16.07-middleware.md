# Lecture 16.07 · Middleware: `storeAPI => next => action`, and Why Three Nested Functions

> **Section:** S16 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~35 minutes
> 🔗 Official companion reading: Fundamentals Part 4 ("Middleware"); the Redux docs page "Middleware"

---

## 1. The problem middleware solves

You've seen three needs that don't fit in reducers (pure) or listeners (no action, 14.10):
- **logging** every action with what it changed;
- **side effects** in response to actions: analytics, crash reports, API calls (S18);
- **transforming or blocking** actions before reducers see them.

All three want to sit **between `dispatch(action)` and the reducer**. That's what middleware is: a pipeline around `dispatch`.

```text
dispatch(action) → [crash reporter] → [logger] → [analytics] → store's real dispatch → reducers
                  ←─────────────── return values travel back up the chain ───────────────┘
```

(Server-side analogy: servlet **filters** wrap servlets the same way, and `chain.doFilter(request, response)` is `next(action)`. You'll write filters in S40.)

## 2. The shape

```ts
const middleware = (storeAPI) => (next) => (action) => {
  // before: runs when the action arrives
  const result = next(action);       // pass it on down the chain (eventually: the reducers)
  // after: runs once everything further down has finished (state is updated)
  return result;                     // pass the result back up
};
```

| Level | Called | Receives | Used for |
|---|---|---|---|
| `storeAPI =>` | **once**, when the store is created | `{ getState, dispatch }` | Reading state, dispatching **new** actions (from the start of the chain) |
| `next =>` | **once**, when the chain is assembled | the **next** middleware's dispatch (or the store's real one) | Passing the action on |
| `action =>` | **for every dispatch** | the action | The actual work |

### Why three functions and not one `(storeAPI, next, action) =>`?

It's **currying** plus **closures** (04.08):
- The outer two levels run **once**, at setup, and their parameters are captured in closures. The innermost function is what runs per action, with `storeAPI` and `next` already available: no lookups, no re-wiring per dispatch.
- It lets `applyMiddleware` build the chain by **composition** (16.09): each middleware's `next =>` level is a function from "dispatch" to "wrapped dispatch", so the chain is `m1(m2(m3(realDispatch)))`. That's `compose`.
- The middleware can keep private per-store state in the outer closure (a counter, a queue).

## 3. `next(action)` vs `storeAPI.dispatch(action)`

- **`next(action)`**: continue **down** from this point. Middleware before this one don't see it again.
- **`storeAPI.dispatch(action)`**: start again from the **top** of the chain. Every middleware sees the new action, including this one (watch out for infinite loops).

Rule: pass the **current** action on with `next`; dispatch **new** actions with `storeAPI.dispatch`. Thunks (S18) depend on this: a thunk dispatches actions that must go through the whole chain.

## 4. Typing in Redux 5: `action` is `unknown`

```ts
import { isAction } from 'redux';
import type { Middleware } from 'redux';

export const example: Middleware = (storeAPI) => (next) => (action) => {
  if (!isAction(action)) return next(action); // a thunk (function) or something else: pass it on untouched
  console.log(action.type);                   // narrowed: { type: string }
  return next(action);
};
```

Since Redux 5, the innermost `action` parameter is typed **`unknown`**, not `AnyAction`. It's honest: with thunks installed, functions travel through middleware too, so code must check before reading `.type`. `isAction` (exported by Redux) is the type guard.

## 5. Summary

- Middleware wraps `dispatch`: code before `next` runs on the way in, code after runs once reducers are done.
- Three levels: setup-time `storeAPI`, chain-time `next`, per-action `action`, joined by closures.
- `next` continues down; `storeAPI.dispatch` restarts at the top.
- In Redux 5, `action` is `unknown`: narrow with `isAction`.
