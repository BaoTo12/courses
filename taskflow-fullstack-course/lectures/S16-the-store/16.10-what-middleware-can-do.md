# Lecture 16.10 · What Middleware Can Do: Modify, Delay, Stop, Dispatch More. Side Effects Live Here.

> **Section:** S16 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> 🔗 Official companion reading: Fundamentals Part 4 ("Middleware Use Cases")

---

## 1. The five powers

Inside `action => { … }`, a middleware can:

| Power | Code | Example |
|---|---|---|
| **Observe** | `const r = next(action); log(…); return r;` | Logger (16.08), analytics (16.12) |
| **Modify** | `return next({ ...action, meta: { at: now() } })` | Add metadata; rename legacy action types (16.14) |
| **Stop** | `return undefined` (don't call `next`) | Block actions that need a login (16.99 exercise) |
| **Delay** | `setTimeout(() => next(action), 500)` | Debounce noisy actions (rarely a good idea: 16.04's predictability is lost) |
| **Dispatch other actions** | `storeAPI.dispatch(toastShown(…))` | Show a toast when a save fails; thunks dispatch many actions (S18) |

It can also **return something other than the action**, and whatever the **outermost** middleware returns is what `store.dispatch(…)` returns. That's how thunk middleware makes `dispatch(fetchTasks())` return a **promise** (S18).

## 2. Side effects belong here

Reducers must be pure (15.04). Components shouldn't contain business logic. So where do API calls, timers, `localStorage` writes and analytics go?

**Middleware** (or thunks, which are themselves implemented as a tiny middleware). It's the place in Redux that's:
- **allowed** to be impure;
- **central** (every action passes through);
- **testable** (a middleware is a function; inject its dependencies as factory parameters, like TaskFlow's `createAnalyticsMiddleware(send)`).

The official Fundamentals tutorial puts it this way, in essence: middleware exist so that side effects can be written in one place, while reducers stay pure.

## 3. What NOT to put in middleware

- **Logic that computes state:** that's a reducer's job (and a reducer's test).
- **Validation of user input:** do it in the UI and on the server. A middleware silently stopping "invalid" actions makes bugs very hard to trace.
- **Formatting data for display:** use selectors.
- **Heavy work on every action:** middleware runs for every dispatch; keep the per-action path fast. `isAction` + a quick type check first.

## 4. Order matters

Each middleware sees the action as **modified by the ones before it**, and the results as **returned by the ones after it**. A logger placed before a transformer logs the original action; placed after, it logs the transformed one (16.14). A crash reporter must be **first** to catch errors from everything else.

## 5. Summary

- Middleware can observe, modify, stop, delay, dispatch more, and change `dispatch`'s return value.
- It's Redux's home for side effects; keep reducers pure and components thin.
- Keep middleware fast and focused, and mind the order.
