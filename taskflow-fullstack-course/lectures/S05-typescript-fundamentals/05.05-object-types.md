# Lecture 05.05 · Object Types: `type` vs `interface`, Optional, `readonly`, Index Signatures, Excess Property Checks

> **Section:** S05 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes

---

## 1. Describing object shapes

```ts
interface Task {
  id: number;
  title: string;
  description: string;
  status: TaskStatus;
  priority: Priority;
  dueDate: string | null;   // present, but may be null
  categoryId?: number;      // optional: may be absent (undefined)
}

// Equivalent with a type alias:
type TaskT = {
  id: number;
  title: string;
  // …
};
```

## 2. `type` vs `interface`

| | `interface` | `type` alias |
|---|---|---|
| Object shapes | ✅ | ✅ |
| Unions (`'A' \| 'B'`), tuples, primitives, functions | ❌ | ✅ |
| Extending | `interface B extends A {}` | `type B = A & { … }` (intersection) |
| **Declaration merging** (re-open and add fields) | ✅ | ❌ |
| Error messages | Show the interface name | Sometimes expand the full structure |

**Declaration merging** means two `interface X` declarations combine. Libraries use it to let you **augment** their types. You'll do this for the styled-components theme (S10) and i18next (S25):

```ts
declare module 'styled-components' {
  export interface DefaultTheme { colors: … }   // merges into the library's interface
}
```

**TaskFlow convention:** `interface` for object shapes (entities, DTOs, props), `type` for unions, tuples and computed types. Many teams use `type` for everything. Consistency matters more than the choice.

## 3. Structural typing: shape matters, not name

TypeScript is **structurally** typed: a value is compatible with a type if it has the required properties, whatever it's called:

```ts
interface HasId { id: number }
function findById(items: readonly HasId[], id: number) { … }

findById(tasks, 1);        // ✅ Task has id: number
findById(categories, 1);   // ✅ Category has id: number
```

That's different from Java, where a class must explicitly `implements` an interface (**nominal** typing). It's very convenient, and you'll use it with generics in 06.01.

## 4. Optional vs nullable

```ts
interface Example {
  a?: string;          // may be ABSENT → type string | undefined when read
  b: string | null;    // must be PRESENT; value may be null
  c?: string | null;   // may be absent, or present with null
}
```

These carry different meanings in an API contract:
- `dueDate: string | null`: the server always sends the field; `null` means "no due date".
- `categoryId?: number`: the field may be missing entirely.

Match what your backend actually sends. You'll align DTOs with the Java model in S06 and fix mismatches in S48.

> 🔎 With the stricter option `exactOptionalPropertyTypes` (enabled by `tsc --init` in recent TypeScript versions), `a?: string` means "absent **or** a string", and explicitly assigning `undefined` is an error. We don't enable it in the playground, but you may meet it.

## 5. `readonly` properties

```ts
interface Comment {
  readonly id: number;
  body: string;
}
const c: Comment = { id: 1, body: 'hi' };
c.id = 2;   // ❌ Cannot assign to 'id' because it is a read-only property.
```

Compile-time only (erased). `Readonly<Task>` makes every property readonly (06.03).

## 6. Index signatures and `Record`

For objects used as **dictionaries** (arbitrary keys):

```ts
interface TasksById {
  [id: number]: Task;
}
type CountsByStatus = Record<TaskStatus, number>;   // exactly the three keys, each a number
```

`Record<K, V>` with a union key type (`TaskStatus`) requires **all** keys, which is great for `groupByStatus` return types and lookup tables:

```ts
const PRIORITY_RANK: Record<Priority, number> = { LOW: 1, MEDIUM: 2, HIGH: 3 };
// forget HIGH → error: Property 'HIGH' is missing
```

With `noUncheckedIndexedAccess`, reading from an index signature (`byId[5]`) gives `Task | undefined`: the key might not exist. A `Record` over a finite union doesn't add `undefined`, because TS knows every key exists.

## 7. Excess property checks

```ts
const t2: Task = {
  id: 1, title: 'x', description: '', status: 'TODO', priority: 'LOW', dueDate: null,
  colour: 'red',
  // ~~~~~ error TS2353: Object literal may only specify known properties,
  //       and 'colour' does not exist in type 'Task'.
};
```

When you write an **object literal directly** where a type is expected, TS flags unknown properties. They're usually typos (`colour` vs `color`, `stauts` vs `status`). This check applies only to **fresh literals**; an existing variable with extra properties is allowed through structural typing.

## 8. Missing properties

```ts
const t: Task = { id: 1, title: 'x' };
//    ~ error TS2739: Type '{ id: number; title: string; }' is missing the following
//      properties from type 'Task': description, status, priority, dueDate
```

This is exactly the error that caught the incomplete test fixtures in 05.01.

## 9. Summary

- `interface` for object shapes (merge-able); `type` for unions/tuples/computed types.
- Structural typing: compatible if the shape fits.
- `?` = may be absent; `| null` = present but may be null. Match the API contract.
- `readonly` and `Record<K, V>`; index signatures for dictionaries.
- Excess property checks catch typos in fresh object literals.

## 10. Check yourself

1. The backend always sends `dueDate`, sometimes `null`. `dueDate?: string` or `dueDate: string | null`?
2. Why does `const x = { …task, extra: 1 }; const t: Task = x;` compile, but writing the literal inline doesn't?
3. `type` or `interface` for `TaskStatus`?

<details>
<summary>Answers</summary>

1. `dueDate: string | null`: the field is always present.
2. Excess property checks only apply to **fresh object literals**. An existing variable is checked structurally: it has all of `Task`'s properties, and extra ones are allowed.
3. `type`: it's a union of string literals, which interfaces can't express.

</details>
