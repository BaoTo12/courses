# Lecture 05.04 · Type Inference: When to Annotate and When to Let TypeScript Infer

> **Section:** S05 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes

---

## 1. TypeScript figures out most types for you

```ts
const count = 3;                         // number (actually the literal type 3, see §3)
let title = 'Write report';              // string
const ids = [1, 2, 3];                   // number[]
const task = { id: 1, done: false };     // { id: number; done: boolean }
const titles = tasks.map((t) => t.title); // string[] (inferred from Task)
```

**Inference** means TypeScript computes a type from the value or expression. Hover over any variable in VS Code to see what it inferred. That's the fastest way to build intuition.

## 2. Where to annotate (the practical rules)

| Annotate | Don't bother |
|---|---|
| **Function parameters** (TS can't guess what callers will pass) | Local variables initialised with a value |
| **Exported function return types** (a stable contract; catches accidental changes) | Callback parameters where the type flows in (`tasks.map((t) => …)`: `t` is `Task`) |
| **Empty initial values**: `const tasks: Task[] = []` (otherwise `never[]`) | Simple return types of small private helpers |
| **Object literals meant to be a known type**: `const t: Task = {…}` (enables excess-property checks) | Values whose type is obvious from the right-hand side |

```ts
// Parameters annotated, return type annotated (exported), locals inferred
export function countOpen(tasks: readonly Task[]): number {
  const open = tasks.filter((t) => t.status !== 'DONE');   // Task[], inferred
  return open.length;
}
```

### Contextual typing

Types flow **into** callbacks from where they're used:

```ts
tasks.forEach((task) => task.title.toUpperCase());   // task: Task, no annotation needed
button.addEventListener('click', (event) => event.clientX);   // event: MouseEvent
```

## 3. Literal types and widening

```ts
const s = 'TODO';   // type: 'TODO' (a literal type: exactly this string)
let s2 = 'TODO';    // type: string  ("widened", because let can be reassigned)
```

Why? A `const` can never change, so TypeScript keeps the precise literal. A `let` might be reassigned to any string, so TS widens it to `string`.

This matters immediately with union types (05.06):

```ts
type TaskStatus = 'TODO' | 'IN_PROGRESS' | 'DONE';

let s1 = 'TODO';
const st: TaskStatus = s1;
//    ~~ error TS2322: Type 'string' is not assignable to type 'TaskStatus'.

const s3 = 'TODO';
const ok: TaskStatus = s3;   // ✅ 'TODO' is assignable to TaskStatus
```

### Objects widen their properties

```ts
const filter = { status: 'DONE' };          // { status: string }: properties are mutable, so widened
filterTasks(tasks, filter);                 // ❌ string isn't assignable to TaskStatus | undefined

const filter2 = { status: 'DONE' } as const;          // { readonly status: 'DONE' }
const filter3: TaskFilter = { status: 'DONE' };       // annotated: checked against TaskFilter
filterTasks(tasks, { status: 'DONE' });               // inline: contextually typed ✅
```

`as const` (06.05) freezes literal types. Annotating the variable's type is often clearest.

## 4. Empty arrays and `null`: evolving types, and where they break

For a **local variable** initialised with `[]` or `null` (or nothing), TypeScript uses a special rule: the type **evolves** with later assignments in the same function:

```ts
const ids = [];
ids.push(1);                  // ids evolves to number[]
let x = null;
x = 'a';                      // x evolves to string: compiles
```

But this only works for simple locals. In **object properties**, and when the value **escapes** the function before its type is settled, you get errors:

```ts
const state = { dueDate: null };
state.dueDate = '2026-10-03';
//    ~~~~~~~ error TS2322: Type '"2026-10-03"' is not assignable to type 'null'.

const s2 = { tasks: [] };
s2.tasks.push(task);
//            ~~~~ error TS2345: Argument of type 'Task' is not assignable to parameter of type 'never'.

function make() { const out = []; return out; }
//                      ~~~ error TS7034: Variable 'out' implicitly has type 'any[]' in some locations…
```

The robust habit: **annotate empty collections and nullable starting values**.

```ts
const tasks: Task[] = [];
const state: { dueDate: string | null } = { dueDate: null };
```

(You'll meet the `never[]` error again with React: `useState([])` gives `never[]`, which is why you write `useState<Task[]>([])` in S08.)

## 5. Inference is not guessing from usage later

Apart from those evolving locals, TypeScript infers from the **initial value** and the **expression**, not from how you use a variable 50 lines later. If you need a wider type than the initial value suggests, annotate:

```ts
let priority = 'LOW';                  // string: TS doesn't know you meant a Priority
let priority2: Priority = 'LOW';       // ✅ the union: typos like 'HIHG' are caught
```

## 6. Summary

- TS infers types from values and expressions; hover to see them.
- Annotate **parameters**, **exported return types**, **empty collections** and **object literals of a known type**; let the rest be inferred.
- `const` keeps **literal types**; `let` and object properties **widen**. That affects union types.
- Types flow into callbacks (contextual typing).

## 7. Check yourself

1. Why does `const s = 'TODO'` have type `'TODO'`, but `let s = 'TODO'` has type `string`?
2. `const form = { dueDate: null }; form.dueDate = '2026-10-03';`: does it compile under strict? And `let x = null; x = 'a';`?
3. Should you annotate `t` in `tasks.filter((t) => t.status === 'DONE')`?

<details>
<summary>Answers</summary>

1. `const` can't be reassigned, so the exact literal is safe to keep; `let` could later hold any string, so TS widens to `string`.
2. The object version **fails** (`dueDate` is inferred as `null`). The local `let x = null` **compiles**, because simple locals get an evolving type. Annotate either way: `{ dueDate: string | null }`.
3. No. It's contextually typed as `Task` from `tasks: Task[]`.

</details>
