# Lecture 05.10 · `null` and `undefined` Under Strict Null Checks; `?.`, `??` and Indexed Access

> **Section:** S05 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes

---

## 1. "The billion-dollar mistake"

In Java, any object reference can be `null`, and `NullPointerException` is the most common runtime error. JavaScript has **two** "no value" values, `null` and `undefined`, and `TypeError: Cannot read properties of undefined` is its equivalent.

With `strictNullChecks` (part of `strict`), TypeScript makes absence **part of the type**:

```ts
let title: string = null;            // ❌ Type 'null' is not assignable to type 'string'.
let dueDate: string | null = null;   // ✅ absence is explicit
```

Now the compiler forces you to handle the `null` case before using the value (narrowing, 05.07):

```ts
function formatDue(task: Task): string {
  return task.dueDate.toUpperCase();
  //     ~~~~~~~~~~~~ error TS18047: 'task.dueDate' is possibly 'null'.
}
```

## 2. `null` vs `undefined`: a working convention

| | Meaning (convention) | Where it appears |
|---|---|---|
| `undefined` | "not set / not provided / missing" | Optional properties (`?`), missing function args, `array.find()` with no match, `obj.unknownKey` |
| `null` | "explicitly no value" | APIs/JSON (`"dueDate": null`); JSON has no `undefined` |

TaskFlow uses `null` for **data from the API** (because JSON has `null`) and `undefined` for **optional parameters/properties in code**. Don't treat them as interchangeable in comparisons: `x === null` doesn't match `undefined`. (`x == null` matches both, one of the few legitimate uses of `==`.)

## 3. Optional chaining `?.`

```ts
const name = task.owner?.displayName;          // undefined if owner is null/undefined
const first = tasks[0]?.title;                 // undefined if the array is empty
const len = q?.trim().length;                  // stops at the first nullish link
onSave?.(task);                                // call only if the callback exists
```

`a?.b` evaluates to `undefined` (not an error) when `a` is `null` or `undefined`. It short-circuits the rest of the chain.

## 4. Nullish coalescing `??` vs `||`

```ts
const label = task.categoryName ?? 'Uncategorised';   // only for null/undefined
const count = savedCount ?? 0;
```

**`||` is a trap for numbers and strings**:

```ts
const estimate = task.estimate || 1;    // 0 hours becomes 1 ❌ (0 is falsy)
const estimate2 = task.estimate ?? 1;   // 0 stays 0 ✅
const title = input || 'Untitled';      // '' becomes 'Untitled': maybe intended, maybe not
```

Use `??` when you mean "if missing"; use `||` only when you really mean "if falsy".

Assignment variants: `settings.pageSize ??= 20;` sets it only if it's null/undefined.

## 5. Non-null assertion `!`: use sparingly

```ts
const root = document.getElementById('root')!;   // "trust me, it's not null"
```

`!` removes `null | undefined` from the type **without any check**. If you're wrong, you get the runtime crash TypeScript was trying to prevent. Acceptable when you have knowledge TS lacks (the element is guaranteed by `index.html`); otherwise prefer a real check:

```ts
const root = document.getElementById('root');
if (!root) throw new Error('#root element missing from index.html');
```

## 6. `noUncheckedIndexedAccess`: honest array and dictionary access

```ts
const arr: string[] = ['a'];
const first: string = arr[0];
//    ~~~~~ error TS2322: Type 'string | undefined' is not assignable to type 'string'.
```

Without this option, TS assumes `arr[0]` is always a `string`, even for an empty array. That's a lie that causes real crashes. With it, index access returns `T | undefined` and you must handle it:

```ts
const first = arr[0];
if (first !== undefined) use(first);
const title = tasks[0]?.title ?? '(no tasks)';
```

Iteration methods (`for…of`, `map`, `forEach`) are **not** affected; the element type there is `string`, because every element visited exists.

## 7. `Array.find` returns `T | undefined`

```ts
const task = tasks.find((t) => t.id === id);   // Task | undefined
task.title;             // ❌ 'task' is possibly 'undefined'.
if (!task) return notFound();
task.title;             // ✅ narrowed to Task
```

Every "look up by id" in TaskFlow (details page, selectors, reducers) must decide what happens when the id doesn't exist. TypeScript makes that decision **unavoidable**, which is good, because "task not found" is a real scenario (deleted in another tab, bad URL, IDOR attempt).

## 8. Summary

- `strictNullChecks`: absence must be part of the type (`string | null`) and handled before use.
- Convention: `null` for API data, `undefined` for optional/missing in code.
- `?.` short-circuits on nullish; `??` defaults only for nullish (unlike `||`).
- `!` asserts without checking; use it sparingly.
- `noUncheckedIndexedAccess` and `find` make "might not exist" explicit.

## 9. Check yourself

1. What do `0 || 5`, `0 ?? 5`, `null ?? 5`, `'' ?? 'x'` evaluate to?
2. Why can't you write `task.dueDate.slice(0, 4)` without a check?
3. Write a safe expression for "the title of the first HIGH priority task, or `'—'`".

<details>
<summary>Answers</summary>

1. `5`, `0`, `5`, `''`.
2. `dueDate` is `string | null`; calling `.slice` on `null` would crash, so TS requires narrowing.
3. `tasks.find((t) => t.priority === 'HIGH')?.title ?? '—'`

</details>
