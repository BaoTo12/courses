# Lecture 05.06 · Union and Literal Types; Unions vs `enum`

> **Section:** S05 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes

---

## 1. Modelling "one of these values"

```ts
type TaskStatus = 'TODO' | 'IN_PROGRESS' | 'DONE';
type Priority = 'LOW' | 'MEDIUM' | 'HIGH';

let s: TaskStatus = 'DONE';     // ✅
s = 'BLOCKED';
//  ~~~~~~~~~ error TS2322: Type '"BLOCKED"' is not assignable to type 'TaskStatus'.
```

A **union type** `A | B | C` means "a value of type A, **or** B, **or** C". A **literal type** like `'DONE'` means "exactly this value". Combined, they model **enumerations** precisely, with autocomplete and typo detection, and **zero runtime cost** (erased like all types).

## 2. Unions of different types

```ts
type Id = number | string;
type DueDate = string | null;

function formatId(id: Id): string {
  return typeof id === 'number' ? `#${id}` : id.toUpperCase();   // narrowing, 05.07
}
```

With a union you can only use members that exist on **all** alternatives, until you narrow:

```ts
function f(x: number | string) {
  x.toUpperCase();
  // ❌ error TS2339: Property 'toUpperCase' does not exist on type 'string | number'.
  //      Property 'toUpperCase' does not exist on type 'number'.
}
```

## 3. `enum`: the alternative (and why TaskFlow doesn't use it)

```ts
enum TaskStatusEnum {
  Todo = 'TODO',
  InProgress = 'IN_PROGRESS',
  Done = 'DONE',
}
const s = TaskStatusEnum.Done;   // 'DONE' at runtime
```

Enums look familiar to Java developers. But they're one of the few TypeScript features that **generate runtime code** (an object), and that has consequences:

| | String literal union | `enum` |
|---|---|---|
| Runtime code | None (erased) | Generates an object |
| Works with type-stripping tools (Node's built-in TS support, `erasableSyntaxOnly`) | ✅ | ❌ (can't be stripped; must be compiled) |
| JSON from the API (`"status": "DONE"`) | Directly assignable after validation | You compare with `TaskStatusEnum.Done` everywhere, or cast |
| Iterating all values | Needs a separate `const` array (06.05) | `Object.values(TaskStatusEnum)` |
| Refactoring the *name* of a value | Change strings | Change one member |

The modern consensus in React/TS codebases is **string literal unions** (often paired with an `as const` array when you need to iterate, 06.05). You'll still read enums in existing code.

> 🔗 **Cross-stack note:** the backend has a Java enum `TaskStatus { TODO, IN_PROGRESS, DONE }`, serialised to JSON as `"TODO"`, … The TS union has **the same string values**, and the SCSS map uses the kebab-cased form. One concept, three representations, kept in sync by convention (and later by generated types, S48).

## 4. Unions describe states, not just values

Unions shine for modelling **alternatives with different data**. A preview of 06.06:

```ts
type LoadState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'succeeded'; tasks: Task[] }
  | { status: 'failed'; error: string };
```

This makes "loading **and** has an error" impossible to represent. You'll use this pattern for every async request in Redux (S19).

## 5. Summary

- Union `A | B`; literal types `'DONE'`; together they model fixed sets of values precisely.
- Only members common to all alternatives are usable until you narrow.
- Prefer **string literal unions** over `enum`: erased, JSON-friendly, compatible with type-stripping tools.
- Unions of object types model **states** (discriminated unions, 06.06).

## 6. Check yourself

1. What's the runtime JavaScript for `type Priority = 'LOW' | 'MEDIUM' | 'HIGH';`?
2. `enum TaskStatus` or a union of string literals, in a codebase that also has Java enums? Argue for one.

<details>
<summary>Answers</summary>

1. **Nothing.** Type aliases are erased completely.
2. A union: it matches the JSON strings the Java backend sends exactly, generates no runtime code, works with type-stripping tools, and gets autocomplete and typo checks anyway. (An enum is defensible if the team values `Object.values(TaskStatus)` and dot-access; it's a trade-off, not a crime.)
