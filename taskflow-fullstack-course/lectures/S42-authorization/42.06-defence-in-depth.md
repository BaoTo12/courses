# Lecture 42.06 · Defence in Depth: The UI Hides, the Server Enforces

> **Section:** S42 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes
> Verified: `S42AuthorizationTest.nonAdminsAreDeniedEveryAdminPathAndMethod` (no Users link for alice, and 403 anyway)

## 1. Two jobs, two layers

| Layer | Job | TaskFlow |
|---|---|---|
| **view** | don't **offer** what the user can't do: less confusion, fewer 403s | the nav shows **Users** only when `${currentUser.admin}` |
| **server** | **refuse** what the user can't do, however the request was made | `AuthorizationFilter` (URL), `TaskService` (data), `UserAdminService.requireAdmin` (again) |

```jsp
<%-- S42 (42.06): only admins SEE the link; AuthorizationFilter is what actually protects /admin/*. --%>
<c:if test="${currentUser.admin}">
  <a class="page__nav-link…" href="<c:url value='/admin/users'/>">Users</a>
</c:if>
```

## 2. Why hiding isn't access control

The browser isn't the only client. A user can type the URL, replay a request from DevTools (**Copy as cURL**), change a hidden field, or submit a form saved from an earlier visit. A `<c:if>` controls what's **drawn**, not what's **accepted**.

## 3. Layers inside the server

`/admin/users` is checked **twice**: by `AuthorizationFilter` (the URL) and by `UserAdminService` (`requireAdmin`, before any change). Why both?
- a future controller could call the service from a path outside `/admin` (the JSON API in S46);
- a mistake in the filter's mapping (42.11) doesn't expose the operation;
- the service is where a reviewer looks for "who may do this?".

The same applies to data: `TaskService` checks ownership for every use case, whichever controller calls it.

## 4. The costs, and where to stop

Each extra check is code to keep consistent. The rule of thumb: **one authoritative check** per rule, where the knowledge lives (the service for data, the filter for URL areas); the view only mirrors it for usability; duplicates only for high-value operations (user administration).

## ✅ Recap

Hide for usability, enforce for security. The enforcement lives on the server, as close to the data as possible.
