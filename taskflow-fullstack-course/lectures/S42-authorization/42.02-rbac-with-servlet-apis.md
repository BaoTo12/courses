# Lecture 42.02 · Role-Based Access Control with the Servlet API

> **Section:** S42 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes

---

## 1. RBAC in one table

Users have **roles**; roles have **permissions**. The code asks about roles (or, better, permissions), never about individual users.

| Role | TaskFlow may |
|---|---|
| `USER` | see, create, edit, delete **their own** tasks; comment on them; manage categories |
| `ADMIN` | everything a USER may, on **every** task; manage users (`/admin/*`) |

The role is a column (`users.role ENUM('USER','ADMIN')`), copied into `AuthUser` at login (41.07).

## 2. Our own check vs the container's

📇 **API card: container-managed security** (for recognition; TaskFlow doesn't use it)

| Piece | What it does |
|---|---|
| `<security-constraint>` + `<web-resource-collection><url-pattern>/admin/*` + `<auth-constraint><role-name>ADMIN` in `web.xml` | Tomcat refuses the URL to users without the role |
| `<login-config>` (`FORM`, `BASIC`) | Tomcat runs the login itself |
| a **Realm** (`JDBCRealm`, `DataSourceRealm`) in `server.xml`/`context.xml` | where Tomcat looks up users, password hashes and roles |
| `request.isUserInRole("ADMIN")`, `request.getUserPrincipal()`, `request.getRemoteUser()` | the programmatic checks |
| `@ServletSecurity(@HttpConstraint(rolesAllowed = "ADMIN"))` | the annotation form, per servlet |
| `request.login(user, pw)`, `request.logout()` | programmatic login into the container's mechanism (Servlet 3.0) |

| | Container-managed | TaskFlow's own (`AuthUser.role` + filters) |
|---|---|---|
| configuration | `web.xml` + realm, per server | code, in the application |
| throttling, audit, generic messages, `returnUrl` checks | not built in (valves, extensions) | ours (S41) |
| object-level checks ("own tasks") | not covered at all | the service (42.05) |
| portability | standard | ours to maintain |

Spring Security sits in between: a filter chain like S40's, with roles, method-level annotations (`@PreAuthorize`), and object-level hooks. Whichever you use, **object-level rules stay in your code**.

## 3. Roles vs permissions

With two roles, `user.isAdmin()` is fine. When roles multiply ("support may view but not delete"), check **permissions** (`can(user, Permission.DELETE_ANY_TASK)`) and map roles to permissions in one place. Checks written as `role == "ADMIN" || role == "SUPPORT" || …` scattered through the code are how access rules drift apart.

## ✅ Recap

RBAC: users → roles → permissions. The container can enforce URL rules; object-level rules are always the application's job.
