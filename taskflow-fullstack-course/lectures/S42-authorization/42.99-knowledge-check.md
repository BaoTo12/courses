# Lecture 42.99 · ✅ Knowledge Check: Authorization and Access Control

> **Section:** S42 · **Type:** ✅ Knowledge Check · **Track:** ★ Core · **Time:** ~15 minutes

---

**1. (Concept)** Why is `<c:if test="${sessionScope.user.role == 'ADMIN'}">` around a button not access control?

<details><summary>Answer</summary>

It decides what's **drawn**, not what the server **accepts**. The request behind the button can be sent without the button: typed, replayed from DevTools, scripted with curl. Access control is the server refusing the request (the filter for `/admin/*`, the service for data). The `<c:if>` is a usability layer on top (42.06). (And in TaskFlow's `session="false"` views, `sessionScope` would throw: 34.25.)
</details>

**2. (Debugging)** A disabled user can still use their existing session. What should happen, and where?

<details><summary>Answer</summary>

The session holds a copy of the user taken at login, and nothing re-checks it. The **next request** should end the session: compare the session's user with the account's current state in the authentication step, where every request passes. TaskFlow's `AuthenticationFilter` looks the account up in `AccountRegistry` (an in-memory snapshot refreshed when an admin changes an account), invalidates the session, audits `SESSION_REVOKED` and redirects to the login page (42.07). Alternatives: a query per request, or a session registry that invalidates the user's sessions immediately (45.09).
</details>

**3. (Design)** Filter-level checks vs service-level checks: which access rules belong where?

<details><summary>Answer</summary>

| Rule | Where | Why |
|---|---|---|
| "only admins under `/admin/*`" | filter | depends only on the URL and the role; one mapping covers every method and sub-path |
| "only the owner or an admin may edit task 23" | service | needs the row; every caller (HTML controllers, the S46 JSON API) passes through it |
| "users list only their own tasks" | service (`ownerScope`) | the query must be restricted, not the output |
| "admins can't change their own role" | service | a business rule about the data |

The filter can't decide object-level rules without loading data, which is the service's job. The service shouldn't know URLs.
</details>

**4. (Code reading)** Why does alice get a **404** for Bob's task but a **403** for `/admin/users`?

<details><summary>Answer</summary>

`/admin/users` isn't a secret: everyone knows the admin area exists, so "you may not" (403) reveals nothing. Task 23 is data: a 403 would confirm that task 23 exists and belongs to someone else, which lets ids be probed. Answering 404 makes "not yours" indistinguishable from "doesn't exist". Both are audited as `ACCESS_DENIED` (42.05).
</details>

**5. (Implementation)** Add a rule: comments on a task may be deleted by their author or an admin. Where does the check go, and what does it look like?

<details><summary>Answer</summary>

In the service, like `visible`:

```java
public boolean deleteComment(long commentId, AuthUser caller) {
  Optional<Comment> comment = comments.findById(commentId);
  if (comment.isEmpty()) return false;
  if (!caller.isAdmin() && comment.get().getAuthorId() != caller.getId()) {
    throw new AccessDeniedException("comment " + commentId);
  }
  return comments.delete(commentId);
}
```

The controller passes `CurrentUser.get(request)`; `AuthorizationFilter` already turns the exception into a 404 + audit. The view shows the Delete button only to the author and admins (for usability).
</details>
