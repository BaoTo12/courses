# Lecture 39.06 · Passing Data to Fragments: Request Attributes vs `<jsp:param>`

> **Section:** S39 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes

---

| | Request attribute | `<jsp:param>` |
|---|---|---|
| set by | the controller (or `<c:set scope="request">`) | the including page, per include |
| type | any **object** (a `Map`, a `List<Task>`, a bean) | a **string** |
| read as | `${errors}` / `${requestScope.errors}` | `${param.title}` |
| visible to | everything in this request, after it's set | the included resource only, for that include |
| encoding | none: it's a Java object | URL-encoded into a query string (request encoding: keep it ASCII, 39.03) |
| typical use | the data to show | a small per-use option: a title, a CSS modifier, a flag |

**For directive-included fragments** (`.jspf`), there's no parameter mechanism: they simply see the page's variables. That's why `task-row.jspf` starts with a comment stating its **contract**: `task`, `row`, `today`, `csrfToken`. It's the documentation a tag file (S44) would turn into declared, checked attributes.

**Rule of thumb:** data → request attributes (the controller's job); presentation options → `<jsp:param>`; implicit contracts → document them at the top of the fragment.
