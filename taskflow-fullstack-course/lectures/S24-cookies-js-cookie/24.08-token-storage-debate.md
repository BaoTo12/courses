# Lecture 24.08 · 🛡 The Token Storage Debate: localStorage vs Readable Cookie vs HttpOnly Cookie

> **Section:** S24 · **Type:** 📖 Theory (🛡 Security) · **Track:** ★ Core · **Time:** ~35 minutes
> 🔗 Reference: OWASP Cheat Sheets, "HTML5 Security → Local Storage" and "Session Management"

---

## 1. The question

Your app gets a credential after login: a session id or a JWT. Where does the browser keep it?

| Option | How it reaches the server | Readable by page JavaScript |
|---|---|---|
| **A. `localStorage`** + `Authorization: Bearer …` header | your code adds it | ✅ |
| **B. a JS-readable cookie** | the browser, automatically | ✅ |
| **C. an `HttpOnly` cookie** | the browser, automatically | ❌ |

## 2. Assume XSS happens

Assume an attacker runs JavaScript in your page (S26 shows how).

| | A. localStorage | B. readable cookie | C. HttpOnly cookie |
|---|---|---|---|
| **Steal** the credential and use it elsewhere, for as long as it's valid | ✅ trivially | ✅ trivially | ❌ **no** |
| **Ride** the session *from the victim's page* (make requests while it's open) | ✅ | ✅ | ✅ (the browser attaches the cookie) |
| Attack ends when the tab closes | ❌ | ❌ | ✅ mostly |

XSS is game over for that page **either way**. The difference is whether it's also game over for the account, for days. C limits the damage to "while the page is open", and it's the only option where a leaked `document.cookie` or `localStorage` dump contains no credential.

## 3. Assume CSRF is attempted

Another site makes the victim's browser send a request to your API.

| | A. localStorage + header | B/C. cookie |
|---|---|---|
| Browser attaches the credential automatically | ❌ **no**: the attacker's page can't read your localStorage | ✅ yes: needs `SameSite` + a CSRF token (24.10) |

This is A's one real advantage, and it's why header-token APIs "don't need CSRF protection". With C, you add `SameSite=Lax` and a CSRF token, which is cheap and well understood.

## 4. The verdict for TaskFlow (and most same-site web apps)

> **C: an `HttpOnly`, `Secure`, `SameSite=Lax` session cookie, plus a CSRF token.**
> The SPA never touches the credential. It asks `/api/auth/me`.

A is reasonable for **third-party API clients** (mobile apps, other servers), where there's no browser cookie jar. B has A's XSS weakness *and* C's CSRF exposure. Avoid it for credentials. It's fine for **non-secret** values like the CSRF token and preferences.

## 5. What to put in JS-readable cookies

| Value | JS-readable? | Why |
|---|---|---|
| session id | ❌ never | it *is* the login |
| CSRF token | ✅ must be | the SPA copies it to a header; useless to an attacker without the session **and** the same origin |
| theme, language | ✅ | not secret |
| user role | ❌ don't store it for decisions | the client can edit it. Show UI from `/auth/me`; the **server** checks the role on every request. |
| last visited task id | ✅, but user data | a session cookie, removed on logout (24.16) |

## ✅ Recap

- XSS can **ride** any session, but only non-HttpOnly storage lets it **steal** one.
- Cookies need CSRF protection, and headers don't. `SameSite` + a token solves that cheaply.
- TaskFlow: an HttpOnly session cookie, a readable CSRF cookie, readable preference cookies.
