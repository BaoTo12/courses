# Lecture 24.09 · Session-Cookie Authentication for SPAs

> **Section:** S24 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes
> The mock API implements this flow with `--secure`; the servlet backend implements the same contract in S38.

---

## 1. The whole flow

```text
App start ── GET /api/auth/me ──────────────► 401 UNAUTHENTICATED   → "nobody": show /login
                                             (or 200 {user}          → a session cookie from earlier is still valid)

Login ────── GET /api/auth/csrf ────────────► 204  Set-Cookie: XSRF-TOKEN=…           (first write: get a token, 24.11)
             POST /api/auth/login  {username, password}
             X-XSRF-TOKEN: …        ────────► 200 {user}
                                               Set-Cookie: JSESSIONID=…; HttpOnly; SameSite=Lax
                                               Set-Cookie: XSRF-TOKEN=<new>        (rotated on login)

Any call ─── GET /api/tasks   Cookie: JSESSIONID=… ───► 200     (the browser attached the cookie)

Expiry ───── GET /api/tasks ────────────────► 401               → sessionExpired → /login?returnTo=… (24.13)

Logout ───── POST /api/auth/logout  X-XSRF-TOKEN: … ► 204  Set-Cookie: JSESSIONID=; Max-Age=0   → clear everything local
```

## 2. The contract

| Endpoint | Success | Failure |
|---|---|---|
| `GET /api/auth/csrf` | `204` + `XSRF-TOKEN` cookie | — |
| `POST /api/auth/login` `{ username, password }` | `200` `User` + session cookie + a new CSRF cookie | `401 BAD_CREDENTIALS` (same message for an unknown user and a wrong password) |
| `GET /api/auth/me` | `200` `User` | `401 UNAUTHENTICATED` |
| `POST /api/auth/logout` | `204`, session ended, cookie cleared | — |
| everything else (secure mode) | as before | `401` without a session, `403 CSRF_TOKEN_INVALID` without a matching header on writes |

## 3. What the SPA keeps: only "who am I?"

The client state for auth is **one value**, `User | null`, from `/auth/me`. There's no token and no expiry time. The server decides everything else. That's why TaskFlow models it as an RTK Query endpoint (`getMe`), not a hand-written `authSlice`:

- it's **server state** (22.01): the truth lives in the server's session table;
- it's fetched once at start-up and cached;
- login and logout are **mutations** that write the answer into that cache entry (23.06).

## 4. The three states

| `getMe` state | Meaning | UI |
|---|---|---|
| loading (first time) | we don't know yet | "Checking your session…", **not** a redirect (24.12) |
| `data: null` | anonymous | protected routes redirect to `/login?returnTo=…` |
| `data: User` | logged in | the app |

## 5. Why a 401 from `/auth/me` is not an error

For `/auth/me`, "401" is the **answer** "nobody is logged in". Treating it as an error would show an error banner on every visit by an anonymous user. So `getMe` uses a `queryFn` that maps **401 → `data: null`**. Any other failure (network, 500) stays an error (24.12).

## ✅ Recap

The browser carries the session. The SPA asks `/auth/me`, sends the CSRF header on writes, and reacts to 401. Auth state is one cached `User | null`.
