# Lecture 24.15 · Axios's Built-in `xsrfCookieName` / `xsrfHeaderName` vs the Explicit Interceptor

> **Section:** S24 · **Type:** 📖 Theory · **Track:** ＋ Extended · **Time:** ~15 minutes
> 🔗 Reference: Axios docs, "Request Config" (`xsrfCookieName`, `xsrfHeaderName`, `withXSRFToken`)

*Extended track: outline.*

---

**What Axios does by itself (in browsers, with its XHR/fetch adapters):**

- It reads the cookie named by `xsrfCookieName` (default `'XSRF-TOKEN'`) and sends it in the header named by `xsrfHeaderName` (default `'X-XSRF-TOKEN'`). These are exactly our names, the same Angular-era convention.
- Since Axios 1.6, it does this only for **same-origin** requests, unless you set `withXSRFToken: true` (or a function deciding per request). Earlier versions also sent it cross-origin when `withCredentials` was on, which leaked the token to third-party hosts (CVE-2023-45857).
- It adds the header to **every** method, GET included.

**Why TaskFlow still has an explicit interceptor (24.11):**

| | Built-in | Our interceptor |
|---|---|---|
| Visible in our code, reviewable | ❌ a hidden default | ✅ |
| Fetches a token when there isn't one yet | ❌ | ✅ (`GET /auth/csrf`) |
| Unsafe methods only | ❌ all methods | ✅ |
| Works if Part 3's backend runs cross-origin | only with `withXSRFToken` | ✅ (still our cookie, our header) |
| Testable with a custom adapter | ❌ (it lives inside the browser adapters) | ✅ (`cookies.test.ts`) |

With the Vite proxy, both run, and the headers carry the same value. That's harmless. To keep one mechanism, disable the built-in with an instance config such as `xsrfCookieName: ''`. Check the Network tab after changing it.

**Takeaway:** know the default exists (it explains "where did this header come from?" moments), but keep security-relevant behaviour **explicit** in your own code.
