# Lecture 24.13 · 🛠 Build: 401 → `auth/sessionExpired` → Back to Login with `returnTo`

> **Section:** S24 · **Type:** 🛠 Build · **Track:** ★ Core · **Time:** ~45 minutes
> **Project feature:** when the server session ends (it expired, or the server restarted), the next request's 401 logs the user out cleanly, with one toast, and sends them to `/login?returnTo=<where they were>`.
> Verified: `src/features/auth/auth.test.ts` ("a 401 on a data request → sessionExpired": data cleared, user null, **one** toast for two simultaneous 401s), `tsc`, lint.

---

## 1. Where to detect it: the base query

✍️ `src/api/axiosBaseQuery.ts`

```ts
// S22 (22.03): RTK Query's "base query" = the ONE function every endpoint uses to talk to the server.
// Ours goes through the S13 Axios instance, so the interceptors (request id, timing, error normalisation)
// keep working, and failures reach RTK Query as the same serialisable ApiErrorPayload the thunks used.
import type { BaseQueryFn } from '@reduxjs/toolkit/query';
import type { AxiosRequestConfig } from 'axios';
import { ApiRequestError, toApiErrorPayload } from './api-error';
import type { ApiErrorPayload } from './api-error';
import { api } from './client';
import { sessionExpired } from '../features/auth/authActions';

/** What an endpoint's `query()` returns: a description of the HTTP request. */
export interface AxiosQueryArgs {
  url: string;
  method?: 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE';
  /** The JSON body (POST, PUT, PATCH). */
  data?: unknown;
  /** Query-string parameters; Axios drops `undefined` values. */
  params?: AxiosRequestConfig['params'];
  /** A type guard for the response body (13.05): a mismatch becomes an 'unexpected' error, not bad data. */
  validate?: (data: unknown) => boolean;
}

/** Endpoints for which 401 is an expected answer, not an expired session. */
const SESSION_ENDPOINTS = new Set(['getMe', 'login']);

export function axiosBaseQuery(): BaseQueryFn<AxiosQueryArgs, unknown, ApiErrorPayload> {
  return async ({ url, method = 'GET', data, params, validate }, { signal, dispatch, endpoint }) => {
    try {
      // `signal` is RTK Query's AbortSignal (22.06): `queryResult.abort()` really aborts the HTTP request.
      const response = await api.request({ url, method, data, params, signal });
      if (validate && !validate(response.data)) {
        const error = new ApiRequestError({ kind: 'unexpected', message: 'The server sent an unexpected response.' });
        return { error: toApiErrorPayload(error) };
      }
      return { data: response.data };
    } catch (error) {
      // The response interceptor already turned any failure into an ApiRequestError (13.08);
      // RTK Query stores `error` in its cache, so it must be plain, serialisable data (20.16).
      const payload = toApiErrorPayload(error);
      // 401 = "no session" (24.13). For getMe and login that's an ANSWER; anywhere else the session is gone.
      // An action, not a redirect: the base query knows nothing about routing; a listener decides.
      if (payload.status === 401 && !SESSION_ENDPOINTS.has(endpoint)) dispatch(sessionExpired());
      return { error: payload };
    }
  };
}
```

- **Every** RTK Query request passes through here, and `BaseQueryApi` gives us `dispatch` and `endpoint` (22.03).
- **`SESSION_ENDPOINTS`**: for `getMe` and `login`, a 401 is the **expected answer** ("nobody", "wrong password"). Dispatching `sessionExpired` there would loop or show a bogus toast.
- **An action, not a redirect.** The base query knows HTTP, not routing or toasts. It reports a fact, `auth/sessionExpired`, and a listener decides what to do. That's the same split as the task toasts (22.09).

The action is declared next to `loggedOut` in `src/features/auth/authActions.ts`:

```ts
/** S24 (24.13): the API answered 401 to a logged-in user: the server session is gone (expired, or ended elsewhere). */
export const sessionExpired = createAction('auth/sessionExpired');
```

## 2. The reaction: a listener

✍️ `src/features/auth/authListeners.ts`

```ts
import type { AppStartListening } from '../../app/listeners';
import { toastShown } from '../ui/toastActions';
import { sessionExpired } from './authActions';
import { authApi } from './authApi';
import { clearUserData } from './clearUserData';

const selectMe = authApi.endpoints.getMe.select();

/**
 * 24.13: the server said 401 to a request that needed a session. Forget the user and their data; `RequireAuth`
 * then sends them to /login?returnTo=<where they were>. After a successful login they come back there.
 */
export function addAuthListeners(startAppListening: AppStartListening) {
  startAppListening({
    actionCreator: sessionExpired,
    effect: (_action, listenerApi) => {
      // Several requests can fail with 401 at once: react to the first only. Once "me" is null, ignore.
      if (!selectMe(listenerApi.getState()).data) return;
      listenerApi.dispatch(clearUserData());
      listenerApi.dispatch(authApi.util.upsertQueryData('getMe', undefined, null));
      listenerApi.dispatch(toastShown({ tone: 'info', message: 'Your session has expired. Please log in again.' }));
    },
  });
}
```

- **"React to the first only."** A page often has several requests in flight: the list, the categories, a task. All of them fail with 401 at once. The guard `if (!me) return` makes the second and later ones no-ops. The test fires two and expects **one** toast.
- **`clearUserData()`** is the same clean-up as a normal logout (23.11): slices, cache and user cookies.
- **Setting `getMe` to `null`** is what makes `RequireAuth` redirect. There's no `navigate()` here: the listener doesn't know about the router, and doesn't need to.
- Register it in `src/app/listeners.ts`: `addAuthListeners(startAppListening); // 24.13`.

## 3. The redirect, for free

```text
401 → sessionExpired → listener: clearUserData + me = null
    → RequireAuth re-renders: user === null → <Navigate to="/login?returnTo=%2Ftasks%2F5" replace />
    → login → LoginPage navigates to safeReturnTo('/tasks/5')
```

`RequireAuth` (24.12) already builds `returnTo` from the **current** location, so the user lands exactly where the session died.

## 4. What about requests outside RTK Query?

The quick-find listener calls `extra.api.getTasks` directly (21.15), so it doesn't go through the base query. Its 401 shows as a failed search, and the **next** RTK Query request triggers the logout. That's acceptable here. If more code bypassed RTK Query, the detection would move into the Axios **response interceptor**, with a callback registered by the store (`setUnauthorizedHandler(() => store.dispatch(sessionExpired()))`). That's the pattern to use when the API module can't import the store.

## ✅ Checkpoint

Log in, open a task. Restart the mock server: sessions live in memory, so they're gone. Click another task: one toast, "Your session has expired. Please log in again.", then the login page with `returnTo`. Log in again, and you're back on that task.
