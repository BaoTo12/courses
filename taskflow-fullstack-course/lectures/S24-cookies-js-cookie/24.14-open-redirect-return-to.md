# Lecture 24.14 · 🛡 Open Redirect via `returnTo`: Allow Internal Paths Only

> **Section:** S24 · **Type:** 📖 Theory (🛡 Security) · **Track:** ★ Core · **Time:** ~25 minutes
> Verified: `src/domain/safe-redirect.test.ts` (since S12)
> 🔗 Reference: OWASP Cheat Sheet, "Unvalidated Redirects and Forwards"

---

## 1. The attack

`/login?returnTo=…` is now a real feature: after a successful login, we navigate to it. An attacker emails:

```text
https://taskflow.example/login?returnTo=https://taskflow-login.evil.example/session-expired
```

The link **really is taskflow**, so the user trusts it. They log in, and TaskFlow itself sends them to a look-alike page that says "Session expired, please enter your password again". That's phishing with our domain's credibility. Variants target OAuth flows to steal tokens.

## 2. The rule: an allow-list, not a block-list

Accept **only app-internal paths**. `safeReturnTo` (written in S12, used for real now):

```ts
export function safeReturnTo(value: string | null, fallback = '/tasks'): string {
  if (value === null) return fallback;
  if (!value.startsWith('/')) return fallback;                           // https://evil…, javascript:…, evil.com
  if (value.startsWith('//') || value.startsWith('/\\')) return fallback; // protocol-relative tricks
  return value;
}
```

| Input | Why it's dangerous | Result |
|---|---|---|
| `/tasks/5?view=board` | — | ✅ kept |
| `https://evil.example` | absolute URL | ❌ `/tasks` |
| `//evil.example` | **protocol-relative**: the browser reads it as `https://evil.example` | ❌ |
| `/\evil.example` | some browsers normalise `\` to `/`, which gives `//evil.example` | ❌ |
| `javascript:alert(1)` | script URL | ❌ (doesn't start with `/`) |
| `evil.example` | relative to the current path in some APIs | ❌ |

## 3. Why React Router alone isn't the risk here, and why we validate anyway

`navigate('https://evil.example')` in React Router treats the string as a **path** inside the app, so it wouldn't leave the site. But:

- the same `returnTo` is used by the **server** in S38 (`response.sendRedirect(returnTo)`), and there it's a real redirect;
- `window.location.assign(returnTo)`, which you might use later to force a reload after login (23.10 §4), **would** leave the site;
- validation at the boundary is cheap, and it survives refactors.

## 4. Stronger options

- **Only the pathname**: `new URL(value, window.location.origin)`, then check that `url.origin === window.location.origin` and use `url.pathname + url.search`. This normalises everything the browser would.
- **An opaque key**: store the target in `sessionStorage` under a random id, and pass only the id in the URL.

## ✅ Recap

`returnTo` is attacker-controlled input. Allow internal paths (`/…`, not `//…` or `/\…`) and fall back otherwise. Validate on both sides: the SPA here, the server in S38.
