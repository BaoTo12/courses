# Lecture 24.19 · 🐞 Debug: `Cookies.get('JSESSIONID')` Is `undefined`, but DevTools Shows It

> **Section:** S24 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~15 minutes

---

## 1. The report

> "I want the header to show 'Logged in' only when there's a session, so I wrote `const loggedIn = Cookies.get('JSESSIONID') !== undefined`. It's always false, even right after login. DevTools clearly shows the JSESSIONID cookie. js-cookie bug?"

## 2. Investigate

1. DevTools → Application → Cookies → `JSESSIONID`: the **HttpOnly** column is ✓.
2. Console: `document.cookie` doesn't contain `JSESSIONID`. js-cookie reads `document.cookie`, so it can't see it either.
3. Network → any `/api` request → Request Headers: `Cookie: JSESSIONID=…`. The browser **does** send it.

## 3. Diagnosis: working as designed

`HttpOnly` cookies are hidden from page JavaScript on purpose (24.07). **Not a bug, and not fixable from the client.** And it must not be "fixed" on the server by removing `HttpOnly`: that would expose the session to every XSS (24.08).

## 4. The right way to answer "am I logged in?"

Ask the server: `GET /api/auth/me` → `User` or 401 (24.09). TaskFlow already has it: `useAuth().user`, from the `getMe` cache entry (24.12).

Even if JavaScript *could* see the cookie, "a cookie exists" wouldn't mean "the session is valid". It may have expired server-side, or the server may have restarted. Only the server knows.

## ✅ Takeaway

If DevTools shows a cookie that JavaScript can't read, check the HttpOnly column first. For sessions, that's the point. Ask an endpoint instead.
