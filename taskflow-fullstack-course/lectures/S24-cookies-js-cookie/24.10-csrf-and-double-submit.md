# Lecture 24.10 · 🛡 CSRF in One Picture, and the Double-Submit Cookie Defence

> **Section:** S24 · **Type:** 📖 Theory (🛡 Security) · **Track:** ★ Core · **Time:** ~40 minutes
> 🔗 Reference: OWASP Cheat Sheet, "Cross-Site Request Forgery Prevention"
> The attack lab against your own local TaskFlow comes in S26; the server-side filter in S41.

---

## 1. The attack

```text
alice is logged in to taskflow (JSESSIONID cookie in her browser)
alice visits evil.example, which contains:

  <form action="https://taskflow.example/api/tasks/7" method="POST">…</form>
  <script>document.forms[0].submit()</script>

The browser sends the POST to taskflow WITH alice's cookie (cookies are attached automatically, 24.01).
The server sees a valid session → the request "comes from alice".
```

**Cross-Site Request Forgery**: another site makes the victim's browser send an authenticated request. The attacker can't read the response (the same-origin policy), but the **side effect** happens: a delete, a transfer, a password change.

## 2. Layers of defence

| Layer | How it helps | Limit |
|---|---|---|
| `SameSite=Lax` on the session (24.02) | cross-site POSTs arrive **without** the cookie | same-*site* attackers (a sibling subdomain), old browsers, GET endpoints with side effects |
| JSON-only writes (the mock returns 415 otherwise) | a plain HTML form can't send `application/json` | other request types; not a guarantee on its own |
| **A CSRF token** | the request must prove it came from **our** page | — |

## 3. The double-submit cookie

```text
① Server sets a random token in a cookie that JavaScript CAN read:
     Set-Cookie: XSRF-TOKEN=9a1e…; Path=/; SameSite=Lax          (NOT HttpOnly, on purpose)
② Our SPA reads it (js-cookie) and copies it into a header on every unsafe request:
     POST /api/tasks   Cookie: JSESSIONID=…; XSRF-TOKEN=9a1e…   X-XSRF-TOKEN: 9a1e…
③ Server: cookie value === header value?  yes → proceed.  no/missing → 403 CSRF_TOKEN_INVALID
```

**Why it works, even though the attacker's request carries the cookie:**

- The attacker's page can make the browser **send** the cookie, but it can't **read** it. `evil.example` has no access to `taskflow.example`'s cookies (the same-origin policy).
- A header like `X-XSRF-TOKEN` can't be added by a cross-site form. A cross-site `fetch` with custom headers triggers a CORS preflight, which our server refuses.
- So the attacker can't make the header match the cookie. Only JavaScript running **on our origin** can.

**What it doesn't protect against:** XSS. A script on our origin can read the token too. CSRF defences assume there is no XSS (S26).

## 4. Details that matter

- **Unsafe methods only**: POST, PUT, PATCH, DELETE. GET must have no side effects, so it doesn't need the token.
- **Rotate on login**: the mock issues a new token at login. A token planted before login is worthless after it.
- **Random and long enough** (a UUID here). Compare in constant time on the real server (S41).
- The "synchroniser token" variant stores the token in the server session instead of comparing it with a cookie. Spring and Tomcat filters do either. S41 builds one.

## ✅ Recap

- CSRF abuses automatic cookies. `SameSite=Lax` blocks most of it, and a token blocks the rest.
- Double submit: a readable cookie, copied to a header by **our** JavaScript, compared by the server.
- It relies on the attacker being unable to read our cookies, so XSS defeats it.
