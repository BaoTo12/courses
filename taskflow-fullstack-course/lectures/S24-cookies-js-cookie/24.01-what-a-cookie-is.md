# Lecture 24.01 · What a Cookie *Is*: `Set-Cookie` → Browser Storage → `Cookie`

> **Section:** S24 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes
> 🔗 Reference: MDN, "Using HTTP cookies"; RFC 6265 (HTTP State Management)

---

## 1. HTTP forgets, cookies remember

HTTP is **stateless**: each request stands alone. The server can't tell that `GET /tasks` and `POST /tasks` a second later come from the same person. A **cookie** is how it gets memory. It's a small `name=value` string the **server** asks the **browser** to store and send back.

```text
① Browser ─────────────── POST /api/auth/login ───────────────► Server
② Browser ◄── 200 OK
              Set-Cookie: JSESSIONID=5f2c…; Path=/; HttpOnly; SameSite=Lax
              Set-Cookie: XSRF-TOKEN=9a1e…; Path=/; SameSite=Lax
③ The browser stores both, under the server's host (localhost), with their attributes.
④ Browser ─── GET /api/tasks
              Cookie: JSESSIONID=5f2c…; XSRF-TOKEN=9a1e…  ─────────► Server: "session 5f2c… is alice"
```

## 2. Three facts that drive the whole section

1. **The browser attaches cookies automatically.** On every request to a matching host and path, the `Cookie` header is added by the **browser**. Not by Axios, and not by your code. (With `fetch`/Axios **cross-origin**, you must also opt in: `credentials: 'include'` / `withCredentials: true`, 13.10.)
2. **Every cookie travels on every matching request**, including images and CSS. Keep them small and few.
3. **A cookie is user input.** The user, or malware, can read and edit it in DevTools. Never trust a cookie value without validating it, and never store secrets in a cookie JavaScript can read.

## 3. Who can create a cookie

| Who | How | Can set `HttpOnly`? |
|---|---|---|
| the **server** | a `Set-Cookie` response header | ✅ |
| **JavaScript** | `document.cookie = '…'` (or js-cookie) | ❌ never |

## 4. Where to see them

- **DevTools → Application → Cookies → http://localhost:5173** lists name, value, domain, path, expiry, size, and the HttpOnly/Secure/SameSite columns.
- **DevTools → Network → a request → Headers**: `Cookie` (sent) and `Set-Cookie` (received).
- Why does a Vite page on `:5173` see cookies set by the mock API on `:3001`? The dev **proxy** (13.10) makes `/api` same-origin, so the browser sees `localhost:5173` as the setter. Cookies are scoped by **host**, not by port.

## 5. Cookies vs other browser storage

| | Cookie | `localStorage` | `sessionStorage` |
|---|---|---|---|
| Sent to the server automatically | ✅ | ❌ | ❌ |
| JavaScript can read it | unless `HttpOnly` | ✅ always | ✅ always |
| Size | ~4 KB each | ~5 MB | ~5 MB |
| Lifetime | `Expires`/`Max-Age`, or the browser session | until cleared | until the tab closes |
| Good for | sessions, CSRF tokens, prefs the **server** needs | client-only prefs, drafts | per-tab state |

## ✅ Recap

- Server says `Set-Cookie`, browser stores it, browser sends `Cookie`, **automatically**.
- Cookies are small, travel with every request, and are user-editable input.
- Only the server can make a cookie `HttpOnly`.
