# Lecture 24.99 · ✅ Knowledge Check: Cookies, Sessions and CSRF

> **Section:** S24 · **Type:** ✅ Knowledge Check · **Track:** ★ Core · **Time:** ~25 minutes

---

**1.** Who attaches the session cookie to an Axios request: Axios, js-cookie, or the browser? Under what conditions?

<details><summary>Answer</summary>

**The browser.** It does so when the cookie's domain and path match the URL, it hasn't expired, `Secure` matches the scheme, and `SameSite` allows the context. For **cross-origin** requests, the code must also opt in (`withCredentials: true` in Axios, `credentials: 'include'` in fetch). Neither Axios nor js-cookie ever touches `JSESSIONID`: it's HttpOnly (24.01, 24.07).
</details>

**2.** Why does double-submit CSRF protection work if an attacker's site can make the browser **send** our cookies?

<details><summary>Answer</summary>

Sending isn't reading. The attacker's page can't **read** `XSRF-TOKEN` (the same-origin policy), so it can't put the matching value in `X-XSRF-TOKEN`. A cross-site form can't set custom headers at all, and a cross-site fetch with one needs a CORS preflight that we refuse (24.10).
</details>

**3.** The server sends:

```text
Set-Cookie: JSESSIONID=a1; Path=/; HttpOnly; SameSite=Lax
Set-Cookie: XSRF-TOKEN=b2; Path=/; SameSite=Lax
Set-Cookie: report_filter=q3; Path=/reports
```

On the page `/tasks`, what does `Cookies.get()` return? Which cookies go with `GET /api/tasks`?

<details><summary>Answer</summary>

`Cookies.get()` returns `{ 'XSRF-TOKEN': 'b2' }`. `JSESSIONID` is HttpOnly, and `report_filter` is scoped to `/reports`, so it isn't visible on `/tasks`. Sent to `/api/tasks`: `JSESSIONID=a1; XSRF-TOKEN=b2`. `report_filter` isn't sent, because the path doesn't match (24.02, 24.18).
</details>

**4.** The CSRF header is missing on DELETE only. The interceptor has `if (['post', 'put', 'patch'].includes(config.method)) …`. What's wrong, and how would you make this class of bug impossible?

<details><summary>Answer</summary>

`'delete'` is missing from the list. Keep **one** named constant (`UNSAFE_METHODS`) and test **every** method, like `cookies.test.ts` does. Alternatively, invert the rule: add the header to everything **except** GET, HEAD and OPTIONS (24.11).
</details>

**5.** Which may be JavaScript-readable: session id, CSRF token, theme, language, user role? Justify each.

<details><summary>Answer</summary>

- **Session id:** never, because it *is* the credential.
- **CSRF token:** must be readable, because JavaScript copies it into the header. It's useless without the session and our origin.
- **Theme and language:** fine, they're not secret.
- **User role:** readable doesn't matter, because it's **editable** too. Never decide anything from a client-side role. Get it from `/auth/me` for display only, and let the server authorise every request (24.08 §5).
</details>

**6.** Implement `returnTo` validation that rejects `//evil.com`, `https://…` and `/\evil.com`.

<details><summary>Answer</summary>

```ts
export function safeReturnTo(value: string | null, fallback = '/tasks'): string {
  if (value === null || !value.startsWith('/')) return fallback;
  if (value.startsWith('//') || value.startsWith('/\\')) return fallback;
  return value;
}
```

A stronger version parses with `new URL(value, location.origin)`, requires the same origin, and returns `pathname + search` (24.14).
</details>

**7.** After a reload, a logged-in user is briefly sent to `/login` and then back. What's missing?

<details><summary>Answer</summary>

The guard redirects while `getMe` is still **loading**, treating "unknown" as "anonymous". `RequireAuth` must render a "Checking your session…" state while `isChecking` is true (24.12).
</details>

**8.** Five requests fail with 401 at the same moment. How does TaskFlow avoid five logouts and five toasts?

<details><summary>Answer</summary>

Each dispatches `sessionExpired`, but the listener acts only while `getMe` still holds a user. The first one clears everything and sets `me = null`, and the rest return immediately. The test asserts one toast for two 401s (24.13).
</details>
