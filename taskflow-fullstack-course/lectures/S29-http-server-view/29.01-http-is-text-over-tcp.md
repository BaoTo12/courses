# Lecture 29.01 · HTTP Is Text over TCP

> **Section:** S29 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes
> Captured for this lecture: `curl -v http://localhost:3001/api/auth/me` against the course's mock API (output below is real, trimmed).

## 1. Why a whole section on HTTP now

In Part 1 you *used* HTTP through Axios: `api.get('/tasks')` returned objects. From now on you're on the **other side**: a servlet receives an `HttpServletRequest` and must produce an `HttpServletResponse`. Every method on those two objects (`getParameter`, `getHeader`, `setStatus`, `sendRedirect`…) is a view onto the text you'll see here. If you can read raw HTTP, the Servlet API becomes obvious.

## 2. A real exchange

```text
> GET /api/auth/me HTTP/1.1                ← request line: METHOD  PATH(+query)  VERSION
> Host: localhost:3001                     ← headers: "Name: value", one per line
> User-Agent: curl/8.18.0
> Accept: */*
>                                          ← an EMPTY line: "headers are over" (no body for this GET)

< HTTP/1.1 401 Unauthorized                ← status line: VERSION  CODE  REASON
< X-Powered-By: Express
< Cache-Control: no-cache
< Content-Type: application/json; charset=utf-8
< Content-Length: 148                      ← how many bytes of body follow
< Date: Sat, 26 Sep 2026 09:23:27 GMT
< Connection: keep-alive
<                                          ← empty line
{"status":401,"error":"UNAUTHENTICATED",…} ← body: exactly 148 bytes
```

(`>` = sent by curl, `<` = received. The prefixes are curl's decoration, not part of HTTP.)

## 3. The grammar

```text
REQUEST                                   RESPONSE
method SP target SP HTTP/1.1 CRLF         HTTP/1.1 SP status SP reason CRLF
(header-name ":" value CRLF)*             (header-name ":" value CRLF)*
CRLF                                      CRLF
[body]                                    [body]
```

- Lines end with **CRLF** (`\r\n`). The blank line (CRLF CRLF) separates headers from the body.
- Header names are **case-insensitive** (`content-type` = `Content-Type`). Values are text.
- The body's length is given by `Content-Length`, or by `Transfer-Encoding: chunked` (pieces with sizes, used when the server streams).
- **`Host` is mandatory** in HTTP/1.1: one IP can serve many sites, and Tomcat's `<Host>` (28.03) is chosen from it.

## 4. Underneath: a TCP connection

```text
browser ──TCP connect to 127.0.0.1:8080──► Tomcat's Connector (server.xml)
        ──bytes: "GET /taskflow/ HTTP/1.1\r\nHost: …\r\n\r\n"──►
        ◄──bytes: "HTTP/1.1 200 \r\nContent-Type: text/html…\r\n\r\n<!doctype html>…"──
        (keep-alive: the same connection serves the next request)
```

Tomcat's connector reads the bytes, parses them into an `HttpServletRequest`, calls your servlet, and serialises your `HttpServletResponse` back into bytes (S30).

## 5. HTTP/2 and HTTP/3?

On the wire they're binary, multiplexed and compressed, but the **semantics are the same**: methods, paths, headers, status codes, bodies. DevTools and the Servlet API show you the same model. Tomcat 9 speaks HTTP/1.1, plus HTTP/2 over TLS if configured. We use HTTP/1.1, where you can read the bytes.

## ✅ Recap

A request is a request line, headers, a blank line, then a body. A response is a status line, headers, a blank line, then a body. Everything the Servlet API offers is a parsed view of these lines.
