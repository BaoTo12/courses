## 1. `Content-Type` and `charset`: why Vietnamese breaks

```http
Content-Type: text/html;charset=UTF-8
```

Without a charset, the browser guesses. "Công việc" can turn into "CÃ´ng viá»‡c" (UTF-8 bytes read as ISO-8859-1). The fixes arrive in S30–S32: `response.setContentType("text/html;charset=UTF-8")`, `<%@ page pageEncoding="UTF-8" %>`, and for **request** bodies, `request.setCharacterEncoding("UTF-8")` **before** the first `getParameter` (an encoding filter, S39).

## 2. `Content-Length` vs chunked

For a known-size body, the server sends `Content-Length`. When it streams (a big JSP page flushed in parts), it sends `Transfer-Encoding: chunked`. The Servlet container decides for you: if your output fits the response buffer (8 KB by default), you get a `Content-Length`.

## 3. Response headers must come before the body

Headers are sent before the body. Once the response is **committed** (the buffer flushed), `setHeader`, `sendRedirect` and `setStatus` can no longer change anything, and you get `IllegalStateException: Cannot call sendRedirect() after the response has been committed` (S31). That one is a rite of passage.

## 4. Security headers (preview)

`Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Strict-Transport-Security`: all set by a filter in S40 (26.11 previewed them).

## ✅ Recap

`Content-Type` with its charset, `Location` for redirects and creates, `Set-Cookie`/`Cookie` for state, `Cache-Control` for privacy. Request headers are client input: read them, never trust them.
