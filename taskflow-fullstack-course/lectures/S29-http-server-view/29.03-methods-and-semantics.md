# Lecture 29.03 · Methods and Semantics: Safe, Idempotent; GET Must Not Change State

> **Section:** S29 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes
> 🔗 Reference: RFC 9110 §9 (Methods)

---

## 1. The methods and their promises

| Method | Meaning | Body | **Safe** (no state change) | **Idempotent** (N times = once) | Cacheable |
|---|---|---|---|---|---|
| `GET` | read a resource | no | ✅ | ✅ | ✅ |
| `HEAD` | GET without the body | no | ✅ | ✅ | ✅ |
| `OPTIONS` | what's allowed (CORS preflight, S47) | no | ✅ | ✅ | ❌ |
| `POST` | create / process ("do this") | yes | ❌ | ❌ | rarely |
| `PUT` | replace the resource at this URL | yes | ❌ | ✅ | ❌ |
| `PATCH` | change part of it | yes | ❌ | not guaranteed | ❌ |
| `DELETE` | remove it | usually no | ❌ | ✅ | ❌ |

- **Safe:** the client asks for nothing to change. Browsers, crawlers, prefetchers and link-preview bots all feel free to send GETs.
- **Idempotent:** repeating the request leaves the same final state. `DELETE /tasks/5` twice: gone after the first, and still gone after the second (the response may differ, 204 then 404, but the state doesn't). `POST /tasks` twice creates **two** tasks.
- Why it matters: after a network timeout, a client may **retry** an idempotent request safely, but not a POST.

## 2. GET must not change state

```html
<a href="/taskflow/tasks/delete?id=5">Delete</a>          <!-- ❌ -->
```

What goes wrong:

1. **Prefetch and crawlers**: a browser's link prefetch, a search engine, an antivirus link scanner, or a chat app's link preview "clicks" every link, and the tasks disappear.
2. **CSRF, made trivial**: `<img src="https://taskflow.example/tasks/delete?id=5">` on any web page deletes it with the victim's cookies. `SameSite=Lax` even **allows** cookies on top-level GET navigations (24.02).
3. **Caching and history**: a proxy or the browser cache may serve or replay it, and it lands in logs, history and Referer headers.
4. **Back/Reload** re-send it without any warning.

The fix: `POST /tasks/delete` from a form with a CSRF token (S37), or `DELETE /api/tasks/5` from JavaScript (Part 3).

## 3. In the Servlet API

`HttpServlet.service()` reads the method and calls `doGet`, `doPost`, `doPut`, `doDelete`, `doHead`, `doOptions`… (S30). A method you don't override answers **405 Method Not Allowed**. That's the default "deny" for methods you didn't design for.

HTML forms can only send GET and POST, so TaskFlow Admin (JSP) uses POST for every change. The JSON API (Part 3) uses the full set.

## ✅ Recap

GET/HEAD/OPTIONS are safe. PUT/DELETE are idempotent but not safe. POST is neither. Never change state on GET.
