# Lecture 01.04 · package.json, node_modules, Lockfiles and Semver

> **Section:** S01 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> 🛡 Includes: why the lockfile is a security control

---

## 1. The problem

You and a teammate both run `npm install` on the same project a week apart. Can you end up with **different code** in `node_modules`? Yes, easily. That's how you get "works on my machine" bugs, and how a compromised package version can slip into a build unnoticed.

This lecture explains the three pieces that control this: `package.json`, **semver ranges**, and `package-lock.json`.

---

## 2. `package.json`: what you *want*

Let's create the root `package.json` now (we'll add Sass in S02):

```bash
cd /c/dev/taskflow
```

```bash
npm init -y
```

Then edit it to:

```json
{
  "name": "taskflow",
  "private": true,
  "version": "0.1.0",
  "description": "TaskFlow monorepo root: shared scripts",
  "scripts": {},
  "engines": {
    "node": ">=22"
  }
}
```

- `"private": true` prevents accidentally publishing to the npm registry.
- `"engines"` documents the Node version the project expects (and warns if someone uses an old one).

The important fields:

| Field | Meaning |
|---|---|
| `dependencies` / `devDependencies` | Packages you want, with **version ranges** |
| `scripts` | Named commands: `npm run <name>` |
| `type` | `"module"` → `.js` files use ES modules (you'll see this in Vite projects) |

---

## 3. Semver: `MAJOR.MINOR.PATCH`

Most packages follow **semantic versioning**:

```text
  1 . 7 . 2
  │   │   └─ PATCH: bug fixes, no API changes
  │   └───── MINOR: new features, backwards compatible
  └───────── MAJOR: breaking changes
```

Version **ranges** in `package.json`:

| Range | Means | Example: `x` allows |
|---|---|---|
| `1.7.2` | Exactly this | `1.7.2` only |
| `~1.7.2` | Patch updates | `1.7.2` … `1.7.x` (< 1.8.0) |
| `^1.7.2` | Minor + patch updates (**npm's default**) | `1.7.2` … `1.x.x` (< 2.0.0) |
| `^0.17.4` | Special: for `0.x`, caret only allows patch updates | `0.17.4` … `0.17.x` |
| `*` / `latest` | Anything | Don't. |

So `"axios": "^1.7.2"` means "any 1.x version from 1.7.2 up". Two `npm install`s a month apart could pick `1.7.2` and `1.9.0`.

> ⚠️ **Why the `0.x` rule matters to us:** we'll pin `json-server@0.17` because v1 (a beta rewrite) changed behaviour. With `^0.17.4`, npm won't jump to `1.0.0`, which is exactly what we want.

## 4. `package-lock.json`: what you *got*

When you run `npm install`, npm resolves every range in the whole dependency **tree** to exact versions and writes them to `package-lock.json`, including each package's **download URL** and **integrity hash**:

```json
"node_modules/axios": {
  "version": "1.7.9",
  "resolved": "https://registry.npmjs.org/axios/-/axios-1.7.9.tgz",
  "integrity": "sha512-…(a long base64 hash)…"
}
```

(Illustrative entry. Open your own `package-lock.json` after S02 to see real ones.)

**Commit the lockfile.** With it:
- Everyone (and CI) installs **the same exact versions**.
- npm verifies each downloaded package against its **integrity hash**. If the file on the registry (or a mirror/proxy) differs from what was locked, installation fails.

---

## 5. `npm install` vs `npm ci`

| | `npm install` | `npm ci` |
|---|---|---|
| Reads | `package.json` (+ lockfile as a guide) | **Lockfile only** (must match `package.json`) |
| May update the lockfile? | **Yes**, if ranges allow or you add packages | **Never.** It fails if the lockfile and `package.json` disagree. |
| `node_modules` | Updates in place | Deletes and reinstalls from scratch |
| Use it | While developing: adding/updating packages | CI, fresh clones, "make it exactly like the lockfile" |

---

## 6. 🛡 Why the lockfile is a security control

Supply-chain attacks against npm are real. A common scenario: an attacker compromises a maintainer's account and publishes a malicious **patch** version (`1.7.10`) of a popular package. Anyone installing with a range like `^1.7.2` **without** a lockfile, or running `npm update`, can pull it in automatically.

The lockfile helps because:
1. Builds use **exactly** the reviewed versions, not "whatever is newest".
2. The **integrity hash** detects tampering in transit or at mirrors.
3. Version changes show up as a **diff in code review** (`package-lock.json` changed), which is a chance to ask "why did this change?"

It doesn't protect you from a version that was *already* malicious when you locked it. For that you also use `npm audit`, careful upgrades, and minimal dependencies (S26, S50).

## 7. Useful commands

```bash
npm install axios            # add a dependency (writes to package.json + lockfile)
npm install -D sass          # add a devDependency
npm uninstall axios          # remove
npm outdated                 # what newer versions exist
npm ls axios                 # where is axios in the tree, which version
npm ci                       # clean, exact install from the lockfile
npm audit                    # known vulnerabilities in the tree
```

---

## 8. Summary

- `package.json` = **what you want** (ranges). `package-lock.json` = **what you got** (exact versions + hashes). **Commit both.**
- `^` = minor+patch updates; `~` = patch updates; `0.x` carets are stricter.
- `npm ci` for reproducible installs; `npm install` when changing dependencies.
- The lockfile is a **security control**: exact versions, integrity checks, reviewable diffs.

## 9. Check yourself

1. `"axios": "^1.7.2"` and there's no lockfile. The registry has `1.7.2`, `1.8.0`, `2.0.0`. Which does `npm install` pick?
2. Same, but a lockfile pins `1.7.2`. Which does `npm ci` pick? And `npm install`?
3. What does the `integrity` field protect against?

<details>
<summary>Answers</summary>

1. **`1.8.0`**: the highest version satisfying `>=1.7.2 <2.0.0`.
2. `npm ci` → **`1.7.2`** (exactly the lockfile). `npm install` → also **`1.7.2`** (it respects a lockfile that satisfies `package.json`); it only changes versions when you ask (e.g. `npm install axios@latest`, `npm update`) or when `package.json` no longer matches.
3. The downloaded package contents being **different** from what was locked, whether through tampering, corruption, or a compromised mirror.

</details>
