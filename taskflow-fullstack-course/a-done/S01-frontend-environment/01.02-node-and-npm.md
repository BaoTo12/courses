# Lecture 01.02 · What Node and npm Actually Do for a Frontend Project

> **Section:** S01 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes

---

## 1. The confusion this lecture removes

Beginners often think: "React needs Node, so my React app runs on Node." That's wrong, and the wrong model causes real mistakes later, such as trying to read files from disk in a React component, or putting secrets in frontend environment variables.

The correct model:

> 🧠 **Node runs your tools. The browser runs your app.**

---

## 2. What Node.js is

**Node.js** is a program that runs JavaScript *outside* a browser. It takes the V8 JavaScript engine (the same one inside Chrome) and adds APIs a browser doesn't have: reading/writing files, opening network ports, starting processes.

That makes it perfect for **developer tools written in JavaScript**:

| Tool | What it does with Node's powers |
|---|---|
| **Sass** (dart-sass, distributed as JS) | Reads `.scss` files from disk, writes `.css` files |
| **TypeScript** (`tsc`) | Reads `.ts` files, type-checks, writes `.js` |
| **Vite** | Starts a dev server on port 5173, watches files, bundles for production |
| **Vitest** | Runs your tests |
| **ESLint / Prettier** | Read and rewrite source files |
| **json-server** | Starts an HTTP server serving `db.json` as a REST API (our mock backend) |

None of these ship to the user. They run on **your machine** (and on CI servers) and **produce files** that the browser will run.

---

## 3. What runs where

```text
YOUR MACHINE (Node)                                   USER'S BROWSER
─────────────────────────────────────────            ────────────────────────────
src/App.tsx ─┐                                        index.html
src/*.scss ──┼──▶ Vite (Node) ──▶ dist/index.html ──▶ assets/app-3f9a.js   ← runs here
node_modules/┘                     dist/assets/*.js    assets/app-7c1b.css
                                   dist/assets/*.css
```

During development, Vite's dev server (a Node process) serves files to your browser on `http://localhost:5173` and transforms TS/JSX/SCSS on the fly. It's still Node serving *files*; your React code executes in the browser tab.

In production there's no Vite and no Node needed for the frontend at all. The built `dist/` folder is just static files. In S49 you'll put them inside the Tomcat WAR, served by Java, with Node nowhere in sight.

### Consequences

| You might try… | Why it fails / is wrong |
|---|---|
| `import fs from 'fs'` in a React component | `fs` is a Node API; the browser has no file system access. |
| Putting an API secret in `import.meta.env.VITE_SECRET` | Vite **inlines** it into the JS bundle; anyone can read it in DevTools (Lecture 13.11). |
| "The frontend server" for security checks | There is no frontend server in production, only static files. Security checks go in the backend. |

## 4. What npm is

**npm** has three jobs:

1. **Registry client**: downloads packages from the npm registry (registry.npmjs.org) into `node_modules/`.
2. **Dependency manager**: records what your project needs in `package.json` and the *exact resolved versions* in `package-lock.json` (Lecture 01.04).
3. **Script runner**: `npm run dev` runs the command listed under `"scripts": { "dev": "vite" }` in `package.json`, with `node_modules/.bin` on the PATH (that's how the `vite` command is found without a global install).

### Dependencies vs devDependencies

```json
{
  "dependencies":    { "react": "^19.0.0", "axios": "^1.7.0" },
  "devDependencies": { "vite": "^8.3.0", "typescript": "^5.9.0", "sass": "^1.105.0" }
}
```

- **dependencies**: code that ends up **in the bundle** (runs in the browser): React, Redux, Axios, js-cookie, i18next.
- **devDependencies**: **tools** used only during development/build: Vite, TypeScript, Sass, Vitest, ESLint.

For a bundled frontend app the distinction is mostly organisational, because the bundler includes whatever you import. For a published library or a Node server it matters more. Keep it tidy anyway; it documents intent.

### `npx`

`npx <tool>` runs a package's command without adding it to your scripts, downloading it temporarily if needed. You'll use it for one-off commands like `npx sass --version`.

> 🛡 **Security note:** `npx some-package` and `npm install` can execute code from the internet (install scripts). Type package names carefully. Typosquatting (e.g. `raect` instead of `react`) is a real supply-chain attack (S26).

## 5. `node_modules`: why it's huge and why it's not committed

A fresh Vite + React project pulls in hundreds of packages, because each tool depends on others (a dependency *tree*). That folder:
- is **regenerated** from `package.json` + `package-lock.json` with `npm install` / `npm ci`,
- is platform-specific in places (some tools ship native binaries per OS),
- is therefore **never committed** to git (`.gitignore` excludes it).

---

## 6. Summary

- **Node runs your tools** (Sass, Vite, TypeScript, tests, mock server). **The browser runs your app.**
- In production the frontend is **static files**, and Node isn't involved.
- **npm** installs packages, records versions, and runs scripts.
- `dependencies` = ships in the bundle; `devDependencies` = build tools.
- Never commit `node_modules`; never put secrets in frontend env vars.

---

## 7. Check yourself

1. Does `axios` in TaskFlow Web run in Node or in the browser? What about `vite`?
2. Why can't a React component read `C:\data\tasks.json` with `fs`?
3. How does `npm run dev` find the `vite` command if Vite isn't installed globally?

<details>
<summary>Answers</summary>

1. `axios` runs in the **browser** (it's bundled into your app). `vite` runs in **Node** on your machine; it's a build/dev tool.
2. The component runs in the browser, which has no Node `fs` API and (for security) no general access to the user's file system.
3. npm adds `node_modules/.bin` to the PATH while running scripts; Vite's executable is installed there.

</details>
