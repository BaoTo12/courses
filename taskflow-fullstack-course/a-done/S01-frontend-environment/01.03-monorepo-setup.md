## 1. What we're building

```text
C:\dev\taskflow\
├── .editorconfig
├── .gitattributes
├── .gitignore
├── .prettierrc.json
├── package.json           ← root: shared scripts (Sass in S02); created in S02
├── README.md
├── styles/                ← shared SCSS design system (S02)
├── frontend/              ← TaskFlow Web (S07)
├── mock-api/              ← json-server mock (S13)
├── backend/               ← Java WAR (S28)
├── db/                    ← SQL (S28)
└── docs/
    ├── architecture.md
    ├── notes/
    └── security/
        └── threat-notes.md
```

It's a **monorepo**: one git repository holding several related projects. Why one repo?
- The frontend, backend and shared styles evolve together: a feature often touches all three.
- Checkpoint tags capture the whole system at a known-good point.
- In S49 the backend build will include the frontend build; having both in one repo makes that simple.

(Large companies use both monorepos and multi-repo setups; each has trade-offs around tooling, access control and release independence. For a course project, one repo is clearly simpler.)

## 2. Step by step

### Step 1: create the folders

In a terminal (Git Bash shown; PowerShell equivalents in comments):

```bash
mkdir -p /c/dev/taskflow
```

```bash
cd /c/dev/taskflow
```

```bash
mkdir -p styles frontend mock-api backend db docs/notes docs/security
```

> PowerShell: `New-Item -ItemType Directory -Force C:\dev\taskflow\docs\notes, C:\dev\taskflow\docs\security` etc.

Empty folders aren't tracked by git. Add a placeholder so the structure is visible:

```bash
touch styles/.gitkeep frontend/.gitkeep mock-api/.gitkeep backend/.gitkeep db/.gitkeep docs/notes/.gitkeep
```

### Step 2: `.gitignore` 📦 Provided

```gitignore
# Dependencies
node_modules/

# Builds
dist/
build/
target/
*.war
*.class

# Compiled CSS for JSP (generated from styles/ in S28)
backend/src/main/webapp/static/css/

# Logs
*.log
npm-debug.log*
logs/

# Env files (never commit secrets)
.env
.env.*
!.env.example

# IDE / OS
.idea/
*.iml
.vscode/*
!.vscode/extensions.json
!.vscode/settings.json
.DS_Store
Thumbs.db

# Tomcat work dir if run locally in repo
work/
```

Why ignore `.env`? It's where local secrets (like a DB password) might go. `.env.example` (committed) documents *which* variables exist without real values.

### Step 3: `.editorconfig` 📦 Provided

```ini
root = true

[*]
charset = utf-8
end_of_line = lf
indent_style = space
indent_size = 2
insert_final_newline = true
trim_trailing_whitespace = true

[*.java]
indent_size = 4

[*.md]
trim_trailing_whitespace = false
```

`charset = utf-8` matters more than it looks: in Part 2 you'll debug Vietnamese characters turning into `?`. Encoding problems start with files saved in the wrong encoding.

### Step 4: `.gitattributes` 📦 Provided

```gitattributes
* text=auto eol=lf
*.bat text eol=crlf
*.png binary
*.jpg binary
*.ico binary
*.jar binary
```

This makes line endings consistent in the repo regardless of OS, so diffs don't show every line changed.

### Step 5: `.prettierrc.json` 📦 Provided

```json
{
  "singleQuote": true,
  "semi": true,
  "trailingComma": "all",
  "printWidth": 100
}
```

### Step 6: `README.md` ✍️ You write

Write a short README in your own words: what TaskFlow is, the folder layout, and "how to run" (empty for now; you'll fill it in as you go). Writing it yourself forces you to articulate the architecture.

### Step 7: move your S00 documents in

Copy your `architecture.md` into `docs/` and `threat-notes.md` into `docs/security/`.

### Step 8: initialise git, commit, tag

```bash
git init
```

```bash
git add .
```

```bash
git commit -m "chore: repository skeleton, editor config, S00 docs"
```

Now tag the checkpoints. S00 produced documents only, so both tags point to this commit:

```bash
git tag s00-end
```

```bash
git tag s01-end
```

(You'll move `s01-end` if you add more in this section. See "moving a tag" in Lecture 01.05.)

Check:

```bash
git log --oneline --decorate
```

You should see something like:

```text
a1b2c3d (HEAD -> main, tag: s01-end, tag: s00-end) chore: repository skeleton, editor config, S00 docs
```

### Step 9 (optional): push to a private remote

If you want a backup, create a **private** repository on GitHub/GitLab and push:

```bash
git remote add origin <your-private-repo-url>
```

```bash
git push -u origin main --tags
```

`--tags` is needed; tags aren't pushed by default.

## 3. Commit message convention

We'll use a light **Conventional Commits** style, as many companies do:

| Prefix | Use for |
|---|---|
| `feat:` | A new feature (`feat(tasks): add task list page`) |
| `fix:` | A bug fix |
| `refactor:` | Code change with no behaviour change (e.g. Redux → RTK) |
| `style:` | Formatting / SCSS-only visual changes |
| `test:` | Tests |
| `docs:` | Documentation, notes |
| `chore:` | Tooling, configs |
| `security:` | 🛡 fixes from labs (our own addition; makes the security history easy to find) |
