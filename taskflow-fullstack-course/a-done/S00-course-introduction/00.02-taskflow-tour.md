# Lecture 00.02 · TaskFlow Tour: Two Clients, One Backend

> **Section:** S00 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes

## 1. Why this lecture matters

Before writing code, you need a clear picture of the finished system. Otherwise every lecture feels like a disconnected tutorial. This lecture walks through TaskFlow as if you'd just joined the team building it: what the product does, who uses which part, and why the architecture looks the way it does.

---

## 2. The product

TaskFlow is a task-management platform. Users create tasks, organise them by category, set status/priority/due dates, comment on them, and see a dashboard. Administrators manage users, categories and audit logs.

### The data at the centre

```text
User ──owns──▶ Task ◀──belongs to── Category
  │              ▲
  └──writes──▶ Comment
```

- A **User** has a role (`USER` or `ADMIN`) and a preferred language (`en` or `vi`).
- A **Task** has a title, description, status (`TODO`, `IN_PROGRESS`, `DONE`), priority (`LOW`, `MEDIUM`, `HIGH`), an optional due date, a category, and an owner.
- A **Comment** belongs to a task and has an author.
- An **AuditEvent** records security-relevant events (logins, failures, access denials).

Every entity exists to teach something. For example, `Comment.body` is user-written text displayed to other users, which makes it the perfect target for the **stored XSS** labs. `Task.ownerId` makes the **IDOR** lab possible ("can I edit someone else's task by changing the ID?").

## 3. The two clients

### TaskFlow Web: the React SPA (Part 1)

Used by regular users to manage their own tasks.

```text
┌─────────────────────────────────────────────────────────────┐
│  TaskFlow        Tasks  Dashboard            EN|VI  ☾  An ▾ │
├─────────────────────────────────────────────────────────────┤
│ 🔍 search…   [Status ▾] [Priority ▾] [Category ▾]  + New    │
│                                                             │
│  TODO (4)           IN PROGRESS (2)       DONE (7)          │
│ ┌──────────────┐   ┌──────────────┐     ┌──────────────┐    │
│ │▌Write report │   │▌Fix login bug│     │▌Plan sprint  │    │
│ │ HIGH · Oct 3 │   │ MED  · Oct 5 │     │ LOW          │    │
│ └──────────────┘   └──────────────┘     └──────────────┘    │
└─────────────────────────────────────────────────────────────┘
```

Technologies: React, TypeScript, Redux (classic → Redux Toolkit → RTK Query), reselect, Axios, js-cookie, i18next, SCSS, styled-components.

**How it gets data:** the browser downloads the app's JavaScript **once**. After that, the JavaScript calls the backend's **JSON API** (`GET /api/tasks`, `POST /api/tasks`, …) and React draws the screen **in the browser**.

### TaskFlow Admin: the JSP portal (Part 2)

Used by administrators (and it hosts some legacy pages).

```text
┌─────────────────────────────────────────────────────────────┐
│  TaskFlow Admin   Tasks  Categories  Users  Audit    Logout │
├─────────────────────────────────────────────────────────────┤
│  Tasks  (Showing 1–20 of 134)                 [+ New task]  │
│  ┌────┬──────────────────┬───────────┬──────────┬────────┐  │
│  │ #  │ Title            │ Status    │ Owner    │        │  │
│  ├────┼──────────────────┼───────────┼──────────┼────────┤  │
│  │ 1  │ Write report     │ TODO      │ an       │ Edit   │  │
│  │ 2  │ Fix login bug    │ IN PROG.  │ binh     │ Edit   │  │
│  └────┴──────────────────┴───────────┴──────────┴────────┘  │
│  « Prev   1  2  3 … 7   Next »                              │
└─────────────────────────────────────────────────────────────┘
```

Technologies: Java Servlets, JSP, EL, JSTL, filters, listeners, sessions, on Tomcat 9, styled with the **same SCSS design system** (compiled to plain CSS).

**How it gets data:** every click that navigates is a **new HTTP request**. A Servlet loads the data, hands it to a JSP, and the JSP produces a complete **HTML page on the server**. The browser just displays it.

## 4. One backend

Both clients talk to the same Java application running in Tomcat:

```text
                        ┌──────────────── Browser ────────────────┐
                        │                                         │
        TaskFlow Admin (JSP pages)                 TaskFlow Web (React SPA)
                        │ HTML                                    │ JSON
                        ↓                                         ↓
         ┌─────────────────────────── Tomcat 9 ──────────────────────────┐
         │   Filters (encoding, logging, security headers, locale,       │
         │            CORS, authentication, CSRF, authorization)         │
         │        ├── Page Servlets → JSP + EL + JSTL → HTML              │
         │        └── API Servlets  → JSON                                │
         │                     ↓                                          │
         │        Service layer  →  DAO (JDBC)  →  MySQL 8                │
         └────────────────────────────────────────────────────────────────┘
```

Notice what's **shared**:

| Shared thing | Why it matters |
|---|---|
| **Service layer + DAOs** | Business rules ("only the owner may edit a task") live in one place, so both clients obey them. |
| **Filters** | Authentication, CSRF protection, security headers and logging apply to both. |
| **The session** | Log in once, and both clients know you (same `JSESSIONID` cookie). |
| **The `lang` cookie** | Switch to Vietnamese in React → the JSP portal is in Vietnamese too. |
| **The SCSS design system** | Both clients look like one product. |

And what's **different**: only the last step. One kind of Servlet forwards to a JSP (HTML); the other writes JSON.

## 5. Why would a real company have both?

This isn't an artificial setup to cram two technologies into one course. It's extremely common in industry:

1. **Legacy + modernisation.** Many companies have large JSP/Servlet (or JSF, Struts, Spring MVC + JSP) applications that work fine and earn money. Rewriting everything at once is risky and expensive. So new features get built in React, while the old pages keep running, sometimes for years.
2. **Different audiences, different needs.** An internal admin portal often doesn't need a rich interactive UI; server-rendered pages are simpler, faster to build, and easy to secure. The customer-facing app benefits from a SPA's interactivity.
3. **Incremental migration.** Teams often embed React widgets *inside* old JSP pages as a first step (the "strangler fig" pattern). You'll build exactly this in S49.

When you join a large company with a long-lived product, you'll very likely meet both worlds in the same codebase. Knowing both, and especially knowing **how they differ at the HTTP level**, is a real advantage.

## 6. The build order and why

```text
Part 1: TaskFlow Web against a mock API ──▶ Part 2: TaskFlow Admin + backend
          ──▶ Part 3: JSON API replaces the mock ──▶ Part 4: hybrid + review
```

During Part 1, the "backend" is **json-server**, a small tool that serves a JSON file as a REST API, plus a provided middleware that imitates login, cookies and error responses. It follows the **same API contract** as the real Java backend will (see [02-project-spec.md](../../02-project-spec.md), section 5).

That's deliberate:
- You learn React/Redux without waiting for a backend.
- You learn to program **against a contract**, not against an implementation, which is how frontend and backend teams work in practice.
- In S48 you switch to the real backend by changing the Axios configuration. If your layering is right, nothing else changes. If something breaks, the integration-debugging lab teaches you why.

## 8. Summary

- TaskFlow = **two clients** (React SPA for users, JSP portal for admins) + **one backend** (Servlets on Tomcat, MySQL).
- The React app gets **JSON** and renders in the browser; the JSP portal gets **complete HTML** rendered on the server.
- Services, filters, session, language cookie and design system are **shared**; only the last step (JSP vs JSON) differs.
- Companies really do run both, for legacy/modernisation and different audiences.
- The frontend is built first against a **mock API with the same contract**, then switched to the real backend.

## 9. Check yourself

1. Which client asks the server for a complete new HTML page when you click "Next page"?
2. Why do business rules live in the service layer rather than in the Servlets?
3. Name three things the two clients share at runtime.
4. What makes it possible to build the React app before the Java backend exists?

<details>
<summary>Answers</summary>

1. **TaskFlow Admin (JSP).** Each navigation is a new HTTP request, and the server returns a full HTML page. (TaskFlow Web would request JSON and re-render in the browser.)
2. Because **both** the page Servlets and the API Servlets call the same services. Rules written once apply to both clients. If they lived in Servlets, you'd duplicate them and eventually one copy would drift (a classic source of security holes).
3. Any three of: the session (`JSESSIONID`), the `lang` cookie, the filters (auth, CSRF, headers, logging), the service layer/DAOs/database, the SCSS design system.
4. A **mock API (json-server)** that implements the **same API contract** the real backend will implement.
