# Lecture 00.01 · Welcome: How This Course Works

> **Section:** S00 · Course Introduction and the Big Picture
> **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> **Project feature:** none (orientation)

---

## 1. Welcome

Welcome to **TaskFlow: Full-Stack Web Engineering**.

Over this course you'll build one application, **TaskFlow**, from an empty folder to a secured, two-language, two-client system:

- **TaskFlow Web**: a React + TypeScript single-page app with Redux, styled with SCSS and styled-components.
- **TaskFlow Admin**: a server-rendered Admin Portal built with Java Servlets, JSP, EL and JSTL on Tomcat 9.
- **One Java backend** serving both: HTML pages to the Admin Portal, and JSON to the React app.

You'll build it the way you'd grow a real product: small working steps, each one adding a feature, each one teaching a concept.

But the project is **not** the goal. The project is the *vehicle*. The goal is this:

> **When you look at any line of code in TaskFlow, you can explain what it does, where it runs, when it runs, why it's written that way, and what would break if it were written differently.**

Plenty of developers can write `${user.name}` in a JSP or `useSelector(selectTasks)` in React. Far fewer can explain *where* `user` comes from, *which* scopes were searched, *when* the JSP executed, or *why* the component re-rendered. That second group debugs faster, designs better, and gets trusted with harder work. This course is designed to put you in the second group.

## 2. The one idea that runs through the whole course

If you remember one sentence from this lecture, make it this one:

> **Always know *where* your code runs and *when* it runs.**

TaskFlow has code that runs in four very different places:

| Where | What runs there | When |
|---|---|---|
| **Your machine, at build time** | Sass compiler, TypeScript compiler, Vite bundler, Maven, the JSP translator | Before anything reaches a user |
| **The server (Tomcat, JVM)** | Servlets, filters, listeners, JSP (as compiled servlets), EL, JSTL, services, DAOs | When an HTTP request arrives |
| **The browser (JavaScript engine)** | React, Redux, Axios, js-cookie, i18next, styled-components | After the page and scripts have been downloaded |
| **The database (MySQL)** | SQL queries | When the DAO sends them |

Almost every confusing bug in web development comes from mixing these up:

- "Why can't my JavaScript read the session cookie?" (because the **server** marked it HttpOnly, and the **browser** enforces that)
- "Why is my `${…}` inside `<script>` not updating when I click?" (because the **server** evaluated it once, before the browser ever saw the page)
- "Why can't I change my SCSS variable from JavaScript?" (because it only exists at **build time**)
- "Why does disabling the delete button not stop users deleting?" (because the **browser** is controlled by the user, not by you)

You'll meet each of these in the course. Each time, the fix starts with the same question: *where and when does this run?*

## 3. How deep we go: the nine questions

For every important concept, whether that's a Servlet filter, `createSelector`, a JSP include or an Axios interceptor, the lectures answer nine questions:

1. **What problem does it solve?**
2. **Why does it exist?** (What did people do before it?)
3. **How does it work?** (From the user's point of view.)
4. **What happens internally?** (What the machine actually does.)
5. **How does it interact with the other technologies?**
6. **What are the alternatives?**
7. **What are the trade-offs?**
8. **When should I use it?**
9. **When should I avoid it?**

Not every lecture has nine headings. Small concepts don't need them. But the big ones (Servlet lifecycle, EL resolution, Redux data flow, memoization, CSRF…) are explained along all nine axes.

A practical tip: when you finish a concept, try to answer the nine questions **out loud, without notes**. The ones you can't answer tell you exactly what to re-read. This is also how senior engineers prepare for technical interviews: they rehearse explanations, not definitions.

## 4. Lecture types

Every section is a sequence of short lectures. Each lecture has a type, shown by an icon:

| Icon | Type | What you do |
|---|---|---|
| 📖 | **Theory** | Read and think. Concepts, mental models, diagrams, internals. Sometimes you run small experiments. |
| 🛠 | **Build** | Code along. We add a feature to TaskFlow step by step. You type the code yourself; don't copy-paste. Typing makes you read every line. |
| 🎯 | **Your Turn** | You implement something **alone**. The lecture gives the requirements, hints and acceptance criteria, **not** the solution. |
| 💡 | **Solution walkthrough** | The reference solution, explained: the reasoning, line by line, alternatives, and common wrong approaches with *why* they fail. Stored in `solutions/`. |
| 🐞 | **Debug** | You get broken code and a symptom. You investigate with a checklist *before* reading the explanation. |
| 🧩 | **Just-in-time** | Something the project needs that isn't a core topic (Git, React Router, Vite proxy…). Only as deep as needed. |
| 🔓 | **Attack lab** | You exploit a vulnerability in **your own local** TaskFlow to understand it. |
| 🛡 | **Defend** | You fix the vulnerability properly, re-run the attack, and explain why the fix works. |
| ✅ | **Knowledge check** | End of section: concept questions, code reading, debugging, design questions, and an implementation task. |

### How to use 🎯 and 💡 (important)

The value of a 🎯 exercise comes from the struggle, not from the answer. Here is the rule:

1. Attempt the exercise for real. Give it **at least 20–30 minutes** of honest effort.
2. If you're stuck, re-read the relevant 📖 lecture, check the hints, and use the debugging checklist.
3. Only then open the 💡 solution.
4. Even if your solution works, **read the 💡 walkthrough anyway**. It explains trade-offs and wrong approaches you may not have thought of.

Your solution does not have to match mine. If yours is different and you can argue why it's correct, that's a win.

### How to use 🐞

Debugging lectures have a fixed shape:

```text
Symptom      → what the user/developer sees
Checklist    → questions to investigate, in order
Your notes   → what you tried and what you observed
Explanation  → the cause, why it happened, and the fix
```

Don't jump to the explanation. The checklist habit ("Was the attribute set? Was it the same request? Did it forward or redirect?…") is the skill being trained. The specific bug is just practice material.

### How to use 🔓 attack labs safely

Attack labs run **only against your own TaskFlow on `localhost`**. The vulnerable code lives on separate git branches (`lab/sqli`, `lab/xss-stored`, …) and never gets merged into `main`. Never try these techniques against systems you don't own or aren't explicitly authorised to test. That includes your employer's systems, even "just to check".

## 6. Checkpoints

Every section ends with a **git tag**: `s00-end`, `s01-end`, … `s51-end`, and finally `v1.0`.

They help you in three ways:

- **Recovery.** If your project gets into a broken state, you can compare it with a known-good state:
  ```bash
  git diff s12-end -- frontend/src/api
  ```
- **Seeing progress.** `git log --oneline --decorate` shows your whole journey.
- **Learning by diffing.** Some of the best lessons in this course are diffs, for example classic Redux (`s19-end`) vs Redux Toolkit (`s20-end`).

You'll set this up in Lecture 01.03 and learn the Git you need in 01.05.

## 7. How each lecture file is organised

Most lectures follow this layout:

```text
# Lecture number · Title
> Section, type, track, time, project feature

1. Why this lecture matters      (the problem)
2. Concepts                      (the nine questions, as needed)
3. Build steps / experiments     (with code)
4. What happened internally      (diagrams, traces)
5. Common mistakes
6. Summary                       (the 3–5 things to remember)
7. Check yourself                (quick questions, answers at the bottom)
```

You'll also see these boxes:

> 🧠 **Mental model**: a short picture to keep in your head.

> ⚠️ **Pitfall**: a mistake that costs people hours.

> 🛡 **Security note**: a security consequence of the concept.

> 🔗 **Official reading**: the matching page in the official documentation (Redux docs, React docs, Servlet spec…). Read it *after* the lecture, as a second angle.

And two labels on code:

> **✍️ You write**: this is a learning objective. Type it yourself.

> **📦 Provided**: supporting code (configs, DAOs, CSS reset, mock API). Copy it, read the explanation, and move on. It's not what this lecture is about.

## 8. What you write vs what you're given

This course has a strict rule about your time:

> **If it's the learning objective, you write it. If it's plumbing, it's provided.**

So you **will** write the Servlets, filters, JSPs, EL, JSTL, React components, reducers, middleware, thunks, selectors, Axios interceptors, SCSS and styled components yourself, and you'll even write `createStore` and thunk middleware by hand.

You **won't** spend 30 minutes writing JDBC boilerplate when the lesson is about JSTL. When plumbing appears, the lecture says something like:

> "Here is `TaskDao`. You don't need to implement it. Read the method signatures, then focus on how the Servlet calls the service and passes the result to the JSP."

The complete list is in [02-project-spec.md](../../02-project-spec.md), section 6.

## 9. The course route

```text
Part 0   Orientation                                 S00–S01
Part 1   Frontend: TaskFlow Web (mock API)           S02–S27
         SCSS → JS/TS → React + styled-components → Redux track → cookies · i18n · security
Part 2   Backend: TaskFlow Admin                     S28–S45
         HTTP → Servlet → JSP → EL → JSTL → MVC → forms → scopes → filters → auth → errors → advanced
Part 3   JSON API, and replacing the mock            S46–S48
Part 4   Hybrid JSP + React · security review · final project   S49–S51
```

Why the frontend first, when the backend is where the data lives? Because the React app starts against a **mock API** (json-server) that follows the exact same contract as the real backend. In Part 3, you switch it to your Java backend by changing one config value. If the app still works after that switch, you'll have proof that your frontend architecture is right. That moment is one of the course's best lessons.

## 10. How to study effectively

A few habits that pay off, especially on the intensive plan:

1. **Type, don't paste.** Your fingers force your eyes to read every token.
2. **Predict before you run.** Before refreshing the browser or running a test, say out loud what you expect. When you're wrong, you've found a gap in your mental model, which is the most valuable thing a lecture can give you.
3. **Use the tools constantly.** DevTools Network tab, Redux DevTools, React DevTools, Tomcat logs, `curl -v`. Seeing the real HTTP messages and state changes beats reading about them.
4. **Write "explain it to a junior" notes.** At the end of each day, write 5–10 short explanations in `docs/notes/` in your own words (for example: "How `${user.name}` is resolved", "Why `useSelector` re-rendered"). This is the single best preparation for code reviews and interviews.
5. **Use the checkpoints.** When you're stuck for more than 30 minutes, `git diff` against the previous checkpoint.
6. **Don't skip ✅ knowledge checks.** They show whether you actually understood, not just followed along.

## 13. Check yourself

1. Name the four places where TaskFlow code runs, and one technology that runs in each.
2. A React component and a JSP page both "produce HTML". Which one produces it on the server?
3. What should you do before opening a 💡 solution?
4. What's the difference between a 🔓 lecture and a 🛡 lecture, and where are 🔓 labs allowed to run?
5. You're stuck on Section 21 and your app is broken. What's your first recovery step?

<details>
<summary>Answers</summary>

1. **Build time on your machine:** Sass, TypeScript compiler, Vite, Maven, JSP translator. **Server:** Servlets, filters, JSP/EL/JSTL, services, DAOs. **Browser:** React, Redux, Axios, js-cookie, i18next, styled-components. **Database:** SQL in MySQL.
2. The **JSP page**. It runs inside Tomcat (as a compiled servlet) when a request arrives, and the browser receives only the resulting HTML. React produces DOM in the **browser**, after its JavaScript has been downloaded.
3. Make a genuine attempt (20–30 minutes), re-read the relevant theory lecture, use the hints and the debugging checklist. Only then open the solution, and read it even if you succeeded.
4. 🔓 = you exploit a vulnerability to understand it; 🛡 = you fix it and prove the fix works. Attack labs run **only against your own local TaskFlow**.
5. Compare with the last checkpoint, e.g. `git diff s20-end`, to see what changed since the last known-good state (or check it out on a new branch to compare behaviour).

</details>
