# Lecture 11.06 · Submitting: `preventDefault`, Double Submits, and What a Form Does Without JavaScript

> **Section:** S11 · **Type:** 📖 Theory + 🛠 Build · **Track:** ★ Core · **Time:** ~30 minutes

---

## 1. What a `<form>` does on its own

Without JavaScript, submitting this form:

```html
<form action="/tasks/new" method="post">
  <input name="title" value="Write report">
  <button type="submit">Create</button>
</form>
```

makes the **browser** send an HTTP request and **navigate** to the response:

```http
POST /tasks/new HTTP/1.1
Content-Type: application/x-www-form-urlencoded

title=Write+report
```

The whole page is replaced by whatever the server returns. That's exactly how the **JSP Admin Portal** will work in Part 2 (S37), with no JavaScript required.

In a React SPA we don't want a page navigation: we want to handle the data in JavaScript and update part of the UI. So the first line of every submit handler is:

```tsx
async function handleSubmit(e: FormEvent<HTMLFormElement>) {
  e.preventDefault();   // cancel the browser's default: no request, no navigation
  // …our own handling
}
```

Why still use a `<form>` at all (instead of a `div` + button `onClick`)? Because the form element gives you **Enter-to-submit** in text fields, correct semantics for screen readers, and `type="submit"` buttons, all for free.

## 2. 🐞 The double-submit problem (found while building this course)

The 11.05 form guards against double submits with state:

```tsx
if (isSubmitting) return;   // ⚠️ naive guard
// …
setIsSubmitting(true);
```

The course's reference app was tested by clicking **Create task** twice in quick succession (two synchronous clicks, like a fast double-click or a stuck mouse button). Result: **8 cards → 10 cards**, so **two tasks were created**.

Why the guard failed:
1. Click 1: `handleSubmit` runs, sees `isSubmitting === false`, calls `setIsSubmitting(true)`, which **schedules** a re-render (08.02), and starts `onSubmit`.
2. Click 2 arrives **before React re-renders**. The button isn't disabled yet in the DOM, and the `handleSubmit` it calls is **from the same render**, whose closure still has `isSubmitting === false` (a stale closure, 08.02 §4).
3. Both submissions go through.

State is the right tool for **rendering** ("Saving…", disabled button). It's the wrong tool for a **synchronous lock**, because updates aren't visible until the next render. A **ref** is updated immediately (08.06):

```tsx
const [isSubmitting, setIsSubmitting] = useState(false); // for rendering (disabled button, label)
const submittingRef = useRef(false); // synchronous guard: state updates are not visible until the next render

async function handleSubmit(e: FormEvent<HTMLFormElement>) {
  e.preventDefault();
  if (submittingRef.current) return; // a second click in the same frame sees the ref, not stale state
  setSubmitAttempted(true);
  if (hasErrors(errors)) return;

  submittingRef.current = true;
  setIsSubmitting(true);
  try {
    await onSubmit(values);
  } finally {
    submittingRef.current = false;
    setIsSubmitting(false);
  }
}
```

Re-tested: **three** synchronous clicks → **8 → 9** cards. One task.

- **`try/finally`** resets the lock even if `onSubmit` throws, otherwise a failed save would lock the form forever.
- The disabled button is still valuable (visual feedback, and it blocks later clicks), but it's **not** the lock.

## 3. The server must be idempotent-aware too

Client guards reduce duplicates; they can't eliminate them. Network retries, two browser tabs, or a script calling the API directly all bypass the UI. The backend handles this with techniques like PRG for page forms (S37), unique constraints, and idempotency keys for APIs. Client-side protection is UX; data integrity is the server's job (the same principle as 11.08).

## 4. Summary

- A `<form>` natively POSTs and navigates; SPAs call `preventDefault()` and handle submission in JS. JSP forms (S37) keep the native behaviour.
- Use a `<form>` for Enter-to-submit and semantics.
- A **state** guard fails for clicks within the same frame (stale closure); use a **ref** as the lock and state for rendering; reset in `finally`.
- Duplicates are ultimately the server's problem.
