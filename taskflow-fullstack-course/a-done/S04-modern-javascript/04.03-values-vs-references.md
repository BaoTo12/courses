# Lecture 04.03 · Values vs References: the Most Important Idea for React and Redux

> **Section:** S04 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes
> If you only deeply learn one lecture in S04, make it this one.

---

## 1. Two kinds of values

JavaScript has:

- **Primitives:** `string`, `number`, `boolean`, `null`, `undefined`, `bigint`, `symbol`. They're **immutable** and compared **by value**.
- **Objects:** everything else, including plain objects `{}`, arrays `[]`, functions, `Date`, `Map`… They're **mutable** and compared **by reference** (identity).

```js
'abc' === 'abc'        // true: same value
5 === 5                // true

{} === {}              // false: two different objects
[1, 2] === [1, 2]      // false: two different arrays

const a = { x: 1 };
const b = a;
a === b                // true: same object (same reference)
```

## 2. The mental model: variables hold arrows

> 🧠 **A variable holding an object doesn't contain the object. It contains a *reference* (an arrow) to an object that lives somewhere in memory (the heap).**

```text
const a = { title: 'Write report' };
const b = a;

   a ──┐
       ├──▶ { title: 'Write report' }      ← ONE object in memory
   b ──┘

b.title = 'Changed';
console.log(a.title);   // 'Changed' (it's the same object!)
```

Copying a variable copies the **arrow**, not the object. That's why "I changed `b` and `a` changed too" happens.

With primitives there are no arrows to share; each variable holds its own value:

```js
let x = 'A';
let y = x;
y = 'B';
console.log(x);   // 'A'
```

## 3. Passing to functions: the same rule

JavaScript always passes **the value in the variable**. For objects, that value *is* the reference. So a function receives an arrow to **the same object** (some people call this "pass by sharing"):

```js
function rename(task) {
  task.title = 'Renamed';     // mutates the caller's object!
}

const t = { title: 'Original' };
rename(t);
console.log(t.title);         // 'Renamed'
```

But **reassigning** the parameter only moves the function's own arrow:

```js
function replace(task) {
  task = { title: 'New' };    // local arrow now points elsewhere
}
replace(t);
console.log(t.title);         // still 'Renamed'
```

## 4. `===` on objects asks "same object?", not "same contents?"

```js
const before = { title: 'A' };
const after = { ...before };       // new object, same contents
before === after                   // false: different objects
JSON.stringify(before) === JSON.stringify(after)   // true: same contents (a slow "deep" comparison)
```

Checking whether two references are the same is **O(1)**: one comparison, regardless of object size. Deep comparison has to walk every property, which is **O(size)**, and for big state trees on every render that's too slow.

## 5. Why React and Redux are built on reference equality

This is where the lecture pays off. React and Redux need to answer, *very* frequently: **"did this data change?"**

They answer with `===` (or `Object.is`), because it's instant:

| Tool | Question | How it's answered |
|---|---|---|
| React `useState` | Should I re-render after `setState(x)`? | Skips if `Object.is(x, previous)` |
| React `useEffect` deps | Should the effect re-run? | Compares each dependency with `Object.is` |
| `React.memo` | Can I skip re-rendering this component? | Shallow-compares props with `Object.is` |
| Redux `useSelector` | Should this component re-render after a dispatch? | Compares selector result with `===` |
| reselect `createSelector` | Can I return the cached result? | Compares inputs with `===` |

For this to work, there's a contract:

> **If data changed, it must be a new object. If data didn't change, it should be the same object.**

Break the first half (mutate in place) → the reference is the same → **the UI doesn't update**.
Break the second half (create new objects when nothing changed) → the reference is different → **unnecessary re-renders** (S21's performance topic).

```js
// ❌ Mutation: same reference, React sees "no change"
tasks.push(newTask);
setTasks(tasks);

// ✅ New array: different reference, React re-renders
setTasks([...tasks, newTask]);
```

That's the entire reason the next two lectures (immutable update patterns) exist, and why Redux reducers must never mutate.

## 6. Structural sharing: new objects without copying everything

"Create new objects for every change" sounds expensive. It isn't, because you only create new objects **along the path that changed**; everything else is **shared**:

```text
before:  state ─▶ { tasks: [ t1, t2, t3 ], filters: F }
after toggling t2:
         state' ─▶ { tasks: [ t1, t2', t3 ], filters: F }
                             ▲    ▲    ▲           ▲
                          same  NEW  same        same reference
```

- `state'` is new (because something inside changed).
- `tasks` array is new.
- `t2'` is new.
- `t1`, `t3`, `filters` are **the same objects** as before.

So a component displaying only `t1` can tell *instantly* (`t1 === t1`) that it doesn't need to re-render. The provided test for `toggleTask` checks exactly this: `expect(next[0]).toBe(tasks[0])`.

## 7. Summary

- Primitives: compared by value. Objects: compared by **reference**.
- Variables hold **arrows** to objects; copying a variable copies the arrow.
- Functions receive the same reference: mutation inside affects the caller.
- `===` on objects = "same object?" (O(1)).
- React/Redux detect change by reference: **changed ⇒ new object; unchanged ⇒ same object.**
- Structural sharing makes this cheap: only the changed path gets new objects.

## 8. Check yourself

```js
const a = { user: { name: 'An' } };
const b = { ...a };
b.user.name = 'Binh';
console.log(a.user.name, a === b, a.user === b.user);
```

<details>
<summary>Answer</summary>

`'Binh' false true`

`{ ...a }` creates a **new outer object** (`a !== b`) but copies the **reference** to the same inner `user` object (`a.user === b.user`). Changing `b.user.name` changes the one shared `user`. The next lecture explains this "shallow copy" behaviour and how to update nested data correctly.

</details>
