# Lecture 04.11 · Asynchronous JavaScript: Callbacks → Promises → `async`/`await`

> **Section:** S04 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~35 minutes
> Foundation for Axios (S13), thunks (S18) and RTK Query (S22).

---

## 1. The problem: waiting without freezing

JavaScript in the browser runs your code on **one main thread**, the same thread that handles clicks, typing and painting. A network request can take 300 ms, or 30 s. If JavaScript *waited* synchronously, the whole page would freeze.

So slow operations (network, timers, file reads in Node) are **asynchronous**: you start them, JavaScript continues, and **you get notified later** with the result.

## 2. Callbacks: the original approach

```js
setTimeout(() => console.log('later'), 1000);

// Node-style callbacks
readFile('db.json', (err, data) => {
  if (err) return handle(err);
  parse(data, (err, json) => {
    if (err) return handle(err);
    save(json, (err) => { … });     // "callback hell" / pyramid of doom
  });
});
```

Problems: deep nesting, error handling repeated at every level, hard to run things in parallel, easy to call a callback twice or never.

## 3. Promises: a value that arrives later

A **Promise** is an object representing the eventual result of an async operation. It's in one of three states:

```text
            ┌──────────── fulfilled (with a value)
pending ────┤
            └──────────── rejected  (with a reason, usually an Error)
```

Once settled (fulfilled or rejected) it **never changes again**.

```js
const p = fetch('/api/tasks');   // returns a Promise immediately (pending)

p.then((response) => response.json())      // runs when fulfilled; returns a NEW promise
 .then((tasks) => render(tasks))
 .catch((error) => showError(error))       // catches a rejection from ANY step above
 .finally(() => hideSpinner());            // runs either way
```

Key internals:
- `.then(fn)` returns a **new promise** resolved with `fn`'s return value. If `fn` returns a promise, the chain **waits** for it. That's what flattens callback hell into a chain.
- A thrown error inside `.then` becomes a rejection, so one `.catch` handles errors from the whole chain.
- `.then` callbacks always run **asynchronously** (as microtasks, 04.12), even if the promise is already resolved.

### Creating a promise (you'll rarely need to)

```js
const delay = (ms) => new Promise((resolve) => setTimeout(resolve, ms));
await delay(300);
```

### Running things in parallel

```js
const [tasks, categories] = await Promise.all([getTasks(), getCategories()]);
// rejects as soon as ONE rejects

const results = await Promise.allSettled([getTasks(), getCategories()]);
// never rejects; gives [{status:'fulfilled', value}, {status:'rejected', reason}]

const fastest = await Promise.race([fetchData(), timeout(5000)]);
```

## 4. `async` / `await`: promises that read like synchronous code

```js
async function loadTasks() {
  try {
    const response = await fetch('/api/tasks');
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    const tasks = await response.json();
    return tasks;                        // the async function's promise fulfils with this
  } catch (error) {
    console.error('Failed to load tasks', error);
    throw error;                         // re-throw so callers know it failed
  } finally {
    console.log('done');
  }
}
```

The rules:
- An `async` function **always returns a promise**. `return x` fulfils it with `x`; `throw e` rejects it.
- `await p` **pauses this function** (not the thread!) until `p` settles, then gives you its value or throws its reason.
- While paused, the main thread keeps handling other work: clicks, rendering, other code.
- `try/catch` works around `await` exactly like synchronous code.

> 🧠 `await` doesn't block JavaScript. It splits your function into "before" and "after" parts. The "after" part is scheduled to run when the promise settles.

### ⚠️ `fetch` doesn't reject on HTTP errors

`fetch` rejects only on **network failures** (DNS, offline, CORS blocked). A `404` or `500` response **fulfils** the promise with `response.ok === false`. You must check it yourself, as above. **Axios rejects on non-2xx by default**, one of the reasons we use it (S13).

### ⚠️ Sequential vs parallel `await`

```js
// Sequential: ~600 ms total if each takes 300 ms
const tasks = await getTasks();
const cats = await getCategories();

// Parallel: ~300 ms total
const [tasks2, cats2] = await Promise.all([getTasks(), getCategories()]);
```

Only use sequential `await` when the second call **depends on** the first.

### ⚠️ Forgetting `await`

```js
async function save() {
  const result = saveTask(task);   // forgot await: `result` is a Promise, not the saved task
  console.log(result.id);          // undefined
}
```

And an unhandled rejected promise shows up as `Uncaught (in promise)` in the console. That usually means a missing `await`/`catch`.

## 5. Where this shows up in TaskFlow

## 6. Summary

- Async operations let JavaScript start slow work without freezing the single main thread.
- Callbacks → nesting and scattered error handling.
- **Promises**: pending → fulfilled/rejected, chainable `.then`, one `.catch`, `Promise.all`/`allSettled`/`race`.
- **`async`/`await`**: sequential-looking code, `try/catch`; `await` pauses the function, not the thread.
- `fetch` doesn't reject on HTTP errors; check `response.ok`. Parallelise independent awaits.

## 7. Check yourself

1. What does `async function f() { return 5; }` return when called?
2. `fetch('/api/missing')` gets a 404. Does `await fetch(…)` throw?
3. Rewrite with `async/await` and `try/catch`:
   ```js
   getTask(1).then((t) => updateTask({ ...t, status: 'DONE' })).catch(showError);
   ```

   async function completeTask() {
     try {
       const t = await getTask(1);

     }
   }
