# Lecture 04.05 · Immutable Update Patterns: Nested Objects, Arrays, and `structuredClone`

> **Section:** S04 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes
> These patterns are exactly what you'll write in hand-made Redux reducers (S15), and what Immer automates (S20).

---

## 1. The rule

> **To change something, create new objects along the path from the root to the change. Reuse everything else.**

"Mutating methods" to avoid on shared data: `push`, `pop`, `shift`, `unshift`, `splice`, `sort`, `reverse`, `fill`, `copyWithin`, and direct assignment `obj.x = …` / `arr[i] = …`.

Non-mutating alternatives: spread, `map`, `filter`, `slice`, `concat`, `toSorted`, `toReversed`, `toSpliced`, `with` (the last four are newer, ES2023, and supported in all modern browsers and Node 20+).

## 2. Arrays

```js
// ADD
const added = [...tasks, newTask];                    // at end
const prepended = [newTask, ...tasks];                // at start
const inserted = tasks.toSpliced(2, 0, newTask);      // at index 2

// REMOVE
const removed = tasks.filter((t) => t.id !== id);
const withoutIndex = tasks.toSpliced(index, 1);

// UPDATE ONE ITEM (by id): the pattern you'll write 100 times
const updated = tasks.map((t) => (t.id === id ? { ...t, status: 'DONE' } : t));

// REPLACE BY INDEX
const replaced = tasks.with(index, newTask);

// SORT / REVERSE WITHOUT MUTATING
const sorted = tasks.toSorted((a, b) => a.title.localeCompare(b.title));
const sortedOld = [...tasks].sort(compare);           // pre-ES2023 equivalent: copy, then sort
```

Look closely at the **update** pattern: `map` returns a new array; for the matching item we return a **new object** (`{ ...t, status }`); for all others we return **the same object** `t`. That's structural sharing (04.03) in one line.

## 3. Objects

```js
// set / override a property
const next = { ...task, status: 'DONE' };

// remove a property
const { dueDate, ...withoutDue } = task;

// conditional property
const payload = { ...task, ...(includeOwner && { ownerId }) };
```

## 4. Nested updates: copy every level on the path

State shape (preview of Redux state):

```js
const state = {
  tasks: {
    byId: {
      1: { id: 1, title: 'A', status: 'TODO', tags: ['x'] },
      2: { id: 2, title: 'B', status: 'DONE', tags: [] },
    },
    allIds: [1, 2],
  },
  filters: { status: null },
};
```

Goal: set task 1's status to `'DONE'`.

```js
const next = {
  ...state,                          // new root
  tasks: {
    ...state.tasks,                  // new tasks slice
    byId: {
      ...state.tasks.byId,           // new byId map
      1: {
        ...state.tasks.byId[1],      // new task 1
        status: 'DONE',
      },
    },
  },
};
```

What's shared and what's new:

```text
next            NEW
next.tasks      NEW
next.tasks.byId NEW
next.tasks.byId[1]      NEW
next.tasks.byId[2]      same as before ✅
next.tasks.allIds       same as before ✅
next.filters            same as before ✅
next.tasks.byId[1].tags same array as before ✅ (we didn't change it)
```

Adding a tag to task 1 needs one more level:

```js
1: { ...state.tasks.byId[1], tags: [...state.tasks.byId[1].tags, 'urgent'] }
```

Yes, this nesting is verbose. That verbosity is **why Immer exists** (S20). With Immer you write `draft.tasks.byId[1].status = 'DONE'` and it produces exactly the object above. But you need to understand the manual version to understand what Immer does and to debug it.

## 5. Deep copies: `structuredClone`, and why it's not the default answer

```js
const deep = structuredClone(state);   // copies EVERY level (built into browsers and Node 17+)
```

Tempting, but:

1. **It breaks structural sharing.** Every object gets a new reference, so every memoised component and selector thinks *everything* changed → mass re-renders.
2. **It's slower** for large state (copies everything, not just the changed path).
3. It can't copy functions, DOM nodes or class prototypes (instances become plain objects).

`JSON.parse(JSON.stringify(x))` is the old hack. It's worse: it loses `undefined`, `Date` (becomes a string), `Map`, `Set`, `NaN`…

**When deep cloning is appropriate:** creating an independent working copy (e.g. a form draft initialised from server data, a snapshot for undo), or defensive copying at a trust boundary. **Not** for state updates.

## 6. Arrays in state: "copy before sort" trap

```js
// ❌ sorts the ORIGINAL array in place, then returns it
const sorted = state.tasks.sort(byTitle);

// ✅
const sorted = state.tasks.toSorted(byTitle);
```

`sort` returns the same array it sorted, so the result *looks* fine, while it has silently reordered your state. S15 has a debug lecture on precisely this.

## 7. Summary

- Change = new objects **along the path**; reuse everything else (structural sharing).
- Array: `[...a, x]`, `filter`, `map` with `{...t, …}`, `toSorted`, `toSpliced`, `with`.
- Object: `{ ...o, k: v }`, rest to remove, computed keys `[k]: v`.
- Nested: spread every level down to the change. Immer automates this later.
- `structuredClone` makes deep copies, which is useful for drafts but **wrong for state updates**.

## 8. Check yourself

Write immutable versions:
1. Mark all tasks as `DONE`.
2. Remove task with `id: 2` from `state.tasks.byId` **and** `state.tasks.allIds` (normalised shape above).
3. Find the mutation: `return { ...state, items: state.items.sort(bySortKey) }`.

<details>
<summary>Answers</summary>

1. `tasks.map((t) => (t.status === 'DONE' ? t : { ...t, status: 'DONE' }))`. Returning `t` unchanged when already done preserves references.
2.
   ```js
   const { [2]: removed, ...restById } = state.tasks.byId;
   const next = {
     ...state,
     tasks: { ...state.tasks, byId: restById, allIds: state.tasks.allIds.filter((id) => id !== 2) },
   };
   ```
3. `state.items.sort(…)` sorts **the existing array in place**. The outer object is new, but the old state's `items` array was reordered. Use `state.items.toSorted(bySortKey)`.

</details>
