# Lecture 13.09 · Cancellation with `AbortController`: Search, Route Changes, StrictMode

> **Section:** S13 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes

---

## 1. Why cancel?

Three situations produce responses nobody wants any more:

1. **Typing in a search box.** "r", "re", "rep"… each keystroke (after debouncing, 08.12) may start a request. Responses can arrive **out of order**: the slow "r" response lands after "report" and overwrites the correct results. You reproduced this race in 08.18.
2. **Leaving a page.** The user opens task 5, then quickly task 6. Task 5's response arrives while task 6's page is showing.
3. **Unmounting.** In development, StrictMode mounts, unmounts and re-mounts every component (08.03), so every effect's first request is immediately obsolete.

Ignoring stale responses (a `let ignore = true` flag, 08.18) fixes correctness. **Cancelling** also saves the network and the server work, and it's the same code with Axios.

## 2. The API: one controller, one signal

```ts
const controller = new AbortController();
api.get('/tasks', { params: { q }, signal: controller.signal });
controller.abort(); // → the request rejects with a CanceledError (verified: code 'ERR_CANCELED', message 'canceled')
```

`AbortController` is a web standard, the same one `fetch` uses. One controller can cancel several requests: pass the same signal to each.

(Axios's older `CancelToken` API is **deprecated**. You'll still see it in legacy code; don't write new code with it.)

## 3. The effect pattern (what `useTasks` does)

```ts
useEffect(() => {
  const controller = new AbortController();
  dispatch({ type: 'fetchStarted' });

  getTasks(LIST_QUERY, controller.signal)
    .then((page) => dispatch({ type: 'fetchSucceeded', tasks: page.items }))
    .catch((error: unknown) => {
      if (controller.signal.aborted) return; // cancelled on purpose: not an error
      dispatch({ type: 'fetchFailed', error: toErrorMessage(error) });
    });

  return () => controller.abort(); // cleanup: runs before re-running and on unmount
}, [reloadCount]);
```

- **One controller per effect run.** The cleanup of run N aborts run N's request just before run N+1 starts. That's exactly "cancel the previous search when the query changes".
- **Check `controller.signal.aborted`**, not just the error type. If the response had already arrived and was being processed when the abort happened, there's no `CanceledError`, but the result is still stale. The signal tells you the truth either way. (`isCancelled(error)` from 13.07 is useful in places that don't own the controller.)
- **Never show "Request cancelled" to the user.** They didn't do anything wrong.

### 🔬 StrictMode + Axios: one request, not two

With `fetch` (S08), the Network tab showed StrictMode's first request as **(canceled)**: it was sent, then aborted. With Axios, the reference app's mock log shows **one** `GET /api/tasks?size=100` on page load. Why? Axios runs request interceptors asynchronously (13.06 §4), so the XHR isn't created in the same tick. StrictMode's simulated unmount aborts the controller **synchronously**, before Axios gets to send. Axios checks the signal first and rejects with `CanceledError` without touching the network. Same outcome for your code (a cancelled promise), less noise in DevTools.

## 4. Search: debounce + cancel together

When the search moves to the server (S21: `GET /api/tasks?q=…&page=…`), the pattern combines both tools:

```ts
const debouncedQ = useDebounce(q, 300);             // fewer requests (08.12)

useEffect(() => {
  const controller = new AbortController();         // …and the ones still in flight get cancelled
  getTasks({ q: debouncedQ || undefined, size: 20 }, controller.signal)
    .then((page) => setResults(page.items))
    .catch((error: unknown) => {
      if (!controller.signal.aborted) setError(toErrorMessage(error));
    });
  return () => controller.abort();
}, [debouncedQ]);
```

- Debouncing reduces **how many** requests start.
- Cancelling guarantees that **only the latest** one can update the UI.

You need both. Debouncing alone still has races (a slow response can outlive the 300 ms window); cancelling alone still sends a request per keystroke.

## 5. Does cancelling stop the server?

**No, not reliably.** Aborting closes the connection from the browser's side. A request that already reached the server usually runs to completion there (a servlet doesn't notice until it tries to write the response). That's why:
- cancelling a **GET** is always fine: nothing changes on the server;
- cancelling a **POST/PUT/DELETE** doesn't undo it: the write may have happened. Our write functions don't even accept a signal (13.05).

## 6. Route changes

In TaskFlow, the details and edit pages read from the shared tasks context, so they don't fetch on their own. When a page does fetch its own data (for example, comments on the details page, S26), use the effect pattern with the route param in the dependency list: `useEffect(…, [id])`. Navigating from `/tasks/5` to `/tasks/6` re-runs the effect, and the cleanup aborts task 5's request. In S22, RTK Query does all of this for you, and you'll recognise what it's doing.

## 7. Summary

- `AbortController` + `signal` cancels Axios requests. `CancelToken` is deprecated.
- In effects: a new controller per run, `abort()` in cleanup, ignore results when `signal.aborted`.
- Search = debounce **and** cancel.
- Cancelling doesn't undo server-side writes.
