# Lecture 13.10 · `withCredentials`, Cookies and CORS: a First Look

> **Section:** S13 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~35 minutes
> The full treatment, including configuring CORS on your own servlets, is in S47. This lecture gives you the model you need to debug it.

## 1. Origin, site, and the same-origin policy

An **origin** is `scheme + host + port`:

| URL A | URL B | Same origin? |
|---|---|---|
| `http://localhost:5173/tasks` | `http://localhost:5173/api/tasks` | ✅ (paths don't matter) |
| `http://localhost:5173` | `http://localhost:3001` | ❌ different port |
| `http://localhost:5173` | `https://localhost:5173` | ❌ different scheme |
| `https://taskflow.example` | `https://api.taskflow.example` | ❌ different host |

The **same-origin policy**: a page may *send* requests anywhere (links, forms and images always could), but its **scripts may not read responses** from another origin, unless that origin allows it. Without this rule, any website you visit could read your webmail through your logged-in browser.

A **site** is looser: scheme + registrable domain (`example.com`), **ignoring port and subdomains**. `localhost:5173` and `localhost:3001` are **cross-origin but same-site**. The distinction matters for `SameSite` cookies (S24).

## 2. CORS: the server opts in

**CORS** (Cross-Origin Resource Sharing) is how a server says "scripts from origin X may read my responses", using response headers:

```http
Access-Control-Allow-Origin: http://localhost:5173
Access-Control-Allow-Credentials: true           ← only if cookies are involved
```

CORS is **enforced by the browser**, on behalf of the user. It's not a server-side access control: curl, Postman and server-to-server calls ignore it completely. It doesn't protect your API from attackers. It protects **users** from malicious pages that would use *their* browser and cookies.

### Simple requests vs preflighted requests

**Simple** requests (GET/HEAD/POST with only "safe" headers, and a form-style `Content-Type`) are **sent directly**. The browser just refuses to hand the response to the script.

Verified: `axios.get('http://localhost:3001/api/tasks')` from `localhost:5198` (plain Axios, no custom headers). The console showed *"blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present"*, and the script got `Network Error`… **but the mock's log shows `GET /api/tasks 200`**. The request ran on the server.

**Preflighted** requests (PUT/PATCH/DELETE, `Content-Type: application/json`, or any custom header such as `X-Request-Id`) are first **asked about** with an `OPTIONS` request:

```http
OPTIONS /api/tasks
Origin: http://localhost:5173
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, x-request-id
```

Only if the answer allows it does the browser send the real request. Verified with TaskFlow's `api` instance posting JSON straight to `:3001`: the mock logged **`OPTIONS /api/tasks 404`**, and **no POST** (no task was created). The console said *"Response to preflight request doesn't pass access control check"*.

> 🛡 Consequence: CORS is **not** a defence against state-changing *simple* requests. A cross-site `<form method="post">` is a simple request, and it will execute on the server. Defending against that is CSRF protection's job (S24, S47). Our mock (and later your servlets) also **require `Content-Type: application/json`** on writes (verified: a form-encoded POST got `415`), which forces a preflight for any cross-site script.

## 3. Cookies and `withCredentials`

| Request | Cookies sent? | Response cookies stored? |
|---|---|---|
| Same-origin (our proxy setup) | ✅ always | ✅ |
| Cross-origin, `withCredentials: false` (the default) | ❌ | ❌ `Set-Cookie` is ignored |
| Cross-origin, `withCredentials: true` | ✅, if `SameSite` allows | ✅ if the server also allows credentials |

For a **credentialed** cross-origin request, the server's CORS answer must be stricter:
- `Access-Control-Allow-Origin` must be the **exact** origin. The wildcard `*` is **rejected** with credentials.
- `Access-Control-Allow-Credentials: true` must be present.

(`withCredentials` is the XHR property's name; `fetch` calls the same thing `credentials: 'include'`.)

The "reflect any origin with credentials" misconfiguration (echoing back whatever `Origin` arrives, plus `Allow-Credentials: true`) turns CORS off for every website. It's a real, common vulnerability. json-server's default CORS middleware does exactly that for local development, which is one reason the mock sets `noCors: true`. You'll write a correct allowlist in S47.

## 4. TaskFlow's architecture avoids CORS

| Environment | Browser talks to | Cross-origin? |
|---|---|---|
| Dev (now) | Vite `:5173` for both app and `/api` (proxy) | ❌ |
| Dev (Part 3) | Vite `:5173`, proxy to Tomcat `:8080` | ❌ |
| Production (S49) | Tomcat serves both `/app/*` and `/api/*` | ❌ |

So why set `withCredentials: true` at all? It's harmless on same-origin requests, and it keeps the client correct if the API is ever deployed on its own origin (`api.taskflow.example`), which is common at larger companies.

## 5. Summary

- Origin = scheme + host + port. The same-origin policy stops **scripts reading** cross-origin responses, not requests being sent.
- CORS = server response headers that relax that, enforced by the browser for users' protection. Not an API firewall.
- JSON bodies and custom headers trigger a **preflight**; a failed preflight means the real request is never sent.
- Cookies cross origins only with `withCredentials` **and** exact-origin + `Allow-Credentials` from the server.
- TaskFlow stays same-origin via the proxy, then via a single deployment.
