## 2. Anatomy of an HTTP exchange

```http
PATCH /api/tasks/2 HTTP/1.1                    ← request line: METHOD  PATH  VERSION
Host: localhost:5173                           ← headers: metadata, one per line
Content-Type: application/json                   (what the BODY is)
Accept: application/json                         (what I want BACK)
Cookie: JSESSIONID=9f2c…                          (sent automatically by the browser, S24)
X-Request-Id: 0b8e…                               (our own header, 13.07)

{"status":"DONE"}                              ← body (after one empty line)
```

```http
HTTP/1.1 200 OK                                ← status line: VERSION  CODE  REASON
Content-Type: application/json; charset=utf-8

{"id":2,"title":"Fix login redirect bug","status":"DONE", …}
```

Plain text over a TCP connection (HTTP/1.1; HTTP/2 and 3 change the wire format, not these concepts). In Part 2 you'll read exactly these parts with `request.getMethod()`, `request.getHeader("Content-Type")` and `request.getReader()`.

## 3. Methods: what the client wants to do

| Method | Meaning in TaskFlow | Body? | **Safe** (no changes) | **Idempotent** (repeat = same result) |
|---|---|---|---|---|
| `GET` | Read: `GET /api/tasks?status=DONE` | No | ✅ | ✅ |
| `POST` | Create: `POST /api/tasks` | Yes | ❌ | ❌ two POSTs = two tasks |
| `PUT` | Replace all editable fields: `PUT /api/tasks/2` | Yes | ❌ | ✅ |
| `PATCH` | Change some fields: `PATCH /api/tasks/2 {"status":"DONE"}` | Yes | ❌ | Usually (ours is) |
| `DELETE` | Delete: `DELETE /api/tasks/2` | No | ❌ | ✅ (2nd time: 404, but the state is the same) |

Why these properties matter:
- **Safe** methods must never change data. Browsers, crawlers and link prefetchers issue GETs freely. A "delete" link (`GET /tasks/delete?id=5`) could be triggered by an `<img src>` on another site. That's why TaskFlow Admin deletes with POST (S37), and why CSRF protection targets unsafe methods (S24, S47).
- **Idempotent** methods can be **retried** safely after a network failure (13.99 exercise). Retrying a POST can create a duplicate (remember the double-submit bug in 11.06).

## 4. Status codes: what happened

| Range | Meaning | TaskFlow examples |
|---|---|---|
| **2xx** success | It worked | `200 OK` (read/update), `201 Created` (+ `Location` header), `204 No Content` (delete, logout) |
| **3xx** redirection | Look elsewhere | `302 Found` after a JSP form POST (PRG, S37). **APIs rarely redirect.** |
| **4xx** client error | *Your* request is wrong: don't retry unchanged | `400` invalid input, `401` not logged in, `403` logged in but not allowed / bad CSRF token, `404` not found, `415` wrong content type |
| **5xx** server error | The server failed: maybe retry later | `500` bug, `502`/`503`/`504` gateway or server unavailable |

`401` vs `403` is a classic interview question: **401 Unauthorized** actually means *unauthenticated* ("who are you?"), and **403 Forbidden** means *authenticated but not allowed* ("I know you, and no").

## 5. Headers you'll meet in this course

| Header | Direction | Purpose |
|---|---|---|
| `Content-Type: application/json` | both | The format of **this** message's body |
| `Accept: application/json` | request | The format the client wants back |
| `Location: /api/tasks/26` | response | Where the created resource lives (with `201`) |
| `Cookie` / `Set-Cookie` | request / response | Sessions, CSRF token, preferences (S24, S39) |
| `Cache-Control` | response | Caching rules (12.12) |
| `Origin` | request | Which site a cross-origin request comes from (CORS, 13.10) |
| `X-XSRF-TOKEN` | request | The CSRF token (S24) |
| `X-Request-Id` | request | A correlation id for logs (13.07) |

## 6. JSON bodies

JSON is text. Sending an object means **serialising** it (`JSON.stringify`) and setting `Content-Type: application/json`. Receiving means **parsing** (`JSON.parse`) and then **validating**, because the parsed value is `unknown` (06.09). Types like `Date`, `Map` and `undefined` don't exist in JSON: dates travel as ISO strings (`"2026-10-03"`), and a missing field is not the same as `null`.

## 7. Watching it: the Network tab

DevTools → **Network** → filter **Fetch/XHR**. Click a request:
- **Headers:** method, URL, status, request and response headers.
- **Payload:** the request body and query parameters.
- **Preview / Response:** the response body.
- **Timing:** where the time went (waiting for the server = "TTFB").

Right-click → **Copy → Copy as cURL** replays the request from a terminal. That's invaluable for bug reports, and for security testing: it shows that anyone can send any request, with no UI involved (12.07).

## 8. Summary

- Request = method + path + headers + optional body. Response = status + headers + optional body.
- Safe methods (GET) must not change data. Idempotent methods (GET, PUT, DELETE) can be retried; POST can't.
- 2xx success, 4xx the client's fault, 5xx the server's fault. 401 = who are you, 403 = not allowed.
- JSON crosses the wire as text: stringify, parse, validate.
