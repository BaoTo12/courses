# Lecture 13.08 · Error Anatomy: Network Error vs Timeout vs 4xx vs 5xx

> **Section:** S13 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~35 minutes
> Every raw error below was captured in the reference app (Axios 1.20, Chrome), using the mock's `_mockDelay`/`_mockStatus` helpers.

## 1. Five ways a request can end badly

| Situation | Raw Axios error (verified) | `error.response`? | Our `kind` |
|---|---|---|---|
| Server answered **404** | `AxiosError`, `code: 'ERR_BAD_REQUEST'`, `message: 'Request failed with status code 404'` | ✅ status 404, body = our error JSON | `http` |
| Server answered **503** | `AxiosError`, `code: 'ERR_BAD_RESPONSE'` (Axios uses this code for 5xx) | ✅ | `http` |
| **Timeout** (300 ms limit, 1500 ms server) | `AxiosError`, `code: 'ECONNABORTED'`, `message: 'timeout of 300ms exceeded'` | ❌ | `timeout` |
| **Connection refused** (nothing on the port) | `AxiosError`, `code: 'ERR_NETWORK'`, `message: 'Network Error'` | ❌ | `network` |
| **CORS** blocked (13.15) | `AxiosError`, `code: 'ERR_NETWORK'`, `message: 'Network Error'` (identical!) | ❌ | `network` |
| **We aborted** (`AbortController`) | `CanceledError`, `code: 'ERR_CANCELED'`, `message: 'canceled'` | ❌ | `cancelled` |
| Mock down **behind the Vite proxy** | `AxiosError`, `ERR_BAD_RESPONSE`, **status 502**, empty `text/plain` body | ✅ (from the proxy!) | `http` (5xx) |

Three lessons hide in this table.

### Lesson 1: "no response" has several causes, and JavaScript can't tell them apart

A refused connection, DNS failure, offline laptop, TLS error and CORS block all produce the same `ERR_NETWORK` / `'Network Error'`. **By design**: if the browser told scripts *why* a cross-origin request failed, a malicious page could use your browser to scan your internal network ("port 8080 on 192.168.1.5 refused, port 22 timed out…"). The details are only in the **DevTools console**, which scripts can't read. When debugging `Network Error`, open the console first.

### Lesson 2: a proxy changes the failure you see

With the dev proxy, the browser always reaches Vite, so "backend down" arrives as a **502** from Vite, not as a network error. In production, a load balancer or Nginx does the same (502/503/504, often with an **HTML** body). That's why `toApiRequestError` treats "a 5xx whose body isn't our contract" as "server unavailable" (13.07).

### Lesson 3: a response doesn't mean our server wrote it

`error.response.data` may be our JSON error body, a proxy's HTML page, an empty string, or anything else. `isApiError(data)` checks before we trust `data.message`. The same boundary rule as always (06.09).

## 2. `axios.isAxiosError` and typing `AxiosError<ApiError>`

`catch (e)` gives `unknown` (05.07). `axios.isAxiosError(e)` is a type guard that narrows it to `AxiosError`. You can pass a type argument:

```ts
if (axios.isAxiosError<ApiError>(error)) {
  error.response?.data.message; // typed as string… but NOT checked
}
```

⚠️ Like `api.get<Task>()` (13.05), that type argument is an **assertion**. The guard checks "is this an AxiosError?", not "is `response.data` an `ApiError`?". A 502 from a proxy would have `data === ''`, and `data.message` would be `undefined` at runtime despite the `string` type. That's why TaskFlow narrows with `isAxiosError(error)` (no type argument) and then validates the body with `isApiError(data)`.

## 3. Which status codes should the UI treat differently?

| Status | What the UI should do | Where in TaskFlow |
|---|---|---|
| 400 + `fieldErrors` | Show errors **next to the fields** | 13.12 stretch goal |
| 401 | "Your session expired": go to login, keep `returnTo` | S24 (a response interceptor) |
| 403 | "You don't have permission" (or, with a CSRF error code, refresh the token and retry once) | S24, S26 |
| 404 | "Not found" page or message | details/edit pages |
| 409 | "Someone else changed this": reload and merge | S46 (optimistic locking, extension) |
| 5xx / network / timeout | "Try again" with a retry button | list page (13.12) |
| cancelled | **Nothing**. The user (or the code) asked for it. | `useTasks` (13.09) |

## 4. Retry: only when it's safe

Automatic retries are tempting for network errors. The rules (13.01 §3):
- Retry only **idempotent** methods (GET, PUT, DELETE). A retried POST can create a duplicate: the first attempt may have reached the server, with only the response lost.
- Retry only **transient** failures (network, timeout, 502/503/504), never 4xx: the same request will fail the same way.
- Back off (wait 0.5 s, then 1 s…) and cap the attempts, or a struggling server gets hammered by every client at once.

You'll implement a retry-once interceptor in the knowledge check (13.99).

## 5. Summary

- `error.response` present → the **server (or a proxy)** answered: check the status, then validate the body.
- Absent → timeout (`ECONNABORTED`), cancellation (`ERR_CANCELED`), or "network" (`ERR_NETWORK`: refused, offline, **CORS**…). The browser hides the reason from scripts on purpose.
- `isAxiosError<T>` doesn't validate `T`. Validate bodies with guards.
- React to failures by **kind** and **status**; retry only idempotent, transient failures.
