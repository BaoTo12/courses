# Lecture 03.12 · Design Tokens → CSS Custom Properties: the Bridge Between Compile Time and Runtime

> **Section:** S03 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes
> This lecture explains the idea that connects SCSS, styled-components (S10) and the JSP portal (S32).

---

## 1. The problem

TaskFlow needs **light and dark themes**, switchable **while the page is running** (a toggle in the header, or following the OS setting).

With colours as Sass variables, the compiled CSS contains literal values:

```css
.card { background: #ffffff; border: 1px solid #e2e8f0; }
```

To switch themes you'd need a second copy of every rule with dark values, or to recompile. Neither is acceptable.

## 2. The idea

Split each colour decision into two layers:

```text
          COMPILE TIME (Sass)                           RUNTIME (browser)
┌─────────────────────────────────────┐        ┌─────────────────────────────────────┐
│ $themes: (                          │ emits  │ :root {                             │
│   'light': ('surface': #fff, …),    │ ─────▶ │   --color-surface: #fff; …          │
│   'dark':  ('surface': #1e293b, …)  │        │ }                                   │
│ )                                   │        │ [data-theme='dark'] {               │
│                                     │        │   --color-surface: #1e293b; …       │
│ theme('surface')  ──returns──▶      │        │ }                                   │
│      var(--color-surface)           │        │ .card { background:                 │
│                                     │        │         var(--color-surface); }     │
└─────────────────────────────────────┘        └─────────────────────────────────────┘
```

- **Sass** holds the *data* (theme maps), *validates* names, and *generates* the custom properties.
- **Components** reference `var(--color-surface)` (through a `theme()` function), never literal colours.
- **The browser** resolves `var(--color-surface)` using whichever rule applies to the element *right now*. Switch `data-theme="dark"` on `<html>` and every component updates instantly, with no recompile.

## 3. Semantic vs raw tokens

Two kinds of tokens:

| Raw (palette) | Semantic (role) |
|---|---|
| `slate-800: #1e293b` | `surface`, `text`, `border`, `primary`, `danger`… |
| What colour it **is** | What it's **for** |
| Never used directly by components | The only colours components use |

A theme is just a **mapping from semantic names to raw colours**. In light mode `surface` = white; in dark mode `surface` = slate-800. Components only know `surface`, so they work in any theme. Adding a "high contrast" theme later means writing one new map, and **zero component changes**.

## 4. How custom properties resolve (internals)

1. `--color-surface` is a **custom property**. Like any CSS property, it's set by rules and **inherits** down the DOM tree.
2. `var(--color-surface)` is looked up **on the element being styled**, at computed-value time: "what's the inherited value of `--color-surface` here?"
3. So `[data-theme='dark'] { --color-surface: … }` on `<html>` changes the value for **every descendant**.
4. You can even theme a subtree: `<aside data-theme="dark">` makes only the sidebar dark.
5. If a property is **undefined**, `var()` uses its fallback (`var(--x, red)`), otherwise the declaration becomes "invalid at computed-value time" and the property falls back to its inherited/initial value.

## 5. The `theme()` function: compile-time safety for runtime values

Writing `var(--color-surfce)` by hand has a typo problem: the browser silently ignores it. So TaskFlow wraps references in a Sass function:

```scss
@function theme($name) {
  @if not map.has-key(map.get($themes, 'light'), $name) {
    @error 'Unknown theme token "#{$name}". Known: #{map.keys(map.get($themes, "light"))}';
  }
  @return var(--color-#{$name});
}
```

```scss
.card { background: theme('surfce'); }
```

```text
Error: 'Unknown theme token "surfce". Known: primary, primary-hover, on-primary, danger, …'
```

**Validated at compile time, resolved at runtime.** Best of both worlds.

## 6. Three ways a theme gets chosen

```scss
// 1. Default: light
:root, [data-theme='light'] { /* light tokens */ }

// 2. User explicitly chose dark in the app → JS/JSP sets <html data-theme="dark">
[data-theme='dark'] { /* dark tokens */ }

// 3. No explicit choice: follow the OS setting
@media (prefers-color-scheme: dark) {
  :root:not([data-theme='light']) { /* dark tokens */ }
}
```

`:root:not([data-theme='light'])` means "follow the OS **unless** the user explicitly chose light". The user's choice will be stored in a **`theme` cookie** (S24 with js-cookie in React, S39 in JSP), which is how the choice survives reloads and is shared by both apps.

`color-scheme: dark;` tells the browser to render its **own** UI (scrollbars, form controls, date pickers) in dark style too.

## 7. What stays as Sass variables?

| Stays compile-time (Sass) | Becomes runtime (custom property) |
|---|---|
| Breakpoints (media queries can't use `var()`) | Theme colours |
| Spacing scale, radii (could be either; rarely themed) | Anything a user preference changes |
| Status/priority colours: optional. They're the same in both themes here; you could theme them later | Values JS or styled-components need to read |

TaskFlow keeps status/priority colours as Sass maps (not themed) to keep the lecture focused. A good extension exercise is to make them themeable too.

## 8. Why this matters beyond SCSS

- **styled-components (S10):** the React theme object will reference these same custom properties (`theme.colors.surface = 'var(--color-surface)'`), so SCSS components and styled components switch themes **together**, from one source of truth.
- **JSP (S32, S39):** the compiled `app.css` contains the same custom properties; JSP just sets `data-theme` on `<html>` from a cookie. Same tokens, no JavaScript needed.

## 9. Summary

- Sass holds **theme maps** and **emits** `--color-*` custom properties per theme.
- Components use **semantic** tokens via `theme('name')` → `var(--color-name)`.
- The browser resolves `var()` at runtime; switching `data-theme` re-themes everything instantly.
- Compile-time validation (`@error`) + runtime flexibility (custom properties).
- The same tokens will drive styled-components and the JSP portal.

## 10. Check yourself

1. Why can't a pure Sass-variable approach support a runtime theme toggle?
2. What does `theme('border')` compile to?
3. A component has `color: var(--color-txt)` (typo, written by hand). What happens in the browser? How does `theme()` prevent this?
4. What does `:root:not([data-theme='light'])` inside `prefers-color-scheme: dark` achieve?

<details>
<summary>Answers</summary>

1. Sass variables are replaced by literal values at compile time; the CSS has no "switch" left to flip.
2. `var(--color-border)`.
3. The property is undefined, so the declaration is invalid at computed-value time and the element falls back to the inherited/initial colour, **silently**. `theme('txt')` fails the **build** with a list of valid names.
4. It applies the dark tokens when the OS prefers dark, **unless** the user explicitly chose light (`data-theme="light"`).

</details>
