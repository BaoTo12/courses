# Lecture 03.10 · Architecture: the 7-1 Pattern, `@forward`, and a Library's Public API

> **Section:** S03 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes

---

## 1. The problem

Each component file now starts with:

```scss
@use 'sass:map';
@use '../abstracts/variables' as *;
@use '../abstracts/tokens' as *;
@use '../abstracts/functions' as *;
@use '../abstracts/mixins' as *;
```

And the folder layout was improvised. As the design system grows (and it will be consumed by **two apps**), you need:
1. A **predictable folder structure** so everyone knows where things go.
2. A **single entry point** for shared tools (variables, functions, mixins).

## 2. `@forward`: re-exporting modules

`@forward` makes a module's members available **to whoever `@use`s the forwarding file**, without using them in the forwarding file itself.

```scss
// styles/abstracts/_index.scss
@forward 'variables';
@forward 'tokens';
@forward 'functions';
@forward 'mixins';
```

Now every component needs one line:

```scss
@use '../abstracts' as *;      // loads abstracts/_index.scss
```

- `@use '../abstracts'` finds `abstracts/_index.scss` automatically (a folder with an index file acts as a module).
- The namespace would be `abstracts` (the folder name); `as *` removes it.

### `@use` vs `@forward`

| | `@use 'x'` | `@forward 'x'` |
|---|---|---|
| Makes x's members usable **in this file** | ✅ | ❌ |
| Makes x's members available **to files that use this file** | ❌ | ✅ |
| Typical place | Components, layouts | Index files / library entry points |

A file can do both: `@forward 'tokens';` **and** `@use 'tokens' as *;` if it needs them itself.

### Controlling the public API

```scss
@forward 'functions' hide space;                 // don't expose space()
@forward 'mixins' show respond-to, focus-ring;  // expose only these
@forward 'variables' as tf-*;                    // prefix: $tf-color-primary, …
```

`show`/`hide` let a design-system maintainer keep internal helpers private, which is useful when other teams consume your styles.

### Configuring through `@forward`

```scss
@forward 'variables' with ($space-unit: 4px !default);
```

This lets the next layer up still override `$space-unit` (because of `!default`).

## 3. The 7-1 pattern (adapted)

The classic **7-1 pattern** is 7 folders + 1 main file. TaskFlow uses a trimmed version. Folders are only created when there's something to put in them:

```text
styles/
├── abstracts/        # NO CSS output: variables, tokens (maps), functions, mixins
│   ├── _variables.scss
│   ├── _tokens.scss
│   ├── _functions.scss
│   ├── _mixins.scss
│   └── _index.scss   # @forward all of the above
├── base/             # global element styles: reset, typography, :root custom properties
│   ├── _reset.scss
│   ├── _root.scss
│   └── _typography.scss
├── layout/           # page-level structure: page shell, grids
│   ├── _page.scss
│   └── _kit.scss
├── components/       # BEM blocks: button, badge, card, form…
├── themes/           # theme-specific overrides (if any beyond tokens)
├── utilities/        # single-purpose helpers, loaded LAST (.visually-hidden, .text-muted)
└── main.scss         # the "1": loads everything in cascade order
```

The two classic folders we skip are `vendors/` (third-party CSS) and `pages/` (page-specific styles). You'd add them when needed.

### The most important rule: `abstracts/` emits no CSS

Everything in `abstracts/` must be **pure tools**: variables, maps, functions, mixins. If a file in `abstracts/` contained a rule like `:root { … }`, that CSS would be emitted wherever `abstracts` is first loaded, and in a React app where **each component `.module.scss` is compiled separately** (S07), it would be **duplicated into every component's CSS**. Rules that output CSS belong in `base/`, `layout/`, `components/`, etc.

### Cascade order in `main.scss`

```scss
@use 'base/reset';
@use 'base/root';
@use 'base/typography';
@use 'layout/page';
@use 'layout/kit';
@use 'components/button';
@use 'components/badge';
@use 'components/card';
@use 'components/form';
@use 'utilities/text';
```

Generic → specific: base styles first, utilities last (so a utility can override a component at equal specificity, as in 02.13).

## 4. How this serves two apps

```text
styles/abstracts  ──@use──▶  React: every *.module.scss can @use the tools (no CSS duplicated)
styles/main.scss  ────────▶  React: imported once in main.tsx (global base/layout/components)
styles/main.scss  ──sass──▶  JSP: compiled to app.css (S28)
```

Tools shared, CSS output controlled, one source of truth.

## 5. Summary

- `@forward` re-exports modules; an `_index.scss` makes a folder usable as one module.
- `show`/`hide`/`as prefix-*` control a library's public API.
- 7-1 (trimmed): abstracts (no CSS!), base, layout, components, themes, utilities, main.
- `main.scss` defines cascade order: generic → specific, utilities last.

## 6. Check yourself

1. A component writes `@use '../abstracts' as *;` and calls `respond-to('md')`. What makes the mixin visible?
2. Why must `abstracts/` never contain CSS rules?
3. What's the difference between `@use 'tokens'` and `@forward 'tokens'` in `_index.scss`?

<details>
<summary>Answers</summary>

1. `abstracts/_index.scss` does `@forward 'mixins';`, so the mixins module's members are exposed to any file that `@use`s the abstracts folder.
2. Because `abstracts` is loaded by many files, and in setups that compile files separately (CSS Modules in React) its CSS would be emitted into **every** consumer's output, duplicating it.
3. `@use` makes the members usable **inside `_index.scss`** only; `@forward` passes them **through** to files that use the index. The index needs `@forward`.

</details>
