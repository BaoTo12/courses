# Lecture 02.02 · What Sass Is: a Compiler (SCSS → CSS at Build Time)

> **Section:** S02 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes

---

## 1. Sass is a program

When people say "Sass", they mean two things:
1. The **language** (SCSS syntax).
2. The **compiler**, a program that reads `.scss` files and writes `.css` files.

Today the official compiler is **Dart Sass**. It's distributed on npm as the `sass` package (compiled to JavaScript, runs on Node) and also as a standalone binary (`sass-embedded` is a faster variant). The older **node-sass / LibSass** is **deprecated**; if you see it in an old project, it's legacy.

---

## 2. What the compiler does, step by step

```text
main.scss
  │ 1. Parse        text → syntax tree
  │ 2. Load modules  follow @use/@forward, load each file ONCE
  │ 3. Evaluate      variables, math, functions, mixins, @if/@each, interpolation
  │ 4. Resolve       nesting & `&` → flat selectors
  │ 5. Emit          write plain CSS (+ optional source map)
  ▼
main.css (+ main.css.map)
```

Example:

```scss
// input
$radius: 6px;
.card {
  border-radius: $radius * 2;
  &__title { font-weight: 600; }
}
```

```css
/* output */
.card {
  border-radius: 12px;
}
.card__title {
  font-weight: 600;
}
```

Everything Sass-specific (`$radius`, `*`, `&`, nesting) is **gone** from the output. What's left is ordinary CSS.

---

## 3. Compile-time errors are a feature

Because Sass evaluates your code, it can **stop the build** when something is wrong:

```scss
.x { width: 10px + 2em; }   // Error: 10px and 2em have incompatible units.
.y { color: $undefined; }    // Error: Undefined variable.
```

Plain CSS would silently ignore a bad declaration and you'd find out in the browser (maybe). Sass fails loudly on your machine. You can also raise your own errors (`@error`) in mixins and functions (S03).

---

## 4. Source maps

The browser runs `main.css`, but you edit `_button.scss`. A **source map** (`main.css.map`) is a file that maps each CSS line back to the SCSS file and line that produced it. With it, DevTools' Styles pane shows `_button.scss:12` instead of `main.css:340`.

- Great in development.
- In production, you may choose not to publish source maps (they reveal your source structure). It's not a big security issue for CSS, but it's a good habit to decide consciously.

---

## 5. When does compilation happen?

| Context | Who runs Sass | When |
|---|---|---|
| UI kit (this section) | You, via `sass --watch` | Every time you save |
| React app (S07+) | **Vite** (it calls the `sass` package for `.scss` imports) | On the fly in dev; once at `vite build` |
| JSP Admin Portal (S28+) | An npm script calling the Sass CLI | Before/while deploying the WAR |

In all cases, **the browser receives CSS**. It never runs Sass.

---

## 6. Summary

- Sass = the SCSS language + the **Dart Sass** compiler (`sass` on npm). node-sass is deprecated.
- Compilation: parse → load modules → evaluate → flatten nesting → emit CSS.
- Sass errors stop the build: good.
- Source maps map CSS back to SCSS for debugging.
- The browser only ever sees CSS.

---

## 7. Check yourself

1. Does the browser download your `.scss` files?
2. What happens to `$radius` in the compiled output?
3. Why is a compile-time error better than a browser silently ignoring a bad rule?

<details>
<summary>Answers</summary>

1. No (unless you publish them for source maps). It downloads compiled `.css`.
2. It's replaced by its value wherever it was used; the variable itself doesn't exist in CSS.
3. You find the mistake immediately on your machine, before shipping, instead of discovering (or never discovering) a missing style in production.

</details>
