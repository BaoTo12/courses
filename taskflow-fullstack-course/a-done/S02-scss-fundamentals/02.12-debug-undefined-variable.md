# Lecture 02.12 · 🐞 Debug: "Undefined variable: $color-primary"

> **Section:** S02 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~15 minutes

---

## Symptom

A teammate adds a new component, `styles/components/_avatar.scss`:

```scss
.avatar {
  width: 32px;
  height: 32px;
  border-radius: $radius-full;
  background: $color-primary;
  color: #fff;
}
```

and adds it to `main.scss`:

```scss
@use 'base/reset';
@use 'abstracts/variables' as *;
@use 'layout/page';
@use 'components/button';
@use 'components/avatar';
```

The watcher prints:

```text
Error: Undefined variable.
  ╷
4 │   border-radius: $radius-full;
  │                  ^^^^^^^^^^^^
  ╵
  styles/components/_avatar.scss 4:18  @use
  styles/main.scss 5:1                  root stylesheet
```

Their reasoning: "`main.scss` loads the variables **before** the avatar, so the variables should be available. Sass must be loading files in the wrong order."

---

## Investigation checklist

Work through these before reading the explanation:

1. Read the error's **stack** (the lines under the code frame). Which file failed, and which file loaded it?
2. Open `_button.scss`, which works. What does it have at the top that `_avatar.scss` doesn't?
3. Recall 02.07: with `@use`, where are a module's members visible?
4. Would this code have worked with the old `@import`? Why?

---

## Explanation

**Cause.** With `@use`, a module's members are available **only in the file that wrote the `@use`**. `main.scss` loaded the variables for *itself*. That doesn't make them visible inside `_avatar.scss`. Every module is evaluated in its own scope, with only what *it* loads.

The teammate's mental model ("load order makes things available") is the **`@import` model**, where everything was pasted into one global scope, so anything loaded earlier was visible later. That model is exactly what `@use` was designed to replace: dependencies are now **explicit per file**.

**Fix.** Add the dependency to the file that needs it:

```scss
@use '../abstracts/variables' as *;

.avatar {
  …
}
```

**Why this is better, even though it's more typing:**
- Each file declares what it depends on. You can read `_avatar.scss` alone and know where `$radius-full` comes from.
- Reordering `@use`s in `main.scss` can never break a component.
- The variables module is still only **evaluated once**, however many files `@use` it, so there's no duplication in the output.

(In S03, `abstracts/_index.scss` will `@forward` variables, mixins and functions, so the line becomes `@use '../abstracts' as *;` in every component.)

---

## Related gotchas

| Error | Likely cause |
|---|---|
| `Undefined variable` in a partial | Missing `@use` in *that* partial |
| `There's already a module with namespace "variables"` | Two `@use`s whose last path segment is the same (`abstracts/variables` and `themes/variables`); fix with `as` |
| `This module was already loaded, so it can't be configured using "with"` | `@use … with (…)` isn't the **first** load of that module |
| `Private members can't be accessed from outside their modules` | Using a `$-private` or `$_private` name from another file |

---

## What this trained

Reading the compile error's **stack of loads** and recognising that `@use` scoping is **per file**, not per load order. Keep this in mind for S07: ES modules in JavaScript/TypeScript work the same way. Each file imports what it uses.
