## D. Design

9. A button colour depends on the user's saved theme preference. SCSS variable or CSS custom property? Justify. [02.04]
10. Your team's `_variables.scss` has `$blue-600`, `$red-600`, `$gray-200`. What naming change would you propose, and why? [02.04]

## E. Implementation

11. Add `.btn--danger` (danger background, derived darker hover) and `.btn--sm` (smaller padding and font) using only variables, nesting and `sass:color`. Both buttons already exist in the UI kit HTML.

---

<details>
<summary><b>Answers</b></summary>

1. **No.** Sass variables exist only at compile time; they're replaced by values in the CSS. Use **CSS custom properties** (`--color-primary`), switched by a class/attribute or `style.setProperty`.

2. `@import` pasted files into one **global** scope, **re-output** files imported multiple times, and made correctness depend on **import order**. `@use` loads each module **once**, with **namespaced, per-file** visibility and private members.

3. It maps compiled CSS lines back to the original SCSS file/line. **DevTools** uses it to show `_button.scss:12` in the Styles pane.

4.
   ```css
   .badge--done { color: green; }
   .icon + .badge { margin-left: 4px; }
   ```

5. `.card__title a:hover` → **(0,2,1)**. `.nav .nav__item .nav__link` → **(0,3,0)** (needlessly high; `.nav__link` alone would be (0,1,0)).

6. `.btn :hover { opacity: 0.9; }`: "any hovered **descendant** of `.btn`". The author meant `&:hover` → `.btn:hover`.

7. With `@use`, members are visible **only in the file that `@use`s them**. Each partial must add `@use '../abstracts/variables' as *;` (or later `@use '../abstracts' as *;`).

8. Check the winning rule's selector and **specificity** in DevTools. Fixes: (a) flatten the over-nested component selector so it's one class; (b) express the state as a **component modifier** (e.g. `.nav__link--muted`), and/or place utilities last with equal specificity. Not `!important`.

9. **CSS custom property.** The value must change at **runtime** based on user preference. A Sass variable is fixed at build time. (Define the token in Sass and emit it as a custom property: best of both.)

10. Name tokens by **purpose** (`$color-primary`, `$color-danger`, `$color-border`), not by value. A rebrand or theme change then doesn't require renaming, and components express intent. (Keeping a raw palette like `$blue-600` *underneath* semantic tokens is fine.)

11. One solution, inside `.btn { … }` in `_button.scss` (with `@use 'sass:color';` at the top, or using `$color-danger-dark` from 02.08):
    ```scss
    &--danger {
      background: $color-danger;
      color: #fff;

      &:hover:not(:disabled) {
        background: $color-danger-dark;
      }
    }

    &--sm {
      padding: $space-1 $space-3;
      font-size: 0.75rem;
    }
    ```
    `.btn--sm` only changes size, so it combines with any colour variant (`btn btn--primary btn--sm`). Size and colour are **independent axes**, each with its own modifier.

</details>
