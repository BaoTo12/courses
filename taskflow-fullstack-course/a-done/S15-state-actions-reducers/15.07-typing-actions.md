# Lecture 15.07 · TS: Actions as a Discriminated Union, and Why `assertNever` Crashes a Redux Store

> **Section:** S15 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~35 minutes
> 🔗 Official companion reading: the Redux docs page "Usage with TypeScript" (and, for context, the RTK version in S20)
> All errors and behaviours below were reproduced with redux 5.0.1 and TypeScript 6 in the reference app.

---

## 1. The union of all actions: `src/app/app-action.ts`

```ts
import type { AuthAction } from '../features/auth/authActions';
import type { TasksAction } from '../features/tasks/tasksSlice';

/**
 * Every action TaskFlow can dispatch. In Redux, EVERY slice reducer receives EVERY action,
 * so each reducer's `action` parameter is this whole union, not just "its own" actions (15.07).
 */
export type AppAction = TasksAction | AuthAction;
```

In 15.12 you'll add `ListPrefsAction` and `UiAction` to it. The files import each other's **types** only (`import type`), so this "cycle" (the slices import `AppAction`, which imports the slices' action types) is erased at compile time and harmless at runtime.

## 2. What the discriminated union buys you

`type` is the **discriminant** (06.06). Inside a `case`, TypeScript narrows `action` to that member, and it checks the `case` labels themselves.

A misspelled case (verified, with the finished S15 code, so the list also includes the `listPrefs`/`ui` actions you add in 15.12):

```text
error TS2678: Type '"tasks/taskAded"' is not comparable to type '"auth/loggedOut" | "listPrefs/sortChanged" |
"listPrefs/pageSizeChanged" | "tasks/fetchStarted" | "tasks/fetchSucceeded" | … 6 more … | "ui/selectionCleared"'.
```

A payload that doesn't exist on that action (verified):

```text
error TS2339: Property 'payload' does not exist on type '{ type: "tasks/fetchStarted"; }'.
```

And inside `case 'tasks/taskDeleted':`, `action.payload` is a `number`, so `action.payload.title` is an error. In plain JavaScript, all three bugs are silent: the case never matches, or the reducer reads `undefined`.

### Typed action creators with `Extract`

```ts
type TasksActionOf<T extends TasksAction['type']> = Extract<TasksAction, { type: T }>;

export const taskDeleted = (id: number): TasksActionOf<'tasks/taskDeleted'> => ({ type: 'tasks/taskDeleted', payload: id });
```

`Extract` (06.03) picks the union member whose `type` is `'tasks/taskDeleted'`. The return type is then precise: the object must have exactly that `type` and a `number` payload. Without the annotation, TypeScript would widen `type` to `string`, and the object would no longer be assignable to the union.

## 3. Why the `useReducer` habit breaks here

In 08.07 and 13.12, TaskFlow's `useReducer` reducer ended with:

```ts
default:
  return assertNever(action);   // compile-time exhaustiveness: every action type must have a case
```

That was correct there: the action type was **closed**. Only our own code dispatched to that reducer, only with `TasksAction`.

A Redux slice reducer is different. **It receives every action dispatched to the store**:
- Redux's own **init** action, with a random type like `@@redux/INITe.t.u.w.a.9`;
- `combineReducers`' **probe** actions, sent at startup to check that each slice returns an initial state;
- **other slices' actions**: `listPrefs/sortChanged` goes through `tasksReducer` too;
- in S20+, actions from libraries (RTK Query's internal actions).

Verified with a reducer whose `default` calls `assertNever`:

```text
createStore(strictReducer)                       → throws: Unexpected value: {"type":"@@redux/INITe.t.u.w.a.9"}
createStore(combineReducers({ counter: strict })) → throws: Unexpected value: {"type":"@@redux/INITe.t.u.w.a.9"}
```

The store can't even be created. So in Redux:

> **`default: return state;` is required**, and "the action isn't mine" is normal, not an error.

### Then what does "exhaustive" mean?

You lose the compile error for a **forgotten** case: if you add `tasks/taskArchived` to the union and forget the reducer case, nothing complains. Protections that remain:
- The **tests** (15.11): every action creator has a test that dispatches it and checks the result.
- **Typo protection** (§2): a case can't reference an action type that doesn't exist.
- In S20, `createSlice` generates the action types **from** the reducer cases, so a forgotten case can't happen at all.

(There's a type-level trick to regain the exhaustiveness check: a handler map typed as `Record<TasksAction['type'], …>`. It's essentially what RTK's `createReducer` does. We'll get it for free in S20, so we don't hand-roll it.)

## 4. The action parameter's type: a deliberate half-truth

`action: AppAction` claims the reducer only receives app actions. At runtime it also receives `@@redux/INIT…`. That's acceptable because the `default` branch handles anything unknown, and no `case` could ever match a random internal type. (RTK's own types model this with `UnknownAction` plus type guards. You'll see that in S20.)

## 5. Summary

- `AppAction` = the union of every slice's actions; each reducer takes all of them.
- The union gives typo checks, payload narrowing and precise action creators (`Extract`).
- Never `assertNever` in a Redux reducer's `default`: the store crashes on Redux's init action (verified). Use `default: return state`.
- Forgotten cases are caught by tests now, and are impossible with `createSlice` later.
