# Lecture 15.10 · Reducers and Actions Are Many-to-Many

> **Section:** S15 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> 🔗 Official companion reading: Style Guide: "Allow Many Reducers to Respond to the Same Action"

---

## 1. The idea

Because every slice reducer receives every action (15.08), **any slice can respond to any action**:

```text
              tasks/taskDeleted ──┬──► tasksReducer   (remove the task)
                                  └──► uiReducer      (remove it from the selection)

              auth/loggedOut ─────┬──► tasksReducer   (forget the tasks)
                                  ├──► listPrefsReducer (back to defaults)
                                  └──► uiReducer      (no toasts, no selection)
```

The component dispatches **one** event. It doesn't know, and doesn't need to know, which slices care.

## 2. TaskFlow examples (all tested in the reference app)

In `uiReducer`:

```ts
// ── Other slices' events this slice cares about (15.10) ──────────────────
case 'tasks/taskDeleted':
  return removeFromSelection(state, [action.payload]);
case 'tasks/completedCleared':
  return removeFromSelection(state, action.payload);
case 'auth/loggedOut':
  return initialUiState;
```

Verified with the real store: select tasks 5 and 7, dispatch `taskDeleted(5)`, and the selection is `[7]`. Dispatch `loggedOut()` after changing the sort, page size and toasts, and the whole state equals the initial state.

This is also why `tasks/completedCleared` carries the **ids** (14.13): the `ui` slice doesn't have the tasks, so it couldn't work out which ids were completed. An event's payload should contain what **every** interested slice needs.

## 3. 🛡 Logout must reset user data

`auth/loggedOut` handled everywhere isn't just tidiness. Without it:
1. Bob logs in on a shared computer, and his tasks load into the store.
2. Bob logs out. The SPA doesn't reload the page (12.01), so the store is still in memory.
3. Alice logs in. For a moment, until her fetch returns, the list shows **Bob's** tasks, and the dashboard counts them.

That's a real data-exposure bug in SPAs. Two rules prevent it: every slice with user data resets on `auth/loggedOut` (now), and the server never returns another user's data anyway (the mock's owner check, 13.02; your servlets in S44). In S23 you'll also reset the RTK Query cache on logout.

## 4. The opposite: one reducer, many actions

A single slice obviously handles many actions: `tasksReducer` has eight. So the relationship is **many-to-many**. That's the difference from setters (15.03), where each action is tied to one field of one slice.

## 5. Don't abuse it

- A slice may **react** to another slice's events, but it shouldn't **reach into** another slice's state (reducers only see their own part).
- If you find a slice handling many of another slice's actions, the data may belong in that other slice.
- Keep cross-slice handling for genuine domain relationships (deletion affects selection; logout affects everything).

## 6. Summary

- One action can update several slices; one slice handles many actions.
- Put in the payload what every interested slice needs (ids).
- `auth/loggedOut` resetting every slice with user data is a security requirement in an SPA.
