# Lecture 15.02 · Designing the State Structure: Organise by Feature, Not by Component

> **Section:** S15 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> 🔗 Official companion reading: Fundamentals Part 3 ("Designing the State Structure"); Style Guide: "Structure Files as Feature Folders with Single-File Logic"

---

## 1. The root state is an object of "slices"

```ts
{
  tasks: { … },       // everything about tasks
  listPrefs: { … },   // list preferences
  ui: { … },          // toasts, selection
}
```

Each top-level key is a **slice** of state, owned by **one** slice reducer (15.08). The keys are named after **domain concepts**, not screens: there's no `taskListPage` or `headerState` key. Five screens read `tasks`; one reducer writes it.

## 2. Folder structure: feature folders

The Redux Style Guide recommends grouping by **feature**, with a feature's Redux logic in **one file** (the "slice file", also called the "ducks" pattern in older code):

```text
src/
├── app/
│   ├── app-action.ts          ← the union of every action type (15.07)
│   ├── rootReducer.ts         ← combineReducers({ tasks, listPrefs, ui })
│   └── store.ts               ← S16
├── features/
│   ├── tasks/
│   │   ├── tasksSlice.ts      ← state type, action types, action creators, reducer
│   │   └── tasksSlice.test.ts
│   ├── listPrefs/listPrefsSlice.ts
│   ├── ui/uiSlice.ts
│   └── auth/authActions.ts    ← only the logout event for now; the slice comes in S24
└── (existing: api/, components/, domain/, pages/…)
```

The alternative you'll meet in older codebases is **"folder by type"**: `actions/`, `reducers/`, `constants/`, `selectors/`. Adding one feature then touches four folders, and the action type constants, creators and reducer cases that belong together live apart. Feature folders keep a change in one place.

`createSlice` (S20) is literally named after this idea. Writing slice files by hand now makes S20's migration a straight before/after comparison.

## 3. Nesting: keep it shallow

- **One level of slices, then plain data.** `state.tasks.items`, not `state.data.domain.tasks.list.items`.
- Deep nesting makes immutable updates painful: every level on the path must be copied (14.06 §3).
- Related data that changes together lives together (`items` + `status` + `error` for the same request).

## 4. Summary

- Root state = slices named after domain concepts; one reducer per slice.
- Feature folders with one slice file each (Style Guide), not folders by file type.
- Shallow nesting keeps updates simple.
