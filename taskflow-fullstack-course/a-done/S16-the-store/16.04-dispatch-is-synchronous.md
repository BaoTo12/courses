# Lecture 16.04 · Why `dispatch` Is Synchronous, and What Happens If You Dispatch Inside a Reducer

> **Section:** S16 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> Verified with redux 5.0.1 in Node.

---

## 1. Synchronous, start to finish

```js
store.getState().n;              // 0
store.subscribe(() => log(`listener sees: ${store.getState().n}`));
store.dispatch({ type: 'inc' }); // prints "listener sees: 1" BEFORE dispatch returns
store.getState().n;              // 1
```

Verified output order: `before dispatch: 0` → `listener sees: 1` → `right after dispatch returns: 1`.

Inside `dispatch`: the reducer runs, the state is saved, **every** listener runs, and only then does `dispatch` return. Nothing is queued, batched or deferred by Redux itself.

Why this design?
- **Predictability.** After `dispatch(x)`, the state reflects `x`. Code that dispatches and then reads state (a thunk in S18) can rely on it.
- **Ordering.** Actions are processed strictly one at a time, in dispatch order. There's no "which update wins" race inside the store.
- **Simplicity.** Async behaviour is added **outside** the store, by middleware (thunks, S18), where it can be controlled.

(React may batch the **re-renders** that follow several dispatches in one event handler. That's React's scheduling, S17, not the store's.)

## 2. Dispatching from a listener: allowed, and immediate

A listener may dispatch. The nested dispatch runs **right away**, inside the outer one's notification loop. Verified:

```text
listener sees: 2              ← outer dispatch, listener 1
listener 2 dispatches inc     ← outer dispatch, listener 2 dispatches…
listener sees: 3              ← …the NESTED dispatch notifies listener 1 immediately
final: 3
```

It works, but it's easy to create loops (a listener that always dispatches never ends), and listeners observe intermediate states. In practice, **don't dispatch from `subscribe` listeners**: React components dispatch from event handlers, and follow-up logic belongs in thunks (S18) or the listener middleware (S21).

## 3. Dispatching (or subscribing) inside a reducer: forbidden

| In a reducer you call… | Redux says (verified) |
|---|---|
| `store.dispatch(…)` | *Reducers may not dispatch actions.* |
| `store.getState()` | *You may not call store.getState() while the reducer is executing…* |
| `store.subscribe(…)` | *You may not call store.subscribe() while the reducer is executing…* |

A reducer computes the next state from the **current** state and **one** action. A dispatch from inside would start a second state transition in the middle of the first one: which state would the outer reducer's return value overwrite? Rather than define confusing semantics, Redux forbids it. (Your `createMiniStore` enforces the first two with the same `isDispatching` flag.)

If handling one event should cause another event, **dispatch both from outside** (usually a thunk), or let several slices react to the one event (15.10).

## 4. Summary

- `dispatch` runs the reducer, saves, notifies every listener, and only then returns.
- Listeners may dispatch (it nests immediately), but avoid it.
- Reducers may not dispatch, read the store, or subscribe.
