## 1. ✍️ `src/app/mini-redux/create-mini-store.ts`

```ts
// 16.03: our own createStore, for learning. The app uses Redux's (store.ts).

export interface MiniAction {
  type: string;
}

export type MiniReducer<S, A extends MiniAction> = (state: S | undefined, action: A) => S;

export interface MiniStore<S, A extends MiniAction> {
  getState: () => S;
  dispatch: (action: A) => A;
  /** Returns an unsubscribe function. */
  subscribe: (listener: () => void) => () => void;
}

export function createMiniStore<S, A extends MiniAction>(reducer: MiniReducer<S, A>, preloadedState?: S): MiniStore<S, A> {
  let state = preloadedState;
  let listeners: Array<() => void> = [];
  let isDispatching = false;

  function getState(): S {
    if (isDispatching) throw new Error('You may not call getState() while the reducer is executing.');
    return state as S;
  }

  function subscribe(listener: () => void) {
    listeners = [...listeners, listener]; // a NEW array: a dispatch already notifying keeps its snapshot
    let subscribed = true;
    return () => {
      if (!subscribed) return;
      subscribed = false;
      listeners = listeners.filter((l) => l !== listener);
    };
  }

  function dispatch(action: A): A {
    if (isDispatching) throw new Error('Reducers may not dispatch actions.');
    try {
      isDispatching = true;
      state = reducer(state, action); // 1. compute and SAVE the new state…
    } finally {
      isDispatching = false;
    }
    for (const listener of listeners) listener(); // 2. …THEN notify (the order matters: 16.99)
    return action;
  }

  dispatch({ type: '@@mini/INIT' } as A); // let every reducer produce its initial state
  return { getState, dispatch, subscribe };
}
```

## 2. Walkthrough

- **`state`** starts as the preloaded state (or `undefined`), and the **init dispatch** at the end lets every reducer fill in its initial state. That's why reducers need default parameters (15.15).
- **`isDispatching`** implements two of Redux's guard rails from 14.10: no `dispatch` and no `getState` while a reducer runs. The `try/finally` resets the flag even if a reducer throws, so one bad action can't lock the store forever.
- **`dispatch`** does exactly two things, **in this order**: save the new state, then notify. Swap them, and listeners read the old state (the 16.99 debugging question).
- **Listeners are called with no arguments.** They call `getState()` themselves.
- **`subscribe` creates a new array** instead of `push`ing. A dispatch that is currently looping over the old array isn't affected, so a listener added **during** a notification starts with the **next** dispatch. Redux does the same with a snapshot of its listener map.
- **`unsubscribe` is idempotent**: calling it twice does nothing the second time.

Compare with `node_modules/redux/dist/redux.mjs` (search for `function createStore`). The real one adds: argument validation, the enhancer hand-off (16.05), plain-object and `type` checks on actions (14.10), `replaceReducer`, and the observable interop. The core is the same.

## 3. ✍️ Run it with the S15 reducers

```ts
import { createMiniStore } from './app/mini-redux/create-mini-store';
import { rootReducer } from './app/rootReducer';
import { taskSelectionToggled } from './features/ui/uiSlice';

const store = createMiniStore(rootReducer);
store.subscribe(() => console.log(store.getState().ui.selectedTaskIds));
store.dispatch(taskSelectionToggled(7)); // logs [7]
```

Your reducers don't know or care which store runs them. That's the payoff of pure reducers (14.08).

```ts
describe('createMiniStore (16.03)', () => {
  it('produces the same states as Redux createStore for the same actions', () => {
    const mini = createMiniStore(rootReducer);
    const real = createStore(rootReducer);
    expect(mini.getState()).toEqual(real.getState());

      mini.dispatch(action);
      real.dispatch(action);
      expect(mini.getState()).toEqual(real.getState());
    }
  });

  it('a listener added DURING a notification is not called for that same dispatch', () => {
    const store = createMiniStore(rootReducer);
    const log: string[] = [];
    store.subscribe(() => {
      log.push('first');
      if (log.length === 1) store.subscribe(() => log.push('late'));
    });
    store.dispatch(taskSelectionToggled(1));
    expect(log).toEqual(['first']);
    store.dispatch(taskSelectionToggled(2));
    expect(log).toEqual(['first', 'first', 'late']);
  });
});
```

## 5. A TypeScript snag with Redux 5 and hand-written reducers

When you pass TaskFlow's `rootReducer` from 15.09 to Redux's `createStore` **together with an enhancer** (from 16.06 on), TypeScript fails (verified):

```text
error TS2769: No overload matches this call.
  …Call signature return types '{ tasks: TasksState; listPrefs: ListPrefsState; ui: UiState; }' and
  'Partial<{ tasks: never; listPrefs: never; ui: never; }>' are incompatible.
    The types of 'tasks' are incompatible between these types.
      Type 'TasksState' is not assignable to type 'undefined'.
```

The cause is in `redux.d.ts`: `combineReducers` infers each slice's **preloaded-state** type with a conditional type that expects the slice reducer to accept an `UnknownAction`. Ours accept the narrower `AppAction` (15.07), the conditional fails, and the inferred preloaded type becomes `never` for every slice. Plain `createStore(rootReducer)` happens to compile; the overloads with an enhancer or a preloaded state don't.

The fix is to state the correct type **once**, where the root reducer is defined. ✍️ `src/app/rootReducer.ts` becomes:

```ts
import { combineReducers } from 'redux';
import type { Reducer } from 'redux';
import type { AppAction } from './app-action';
import { tasksReducer } from '../features/tasks/tasksSlice';
import { listPrefsReducer } from '../features/listPrefs/listPrefsSlice';
import { uiReducer } from '../features/ui/uiSlice';

/** Each key of the root state is owned by one slice reducer (15.08). */
const sliceReducers = {
  tasks: tasksReducer,
  listPrefs: listPrefsReducer,
  ui: uiReducer,
};

/** The state type is DERIVED from the reducers: no hand-written interface to keep in sync (06.03). */
export type RootState = { [K in keyof typeof sliceReducers]: ReturnType<(typeof sliceReducers)[K]> };

/**
 * Redux 5's combineReducers infers the PRELOADED-state type only for slice reducers that accept
 * UnknownAction. Ours accept the narrower AppAction, so it infers `never` per slice, and createStore's
 * overloads then reject our own reducer (16.03 §5). We state the correct type once, here. RTK avoids this (S20).
 */
export const rootReducer = combineReducers(sliceReducers) as Reducer<RootState, AppAction, Partial<RootState>>;
```

- `RootState` is still **derived** from the slice reducers (a mapped type over their return types) instead of from the inferred root reducer.
- `as Reducer<…>` is a type assertion: we tell the compiler something it can't infer. Assertions are normally a smell (05.13), so it's contained in one line, with a comment explaining exactly why.
- RTK's `configureStore` and `createSlice` (S20) type slice reducers with `UnknownAction` internally, so this workaround disappears.

It's a good example of a real-world skill: when a library's types and your code disagree, read the library's `.d.ts`, find the exact rule, and make the smallest, documented fix.

## 6. Summary

- A store is ~40 lines: state, listeners, guarded dispatch, init action.
- Save **then** notify; snapshot the listeners; make unsubscribe idempotent.
- Your reducers run unchanged on any store implementation.
- Redux 5's typings need one documented cast for hand-written reducers typed with a closed union.
