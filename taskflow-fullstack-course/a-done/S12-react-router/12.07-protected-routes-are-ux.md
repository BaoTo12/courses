# Lecture 12.07 · 🛡 A Protected Route Is a UX Feature; Open Redirects

> **Section:** S12 · **Type:** 🛡 Defence · **Track:** ★ Core · **Time:** ~30 minutes
> **Security scope:** broken access control (OWASP A01), unvalidated redirects. See `03-security-scope.md`.

---

## 1. The claim

> **`RequireAuth` does not protect any data.** It hides screens from people who aren't logged in. The **server** decides who can read or change what.

This isn't specific to our fake auth. It stays true after S24, when the login is real.

## 2. Why: everything in the browser belongs to the user

The JavaScript bundle is downloaded to the user's machine. They control it completely:

| What the attacker does | Result |
|---|---|
| Opens `dist/assets/*.js` | Reads **every** page's code, including protected pages and every API URL. Code splitting (12.09) doesn't hide anything; the chunk is downloadable by anyone who knows its URL (and the URL is in the main bundle). |
| Sets a breakpoint in `RequireAuth` and changes `user` | The guard lets them through. |
| Uses the React DevTools to edit the `AuthProvider` state | Same. |
| Skips the UI and calls the API with curl | The guard never runs at all. |

So what does the guard give you? **UX**: an anonymous user sees a login page instead of a broken form that fails on save. That's valuable, and it's all it does.

## 3. Where the real protection lives

```text
Browser (untrusted)                    Server (trusted)
─────────────────────                  ──────────────────────────────────────────
RequireAuth → nice redirect            AuthFilter (S41): no session → 401
Hide "Edit" for non-owners             TaskService (S44): not the owner → 403
Client validation (11.08)              Server validation (S37, S46) → 400
```

The rule, which you'll apply on every endpoint in Part 2:
- **Authentication**: "who are you?" Checked on **every** request by a server filter (S41), not once at login.
- **Authorization**: "may *you* do *this* to *that* resource?" Checked on the server, **per object**. `GET /api/tasks/5` must check that task 5 belongs to the session's user. Otherwise any logged-in user can read anyone's task by changing the number. That's **IDOR** (Insecure Direct Object Reference), which you'll attack and fix in S44.

In the SPA, hiding a button the user may not use is still good UX. Just never let it be the *only* check.

### 🔓 Try it now (on your own local app)

1. Log out. Visit `/tasks/new`: you're redirected. Good UX.
2. Open the React DevTools → Components → `AuthProvider` → edit the `user` hook state to any object (or set a breakpoint in `RequireAuth` and run `user = {}` in the console while paused).
3. The "protected" page renders.

Nothing is broken: there was no data to protect, because the fake auth has no server. From S24 on, doing this shows the form, but every API call it makes returns **401**, because the server doesn't know you. That's the correct design.

## 4. The second lesson in this section: open redirects

The login page redirects to `?returnTo=…`, a value **from the URL**. Imagine it didn't validate it:

```tsx
navigate(searchParams.get('returnTo') ?? '/tasks'); // ❌ trusting the URL
```

An attacker sends a phishing email:

```text
Your TaskFlow session expired. Please log in again:
https://taskflow.example/login?returnTo=https://taskf1ow.example/login
```

The victim checks the domain (it's the real TaskFlow), logs in, and is then sent to a fake site that looks identical and says "wrong password, try again". They type their password into the attacker's page. The real site's trustworthy domain was used to launch the attack. That's an **open redirect**.

### 🔬 What React Router 8 does (verified)

In the reference app, calling `navigate('https://example.com')` and `navigate('//example.com')` both **threw an error**: *"External navigation is not allowed"*. So the router blocks this particular attack. Should we skip validation then? **No**, for three reasons:

1. **It throws, it doesn't fall back.** An unvalidated `returnTo` would crash the login handler after `login()` ran. The user is logged in but stuck on the login page with an error. `safeReturnTo` gives a clean fallback.
2. **It covers only `navigate()`.** `window.location.href = returnTo`, `<a href={returnTo}>`, and a server-side `response.sendRedirect(returnTo)` (the JSP login in S41) are **not** protected by React Router.
3. **Library behaviour changes between versions.** Older React Router versions and other routers behave differently. Your security shouldn't depend on an implementation detail of a dependency.

This is **defence in depth**: validate at the point where you use the value, even if a lower layer might catch it.

### `safeReturnTo` explained

```ts
export function safeReturnTo(value: string | null, fallback = '/tasks'): string {
  if (value === null) return fallback;
  if (!value.startsWith('/')) return fallback;                       // https://…, javascript:…, "tasks"
  if (value.startsWith('//') || value.startsWith('/\\')) return fallback; // //evil.example, /\evil.example
  return value;
}
```

| Input | Result | Why |
|---|---|---|
| `null` | `/tasks` | No parameter. |
| `/tasks/5?status=DONE` | `/tasks/5?status=DONE` | App-internal path. |
| `https://evil.example` | `/tasks` | Absolute URL. |
| `javascript:alert(1)` | `/tasks` | A script URL would be XSS if used in `location.href`. |
| `//evil.example` | `/tasks` | **Protocol-relative** URL: the browser treats it as `https://evil.example`. |
| `/\evil.example` | `/tasks` | Browsers normalise `\` to `/` in URLs, so this becomes `//evil.example`. |

This is an **allowlist** approach ("only paths starting with a single `/`"), not a denylist ("block `http`"). Denylists miss cases like `HTTPS://`, `\t//`, and new schemes. Allowlists fail safe. You'll see the same idea on the server in S41, with `request.getContextPath()` prefixes.

## 5. Summary

- A client-side route guard is **UX**. Authentication and authorization happen on the server, on every request, per object.
- Anything in the bundle is public: code, routes, API URLs, lazy chunks.
- `returnTo` is user input. Validate redirects with an **allowlist** of internal paths, even when the router happens to block external URLs.
