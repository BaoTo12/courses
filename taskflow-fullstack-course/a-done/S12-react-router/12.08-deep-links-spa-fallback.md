# Lecture 12.08 · Why Deep Links 404 on a Real Server Without "SPA Fallback"

> **Section:** S12 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> Verified with the reference app's production build (`npm run build`), served two ways (results below).

---

## 1. The experiment

Build the app, then serve `dist/` with a plain static file server:

```bash
npm run build
```

```bash
npx http-server dist -p 5195
```

| Request | Result (verified) |
|---|---|
| `GET /` | **200**: `dist/index.html` exists. The app loads; clicking around works. |
| Click a task → URL `/tasks/5` | Works: client-side navigation, no request (12.01). |
| **Reload** on `/tasks/5` | **404**: the server looks for a file `dist/tasks/5` and there isn't one. |

Now serve the same build with Vite's preview server:

```bash
npx vite preview --port 5196
```

`GET /tasks/5` → **200 `text/html`**: the app loads and shows task 5.

## 2. Why

A static server maps URLs to **files**:

```text
/                    → dist/index.html        ✓
/assets/index-….js   → dist/assets/index-….js ✓
/tasks/5             → dist/tasks/5           ✗ 404
```

But `/tasks/5` isn't a file. It's a route **inside** the JavaScript app. The server has to hand out `index.html`, let React Router read `location.pathname`, and render the right page. That rule is called **SPA fallback** (or "history API fallback"):

> For a `GET` request that doesn't match a real file (and isn't an API call), respond with `index.html`.

The Vite dev server (`npm run dev`) and `vite preview` do this for you. That's why you never saw the problem in development. It only shows up when you deploy, which is why it's such a common production bug.

## 3. The rule has exceptions

A careless fallback ("send `index.html` for **every** 404") causes new bugs:

| Request | Should get | With a careless fallback |
|---|---|---|
| `/tasks/5` (app route) | `index.html` | ✓ |
| `/assets/index-OLD.js` (a file from a previous deploy) | **404** | `index.html` as JavaScript, which fails with *"Unexpected token '<'"* |
| `/api/tasks/999` (API) | **404 JSON** | `index.html` with status 200: the client tries to parse HTML as JSON |
| `POST /tasks/5` | 405 / 404 | `index.html` |

🔬 Verified with `http-server dist --proxy "http://localhost:5195?"`: `/tasks/5` returned **200 `text/html`** (good), but `/assets/index-OLD.js` *also* returned **200 `text/html`** (bad). A browser loading that script would fail with a confusing syntax error instead of a clear 404.

So a correct fallback applies only to:
- `GET` (or `HEAD`) requests,
- that **accept HTML** (`Accept: text/html`, which is what browsers send for navigation),
- whose path **isn't** under `/api/`, and **isn't** a real static file.

## 4. How it's done in different servers

| Server | SPA fallback |
|---|---|
| Vite dev / preview | Built in. But it's a simple fallback too: verified, `vite preview` returned **200 `text/html`** for a missing `/assets/index-OLD.js`. Fine for local testing, not a production server. |
| `http-server` | `--proxy "http://localhost:5195?"` proxies every unknown path back to itself as `/?`, which returns `index.html`. It's a careless fallback (see below). |
| Nginx | `try_files $uri $uri/ /index.html;` |
| **Tomcat (TaskFlow, S49)** | A `SpaFallbackFilter` that forwards matching requests to `/app/index.html`. |

### Preview of S49: the Tomcat filter

In S49, the React build is deployed inside the same WAR as the JSP portal, under `/app/*`. You'll write a servlet filter (filters are taught in S40) whose logic is roughly:

```java
// Sketch only. Full, tested version in S49.
boolean isGet = "GET".equals(request.getMethod());
String path = request.getRequestURI().substring(request.getContextPath().length());
boolean isAsset = path.startsWith("/app/assets/");
boolean acceptsHtml = String.valueOf(request.getHeader("Accept")).contains("text/html");

if (isGet && path.startsWith("/app/") && !isAsset && acceptsHtml) {
  request.getRequestDispatcher("/app/index.html").forward(request, response); // a server-side forward (S33)
  return;
}
chain.doFilter(request, response);
```

It's a **forward**, not a redirect: the URL in the browser stays `/app/tasks/5`, and React Router renders task 5. (Forward vs redirect is a core Servlet topic in S33.)

## 5. Two consequences to remember

1. **The HTTP status is always 200** for app routes, even `/app/nope`. The 404 page is a visual state (12.06 §1).
2. **Set React Router's `basename`** when the app isn't served at `/`. In S49 it's served at `/<context>/app/`, so the router needs `basename="/taskflow/app/"`. Otherwise every route misses. Vite's `base` option must match too, so assets load from the right path. 12.12 shows how to set both from one value (`import.meta.env.BASE_URL`).

## 6. Summary

- Client routes aren't files. A static server returns 404 when a deep link is loaded or refreshed.
- Fix: **SPA fallback**, meaning serve `index.html` for HTML `GET` requests that aren't files or API calls.
- Dev servers hide the problem; production reveals it. TaskFlow fixes it with a Tomcat filter in S49.
