# Lecture 12.06 · 🛠 Build: a 404 Page, Fake Auth, and a `RequireAuth` Wrapper

> **Section:** S12 · **Type:** 🛠 Build · **Track:** ★ Core · **Time:** ~45 minutes
> **Project feature:** a login page, a user in the header, and protected routes (`/tasks/new`, `/tasks/:id/edit`, `/dashboard`)
> Verified in the reference app: `/dashboard` while logged out → `/login?returnTo=%2Fdashboard`; after logging in → `/dashboard`.

---

## 0. ⚠️ Read this first: this auth is FAKE

In this lecture the "logged-in user" is just a `useState` value in the browser. **Nothing about it is secure**. Anyone can open DevTools and set it. We build it now for one reason: to learn the **routing** side of authentication (guards, redirects, `returnTo`). Real authentication comes later:
- **S24:** the client side (session cookie, CSRF token with js-cookie, `/api/auth/me`).
- **S41 and S47:** the server side (a login servlet, `HttpSession`, an auth filter that returns 401).

12.07 explains why even a *real* client-side guard is only a UX feature.

## 1. The 404 page (already done)

You created `NotFoundPage` in 12.02 and used it in three places:
- the `*` route (unknown URLs, such as `/nope/deep`);
- `TaskDetailsPage` and `EditTaskPage` for invalid ids (`/tasks/abc`);
- the same pages for unknown ids (`/tasks/999`).

One more note: the SPA can't send a real **HTTP 404 status** for `/nope`. The server already answered `200 index.html` (12.08). The 404 is only visual. Search engines and monitoring tools see a 200. For TaskFlow (a logged-in app, not a public site) that's fine. Server-rendered JSP pages *can* set real status codes (S35).

## 2. ✍️ `src/auth/auth-context.ts`

The same pattern as `theme-context.ts` and `toast-context.ts` (08.09, 10.07): a context with a `null` default, plus a hook that throws outside the provider.

```ts
import { createContext, useContext } from 'react';
import type { User } from '../domain/types';

export interface AuthContextValue {
  user: User | null;
  /** FAKE for S12: accepts any username. Real login against the API arrives in S24/S48. */
  login: (username: string) => void;
  logout: () => void;
}

export const AuthContext = createContext<AuthContextValue | null>(null);

export function useAuth(): AuthContextValue {
  const context = useContext(AuthContext);
  if (context === null) {
    throw new Error('useAuth must be used inside <AuthProvider>');
  }
  return context;
}
```

`User` is the type from 05.08 (`id`, `username`, `displayName`, `role`, `locale`). The context shape (`user`, `login`, `logout`) stays the same in S24, so the pages written now won't need changes. Only the provider's implementation changes.

## 3. ✍️ `src/auth/AuthProvider.tsx`

```tsx
import { useMemo, useState } from 'react';
import type { ReactNode } from 'react';
import type { User } from '../domain/types';
import { AuthContext } from './auth-context';
import type { AuthContextValue } from './auth-context';

/**
 * ⚠️ FAKE authentication for S12 (routing lessons only). Nothing here is secure:
 * the "user" is just client state. Real sessions come in S24 (client) and S41/S47 (server).
 */
export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);

  const value = useMemo<AuthContextValue>(
    () => ({
      user,
      login: (username) =>
        setUser({ id: 1, username, displayName: username, role: 'USER', locale: 'en' }),
      logout: () => setUser(null),
    }),
    [user],
  );

  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}
```

- **`useMemo`** keeps the `value` object stable while `user` doesn't change. Without it, every render of `AuthProvider` would create a new object, and every `useAuth()` consumer would re-render (08.09 §4, 08.13).
- **The user is not persisted.** A reload logs you out. That's deliberate: storing a fake "logged in" flag in `localStorage` would teach a bad habit (S26 explains why tokens in `localStorage` are an XSS target). In S24, the server's session cookie survives the reload, and the app asks `/api/auth/me` who you are.

Add `<AuthProvider>` to `main.tsx`, **inside** `<BrowserRouter>` and **outside** `<TasksProvider>` (12.02 §3 already shows the final order).

## 4. ✍️ `src/auth/RequireAuth.tsx`: the guard

```tsx
import type { ReactNode } from 'react';
import { Navigate, useLocation } from 'react-router';
import { useAuth } from './auth-context';

/**
 * Redirects anonymous users to /login?returnTo=<current path>.
 * 🛡 This is UX, not security: the data must be protected by the API (12.07).
 */
export function RequireAuth({ children }: { children: ReactNode }) {
  const { user } = useAuth();
  const location = useLocation();

  if (user === null) {
    const returnTo = location.pathname + location.search;
    return <Navigate to={`/login?returnTo=${encodeURIComponent(returnTo)}`} replace />;
  }
  return children;
}
```

Line by line:
- **`<Navigate>` rather than `navigate()`.** Deciding where to go is part of **rendering** ("if anonymous, render a redirect"). Calling `navigate()` during render is a side effect (07.04). `<Navigate>` is a component that performs the navigation in an effect for you.
- **`replace`.** Without it, history would be `/dashboard → /login`. After logging in, pressing Back would return to `/dashboard`, which redirects to `/login` again… With `replace`, `/dashboard` is replaced by `/login`.
- **`returnTo` = pathname + search.** The user asked for `/tasks/new` or `/tasks?status=DONE`, and should land there after logging in, with filters intact.
- **`encodeURIComponent`.** `returnTo` contains `/`, `?` and `&`. Without encoding, `/login?returnTo=/tasks?status=DONE&q=x` would be parsed as two parameters (`returnTo=/tasks?status=DONE` and `q=x`). Encoded, it's one value: `returnTo=%2Ftasks%3Fstatus%3DDONE%26q%3Dx`. `searchParams.get('returnTo')` decodes it for you.
- **`return children`.** In React 19, a component can return a `ReactNode` directly. There's no need for `<>{children}</>`.

### Why a wrapper component and not a check in each page?

Each protected page could start with `if (!user) return <Navigate …/>`. A wrapper keeps the rule in **one** place and makes the route table readable: you can see which routes are protected at a glance. (Another common style is a **layout route**, `<Route element={<RequireAuth />}>`, rendering `<Outlet />`, with protected routes nested inside. Both are fine. We use the wrapper because it's explicit per route.)

## 5. ✍️ `src/domain/safe-redirect.ts`

The login page will navigate to `returnTo`, **a value from the URL**, which anybody can craft. Before using it, validate it (12.07 explains the attack in detail):

```ts
/**
 * 🛡 Open-redirect protection (preview of S24/S41): only allow app-internal paths.
 * Accepts "/tasks/5?x=1". Rejects "https://evil.example", "//evil.example" (protocol-relative),
 * "/\evil.example" (browsers may normalise the backslash to a slash), and anything not starting with "/".
 */
export function safeReturnTo(value: string | null, fallback = '/tasks'): string {
  if (value === null) return fallback;
  if (!value.startsWith('/')) return fallback;
  if (value.startsWith('//') || value.startsWith('/\\')) return fallback;
  return value;
}
```

## 6. ✍️ `src/pages/LoginPage.tsx`

```tsx
import { useState } from 'react';
import type { FormEvent } from 'react';
import { useNavigate, useSearchParams } from 'react-router';
import { useAuth } from '../auth/auth-context';
import { safeReturnTo } from '../domain/safe-redirect';
import { FormField } from '../components/forms/FormField';
import { Button } from '../components/Button';

/** ⚠️ FAKE login for S12: no password, no server. Real authentication arrives in S24/S48. */
export function LoginPage() {
  const { login } = useAuth();
  const navigate = useNavigate();
  const [searchParams] = useSearchParams();
  const [username, setUsername] = useState('');

  function handleSubmit(e: FormEvent<HTMLFormElement>) {
    e.preventDefault();
    if (username.trim() === '') return;
    login(username.trim());
    // 🛡 never navigate to an unvalidated returnTo (open redirect, 12.07 / S24)
    navigate(safeReturnTo(searchParams.get('returnTo')), { replace: true });
  }

  return (
    <>
      <h1 className="page__title">Log in</h1>
      <form className="form" onSubmit={handleSubmit} aria-label="Log in">
        <FormField label="Username" help="Demo only: any name works, no password (see S24).">
          {(control) => (
            <input
              {...control}
              className="form-field__input"
              value={username}
              onChange={(e) => setUsername(e.target.value)}
              autoComplete="username"
            />
          )}
        </FormField>
        <div className="form__actions">
          <Button type="submit" variant="primary">
            Log in
          </Button>
        </div>
      </form>
    </>
  );
}
```

- **`login()` then `navigate()` in the same handler.** `setUser` is batched, so by the time the router renders `/dashboard`, `user` is set, and `RequireAuth` lets it through. (If the navigation ran *before* the state update committed, `RequireAuth` would bounce you straight back to login. React 18+ batching avoids that here.)
- **`replace: true`**: after login, Back shouldn't return to the login form (the PRG idea again, 12.05).
- **`autoComplete="username"`** helps password managers. In S24 you'll add a `password` field with `autoComplete="current-password"`.

## 7. ✍️ The header shows who's logged in (`AppLayout.tsx`)

```tsx
import { NavLink, Outlet, useNavigate } from 'react-router';
import { ThemeToggle } from '../components/ThemeToggle';
import { Avatar } from '../components/styled/Avatar';
import { Stack } from '../components/styled/Stack';
import { Button } from '../components/Button';
import { useAuth } from '../auth/auth-context';

/** NavLink passes { isActive } so the active link gets the design system's modifier class. */
const navClass = ({ isActive }: { isActive: boolean }) =>
  `page__nav-link${isActive ? ' page__nav-link--active' : ''}`;

/** The shell shared by every page: header + nav, the current page (<Outlet/>), footer. */
export function AppLayout() {
  const { user, logout } = useAuth();
  const navigate = useNavigate();

  function handleLogout() {
    logout();
    navigate('/tasks', { replace: true });
  }

  return (
    <div className="page">
      <header className="page__header">
        <span className="page__brand">TaskFlow</span>
        <nav className="page__nav" aria-label="Main">
          <NavLink className={navClass} to="/tasks">
            Tasks
          </NavLink>
          <NavLink className={navClass} to="/dashboard">
            Dashboard
          </NavLink>
        </nav>
        <Stack $direction="row" $gap={3} $align="center" style={{ marginLeft: 'auto' }}>
          <ThemeToggle />
          {user ? (
            <>
              <Avatar name={user.displayName} size="sm" />
              <Button size="sm" onClick={handleLogout}>
                Log out
              </Button>
            </>
          ) : (
            <NavLink className={navClass} to="/login">
              Log in
            </NavLink>
          )}
        </Stack>
      </header>
      <main className="page__main">
        <Outlet />
      </main>
      <footer className="page__footer">TaskFlow Web</footer>
    </div>
  );
}
```

**Why navigate after logout?** If you log out while on `/dashboard`, `RequireAuth` would redirect to `/login?returnTo=%2Fdashboard`. Correct, but odd UX: you just chose to leave. Sending the user to the public list is clearer. (With a real server, logout is also a `POST /api/auth/logout` that invalidates the session, S41.)

The `Avatar` component comes from 09.09. Its colour is derived from a hash of the name, so every user gets a stable colour.

```tsx
  path="tasks/:id/edit"
  element={

```

The dashboard route is added in 12.09 (lazy-loaded, also inside `RequireAuth`).

**Design decision: reading is public, writing requires login.** That's a product choice for TaskFlow's demo. In the real app (S24 onward), the API requires a session for *all* task endpoints, and the list page will be protected too.

## 9. Try it

| Action | Expected |
|---|---|
| Logged out, click "+ New task" | URL becomes `/login?returnTo=%2Ftasks%2Fnew`. |
| Log in as `alice` | You land on `/tasks/new`. The header shows the "A" avatar and "Log out". |
| Press Back | You go to `/tasks` (the login page was replaced, and so was `/tasks/new`'s redirect). |
| Log out on `/tasks/new` | You're sent to `/tasks`. |
| Visit `/login?returnTo=https://evil.example` and log in | You land on `/tasks` (fallback), **not** on the external site. |
| Reload while logged in | You're logged out (the fake user isn't persisted, §3). |
