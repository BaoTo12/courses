## B. Code reading

6. Given this reducer, write the state after the first three actions, and then after all six. [14.07]
   ```js
   const initialState = { items: [], nextHint: 'add something' };
   function reducer(state = initialState, action) {
     switch (action.type) {
       case 'todos/added':
         return { ...state, items: [...state.items, { text: action.payload, done: false }] };
       case 'todos/toggled':
         return { ...state, items: state.items.map((t, i) => (i === action.payload ? { ...t, done: !t.done } : t)) };
       case 'todos/cleared':
         return { ...state, items: state.items.filter((t) => !t.done) };
       default:
         return state;
     }
   }
   // dispatched in order:
   // { type: 'todos/added', payload: 'Buy milk' }
   // { type: 'todos/added', payload: 'Call Bob' }
   // { type: 'todos/toggled', payload: 0 }
   // { type: 'todos/cleared' }
   // { type: 'todos/renamed', payload: 'x' }
   // { type: 'todos/unknown' }
   ```

<details>
<summary><b>Answers</b></summary>

1. Click → `dispatch` → the reducer runs → the store saves the new state → subscribers are notified → the UI re-reads state (and re-renders if its data changed).

2. Redux and React-Redux detect changes by **reference** (`===`). A mutated object keeps its reference. Verified: after a mutating reducer ran, `before === store.getState()` was `true`. Breaks: (a) `useSelector` thinks nothing changed, so there's no re-render; (b) memoised selectors return stale results; (c) the DevTools history is corrupted (old states were modified in place), so time travel and diffs lie. Also, tests that compare before/after can pass by accident.

3. **Single source of truth**: one store for shared state, so there's one place to inspect, serialise or restore. **State is read-only**: changes only through actions, so every change is centralised, ordered and loggable. **Pure reducers**: deterministic updates, so they're easy to test, and replay/time travel is exact.

4. **Context** passes a value down the tree (dependency injection); every consumer re-renders when the value changes. **Redux** manages state, and components subscribe to the parts they select. React-Redux puts only the **store object** in context, and the store reference never changes, so context never triggers re-renders. Updates reach components through store **subscriptions** plus `===` checks on selected values (S17).

5. Not broken: it works and logs nothing at runtime (verified). The `@deprecated` tag nudges application code towards RTK's `configureStore`. `legacy_createStore` is the same function without the strikethrough. We use it deliberately to learn how Redux works underneath, following the official Fundamentals tutorial, and switch in S20.

6. After three actions (verified by running it):
   ```json
   { "items": [{ "text": "Buy milk", "done": true }, { "text": "Call Bob", "done": false }], "nextHint": "add something" }
   ```
   After six: `{ "items": [{ "text": "Call Bob", "done": false }], "nextHint": "add something" }`. `todos/renamed` and `todos/unknown` hit `default` and return the **same** state object (verified: `store.getState() === s5` stayed `true`). The initial state object was never modified.

7. (a) Not an object. It throws *"Actions must be plain objects. Instead, the actual type was: 'string'…"*. (b) A **setter**, not an event, and not `domain/eventName`: it doesn't say what happened (14.07, 14.13). (c) `new Date()` isn't serialisable: store `'2026-10-03T09:30:00Z'` (a string). Also, a generated value like `createdAt` belongs in the action creator, which is fine here; just not as a `Date`. (d) No `type`: *"Actions may not have an undefined "type" property…"*.

8. Subscribers are called with **no arguments**: they don't know which action caused the change. Middleware (S16) sees every action as it passes through `dispatch`. A logger is the classic first middleware (16.08).

9. Browsers refuse to load ES modules from `file://` (the page's origin is `null`). Serve the folder over HTTP: `npx http-server -c-1`.

10. You're using the **production** build (`redux.browser.mjs`), where messages are replaced by codes to save bytes. Open the URL for the message, or import the development build (`redux.mjs`) with `process.env.NODE_ENV` defined as `'development'`. A bundler (Vite) chooses automatically.

11. A reducer **mutates** state: the "old" states in the history are the same objects that were later modified.

12. Status filter → **URL** (shareable, survives reload: S12). Search text while typing → **URL** with `replace` (plus a local debounced copy). Logged-in user → **Redux**. Modal open → **local**. Task list → **Redux** (or the RTK Query cache from S22).

13. **Ids, not copies:** copies go stale when the task changes, and the selection would show old titles. **Array, not `Set`:** state must be serialisable for the DevTools, persistence and time travel. A `Set` doesn't survive `JSON.stringify` (it becomes `{}`).

14. Convert in the **handler** (UI code): `Number(stepInput.value)`, and validate it (`Number.isFinite`, > 0) before dispatching. The action should carry a clean `number`: actions describe events in domain terms, not raw DOM strings. The reducer must stay a pure "how state changes", without parsing or input validation that belongs to the UI. The reducer additions:
    ```js
    case 'counter/reset':
      return initialState;
    ```
    `+`: `dispatch(incrementedBy(step))`; `−`: `dispatch(incrementedBy(-step))`. Returning `initialState` itself is fine: it's never mutated.

</details>
