# Lecture 14.03 · When to Use Redux, and When Not To

> **Section:** S14 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes
> 🔗 Official companion reading: Essentials Part 1 ("When Should I Use Redux?"); the Redux FAQ, "Organizing State"; the Style Guide rule on form state

---

## 1. Four kinds of state, four homes

Most state-management debates dissolve once you classify the state:

| Kind | Examples in TaskFlow | Best home |
|---|---|---|
| **Local UI state**: one component cares | Inline title draft (08.16), "is this dropdown open", form values while typing (S11) | `useState` / `useReducer` in the component |
| **URL state**: should survive reload, be shareable | Status filter, search text, view mode, current task id (S12) | The URL (`useSearchParams`, route params) |
| **Server state**: a *cache* of data owned by the backend | Tasks, categories, comments, stats | A server-cache tool (**RTK Query**, S22) or Redux with thunks (S18) |
| **Global client state**: app-wide, not from the server | Logged-in user, theme, toasts, "which tasks are selected for a bulk action" | **Redux** (or context, if small and rarely changing) |

Redux is one tool among four, not the default home for everything.

## 2. Redux is worth it when…

(Paraphrasing the official guidance.)

- **Lots of state** is needed in **many places** of the app.
- That state **changes frequently**.
- The **update logic is complex** (many events affect the same data; ordering matters).
- The codebase is **medium or large**, with **many people** working on it.
- You want to see **how state changed over time** (debugging, auditing, bug reports).

TaskFlow ticks enough of these boxes by S17: tasks, categories, filters, the user and toasts are read by many components and changed by many events.

## 3. …and not worth it when

- The app is small, or the state is mostly **local**.
- The only "global" data is **server data** that you fetch and display. A server-cache tool (RTK Query, TanStack Query) handles caching, loading and invalidation better than hand-written reducers.
- The shared state is **small and rarely changes** (theme, locale, the current user). **Context** is enough (you did exactly this for the theme in S10).

### Context is not a Redux replacement, and Redux is not a context replacement

They solve different problems:
- **Context** is a **dependency-injection** mechanism: it passes a value down the tree. It doesn't manage state; `useState`/`useReducer` in a provider does. When the value changes, **every** consumer re-renders (08.09 §4).
- **Redux** is a **state container** with a subscription model: components subscribe to the **slice** they read and re-render only when that slice changes (S17). React-Redux uses context only to pass the **store** (which never changes), not the state.

## 4. What does NOT belong in Redux, even in a Redux app

- **Form drafts while typing.** The Style Guide recommends keeping form state local, and dispatching only the **submitted** result. Every keystroke in a global store means work for every subscriber, and nobody else needs a half-typed title. (11.99 Q9 already hinted at this.)
- **Non-serialisable values**: DOM nodes, class instances, promises, functions, `Map`/`Set`, `Date` objects. They break DevTools, persistence and time travel. Store `'2026-10-03'`, not `new Date(…)`.
- **Derived data**: filtered lists, counts, totals. Store the minimum, and **compute** the rest with selectors (S21). Storing both creates two sources of truth that can disagree (08.05's rule, again).
- **URL state**: if the URL is the source of truth (S12), don't copy it into Redux. You'd have two sources of truth again.

## 5. TaskFlow's plan

| Data | Home | Section |
|---|---|---|
| Tasks, categories | Redux slices loaded with thunks (S18), later RTK Query (S22) | S17–S23 |
| Filters | The URL stays the source of truth for the list (S12). Redux holds only filter *preferences* that aren't in the URL (e.g. the default sort) | S15, S21 |
| Current user | Redux (`auth` slice) | S24 |
| Toasts | Redux (`ui` slice), replacing the S10 context's own state | S18 |
| Theme | Stays in context: small and rarely changes | — |
| Form drafts | Stay in `TaskForm` | — |

You'll justify each choice yourself in the 14.12 exercise.

## 6. Summary

- Classify state first: local, URL, server cache, global client state.
- Redux fits frequently changing global state with complex update logic, in larger apps and teams.
- Keep form drafts, derived data, URL state and non-serialisable values **out** of Redux.
- Context passes values; Redux manages state with fine-grained subscriptions.
