# Lecture 14.05 · State Management: the One-Way Data Flow Cycle

> **Section:** S14 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~15 minutes
> 🔗 Official companion reading: Fundamentals Part 2 / Essentials Part 1 ("State Management")

## 1. Three parts of every interactive piece of UI

Take the counter you'll build in 14.10:

```tsx
function Counter() {
  const [count, setCount] = useState(0);            // STATE: the source of truth
  return (
    <div>
      <output>{count}</output>                        {/* VIEW: a description of the UI for the current state */}
      <button onClick={() => setCount(count + 1)}>+</button>   {/* ACTIONS: events that update state */}
    </div>
  );
}
```

- **State**: the data that drives the app.
- **View**: the UI, derived from the state (07.04: render is a pure function of state).
- **Actions**: events (user input, a timer, a response) that update the state.

## 2. The cycle

```text
        ┌──────────────► VIEW ───────────────┐
        │  (render from state)               │ user clicks "+"
        │                                    ▼
      STATE ◄──────── update ──────────── ACTION
```

Data flows **one way**: state → view → action → new state → view… The view never modifies state directly; it only reports events. This is **one-way data flow**, the same principle React is built on (props go down, events go up, 07.13).

## 3. When many components share the state

Inside one component, the cycle is easy. The trouble starts when **several components** in different parts of the tree need the same state. The React answer is **lifting state up** (07.13) to a common ancestor and passing it down as props. With enough sharing, that means lifting to the root and **prop drilling** through components that don't care (07.14), or a context whose every change re-renders every consumer (08.09).

Redux's answer: take the shared state **out of the component tree** entirely, into one central place. Any component can read it or dispatch actions, wherever it is in the tree. The tree becomes "one big view", and the one-way cycle stays exactly the same:

```text
   store state ──► any component reads what it needs (subscribes)
        ▲                          │
        │                          ▼  user event
     reducer ◄──── dispatch(action) from any component
```

Redux adds rules on **how** the central state may change (14.08), which is what keeps this predictable at scale.

## 4. Summary

- State → view → action → state: one-way data flow.
- Sharing state across a big tree is the hard part: lifting, drilling, context.
- Redux moves shared state outside the tree, keeping the one-way cycle and adding rules for changes.
