# Lecture 14.09 · Redux Data Flow, Step by Step

> **Section:** S14 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> 🔗 Official companion reading: Fundamentals Part 2 / Essentials Part 1 ("Redux Application Data Flow")

---

## 1. Initial setup

1. A store is created with a **root reducer**.
2. The store calls the reducer once, with `state = undefined` and an internal init action. The reducer returns its **initial state**, which the store saves.
3. The UI renders for the first time: components read the state they need.
4. Components **subscribe** to store updates, to know when to re-render.

## 2. The update cycle

Taking TaskFlow's "Mark done" button once it's on Redux (S17):

```text
 ① click "Mark done" on task 5
        │
 ② handler:  dispatch({ type: 'tasks/taskCompleted', payload: 5 })        (in S18: a thunk that calls the API first)
        │
 ③ store runs:  newState = rootReducer(oldState, action)
        │         └─ tasksReducer returns a new tasks slice (task 5 copied with status 'DONE')
        │         └─ other slices return their existing state (same references)
 ④ store saves newState
        │
 ⑤ store notifies every subscriber
        │
 ⑥ each subscribed component re-reads its data (selectors) and compares with its previous value
        │         └─ changed → re-render (task 5's card, the "N open" badge)
        │         └─ unchanged → skip (the theme toggle, the category sidebar)
 ⑦ the UI shows the new state
```

Two details worth noticing:
- **Step ⑤ notifies everyone**, and **step ⑥ filters**. The store doesn't know which components care. Each subscriber checks its own data. React-Redux's `useSelector` does step ⑥ with a `===` comparison (S17), which is why immutability (14.06) is essential: a mutated slice looks "unchanged".
- **Steps ② to ⑤ are synchronous.** When `dispatch` returns, the reducer has run and the subscribers have been called. Async work (the API call) happens **before** or **after** dispatching, in middleware or thunks (S16, S18), never inside the reducer.

## 3. Compare with TaskFlow's current setup

| Step | Today (`useReducer` in `TasksProvider`) | With Redux (S17) |
|---|---|---|
| Where state lives | Inside a React component | In the store, outside React |
| Who re-renders on change | **Every** consumer of `TasksContext` | Only components whose selected data changed |
| Async | Inside `useTasks` callbacks | Thunks (S18), then RTK Query (S22) |
| Inspecting history | `console.log` | DevTools: action log, diffs, time travel |

## 4. Summary

- Setup: the reducer produces the initial state; the UI renders and subscribes.
- Update: event → dispatch → reducer → save → notify → components compare → re-render only what changed.
- Dispatch is synchronous; async work lives outside reducers.
