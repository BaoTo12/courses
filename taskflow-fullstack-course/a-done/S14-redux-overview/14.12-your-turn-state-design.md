## 1. The task

Before writing any Redux code (S15), design it on paper, the way you would at work before a refactor.

### Part A: classify every piece of data

For each item below, choose **one** home and justify it in one sentence: **Redux**, **local component state**, **URL**, or **context**. (Use 14.03.)

1. The list of tasks loaded from the API
2. The loading/error status of that list
3. The categories
4. The status filter on the list page
5. The search text while the user is typing
6. The logged-in user
7. The light/dark theme
8. Toast notifications
9. The values of the task form while typing
10. "Is the delete-confirmation dialog open"
11. The set of task ids selected with checkboxes for a bulk action ("complete 5 tasks")
12. The number of open tasks shown in a header badge
13. The id of the task shown on `/tasks/5`
14. The UI language (English/Vietnamese, S25)

### Part B: the state tree

Write the `RootState` shape for the data you placed in Redux, as a TypeScript interface (you know how from S05/S06). Decide:
- how the tasks are stored: an array, or something else? (Think about "update task 17" and "show task 17" with 500 tasks.)
- where loading status and errors live;
- which values are **derived** and must **not** be stored.

### Part C: 12 actions as past-tense events

List 12 actions for TaskFlow in the form:

```text
type                      payload                      dispatched when…                    handled by (slices)
tasks/taskCompleted       taskId: number               the server confirmed the PATCH      tasks
```

Rules:
- `domain/eventName`, **past tense**, describing what **happened**, not "set X" commands (14.07).
- At least one action handled by **more than one** slice (hint: logging out).
- At least three actions for the **async lifecycle** of loading tasks.
- No action whose payload is a whole new state ("`tasks/tasksSet`"-style setters are what we're avoiding).

## 2. Hints

<details>
<summary>Hint 1: arrays vs lookup tables</summary>

With an array, "find task 17" is a scan, and updating it means mapping the whole array. A **lookup table** (`Record<number, Task>`) plus an **ordered list of ids** gives direct access and keeps the order. Redux calls this **normalised** state (S19, and RTK's `createEntityAdapter` in S21).
</details>

<details>
<summary>Hint 2: what's derived?</summary>

If you can compute it from other state in a selector, don't store it: the count of open tasks, the filtered list, "are all tasks done".
</details>

<details>
<summary>Hint 3: the async lifecycle</summary>

A request has a start, a success and a failure. Name them as events (`…/fetchStarted`…). RTK's `createAsyncThunk` generates exactly this trio (`pending`/`fulfilled`/`rejected`) in S20.
</details>

## 3. Acceptance checklist

- [ ] Every one of the 14 items has a home and a reason.
- [ ] No derived data, form drafts or URL state in `RootState`.
- [ ] Everything in `RootState` is serialisable (no `Date`, `Map`, functions).
- [ ] 12 actions, all past-tense events, with at least one handled by several slices.
