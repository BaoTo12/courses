# Lecture 07.11 · Lists and Keys: What Reconciliation Does with `key`, and Why Index Keys Break

> **Section:** S07 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> 🔗 Official reading: react.dev → Learn → "Rendering Lists"

---

## 1. Rendering a list

```tsx
<div className="task-grid">
  {tasks.map((task) => (
    <TaskCard key={task.id} task={task} onToggle={onToggle} />
  ))}
</div>
```

`map` turns data into an array of elements (04.07), and React renders arrays of elements. Each item needs a **`key`**.

Without it, React warns in the console: `Each child in a list should have a unique "key" prop.`

## 2. What `key` is for

Between renders, React must match **old** children with **new** children to decide what to update, move, create or destroy (07.04). By position alone, it can't tell whether you **inserted** an item at the top (everything shifts) or **changed** every item.

`key` gives each child a **stable identity**:

```text
Render 1:  [key=1 "Write report"] [key=2 "Fix bug"] [key=3 "Plan offsite"]
Render 2:  [key=7 "NEW"] [key=1 "Write report"] [key=2 "Fix bug"] [key=3 "Plan offsite"]

React: key 7 is new → create one card. Keys 1,2,3 exist → keep their instances (and state) and just move them.
```

- Keys must be **unique among siblings** (not globally) and **stable** across renders.
- `key` is **not a prop**: the child can't read `props.key`. It's for React's bookkeeping.
- The best key is the data's **ID** from the database (`task.id`).

## 3. Why index keys break

```tsx
{tasks.map((task, index) => <TaskRow key={index} task={task} />)}
```

Index keys identify the **position**, not the **item**. Delete the first task:

```text
Before: key=0 → task A (row has an input with draft text "a…")
        key=1 → task B (input "b…")
After:  key=0 → task B    ← React thinks "item 0 still exists, its props changed"
```

React **reuses** instance 0 (with its state and DOM, including the input's typed text) for task B. Result: the draft text, focus, checkbox state or animation of A appears on B's row. You'll reproduce this in 07.18.

Index keys are acceptable **only** if the list never reorders, never filters, never inserts/deletes in the middle, and items have no state. When in doubt, use an ID.

### Never generate keys during render

```tsx
<TaskCard key={Math.random()} … />   // ❌ new key every render → every card destroyed and recreated
<TaskCard key={crypto.randomUUID()} … />   // ❌ same problem
```

That throws away all state and DOM on every render. If data has no ID, create IDs **once** when the data is created (e.g. `nanoid()` in an action creator, S19), not while rendering.

## 4. Keys can reset state on purpose

Because a new key means "a different item", changing a component's key **resets** it:

```tsx
<TaskEditor key={selectedTask.id} task={selectedTask} />
```

Switching tasks gives a fresh editor with fresh form state, instead of leftover state from the previous task. This is a common, legitimate trick.

## 5. Summary

- Lists: `array.map(item => <X key={item.id} … />)`.
- Keys give children identity so React can keep, move, create or destroy the right instances.
- Use stable, unique IDs; avoid index keys for dynamic lists; never random keys.
- Changing a key intentionally resets a component.
