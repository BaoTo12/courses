# Lecture 09.01 · CSS-in-JS: the Problem It Solves and What It Costs

> **Section:** S09 · styled-components Fundamentals

> 🔗 Official reading afterwards: styled-components.com/docs/basics

## 1. Where SCSS gets awkward

SCSS (S02–S03) is excellent for a **shared, mostly static** design system. But some styles depend on **values known only at runtime, per component instance**:

- A priority bar whose **number of filled segments and colour** depend on `task.priority`.
- An avatar whose **size** is a prop and whose **background colour** is computed from the user's name.
- A progress ring whose **stroke offset** is computed from "tasks done / total".
- A category tag whose colour comes **from the API**.

With SCSS you'd write a modifier class for every possible value (impossible for continuous values), or fall back to inline `style={{…}}` (no pseudo-classes, no media queries, no hover). CSS custom properties help (`style={{ '--size': '32px' }}`), but the styling logic then lives in two places.

## 2. What CSS-in-JS is

**CSS-in-JS** means writing styles **in JavaScript/TypeScript, next to the component**, with access to props and JS logic. styled-components is the most widely used library of this kind (alongside Emotion; newer "zero-runtime" options such as vanilla-extract or Panda compile to static CSS instead).

```tsx
const Segment = styled.span<{ $filled: boolean; $color: string }>`
  flex: 1;
  border-radius: 999px;
  background: ${({ $filled, $color }) => ($filled ? $color : 'var(--color-border)')};
`;
```

## 3. What it solves

| Benefit | What it means |
|---|---|
| **Co-location** | Component markup, logic and styles in one file; delete the component, the styles go too (no dead CSS) |
| **Automatic scoping** | Generated class names; no naming conventions needed |
| **Dynamic styles from props** | `${(p) => …}` interpolations with full JS power |
| **Typed style API** | Props like `$size: 'sm' \| 'md'` are type-checked |
| **Theming** | A `ThemeProvider` injects a theme into every styled component (S10) |

## 4. What it costs

| Cost | Detail |
|---|---|
| **Runtime work** | styled-components computes CSS **in the browser** while rendering, hashes it, and injects `<style>` rules. SCSS did all of that at build time (02.02). |
| **Bundle size** | In TaskFlow's reference build, adding styled-components increased the JS bundle from about 70 kB to about 84 kB gzipped. |
| **Server rendering / React Server Components** | Runtime CSS-in-JS needs extra setup for SSR and doesn't work in React Server Components (not relevant for our SPA, but relevant to the wider ecosystem). |
| **Can't be shared with non-React clients** | The JSP portal can't use it. Styles exist only inside the React bundle (10.08). |

This is the same **compile time vs runtime** trade-off you've seen with Sass variables vs CSS custom properties (02.04) and JSP vs React (00.04).

## 5. TaskFlow's decision (from 07.06, now complete)

| Kind of style | Tool |
|---|---|
| Shared components used by React **and** JSP (button, badge, card, form, layout) | Global SCSS (BEM) |
| React-only static structure (toolbars, board columns) | CSS Modules |
| React-only **dynamic, prop-driven** components (priority bar, avatar, progress ring, tags, layout primitives) | **styled-components** |

Many real teams run exactly this mix: SCSS for the design system, styled-components for dynamic component styling. S10 shows how both read **the same design tokens**, so a theme change affects everything.

## 6. Summary

- CSS-in-JS co-locates styles with components and makes prop-driven styles natural.
- styled-components computes CSS at **runtime**, costing bundle size and CPU, and it's React-only.
- TaskFlow uses SCSS for shared components, CSS Modules for static React structure, and styled-components for dynamic components.
