# Lecture 19.05 · Normalised State: `{ ids, entities }`; Lookups, Updates, No Duplication

> **Section:** S19 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes
> 🔗 Official companion reading: Fundamentals Part 7 ("Normalized State"); the Redux docs page "Normalizing State Shape"; Style Guide: "Normalize Complex Nested/Relational State"

## 1. The array version and its costs

Until now, `state.tasks.items` was an array:

| Operation | Array | Cost |
|---|---|---|
| "Show task 17" | `items.find((t) => t.id === 17)` | Scan: O(n) |
| "Update task 17" | `items.map((t) => (t.id === 17 ? updated : t))` | Scan + a **new array** of n references |
| "Delete task 17" | `items.filter(…)` | Scan + new array |
| "Does task 17 exist?" | `items.some(…)` | Scan |

For 22 tasks, none of this matters. For thousands, or for code that looks items up in loops ("the category of each task", "the tasks of each category"), it adds up. And every update produces a **new array**, which changes the reference of "the list" even when only one task's title changed (17.10).

## 2. The normalised version

```ts
interface Normalized<T> {
  ids: number[];                 // the ORDER (as the server sent it, or as sorted)
  entities: Record<number, T>;   // each item ONCE, keyed by id
}
```

```json
{
  "ids": [1, 2, 3],
  "entities": {
    "1": { "id": 1, "title": "Write quarterly report", "categoryId": 1 },
    "2": { "id": 2, "title": "Fix login redirect bug", "categoryId": 2 },
    "3": { "id": 3, "title": "Plan team offsite", "categoryId": 3 }
  }
}
```

| Operation | Normalised |
|---|---|
| "Show task 17" | `entities[17]`: O(1) |
| "Update task 17" | `{ ...entities, 17: updated }`: `ids` **unchanged** (same reference) |
| "Delete task 17" | filter `ids` + remove the key from `entities` |
| "Does task 17 exist?" | `17 in entities` / `entities[17] !== undefined` |
| "The list in order" | `ids.map((id) => entities[id])`: memoise it (19.02) |

## 3. The principles (the official "Normalizing State Shape" rules)

1. **Each type of data gets its own "table"** in state: `tasks`, `categories` (and in the real app `users`, `comments`).
2. **Each item is stored once**, in `entities`, keyed by id.
3. **Other items refer to it by id** (`task.categoryId`), never by embedding a copy (19.07, 19.13).
4. **An array of ids gives the order.**

It's database thinking applied to client state. The API already sends data this way: `Task.categoryId` is a foreign key, and categories come from their own endpoint. TaskFlow's MySQL schema in Part 2 has the same shape: a tasks table with a foreign key to categories (`02-project-spec.md` §2).

## 4. When it's overkill

- Small lists that are always shown whole and rarely updated individually.
- Data that's never looked up by id and has no relations.
- Server data managed by RTK Query (S22), which caches responses by request: you normalise there only when you need to (it's optional).

TaskFlow normalises `tasks` (looked up by id on every details, edit and card render; updated one at a time) and `categories` (looked up by id from every card). `ui.toasts` stays an array: few, short-lived, always rendered whole.

## 5. Summary

- `{ ids, entities }`: order + O(1) lookup; each item stored once.
- Updates touch one entity and leave `ids` alone, which makes stable references (and fewer re-renders) easy.
- Relations are ids, joined in selectors.
- Don't normalise what's small, unrelated and rendered whole.
