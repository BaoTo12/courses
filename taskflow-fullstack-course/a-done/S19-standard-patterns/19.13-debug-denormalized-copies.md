# Lecture 19.13 · 🐞 Debug: After Renaming a Category, Three Tasks Show the Old Name (Denormalised Copies)

> **Section:** S19 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~20 minutes
> Reproduced with a two-slice Redux store in Node (the bug); the fix was verified in TaskFlow's browser app (19.07).

---

## Symptom

A teammate adds "rename category" to an admin screen. The rename succeeds on the server, and the category sidebar shows the new name "Office". But three task cards still say **"Work"** until the page is reloaded.

Their tasks slice, written "to avoid a lookup on every card":

```ts
// when tasks arrive, embed the category name for convenience
case 'tasks/fetchSucceeded':
  return {
    ...state,
    items: action.payload.tasks.map((t) => ({ ...t, categoryName: categoriesById[t.categoryId]?.name })),
  };
```

Reproduced: after dispatching `categories/renamed` (id 1 → "Office"), the store contained:

```json
{ "sidebar": ["Office", "Personal"],
  "cards":   ["Write report [Work]", "Fix bug [Work]", "Plan offsite [Work]", "Dentist [Personal]"] }
```

## Investigation checklist

1. How many places in the state hold the name of category 1? (19.05, principle 2)
2. Which reducer handled `categories/renamed`? Which state did it update?
3. Should the tasks reducer handle `categories/renamed` too? What else would then need to handle it?
4. Where does TaskFlow's real app get the category name for a card? (19.07)

## Explanation

The data was **denormalised**: the category name was copied into every task. After the rename, the state contains **four** copies of "the name of category 1": one in `categories` (updated) and three in `tasks` (stale). Two sources of truth, and they disagree.

(It also read `categoriesById` from outside the reducer, which is another rule broken: reducers compute only from `state` and `action`, 15.04.)

Patching it ("make `tasksReducer` also handle `categories/renamed` and rewrite `categoryName` in every task") works for renames, but every future change to categories (recolouring, merging, deleting) needs the same patch in **every** slice holding a copy. The bug class remains.

## Fix: store the id, join when reading

- Tasks keep only `categoryId` (as the API sends them).
- Components join at read time: TaskFlow's `TaskCategoryTag` selects `selectCategoryById(state, task.categoryId)`: an O(1) lookup (19.07).
- Lists that need joined data use a memoised selector producing view models (19.07 §3).

Verified in TaskFlow: renaming category 1 in the store changed **all 5** "Work" tags and the sidebar at once, because there was only one copy of the name.

## Lessons

- Every copy of a value is a chance for it to be stale. Store each fact once (normalise), reference it by id.
- "Avoid a lookup" isn't a reason to copy: lookups by id are O(1).
- If data must be denormalised (for example, a server response you can't change), normalise it on arrival.
