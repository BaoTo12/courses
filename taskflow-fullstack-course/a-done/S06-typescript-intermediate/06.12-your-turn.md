## 1. Tasks

### A. `groupBy<T, K extends keyof T>(items: readonly T[], key: K)`

In `src/generic-utils.ts`, write a generic `groupBy` that groups **any** objects by the value of **any** of their properties.

```ts
groupBy(tasks, 'priority');     // groups keyed by Priority values
groupBy(tasks, 'categoryId');   // groups keyed by number | null
groupBy(tasks, 'nope');         // ❌ must not compile
```

Decide the return type yourself. Two candidates:
- `Record<…, T[]>`: but can a property value like `null` or a number be a record key? What happens to key types?
- `Map<T[K], T[]>`: keys can be any value (including `null`) and keep their type.

Justify your choice in a comment. Groups should appear in **first-seen order**, and a key only exists if at least one item has that value.

### B. `statusLabel(status: TaskStatus): string`

In `src/labels.ts`, return `'To do' | 'In progress' | 'Done'` with a `switch` + `assertNever`. Then write `priorityColor(priority: Priority): string` using a `Record<Priority, string>` lookup table instead of a switch.

### C. Prove exhaustiveness

Temporarily add `'BLOCKED'` to `TASK_STATUSES`. Run `npm run typecheck`. Write down **every** error and what each one is telling you. Then remove `'BLOCKED'`.

## 3. Hints

<details>
<summary>Hint 1: the Map approach</summary>

`const groups = new Map<T[K], T[]>();` Then for each item, `groups.get(item[key])`, and create or append. `Map` preserves insertion order.
</details>

<details>
<summary>Hint 2: why Record struggles here</summary>

`Record<K, V>` requires `K extends string | number | symbol` (`PropertyKey`). `T[K]` could be `null`, a boolean or an object. Also, object keys are converted to **strings** at runtime: `{ 1: … }` has key `'1'`.
</details>
