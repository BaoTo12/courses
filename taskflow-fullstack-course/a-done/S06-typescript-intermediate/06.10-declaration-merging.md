# Lecture 06.10 · Module Augmentation and Declaration Merging

> **Section:** S06 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> Needed for the styled-components theme (S10), i18next typed keys (S25), and data passed from JSP to React (S49).

---

## 1. The problem

Some libraries expose an **empty or generic interface** and expect *you* to describe your app's specifics:

- styled-components: `props.theme` is typed as `DefaultTheme`, an **empty interface** by default. Your theme's `colors` are unknown to TypeScript.
- i18next: translation keys are plain `string`s unless you describe your resources.
- The browser: `window.__TASKFLOW_INITIAL__` (data a JSP page injects for React in S49) isn't a known property of `Window`.

You can't edit the library's `.d.ts` files in `node_modules`. You need to **add to** their types from your code.

## 2. Declaration merging

Two `interface` declarations with the same name in the same scope **merge** (05.05):

```ts
interface Box { width: number }
interface Box { height: number }
const b: Box = { width: 1, height: 2 };   // both properties required
```

Type aliases (`type`) can't merge. That's the main practical difference between `type` and `interface`.

## 3. Module augmentation: merging into a library's interface

```ts
// src/styled.d.ts (S10)
import 'styled-components';

declare module 'styled-components' {
  export interface DefaultTheme {
    colors: {
      primary: string;
      surface: string;
      text: string;
    };
  }
}
```

- `declare module 'styled-components'` re-opens that module's type declarations.
- `export interface DefaultTheme { … }` **merges** your properties into the library's empty interface.
- Now, everywhere in the app, `props.theme.colors.primary` is typed, and `theme.colours` is a compile error.
- The `import 'styled-components'` at the top makes this file a **module augmentation** (adding to an existing module) rather than a declaration of a brand-new module.

## 4. Global augmentation: extending `Window`

```ts
// src/global.d.ts
import type { Task } from './domain';

declare global {
  interface Window {
    __TASKFLOW_INITIAL__?: { tasks: Task[] };
  }
}

export {};   // makes this file a module, so `declare global` is allowed
```

```ts
const initialTasks = window.__TASKFLOW_INITIAL__?.tasks ?? [];   // typed, and optional
```

Declaring it **optional** (`?`) is honest: the React app might run without the JSP page (e.g. in the Vite dev server). And remember 06.09: data injected by a server page is still a **boundary**. In S49 we'll validate it (and see why injecting it safely matters for XSS).

## 5. `.d.ts` files

Files ending in `.d.ts` contain **only type declarations** (no runtime code). They're used for:
- Library types (`node_modules/@types/…`, or shipped inside packages).
- Your augmentations (`styled.d.ts`, `global.d.ts`, `i18next.d.ts`).
- Types for non-TS assets, e.g. `declare module '*.module.scss' { const classes: Record<string, string>; export default classes; }`. Vite's client types provide this for you (S07).

Make sure your `tsconfig.json` `include` covers them (our `"include": ["src"]` does if they live in `src/`).

## 6. Summary

- Interfaces with the same name merge; type aliases don't.
- `declare module 'lib' { interface X { … } }` adds your specifics to a library's types.
- `declare global { interface Window { … } }` types globals (make them optional, and still validate).
- `.d.ts` files hold type-only declarations.
