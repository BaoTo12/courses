# Lecture 06.03 · Utility Types: `Partial`, `Required`, `Pick`, `Omit`, `Record`, `Readonly`, `ReturnType`, `Parameters`, `Awaited`

> **Section:** S06 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes

---

## 1. The problem: many shapes of the same entity

A `Task` appears in many shapes across TaskFlow:

| Situation | Shape |
|---|---|
| Server response | All fields, including `id`, `ownerId`, timestamps |
| "Create task" form submission | No `id`, `ownerId`, timestamps (server sets them) |
| "Edit task" PATCH | **Any subset** of editable fields |
| A task card | Only `id`, `title`, `status`, `priority`, `dueDate` |
| Redux state | Readonly |

Writing each by hand duplicates fields and drifts out of sync. **Utility types** derive new types from existing ones, so changes to `Task` flow everywhere automatically.

## 2. The core utility types

```ts
interface Task { id: number; title: string; status: TaskStatus; dueDate: string | null; ownerId: number; /* … */ }
```

| Utility | Result | Example use |
|---|---|---|
| `Partial<Task>` | Every property optional | PATCH body, test-factory overrides |
| `Required<T>` | Every property required | After defaults are applied |
| `Readonly<Task>` | Every property `readonly` | State that must not be mutated |
| `Pick<Task, 'id' \| 'title'>` | Only those properties | Props for a small component |
| `Omit<Task, 'id' \| 'ownerId'>` | All **except** those | Create-request bodies |
| `Record<TaskStatus, Task[]>` | Object with exactly those keys | Grouping, lookup tables |
| `NonNullable<string \| null>` | `string` | After a null check |
| `ReturnType<typeof fn>` | What a function returns | Typing Redux `RootState` |
| `Parameters<typeof fn>` | Tuple of a function's parameters | Wrapping functions |
| `Awaited<Promise<Task>>` | `Task` | Unwrapping async results |
| `Exclude<TaskStatus, 'DONE'>` | `'TODO' \| 'IN_PROGRESS'` | Removing union members |
| `Extract<TaskStatus, 'DONE' \| 'X'>` | `'DONE'` | Keeping union members |

### They compose

```ts
// "id and title required, everything else optional": the test factory from 05.09
type TaskOverrides = Partial<Task> & Pick<Task, 'id' | 'title'>;

// open statuses
type OpenStatus = Exclude<TaskStatus, 'DONE'>;
```

`&` is an **intersection**: the value must satisfy **both** types.

## 3. `ReturnType`: letting the implementation define the type

The single most famous use in this course (S17):

```ts
const store = configureStore({ reducer: { tasks: tasksReducer, filters: filtersReducer } });

export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;
```

- `typeof store.getState` = the **type** of that function (TS's `typeof` in a type position, 06.05).
- `ReturnType<…>` = what it returns = the whole state shape.
- Add a new slice, and `RootState` updates **automatically**. You never write the state type by hand.

## 4. How they work (a peek inside)

They're not magic. They're written in TypeScript itself, with **mapped types** (06.11):

```ts
type MyPartial<T> = { [K in keyof T]?: T[K] };
type MyReadonly<T> = { readonly [K in keyof T]: T[K] };
type MyPick<T, K extends keyof T> = { [P in K]: T[P] };
```

"For each key `K` of `T`, make a property with the same type, but optional/readonly." Knowing this lets you read library types without panic.

## 5. Caveats

- `Partial` is **shallow**: nested objects stay required. (Deep variants exist in libraries; rarely needed here.)
- `Readonly` is **compile-time only** and shallow (05.03).
- `Omit<T, 'typo'>` does **not** error on a key that doesn't exist (its key parameter is `keyof any`). Double-check spelling, or use a stricter helper.

## 6. Summary

- Utility types derive shapes from one source type, so changes propagate.
- `Partial`/`Pick`/`Omit`/`Record`/`Readonly` shape objects; `Exclude`/`Extract`/`NonNullable` shape unions; `ReturnType`/`Parameters`/`Awaited` extract from functions and promises.
- `RootState = ReturnType<typeof store.getState>` is coming in S17.
