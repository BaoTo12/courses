# Lecture 06.01 · Generics: Functions, Types and Constraints

> **Section:** S06 · TypeScript Intermediate: Modelling a Real App
> **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~30 minutes

---

## 1. The problem

You want one `findById` for tasks, categories, users and comments. Options without generics:

```ts
function findById(items: any[], id: number): any { … }          // ❌ loses all type information
function findTaskById(items: Task[], id: number): Task | undefined { … }   // ❌ duplicated per type
function findById(items: HasId[], id: number): HasId | undefined { … }     // ❌ returns HasId, not Task
```

With the last version, `findById(tasks, 1)?.title` fails: the result is only known to be a `HasId`. The *specific* type got lost.

## 2. A type parameter: a variable for types

```ts
function findById<T extends HasId>(items: readonly T[], id: number): T | undefined {
  return items.find((item) => item.id === id);
}

const task = findById(tasks, 1);          // Task | undefined
const cat = findById(categories, 2);      // Category | undefined
task?.title;                              // ✅ the specific type survives
```

- `<T>` declares a **type parameter**, a placeholder filled in at each call.
- TypeScript **infers** `T` from the arguments (`tasks: Task[]` → `T = Task`). You rarely write `findById<Task>(…)` explicitly.
- The return type `T | undefined` is **linked** to the input type. That link is the whole point.

> 🧠 Generics are to types what parameters are to values: `f(x)` works for any value `x`; `f<T>` works for any type `T`, and relates input types to output types.

## 3. Constraints: `extends`

Inside `findById`, TypeScript must know `item.id` exists. `T extends HasId` means "T can be any type that has at least `id: number`". Without the constraint:

```ts
function findById<T>(items: readonly T[], id: number) {
  return items.find((item) => item.id === id);
  //                          ~~ Property 'id' does not exist on type 'T'.
}
```

Constraints use structural typing (05.05): `Task`, `Category` and `{ id: 5, anything: true }` all satisfy `HasId`.

## 4. Generic types

Types can have parameters too:

```ts
interface Page<T> {
  items: T[];
  page: number;
  size: number;
  totalItems: number;
  totalPages: number;
}

type TaskPage = Page<Task>;
type CategoryPage = Page<Category>;
```

You already use built-in generic types: `Array<T>`, `Promise<T>`, `Record<K, V>`, `Map<K, V>`, `ReadonlyArray<T>`. React and Redux are full of them: `useState<T>`, `PayloadAction<P>`, `createSlice`, `createAsyncThunk<Returned, Arg>`.

## 5. Multiple parameters and keys

```ts
function pluck<T, K extends keyof T>(items: readonly T[], key: K): T[K][] {
  return items.map((item) => item[key]);
}

pluck(tasks, 'title');      // string[]
pluck(tasks, 'priority');   // Priority[]
pluck(tasks, 'nope');       // ❌ Argument of type '"nope"' is not assignable to parameter of type 'keyof Task'.
```

- `keyof T` = the union of `T`'s property names (06.05).
- `T[K]` = the type of property `K` of `T` (an **indexed access type**).
- `K extends keyof T` ties the key to the object, and `T[K]` ties the result to the key. This is exactly what fixes `updateTaskField` in the next lecture.

## 6. Defaults

```ts
interface ApiResponse<T = unknown> { data: T; receivedAt: number }
let r: ApiResponse;            // ApiResponse<unknown>
```

## 7. When not to use generics

- If a type parameter appears **only once** (e.g. only in a parameter), it usually adds nothing: `function log<T>(x: T): void` could just be `(x: unknown) => void`.
- Don't make a function generic "just in case". Generics earn their place when they **link** types (input ↔ output, key ↔ value).

## 8. Summary

- Generics are type parameters (`<T>`) that preserve and link specific types across a function or type.
- `extends` constrains what `T` may be, so you can use its known members.
- `K extends keyof T` + `T[K]` link keys to their value types.
- Built-in and library types (`Promise<T>`, `Record<K,V>`, `useState<T>`) are generics you already use.

## 9. Check yourself

1. What's the return type of `findById(users, 3)`?
2. Why does `findById<T>(items: T[])` fail to compile `item.id` without a constraint?
3. What does `pluck(tasks, 'dueDate')` return?

<details>
<summary>Answers</summary>

1. `User | undefined`.
2. `T` could be any type (like `string`), which has no `id`. The constraint `T extends HasId` guarantees it.
3. `(string | null)[]`, since `Task['dueDate']` is `IsoDate | null`, i.e. `string | null`.

</details>
