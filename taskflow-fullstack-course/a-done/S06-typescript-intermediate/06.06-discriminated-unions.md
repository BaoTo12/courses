# Lecture 06.06 · Discriminated Unions and Exhaustive `switch` with `never`

> **Section:** S06 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~35 minutes
> The foundation of typed Redux actions (S15) and request state (S19).

---

## 1. The problem: "boolean soup"

A common way to model loading data:

```ts
interface TasksState {
  loading: boolean;
  error?: string;
  data?: Task[];
}
```

How many combinations are possible? `loading` × `error?` × `data?` = 8. How many make sense?

| loading | error | data | Meaning |
|---|---|---|---|
| false | – | – | idle ✅ |
| true | – | – | loading ✅ |
| false | – | ✓ | succeeded ✅ |
| false | ✓ | – | failed ✅ |
| true | ✓ | – | loading *and* failed?? ❌ |
| true | – | ✓ | loading with old data? (maybe) |
| false | ✓ | ✓ | failed but has data?? ❌ |
| true | ✓ | ✓ | ??? ❌ |

The type **allows impossible states**, so every component must defensively handle them, and eventually someone renders a spinner *and* an error at the same time.

## 2. The solution: a union of states with a tag

```ts
type RequestState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'succeeded'; data: T }
  | { status: 'failed'; error: string };
```

- Each member has a common property with a **literal type**: the **discriminant** (`status`).
- Each member carries **only** the data valid in that state: `data` exists only when `succeeded`, `error` only when `failed`.
- Impossible combinations **can't be represented**. ("Make illegal states unrepresentable.")

## 3. Narrowing by the discriminant

```ts
function render(state: RequestState<Task[]>): string {
  switch (state.status) {
    case 'idle':
      return 'Nothing loaded yet';
    case 'loading':
      return 'Loading…';
    case 'succeeded':
      return `${state.data.length} tasks`;     // ✅ data exists here
    case 'failed':
      return `Error: ${state.error}`;          // ✅ error exists here
  }
}
```

Checking `state.status === 'succeeded'` narrows `state` to exactly that member, so `state.data` is available. Outside that branch, `state.data` is a compile error. The type system forces you to check before using.

## 4. Exhaustiveness: `assertNever`

What if someone adds `{ status: 'refreshing'; data: T }` later? We want **every switch** over `RequestState` to fail to compile until it handles the new case.

```ts
export function assertNever(value: never): never {
  throw new Error(`Unexpected value: ${JSON.stringify(value)}`);
}

function render(state: RequestState<Task[]>): string {
  switch (state.status) {
    case 'idle': return '…';
    case 'loading': return '…';
    case 'succeeded': return '…';
    case 'failed': return '…';
    default:
      return assertNever(state);   // state is `never` here if all cases were handled
  }
}
```

How it works:
- After all cases, the remaining type is `never` (05.03), so passing it to `assertNever(value: never)` compiles.
- If a case is missing, the remaining type is that member (e.g. `{ status: 'refreshing' … }`), which **isn't assignable to `never`** → compile error at the `default` line, naming the missing variant.
- At runtime, if bad data slips in (e.g. an unknown status from an old server), `assertNever` throws a clear error instead of silently returning `undefined`.

You saw exactly this in action when `'BLOCKED'` was added in this section's reference project:

```text
src/labels.ts(14,26): error TS2345: Argument of type '"BLOCKED"' is not assignable to parameter of type 'never'.
```

## 5. Redux actions are discriminated unions (preview of S15)

```ts
type TasksAction =
  | { type: 'tasks/taskAdded'; payload: Task }
  | { type: 'tasks/taskToggled'; payload: { id: number } }
  | { type: 'tasks/tasksLoaded'; payload: Task[] };

function tasksReducer(state: Task[], action: TasksAction): Task[] {
  switch (action.type) {
    case 'tasks/taskAdded':
      return [...state, action.payload];                  // payload: Task
    case 'tasks/taskToggled':
      return toggleTask(state, action.payload.id);        // payload: { id }
    case 'tasks/tasksLoaded':
      return action.payload;                              // payload: Task[]
    default:
      return assertNever(action);
  }
}
```

The discriminant is `type`, and each action's `payload` is typed precisely. When you write classic Redux by hand in S15, this is the pattern. (Real Redux reducers also receive *other slices'* actions, so their `default` returns `state` instead of asserting never. You'll see why in S15.)

## 6. Summary

- Boolean flags allow impossible states; **discriminated unions** make them unrepresentable.
- A shared literal property (`status`, `type`) discriminates; narrowing gives access to member-specific fields.
- `assertNever` in `default` = compile-time exhaustiveness + runtime safety.
- Redux actions and request state are discriminated unions.

## 7. Check yourself

1. List two impossible states that `{ loading: boolean; error?: string; data?: T }` allows.
2. Inside `case 'failed':`, can you access `state.data`?
3. Why does `assertNever(state)` compile only when all cases are handled?

<details>
<summary>Answers</summary>

1. `loading: true` with an `error`; `error` and `data` both present with `loading: false` (and others).
2. **No.** `state` is narrowed to `{ status: 'failed'; error: string }`, which has no `data`.
3. When every member has been handled, the remaining type is `never`, the only type assignable to the `never` parameter. Any unhandled member makes the argument type non-`never`.

</details>
