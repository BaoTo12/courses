## 1. Goal

`RequestState<T>` (defined in 06.04) models a request's lifecycle. Let's add small, pure helpers for working with it, plus a renderer with exhaustive handling.

## 2. ✍️ `src/request-state.ts`

```ts
import type { RequestState } from './api-types';
import { assertNever } from './guards';

export const idle = <T>(): RequestState<T> => ({ status: 'idle' });
export const loading = <T>(): RequestState<T> => ({ status: 'loading' });
export const succeeded = <T>(data: T): RequestState<T> => ({ status: 'succeeded', data });
export const failed = <T>(error: string): RequestState<T> => ({ status: 'failed', error });

/** Return the data if the request succeeded, otherwise a fallback. */
export function dataOr<T>(state: RequestState<T>, fallback: T): T {
  return state.status === 'succeeded' ? state.data : fallback;
}

/** Describe any request state for a status line. Exhaustive. */
export function describe<T>(state: RequestState<T>, describeData: (data: T) => string): string {
  switch (state.status) {
    case 'idle':
      return '';
    case 'loading':
      return 'Loading…';
    case 'succeeded':
      return describeData(state.data);
    case 'failed':
      return `Something went wrong: ${state.error}`;
    default:
      return assertNever(state);
  }
}
```

(Create `src/guards.ts` with `assertNever` now if you haven't; 06.08 fills in the rest of that file:)

```ts
/** Compile-time exhaustiveness helper: only callable with `never`. */
export function assertNever(value: never): never {
  throw new Error(`Unexpected value: ${JSON.stringify(value)}`);
}
```

### Why these helpers?

- **Constructors (`loading()`, `succeeded(data)`)** make state transitions read like a sentence, and the generic `<T>` keeps the data type. `succeeded(tasks)` is `RequestState<Task[]>`.
- **`dataOr`** is the safe way to read data. You *cannot* read `state.data` without checking `status`; the helper encapsulates the check.
- **`describe`** shows exhaustive handling with a callback (a higher-order function, 04.08) for the data-specific part.

## 3. Use it

```ts
import { loading, succeeded, failed, describe } from './request-state';
import type { RequestState } from './api-types';
import type { Task } from './domain';

let state: RequestState<Task[]> = loading();
console.log(describe(state, (tasks) => `${tasks.length} tasks`));   // Loading…

state = succeeded([/* tasks */]);
console.log(describe(state, (tasks) => `${tasks.length} tasks`));   // 0 tasks

state = failed('HTTP 503');
console.log(describe(state, (tasks) => `${tasks.length} tasks`));   // Something went wrong: HTTP 503
```

Try writing `state.data` directly after `state = failed(…)`: the compiler refuses (`Property 'data' does not exist on type …`).

## 5. Where this goes next

- **S08:** `useTasks()` returns a `RequestState<Task[]>`, and components `switch` on `status`.
- **S19:** Redux slices store `status: 'idle' | 'loading' | 'succeeded' | 'failed'` + `error`. That's the official "loading state" pattern from the Redux Fundamentals tutorial, with the reasoning you now know.
- **S22:** RTK Query gives you `isLoading`/`isFetching`/`isError`/`data` flags. You'll understand its trade-offs against a discriminated union.

## 6. Summary

- Small generic constructors + `dataOr` + an exhaustive `describe` make request state safe and pleasant.
- The compiler prevents reading `data` or `error` in the wrong state.
