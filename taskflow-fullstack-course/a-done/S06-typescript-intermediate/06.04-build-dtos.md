## 1. A design decision: the frontend model *is* the API contract

In large systems, teams sometimes keep separate "API DTO" and "client model" types, with mapping functions between them. That's useful when the API shape is awkward or unstable. TaskFlow controls both sides, so the frontend's `Task` **is** the JSON contract from [02-project-spec.md](../../02-project-spec.md) §5. We derive **request** shapes from it with utility types.

## 2. ✍️ Final `src/domain.ts`

```ts
// TaskFlow domain model = the JSON contract of the API (02-project-spec.md §5).
// Values first (usable at runtime), types derived from them (06.05).

export const TASK_STATUSES = ['TODO', 'IN_PROGRESS', 'DONE'] as const;
export type TaskStatus = (typeof TASK_STATUSES)[number];

export const PRIORITIES = ['LOW', 'MEDIUM', 'HIGH'] as const;
export type Priority = (typeof PRIORITIES)[number];

export type Role = 'USER' | 'ADMIN';

/** '2026-10-03' */
export type IsoDate = string;
/** '2026-10-01T09:30:00Z' */
export type IsoDateTime = string;

export interface HasId {
  id: number;
}

export interface Task extends HasId {
  title: string;
  description: string;
  status: TaskStatus;
  priority: Priority;
  dueDate: IsoDate | null;
  categoryId: number | null;
  ownerId: number;
  createdAt: IsoDateTime;
  updatedAt: IsoDateTime;
}

export interface Category extends HasId {
  name: string;
  color: string;
}

export interface User extends HasId {
  username: string;
  displayName: string;
  role: Role;
  locale: 'en' | 'vi';
}

export interface Comment extends HasId {
  taskId: number;
  authorId: number;
  body: string;
  createdAt: IsoDateTime;
}

export interface TaskFilter {
  status?: TaskStatus;
  priority?: Priority;
  categoryId?: number;
  q?: string;
}

export type SortKey = 'title' | 'priority' | 'dueDate';
export type SortDirection = 'asc' | 'desc';
```

What changed from S05:
- **`TASK_STATUSES` / `PRIORITIES` arrays with `as const`**, and the union types **derived** from them. Explained in 06.05; the payoff is that you get runtime lists (for dropdowns and validation) *and* types from one source.
- **`categoryId: number | null`** and **`ownerId: number`** are now required, matching what the server always sends.
- **Timestamps** added (`createdAt`, `updatedAt`) as ISO strings: JSON has no date type (05.99 Q7).
- **`extends HasId`** documents the shared shape and makes all entities work with `findById`.

Update the test factory in `task-utils.test.ts` so fixtures satisfy the new required fields:

```ts
const task = (overrides: Partial<Task> & Pick<Task, 'id' | 'title'>): Task => ({

  updatedAt: '2026-09-01T00:00:00Z',

```

This is the payoff of a **factory with defaults**: the model gained four required fields, and you edited **one** place instead of every test.

## 3. ✍️ `src/api-types.ts`

```ts
import type { Task } from './domain';

// ── Requests: what the client SENDS ─────────────────────────────────────────

/** Fields the server generates or controls are excluded: the client can't set them. */
export type CreateTaskRequest = Omit<Task, 'id' | 'ownerId' | 'createdAt' | 'updatedAt'>;

/** PATCH semantics: any subset of the editable fields. */
export type UpdateTaskRequest = Partial<CreateTaskRequest>;

// ── Responses: what the server RETURNS ──────────────────────────────────────

export interface Page<T> {
  items: T[];
  page: number;
  size: number;
  totalItems: number;
  totalPages: number;
}

/** Standard error body for every non-2xx response. */
export interface ApiError {
  status: number;
  error: string;
  message: string;
  fieldErrors?: Record<string, string>;
  path: string;
  timestamp: string;
}

// ── Client-side request lifecycle ──────────────────────────────────────────

export type RequestState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'succeeded'; data: T }
  | { status: 'failed'; error: string };
```

### Why each type looks like this

- **`CreateTaskRequest` omits `ownerId`**: the **server** sets the owner from the session, never from the request body. If the client could send `ownerId`, a user could create tasks for someone else. That's **mass assignment** (S37, S46). The type documents the rule on the client; the server must **enforce** it (types aren't validation).
- **`UpdateTaskRequest = Partial<…>`** matches **PATCH** semantics: send only what changed.
- **`Page<T>`** is generic because tasks, comments and audit events are all paginated.
- **`ApiError`** mirrors the backend's error body, so the UI can show `message` and map `fieldErrors` onto form fields (S11, S48).
- **`RequestState<T>`** is a **discriminated union** (06.06): each state carries exactly the data that makes sense in it.

## 6. Summary

- Frontend `Task` = the API JSON contract; request types derived with `Omit`/`Partial`.
- Server-controlled fields (`id`, `ownerId`, timestamps) are excluded from request types, which documents the mass-assignment rule.
- `Page<T>`, `ApiError`, `RequestState<T>` will be reused by Axios, Redux and RTK Query.
