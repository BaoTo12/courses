# Lecture 05.13 · 🐞 Debug: "TypeScript Says It's Fine, but It Crashes at Runtime"

> **Section:** S05 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~15 minutes

---

## Symptom

A teammate's dashboard code type-checks with **zero errors**:

```ts
async function fetchOverdueCount(): Promise<number> {
  const res = await fetch('/api/tasks');
  const tasks = (await res.json()) as Task[];
  return tasks.filter((t) => isOverdue(t, today())).length;
}
```

It works all morning. After lunch, the dashboard shows a blank area and the console says:

```text
Uncaught (in promise) TypeError: tasks.filter is not a function
```

In the Network tab, the `/api/tasks` response has status **401** and body:

```json
{ "status": 401, "error": "UNAUTHORIZED", "message": "Session expired" }
```

"But TypeScript said `tasks` is a `Task[]`!"

## Investigation checklist

1. What did `as Task[]` tell the compiler? Did it cause any runtime check?
2. What is the runtime type of `tasks` for the 401 response?
3. `fetch` got a 401. Did it reject? (04.11)
4. Which two checks would have turned this into a clear, handled error?

## Explanation

- **`as Task[]` is an assertion, not a conversion or a check.** It tells the compiler "trust me", and it compiles to **nothing** (type erasure, 05.01). At runtime, `tasks` is whatever the server sent.
- The session expired, so the API answered **401 with an error object**. `fetch` **doesn't reject on HTTP errors**, so the code carried on.
- `tasks` was actually `{ status: 401, … }`; objects don't have `.filter` → `TypeError`.
- TypeScript was "fine" because it was **told** to be fine. The lie happened at the trust boundary.

**Fix:** check the status, treat the body as `unknown`, and validate the shape (the 05.12 pattern):

```ts
async function fetchOverdueCount(): Promise<number> {
  const tasks = await loadTasks('/api/tasks');   // throws a clear Error on 401 or bad shape
  return tasks.filter((t) => isOverdue(t, today())).length;
}
```

Now the failure is an explicit `Error('Failed to load tasks: HTTP 401')` that the UI can catch and turn into "Your session expired. Please log in again". In S13 the Axios response interceptor handles every 401 in one place, and in S24 it triggers a logout flow.

## Rules of thumb

- `as` is acceptable when **you** have knowledge the compiler lacks and nothing untrusted is involved (e.g. `as const`, narrowing a DOM element type you just created).
- `as` on **external data** (API responses, `JSON.parse`, storage) is a **bug waiting to happen**. Use `unknown` + checks (or type guards, 06.08, or a schema library like zod).
- Code review signal: every `as SomeType` deserves a question: "what guarantees this?"
