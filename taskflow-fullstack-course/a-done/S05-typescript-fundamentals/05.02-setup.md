# Lecture 05.02 · 🛠 Setup: `tsc`, `tsconfig.json`, `strict: true`, and How TS Runs with Vite/Vitest

> **Section:** S05 · **Type:** 🛠 Build · **Track:** ★ Core · **Time:** ~30 minutes
> **Project feature:** `playground/ts/` with a strict `tsconfig.json`, `typecheck` and `test` scripts

---

## 1. Two jobs, two tools

| Job | Tool | Speed | Checks types? |
|---|---|---|---|
| **Remove types** so JS can run | Vite / Vitest (via fast transpilers) | Very fast, file by file | ❌ No |
| **Check types** across the whole project | `tsc` (the TypeScript compiler), or your editor's TS language service | Slower, whole program | ✅ Yes |

We use `tsc` **only** for checking (`noEmit`); Vite produces the JavaScript that runs. That's the standard setup for modern frontend projects.

> 📌 **TypeScript version.** At the time of writing, `npm install typescript` installs **TypeScript 7**, the native (Go) rewrite of the compiler, which type-checks roughly an order of magnitude faster than TypeScript 5.x. The *language* is the same; what you learn here applies to TS 5.x codebases at work too. A few legacy compiler options were removed in newer versions. If an old `tsconfig.json` complains, check the release notes.

## 3. ✍️ `playground/ts/tsconfig.json`

You *could* run `npx tsc --init` (it generates a documented config with modern strict defaults). Instead, write this one so you understand every line:

```jsonc
{
  "compilerOptions": {
    /* Language & environment */
    "target": "es2023",
    "lib": ["es2023", "dom", "dom.iterable"],

    /* Modules: we use a bundler (Vite) / test runner (Vitest), not tsc, to run code */
    "module": "esnext",
    "moduleResolution": "bundler",
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "noEmit": true,

    /* Type-checking strictness */
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,

    "skipLibCheck": true
  },
  "include": ["src"]
}
```

### What each option does

| Option | Meaning | Why we want it |
|---|---|---|
| `target: es2023` | Which JS syntax the output may use | Modern browsers/Node support ES2023 |
| `lib` | Which built-in APIs TS knows about | `es2023` gives `toSorted`/`toSpliced`/`with`; `dom` gives `document`, `fetch` |
| `module: esnext` + `moduleResolution: bundler` | How imports are written and resolved | Matches how Vite resolves imports (extensionless `'./domain'` is fine) |
| `verbatimModuleSyntax` | Type-only imports must say `import type` | The bundler can drop them safely, file by file (see §5) |
| `isolatedModules` | Every file must be transpilable on its own | Required for Vite/esbuild-style per-file transpiling |
| `noEmit` | `tsc` only checks; it writes no files | Vite does the emitting |
| **`strict: true`** | Enables a family of checks (below) | **Non-negotiable in this course** |
| `noUncheckedIndexedAccess` | `arr[i]` and `record[key]` include `undefined` | Array access really can be out of bounds (05.10) |
| `noFallthroughCasesInSwitch` | Error on accidental switch fall-through | Reducers use `switch` (S15) |
| `skipLibCheck` | Don't type-check `.d.ts` files in `node_modules` | Faster; library bugs aren't your problem |

### What `strict: true` turns on

| Flag | Effect |
|---|---|
| `strictNullChecks` | `null`/`undefined` aren't assignable to other types unless declared: `string \| null` |
| `noImplicitAny` | Parameters without inferable types must be annotated (no silent `any`) |
| `strictFunctionTypes` | Correct (contravariant) checking of function parameter types |
| `strictPropertyInitialization` | Class properties must be initialised |
| `useUnknownInCatchVariables` | `catch (e)` gives `e: unknown`, not `any` (06.09) |
| `alwaysStrict`, `strictBindCallApply`, … | Stricter checks of JS semantics |

Without `strict`, TypeScript lets a lot of real bugs through, and you get the syntax cost without the safety.

## 4. First type-check

Create `src/hello.ts`:

```ts
function greet(name: string): string {
  return `Hello ${name}`;
}

greet(42);
```

```bash
npm run typecheck
```

```text
src/hello.ts(5,7): error TS2345: Argument of type 'number' is not assignable to parameter of type 'string'.
```

Read the format: `file(line,column): error TSxxxx: message`. The `TSxxxx` code is searchable. Fix the call (`greet('An')`), re-run: no output means **no errors**. Delete `hello.ts`.

## 5. `import type`

With `verbatimModuleSyntax`, importing **only types** must be marked:

```ts
import type { Task, TaskStatus } from './domain';     // erased completely
import { filterTasks } from './task-utils';           // a real runtime import
import { type Task, filterTasks } from './mixed';     // inline marker for one name
```

Why it matters: a bundler transpiling one file at a time can't look into `domain.ts` to discover that `Task` is "only a type". `import type` tells it: delete this import. Without it you'd risk importing a module (with side effects) just for a type, or a runtime error for a name that doesn't exist in the JS.

## 6. Editor integration

VS Code uses a TypeScript language service to show red squiggles **as you type**, which is where you'll catch most errors. Tips:
- Hover any variable to see its inferred type. This is the best way to learn inference (05.04).
- `F12` goes to a type's definition, including library types in `node_modules`.
- If VS Code and `npm run typecheck` disagree, VS Code may be using a different TypeScript version: **Ctrl+Shift+P → "TypeScript: Select TypeScript Version" → Use Workspace Version**.

## 8. Summary

- `tsc --noEmit` **checks**; Vite/Vitest **strip** types to run code. Run both (editor + `npm run typecheck` + CI).
- `strict: true` + `noUncheckedIndexedAccess` = the safety you actually want.
- `moduleResolution: bundler`, `isolatedModules`, `verbatimModuleSyntax` match how Vite works.
- Use `import type` for type-only imports.
