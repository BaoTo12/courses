# Lecture 05.01 · Why TypeScript: Static Types, Type Erasure, and What TS Can't Protect You From

> **Section:** S05 · TypeScript Fundamentals
> **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes

---

## 1. The problem

JavaScript tells you about many mistakes only **when the code runs**, and only if that line actually runs:

```js
function formatDue(task) {
  return task.dueDate.toUpperCase();   // 💥 TypeError when dueDate is null… on Friday evening, in production
}
toggleTask(tasks, '2');                // id as a string: silently matches nothing
task.stauts = 'DONE';                  // typo: creates a new property, nothing complains
```

In a 5-file playground you catch these by testing. In a 500-file app with many developers, the **shape** of data (what a `Task` has, which statuses exist, what a function accepts) must be written down somewhere, and **checked automatically**.

## 2. What TypeScript is

**TypeScript = JavaScript + a static type system.**

- You add **type annotations** (or let TS **infer** them).
- The **type checker** (`tsc`) analyses your code **without running it** and reports mismatches.
- Then the types are **removed**, and plain JavaScript runs.

```ts
function formatDue(task: Task): string {
  return task.dueDate.toUpperCase();
  //     ~~~~~~~~~~~~ error TS18047: 'task.dueDate' is possibly 'null'.
}
```

The bug is reported **while you type**, in the editor, before the code ever runs.

## 3. Type erasure: types don't exist at runtime

> 🧠 **TypeScript types exist only at compile time. The browser and Node run JavaScript with all types stripped away.**

```ts
// what you write
function isDone(task: Task): boolean {
  return task.status === 'DONE';
}

// what actually runs
function isDone(task) {
  return task.status === 'DONE';
}
```

This is the same compile-time/runtime split you met with Sass (02.02): `$variables` vanish from CSS; `: Task` vanishes from JS.

### Proof: tests pass even when types are wrong

When the S04 tests were converted to TypeScript for this course, the type checker reported **six errors** (fixture objects missing the required `description` field, and array accesses that might be `undefined`). But running the tests:

```text
$ npx tsc --noEmit
src/task-utils.test.ts(24,3): error TS2322: … Property 'description' is missing … but required in type 'Task'.
…
$ npx vitest run
      Tests  8 passed (8)
```

**Vitest passed.** Like Vite, it **strips types without checking them** (for speed). Type checking is a **separate step** that you must run: in your editor, in `npm run typecheck`, and in CI. You'll set up both in 05.02.

## 4. What TypeScript can't protect you from

Because types are erased, anything that comes from **outside your code at runtime** is only *assumed* to match its type:

| Source | Why TS can't guarantee it |
|---|---|
| JSON from an API (`await res.json()`) | The server could send anything: a different version, an error body, `null` |
| `localStorage`, cookies, URL params | The user can edit them |
| `JSON.parse(text)` | Returns `any`, so TS believes whatever you say |
| Third-party JS without accurate types | Types may be wrong or missing |
| `as` type assertions | You told the compiler "trust me" |

```ts
const tasks = (await res.json()) as Task[];   // a PROMISE to the compiler, not a check
```

If the server sends `{ "error": "Unauthorized" }`, `tasks` is typed `Task[]` but is actually an object, and `tasks.map` crashes. Lecture 05.13 debugs exactly this, and S06 shows how to **validate at the boundary** with type guards.

> 🛡 **Types are not validation.** Security-relevant checks (is this ID a number? is this role allowed?) must happen at runtime, on the server (S37, S46). TypeScript helps you write *correct code*; it doesn't make *untrusted input* trustworthy.

## 5. What you get in return

| Benefit | Example in TaskFlow |
|---|---|
| **Errors before running** | Misspelled `stauts`, passing `'2'` where `number` is expected |
| **Documentation that can't go stale** | `function sortTasks(tasks: readonly Task[], key: SortKey)` tells you exactly what's allowed |
| **Autocomplete** | `task.` lists `title`, `status`, `priority`… |
| **Safe refactoring** | Rename `dueDate` → the compiler lists every place to update |
| **Modelling the domain** | `type TaskStatus = 'TODO' \| 'IN_PROGRESS' \| 'DONE'`: impossible values rejected |
| **Typed Redux** | `RootState`, typed actions, typed hooks (S15–S17) |
| **Typed API contracts** | DTOs matching the Java backend (S06, S13) |

The cost: some learning curve, more syntax, and occasional fights with the type checker. For team-scale applications it's overwhelmingly considered worth it. Most React job descriptions today assume TypeScript.

## 6. The nine questions in brief

| | |
|---|---|
| Problem | Runtime-only discovery of shape/type errors in large JS codebases |
| How | Annotations + inference → static analysis by `tsc` → types erased → JS runs |
| Alternatives | Plain JS + tests; JSDoc type annotations checked by TS (`// @ts-check`); runtime validation libraries (zod, valibot); Flow (largely legacy) |
| Trade-offs | Safety, tooling, documentation vs. learning curve, build step, false confidence at boundaries |
| Use when | Anything beyond a small script, especially with multiple developers |
| Avoid when | Tiny throwaway scripts; and never as a substitute for runtime validation of external data |

## 7. Summary

- TypeScript adds a static type system to JavaScript; `tsc` checks without running.
- **Type erasure:** types vanish at runtime. Vite/Vitest strip types **without checking**, so run `tsc` separately.
- External data (APIs, storage, `JSON.parse`, `as` casts) is **not** verified by types.
- Types are not validation; security checks stay on the server.

## 8. Check yourself

1. If TypeScript types are erased at runtime, what guarantees do you have about JSON returned by an API?
2. Your tests pass with Vitest. Does that mean the code type-checks?
3. What's the difference between `const x: Task = data` and `const x = data as Task`?

<details>
<summary>Answers</summary>

1. **None from TypeScript.** You only have what you verify at runtime (checks, type guards, schema validation) or what the server contract promises.
2. **No.** Vitest strips types without checking. Run `tsc --noEmit` (or your editor/CI) to type-check.
3. The annotation **checks** that `data`'s known type is assignable to `Task` (compile error if not). The `as` assertion **overrides** the checker ("trust me"), so it compiles even when `data` is `any`/`unknown` or a looser type, and can hide real mismatches.

</details>
