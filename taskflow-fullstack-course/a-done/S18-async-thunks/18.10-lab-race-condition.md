# Lecture 18.10 · 🔓 Lab: a Race Condition. Type Fast; Older Responses Overwrite Newer Ones.

> **Section:** S18 · **Type:** 🔓 Lab · **Track:** ★ Core · **Time:** ~30 minutes
> ⚠️ Run this lab only against **your own local TaskFlow** and its mock API.
> Reproduced in the reference app with the mock's `?_mockDelay` helper (13.02). The numbers are from that run.

---

## 1. The scenario

A user types "report" into a search box that queries the server (TaskFlow's list will search on the server once pagination arrives, S21). With debouncing (08.12), the app may still send two requests: one for `r` (the user paused) and one for `report`.

Short queries match more rows, so the server can be **slower** for `r` than for `report`:

```text
t=0 ms     GET /tasks?q=r        (slow: 900 ms)
t=50 ms    GET /tasks?q=report   (fast: 100 ms)
t=150 ms   ← response for "report"  → store shows 1 task    ✓
t=900 ms   ← response for "r"       → store shows 22 tasks  ✗ the OLD query wins
```

The search box says "report", but the list shows the results for "r". That's a **race condition**: the outcome depends on network timing, not on the order of the user's actions.

## 2. 🔓 Reproduce it

With the mock and the dev server running, in the browser console on `http://localhost:5173`:

```js
const { api } = await import('/src/api/client.ts');
const { createStore, applyMiddleware } = await import('/node_modules/.vite/deps/redux.js');
const { thunk } = await import('/node_modules/.vite/deps/redux-thunk.js');

// A NAIVE store: the last response to ARRIVE wins
const naive = createStore(
  (s = { q: null, titles: [] }, a) => (a.type === 'search/succeeded' ? { q: a.payload.q, titles: a.payload.titles } : s),
  applyMiddleware(thunk),
);
const naiveSearch = (q, delay) => async (dispatch) => {
  const { data } = await api.get('/tasks', { params: { q, size: 100, _mockDelay: delay } });
  dispatch({ type: 'search/succeeded', payload: { q, titles: data.items.map((t) => t.title) } });
};

const p1 = naive.dispatch(naiveSearch('r', 900));
await new Promise((r) => setTimeout(r, 50));
const p2 = naive.dispatch(naiveSearch('report', 100));
await Promise.all([p1, p2]);
naive.getState().q;              // 'r'  ← verified: the stale query won
naive.getState().titles.length;  // 22
```

(The paths under `/node_modules/.vite/deps/` are Vite's pre-bundled dependencies, available only in the dev server. This is a lab trick, not app code.)

## 3. Why TaskFlow's own `fetchTasks` has the same weakness

The 18.06 version of `fetchTasks` dispatches `fetchSucceeded(tasks)` for **every** response that arrives. Any two overlapping loads race the same way: "Try again" clicked twice, StrictMode's double effect (before 18.09), a filter change during a slow load. In the real world, mobile networks make timings wildly unpredictable.

## 4. What doesn't fix it

- **Debouncing** (08.12): fewer requests, but two can still overlap.
- **Disabling the input while loading**: terrible UX for search.
- **`await`ing in the component**: each call awaits its own request; nothing orders them.
- **Hoping the server is fast.**

The fix needs one of: ignore stale responses, or cancel stale requests. Ideally both (18.11).

## 5. Summary

- Async results can arrive in a different order than the requests were sent.
- "Last response wins" shows stale data. Verified: typing "report" ended with the results for "r".
- Debouncing reduces, but doesn't remove, overlapping requests.
