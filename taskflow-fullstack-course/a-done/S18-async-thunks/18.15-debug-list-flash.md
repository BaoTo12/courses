# Lecture 18.15 · 🐞 Debug: the List Flashes Empty on Every Navigation (Unconditional Refetch + Reset)

> **Section:** S18 · **Type:** 🐞 Debug · **Track:** ★ Core · **Time:** ~20 minutes
> Reproduced with a Vitest probe: the buggy reducer variant below, the real `fetchTasks` thunk, and a subscriber recording the item counts.

---

## Symptom

After a refactor, users say: *"Every time I come back to the task list, it goes blank for a moment, then the tasks reappear. And my scroll position is lost."*

The refactor made two changes:

```tsx
// 1. TasksPage now loads its own data
useEffect(() => {
  void dispatch(fetchTasks());
}, [dispatch]);
```

```ts
// 2. "Start from a clean state on every load"
case 'tasks/fetchStarted':
  return { ...initialTasksState, status: 'loading', currentRequestId: action.payload.requestId };
```

## Investigation checklist

1. When does the effect run? What happens when the user navigates `/tasks` → `/tasks/5` → back? (12.02: routes mount and unmount pages)
2. What does `tasks.items` contain between `fetchStarted` and `fetchSucceeded` with the new reducer?
3. What does `TasksPage` render when `items` is empty and the status is `loading`? (17.07)
4. Is there any reason to fetch at all when the data was loaded 5 seconds ago? (18.09)

## Explanation

- Navigating back **mounts `TasksPage` again**, so its effect dispatches `fetchTasks()` every time: an **unconditional refetch**.
- The new `fetchStarted` case **resets** `items` to `[]`. Verified with a subscriber on a store using that reducer: during a reload, the item counts it saw were **`0` (while loading), then `1`**. With TaskFlow's real reducer, the list kept its items throughout.
- `TasksPage` shows "Loading tasks…" when there's no data. So the list vanishes, the scroll position is lost, then everything re-renders.

Two independent mistakes, each enough to cause work, and together a visible flash.

## Fix

1. **Keep the data while reloading.** `fetchStarted` updates `status` (and the request id) only: stale data on screen with a "refreshing" hint beats an empty screen (15.06's design note, which this refactor undid).
2. **Don't refetch unconditionally.** Load where it makes sense (the layout, once) and use `fetchTasksIfNeeded()` (18.09). Returning within 30 s reuses the store's data with no request.
3. If a page must refresh on every visit (a live dashboard), still keep old data visible until the new data arrives.

## Lessons

- "Reset on start" reducers + refetch-on-mount = flashing UIs.
- Keep showing what you have; mark it as refreshing.
- Make loading idempotent with "fetch if needed" (and, in S22, RTK Query's cache does this by default).
