# Lecture 18.11 · 🛡 Fix: Request IDs and `AbortController` via `extra`; Ignore Stale Results

> **Section:** S18 · **Type:** 🛡 Defence · **Track:** ★ Core · **Time:** ~50 minutes
> **Project feature:** the tasks slice ignores results of superseded requests; `fetchTasks` aborts the previous request
> Verified: the reducer and thunk tests below pass, and the 18.10 scenario replayed against the real store ends with the **"report"** results (1 task).

---

## 1. Two complementary fixes

| Fix | Where | Guarantees | Saves |
|---|---|---|---|
| **Request ids**: remember the newest request; ignore results from any other | **Reducer** (pure, testable) | Correctness: stale data can never be shown | Nothing on the network |
| **Abort** the previous request when a new one starts | **Thunk** (via `extra`) | Nothing on its own: a response can arrive just before the abort | Bandwidth and client work (the server may still process it, 13.09 §5) |

Request ids are the real fix; aborting is an optimisation. Do both.

## 2. ✍️ The slice (`tasksSlice.ts`)

State gets two fields:

```ts
  /** The id of the fetch in flight; results of any OTHER (older) fetch are ignored (18.11). */
  currentRequestId: string | null;
  /** When the list was last loaded successfully (epoch ms), for "fetch if needed" (18.09). */
  fetchedAt: number | null;
```

Every fetch action carries its `requestId`:

```ts
  | { type: 'tasks/fetchStarted'; payload: { requestId: string } }
  | { type: 'tasks/fetchSucceeded'; payload: { requestId: string; tasks: Task[]; fetchedAt: number } }
  | { type: 'tasks/fetchFailed'; payload: { requestId: string; message: string } }
```

And the reducer decides which results count:

```ts
    case 'tasks/fetchStarted':
      // Keep the current items while reloading (the list doesn't blink); clear the old error.
      // The NEWEST fetch wins: remember its id (18.11).
      return { ...state, status: 'loading', error: null, currentRequestId: action.payload.requestId };
    case 'tasks/fetchSucceeded': {
      const { requestId, tasks, fetchedAt } = action.payload;
      if (requestId !== state.currentRequestId) return state; // a stale response: ignore it (18.10)
      return { ...state, status: 'succeeded', items: tasks, error: null, currentRequestId: null, fetchedAt };
    }
    case 'tasks/fetchFailed': {
      const { requestId, message } = action.payload;
      if (requestId !== state.currentRequestId) return state;
      return { ...state, status: 'failed', error: message, currentRequestId: null };
    }
```

- The check lives in the **reducer**: pure, deterministic, and testable without any timing (below).
- `fetchSucceeded` now also clears `error`: the question left open in 15.13 §3, decided.
- `return state` for stale results: the **same** reference, so nothing re-renders (17.04).

RTK's `createAsyncThunk` (S20) generates a `meta.requestId` for every call, and the official docs show this same reducer check built on it. You're writing it by hand first, so you'll recognise it.

## 3. ✍️ The thunk: ids and aborting (`tasksThunks.ts`)

```ts
export const fetchTasks =
  (query: TaskQuery = DEFAULT_QUERY): AppThunk<Promise<void>> =>
  async (dispatch, _getState, { api, nextRequestId, listRequest }) => {
    listRequest.controller?.abort(); // a newer request supersedes the older one
    const controller = new AbortController();
    listRequest.controller = controller;

    const requestId = nextRequestId();
    dispatch(fetchStarted(requestId));
    try {
      const page = await api.getTasks(query, controller.signal);
      dispatch(fetchSucceeded(requestId, page.items));
    } catch (error) {
      if (isCancelled(error)) return; // superseded by a newer request (or the page went away)
      dispatch(fetchFailed(requestId, toErrorMessage(error)));
    } finally {
      if (listRequest.controller === controller) listRequest.controller = null;
    }
  };
```

- **`nextRequestId()` comes from `extra`**: ids are generated **outside** the reducer (15.04), and each store has its own counter, so tests are deterministic (`req-1`, `req-2`…).
- **`listRequest` is a per-store holder in `extra`.** A module-level variable would be shared by every store, and tests would abort each other's requests. That was my first draft, changed before writing this lecture.
- **Aborted requests dispatch nothing**: `isCancelled` (13.07) recognises the `ApiRequestError` of kind `cancelled`.
- **`finally` clears the holder** only if it still holds **this** request's controller; a newer request may have replaced it.

## 4. ✍️ Tests

Reducer level (`tasksSlice.test.ts`):

```ts
it('ignores responses from a stale (older) request (18.10, 18.11)', () => {
  const first = tasksReducer(loaded(task(1)), fetchStarted('old'));
  const second = deepFreeze(tasksReducer(deepFreeze(first), fetchStarted('new')));
  // The NEW request answers first…
  const afterNew = deepFreeze(tasksReducer(second, fetchSucceeded('new', [task(2), task(3)], 2000)));
  // …then the OLD, slow one arrives: it must not overwrite the newer result.
  expect(tasksReducer(afterNew, fetchSucceeded('old', [task(9)], 3000))).toBe(afterNew);
  expect(tasksReducer(afterNew, fetchFailed('old', 'late error'))).toBe(afterNew);
});
```

Thunk level, with **hand-resolved promises** to control the order of responses (`tasksThunks.test.ts`):

```ts
it('a slow OLD response cannot overwrite a newer one, and the old request is aborted', async () => {
  const slow = deferred<Page<Task>>();
  const fast = deferred<Page<Task>>();
  const signals: AbortSignal[] = [];
  const api = fakeApi({
    getTasks: vi.fn((query, signal?: AbortSignal) => {
      if (signal) signals.push(signal);
      return query?.q === 'r' ? slow.promise : fast.promise;
    }),
  });
  const store = makeStore(undefined, { api });

  const first = store.dispatch(fetchTasks({ q: 'r' }));
  const second = store.dispatch(fetchTasks({ q: 'report' }));
  expect(signals[0]?.aborted).toBe(true); // the newer request aborted the older one
  expect(signals[1]?.aborted).toBe(false);

  fast.resolve(page([task(7)])); // the NEW one answers first
  await second;
  slow.resolve(page([task(1), task(2), task(3)])); // the OLD one arrives late (a fake API ignores abort)
  await first;

  expect(store.getState().tasks.items.map((t) => t.id)).toEqual([7]); // the newer result survived
});
```

The fake API **ignores** the abort signal on purpose, and still delivers the old response. That proves the **reducer check** alone keeps the state correct, even when an abort comes too late.

## 5. 🔬 Replaying 18.10 with the real store code

Same timings (`r`: 900 ms, `report`: 100 ms), the real mock API, a store created by `store.ts`, and the fixed `fetchTasks`. The store's `tasks` states seen by a subscriber: `loading:22 → loading:22 → succeeded:1`. The final list contained only *"Write quarterly report"*. The mock's log showed the `q=r` request **arriving at the server** but finishing without a status: the browser had aborted it.

## 6. Summary

- Give every request an id (generated outside reducers); reducers ignore results whose id isn't the current one.
- Abort superseded requests to save work, keeping the controller in a per-store `extra` holder.
- Test with controlled promise resolution: order is the variable that matters.
