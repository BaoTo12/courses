# Lecture 18.02 · The Redux Async Data Flow: UI → dispatch(thunk) → Middleware → API → dispatch(result) → Reducer

> **Section:** S18 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~20 minutes
> 🔗 Official companion reading: Fundamentals Part 6 ("Redux Async Data Flow" diagram)

## 1. The flow, for "Mark done" in TaskFlow (end of S18)

```text
 ① click "Mark done" on task 1
     │
 ② TasksPage: dispatch(toggleTaskOnServer(1))          ← toggleTaskOnServer(1) returns a FUNCTION
     │
 ③ middleware chain: crash reporter → THUNK MIDDLEWARE
     │   "it's a function": call it with (dispatch, getState, extra). Nothing reaches the reducers yet.
     ▼
 ④ the thunk runs:
     const task = getState().tasks.items.find(…)        ← read state to decide
     await extra.api.patchTask(1, { status: 'DONE' })   ← PATCH /api/tasks/1 (Axios, S13)
     │                     … 300 ms pass; the UI stays interactive …
     ▼
 ⑤ dispatch(taskUpdated(savedTask))                    ← a PLAIN action: goes through the whole chain
     │   crash reporter → thunk (not a function, next) → logger → analytics → reducers
     ▼
 ⑥ tasksReducer replaces task 1 → subscribers notified → the card re-renders "Reopen"
     │
 ⑦ dispatch(toastShown({ tone: 'success', … }))        ← another plain action: uiReducer adds the toast
```

Verified in the reference app, the console showed:

```text
[api] PATCH /tasks/1 → 200 in 474 ms
[redux] tasks/taskUpdated {…}
[redux] ui/toastShown {…}
```

Notice what the logger **doesn't** show: the thunk itself. The thunk middleware runs **before** the logger in TaskFlow's chain (16.11), and it never passes functions on with `next`.

## 2. What changed compared to S17

| | S17 (`useTaskOperations`) | S18 (thunks) |
|---|---|---|
| Called from | Components only (a hook) | Anywhere with `dispatch`: components, other thunks, middleware |
| Reads state | Via props/selectors in the component | `getState()` inside the thunk |
| Dependencies (the API) | Imported by the hook module | **Injected** as `extra` (18.04): fakes in tests |
| Toasts | The component calls `show()` | The thunk can dispatch `toastShown` (the toast list is now in Redux, 18.12) |
| Returns | A promise from the hook function | `dispatch(thunk)` returns the thunk's promise |

## 3. Two kinds of dispatch in one flow

- **`dispatch(thunk)`** at step ②: starts async work. Nothing is recorded in the DevTools for it.
- **`dispatch(plainAction)`** at steps ⑤ and ⑦: reports what **happened**. These are the events you see in the DevTools and in reducer tests.

The DevTools therefore show the **results** of async logic as a sequence of events: `fetchStarted`, `fetchSucceeded`/`fetchFailed`, `taskUpdated`… You can still replay them, because they're plain objects.

## 4. Summary

- UI dispatches a thunk → the thunk middleware calls it → it talks to the API → it dispatches plain actions → reducers update state → UI re-renders.
- Thunks can read state, call injected services, and dispatch any number of actions.
- The DevTools log contains the plain actions, not the thunks.
