# Lecture 08.12 · 🛠 Build: `useDebounce`, `useLocalStorage`, and a Debounced Search Box

> **Section:** S08 · **Type:** 🛠 Build · **Track:** ★ Core · **Time:** ~40 minutes
> **Project feature:** search by title (filtered 300 ms after typing stops); theme preference survives reloads
> Verified in the reference app: 100 ms after typing "report", all 8 cards were still shown; at 500 ms, 1 card; theme stored as `"light"` under `taskflow.theme`.

---

## 1. ✍️ `src/hooks/useDebounce.ts`

```ts
import { useEffect, useState } from 'react';

/** Returns `value`, but only after it has stopped changing for `delayMs`. */
export function useDebounce<T>(value: T, delayMs = 300): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delayMs);
    return () => clearTimeout(timer); // a newer value cancels the pending update
  }, [value, delayMs]);

  return debounced;
}
```

How it works, keystroke by keystroke ("rep", then "repo" 100 ms later):

```text
value="rep"   → effect: start timer A (300 ms)
value="repo"  → cleanup: clear timer A → effect: start timer B
…300 ms of silence…
timer B fires → setDebounced("repo") → re-render with the debounced value
```

The **cleanup** is the debounce: every new value cancels the previous timer. Generic `<T>` makes it work for strings, numbers or filter objects.

Why debounce? Filtering 8 tasks is instant, but in S13+ the search goes to the **server**. Without debouncing, typing "quarterly" would send 9 requests.

## 2. ✍️ `src/components/SearchBox.tsx`

```tsx
import { useId } from 'react';

interface SearchBoxProps {
  value: string;
  onChange: (value: string) => void;
}

export function SearchBox({ value, onChange }: SearchBoxProps) {
  const id = useId();
  return (
    <div className="form-field">
      <label className="form-field__label" htmlFor={id}>
        Search
      </label>
      <input
        id={id}
        className="form-field__input"
        type="search"
        placeholder="Search by title…"
        value={value}
        onChange={(e) => onChange(e.target.value)}
      />
    </div>
  );
}
```

- A **controlled input** (`value` + `onChange`): the parent owns the text (S11 covers forms in depth).
- **`useId()`** generates a unique, stable ID to connect `<label htmlFor>` and `<input id>`. Hard-coding `id="search"` breaks if the component appears twice on a page (08.14).
- It uses the design system's `.form-field` classes from 02.10.

## 3. ✍️ Wire it into `App.tsx`

```tsx
const [query, setQuery] = useState('');
const debouncedQuery = useDebounce(query, 300);

// in the 'succeeded' branch:
const visible = filterTasks(state.data, {
  status: statusFilter ?? undefined,
  q: debouncedQuery,

// above the list:

```

The input shows `query` **immediately** (so typing feels instant); filtering uses `debouncedQuery`. Two values for two purposes.

## 4. ✍️ `src/hooks/useLocalStorage.ts`

```ts
import { useEffect, useState } from 'react';

/**
 * useState that persists to localStorage.
 * Storage can be unavailable (private mode, blocked cookies, quota) or contain garbage:
 * every access is wrapped, and `isValid` guards what we read back (untrusted input!).
 */
export function useLocalStorage<T>(
  key: string,
  initialValue: T,
  isValid: (value: unknown) => value is T,
) {
  const [value, setValue] = useState<T>(() => {
    try {
      const raw = window.localStorage.getItem(key);
      if (raw === null) return initialValue;
      const parsed: unknown = JSON.parse(raw);
      return isValid(parsed) ? parsed : initialValue;
    } catch {
      return initialValue;
    }
  });

  useEffect(() => {
    try {
      window.localStorage.setItem(key, JSON.stringify(value));
    } catch {
      // storage unavailable or full: keep working in memory
    }
  }, [key, value]);

  return [value, setValue] as const;
}
```

### Why each piece

- **Lazy initial state** (08.02): read storage **once**, not on every render.
- **`try/catch`** around every access: `localStorage` can **throw** (disabled storage, some privacy modes, quota exceeded), and `JSON.parse` throws on corrupt data.
- **`isValid` type guard** (06.08): storage is **user-editable** (DevTools → Application → Local Storage). Treat it as untrusted input: `'"purple"'` isn't a `ThemePreference`, so fall back to the default.
- **The effect** writes on every change: synchronising React state → browser storage (a legitimate external system, 08.05).
- **`as const`** makes the return type a tuple `readonly [T, Dispatch<SetStateAction<T>>]`, not an array of a union, so destructuring keeps both types.

Now switch `ThemeProvider` to `useLocalStorage` (08.10's code). Reload the page after choosing "Dark": it stays dark.

> 🛡 **What never goes in localStorage:** session tokens, passwords, personal data. Any script on the page (including injected ones via XSS) can read it. S24 compares localStorage, JS-readable cookies and HttpOnly cookies. A theme preference is harmless. In S24 it moves to a **cookie** so the **JSP portal** can read the same preference on the server.

## 6. Summary

- `useDebounce`: the effect cleanup cancels pending timers, so only the last value "wins".
- Controlled `SearchBox` + `useId` for accessible labels.
- `useLocalStorage`: lazy read, guarded parse, `try/catch`, effect to persist; storage is untrusted.
