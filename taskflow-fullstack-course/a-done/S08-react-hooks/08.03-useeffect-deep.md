# Lecture 08.03 · `useEffect` in Depth: Synchronising with External Systems, Dependencies, Cleanup, StrictMode

> **Section:** S08 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~35 minutes
> 🔗 Official reading: react.dev → Learn → "Synchronizing with Effects", "Lifecycle of Reactive Effects"

---

## 1. What an effect is for

Rendering must be pure (07.04). But apps must talk to the outside world: the network, timers, the DOM directly, `localStorage`, subscriptions, `document.title`. An **effect** is code that runs **after React commits** the render to the screen, to **synchronise** your component with something **outside React**.

```tsx
useEffect(() => {
  document.title = `TaskFlow (${openCount} open)`;
}, [openCount]);
```

Read it as: *"keep `document.title` in sync with `openCount`."* That's the right mental model: **synchronisation**, not "run this on mount".

## 2. When does it run?

```text
render (pure) → commit (DOM updated) → browser paints → effects run
```

- After the **first** commit (mount).
- After every commit where a **dependency changed** (compared with `Object.is`).
- **Cleanup** (the function you return) runs **before** the effect re-runs and when the component **unmounts**.

| Dependency array | Effect runs |
|---|---|
| `[a, b]` | After mount, and whenever `a` or `b` changes |
| `[]` | After mount only (and cleanup on unmount) |
| *(omitted)* | After **every** render (rarely what you want) |

## 3. Dependencies are not a choice: they're what the effect reads

Every reactive value (props, state, and values derived from them) used inside the effect **must** be in the dependency array. Otherwise the effect uses **stale** values (08.02 §4). Linters flag missing dependencies.

```tsx
useEffect(() => {
  const id = setTimeout(() => setDebounced(value), delayMs);
  return () => clearTimeout(id);
}, [value, delayMs]);   // both are read inside → both listed
```

If an effect re-runs too often, the fix is **not** to lie about dependencies. Fix the **cause**: move a function or object inside the effect, use a functional update, or reconsider whether it should be an effect at all (08.05). The infinite loop in 08.17 is caused by exactly this.

## 4. Cleanup

Anything an effect **starts**, its cleanup should **stop**:

| Effect starts | Cleanup |
|---|---|
| `setTimeout` / `setInterval` | `clearTimeout` / `clearInterval` |
| `addEventListener` | `removeEventListener` |
| A fetch | `controller.abort()` |
| A subscription (WebSocket, store) | Unsubscribe |

Without cleanup: timers fire after unmount, listeners pile up, and **stale responses overwrite newer ones** (the race condition in 08.18).

## 5. StrictMode runs effects twice in development

In development, `<StrictMode>` deliberately does **mount → cleanup → mount** for every component. If your effect + cleanup are correct, the user sees no difference. If cleanup is missing, you'll see duplicated subscriptions or requests. **That's the point**: it surfaces bugs that would otherwise appear in real situations (navigating away and back, React re-mounting components).

You can see it in TaskFlow's reference app. Loading the page with the `useTasks` hook (08.04) produces this in the Network panel:

```text
GET /db.json  [FAILED: net::ERR_ABORTED]   ← first mount's request, aborted by the cleanup
GET /db.json  → 200 OK                     ← second mount's request
```

That's correct behaviour, not a bug. In production builds, StrictMode's double invocation doesn't happen.

## 6. Effects run after paint

Effects run **after** the browser paints, so they don't block the screen. The downside: if an effect changes something visible (e.g. measuring and repositioning a tooltip), the user may see a flicker. For that rare case there's `useLayoutEffect` (08.14).

## 7. Summary

- Effects synchronise a component with **external systems**, after commit and paint.
- Dependencies = every reactive value the effect reads (compared with `Object.is`).
- Cleanup undoes what the effect started; it runs before re-running and on unmount.
- StrictMode's dev-only mount→cleanup→mount reveals missing cleanups.
- Fix over-running effects by fixing causes, not by removing dependencies.

## 8. Check yourself

1. Why does `useEffect(() => {…}, [filter])` re-run when `filter` is `{ status: 'TODO' }` recreated every render?
2. An effect logs twice in development only. Bug or feature?

<details>
<summary>Answers</summary>

1. Dependencies are compared with `Object.is`: a **new object** each render is a different reference, even with identical contents (04.03). Depend on primitives (`filter.status`), or create the object inside the effect / memoise it (08.13).
2. **Feature**: StrictMode's development-only mount→cleanup→mount. Make sure the cleanup correctly undoes the effect; production runs it once.

</details>
