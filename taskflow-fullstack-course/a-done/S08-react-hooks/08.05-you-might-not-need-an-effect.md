# Lecture 08.05 · You Might Not Need an Effect: Derived State and Event Handlers vs Effects

> **Section:** S08 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes
> 🔗 Official reading: react.dev → Learn → "You Might Not Need an Effect"

---

## 1. The most common React mistake

Effects are for synchronising with **external** systems. Many developers use them for things that aren't external at all, which causes extra renders, flicker, bugs and infinite loops.

Ask: **"Is there something outside React I'm synchronising with?"** If not, you probably don't need an effect.

## 2. Anti-pattern 1: storing derived data with an effect

```tsx
// ❌
const [tasks, setTasks] = useState<Task[]>([]);
const [visibleTasks, setVisibleTasks] = useState<Task[]>([]);

useEffect(() => {
  setVisibleTasks(filterTasks(tasks, { status: statusFilter ?? undefined }));
}, [tasks, statusFilter]);
```

What happens on each change: render with **stale** `visibleTasks` → commit → effect → `setVisibleTasks` → **second render**. That's two renders instead of one, a frame where the list is out of date, and two sources of truth.

```tsx
// ✅ compute during render
const visibleTasks = filterTasks(tasks, { status: statusFilter ?? undefined });
```

If it's expensive, memoise it (08.13, and `createSelector` in S21). Don't store it.

## 3. Anti-pattern 2: reacting to a user action with an effect

```tsx
// ❌ "when saved becomes true, show a toast"
const [saved, setSaved] = useState(false);
useEffect(() => {
  if (saved) showToast('Saved!');
}, [saved]);

function handleSave() {
  save();
  setSaved(true);
}
```

The toast happens because the **user clicked Save**, which is an **event**, not because the component is "in a saved state". Put event logic in the **event handler**:

```tsx
// ✅
async function handleSave() {
  await save();
  showToast('Saved!');
}
```

Effects run because a component **displayed**; handlers run because a user **did something**. Mixing them leads to bugs like the toast re-appearing when the component remounts.

## 4. Anti-pattern 3: resetting state when a prop changes

```tsx
// ❌
useEffect(() => {
  setDraft(task.title);
}, [task.id]);
```

The first render still shows the old draft, then it flickers to the new one. Alternatives:
- Give the component a **`key`** (07.11): `<TaskEditor key={task.id} task={task} />`. A new key = a fresh instance with fresh state.
- Or initialise the draft when editing **starts** (in the handler). That's what the 08.15 solution does.

## 5. Anti-pattern 4: chains of effects

Effect A sets state that triggers effect B, which sets state that triggers effect C. Each step is a render. Compute everything in one place: in the handler, or during render.

## 6. Legitimate uses of effects in TaskFlow

| Effect | External system |
|---|---|
| Fetch tasks when the page mounts (08.04) | The network. (Later, RTK Query does this for you, S22.) |
| Set `data-theme` on `<html>` from the theme preference (08.10) | The DOM outside React's root |
| Persist the theme to `localStorage` (08.12) | Browser storage |
| Debounce timer (08.12) | Timers |
| Focus/select an input when editing starts (08.15) | The DOM (imperative focus API) |
| `document.title` | The DOM outside React's root |

## 7. Summary

- Effects synchronise with **external** systems. No external system → probably no effect.
- Derived data → compute during render (memoise if expensive).
- User-action consequences → event handlers.
- Reset state on identity change → `key`.
- Avoid effect chains.
