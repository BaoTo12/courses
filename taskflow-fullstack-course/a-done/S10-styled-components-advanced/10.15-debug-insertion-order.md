# Lecture 10.15 · 🐞 Debug: an SCSS Rule Unexpectedly Overrides a Styled Component (Insertion Order + Specificity)

> **Section:** S10 · **Type:** 🐞 Debug · **Track:** ＋ Extended · **Time:** ~20 minutes

---

## Symptom

A developer adds a one-off tweak by styling a BEM button with styled-components:

```tsx
const WideButton = styled(Button)`
  padding: 12px 32px;      /* wider than the design-system .btn */
`;
```

On the task list page it looks right. But on the **Reports** page, which is **lazy-loaded** (code splitting, S12), the same `WideButton` has the normal narrow padding. DevTools shows `.btn { padding: 8px 16px }` **winning** over the styled rule. Both selectors are single classes.

## Investigation checklist

1. What's the specificity of `.btn` and of the styled class `.hash`? (02.13)
2. With equal specificity, what decides the winner?
3. In what order are `<style>`/`<link>` elements in `<head>` on each page? (Elements panel)
4. When does a lazy-loaded chunk's CSS get added to the page?

## Explanation

- `.btn` and `.hash` both have specificity (0,1,0). With equal specificity, **the rule that appears later in the document wins**.
- Observed order in TaskFlow's dev server on initial load:

```text
6: <style data-vite-dev-id>          ← global SCSS (main.scss)
7–9: <style data-vite-dev-id>        ← CSS Modules loaded at startup
10: <style data-styled="active">     ← styled-components (inserted at runtime, LAST)
```

  So on the initial page, styled rules come later and win.
- A **lazy-loaded** route brings its **own CSS** (for example, a CSS Module that also `@use`s or duplicates button rules, or a chunk that re-includes part of the design system). That CSS is appended to `<head>` **when the chunk loads**, which is **after** the styled-components tag. Now the SCSS rule is later and wins.
- The result depends on **navigation history and bundling**, which is why it's so confusing.

## Fixes

1. **Don't style the same element with both systems** (STYLING.md rule 8, 10.07). Better: add a proper **modifier** to the design system (`.btn--wide`) or a `size` prop.
2. If you must bridge, **raise specificity deliberately and locally**: `&&` in styled-components doubles the generated class (`.hash.hash`, specificity (0,2,0)):
   ```tsx
   const WideButton = styled(Button)`
     && { padding: 12px 32px; }
   `;
   ```
3. Make sure shared design-system CSS is loaded **once**, globally, never re-included by lazy chunks (03.10: `abstracts` emits no CSS, and only `main.scss` includes components).

## Lesson

"It works on page A but not page B" + "equal specificity" → **check source order**. Order-dependent styling is fragile. Design it out.
