# Lecture 10.07 · SCSS vs styled-components: the Decision Guide for a Team That Uses Both

> **Section:** S10 · **Type:** 📖 Theory · **Track:** ★ Core · **Time:** ~25 minutes

---

## 1. Why a written guide matters

When a codebase has two styling systems, every new component raises the question "which one?". Without an agreed answer, you get both systems styling the same thing, specificity fights, and reviewers arguing taste. The fix is a short, explicit **STYLING.md** that anyone can apply in ten seconds.

## 2. The decision flow

```text
Is the style needed by the JSP portal (or any non-React page)?
 ├─ yes → SCSS design system (global BEM in styles/)
 └─ no
     Is it global (element defaults, layout shell, utilities)?
      ├─ yes → SCSS base/layout/utilities (or the tiny GlobalStyle for React-only globals)
      └─ no
          Does it depend on props/state values that vary a lot or continuously?
           ├─ yes → styled-components (transient $props, theme)
           │        (continuous per-frame values → style prop / CSS custom property)
           └─ no → finite variants of a React-only component
                    → CSS Module (static) or styled-components (if it needs theme/props)
```

## 3. TaskFlow's `STYLING.md` (commit this to `frontend/`)

```markdown
# Styling rules (TaskFlow Web)

1. **Tokens live in SCSS** (`styles/abstracts/_tokens.scss`). Never hard-code a colour, spacing
   or radius in a component. SCSS: `theme('x')`, `space(n)`. styled-components: `theme.colors.x`,
   `theme.space(n)`.
2. **Shared components are SCSS (BEM)** and wrapped by thin typed React components
   (`Button`, `StatusBadge`, cards, forms). They must also work in the JSP portal.
3. **React-only static structure → CSS Modules** (`*.module.scss` with `@use '@styles/abstracts' as *;`).
4. **Dynamic, prop-driven components → styled-components** with **transient `$props`** only,
   defined at module level, reading `props.theme`.
5. **Continuous values** (drag, progress per frame) → `style` prop or a CSS custom property.
6. **Untrusted values never go into CSS unvalidated** (allow-list: `#rrggbb`, known enums).
7. **No second reset.** Global element styles belong to SCSS `base/`; `GlobalStyle` is for React-only globals.
8. **One component, one system.** Don't style the same element with SCSS *and* styled-components
   (except the documented `styled(Button)` bridge for one-off tweaks).
```

## 4. Specificity and load order when both exist

- **Global SCSS** is imported once in `main.tsx`, so it's in the page's `<link>`/`<style>` from the start.
- **styled-components** insert their rules **later**, at runtime, in their own `<style>` tag.
- Both use **single-class selectors** (BEM `.card__title` vs `.hash`), so specificity is equal and **order decides**: styled-components' tag usually comes later and wins. "Usually" is the problem: in production builds, CSS files may be ordered differently, and relying on it is fragile. That's rule 8. 10.15 is the debug lecture.

## 5. Summary

- Write down the decision rules; the flow is JSP-needed → SCSS; global → SCSS; dynamic → styled-components; static React-only → CSS Modules.
- Tokens in SCSS; both systems read them.
- Never style one element with both systems; order-dependent specificity is fragile.
