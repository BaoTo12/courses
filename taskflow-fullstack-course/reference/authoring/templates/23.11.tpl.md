# Lecture 23.11 · 🛠 Build: Logout Clears the Slices *and* the RTK Query Cache

> **Section:** S23 · **Type:** 🛠 Build · **Track:** ★ Core · **Time:** ~25 minutes
> **Project feature:** one `clearUserData()` thunk that every logout path uses, with a test for the security rule from 23.10.
> Verified: `src/features/api/taskCache.test.ts` ("23.11 clearUserData"), `tsc`, lint.

---

## 1. From two dispatches to one thunk

In 22.09, `AuthProvider`'s logout dispatched `loggedOut()` and `resetApiState()` itself. That works, but S24 adds a **second** logout path (a 401 from the API ends the session), and S38 a third (the server says the session expired). Security rules that must hold on every path belong in **one** function:

✍️ `src/features/auth/clearUserData.ts`

{{file:features/auth/clearUserData.ts:ts}}

- It's a thunk (16.08), so it can dispatch several actions and later read state.
- It lives in its own file, not in `authActions.ts`, because `authActions.ts` is imported by **every slice** (for `loggedOut`). Importing `apiSlice` there would create an import cycle through the slices (20.18).

✍️ In `src/auth/AuthProvider.tsx`, `logout` now does:

```ts
      logout: () => {
        setUser(null);
        dispatch(clearUserData()); // slices AND the RTK Query cache: the next user must not see this user's data (23.11)
      },
```

## 2. The test: write the rule down

The security rule from 23.10 should fail loudly if someone "simplifies" the logout later. The test, in `src/features/api/taskCache.test.ts`:

```ts
  it('23.11 clearUserData: slices reset, the cache is emptied, and a response still in flight is dropped', async () => {
    const { store } = setup(task(1));
    await store.dispatch(apiSlice.endpoints.getTask.initiate(1));
    store.dispatch(sortChanged('title', 'desc'));
    const inFlight = store.dispatch(apiSlice.endpoints.getTasks.initiate({ size: 100 })); // user A's request…

    store.dispatch(clearUserData()); // …A logs out before it answers
    await inFlight;
    await flush();

    expect(store.getState().api.queries).toEqual({});
    expect(store.getState().listPrefs.sort).toEqual({ key: 'dueDate', direction: 'asc' });
    inFlight.unsubscribe();
  });
```

- It uses a **real** cache entry, a changed **preference**, and a request **in flight** at logout: the three things that can leak.
- `toEqual({})` is strict on purpose. A new endpoint whose data survives logout makes it fail.

```bash
npx vitest run src/features/api/taskCache.test.ts
```
