# Lecture 41.15 · 🛡 Brute Force: Per-Account and Per-IP Throttling (In Memory, Thread-Safe)

## 1. The throttle

✍️ `src/main/java/com/taskflow/security/LoginThrottle.java`

{{file:@reference/taskflow/backend/src/main/java/com/taskflow/security/LoginThrottle.java:java}}

TaskFlow's settings (in `AppContextListener`): **5** failures per account or **20** per IP address, in a **15-minute** window.

| Key | Stops |
|---|---|
| per **account** | many guesses at one user's password, from any number of machines |
| per **IP** | one machine trying a few passwords on many accounts ("password spraying") |

## 2. Details that matter

- **Blocked means blocked:** during the window, even the **right** password gets 429. Otherwise the attacker learns the password the moment they hit it.
- `ConcurrentHashMap.compute` is atomic per key (38.07's lesson): parallel failures are all counted.
- The `Clock` is injected: a test can move time forward instead of waiting 15 minutes.
- Success resets the account's counter; the IP's counter decays with its window.

## 3. The trade-offs

| Risk | Mitigation |
|---|---|
| **lockout as a weapon**: an attacker locks a real user out on purpose | short windows (15 min), not permanent locks; notify the user; let admins unlock |
| shared IPs (offices, mobile carriers) hit the IP limit | a higher IP limit than the account limit (20 vs 5) |
| a cluster: each server counts separately | a shared store (Redis) or throttling at the proxy |
| memory growth from sprayed usernames | windows are dropped when they expire and are touched; a periodic cleanup for large sites |

## ✅ Recap

Count failures per account and per IP in a window; refuse **all** attempts while over the limit; keep windows short to limit lockout abuse.
