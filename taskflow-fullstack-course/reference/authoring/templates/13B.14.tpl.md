## 1. Why test types at all?

Most of your tests check **behaviour**: given this input, the UI shows that. But a shared component's **types** are also a contract:

- `SelectField` must hand `onChange` a `TaskStatus`, not a `string` (13B.08).
- `ButtonLink` must *reject* a missing `to` (13B.09).
- `DataTable` must type each column's `render` by its key (13B.10).

If someone "simplifies" `SelectField`'s props to `onChange: (value: string) => void`, every behaviour test still passes: the DOM is identical. Only a **type test** notices that 30 call sites just lost their safety. In a design system or a shared library, type tests are as important as render tests.

## 2. Two tools

### `expectTypeOf` (Vitest): positive and negative assertions about types

```ts
import { expectTypeOf } from 'vitest';

expectTypeOf(status).toEqualTypeOf<TaskStatus>();              // exactly this type
expectTypeOf(e.currentTarget).toExtend<HTMLButtonElement>();   // assignable to it
expectTypeOf<ButtonProps>().toHaveProperty('ref');             // has this key
expectTypeOf(labels).not.toHaveProperty('IN_PROGRESS');        // negation
expectTypeOf(location.state).toBeAny();                         // detect `any` leaks
expectTypeOf(useCounter).returns.toEqualTypeOf<{ count: number }>();
expectTypeOf<Parameters<typeof dispatch>[0]>().toEqualTypeOf<CounterAction>();
```

At **runtime** these calls do nothing. The checking happens when `tsc` compiles the test file: a wrong assertion is a **compile error**.

### `// @ts-expect-error`: "this line must NOT compile"

```tsx
// @ts-expect-error: 'BLOCKED' is not a TaskStatus
<SelectField label="Status" options={TASK_STATUSES} value="BLOCKED" … />
```

- If the line has a type error, the directive suppresses it: ✓.
- If the line **compiles**, TypeScript reports `Unused '@ts-expect-error' directive`: ✗. That's the test failing, because the type became too loose.

Always write the **reason** after the colon. It documents what you expect, and a reviewer can check that the *right* error is the one being suppressed.

⚠️ `@ts-expect-error` only proves *some* error happens on the next line, not *which* one. Keep each negative case to a single, small expression, so an unrelated error (a typo in another prop) can't satisfy it by accident.

## 3. Where the type-checking happens in our setup

```text
npm test      → Vitest: runs the runtime assertions, strips types WITHOUT checking them
npm run build → tsc -b: type-checks src/ INCLUDING *.test.tsx (tsconfig.app.json "include": ["src"])
```

So a broken type test fails `npm run build`, not `npm test`. That's fine as long as **CI runs both**. Alternatives:
- `vitest --typecheck` runs `tsc` on test files as part of Vitest and reports type assertions as test results (useful in a library, where you may keep type tests in `*.test-d.ts` files).
- A separate `"typecheck": "tsc -b"` script, run as its own CI step (clearest).

Enterprise CI for a React + TS app typically runs, in parallel: `tsc -b` (or `typecheck`), `lint`, `test`, `build`. A PR can't merge unless all four are green. **Type errors in CI are not warnings.**

## 4. Rendering without a browser: `renderToStaticMarkup`

The runtime half of our tests uses `react-dom/server`:

```tsx
const html = renderToStaticMarkup(<SelectField … value="IN_PROGRESS" />);
expect(html).toContain('<option value="IN_PROGRESS" selected="">In progress</option>');
```

It renders components (hooks included) to an HTML string in Node, with no DOM and no jsdom setup. Perfect for "what does it render" and for checking that type-level examples also work at runtime. It can't test interaction (clicks, typing, effects that run after mount): that needs a DOM environment and Testing Library (S27).

Patterns worth copying:
- **`const compiles = (check) => …` / `const check = () => (<JSX/>)`**: JSX inside a function that is type-checked but never rendered. Useful for negative cases (`@ts-expect-error` lines) that would crash if rendered.
- **Type assertions inside callbacks** (`getLabel={(priority) => { expectTypeOf(priority)… }}`): proves *inference* at the exact spot a caller relies on it.
- **One `@ts-expect-error` per small expression**, each with a reason.

## 7. What NOT to type-test

- Your **domain logic**: test behaviour (`filterTasks` returns the right tasks), not that it returns `Task[]`. The compiler already enforces signatures at every call site.
- **Private helpers**: types that no other module depends on.
- **Library internals**: test the contract *you* rely on (`useParams` gives `string | undefined`), not the library's whole type surface.

Type tests pay off on **public, reused** APIs: design-system components, shared hooks, SDKs, generated API clients.

## 8. Summary

- Type contracts of shared components deserve tests: `expectTypeOf` for positive cases, `@ts-expect-error: reason` for negative ones.
- In our setup, `tsc -b` checks type tests; Vitest runs the runtime half. CI must run both.
- `renderToStaticMarkup` tests rendering in Node without a DOM.
- Keep negative cases tiny, so the right error is the one expected.
