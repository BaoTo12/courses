# Lecture 24.06 · 🛠 Build: Persist the Theme and the List Preferences in Cookies

> **Section:** S24 · **Type:** 🛠 Build · **Track:** ★ Core · **Time:** ~50 minutes
> **Project feature:** the theme and the list's sort and page size survive a reload. Invalid or edited cookies fall back to the defaults.
> Verified: `src/api/cookies.test.ts` ("list preferences cookie": the listener writes it, logout removes it, bad JSON and unknown keys are ignored), `tsc`, lint.

---

## 1. The theme: a cookie-backed `useState`

✍️ `src/hooks/useCookieState.ts`

{{file:hooks/useCookieState.ts:ts}}

In `src/theme/ThemeProvider.tsx`, one line changes:

```ts
  // S24: a cookie instead of localStorage (24.06), so the server can read the theme too.
  const [preference, setPreference] = useCookieState<ThemePreference>('theme', 'system', isThemePreference);
```

- **Lazy initial state** (`useState(() => …)`, 08.03): the cookie is read once, on mount.
- **Validated**: `isThemePreference(raw)`. A cookie edited to `purple` falls back to `'system'`.
- **Why move from localStorage at all?** The theme is a preference **the server can use**: the JSP admin portal (S44) can render `<html data-theme="dark">` straight away, with no flash of the wrong theme. That's the one good reason to put a preference in a cookie.

## 2. The list preferences: write with a listener, restore at start-up

✍️ `src/features/listPrefs/listPrefsCookie.ts`

{{file:features/listPrefs/listPrefsCookie.ts:ts}}

- **Writing** is a **reaction** to `sortChanged`/`pageSizeChanged`, so it's a listener (21.14). `SortControl` and `Pager` don't know cookies exist.
- **After the reducer:** the effect reads `getState().listPrefs`, the new state, not the action payload. One source of truth.
- **Short keys** (`sortKey`, `direction`, `pageSize`) because the cookie rides along with every request (24.02 §4).
- **Reading** validates **each field** against the allowed values (`find` returns the typed value or `undefined`). A tampered cookie can't inject `sortKey: "owner"` into a server query.
- **Logout** removes it: the slice resets on `loggedOut` (20.11), so its saved copy must too, or the next reload would bring back the previous user's preferences.

Register it in `src/app/listeners.ts`:

```ts
  addListPrefsCookieListener(startAppListening); // 24.06
```

And restore at start-up in `src/app/store.ts`:

```ts
/** State restored from cookies at start-up (24.06): only what's there AND valid. */
function restoredState(): Partial<RootState> {
  const listPrefs = readListPrefsCookie();
  return listPrefs ? { listPrefs } : {};
}

export const store = makeStore(restoredState());
```

- `preloadedState` (14.08) is the standard way to start a store from saved data.
- `makeStore()` in tests still starts clean. Only the app's store reads cookies.

## ✅ Checkpoint

Sort by title (descending), pick 50 per page, reload: both are kept. In DevTools → Application → Cookies, edit `tf_list_prefs` to `{"sortKey":"x"}` and reload: the defaults are back, with no crash.
