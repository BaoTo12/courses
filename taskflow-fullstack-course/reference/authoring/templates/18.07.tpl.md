# Lecture 18.07 · 🛠 Build: `saveNewTask(request)`: the Server Generates the ID; the Reducer Adds the Returned Task

> **Section:** S18 · **Type:** 🛠 Build · **Track:** ★ Core · **Time:** ~35 minutes
> **Project feature:** `saveNewTask`, `saveTask` (PUT), `saveTaskChanges` (PATCH) thunks; the New/Edit pages and inline title editing use them
> Verified by the thunk tests (a fake API returns id 99; the store then contains task 99) and in the browser.

---

## 1. ✍️ The write thunks (in `src/features/tasks/tasksThunks.ts`)

```ts
/** POST. Rejects with an ApiRequestError: the form page decides how to show it. */
export const saveNewTask =
  (request: CreateTaskRequest): AppThunk<Promise<Task>> =>
  async (dispatch, _getState, { api }) => {
    const created = await api.createTask(request);
    dispatch(taskAdded(created));
    return created;
  };

/** PUT. Rejects on failure. */
export const saveTask =
  (id: number, request: CreateTaskRequest): AppThunk<Promise<Task>> =>
  async (dispatch, _getState, { api }) => {
    const saved = await api.updateTask(id, request);
    dispatch(taskUpdated(saved));
    return saved;
  };

/** PATCH (e.g. an inline title edit). Rejects on failure. */
export const saveTaskChanges =
  (id: number, changes: UpdateTaskRequest): AppThunk<Promise<Task>> =>
  async (dispatch, _getState, { api }) => {
    const saved = await api.patchTask(id, changes);
    dispatch(taskUpdated(saved));
    return saved;
  };
```

- **The server's task goes into the store**, never the request (17.11 §3): the server assigned `id`, `ownerId` and the timestamps.
- **They reject on failure.** No `try/catch` inside: the `ApiRequestError` from the API layer (13.07) propagates to the caller, which is a form page that knows how to show it.
- **They resolve with the saved task**, so the page can navigate to it.

## 2. ✍️ `src/pages/NewTaskPage.tsx`

{{file:pages/NewTaskPage.tsx:tsx}}

`await dispatch(saveNewTask(…))` works because the thunk middleware returns the thunk's promise (18.03), and `AppDispatch` knows it (18.08): `created` is typed `Task`.

`EditTaskPage` changes the same way: `await dispatch(saveTask(existing.id, toCreateRequest(values, existing.categoryId)))`. `TasksPage`'s inline title edit uses `await dispatch(saveTaskChanges(id, { title }))` inside its existing `try/catch`.

## 3. Test it with a fake API (preview of 18.13)

```ts
it('saveNewTask resolves with the SERVER task and adds it to the store', async () => {
  const api = fakeApi();                        // createTask resolves with { ...task(99), ...request }
  const store = makeStore(undefined, { api });
  const created = await store.dispatch(
    saveNewTask({ title: 'New', description: '', status: 'TODO', priority: 'LOW', dueDate: null, categoryId: null }),
  );
  expect(created.id).toBe(99);                  // assigned by the (fake) server
  expect(store.getState().tasks.items.map((t) => t.id)).toEqual([99]);
});
```

No server, no network, no rendering. The thunk, the middleware chain and the reducer run for real; only the API is fake.

## 4. Summary

- Write thunks call the API, dispatch what the server returned, and resolve with it.
- They reject on failure; the calling page shows the error.
- `await dispatch(thunk)` gives typed results to components.
