# Lecture 21.05 · 🛠 Build: `selectVisibleTaskIds`, `selectTaskStats` and a Sort Control

> **Section:** S21 · **Type:** 🛠 Build · **Track:** ★ Core · **Time:** ~75 minutes
> **Project feature:** the list is sorted by the user's preference (due date, priority, title; ↑/↓), filtered by the URL, and computed by memoized selectors instead of in render.
> Verified: `src/features/tasks/taskListSelectors.test.ts` (5 tests), `tsc`, lint; in the browser, choosing "Title" re-ordered the 22 cards alphabetically (*Archive old Jira epics, Book dentist appointment, Book flights for conference…*) with **0** card re-renders (21.03 §4).

## 1. Where each piece of the list's state lives

| Data | Lives in | Why |
|---|---|---|
| tasks | `tasks` slice | server data |
| status / category / search filters | the **URL** | shareable, survives reload, Back works (12.03) |
| sort key and direction | `listPrefs` slice | a **preference**: the user's habit, not part of a shared link (15.12). Saved to a cookie in 24.06. |

The visible list is **derived** from all three. The URL values are not in the store, so they reach the selector as an **argument**.

## 2. ✍️ `src/features/tasks/taskListSelectors.ts`

{{file:features/tasks/taskListSelectors.ts:ts}}

Step by step:

1. **`selectSort`** returns an existing object from the state (no `createSelector` needed, 21.09).
2. **`selectSortedTasks`** depends on the tasks and the sort. `sortTasks` uses `toSorted`, which returns a new array: memoization makes it the **same** array until one of the two inputs changes.
3. **`selectVisibleTaskIds`** composes on `selectSortedTasks` (21.06) and takes the filter as an argument. Its three extra input selectors return **primitives** (`filter.status`, `filter.categoryId`, `filter.q`), so a component can pass a brand-new `{ … }` literal on every render and still hit the cache (verified, *"a new filter object with the same values hits the cache"*).
4. It returns **ids**, not tasks: the list only needs the order; each card selects its own task (21.11).
5. **`keepSameIds`** (`resultEqualityCheck`, 21.08): after an edit that doesn't change which tasks are visible, the result function runs again, but the selector hands back the **previous** array (verified: `toBe(first)`). The list component then sees no change at all.
6. **`makeSelectTaskIdsByStatus`** is a factory for the board's columns (21.07).
7. **`selectTaskStats`** replaces the page's `items.length` and `items.filter(…DONE).length`.

## 4. ✍️ `src/pages/TasksPage.tsx`

{{file:pages/TasksPage.tsx:tsx}}

What changed since S20:

- `items` is gone. The page selects **`stats`** (memoized) and **`visibleIds`** (memoized, filter passed as an argument). Nothing in render filters or sorts any more.
- `handleToggle` and `handleEditTitle` are wrapped in `useCallback` (21.10). `handleEditTitle` no longer looks the task up: the "is the new title different?" check moved into `TaskCard`, which knows the current title, so the callback depends only on `dispatch` and `show`, which are stable.
- `<SortControl />` sits next to the view buttons.

And in `src/components/TaskCard.tsx`, `save()` now does the check the page used to do:

```ts
  function save() {
    setIsEditing(false);
    const title = draft.trim();
    // Nothing to save. Checked HERE, where the current title is known, so the parent's callback
    // doesn't need the task list and can stay stable for React.memo (21.11).
    if (title === '' || title === task.title) return;
    onEditTitle(task.id, title);
  }
```
- `TaskList` receives `taskIds`, and `Board` receives no tasks at all: both are rewritten in 21.11.
