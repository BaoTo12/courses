# Lecture 37.09 · Flash Messages: Surviving a Redirect via the Session, Removed After One Read

> **Section:** S37 · **Type:** 📖 Theory + 🛠 · **Track:** ★ Core · **Time:** ~25 minutes
> Verified: `S37FormsTest.aValidCreateIsPostRedirectGetWithAOneTimeFlash` (shown on the first GET, gone on the second), `.deleteIsAPostWithAFlashAndA303`

---

## 1. The problem

After PRG, "Task created." must appear on the **next** request's page. Request attributes die with the POST's request (31.06). Where can the message wait?

| Option | Verdict |
|---|---|
| a request attribute | ❌ gone after the redirect |
| the URL: `?created=1` | works for fixed messages; but the message reappears on Reload and in bookmarks, and free text in URLs invites tampering and XSS |
| **the session, removed when shown** | ✅ the "flash" pattern (Rails, Spring's `RedirectAttributes`) |

## 2. TaskFlow's `Flash`

✍️ `src/main/java/com/taskflow/web/Flash.java`

{{file:@reference/taskflow/backend/src/main/java/com/taskflow/web/Flash.java:java}}

```text
POST /tasks/new   → Flash.put("Task created.")      session: flash = "Task created."
                  → 303
GET  /tasks/view  → Flash.consume()                 session: (removed)   request: flash = "Task created."
                  → header.jspf shows ${flash}
GET  /tasks/view  (Reload) → nothing waiting        no message
```

The header shows it for every page:

```jsp
<c:if test="${not empty flash}"><p class="flash" role="status"><c:out value="${flash}"/></p></c:if>
```

- It's a **request** attribute when the view reads it: pages keep `session="false"` (33.10).
- It's escaped (`<c:out>`): some messages contain user text (a category's name, 37.15).
- `role="status"`: screen readers announce it.

## 3. Rules of thumb

- `Flash.consume` is called by **GET** controllers that render pages (list, view, categories), right before forwarding. A controller that forwards to a page without calling it won't show the message **yet**: it waits for the next page that does (37.18).
- One message at a time is enough here. Frameworks keep a map (`success`, `error`…).
- In a cluster, flashes need sticky sessions or a shared session store, like everything in the session (S38).

## ✅ Recap

A flash message is put in the session before the redirect, and moved into the request (and removed) by the next page: shown exactly once.
