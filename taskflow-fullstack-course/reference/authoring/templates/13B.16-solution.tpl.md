## 1. `src/components/ItemList.tsx`

{{file:@reference/snapshots/s13b-end/frontend/src/components/ItemList.tsx:tsx}}

### Decisions

- **`T extends HasId`** (06.02's `HasId`): the constraint is what lets `ItemList` write `key={item.id}`. Without it, `item.id` is an error: an unconstrained `T` has no known properties.
- **The list owns the key.** `renderItem` returns the *content* of one item; `ItemList` wraps it in `<Fragment key={item.id}>`. Callers can no longer forget the key or use the index (07.18). This is the main design win, not just a type exercise.
- **`<Fragment key>`**, not `<>`: the short syntax can't take a key.
- **`renderItem: (item: T) => ReactNode`**: `ReactNode`, not `JSX.Element`, so a caller may return a string or `null` (13B.01).
- **`if (items.length === 0) return empty;`**: a component can return any `ReactNode`, including whatever the caller passed (13B.01). No wrapper `<div>` is rendered for an empty list, which keeps `TaskList`'s old markup exactly.
- **`readonly T[]`**: accepts the `readonly Task[]` that `TaskList` and `Board` receive.

## 2. `TaskList.tsx` and `Board.tsx`

In `Board.tsx`, `BoardColumn`'s ternary becomes:

```tsx
<ItemList
  items={tasks}
  className={styles.cards}
  empty={<p className={styles.empty}>Nothing here.</p>}
  renderItem={(task) => <TaskCard task={task} onToggle={onToggle} onEditTitle={onEditTitle} />}

```

Hover `task` in either `renderItem`: it's `Task`, inferred from `items`. You never wrote `ItemList<Task>`.

## 3. Tests (`src/components/ItemList.test.tsx`)

{{file:@reference/snapshots/s13b-end/frontend/src/components/ItemList.test.tsx:tsx}}

- The first test uses **categories**, not tasks, on purpose: it proves the component is really generic.
- `items={[]}`: `T` is inferred as `never`, which satisfies `HasId`. The empty case still type-checks.
- The `@ts-expect-error` line proves the constraint: objects without an `id` are rejected at compile time.

## 4. Common wrong approaches

| Approach | Problem |
|---|---|
| `items: any[]` or `items: HasId[]` with `renderItem: (item: HasId) => …` | `renderItem` loses the real type: `item.title` becomes an error or an `any` |
| `function ItemList({ … }: ItemListProps<Task>)` | Not generic: it only works for tasks |
| `renderItem` returns an element **with** a key, and `ItemList` maps without one | The key rule moves back to every caller; forgetting it only warns at runtime |
| `const ItemList = <T extends HasId>(…) => …` in `.tsx` | Works (the `extends` disambiguates it from JSX), but plain `<T>` alone would not: see 13B.10 |
| `key={index}` inside `ItemList` | Breaks identity when items are reordered or deleted (07.11) |

## 5. Stretch: an `as` prop for the wrapper

`<ItemList as="ul" …>` with `<li>` items needs the polymorphic pattern from 13B.11. Try it, then ask whether it's worth the complexity: for a two-caller component, probably not.
