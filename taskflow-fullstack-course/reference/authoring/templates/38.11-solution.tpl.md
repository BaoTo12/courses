## Part A: the decisions

| # | Data | Scope | Why |
|---|---|---|---|
| 1 | list page tasks | request | computed per request, always fresh |
| 2 | form errors | request | shown by a forward in the same request (37.05) |
| 3 | CSRF token | session | per user, between the form's GET and its POST |
| 4 | "Task created." | session → request | survives one redirect, then consumed (flash, 37.09) |
| 5 | category list | application | identical for everyone, rarely changes, refreshed on change (38.06) |
| 6 | request count | application | global by definition, thread-safe counter (38.07) |
| 7 | `<c:forEach>` variable | page | only during the loop, in one JSP |
| 8 | logged-in user | session | per user across requests; non-secret fields only (38.09) |
| 9 | my last 5 tasks | session | per user; ids only |
| 10 | everyone's top 5 | application | shared; concurrent counters |
| 11 | language preference | **cookie** | must outlive the session and be read by the React app (`tf_lang`, S25/S44) |
| 12 | wizard draft | session (or the database) | per user, across steps. Small drafts in the session with a cleanup on finish/cancel; drafts worth keeping → a `drafts` table |

## Part B: recently viewed (session)

{{file:@reference/taskflow/backend/src/main/java/com/taskflow/web/RecentTasks.java:java}}

- `ids(request)` uses `getSession(false)`: reading history never creates a session.
- `record` copies, changes, and stores a **new** list (copy-on-write): a parallel request of the same user reads either the old or the new list, never one being modified.
- `updated.remove(Long.valueOf(taskId))`: `List` has **two** `remove` methods, `remove(int index)` and `remove(Object o)`. With an `int` id, `list.remove(id)` silently removes the element at **position** `id` (or throws). Boxing explicitly always removes the value.

In the list controller, the ids become tasks, fresh from the database:

```java
request.setAttribute("recentTasks", RecentTasks.ids(request).stream()          // S38: this user's last 5 (session)
    .map(service::task).flatMap(Optional::stream).toList());                  // deleted ones simply drop out
```

## Part B: most viewed (application)

`AppStats.taskViewed(id)` (38.07) with `computeIfAbsent` + `LongAdder`; `StatsServlet` resolves the top 5 ids to tasks.

### Wrong approaches

| Attempt | Problem |
|---|---|
| storing `Task` objects in the session history | stale titles, more memory, and `Task` must be `Serializable` |
| `session.getAttribute(…)` list, then `list.add(0, id)` in place | two tabs modify the same `ArrayList` concurrently |
| a `HashMap<Long, Integer>` with `put(get + 1)` in application scope | lost updates, and a corrupted map under load (38.12) |
| the history in application scope keyed by session id | reinvents the session, and leaks between users if the key is wrong |
