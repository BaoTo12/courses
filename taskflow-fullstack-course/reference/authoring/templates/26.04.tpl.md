# Lecture 26.04 · 🛡 Defend: Render as Text; if HTML Is Truly Needed, DOMPurify with a Strict Allow-List

> **Project feature:** comments are plain text by default. A "Show formatting" checkbox renders the **same** bodies as sanitised HTML (bold, lists, code, safe links).
> Verified: `src/security/security.test.tsx` ("sanitizeHtml": formatting kept; `onerror`, `<script>`, `style`, `onclick`, SVG tricks removed; `javascript:` links dropped; safe links forced to `target=_blank rel=noopener noreferrer`; jsdom), `tsc`, lint.

## 1. First choice: don't render HTML at all

The 26.03 fix that solves 95% of cases is **no fix at all**: `<p>{comment.body}</p>`. React escapes it, the payload shows as harmless text, and `white-space: pre-wrap` keeps line breaks. **Ask whether you really need HTML.** Often Markdown rendered to React elements (26.05's approach) or `<Trans>` (25.03) does the job without HTML strings.

## 2. When HTML is a requirement: sanitise with DOMPurify

```bash
npm install dompurify      # v3 ships its own types
```

✍️ `src/security/markup.ts`

{{file:security/markup.ts:ts}}

Why each choice:

| Setting | Why |
|---|---|
| **`ALLOWED_TAGS`** (an allow-list) | everything not listed is removed: `img`, `svg`, `iframe`, `form`, `style`, `script`, `math`… You never need to know every attack vector |
| **`ALLOWED_ATTR: ['href']`** | no `on*` handlers, no `style` (CSS attacks), no `src`, no `class` (overlaying our UI) |
| **`ALLOWED_URI_REGEXP`** | the same protocol allow-list as `safeHref` (26.06): `javascript:` and `data:` hrefs are dropped |
| **`afterSanitizeAttributes` hook** | policy on what survives: every link gets `target="_blank"` and `rel="noopener noreferrer"`, whatever the user wrote |
| **DOMPurify parses with the browser's parser** | it checks what the browser *will* build, not a regex's idea of HTML (mXSS, namespace confusion) |

## 5. Store raw, sanitise on output

The server keeps the body **exactly as typed** (`server.mjs`: "escaping is the job of whoever RENDERS it"). Sanitising **on output** means that:

- a sanitiser upgrade protects old data too;
- the JSP admin portal can apply its **own** encoding for its context (S43);
- nothing is lost if the policy is loosened later.

## 📇 API card: `DOMPurify.sanitize(dirty, config?)`

| Config | Meaning |
|---|---|
| `ALLOWED_TAGS` / `ALLOWED_ATTR` | replace the defaults (an allow-list) |
| `ADD_TAGS` / `ADD_ATTR` | extend the defaults |
| `FORBID_TAGS` / `FORBID_ATTR` | block-list on top (rarely needed with an allow-list) |
| `ALLOWED_URI_REGEXP` | which URLs `href`/`src` may have |
| `USE_PROFILES: { html: true }` | the default HTML profile (instead of explicit lists) |
| `RETURN_DOM` / `RETURN_DOM_FRAGMENT` | return nodes instead of a string |
| `RETURN_TRUSTED_TYPE` | integrate with Trusted Types (a CSP feature, S40) |

`DOMPurify.addHook(name, fn)` with `'uponSanitizeElement'`, `'afterSanitizeAttributes'`, … adjusts the result (TaskFlow's link policy). Hooks are **global** to the DOMPurify instance.

**When to use:** user-authored HTML must be displayed (rich-text editors, imported emails, CMS content).

**When not to:** plain text (use React's escaping), or Markdown (render to elements). Never as a replacement for escaping in server templates.

**Common mistakes:** sanitising and then modifying the string (26.14); sanitising on input only and trusting the database forever; a permissive profile "for now"; running DOMPurify on the server without a DOM (it needs `jsdom` there).
