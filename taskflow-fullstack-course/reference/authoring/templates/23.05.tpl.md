## 2. `patchTask`: optimistic toggle (and any other field)

- **Every cached list** is patched: `selectCachedArgsForQuery(getState(), 'getTasks')`. Then `getTask(id)` is patched too. For entries that don't exist, `updateQueryData` does nothing.
- **`Object.assign(task, changes)`** on the draft works for *any* PATCH: status, title, priority. The toggle thunk (22.09) and the inline title edit get the optimistic behaviour for free.
- **The recipe for `getTask`**: `(task) => void Object.assign(task, changes)`. The `void` matters. An Immer recipe may either mutate the draft **or** return a new value. `Object.assign` *returns* the draft, and returning a draft you also mutated is fine, but returning something else would replace the entry. `void` makes the intent explicit.
- **Rollback** is a `for … of patch.undo()` in `catch`. The **error toast** already exists: the listener on `patchTask.matchRejected` (22.09). The test checks that "Server error" appears.
- **On success**, `invalidatesTags` refetches the id's entries, so the server's version (e.g. its `updatedAt`) replaces our guess.

One card still re-renders per toggle. The patch creates a new object for the toggled task only, and Immer's structural sharing keeps the others identical (22.06).

## 3. `deleteTask`: optimistic removal

- Splice the item out of every cached page, and decrement `totalItems` so the pager stays right.
- On failure, `undo()` puts it back **at the same index**. Inverse patches restore array positions.
- On success, `{ Task, id }` + `TASK_LIST` are invalidated: the lists refetch, and `getTask(id)` is removed or refetched (§4).

### The toast lost its title, and got it back

The S22 listener read the title from `getOriginalState()`, the state just before `deleteTask/fulfilled`. With the optimistic removal, the task is **already gone** from the lists at that point, so the toast said "Deleted: Task 1". The fix is `selectCachedTask`, which falls back to the task's **own** entry, `getTask(id)`. The list seeded that entry (23.06):

✍️ in `src/features/tasks/taskSelectors.ts`:

```ts
/** A task from the main list, or else from its own `getTask(id)` entry (23.05). Not memoized: for effects, not for rendering. */
export const selectCachedTask = (state: RootState, id: number): Task | undefined =>
  selectTaskById(state, id) ?? apiSlice.endpoints.getTask.select(id)(state).data;
```

The test "the toast still has the title" pins it: `Deleted: Old notes`.

## 4. The details page: leave first, then delete

✍️ `src/pages/TaskDetailsPage.tsx`

{{file:pages/TaskDetailsPage.tsx:tsx}}

- `handleDelete` **navigates first**, then fires the mutation, without awaiting it. The list the user returns to already hides the task, thanks to the optimistic patch.
- The details page unmounts, so **`getTask(id)` loses its only subscriber**. When the DELETE succeeds and `{ Task, id }` is invalidated, an entry without subscribers is **removed, not refetched** (22.06). The test confirms that the requests are only `DELETE /tasks/1` and `GET /tasks`: the S22 `404` is gone.
- `if (deletion.isSuccess || deletion.isLoading) return null` is the safety net for the frame between the click and the navigation commit (router updates are transitions, 13.13).
- If the DELETE fails, the user is already on the list. The task reappears (`undo`), with an error toast. That's the optimistic trade-off: the user learns about the failure a moment later, in a different place.
- The priority `<select>` is 23.13's exercise. It's shown here because this is the file at the end of the section.
