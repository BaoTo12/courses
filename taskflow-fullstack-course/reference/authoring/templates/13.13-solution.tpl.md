## 1. `src/hooks/useTasks.ts` (complete)

{{file:hooks/useTasks.ts:ts}}

- **The hook owns the API calls.** Pages call `create`/`update`/`patch`/`remove`; they never call `api/tasks.ts` directly and then remember to dispatch. One place does both, so the list can't miss an update. This is exactly the job **thunks** take over in S18 (`dispatch(saveTask(…))`), so the shape will feel familiar.
- **The operations don't catch.** A hook can't know whether a failure deserves a toast, an inline message or silence. It lets the `ApiRequestError` propagate, and the page decides. (Catching and returning `undefined` here would recreate the 13.14 bug one layer higher.)
- **Every `useCallback` has `[]` dependencies.** `dispatch` from `useReducer` is stable, and the API functions are module imports. So the functions keep the same identity across renders.

## 2. `src/hooks/tasks-reducer.ts` (complete)

{{file:hooks/tasks-reducer.ts:ts}}

`taskToggled` and `titleEdited` are gone. The **server** now decides the new state, and the reducer records what the server returned (`taskUpdated`). ## 3. `src/pages/TasksPage.tsx` (complete)

{{file:pages/TasksPage.tsx:tsx}}

## 5. `src/pages/TaskDetailsPage.tsx`, and the flash of "Page not found"

{{file:pages/TaskDetailsPage.tsx:tsx}}

### The bug

The first version had `if (!task) return <NotFoundPage />;` and this handler:

```ts
await remove(current.id);                 // dispatch({ type: 'taskRemoved' }) inside
navigate(backHref, { replace: true });
```

I recorded the page's `<h1>` with a `MutationObserver`: **"Created through the API" → "Page not found" → "Tasks (22)"**. For a split second, the deleted task's page showed the 404 page.

### Why

Both updates happen in the same function, so you might expect React to batch them into one render. It doesn't, because they have **different priorities**:
- `dispatch(…)` is a normal, **urgent** update.
- React Router 8 wraps **all** its state updates in `React.startTransition` by default. This is documented on `BrowserRouter`'s `useTransitions` prop: when it's left undefined, every router state update is a transition.

Transitions are low priority, so React renders the urgent update **first**. At that moment the location is still `/tasks/26`, but task 26 is gone from the list, so the page renders the 404. Then the transition commits, and the list appears.

### Fixes considered

| Option | Verdict |
|---|---|
| `navigate` first, then `remove` | Same problem: the dispatch is still urgent and renders before the transition. |
| `<BrowserRouter useTransitions={false}>` | Works, but changes the whole app's navigation behaviour to fix one page. |
| **Remember that this page deleted the task:** `if (!task) return isDeleting ? null : <NotFoundPage />;` | ✅ Local, explicit, and it makes no timing assumptions. `isDeleting` stays `true` after a successful delete (it's only reset on failure), so the page renders nothing during the short gap. |

Verified after the fix: the `<h1>` sequence became **"Prepare 1:1 notes" → (none) → "Tasks (21)"**.

The general lesson: **when state and navigation change together, don't assume they render together.** Make every intermediate state render correctly.

### Other details

- `current` is a `const` copy of `task` for the async handler (05.07 §4): TypeScript knows it's a `Task` inside the closure.
- `window.confirm` is acceptable for a course project. A real app would use an accessible dialog component (with focus management), or an "Undo" toast instead of a confirmation.
- The Delete button is hidden from anonymous users, but the API is what enforces the rule. From S24, a `DELETE` without a session returns 401.

## 6. Stretch goals (guidance; not in the reference app)

**Per-card pending state.** In `TasksPage`, keep a set of the task ids that have a request in flight (`useState<ReadonlySet<number>>`). Add the id before `await patch(…)`, and remove it in `finally`. Pass an `isPending` prop through `TaskList`/`Board` to `TaskCard`'s button (`disabled`, `aria-busy`). Later, Redux Toolkit's `createAsyncThunk` gives you `pending`/`fulfilled`/`rejected` actions for exactly this (S20).

**Server field errors in the form.** `TaskForm` derives `errors` from the values (11.04). Add an optional `serverErrors?: TaskFormErrors` prop, merged in with lower priority than the client errors. In the page's `catch`, check `error instanceof ApiRequestError && error.status === 400`. Then keep only the keys of `TaskFormValues` from `error.fieldErrors` (validate them: the server could send any key), and pass them down. Clear a server error when its field changes.

## 7. Common wrong approaches

| Approach | Problem |
|---|---|
| Dispatch the local change, then call the API, ignoring failures | The UI shows changes the server rejected, and a reload "undoes" them. |
| `catch (e) { console.error(e) }` inside the `useTasks` operations | Callers think the save succeeded (13.14, one layer up). |
| Calling `api.patch` in the page and dispatching separately | Easy to forget the dispatch on one page, and the list goes stale. |
| `show({ message: error.response.data.message })` in a page | Crashes on network errors (`response` is `undefined`) and on proxy errors (`data` is `''`). The api layer normalises all of that. |
| Re-fetching the whole list after every change | Works, but costs a request and resets the scroll position. Dispatching the server's response is enough. |
