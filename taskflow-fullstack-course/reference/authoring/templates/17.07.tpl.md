## 2. ✍️ Selectors in `tasksSlice.ts` (append at the end)

```ts
import type { RootState } from '../../app/rootReducer';
// …
// ── Selectors (17.09): co-located with the slice that owns the state shape ────
export const selectTasksState = (state: RootState): TasksState => state.tasks;
export const selectTasks = (state: RootState): Task[] => state.tasks.items;
export const selectTasksStatus = (state: RootState): LoadStatus => state.tasks.status;
export const selectTaskById = (state: RootState, id: number): Task | undefined =>
  state.tasks.items.find((task) => task.id === id);
/** Returns a number (a primitive), so `useSelector` can compare it with === safely (17.04). */
export const selectOpenTaskCount = (state: RootState): number =>
  state.tasks.items.filter((task) => task.status !== 'DONE').length;
```

`import type { RootState }` creates a **type-only** cycle (`rootReducer` imports the slice; the slice imports the `RootState` type), which is erased at compile time.

## 3. ✍️ `src/features/tasks/task-operations.ts`

{{file:features/tasks/task-operations.ts:ts}}

(`clearCompleted` is the 17.13 exercise; write it then.)

- **`loadTasks(dispatch, signal)`** is a plain function taking `dispatch`. It dispatches three lifecycle actions around one API call, and **never throws**: a failure becomes `tasks/fetchFailed`, which the page renders. Look at its shape: a function that receives `dispatch` and does async work. S18 names that shape: a **thunk**.
- **`useTaskOperations()`** wraps the write operations for components. `useMemo(…, [dispatch])` returns a stable object, since `dispatch` never changes (17.05).
- Writes are still **pessimistic** (13.13): the store only changes after the server confirms.

## 4. ✍️ Load once: `src/layouts/AppLayout.tsx`

```tsx
const dispatch = useAppDispatch();

// Load the tasks once for the whole app (every page reads them from the store). S18: a thunk.
useEffect(() => {
  const controller = new AbortController();
  void loadTasks(dispatch, controller.signal);
  return () => controller.abort();
}, [dispatch]);
```

The layout is mounted for every page, so the tasks load once, whatever URL the user opens first. `void` marks the promise as intentionally not awaited. In the browser, the logger middleware (16.08) shows, verified:

```text
[redux] tasks/fetchStarted     ← StrictMode's first effect run (aborted before the request was sent, 13.09)
[redux] tasks/fetchStarted     ← the real run
[api] GET /tasks → 200 in 321 ms
[redux] tasks/fetchSucceeded
```

## 5. ✍️ Pages

### `TasksPage`: the whole slice

```tsx
// One selector for the whole slice: this page shows items, status AND error (17.04).
const { items, status, error } = useAppSelector(selectTasksState);
const { reload, patch } = useTaskOperations();
```

The rendering changes from a `switch` over `RequestState` (a discriminated union) to three conditions, because the slice keeps `items` **while** reloading (15.06):

```tsx
const hasData = status === 'succeeded' || items.length > 0;

if (status === 'failed' && items.length === 0) → error + "Try again"
else if (!hasData)                               → "Loading tasks…"
else                                             → the list (with " · refreshing…" in the title while loading again)
```

The full, final file is in the 17.14 solution.

### `TaskDetailsPage` and `EditTaskPage`: one task by id

```tsx
const id = parseTaskId(rawId);
// Hooks run before any early return (08.01): select with a possibly-null id.
const task = useAppSelector((state) => (id === null ? undefined : selectTaskById(state, id)));
const status = useAppSelector(selectTasksStatus);

if (id === null) return <NotFoundPage />;
if (!task && (status === 'idle' || status === 'loading')) return <p className="text-muted">Loading…</p>;
if (!task) return <NotFoundPage />;
```

- The selector returns an **existing** task object (or `undefined`), so the page re-renders only when **this** task changes, not when another task is edited.
- "Not found" is only decided once loading is finished: a direct load of `/tasks/2` shows "Loading…" first, then the task (verified).
- The details page keeps 13.13's `isDeleting` guard against the 404 flash after a delete. Verified again with the store: the `<h1>` went *title → (none) → "Tasks (22)"*.

### `NewTaskPage`, `DashboardPage`

`NewTaskPage` swaps `useTasksContext()` for `useTaskOperations()` (`create`). `DashboardPage` reads `useAppSelector(selectTasksState)` and groups `items`.
