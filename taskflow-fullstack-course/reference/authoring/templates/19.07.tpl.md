# Lecture 19.07 · Relationships: `task.categoryId` → Join in a Selector, Not in State

> **Section:** S19 · **Type:** 📖 Theory + 🛠 Build · **Track:** ★ Core · **Time:** ~30 minutes
> **Project feature:** every task card shows its category (name + colour), joined at render time
> Verified in the browser: the first three cards showed Work, Engineering, Team; renaming category 1 in the store changed **all 5** "Work" tags (and the sidebar) at once.

---

## 1. Store ids, join when reading

A task references its category by **id** (`categoryId: 1`). The category's name and colour live **once**, in `state.categories.entities[1]`. To show "Work" on a card, **join** the two when reading, in a selector or a small connected component. Never copy the category into the task.

It's exactly SQL's `JOIN`, done in memory:

```sql
SELECT t.*, c.name, c.color FROM tasks t LEFT JOIN categories c ON c.id = t.category_id
```

And in `TaskCard`, next to the priority bar:

```tsx
<TaskCategoryTag categoryId={task.categoryId} />
```

- **A tiny connected component** does the join: `TaskCard` stays presentational (it receives `task`), and the tag asks the store for its one category.
- `selectCategoryById` is an O(1) lookup that returns an **existing** object, so each tag re-renders only when **its** category changes (17.04).
- **Graceful gaps:** uncategorised tasks, or categories still loading, render nothing. No crash, no "undefined".
- `Tag` (10.10) validates the colour with `isSafeHexColor` before it reaches CSS: the category colour comes from the API, so it's untrusted.

## 3. Joined view models, when a list needs them

Sometimes a component needs the joined data **as a list** (a table with a "Category" column, an export). Then a memoised selector produces **view models**:

```ts
export interface TaskWithCategory {
  task: Task;
  category: Category | undefined;
}

export const selectTasksWithCategory = createSelector(
  [selectTasks, (state: RootState) => state.categories.entities],
  (tasks, categories): TaskWithCategory[] =>
    tasks.map((task) => ({ task, category: task.categoryId === null ? undefined : categories[task.categoryId] })),
);
```

The view-model objects are **new** on every recomputation, but memoisation means that happens only when the tasks or categories change. (Implementing and testing it is the knowledge-check exercise, 19.99.)

## 4. Why not store the joined data?

Store `{ ...task, categoryName: 'Work' }`, and:
- renaming a category must find and update **every** task that copied the name, or the UI shows both names (19.13's bug);
- the server doesn't send it that way, so you'd transform on every load;
- memory and serialisation grow with duplicated data.

Joins at read time are cheap (O(1) lookups) and always consistent.

## 5. Summary

- Relations are ids in state; joins happen when reading (selectors or small connected components).
- Lookups by id make joins cheap; memoised selectors make joined lists stable.
- Never store copies of related data.
