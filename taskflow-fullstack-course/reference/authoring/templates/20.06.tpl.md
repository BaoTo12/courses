## 0. The migration strategy: one slice at a time, tests green after each step

A big-bang rewrite of the store is how migrations fail. The Redux docs' migration guide recommends the opposite, and it works because RTK produces **ordinary reducers and actions**:

1. Replace `createStore` with `configureStore` (20.02). Nothing else changes; all tests pass.
2. Migrate one slice with `createSlice`, **keeping its action types and creator signatures**. The other hand-written slices, the thunks and the components don't notice.
3. Repeat per slice.
4. Replace hand-written thunks with `createAsyncThunk` (20.10), which changes action names on purpose.
5. Delete what's no longer needed (`AppAction`, the `as Reducer` cast, the hand-written `AppStore`).

Commit after each step.

Details worth a second look:

## 3. Step 3: `tasksSlice`, same events, less code

The tasks slice has more events. In this step you keep **every S19 action name and creator signature**, so `tasksThunks.ts` (S18) and the hand-written `ui` slice, which reacts to `tasks/taskDeleted`, keep working:

{{file:@reference/snapshots/s20-06-step1/tasksSlice.ts:ts}}

Walk through the differences from S19:

| S19 (hand-written) | Step 1 (`createSlice`) |
|---|---|
| `TasksAction` union written by hand, 8 members | **derived** from the generated creators: `ReturnType<(typeof tasksSlice.actions)[keyof typeof tasksSlice.actions]>` |
| creators with positional parameters | `prepare(requestId, tasks, fetchedAt = Date.now())`: the same signature |
| `withoutIds` rebuilding `entities` | `delete state.entities[id]` on the draft |
| `if (!state.entities[id]) return state;` | an `if` around the mutation: no mutation → Immer returns the same state |
| `allCompleted` rebuilding `entities` | `task.status = 'DONE'` on each open task's draft; DONE tasks keep their identity automatically |

### Why the derived `TasksAction` type matters in this step

`createSlice` types each generated action with a **literal** `type`: `taskDeleted(5)` is `{ type: 'tasks/taskDeleted'; payload: number }`, because `name` and the reducer key are literals. So the derived union is a discriminated union, exactly like the hand-written one, and `AppAction` (15.07) keeps compiling:

```ts
// app/app-action.ts during the migration: migrated slices contribute DERIVED types
export type AppAction =
  | TasksAction                                               // derived (below)
  | ReturnType<typeof sortChanged | typeof pageSizeChanged>   // listPrefs, derived
  | ReturnType<typeof loggedOut>                              // createAction
  | UiAction                                                  // still hand-written until 20.14
  | CategoriesAction;                                         // still hand-written until 20.14
```

The hand-written `ui` reducer's `case 'tasks/taskDeleted':` still narrows `action.payload` to `number`. (Verified: a function narrowing `TasksAction` on `'tasks/taskDeleted'` type-checks and returns `action.payload` as a `number`.)

The migrated `listPrefs` file doesn't export a hand-written union any more; derive its members the same way: `ReturnType<typeof sortChanged | typeof pageSizeChanged>`, and `ReturnType<typeof loggedOut>` for the auth event. `AppAction` itself is deleted in 20.15, once no hand-written reducer needs it.
