✍️ `web.xml`:

```xml
<context-param>
  <param-name>taskflow.cors.allowedOrigins</param-name>
  <param-value>http://localhost:5173</param-value>
</context-param>
…
<filter-mapping><filter-name>cors</filter-name><url-pattern>/api/*</url-pattern></filter-mapping>
<filter-mapping><filter-name>api</filter-name><url-pattern>/api/*</url-pattern></filter-mapping>
```

| Decision | Why |
|---|---|
| **exact** string match against a set | no suffix, prefix or regex tricks (47.09) |
| the origin echoed only when listed | the only way to combine a specific origin with credentials |
| `Vary: Origin` always | a cache (a CDN, a proxy) mustn't serve one origin's answer to another |
| the preflight answered **here** | it carries no cookies and no CSRF header by design: letting it reach authentication gives 401, and the browser cancels the real request (47.16) |
| before `api` | headers are set before the chain, so 401/403/404 JSON is readable by the allowed SPA |
| configuration, not code | production lists the real SPA origin, or nothing at all when both are served from one origin (47.11, S49) |

Not added (the SPA doesn't need them yet): `Access-Control-Expose-Headers: Location, X-Request-Id`, which would let the SPA read those headers cross-origin.

## ✅ Checkpoint

```bash
curl -i -X OPTIONS -H "Origin: http://localhost:5173" -H "Access-Control-Request-Method: PATCH" http://localhost:8080/taskflow/api/tasks/1
```

→ 204 with the four `Access-Control-*` headers. With `Origin: https://evil.example` → 403, none.
