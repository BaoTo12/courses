# Lecture 19.09 · 🛠 Build: "Save, Then Redirect to Details", and Server Errors in the Form

> **Section:** S19 · **Type:** 🛠 Build · **Track:** ★ Core · **Time:** ~60 minutes
> **Project feature:** errors only the server can detect (a duplicate title) appear under the form field, not in a toast
> Verified in the browser: creating "write quarterly REPORT" (an existing title, different case) → the form stayed open, the Title field showed *"A task with this title already exists."* with `aria-invalid="true"`, and no toast appeared. Typing in the field removed the error.

---

## 1. A rule only the server can check

Client validation (11.04) catches what the client **can** know: required fields, lengths, date formats. Some rules need data the client doesn't have, or can't trust:
- "The title must be unique among **your** tasks": another tab or device may have created a task a second ago.
- "This category doesn't exist any more."
- "You don't have permission to move this task."

The mock API now enforces the first one (`provided/mock-api/server.mjs`; added to the API contract in `02-project-spec.md` §5):

```http
POST /api/tasks  {"title": "  write QUARTERLY report ", …}
→ 400 {"error": "VALIDATION_FAILED", "message": "Request contains invalid fields",
       "fieldErrors": {"title": "a task with this title already exists"}, …}
```

Verified with curl: duplicates are detected case-insensitively and ignoring surrounding spaces, on create **and** rename (PATCH/PUT), and a task may keep its own title. Update your copy of the mock (and restart it) to follow along.

## 2. The contract between page and form

The form must show server errors **where the user is looking**: under the field, not in a toast that disappears after 4 seconds. The design:

1. `TaskForm`'s `onSubmit` may **resolve with field errors**. The page decides whether a failure is "field-level" (400 with `fieldErrors`) or global (toast).
2. `TaskForm` keeps server errors in **state** (unlike client errors, they aren't derived from the values: they come from a response), shows them under the fields, and **clears a field's error when the user edits that field** (the server hasn't judged the new value).

## 3. ✍️ `pickFormErrors` (in `src/domain/task-form.ts`)

```ts
const FORM_FIELDS: readonly (keyof TaskFormValues)[] = ['title', 'description', 'status', 'priority', 'dueDate'];

/**
 * Server field errors (a 400's `fieldErrors`, 13.07) → form errors (19.09).
 * Keeps only keys the form knows: the server's object is untrusted input and may contain anything.
 */
export function pickFormErrors(fieldErrors: Readonly<Record<string, string>>): TaskFormErrors {
  const errors: TaskFormErrors = {};
  for (const field of FORM_FIELDS) {
    const message = fieldErrors[field];
    if (message) errors[field] = message.charAt(0).toUpperCase() + message.slice(1) + '.';
  }
  return errors;
}
```

Tested: `{ title: '…', ownerId: 'nope', categoryId: 'x' }` → only `title`, formatted as a sentence.

## 6. Accessibility, for free

`FormField` (11.07) already wires `error` to `aria-invalid` and `aria-describedby`. Server errors travel through the same prop, so screen readers announce them exactly like client errors. Verified: `aria-invalid="true"` after the failed submit, `"false"` after editing.

## 7. Summary

- Some rules only the server can check; its 400 `fieldErrors` belong under the fields.
- The page maps errors (`pickFormErrors`, allowlisting the keys); the form stores them and clears each on edit.
- Other failures (network, 5xx) still go to a toast.
