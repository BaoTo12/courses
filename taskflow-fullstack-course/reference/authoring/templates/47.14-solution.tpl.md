## 2. Why the exception for `/me`

A monitoring rule like "alert on more than 50 `ACCESS_DENIED` per minute" is useless if every visitor's first request adds one. The exception is narrow: `GET`, `401`, that exact path. A `403` on `/me`, or a 401 anywhere else, is still logged.

## 3. What a row looks like

```text
type=ACCESS_DENIED  username=bob  ip=127.0.0.1
details=403 CSRF_TOKEN_INVALID DELETE /api/tasks/23 [request 8c1d0e5b7f3a2291]
```

`/admin/audit?type=ACCESS_DENIED&user=bob` (45.10) shows them; the request id finds the matching lines in the application log.

### Wrong approaches

| Attempt | Problem |
|---|---|
| auditing in each filter and servlet | three copies, and the next 403 source is forgotten |
| `MDC.get("requestId")` | works here (we're inside the logging filter), but the request attribute also works on error dispatches and async threads (43.12) |
| logging the request body or headers "for context" | may contain passwords (the login body) or tokens (43.11) |
| a new event type per code | the audit page's filter is by type; `ACCESS_DENIED` + the code in `details` keeps queries simple |
