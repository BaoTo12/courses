# Lecture 41.06 · 🛡 Password Storage: Why Hashing, Why **Slow** Hashing (BCrypt), Salts

> **Section:** S41 · **Type:** 🛡 Defend · **Track:** ★ Core · **Time:** ~30 minutes
> Verified: `SeedDataTest.demoPasswordsMatchTheirHashes` (S28's seed hashes), and every login in the test suite

---

## 1. Why not store passwords

A database gets copied, backed up, leaked. Stored passwords would be usable immediately, on TaskFlow **and** on every other site where people reuse them.

## 2. Why not a fast hash

`SHA-256("alice123")` can't be reversed, but it can be **guessed**: a GPU computes billions of SHA-256 per second. The same password always gives the same hash, so one precomputed table cracks every user with a common password at once.

| Problem | Fix |
|---|---|
| identical passwords → identical hashes; precomputed tables | a random **salt** per password, stored with the hash |
| fast to compute → fast to guess | a **slow**, tunable hash: BCrypt (cost factor), scrypt, Argon2, PBKDF2 |

## 3. BCrypt's format

```text
$2a$12$oBJehHL5IKGFtEJ6oSSbnukwArGKvDnY7XMcjrHk4ztBXI91vcn62
 │   │  └──── 22 chars: salt ─────┘└──────── 31 chars: hash ─────┘
 │   └ cost 12 = 2^12 rounds (~0.25 s on a laptop)
 └ algorithm version
```

Everything needed to verify is in the string: `checkpw` reads the salt and the cost from it. Raising the cost later only affects new hashes, and you can re-hash at the next successful login.

## 4. TaskFlow's `PasswordHasher` (📦 provided)

{{file:@reference/taskflow/backend/src/main/java/com/taskflow/security/PasswordHasher.java:java}}

| Method | Use |
|---|---|
| `hash(password)` | creating or changing a password (not needed in TaskFlow yet: the seed has hashes) |
| `matches(password, storedHash)` | the login check. A malformed stored hash → `false`, not a 500 |
| `burnTime(password)` | for an **unknown** username: the same ~0.25 s of work, so response times don't tell attackers which usernames exist (41.14) |

**Cost:** each login takes about a quarter of a second of CPU, on purpose. That's also why throttling matters (41.15): without it, an attacker can make your server spend CPU on BCrypt.

## ✅ Recap

Store salted, slow hashes, never passwords. BCrypt packs the algorithm, the cost and the salt into the stored string, and `checkpw` does the rest.
