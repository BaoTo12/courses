# Lecture 21.15 · 🛠 Build: a Toast Whenever a Task Is Saved, and a Debounced, Cancellable Quick Find

> **Section:** S21 · **Type:** 🛠 Build · **Track:** ★ Core · **Time:** ~90 minutes
> **Project feature:** a listener shows "Created: …" / "Saved: …" for every save; a **Quick find** box in the header searches all tasks on the server, 300 ms after the last keystroke, aborting stale requests.
> Verified: `src/features/search/quickFind.test.ts` (4 tests: debounce, abort, errors, save toasts), `tsc`, lint. In the browser: typing *f, l, a, k, y* one key at a time dispatched 6 `quickFind/quickFindChanged` actions (with the clear) and sent **one** request, `GET /api/tasks?q=flaky&size=5`; *"report"* showed *"Write quarterly report · In progress"*; saving task 3 showed the toast *"Saved: Plan team offsite"* from the listener.

## 2. The save toast

✍️ `src/features/tasks/taskListeners.ts`

{{file:features/tasks/taskListeners.ts:ts}}

Then **remove** the success toasts from the pages: `NewTaskPage` and `EditTaskPage` keep only navigation and error handling:

```ts
      const saved = await dispatch(saveTask({ id: existing.id, request: toCreateRequest(values, existing.categoryId) })).unwrap();
      // The success toast comes from a listener (21.15): this page only decides where to go next.
      navigate(`/tasks/${saved.id}`, { replace: true, state: location.state });
```

Why a listener here: "saved → tell the user" is a **reaction** that should happen however a task gets saved. The pages still use `unwrap()` because **they** need the result (to navigate, or to show field errors): that's a thunk's job (21.16).

## 3. Quick find: the slice

✍️ `src/features/search/quickFindSlice.ts`

{{file:features/search/quickFindSlice.ts:ts}}

- A **separate slice**: search results are not "the task list"; putting them in `tasks` would change the list page, the counts and the dashboard.
- `quickFindChanged` is an **event per keystroke**. The reducer only records the text and whether a search is pending; it doesn't decide when to fetch.
- `quickFindSucceeded` ignores answers to an older query, a second safety net besides the abort.
- Add it to `rootReducer.ts` as `quickFind: quickFindReducer`.

## 4. Quick find: the listener

✍️ `src/features/search/quickFindListener.ts`

{{file:features/search/quickFindListener.ts:ts}}

Follow one fast typist, `r`, `e`, `p` (100 ms apart):

1. `r` → effect #1 starts, cancels nothing, returns (shorter than 2 characters).
2. `re` → effect #2: `cancelActiveListeners()` (nothing running), `delay(300)` starts.
3. `rep` (100 ms later) → effect #3 cancels #2: #2's `delay` **rejects**, and #2 stops silently. #3 waits 300 ms and sends `q=rep`.
4. If the user types `o` **while** `rep`'s request is in flight, #4 cancels #3, whose `signal` aborts the Axios request (verified in the test *"a newer keystroke ABORTS the request already in flight"*). The `catch` sees `signal.aborted` and returns without an error.

## 6. The tests

{{file:features/search/quickFind.test.ts:ts}}

- **Fake timers** (`vi.useFakeTimers()` + `advanceTimersByTimeAsync`) make the 300 ms debounce instant and deterministic.
- The abort test uses a fake `getTasks` that never answers on its own: only an abort ends it. That proves the **signal** is wired, not just that a late answer is ignored.
- The save-toast test dispatches `fulfilled` actions directly: listeners react to actions, however they were produced.
