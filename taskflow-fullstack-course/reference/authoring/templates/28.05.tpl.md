## 2. `<packaging>war</packaging>` and `<finalName>`

- `war` makes `mvn package` produce `target/taskflow.war` instead of a JAR, using the `maven-war-plugin`.
- `finalName` = `taskflow`, so the file is `taskflow.war`, and Tomcat deploys it at **`/taskflow`** (28.10). Without it: `taskflow-backend-1.0.0-SNAPSHOT.war` → `/taskflow-backend-1.0.0-SNAPSHOT`.

## 3. Scopes: who supplies the class at runtime?

| Scope | On the compile classpath | In `WEB-INF/lib` | Use for |
|---|---|---|---|
| `compile` (default) | ✅ | ✅ | libraries the container **doesn't** have: JSTL, the MySQL driver, HikariCP, Jackson, Logback |
| **`provided`** | ✅ | ❌ | APIs the **container** supplies: `servlet-api`, `jsp-api` (in Tomcat's `lib/`). (The pom shown is the current one: `el-api` was removed in S32, see 32.16.) |
| `test` | tests only | ❌ | JUnit |
| `runtime` | ❌ | ✅ | needed only at runtime (a JDBC driver loaded by name could be this) |

**Why `servlet-api` must be `provided`:** Tomcat already has `javax.servlet.*` in `lib/servlet-api.jar`. A second copy in `WEB-INF/lib` is at best dead weight: the Servlet spec requires containers to load `javax.servlet.*` from **their own** copy, and Tomcat's web-app class loader always delegates those packages to its parent. At worst, with a different API version or another container, two versions of `Servlet` from two class loaders give you `ClassCastException: MyServlet cannot be cast to javax.servlet.Servlet`, or `NoSuchMethodError`. **Compile against it, never ship it.**

**Why JSTL must be bundled for Tomcat 9:** Tomcat implements Servlet, JSP and EL, but **not JSTL** (that's a full Java EE server's job, e.g. GlassFish). Mark it `provided` and every `<c:forEach>` fails at runtime ("The absolute uri: http://java.sun.com/jsp/jstl/core cannot be resolved", S35). `javax.servlet:jstl:1.2` contains both the API and the implementation. It's the `javax` version, and must not be the Jakarta JSTL 2/3 (28.02).

## 4. A real conflict, fixed in this pom: dependency mediation

`mvn dependency:tree` without the explicit `slf4j-api` entry showed:

```text
+- com.zaxxer:HikariCP:jar:5.1.0:compile
|  \- org.slf4j:slf4j-api:jar:1.7.36:compile      ← chosen
+- ch.qos.logback:logback-classic:jar:1.5.6:compile
   (wants slf4j-api 2.0.x: omitted for conflict)
```

- Maven picks **one** version per artifact: the **nearest** in the tree, and on a tie, the **first declared**. Both were at depth 2, and HikariCP comes first, so 1.7.36 won.
- SLF4J 1.7 can't find Logback 1.5 (which is written for SLF4J 2's provider mechanism). Logging would silently go nowhere, from S43 onward.
- **Fix:** declare `slf4j-api` 2.0.13 directly, at depth 1, so it's nearest. The WAR now contains `slf4j-api-2.0.13.jar` (28.04 §2).

The habit: after adding dependencies, run `mvn dependency:tree` and look for `omitted for conflict`.

## 5. `maven.compiler.release` = 17

`release` compiles **for** Java 17 whatever JDK runs Maven (the course machine had JDK 21). Unlike `source`/`target`, it also checks that you only use Java 17 **APIs**: `List.reversed()` (Java 21) is a compile error.

## 6. Everyday commands

```bash
mvn package             # compile, test, build target/taskflow.war
mvn -DskipTests package # when you're iterating on JSPs (don't make it a habit)
mvn test                # tests only
mvn dependency:tree     # who brings what (§4)
mvn clean               # delete target/
```
