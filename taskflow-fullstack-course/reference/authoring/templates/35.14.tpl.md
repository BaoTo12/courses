# Lecture 35.14 · 🔓 Lab: Stored XSS in Task Comments

> **Section:** S35 · **Type:** 🔓 Attack Lab · **Track:** ★ Core · **Time:** ~35 minutes
> ⚠️ Local only, in a lab branch. The defended version is checked by `S35JstlTest.storedXssInACommentIsRenderedAsText`.

---

## 0. 📦 Provided: comments

`model/Comment` (a JavaBean), `store/InMemoryCommentStore` (seeded with the three comments of `db/03-seed.sql`) and the servlet that saves them:

📦 `src/main/java/com/taskflow/web/tasks/TaskCommentServlet.java`

{{file:@reference/taskflow/backend/src/main/java/com/taskflow/web/tasks/TaskCommentServlet.java:java}}

It validates the **shape** (present, not blank, ≤ 1000 characters) and stores the body **exactly as typed**, HTML included. That's deliberate (35.15). The details page gets a form (`<textarea name="body">`) and the comment list (you build it properly in 35.18).

## 1. The vulnerable display (lab branch)

The quick first version of the list:

```jsp
<c:forEach items="${details.comments}" var="item">
  <li><strong>${item.author.displayName}</strong>: ${item.comment.body}</li>
</c:forEach>
```

JSTL for the loop, but plain EL for the text. EL doesn't escape (34.18).

## 2. The exploit

1. Open task 1 (`/taskflow/tasks/view?id=1`) and post this comment:

   ```html
   Looks good! <img src=x onerror="fetch('/taskflow/tasks/delete',{method:'POST',headers:{'Content-Type':'application/x-www-form-urlencoded'},body:'id=2'})">
   ```

2. The page reloads: "Looks good!" and a broken image. Nothing seems wrong.
3. Open `/taskflow/tasks`: **task 2 is gone**. The comment's `onerror` handler ran in **your** browser, with **your** cookies, and posted a delete.
4. Every future visitor to task 1, and in S38 that means every **admin**, runs it again. One request by the attacker, executed forever, for everybody. That's **stored** (persistent) XSS.

Compared with reflected XSS (30.19, 34.18):

| | Reflected | Stored |
|---|---|---|
| payload lives in | the URL | the database |
| victim must | click a crafted link | just open a normal page |
| reach | whoever clicks | everyone who views it, including admins |

What an attacker could do instead of deleting a task: read the CSRF token from the page and do any action as the victim (S42's CSRF defence doesn't stop XSS: the script runs on your origin); rewrite the page into a fake login form; send data it can read to another server. `JSESSIONID` is `HttpOnly` (28.04), so it can't be read by `document.cookie`, but it doesn't need to be: the script already acts **as** the user.

## 3. Why it works

Data from user A is inserted into the HTML for user B as **markup**. The browser can't tell the page's own `<img>` from a comment's `<img>`.

## 4. Fix

35.15: `<c:out value="${item.comment.body}"/>`.

## Lesson

Anything that one user writes and another user sees is a stored-XSS candidate: comments, titles, names, descriptions, file names, and even log entries shown in an admin UI.
