## 1. The whole idea

> If the dispatched value is a **function**, call it with `(dispatch, getState, extra)` and return what it returns. Otherwise, pass it on.

That's all the thunk middleware does.

## 2. ✍️ `src/app/mini-redux/thunk-middleware.ts`

{{file:app/mini-redux/thunk-middleware.ts:ts}}

Line by line:
- **The middleware shape** from 16.07: `({ dispatch, getState }) => (next) => (action) => …`. It destructures `dispatch` and `getState` from `storeAPI`.
- **`typeof action === 'function'`**: in Redux 5, `action` is typed `unknown` (16.07 §4), so this check also narrows the type.
- **`action(dispatch, getState, extra)`**: the `dispatch` passed to the thunk is `storeAPI.dispatch`, which runs through the **whole** chain (16.09 §3). When the thunk dispatches a plain action, the crash reporter, the logger and the analytics middleware all see it. When it dispatches **another thunk**, the thunk middleware handles that one too. Thunks can compose.
- **`return action(…)`**: the thunk's return value becomes `dispatch`'s return value. That's why `await dispatch(saveNewTask(request))` gives you the created task (18.07). A middleware that forgets to return breaks exactly this (16.15).
- **`return next(action)`** for everything else: plain actions continue unchanged.
- **`extra`**: a value given when the middleware is created, passed to every thunk. TaskFlow injects its API layer through it (18.04).

## 3. ✍️ Test it against the real package (`src/features/tasks/tasksThunks.test.ts`)

```ts
describe('thunk middleware (18.03)', () => {
  it('ours and redux-thunk both call functions with (dispatch, getState, extra) and return their result', () => {
    for (const middleware of [createMiniThunkMiddleware('EXTRA'), withExtraArgument('EXTRA')]) {
      const store = createStore(rootReducer, applyMiddleware(middleware));
      const seen: unknown[] = [];
      const result = store.dispatch(((dispatch: unknown, getState: () => unknown, extra: unknown) => {
        seen.push(typeof dispatch, typeof getState, extra);
        return 'returned by the thunk';
      }) as never);
      expect(result).toBe('returned by the thunk');
      expect(seen).toEqual(['function', 'function', 'EXTRA']);
    }
  });

  it('18.14: without thunk middleware, dispatching a function throws "Actions must be plain objects"', () => {
    const store = createStore(rootReducer);
    expect(() => store.dispatch((() => {}) as never)).toThrow(/Actions must be plain objects/);
  });
});
```

Install the package first (`npm install redux-thunk`; this installs **3.1.0**). `as never` is needed because a plain `Store`'s `dispatch` type accepts only actions. 18.08 fixes the types properly.

## 4. Where the thunk middleware goes in the chain

In `store.ts` (full file in 18.06): crash reporter **first** (it catches errors thrown by thunks too), then the thunk middleware, then the logger and analytics:

```ts
const middleware: Middleware[] = [
  createCrashReporter(…),
  withExtraArgument(extra), // thunks: functions are called here and never reach the logger (18.03)
];
```

Placing the thunk middleware **before** the logger means the logger only ever sees plain actions. Placed after, the logger's `isAction` check would skip functions anyway (16.08), but other middleware might not be so careful. RTK's defaults put it near the front for the same reason.

## 5. Summary

- The thunk middleware: "function? call it with (dispatch, getState, extra) and return its result; otherwise next(action)."
- The `dispatch` a thunk receives goes through the whole chain; thunks can dispatch thunks.
- `dispatch(thunk)` returns what the thunk returns (often a promise).
