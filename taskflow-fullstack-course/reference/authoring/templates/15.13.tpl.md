## 1. `src/features/listPrefs/listPrefsSlice.ts`

{{file:features/listPrefs/listPrefsSlice.ts:ts}}

- **`PAGE_SIZES` as a value, `PageSize` derived from it** (06.05): the same list can later render the page-size `<select>`.
- **"No change → same reference"** is checked explicitly. Without it, `sortChanged` with the current values would create a new `listPrefs` object and a new root state, and every subscriber would re-check for nothing. Verified by the root test "returns the SAME root object when no slice changed".
- Creators return `ListPrefsAction` (the whole union) rather than the precise member. That's enough when callers only dispatch them. `tasksSlice` shows the precise `Extract` style; both are fine.

## 2. `src/features/ui/uiSlice.ts`

{{file:features/ui/uiSlice.ts:ts}}

- **The id counter lives in the action creator.** Reducers stay deterministic; creators may be impure (15.04). In S18, thunks will create toasts, and the counter moves nowhere: it stays in the creator.
- **Cross-slice cases are grouped** under a comment, so readers can see this slice reacts to foreign events.
- **`removeFromSelection` returns the same state** when nothing was selected. Most deletions don't touch the selection, so this saves a re-render of the selection toolbar almost every time.
- `selectionCleared` on an empty selection also returns `state` (tested).

## 3. `src/features/tasks/tasksSlice.ts` (final for S15)

{{file:features/tasks/tasksSlice.ts:ts}}

- **`allCompleted` carries `updatedAt`.** The creator defaults it to "now" (`new Date().toISOString()`), and tests pass a fixed value. In S18, the thunk will pass the server's timestamp instead.
- **Tasks already DONE keep their identity** (`task.status === 'DONE' ? task : …`): only changed tasks get new objects.
- **`new Set(action.payload)` inside the reducer** is fine: it's a local helper for fast lookups, not state. Only what's **returned** must be serialisable.

### About `error` after `fetchSucceeded`

The test "tracks the fetch lifecycle" pins down a subtle behaviour: `fetchFailed('Boom')` then `fetchSucceeded([…])` leaves `error: 'Boom'`. It doesn't matter in practice, because `fetchStarted` always runs first and clears it. But a reducer that relies on the **order** of other events is fragile. A clearer rule is "every terminal event sets both fields": `fetchSucceeded` → `error: null`. Change it if you agree, and update the test: that's what tests are for. (RTK's `createAsyncThunk` pattern in S20 resets the error on `pending`, same as ours.)

- **`[first, second].reduce(uiReducer, initialState)`**: a reducer really is an `Array.prototype.reduce` callback (14.07 §3). Replaying a list of actions is one line.
- **Store-level tests** use a real `createStore(rootReducer)`. They check the wiring (every slice registered, cross-slice events reaching their reducers), which unit tests of single reducers can't.
- The `ui/toastShown` test narrows with `type ===` before reading `payload.id`, because the creator returns the union type `UiAction`. With precise creator types (the `Extract` style), that narrowing wouldn't be needed. That's one argument for the tasks-slice style.

## 6. Common wrong approaches

| Approach | Problem |
|---|---|
| `id: Date.now()` or `crypto.randomUUID()` in the `toastShown` **reducer** | Non-deterministic reducer: replays and tests produce different ids. |
| `selectedTaskIds: new Set<number>()` | Not serialisable: DevTools show `{}`, and `JSON.stringify` loses it. |
| `completedCleared` with no payload, and `ui` "figuring out" the ids | `ui` doesn't have the tasks; it would need to read another slice's state, which reducers can't. |
| `tasksReducer` removing ids from `state.ui` | A slice reducer only sees its own slice. Cross-slice effects go through events. |
| Forgetting `auth/loggedOut` in `listPrefs` | The next user inherits the previous user's preferences (harmless here, but the habit leaks real data elsewhere). |
| No "same reference" checks | Correct values, but every no-op event creates new objects, and every subscriber re-renders. |
