# Lecture 46.09 · 🛡 Response DTOs: Never Serialise Entities

> **Section:** S46 · **Type:** 🛡 Defend · **Track:** ★ Core · **Time:** ~20 minutes
> Verified: `S46JsonApiTest` (the exact field sets of tasks, comments and categories)

---

## 1. The temptation

```java
Json.write(response, 200, task);         // ❌ the JPA entity itself
```

It works today. Then:
- someone maps `password_hash` on `User` "for the login", and every response containing a user leaks it;
- an entity gains an internal field (`deletedBy`, `riskScore`), and it's public;
- a lazy relation (`task.getOwner()`) is serialised: an extra query per item, or an exception outside the transaction, or an infinite loop (`task → owner → tasks → owner…`);
- renaming a Java field silently breaks the React app.

OWASP calls the first two **excessive data exposure**.

## 2. DTOs: the contract as types

✍️ `src/main/java/com/taskflow/web/api/dto/Dtos.java`

{{file:@reference/taskflow/backend/src/main/java/com/taskflow/web/api/dto/Dtos.java:java}}

| DTO | Mirrors (frontend `src/domain/types.ts`) | Deliberately without |
|---|---|---|
| `TaskDto` | `Task` | nothing internal exists yet: the point is that future fields must be **added** here to be exposed |
| `UserDto` | `User` | email, password hash, `enabled`, `created_at` |
| `CommentDto`, `CategoryDto` | `Comment`, `Category` | |
| `PageDto<T>` | `Page<T>` | the service's 1-based numbering |

## 3. Costs

Mapping code by hand (a line per field). Libraries (MapStruct) generate it. The benefit is that **exposing** a field is a decision someone makes in one file, and a reviewer sees it.

## ✅ Recap

Entities are for persistence; DTOs are the API's contract. Map explicitly, so nothing is exposed by accident.
